# Operate all eight managed Agents in their owned journeys

## Problem statement

Reviewed template definitions, qualified credential plumbing and separate Workflow plans do not mean that a
managed Team can actually do engineering work. EPIC-00014 requires **all eight managed roles** to produce
real authorized outcomes, with this Agent/Team integration supplying their missing identity, membership,
credential and current-use seams; a first Explorer demonstration alone cannot close the EPIC.

## Solution and boundaries

First register Fight Agent OS as a Repository with a designated checkout and versioned context, establish a
Team, create its distinct Explorer and manually launch bounded authenticated Pi Harness exploration of that
checkout. Return source-cited findings and uncertainty. The first Explorer is never unassigned, never a
standalone disposable test identity, and does not wait for the Planning database cutover, complete browser
conversation or TASK Workflow. Then use a real Project Manager through the authorized human-governed browser
Planning journey; a model never approves its own Planning proposal.

Integrate the reusable TICKET-00059–64 Agent/Team boundary with the **existing owners' actual paths** so
Team Lead and distinct Software Engineer bring one human-selected TASK to durable Awaiting review; a
non-contributing same-Team Senior Engineer independently reviews; QA Engineer exercises changed behavior
where applicable; Release Manager verifies and publishes the accepted PR for human review, and follows
qualified project-specific library/application release paths when applicable with actual runbooks, signing
and health evidence. Hotfix Engineer follows a confirmed direct emergency route with a separate
non-contributing reviewer and controlled human PR handoff. The separately approved Triage Agent routes a
human-selected TASK through current eligibility and one authoritative start. Use all eight managed roles
under their own current grants rather than rename one credential or count planned screens as work.

This TICKET **coordinates actual integration and working outcomes**, not a duplicate Planning database,
conversation, Runner, claim, review/QA acceptance, hotfix, release or deployment engine. Each owned Workflow
and project-specific effect retains its established authorization, human decisions and evidence standards.
A release PR is not a tagged published library or a deployed application. If a required real target,
provider, independent reviewer, context, grant or Workflow does not exist, that role's outcome remains
unaccepted; do not substitute a synthetic harness, seeded data or another EPIC's historical `done` receipt.

## Validation and permissions

Require each real Agent's distinct Team membership, template/profile/context revision, holder credential,
current eligible direct Permissions and tool/grant scope at use; the initiating human retains their own
decisions. The one Team remains authoritative for subsequent delegation; reviewer/QA independence and
Hotfix/Release effect permissions cannot follow a template title. Reject stale claims, unavailable sandbox,
wrong Repository/base, uncertain delivery and unqualified release targets. Record provider/model and session
lineage without secrets. Manual Harness use is not an exemption from HMAC, broker, origin and host policy.

## Acceptance and evidence

- A real Team-assigned Explorer investigates Fight Agent OS through authenticated tools and returns bounded
  cited findings; a real Project Manager participates in human-governed Planning on its product path.
- Each of the other six roles performs its **intended** authorized path, including independent review/QA,
  actual controlled PR publication, confirmed hotfix and qualified project-specific release/deployment effects
  where required by EPIC-00014. Triage uses the authoritative human-selected TASK start, not autopick.
- Record for every role its stable Agent/Team/Repository/template and credential operation/delivery/activation/
  continuing-use identities, actual session/Workflow, tools/grants, distinct outcome and redacted provenance.
  Missing evidence or a blocked owner remains explicit, not a claim of complete Team operation.
- Verify actual handoffs and safe denial/recovery with owned product behavior checks, real consumer tools and
  `./bin/build`, without creating a separate per-template certification ritual or proof-only test product.
