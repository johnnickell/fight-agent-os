# Deploy and recover private Fight Agent OS in staging and production

## Destination

John can deploy, operate and recover a private Fight Agent OS installation in isolated staging and production,
supporting the first useful **database-backed browser Wayfinder journey with each initiating user's protected
OpenRouter connection**. Supply the production artifact, environment integration and operator-run promotion/
recovery path missing from the existing local installation requirements. This is an actual usable deployment
outcome, not a runbook-only demonstration, a readiness framework or a second deployment orchestration product.

Reuse the existing owners of authentication, Planning, provider connections, conversations, usage, migration,
mail, storage and diagnosis. This EPIC owns their Fight-specific deployment composition and operations, not
replacement implementations or unqualified claims about their readiness. Actual first deployment and recovery
verification occur only under the applicable later target, spending, migration and effect approvals.

The [private production rollout map](../wayfinder/private-production-rollout-map.md#approved-first-production-planning-handoff)
records the approved source decisions. John explicitly confirmed this EPIC's destination, inclusions, exclusions
and existing-owner boundaries after the map handoff. The map stays Closed; its research is not runtime acceptance.

## Decisions and exclusions

### Selected environments and small initial footprint

- Production is `https://fight-agent.dev`; staging is `https://staging.fight-agent.dev`. Begin with John and retain
  private household expansion, not public registration or a commercial hosting product.
- Use separate DigitalOcean **SFO3** application Droplets, initially **2 GiB RAM / 50 GiB SSD / one shared vCPU**
  each. Production uses Managed PostgreSQL; staging uses self-managed PostgreSQL on its own application Droplet.
  These are planning sizes, not measured capacity or a purchase order. Actual supported SKUs must be checked when
  provisioning; do not assume account entitlement or reserve speculative capacity.
- Separate data, database roles, credentials, signing/encryption keys, storage and network authority. Staging
  cannot administer production and receives no implicit production-data copy. Candidate-code execution is not
  permitted on either application host; release CI is a separate build environment.
- Match the exact application artifact and relevant runtime, database major/extensions, schema/migrations,
  required services and security behavior. Staging does not reproduce managed database maintenance/recovery;
  state that operational difference explicitly. Self-managed staging updates, supervision and consistent exports
  are operator-owned. Do not add a parity-certification project or freeze an unqualified runtime version forever.
- Start staging with one worker if possible, at most one projector if genuinely required, and one cron container.
  John requested **512 MB for PHP**; distinguish per-process memory limits from aggregate process/container usage.
  Preserve OS/database/service headroom, modest web concurrency and real transaction/security participants.
  Production concurrency is not fixed by this decision. Return actual fit/cost tradeoffs rather than silently
  reducing accepted functionality or pre-buying speculative capacity.

### Production artifact and secure environment integration

- Build an immutable production artifact through the existing GitHub CI path. Include required application and
  browser assets, private OpenAPI/validation exports, the password corpus and its license, and necessary runtime
  dependencies. Exclude development-only debug tooling, checkout mounts, credentials and execution scratch.
  Application-generated state belongs under the established runtime/storage contract, never `.runs/`.
- Use the selected NGINX/PHP-FPM production serving direction. Existing development Compose/localhost TLS are
  inputs, not a production package. Supply explicit environment configuration, service supervision, update and
  startup procedures without replacing ordinary contributor defaults or local native checks.
- Establish actual public TLS, exact browser origins and proxy behavior, scoped secure cookies, current server
  authorization, debug-off behavior, headers/throttling and safe diagnostics. DNS alone does not establish a
  secure authenticated deployment. Keep environment cookies/authority isolated rather than sharing a parent-domain
  session. Reuse existing application security owners for any required code change; configuration must not bypass
  their fail-closed contracts.
- Keep runtime provider, signing, mail and encryption secrets protected and separate by environment. Preserve
  key versions needed by retained backups and outstanding credential/provider operations. No secrets in images,
  prompts, ordinary logs, browser storage/readback or source control. No new runtime vault access follows from
  selecting human Bitwarden custody.
- Configure required services and schedules through existing owners. Observe application, worker and scheduling
  health separately from log collection, archive and backup health; missing diagnostics or email must not report
  green operation. Preserve the accepted diagnosis isolation, retention and resource requirements rather than
  reducing them to fit a guessed household workload.

### Real mail and provider integration

- Select **Resend Free through HTTPS** for automated account/credential-recovery mail, reusing TICKET-00011's
  package delivery/outbox/retry/failure/runner semantics. Gmail remains John's inbox, not the application's SMTP
  fallback. Qualify the current allowance and actual inbox delivery during authorized integration; the historical
  3,000/month and 100/day figures are documentary observations, not live entitlement or a delivery guarantee.
- Sender/domain enrollment and DNS authentication require their own bounded authority and must preserve existing
  inbound mail. Protect credentials, isolate staging effects, expose quota/delivery failures and do not auto-upgrade
  to a paid plan. Existing Mailpit/null/in-memory adapters do not constitute real production delivery.
- Consume protected per-user OpenRouter connections and original-attempt accounting from their existing owners.
  Do not introduce an administrator/family key, a duplicate credential service, another usage ledger or automatic
  provider fallback. Missing provider allowance remains honestly unavailable and does not by itself disable
  useful recorded Planning usage.
- Routine staging checks use explicitly labeled simulated providers. Controlled live checks require explicit
  enablement, per-user staging connections and independent environment budgets. Production may have higher limits,
  but no numeric inference cap or automatic expansion is approved. Different keys do not prove separate upstream
  wallets; staging cannot borrow production authority or budget.

### Build once, stage, approve and promote

- John selected application CalVer: `YYYY.MM.DD`, optional same-date `.2`, `.3` tie-breakers and optional `-rc.N`
  candidate identifiers. Use `release/<version>` branches such as `release/2026.10.24`; retaining Git release tags
  is not required. The UTC release date is an identifier, not necessarily the deployment date. Preserve exact
  source commit and artifact digests in the release record independently of branch movement; never silently reuse
  an accepted release identifier for different bytes. This does not change package/Harness version contracts,
  existing CI trigger filters or branch/tag mutation authority, and CalVer alone says nothing about schema safety.
- Validate the exact artifact digest in staging and promote that artifact, not a rebuild. Record the target,
  configuration/secrets revisions, database changes, required services and schedules with the proposed release.
  Material changes invalidate the approval; logs and receipts identify secret versions, never secret values.
- John explicitly approves the exact production candidate and bounded effects. Merge, push, a green CI run or an
  EPIC/TASK status does not deploy automatically. Optional Fight-specific human UAT is candidate/configuration-bound,
  not a new universal TASK stage or a replacement for independent Review/QA.
- Coordinate the first rollout with the existing approved Planning migration: immutable inventory, rehearsal,
  exact human approval and atomic authority switch with retained frozen Markdown. TICKET-00028 continues to own
  those semantics. Until an explicitly approved, verified cutover, Markdown stays authoritative; no dual writer,
  automatic archive, incomplete import or new migration engine.
- Preserve original-operation outcomes and uncertain provider/credential liabilities through interruption,
  deployment and recovery. Do not replay paid work or outbound mail blindly. Make partial/unknown deployment and
  migration outcomes inspectable before resuming; connection loss is not proof of failure or permission to repeat.
- First production delivers useful browser Planning through its existing owners. Do not require the full managed
  coding team, candidate workers, release automation or optional domain UI before this user outcome.

### Recovery and human operation

- Accept non-HA production with **verified recovery**, not unlimited loss/outage. Prefer no more than one hour of
  accepted Planning data loss and usable service within 24 hours **after discovery**, operated by John without
  staffed overnight response. Undetected time is additional. Return a concrete daily/worse-loss tradeoff if cost
  or practicality requires one; do not silently claim an hourly guarantee or create an hourly-certification TASK.
- Retain thirty days of daily recovery points **conditional on reasonable cost**, recovering database, referenced
  files and required key versions coherently. This is not thirty-day PITR or a reduction of diagnosis retention.
  A schedule alone does not prove the loss bound. Managed backups and VM images alone are not the complete
  database/files/keys recovery supplier; staging needs consistent database exports and tested restoration.
- Use **Spaces-only backups**, with the accepted shared DigitalOcean provider/account exposure. No guarantee of
  recovery through every provider/account outage is made. Independent B2/Cold storage was researched but is not
  selected or a new launch prerequisite. Backup storage does not replace private application/evidence storage.
- Keep the human recovery kit in **Bitwarden**: necessary application/backup key versions, DigitalOcean account
  recovery material and concise restore/access instructions. It must remain usable without Fight or the failed
  host and avoid circular vault-unlock/second-factor recovery. This authorizes no vault inspection/export, plan
  purchase, runtime integration or sharing of credentials with Agents.
- Permit application-only rollback within an approved deployment **only when compatible with the current
  database** and bound to the exact target/artifact/configuration. Unknown/incompatible schema means stop and
  return the recovery choice. No implied reverse migration or destructive experiment.
- Database restoration requires John's explicit approval after stating the recovery point and expected data loss.
  Deployment/rollback consent does not authorize rewinding data. Isolated restoration suppresses outbound mail
  and provider effects until original operations and authority are reconciled. Retain originals until separately
  authorized cleanup; temporary recovery spending is separately approved.
- Provide usable operator diagnosis, recovery and maintenance/outage communication outside the failed application.
  Human communication through an available independent channel is sufficient; no staffed service, mandatory
  status-page vendor or new general operations platform is selected.

### Budget and purchasing boundary

The preference is **below $100/month combined staging/production recurring costs, including tax**: hosting,
databases, storage/backups/overages, required operations/diagnosis, registry, mail, CI/network and recurring domain
cost. Inference budgets remain separate. This is a preference, not spending authority, an automatic service cutoff
or permission to exceed it. Return unavoidable scope/cost tradeoffs to John instead of omitting requirements.

The dated **$56.35/month pre-tax subtotal** in WF-050 covers two initial application Droplets, one minimum managed
production database, daily boot backups, Spaces and Registry Basic. It is not the complete bill, a live quote,
a measured fit result or a mandate to buy every illustrated service irrespective of the delivered artifact path.
Recheck actual prices, availability, resource use and tax during authorized delivery.

Temporary recovery needs a separate quote and approval covering resource sizes, duration, coexistence with
originals, storage/transfer and cleanup. No automatic reserve, indefinite billing or assumption that powering off
a retained VM ends its charges. Additional resources/duration need appropriate authority.

### Observable completion and delivery discipline

The later implementation must make it possible to:

1. Start and inspect isolated staging/production with the selected exact artifact, real secure ingress and required
   services, while preserving ordinary local development and unrelated projects.
2. Use the first approved browser Planning journey after its existing owners deliver it and its exact database
   cutover is approved; preserve per-user provider/usage isolation and useful unavailable/error states.
3. Promote only a validated, approved candidate, inspect actual operation and service health, and perform a
   compatible application rollback without silently rewinding data or triggering duplicate external work.
4. Restore coherent application data/files/keys through an authorized isolated recovery and demonstrate the
   actually achieved loss/recovery behavior, exposing any gap against the preferred objectives for a human choice.
5. Operate the system with truthful cost/capacity, mail/schedule, diagnosis and backup observations and independent
   runbooks, rather than assuming passing commands or configured timers prove service success.

Use ordinary implementation acceptance, the repository's full `./bin/build` gate, independent Review/QA and
applicable target-specific probes within the real delivery work. Validate infrastructure through its owning tools;
do not add product tests of wrappers, Compose, generated files or planning/quality mechanisms. No standalone
readiness, certification, benchmark or production-before-implementation TASKs. Target-specific missing evidence
blocks only the operation that requires that target, not unrelated local/staging work. After real deployment,
John assesses useful operation and can request concrete bugfix work for observed defects.
