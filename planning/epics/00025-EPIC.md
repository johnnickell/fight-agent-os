# Serve the browser application from root URLs with managed access defaults

## Destination

People enter Fight at `/`, authenticate at `/login` when necessary, and use clean root-level browser
URLs without an `/app` prefix. The authenticated root is the existing permission-aware Dashboard, not a
public homepage. Deliver the complete URL cutover across navigation, credential links, runtime configuration
and local operating tools, rather than changing only the React route registry.

Include the bounded managed-authority catalog update approved during this interview. Ordinary invited users
retain `ROLE_USER` and its approved baseline access; `ROLE_SUPER_ADMIN` receives every managed Permission.
Use one version-controlled JSON catalog and the existing idempotent reconciliation process, not a second
seeding system. This work does not warrant a separate authority EPIC.

## Decisions and exclusions

### Browser URLs and dispatch

- Remove the browser `/app` prefix with no legacy redirects or compatibility aliases. Move existing public,
  account, administration and Swagger browser destinations to root-level equivalents. `/reset-password`
  and `/reset-password/complete` retain that spelling; activation is `/activate` and login is `/login`.
- Make `/` the canonical Dashboard destination. Preserve current Dashboard content, exact Permission checks,
  independently permitted shortcuts and unavailable-capability presentation. Do not add Dashboard features or
  infer access from Role names. Authenticated users without `VIEW_DASHBOARD` retain Forbidden behavior.
- Unauthenticated visits to `/` redirect to `/login`. Preserve existing safe session restoration and admitted
  post-login navigation intent under the new URL grammar, without redirect loops or open redirects.
- Serve the React shell as the final catch-all for browser GET navigation, with explicit server-owned routes
  and assets taking precedence. Direct entry and refresh on registered client destinations work; unknown
  browser destinations retain meaningful client Not Found presentation. Do not turn API/MCP errors, missing
  assets or unsupported server methods into successful shell responses.
- Keep the implemented API namespace at `/api/v1`. Reserve `/mcp/v1` for future MCP entry points; reconcile
  applicable current planning that names `/mcp`, without implementing MCP or changing its separate admission
  and authentication boundary.

### Complete and security-preserving cutover

The read-only source scan found URL literals in the route manifest, root/default navigation, frame/brand links,
page links and permission lookups, intended-route admission, credential-fragment capture and pre-render URL
clearing. It also found exact-path checks in credential delivery and HTTP security configuration, environment
examples, isolated-runtime preparation, synthetic-mail QA extraction, tests and current documentation.
Implementation must recheck the live inventory and update surviving callers together.

- Update generated activation and reset email destinations, trusted-origin/exact-path validation, examples and
  local runtime setup consistently. Preserve fragment-only credential transport, early URL clearing, redaction,
  existing browser request controls and safe same-origin post-login intent. Do not weaken validation merely to
  accept renamed URLs or retain the old browser paths.
- Preserve needed durable identities, invitation/reset state and delivery/recovery contracts. Determine any
  operator/configuration or retained delivery-material obligations before the cutover; no data disposal or
  secret-bearing URL logging is authorized. No compatibility redirect is required for old links.
- Update owned browser consumers, behavioral tests, tooling and applicable current documentation/plans; preserve
  historical acceptance and publication evidence as history rather than rewriting old receipts.
- Distinguish browser URLs from container filesystem paths such as `/app/public/index.php`, Docker workdirs,
  mounts, source filenames and import aliases. These are not part of the prefix removal.

### Managed authority catalog and defaults

- Replace the PHP-held managed definitions/memberships with the single authoritative catalogs at
  `database/seeds/permissions.json` and `database/seeds/roles.json`. Preserve existing stable IDs, Permission
  names/tiers, references and supported typed package contracts; do not maintain duplicate PHP and JSON catalogs.
- Retain an explicit idempotent trusted-operator preview/apply command through the existing reconciler. The
  current entry points are `./bin/managed-policy preview --internal` and `./bin/managed-policy apply --internal`.
  Do not add automatic application-startup reconciliation, reset a database or create a parallel loader.
- Keep `ROLE_USER` membership exactly `VIEW_DASHBOARD`, `READ_OWN_SESSIONS` and `DELETE_OWN_SESSIONS` until a
  separately approved Permission audit changes it. The user's earlier dashboard-only proposal was superseded
  during the interview; the three-Permission baseline is the final decision.
- Make `ROLE_SUPER_ADMIN` include every current and subsequently added managed Permission. This explicitly
  amends the prior requirement for separate approval of each Super Admin default in the
  [managed authority contract](../../docs/engineering/MANAGED_POLICY.md#permission-eligibility-is-not-assignment).
  Permission tier and definition alone still grant nothing to ordinary Users, custom Roles or Agents; retain
  their independent assignment and admission rules. No role-name authorization bypass is introduced.
- Preserve reconciliation idempotency, stable identity/rename behavior, managed membership convergence,
  custom/unmanaged authority protection, collision rejection and existing reference/removal fences. Validate
  malformed catalogs, duplicate IDs/names and unresolved membership references before unsafe effects.
- Ordinary HTTP and Console invitations already assign `ROLE_USER`; preserve those paths. Elevated invitation
  and bootstrap retain their existing Super Admin assignment behavior. Invitation and Role assignment currently
  commit separately; partial issuance may lack its intended assignment. Do not claim this catalog update makes
  issuance atomic or authorizes blind reinvitation or a blanket existing-user backfill.

The Omphalos example was inspected read-only at `~/Ideaverse/AIOS/Omphalos`: its
`database/fixtures/AccessControl.Permissions.json` and `AccessControl.Roles.json` use stable IDs and
Permission-name references. This is a representation example, not an imported workflow or implementation
contract. Retain Fight's existing package-owned reconciler and stronger protections rather than copying the
example's separate synchronizer or unrelated reference catalogs.

### Exclusions

- New Dashboard content, changed Dashboard admission, a broader Permission audit or new ordinary User defaults
- MCP implementation, API version changes, public registration or new invitation journeys
- Invitation transaction/recovery redesign, automatic User backfill or changes to elevated/bootstrap semantics
- Compatibility aliases, legacy redirects, container filesystem moves or speculative routing infrastructure
- Database resets, removal of custom authority, production deployment or executing seed/reconciliation commands
  merely to write this plan

## Observable outcome

Direct browser entry, refresh, internal links, login/restoration and permitted Dashboard navigation use the new
root URLs. Activation/reset mail and their actual browser credential intake agree with runtime validation.
API and reserved machine namespaces never receive the React shell by mistake. The old browser prefix is no
longer a supported alias, while unrelated filesystem paths remain intact.

On an explicitly prepared installation, preview/apply establishes the complete managed JSON catalog, repeat
apply leaves unchanged state unchanged, User membership remains the approved three Permissions and Super Admin
membership includes the complete managed catalog. Invalid or conflicting input fails safely and unrelated
custom authority survives. Qualify the selected package contracts during implementation rather than inferring
runtime guarantees from this source inspection.

Verify owned application behavior through appropriate regression/integration and browser evidence. Validate
configuration, wrappers and planning directly with their owning tools, not product-suite tests of file text.
Detailed requirements, exact verification scenarios and implementation slicing belong to later decomposition.
