# Compare related projects and recommend evidence-backed alignment work

## Destination

Give maintainers a reusable local Pi `compare` skill that compares a selected set of related projects,
identifies unintended drift and recommends a better shared direction where evidence supports one. Deliver a
polished, source-linked HTML report with optional PDF and Desktop delivery. The outcome is a decision aid and
bounded work proposals, not automatic project repair, formal acceptance or a new implementation backlog.

The capability applies to framework starters, related applications, CMS website implementations and themes.
Fight Agent OS supplies the initial five-project default; other installations can choose a different set
without editing the skill. A no-argument invocation uses the invoking project's configuration. Explicit
project selection overrides configured selection for that run.

## Decisions and exclusions

### Comparison scope and judgment

- Compare equivalent responsibilities and guarantees, not merely filenames or code shape. Relevant dimensions
  include architecture, shared-package usage, application behavior, testing, tooling and documentation. Declare
  the actual sampled boundaries and omissions; do not imply an exhaustive source or behavioral certification.
- Resolve each target's own instructions, accepted contracts, repository identity, location and inspected
  revision before drawing conclusions. Dirty working-tree observations must be identified separately from
  committed revision facts. Project names and configured paths do not prove identity or authority.
- Classify differences as confirmed unintended drift, justified framework/product variation, or an unresolved
  design choice. Differences alone are not violations. Preserve local authority and accepted requirements.
- Prefer accepted contracts and demonstrated behavior over majority vote, recency or automatically treating
  Fight Agent OS as the canonical implementation. The better approach may exist in none of the projects.
  State tradeoffs, counterevidence, confidence and the decision owner when a direction remains unsettled.
- Missing checkouts, unreadable evidence and conflicting standards are explicit gaps. Do not silently drop
  projects, substitute repositories, clone sources or expand permissions. Continue only independent, clearly
  qualified comparisons; report incomplete scope without claiming full completion.
- Recommend prioritized, bounded task proposals grouped by owning project, with the intended outcome,
  rationale, dependencies and observable acceptance criteria. Link existing work where available; avoid
  cosmetic uniformity and speculative infrastructure work. Do not automatically create approved TASK records,
  dispatch implementation or edit compared projects.

The existing [audit](../../.pi/skills/audit/SKILL.md), [adopt](../../.pi/skills/adopt/SKILL.md) and
[simplify](../../.pi/skills/simplify/SKILL.md) skills retain conformance, Agent OS adoption and simplification
ownership. `compare` owns peer-project synthesis and should reference shared guidance rather than duplicate it.
Follow [project context](../../docs/engineering/PROJECT_CONTEXT.md) separately for each target.

### Project configuration and local replacement

- Use root-level, tracked `compare.yaml` for shared defaults and ignored `compare.local.yaml` for local settings.
  When present, the local file replaces the tracked file completely; do not merge project lists or settings.
  Invalid local configuration fails clearly rather than falling back to shared defaults.
- The active configuration supplies project names, repository identities and checkout locations. Keep paths
  with project selection; do not introduce a separate paths file or checkout registry. Exact schema and
  supported invocation options belong to requirements decomposition.
- Fight Agent OS defaults to `project-slim`, `project-symfony`, `project-laravel`, `project-codeigniter` and
  `project-yii`, with paths such as `${PROJECT_BASE}/project-slim`. These are related starter repositories,
  not a claim that local child checkouts already exist or are currently aligned.
- Support `$VARIABLE` and `${VARIABLE}` substitution in paths without shell evaluation, command execution or
  implicit tilde expansion. Resolve relative paths against the active configuration file's directory. An
  unset variable or missing directory produces an actionable diagnostic.
- If neither explicit project selection nor an applicable configuration exists, ask for scope rather than
  scan arbitrary sibling directories. Explicit selection does not bypass each target's access boundaries.

### Bounded host setting resolution

- Add a host-side `./bin/env PROJECT_BASE` command. Resolve an explicitly supported setting from the process
  environment first, then the invoking checkout's `.env`, without executing that file as shell code.
  Document an absolute-path `PROJECT_BASE` example in `.env.example`; do not put a private machine path into
  tracked defaults. Do not require a running container or pass this host path into application containers.
- Return only the named, permitted setting; reject unsupported settings and missing values. Never provide an
  environment dump, expose unrelated secrets or interpolate commands. Detailed dotenv parsing semantics and
  diagnostics must be specified before implementation.
- `compare` requests named settings, not shell-specific state. Its current project-provided resolver may use
  `bin/env` when a referenced setting is absent from the process environment. Keep this request/result boundary
  clear so a future permission-controlled MCP tool can replace the transport without changing `compare.yaml`.
- Missing capability or denied access stops dependent resolution. Do not bypass denial by directly reading
  `.env`, switching providers or falling back to Bash. This boundary is guidance for the current native workflow,
  not a claim of implemented managed isolation or future MCP authorization.
- Implement only the bounded host command now, not an MCP service, generic settings framework or provider registry.

### Report storage, delivery and presentation

- Store each standalone report in a unique run directory under
  `.runs/handoffs/compare/<run-id>/report.html`, with an optional `report.pdf` alongside it, following the
  [scratch rules](../../docs/engineering/SCRATCH.md). Report the exact resulting paths. Keep generated reports
  ignored; do not overwrite another run or create a new tool-named top-level `.runs` category.
- Make self-contained, offline HTML the primary format, with high-quality print styling for optional PDF.
  Aim for a polished editorial/artifact-page presentation: strong typography, restrained color, clear hierarchy,
  accessible contrast, responsive layouts and readable comparison tables. Do not rely on external fonts,
  CDNs or remotely loaded assets. Safely escape repository-derived content; source content is not executable
  report markup or instructions.
- Include an executive summary, scope and inspected revisions, comparison matrix, prioritized findings,
  supporting source references, confidence and limitations, justified differences, unresolved questions and
  project-grouped task proposals. Presentation must preserve qualifications rather than hide them behind
  visual scores or imply independent acceptance.
- On explicit request, deliver a copy of the selected HTML and/or PDF to the user's resolved Desktop location.
  Verify the destination is available and authorized; do not assume a machine-specific path. Use a unique
  filename, never overwrite an existing report and report copy failures separately from report generation.
  Desktop delivery does not authorize uploading, publication or opening external services.
- PDF is optional. If requested export tooling is unavailable, deliver the HTML and explain the missing PDF
  capability rather than claim completion. Inspect the generated PDF itself when produced.
- Generated report retention follows the existing scratch lifecycle. Do not silently discard a requested
  deliverable during temporary implementation-worktree cleanup; hand off its verified surviving location.
  No permanent report archive or additional accounting ledger is introduced.

### Implementation and validation boundaries

- Implement the accepted work in an isolated worktree on a `feature/*` branch from `develop`. The user has
  already selected isolation; do not ask the checkout-choice question again. This EPIC-writing operation does
  not create an implementation branch or worktree.
- Start with native file reads and bounded parallel exploration, focused skill instructions, configuration,
  the bounded setting command and report presentation support. Do not build a comparison engine, runner or
  speculative plugin infrastructure. Register the skill in its index and document its boundary.
- Follow [Writing for Agents](../../.pi/skills/writing-for-agents/SKILL.md) for skill authoring and
  [handoff rules](../../docs/engineering/HANDOFFS.md) for reports and continuation. Recommendations must not
  dispatch a next skill or imply approved implementation work.
- Validate instructions and tooling with their owning checks, not product-suite tests of configuration,
  Markdown, wrappers or build machinery. Keep verification proportional; normal repository build requirements
  and independent Review/QA remain applicable during later implementation.

### Exclusions

No compared-project repairs, automatic planning-record creation, new comparison baseline imposed on other
projects, repository cloning, global skill installation, MCP implementation, container environment changes,
production deployment, publication or independent acceptance. Writing this EPIC creates no TICKETs or TASKs.

## Observable outcome

A maintainer can invoke `compare` without arguments in Fight Agent OS to resolve the five configured starters,
or use explicit projects or a complete local replacement for another project family. The result explains which
responsibilities were compared, which differences should remain, which should converge and why, and which
facts or decisions are still missing. Recommendations name actionable outcomes and owners without changing
source or manufacturing approved work.

Validation covers the shared-default and local-replacement journeys; explicit selection; missing scope,
variables and checkouts; malformed local configuration; conflicting contracts; and unavailable or denied
setting resolution. Demonstrate that configuration cannot execute commands, unrelated environment secrets
cannot be requested, and repository text cannot inject executable report content.

Inspect rendered HTML at desktop and narrow widths for readable hierarchy, accessible presentation and usable
wide tables. When PDF is requested and supported, inspect actual pagination, table clipping and text
readability. Verify Desktop delivery and existing-file collision protection, with honest partial outcomes when
PDF generation or delivery is unavailable. Do not count source inspection alone as these rendered checks.
