# Create and register new projects

## Destination

Deliver one confirmed, deterministic, recoverable journey that creates a new project from an approved immutable
starter snapshot, initializes a fresh local Git repository, optionally prepares dependencies, optionally creates
and publishes a private-by-default GitHub repository, and registers the resulting local checkout with its first
database-authoritative context.

An authenticated authorized user chooses names, location, starter, initial branch, development profile, preparation,
and publication settings; reviews every intended filesystem, Git, network, source-host, and registration effect;
and confirms one durable Create Project operation. Deterministic Runner operations—not an AI model—perform those
effects and preserve truthful partial outcomes for explicit retry, continuation, or ownership-checked cleanup.

Register the five accepted managed starter sources and support authorized Workspace custom GitHub starters under
the same stable-release, immutable-snapshot, and generation-manifest contract. Before this EPIC is accepted, at
least one managed starter—preferably `johnnickell/project-slim`—must have a real immutable stable SemVer release
`>=1.0.0`, and that release must create and register a real project successfully. Releasing the starter is an
explicit maintainer action in its source repository, not an Agent OS mutation or certification workflow.

## Decisions and exclusions

- Consume the closed [Complete Fight Agent OS vision map](../wayfinder/complete-agent-os-vision-map.md), especially
  [WF-021](../wayfinder/tickets/WF-021-define-new-project-creation-and-registration.md), together with the accepted
  identity, context, Harness, Runner, onboarding, runtime, and sequencing boundaries in WF-008, WF-009, WF-014,
  WF-016, WF-019, WF-020, and WF-023, without reopening their decisions.
- Depend on [EPIC-00005](00005-EPIC.md) for Repository/Host/Checkout/Worktree identity, approved project roots,
  database-authoritative registration and context, and the authenticated Dashboard. Depend on
  [EPIC-00006](00006-EPIC.md) for managed/custom Harness profile templates and optional browser support Agents.
  Reuse the eligible deterministic Runner capabilities delivered by [EPIC-00007](00007-EPIC.md) without creating
  a coordinated coding Workflow, TASK claim, Team Lead, Software Engineer, Review, or publication pipeline.
- Begin with managed catalog entries for `johnnickell/project-symfony`, `project-slim`, `project-laravel`,
  `project-yii`, and `project-codeigniter`. A managed or custom starter is available only when its selected source
  has a newest stable SemVer tag at or above `1.0.0`; exclude prereleases and do not offer historical-version
  selection for new projects.
- Treat the stable release tag as the source maintainer's support declaration, not Agent OS quality certification.
  Resolve it to an exact source/provider identity and commit, obtain the tracked source archive, verify its digest,
  and install that immutable snapshot with the catalog. Record provenance and compatibility claims without
  manufacturing additional certification.
- Fail catalog refresh closed when a previously known tag resolves to a different commit or archive digest. Never
  replace trusted bytes silently; recovery requires a newer stable tag or explicit operator decision. A newer
  release affects future projects only and never upgrades generated projects.
- Preserve installed snapshots needed by active or failed creation attempts. Explicitly archived, removed, or
  withdrawn entries become unavailable for new attempts without changing generated projects. Installed snapshots
  permit local creation during a GitHub outage; catalog installation/refresh still reports its connectivity needs
  honestly and never substitutes another version.
- Let an authorized Workspace administrator register an accessible public or private GitHub repository as a custom
  starter. Use the Workspace's protected server-side GitHub connection for private source, keep source credentials
  out of snapshots/results, and apply the same newest-stable-release, immutable-tag, digest, retention, withdrawal,
  and failure rules used for managed entries.
- Require each eligible release to contain a small versioned generation manifest declaring exact supported identity
  substitutions and at most one optional preparation command. Reject missing, invalid, ambiguous, changed, or
  unmatched manifests rather than guessing. The manifest is an executable generation contract, not an
  architecture, framework, Fight-library, CQRS, or quality certification.
- Permit custom starters using any language, framework, architecture, or toolchain that fits the bounded Runner
  contract. Preserve reusable source, instructions, tests, architecture, and tooling according to the release
  manifest; never impose Agent OS conventions through broad text replacement.
- Let Workspace administrators associate starter entries with recommended Workspace-owned managed or custom Agent
  profile templates. Show and record the selected profile revision during creation. Profiles and Skills remain
  independently versioned; repository content cannot add/activate them, profile selection cannot grant
  Permissions, and Access Control validates every actual Agent separately.
- Require an editable human display name, machine-facing Workspace project slug, starter, runner-accessible parent
  directory, independently editable local directory name, selected initial branch, preparation choice, and
  development profile. Suggest values but keep path, directory name, project slug, and any remote repository name
  independent.
- Configure one or more approved project roots and suggest `~/Projects` during onboarding without treating it as
  universal. Permit nested Workspace/vendor parents under those roots. Canonicalize parent/destination, verify
  containment and ownership, detect collisions and symlink escape, and reject ambiguous, existing, or unrelated
  destination content before mutation.
- Treat adding a location outside approved mounts as the separate explicit installation operation to add a root
  and reconfigure/restart the Runner. Preserve the pending form/preview where safe, but do not let the browser
  alter mounts or create a partial project the Runner cannot access.
- For optional GitHub publication, require an independently editable owner and repository name, private-by-default
  visibility, and optional description. Suggest the authenticated personal owner and project slug while permitting
  authorized organizations and other names. Public visibility requires a heightened warning and explicit
  acknowledgement.
- Do not request a Composer vendor/package identity merely because a starter uses Composer. Remove or neutralize
  source package identity only through exact manifest transformations. Never copy a starter worktree, `.git`,
  ignored dependencies, caches, local state, secrets, generated credentials, or remotes into the result.
- Create from the retained tracked immutable archive. Apply only declared deterministic transformations and verify
  every expected match/result. A changed, absent, duplicate, unsafe, or out-of-bounds target fails before later
  effects rather than triggering broad search/replace or AI repair.
- Make every result a fresh local Git repository with no inherited history or remotes. Suggest `develop`, allow an
  independently selected branch such as `main`, create only that initial branch, and create exactly one initial
  commit over the deterministic generated state. The selected branch becomes registered context and the remote
  default when publication is chosen.
- Define local-only as a complete fresh local Git repository with no GitHub remote. It is a first-class creation
  result, not a degraded no-Git path, and it still requires registration, checkout identity, context, receipt, and
  deliberate next actions.
- Perform a read-only preflight before preview. Validate snapshot/manifest integrity, canonical destination and
  configured-root containment, all names/collisions, Runner capability/availability, transformation expectations,
  profile availability, and selected GitHub identity/owner/repository/visibility availability where applicable.
- Present one complete preview containing starter source/tag/commit/digest, names and canonical paths, declared
  transformations, initial branch/commit, optional preparation and its executable/network implications, source
  owner/name/visibility/description, publication effects, profile revision, registration, and context effects.
  Any material input, snapshot, authority, capability, collision, or external-state change invalidates the preview.
- One explicit confirmation authorizes only the exact previewed operation. Do not add repeated prompts between
  ordinary stages, but require the public-visibility acknowledgement and any separate installation/root operation
  before confirmation. A confirmation cannot authorize later changed inputs or inferred effects.
- Execute one durable user-authorized attempt through observable stages:

  1. generate tracked source deterministically;
  2. initialize fresh Git and create the initial branch/commit;
  3. optionally run the exact manifest preparation command;
  4. optionally create and push the GitHub repository;
  5. register the Repository and Checkout/Worktree; and
  6. resolve the first database-authoritative repository context.

- Run stages on an eligible authorized Runner without a model choosing paths, substitutions, names, visibility,
  commands, state transitions, retries, or cleanup. Do not create a coding Workflow or grant implementation,
  commit, push, PR, or execution authority merely because registration succeeds.
- Select preparation by default while showing that it is executable and may use the network. Run only the manifest
  command under the accepted Runner containment, credential, egress, timeout, observation, and redaction boundaries.
  Preparation failure retains the valid generated Git repository for explicit retry or deliberate completion
  where policy permits; a successful preparation leaves declared tracked changes observable and accounted for.
- For GitHub publication, use the existing authenticated `gh` identity without collecting/displaying its token.
  Verify the identity and authority for the selected personal/organization owner; respect organization policy,
  SAML, Permission, scope, name collision, and connectivity failures. Prefer configured SSH Git transport for
  push and never expose credentials to generated content, browser Agents, coding Agents, logs, or receipts.
- Keep this human-authorized project publication capability distinct from managed Workflow Release Manager authority.
  It may create the exact confirmed repository, set the selected default branch, and push the generated initial
  commit; it cannot publish unrelated repositories, approve/merge PRs, grant coding Agents source-host access, or
  infer consent from a prior attempt.
- Register only a successfully identified local Git checkout. Reuse the conservative WF-008 Repository/source,
  Checkout marker, Git common-directory, Worktree, Host, and first-link confirmation rules; do not equate source,
  directory, slug, or remote names with identity. Resolve context under WF-009 and begin directly in
  database-authoritative Planning mode without importing or creating Planning records.
- Persist one creation-attempt identity, immutable confirmed plan, actor/grant, expected external identities, and
  verified intent/result evidence for every filesystem, process, Git, provider, registration, and context stage.
  Queue delivery, process exit, browser state, or Agent inference cannot claim success without reconciled evidence.
- Make retry idempotent and stage-aware. Revalidate every completed effect and resume at the first incomplete stage;
  never duplicate a directory, initial commit, GitHub repository, push, Repository registration, Checkout link, or
  context revision. Resolve uncertain outcomes before offering another external effect.
- Preserve truthful partial outcomes: preparation failure retains generated Git; GitHub creation failure retains
  local work; push failure retains both local and remote state; registration/context failure retains prior effects;
  cancellation stops before the next effect and keeps everything already completed.
- Never automatically compensate by deleting a directory, commit, GitHub repository, snapshot, registration,
  profile, or context revision. Offer separate explicit ownership-checked cleanup or deliberate continuation
  choices with complete impact. Existing local/remote content belongs to the separate link/register journey and
  cannot be adopted silently by Create Project.
- Make recovery survive browser disconnect, application/Runner restart, redelivery, process interruption, and
  provider uncertainty through durable state and reconciliation. Pause or enter Needs Human for changed preview,
  missing capability, changed authority, ambiguous ownership, unexpected filesystem/Git state, unknown provider
  result, or unsupported manifest behavior.
- Let an optional in-browser support Agent consume only structured secret-safe attempt evidence and the applicable
  versioned troubleshooting playbook. It identifies observations versus inference and may recommend exact revised
  input, command, retry, cleanup, or next action, but cannot mutate files/settings, add roots, authenticate GitHub,
  delete resources, retry stages, change the attempt, or apply its own recommendation.
- Use the provider-capable browser Agent boundary from EPIC-00006, including OpenRouter through a protected
  installation-held key and explicit model/budget catalog. Browser credentials never receive provider secrets;
  OpenRouter failure disables optional assistance only and never blocks deterministic creation, playbook viewing,
  retry/cleanup controls, or safe diagnostic export. Coding Agents retain their separate Pi provider boundary.
- On completion, show a durable receipt with human/system Repository identities, canonical local path, Host,
  Checkout, Worktree and Runner identities, starter source/tag/commit/digest, generation manifest/revision, initial
  branch/commit, transformations, preparation result, optional GitHub provider identity/URL/owner/visibility/push,
  selected profile revision, context revision, warnings, skipped stages, attempts, and retained resources.
- Open the registered repository Dashboard with deliberate actions to inspect the checkout/context or start
  Planning. Do not automatically create a Wayfinder map, EPIC, TICKET, TASK, planning conversation, coding
  Workflow, claim, Agent session, PR, or any publication not present in the confirmed plan.
- Require at least one managed source—preferably `project-slim`—to publish a real immutable stable SemVer release
  `>=1.0.0` with a valid generation manifest before EPIC acceptance. Exercise that installed release through a real
  deterministic project creation and registration, including fresh Git, context, receipt, and recovery evidence.
  Also verify local-only and private-by-default GitHub publication paths without turning starter repositories into
  Agent OS-owned release work.
- Test important owned catalog integrity, immutable tag/digest, manifest validation/transformation, path
  containment, preview invalidation, authorization, idempotency, stage transitions, partial outcomes, collision,
  registration/context, and reconciliation behavior. Use important real Git/Runner/GitHub integration boundaries
  and manually create/register a real project; do not test Git, GitHub, package managers, frameworks, Compose,
  wrappers, configuration text, or starter quality merely to manufacture coverage.
- Exclude starter source development/release automation, automatic starter upgrades, historical/prerelease picker,
  arbitrary unmanifested repositories, AI-chosen mutations, existing-content adoption, automatic cleanup,
  Workflow coding/review/publication, Planning creation, instruction editing, source-host merge/release/deployment,
  multi-workspace isolation, and support for non-GitHub custom starter sources in this EPIC.
- Defer exact schemas, Commands/events, APIs, Permission identifiers, manifest fields, snapshot storage layout,
  profile-association representation, GitHub adapter details, support prompts/playbooks, UI components, budgets,
  and implementation slices to TICKET and TASK decomposition. Open a new Wayfinder decision only for genuinely
  new hosted-provider, trust, or multi-source starter uncertainty.
