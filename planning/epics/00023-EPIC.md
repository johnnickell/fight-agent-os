# Adopt canonical Fight contracts and refactor Agent OS around Project-owned CQRS

## Destination

Make the entire existing PHP application and its unfinished plans consistently follow the maintainer's strict
DDD, CQRS and Hexagonal Architecture conventions. Long-term maintainability is the primary design constraint,
not delivery speed. A maintainer should be able to identify a business concept, its aggregate, messages,
handlers, persistence and entry adapters without following misleading names or redundant forwarding layers.

John approved this destination after an architecture exploration and decision interview against Agent OS
`7dc5b11fca4dce89f00db34ac9cf75eacade8556`. The scope is the whole PHP application, not just one exemplary
Project aggregate. Implementation must be divided later into bounded, independently verifiable changes.
This EPIC approves the destination and policy amendments below, not implementation or TICKET/TASK decomposition.

## Decisions and exclusions

### Scope and responsibility

Review and correct existing Domain, Application and Adapter code, runtime composition and application entry
paths, affected callers/tests, governing instructions, and current architecture documentation. Include planned
HTTP, Console and MCP contracts without implementing an otherwise unapproved product surface. Apply naming and
quality principles appropriately to shared boundaries; do not impose PHP aggregate folders on React, TypeScript,
Pi modules or engineering tooling. This is not an unrelated frontend or Harness rewrite.

Use the existing product owners and requirements. Necessary refactors remove concrete maintenance problems in
real capabilities; do not add demonstration features, speculative interfaces, generic operation engines or
parallel planning queues. Prioritize this correction rather than knowingly extending superseded designs, while
leaving actual implementation order and supplier edges to the approved decomposition and Board metadata.

### Project is the business concept

Replace the overloaded application business term Repository with **Project**. Initially retain the meaning of
one intended collaboration/publication target in a Workspace, with its stable identity, metadata, optional primary
Git source and equivalent source descriptors. This does not introduce a multi-repository umbrella or merge fork
identities. Host, Checkout and Worktree remain distinct concepts with their own justified identities and links.
Git repository remains a qualified source-control term; Repository names a collection-like persistence contract.

Use `Project`, `ProjectId`, `ProjectRepository`, `RegisterProject`, `RegisterProjectHandler` and `ProjectRegistered`
for the corresponding owned responsibilities. Registration is an operation on a Project, not a replacement
aggregate or a generic Store concept. The primary aggregate table should normally be `projects`; related tables
must express their actual relationships. Assess schema, identifiers, permissions, routes, UI vocabulary, imports,
context and planning references together rather than performing blind text replacement. Coordinate with
[registered Planning](00005-EPIC.md), [registration and checkout requirements](../tickets/00024-TICKET.md), and
[new-project creation](00009-EPIC.md) without duplicating their product outcomes.

### Aggregate-first organization and inward dependencies

- Domain uses `Domain/{BoundedContext}/{Aggregate}` with an aggregate root, typed aggregate ID, repository
  interface, owned value objects and optional nested entities. Commands and Queries express verb-first intent;
  Events describe past facts. Other Domain services, DTOs or building blocks need a demonstrated Domain purpose.
- Application mirrors aggregate ownership with `CommandHandler`, `QueryHandler`, policy-named `EventSubscriber`
  and cohesive semantic capabilities. `Service` is a fallback, not permission for miscellaneous flat classes or
  broad lifecycle forwarding services. A command-shaped class must not conceal an unregistered dispatcher service.
- Adapters are capability-first, with aggregate-oriented persistence and transport presentation where appropriate.
  Concrete Console input/output, HTTP Actions/Data/Responders, MCP Tools and protocol bindings stay outside Domain.
- Framework/provider implementations belong in Adapter or the composition root. Application may use PSR contracts
  and supported upstream Domain/Application contracts; Domain may use pure PHP and supported upstream Domain
  contracts. Reuse canonical Fight identity/value contracts instead of introducing parallel bases or aliases.
- Keep constructor injection and fully descriptive collaborators such as `$projectRepository`, `$queryBus`,
  `$commandBus`, `$transactionalUnitOfWork` and `$eventDispatcher`. Actual collections may retain natural plurals.
  Do not manufacture getters or extra layers merely to satisfy a naming example.

### Handlers own coordination and transactions

Commands carry intent; registered Application CommandHandlers coordinate aggregate behavior, repository
persistence and required audit through the existing `TransactionalUnitOfWork`. Repositories act like collections
of aggregate roots, not transaction managers, use-case services, response factories or unrelated admission stores.
Do not retain a combined Store/UoW contract or disguise business orchestration as transaction mechanics.

Use Common's generic transaction implementations according to actual persistence needs: the existing Doctrine
implementation and the planned DBAL-only implementation are alternatives behind the canonical contract, not two
independent transaction authorities inside one operation. Participating persistence shares the owning connection.
Preserve real business uniqueness, expected-state comparisons, aggregate invariants and required atomic writes.
Success events are dispatched only after commit; external effects do not become rollback-safe merely because an
event was emitted. State post-commit failure and uncertainty honestly without promising exactly-once effects.

Use configured buses for message dispatch, including nested package commands/queries; do not invoke handlers
privately. Use upstream commands, queries and capabilities directly when they already express the use case.
Remove superseded aliases, adapters and forwarding services after replacement verification. Secret-bearing
synchronous upstream operations remain non-serializable where required; uniformity does not justify putting raw
passwords or tokens into messages.

### Entry adapters own authentication and authorization admission

Each HTTP, Console, MCP or other entry adapter owns its authentication, operation permission and target/scope
admission checks. Its normal role is to parse/map input, establish the trusted actor, validate input and access,
dispatch through the command/query bus and present the outcome. HTTP credentials and prospective MCP HMAC
verification must not determine what a business command handler does. The raw bus is trusted in-process
infrastructure, not an independently exposed public API. Every actual entry path needs its own appropriate checks;
request transport identity cannot be replaced by an untrusted actor field.

Do not impose a second blanket authentication/permission gate in Application or bus filters. Keep genuine Domain
invariants with their business owner rather than relocating them into transport code. Admission-time authorization
is sufficient for ordinary requests: a request already admitted may finish after a concurrent revocation; the next
request is freshly checked and refused. Remove locking and test expectations whose sole purpose is to serialize
that hypothetical revocation race through an ordinary command's commit. Preserve locking required for actual
business consistency. Stronger contracts need a separately justified operation requirement, not a universal default.

### Creation IDs and ordinary failure recovery

The creation entry adapter generates the typed aggregate ID and puts it in the command; the aggregate accepts that
identity. Command execution remains `void`. After successful execution the adapter can return the known ID without
a mutable command result, an extra result DTO, or a fetch merely to recover an identity it already knows.

Ordinary creation does not promise transparent replay or an immutable original response. If a command commits and
the response is lost, another creation attempt may fail on unique fields; a refresh or fresh list/detail query
reveals authoritative state and the created Project ID. Remove ordinary-create original-response snapshots,
original-result journals and generic replay machinery where they exist only to support the superseded guarantee.
Do not confuse removal of retry bookkeeping with removal of independently required audit.

Genuine multi-resource operations, including filesystem creation, Git initialization and remote publication,
retain explicitly justified durable intent, partial-outcome and reconciliation contracts. This EPIC does not apply
ordinary database-create recovery to those workflows or invent a replacement general-purpose operation framework.

### Typed reads and shared failure handling

Provide explicit safe typed Views such as `ProjectView`, including appropriate Project and Git-source facts.
Read results are not persistence rows or raw entities. Keep PHP members descriptive and camelCase; HTTP
Data/Responder classes own snake_case JSON, status, headers and representation formatting. Console and MCP own
their respective presentation. Source metadata must not imply physical checkout availability or expose credentials.

Use qualified Common Application failure categories directly where their intent fits, including `ResourceNotFound`
for a required missing-resource query. Repository lookups remain aggregate-or-null; optional discovery states
remain explicit. Domain exceptions stay Domain-owned and do not extend Application categories. Internal faults
must not be relabeled as expected not-found/conflict outcomes. Retain local subtypes only for a useful additional
contract, not duplicated generic vocabulary.

Adopt Common's safe HTTP error boundary with deliberate public projections and one redaction-aware reporting
owner. Reconcile status, headers, validation, JSend shapes and frontend consumers explicitly; Common's expected
failures use `fail`, which is not automatically the existing Agent OS contract. Do not stack competing reporting
or error systems after verified replacement. MCP and other protocols require their own mappings, not HTTP errors
copied into another transport.

### Upstream coordination and availability

Common's inspected TASK-00183 through TASK-00192 plan aggregate-first rules, a separate DBAL
`TransactionalUnitOfWork`, repository/handler separation, domain classification, adapter organization and descriptive
names. Common's local `v1.4.0` tag and release notes already contain Application failure categories and safe HTTP
handling; Agent OS currently requires `~1.3.0`. These observations identify adoption work, not a remotely verified
release, a qualified dependency update or implemented DBAL support.

Access Control's inspected EPIC-00015 and EPIC-00016 cover architecture/canonical Common adoption and library-wide
typing, dispatch, query-result and intentional-failure contracts. Those are upstream plans, including concurrent
local planning changes, not consumer acceptance. Coordinate with their owners instead of duplicating their work.

Explicit handler-owned atomic audit for custom Role mutations is a concrete additional upstream requirement.
The inspected package handlers lack an audit dependency and `AuditEvidence` supports User/Agent, not Role subjects.
Agent OS's `RoleMutationUnitOfWork` currently inserts audit by inspecting a transaction callback's returned event.
Its permanent replacement belongs in explicit package handler coordination, not another specialized UoW, nested
consumer transaction, repository interception or post-commit subscriber. The separate upstream audit grill owns
its API and required/optional-injection decisions. Preserve required mutation/audit atomicity while replacing the
consumer decorator and its superseded local machinery; DBAL transaction support alone does not close this gap.

Plan against these capabilities now. Adopt actual supported/tagged APIs only after verifying their signatures,
behavior, release/source identity and real Agent OS composition; deliberately update the manifest and lock.
Unavailable suppliers hold affected slices only, not unrelated local corrections. Do not invent future version
numbers, use development snapshots as stable dependencies, patch vendor code or build temporary imitation layers.
Package compatibility obligations remain with their owners; this EPIC authorizes no sibling source change or release.

### Application compatibility and data

Agent OS is an application, not a library. Backward compatibility is not a standing obligation at any stage,
including production. Deliberately break PHP APIs, HTTP contracts, permissions and schemas when the agreed design
requires it, updating owned callers/tests/current plans together and removing obsolete paths. Do not add aliases,
legacy modes, dual implementations or deprecation machinery solely to preserve an abandoned application design.

This does not authorize data loss. Establish whether any real durable data needs preservation, an explicit schema/
data migration, or an authorized disposal decision. Preserve needed identities/history and required current
reconstruction contracts. Document observable breaking changes and operator/consumer obligations truthfully.

## Acceptance and evidence

- Account for the whole PHP application and all unfinished planning records through a traceable review and bounded
  corrections, not sample-only completion. Keep execution inventories in existing task evidence rather than adding
  a parallel permanent backlog. Each corrected or retained boundary has an actual responsibility and justification.
- Project, its ID, repository, messages, handlers, Views, persistence, entry adapters and owned callers use the
  agreed vocabulary and contracts. Registration is not modeled as an accidental aggregate or mixed Store.
- Handler-owned transactions, repository collection behavior, shared connection and required business/audit
  atomicity hold in real persistence composition. Success-event timing and uncertain/post-commit outcomes remain
  explicit. Superseded forwarding layers, transaction decorators and redundant implementations are removed after
  their replacements are proven; unavailable upstream audit support is a named incomplete dependency.
- Every supported entry path proves its authentication/admission and bus dispatch. Ordinary commands have no
  redundant Application admission gate or revocation-race serialization requirement introduced by prior guidance.
- Creation uses ID-bearing void commands and the agreed uniqueness/fresh-query reconciliation behavior. Tests and
  docs no longer promise original-response replay for ordinary creates; genuine multi-resource recovery and required
  audit retain their separately justified guarantees.
- Safe typed reads and shared failure categories preserve intentional absence, internal-fault distinctions,
  protocol correctness and non-disclosure. Qualified shared error handling replaces redundant local handling;
  public response changes and owned frontend/transport callers agree.
- Canonical upstream APIs have exact available-release/source/lock and real consumer verification evidence. Actual
  missing suppliers hold only their consumers. No guessed imports, snapshot aliases or duplicate package workflows.
- Governing instructions, current architecture/product docs and unfinished EPIC/TICKET/TASK requirements agree with
  these decisions. Historical evidence remains truthful; implementation and future design are distinguished.
- Each implementation slice preserves or replaces meaningful behavioral coverage at its owning boundary, runs
  focused checks and the canonical gate with fresh/reused evidence correctly identified, and obtains independent
  Review and applicable QA. Changed expectations for replay/authorization timing are deliberate policy changes,
  not tests deleted merely to obtain a pass. Use owning tools for dependency/namespace/documentation/planning checks;
  do not add architecture, wiring or tooling tests to the product suite.
