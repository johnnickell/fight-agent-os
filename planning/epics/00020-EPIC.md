# Keep delivery handoffs synchronized through Land

## Destination

Make the shared Land workflow own synchronization of current delivery routing and documentation, so a
maintainer receives a truthful next action instead of an obsolete publication or human-merge handoff.
Synchronize applicable authored Board, Roadmap and README handoffs as well as generated planning views.
Preserve historical acceptance evidence and delivery-pending checkpoints without presenting them as live state.

Read-only routing verifies the relevant live PR state before repeating a delivery/merge instruction. When a
handoff has ended, routing identifies the observed state and returns reconciliation to Land rather than editing
tracked files itself. Human merge remains a separate action; observing it does not grant merge authority.

This is one shared-contract destination with conditional script/documentation alignment in the ten named
projects below. It is not a broader project-adoption programme or the managed database Workflow implementation
owned by [EPIC-00008](00008-EPIC.md).

## Decisions and exclusions

### Approved ownership and evidence boundary

- Land reconciles current routing and documentation during authorized landing, including authored handoffs
  that parent rollups and generated-view refreshes do not cover. Do not leave that known synchronization work
  for a later `next` invocation to discover.
- Land also owns the correction when a later read-only routing check detects an ended merge handoff. Routing
  reports the relevant live observation and exact reconciliation handoff, then stops without changing files or
  automatically invoking Land.
- Distinguish implementation acceptance, publication, final delivery verification, human review/merge and later
  reconciliation. `done` is not evidence of merge. An ended merge handoff cannot remain the current instruction
  merely because it was truthful at an earlier checkpoint.
- Preserve canonical review/QA evidence, accepted-candidate provenance and historical completion notes. A tracked
  delivery-pending checkpoint remains historical evidence; current routing must be distinguishable from it.
  Do not rewrite an old report to claim that it reviewed a later head or observed a later merge.
- Observe PR identity and live state for the relevant handoff. Open, merged, closed-unmerged and unavailable or
  ambiguous evidence must remain distinguishable. Closed-unmerged is not successful merge; unavailable evidence
  is explicitly unverified and names the recovery action rather than assuming either merged or still open.
- Reconciliation is limited to truthful current handoffs and their derived views. It does not silently change
  requirements, priority, acceptance, Won't Fix decisions or unrelated project planning.

### Validation boundary

- Keep ordinary planning validation offline and deterministic. Normal checks and generated-view refreshes must
  not acquire an implicit network or hosting-credential dependency.
- Require targeted live PR verification when Land or routing evaluates a delivery/merge handoff. Bound it to
  the relevant handoff rather than auditing every historical PR or project on each routing request.
- Align planning-check scripts and `planning/CONVENTIONS.md` where necessary to support and explain this shared
  contract. Reuse adequate existing safeguards; do not rewrite working implementations solely for uniformity.
- Qualify Fight Common's reported TASK-00176 generated routing summaries, delivery markers and
  `--check-delivery` behavior as implementation reference evidence before reuse. This grill has not verified
  that implementation or established compatibility in the other projects. Exact command and representation
  choices belong to subsequent decomposition, not this EPIC's approval.
- Verify tooling directly with its owning commands and bounded workflow probes, following
  [planning conventions](../CONVENTIONS.md#board-and-generated-views). Do not add product-suite tests of planning
  text, wrappers or validation tooling. Implementation still requires each affected project's applicable gates
  and independent acceptance; planning approval supplies none of that evidence.

### Exclusions and existing authorities

- No automatic PR approval or merge, force push, release, deployment, archive or remote-branch deletion.
- No historical-evidence rewriting, acceptance weakening, unrelated cleanup, or adoption work beyond the
  necessary shared Land/routing contract alignment.
- No application database records, managed Workflow state machine, background PR watcher, or fleet-wide audit
  service. This destination concerns the current Markdown-authoritative planning and shared skill workflows.
- No TICKETs, TASKs, prototypes, implementation branches or worktrees are created by this grill. Decomposition
  and implementation remain separate operations.

Existing behavior and the gap are grounded in the [Land skill](../../.pi/skills/land/SKILL.md),
[landing standards](../../docs/engineering/LANDING.md#verify-and-publish),
[lightweight read-only routing](../CONVENTIONS.md#lightweight-work-routing), and
[handoff rules](../../docs/engineering/HANDOFFS.md). They currently provide parent/generated-view refreshes,
separate human merge control and historical delivery checkpoints; this EPIC adds explicit ownership of current
handoff synchronization without replacing those evidence and authority boundaries.

## Observable completion

- An authorized landing reconciles all applicable current Board/Roadmap/README handoffs and generated planning
  views for its subject, while historical acceptance and delivery checkpoints remain intact and identifiable.
- Routing confronted with a still-open PR returns a verified current action. Routing confronted with an ended
  merge handoff does not repeat it: it reports merged or closed-unmerged accurately and hands the needed
  correction to Land without modifying tracked files.
- Missing credentials, inaccessible hosting evidence or ambiguous PR identity produce an explicit unverified
  result and recovery action, never an inferred merge or silently refreshed current-state claim.
- Ordinary planning validation remains usable without live hosting access; handoff-specific live validation is
  exercised separately. Land's corrective result leaves current documents consistent without manufacturing new
  acceptance evidence or treating correction as authority to merge.
- Each of the ten projects has a recorded alignment disposition and verification evidence, or an explicit
  unresolved blocker. Necessary changes use isolated worktrees and do not create per-project TASKs. An unchecked
  project is not counted as aligned.
