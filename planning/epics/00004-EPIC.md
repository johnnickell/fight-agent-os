# Deliver the invite-only authenticated application shell

## Destination

Deliver the first usable browser experience for the private Fight Agent OS: invite-only account activation, secure email/password authentication, long-lived but bounded remembered sessions, self-service password and session security, permission-controlled user invitations, and an honest responsive dashboard shell. Extend that secure foundation with installation-wide user lifecycle, role and read-only permission administration through explicit later TICKETs; no administrative operation may precede its security prerequisites. Use Fight Access Control as the authoritative identity and authorization model and the architecture established by [EPIC-00003](00003-EPIC.md).

The foundation serves one private installation/workspace. It proves the application shell, authorization projection, accessible authentication states, light/dark design language, and operational invitation recovery without pretending that planning, observability, or agent-session dashboard data already exists.

## Decisions and exclusions

- Resolve [WF-005](../wayfinder/tickets/WF-005-design-authentication-and-authorization-journeys.md) with invite-only account creation. Do not expose public self-registration.
- Provide a `ROLE_SUPER_ADMIN`-authorized web experience to list safe user state, invite a canonical email, inspect invitation delivery status, retry or resend delivery, and atomically correct a pending invitation address. Resending revokes the predecessor grant. Never expose raw activation or reset credentials in UI, APIs, logs, analytics, screenshots, or diagnostics.
- Provide a trusted console path to invite a regular user and a separate one-time initial Super Admin bootstrap. Reconcile managed policy first, allow bootstrap only while no Super Admin authority exists, create a pending identity assigned the managed Super Admin role, audit a distinct console/bootstrap actor, and use the normal activation journey. Refuse later bootstrap attempts; administrators never choose user passwords.
- Use a development mail catcher rather than printing credentials. Production delivery remains recoverable from durable invitation/reset delivery state.
- Treat the first deployment as one private installation/workspace. Identities, roles, and permissions are installation-wide. Do not claim multi-tenant isolation or add unused tenant columns. Multiple workspaces and project membership require later explicit domain and migration work.
- Reconcile two version-controlled managed roles: `ROLE_USER` and `ROLE_SUPER_ADMIN`. The former planned `LIST_USERS` is explicitly renamed to `READ_USERS` before policy implementation; `INVITE_USERS` remains an intent-specific pending invitation grant, not general `CREATE_USERS`. Exact catalog, stable IDs, managed memberships and rollout references are owned by TICKET-00015 and the new administrative TICKETs. Do not silently rename an already deployed authority record.
- Give `ROLE_USER` only `VIEW_DASHBOARD` and the approved self-service `READ_OWN_SESSIONS`/`DELETE_OWN_SESSIONS`; `/api/v1/me` needs authentication but no dashboard permission. Give `ROLE_SUPER_ADMIN` these and the approved installation-wide security permissions, including `READ_USERS`, `INVITE_USERS`, `MANAGE_USER_INVITATIONS`, `ASSIGN_SUPER_ADMIN`, `REMOVE_SUPER_ADMIN`, lifecycle, cross-user session, user-role, role-CRUD, role-permission and permission-read capabilities. Authentication and own-target enforcement remain necessary. Ordinary invitations assign only `ROLE_USER`; inviting or assigning managed `ROLE_SUPER_ADMIN` requires distinct `ASSIGN_SUPER_ADMIN`, explicit confirmation and durable audit evidence; direct role assignment additionally requires `MANAGE_USER_ROLES`; removing the managed Super Admin role separately requires `REMOVE_SUPER_ADMIN`, explicit confirmation, audit and last-active-admin/self-change protection.
- Authenticate active users by canonical email and password. Return generic failures that do not reveal whether an identity exists or is pending, disabled, or deleted. Apply bounded throttling and support password managers, paste, accessible labels, and recovery navigation. Defer usernames, magic links, social login, SSO, MFA, and passkeys.
- Keep the 15-minute access JWT in client memory only and send it as Bearer authorization. Keep the rotating opaque refresh credential only in a secure HttpOnly cookie. Never persist credentials in `localStorage`.
- Use a one-day idle/two-day absolute ordinary session with a browser-session cookie. A selected “Keep me signed in” option uses a persistent rotating refresh cookie with a 30-day idle and one-year absolute lifetime. Refresh activity advances idle expiry but never absolute expiry. Logout, revocation, credential or identity changes, and detected refresh reuse may terminate authority sooner.
- Protect ambient-cookie login, refresh, and logout operations with secure cookie policy, exact Origin checks, Fetch Metadata where supported, JSON-only expectations, and explicit CSRF protection. Bearer-authenticated API calls remain independently authorized server-side.
- Coordinate refresh across browser tabs with the Web Locks API on secure origins and BroadcastChannel. One tab refreshes and broadcasts memory-only access authority, principal-refresh signals, or terminal logout. Broadcast logout and authority invalidation to every tab. Use bounded timeouts and a conservative fallback with Fight Access Control’s single refresh-conflict retry; never loop indefinitely or store tokens for coordination.
- After login or refresh, obtain current roles and permissions from an authoritative `/api/v1/me` projection resolved through the request-scoped current-principal boundary. Do not add authorization snapshots to Fight Access Control `TokenSet`, access JWTs, or HTML hidden fields. Cache the projection only for the active client session and invalidate/refetch it after refresh or authority-changing operations. Keep non-sensitive runtime configuration in a separate typed contract.
- Logout revokes only the current refresh session and clears browser authority. Let users list their own active sessions with coarse device/activity/expiry information, identify the current session, and revoke another session after confirmation. Current-session revocation remains the Logout journey. Defer “log out everywhere” and cross-user Super Admin session administration.
- Include generic password-reset request and one-time reset completion. Successful reset revokes every active session and requires fresh login. Include authenticated password change after current-password proof, with session invalidation according to Fight Access Control policy. Defer email-address change and account deletion/restoration UI.
- Apply one password policy to activation, reset, and change: 8–128 characters with at least one uppercase letter, lowercase letter, number, and symbol; allow spaces, Unicode, paste, and password managers; hash with Argon2id; and do not impose periodic expiration.
- Reject known-common passwords through a project-owned capability backed initially by a pinned, checksummed, license-reviewed local hashed denylist. Perform deterministic local checks without runtime network access, never log candidate passwords or lookup material, and record corpus provenance and required third-party notice.
- Use Fight Access Control’s seven-day invitation and one-hour reset grant lifetimes. Grants remain purpose-bound, single-use, hashed at rest, and replaced rather than reused. Use canonical HTTPS links, redact credential-bearing URLs, suppress referrer leakage, remove captured grant material from visible browser history promptly, and give expired/used/invalid grants generic recovery guidance.
- Prefer trusted HTTPS in local development so secure-cookie and browser-security behavior resembles production. Require HTTPS elsewhere. Use same-origin browser/API deployment with CORS disabled until an approved external client requires it.
- Require rate limits for login, password reset, activation, refresh, and invitation delivery actions; generic public responses; secret-free correlated server diagnostics; compatible CSP and standard security headers; externally supplied signing, encryption, and CSRF secrets; production startup failure on missing or weak secrets; and durable audit evidence for sensitive security and administrative actions.
- Provide public routes for Login, Activate Invitation, Request Password Reset, and Complete Password Reset. Provide authenticated Dashboard, Account/Security, Change Password, and Active Sessions routes. Provide Super Admin Users, Invite User, and Pending Invitation Status/Recovery routes.
- Route `/` to Login when anonymous and Dashboard when authenticated. Preserve a safe intended protected route through login, never secret form values. Treat `401` as authentication restoration/login and `403` as an authenticated forbidden state. Provide accessible safe states for unknown routes, expired grants, expired/revoked sessions, validation failures, delivery failures, and system errors.
- Make the dashboard an honest authenticated shell: accepted responsive visual language, navigation, current-user controls, permission-aware links, account/session links, and authorized invitation/user shortcuts. Explain that planning and observability capabilities are not installed; do not display fake charts, metrics, or records.
- Complete disposable design-language exploration and independent design review before production UI implementation. Meet WCAG 2.2 AA expectations for contrast, semantics, labels, keyboard operation, visible and unobscured focus, target sizes, reflow, and accessible authentication. Support narrow/mobile and wide/desktop layouts, reduced motion, and complete loading, empty, validation, authentication failure, forbidden, system error, success, expired-link, and expired-session states.
- Ship light and dark production modes using semantic tokens and Bootstrap mappings. Theme choice has `system`, `light`, and `dark` states, defaults to and tracks the OS in system mode, and stores only an explicit presentation preference in `localStorage`. The compact selector must have an accessible name, keyboard operation, and visible current state. Defer RTL until localization requires it.
- Keep Vitest/React Testing Library and Storybook as the primary frontend behavior and visual-review surfaces. Limit automated browser coverage to critical smoke journeys and behavior that cannot be proved below the browser boundary.
- Add subsequent installation-wide administration TICKETs for safe `GetUserById`, disable/enable/delete/restore, role assignments, cross-user sessions, role CRUD and read-only permission catalog. Custom-role permission delegation waits for an inspected, tagged Fight Access Control release and an Agent OS non-HTTP authorization boundary; a route attribute alone cannot authorize target/tier changes. Package cross-user session, email-change administration and pending-invitation correction capabilities continue to ask the consumer about actor/target ownership; future workspace/repository admin scopes must be separately modelled and bounded, not inferred from a global role.
- Defer multiple workspaces, project-scoped authorization, `ROLE_ADMIN`, direct active-email change, unrestricted `CREATE_USERS`/`UPDATE_USERS` and profile mutation without supported fields, general permission creation/update/deletion, “log out everywhere,” MFA/passkeys, alternate login methods, planning/observability data, agent-session data, RTL and broad browser automation. Tier labels alone do not enforce delegation eligibility.
- Defer exact CSRF mechanism, rate thresholds, local HTTPS tooling, mail provider, denylist corpus, cookie names, schemas, and implementation slicing to TICKET/TASK planning.
