# Coordinate one TASK through implementation

## Destination

Deliver the first production coordinated-execution slice. An authorized human selects one eligible TASK and
confirms **Start coordinated work**; the application atomically revalidates eligibility, exclusively claims that
TASK, creates and dispatches one durable Workflow, and lets a managed Coordinator direct one distinct managed
Builder in a Workflow-owned isolated worktree.

The Builder implements the approved TASK revision, runs its required checks, creates an implementation commit,
and submits a complete commit-specific durable handoff. The Workflow then stops authoritatively at **Awaiting
review** with its claim, branch, worktree, Pi sessions, events, observations, evidence, Artifacts, usage, recovery
state, and next human action preserved.

Make current and historical work understandable through the accepted sessions-first Dashboard and an honest
dynamic completion forecast through Awaiting review. Exercise the production capability on one real Fight Agent
OS TASK; do not create a disposable runner, Workflow type, proof endpoint, alternate persistence path, or
certification suite.

## Decisions and exclusions

- Consume the closed [Complete Fight Agent OS vision map](../wayfinder/complete-agent-os-vision-map.md), especially
  [WF-015](../wayfinder/tickets/WF-015-define-coordinated-task-authority-protocol.md) through
  [WF-019](../wayfinder/tickets/WF-019-select-end-to-end-proof-and-epic-handoff.md), plus the applicable onboarding
  and runtime boundaries from [WF-020](../wayfinder/tickets/WF-020-define-developer-onboarding-and-operator-guidance.md)
  and [WF-023](../wayfinder/tickets/WF-023-define-local-runtime-and-shared-ingress-topology.md), without reopening
  their product decisions.
- Depend on [EPIC-00005](00005-EPIC.md) for registered repository/checkout identity, resolved context,
  PostgreSQL-authoritative Planning, and the canonical eligibility query. Depend on
  [EPIC-00006](00006-EPIC.md) for released Harness resources and snapshots, managed profile templates, Agent
  identity/credential boundaries, and trusted MCP integration. Preserve EPIC-00003/00004 persistence, API,
  React, authentication, authorization, security, and quality foundations.
- Activate only Coordinator and Builder execution in this EPIC. Coordinator validates the Workflow grant,
  current authority, immutable context/Harness snapshots, checkout, limits, and handoffs; it neither edits the
  implementation nor reviews or publishes it. Builder owns implementation, tests, required checks, and commits
  in its isolated worktree; it cannot accept, publish, or expand its own scope.
- Keep Coordinator and Builder as separately authenticated Agents with separate direct Permissions, HMAC
  credentials, profiles, tool sets, and recoverable Pi session lineages. No process or session changes role,
  inherits the Coordinator credential, or gains authority from a Skill, prompt, profile, local instruction, or
  Workflow observation.
- Use the same server-authoritative **Start coordinated work** application operation from browser and console.
  Atomically rerun the canonical Planning eligibility query against the selected TASK revision, validate the
  explicit grant, create one Workflow and durable dispatch intent, and acquire the exclusive TASK claim before
  returning `202 Accepted` and the Workflow identity.
- Make start idempotent by command identity. Repeating the same confirmed start returns the same Workflow;
  competing starts fail with the current owner and a stable understandable eligibility reason. One active
  Workflow claim may own a TASK, and the durable claim is not released merely because a process, lease, runner,
  browser, or network connection disappears.
- Record the selected Repository/TASK/revision, configured base, initiating user, Coordinator, profiles, immutable
  context/Harness snapshots, provider/model choices, grant, time/cost boundaries, process-attempt allowance, and
  future review-revision allowance at start. This EPIC exposes and executes authority only through Awaiting
  review; Reviewer, revision, acceptance, and publication operations remain unavailable until EPIC-00008 extends
  the same production Workflow under the accepted grant and live authority checks.
- Represent one explicit human grant as one event-sourced `Workflow`. Queueing, safe process retry/resumption,
  runner takeover, pause, Needs Human continuation, implementation, and Awaiting review remain within it.
  Cancellation or terminal failure closes it permanently; later human-authorized work creates a linked Workflow
  rather than reopening history. A reasoned limit extension appends a grant instead of rewriting one.
- Keep intent-specific application Commands as the only Workflow authority. Authenticate the actor and validate
  grant, expected revisions, claim/lease, immutable Git/evidence subject, limits, context, and relevant
  observations before appending semantic events. Queue rows, runner/Pi reports, logs, Git inspection, heartbeats,
  observations, Mercure messages, and Dashboard state never transition the Workflow by themselves.
- Use Fight Common event-store and asynchronous-command contracts with the application-owned metadata,
  idempotency, transactional command-critical constraints, durable intents, projections, and reconciliation they
  do not provide automatically. External effects follow durable intent → idempotent effect → verified result →
  authoritative completion; uncertain outcomes pause or require a human instead of becoming fictional success.
- Dispatch by Workflow identity through the dedicated PostgreSQL Doctrine Messenger Agent transport and failed
  queue. Delivery is at least once; a reconciler resolves uncertain dispatch from durable intent. Queued work may
  safely wait for a compatible enabled Runner and must display that fact rather than imply execution.
- Run one explicitly enrolled installation-owned `agent-runner` Compose service with a durable Runner identity,
  bounded health/capability declarations, and three supervised one-shot Agent consumers by default. Each consumer
  handles at most one Workflow command and exits. Runner/container/process instance identities support recovery
  without requiring repeated pairing or becoming authority.
- Admit at most three Workflows concurrently by default, configurable only through explicit bounded installation
  settings. Independent TASKs may run concurrently when branches, worktrees, temporary paths, Pi sessions,
  Artifacts, and declared shared resources do not conflict. Use short checkout-administration locks and explicit
  policy resource claims rather than a repository-wide Workflow lock.
- Mount only explicitly approved Workspace roots into the Runner, preferably at identical absolute paths. Before
  work, resolve and verify registered Host, Checkout, Worktree, and Repository identity, canonical path,
  containment, Agent OS marker, Git common directory, ownership, and availability. Reject ambiguity, symlink
  escape, moved/unavailable checkouts, or unapproved roots.
- Create one `feature/<description>` branch from the configured base and one Workflow-owned isolated worktree.
  Never repurpose, clean, stash, reset, rebase, merge, switch, or discard a human-owned checkout. Shared Git
  object/reference storage is accidental-damage containment, not hostile multi-tenant isolation.
- Give each managed Pi session a Workflow-specific filesystem view: its owned worktree and TASK Artifacts are
  writable; required Harness/runtime content is read-only; private temporary storage is isolated; and unrelated
  roots, worktrees, environment files, credentials, and process state are unavailable.
- Keep required Pi `read`, `edit`, `write`, and `bash` capabilities, but canonicalize and observe file/tool access
  through the trusted Harness and enforce shell execution with an OS-level per-Workflow sandbox. Managed work
  fails closed when sandbox initialization fails and offers no model-selectable bypass.
- Deny general network access from sandboxed shell by default. Route authenticated external effects through
  permission-filtered Agent OS tools. Package traffic may use explicit installation-controlled egress; model
  transport remains infrastructure traffic with observable usage. Include the accepted bounded first-party web
  search query and separately permissioned SSRF-protected retrieval seam without granting direct provider keys.
- Keep Runner, database, Messenger, Mercure, provider, source-host, object-storage, and application credentials out
  of Pi child environments, files, output, transcripts, events, logs, and Artifacts. Bind a Runner-owned protected
  credential broker to the actual Workflow, Agent, profile revision, and Pi session; it performs authorized MCP
  calls and HMAC authentication without exposing raw secrets or arbitrary signing.
- Persist a logical `PhaseAttempt` for each Coordinator or Builder invocation, technical `ProcessAttempt` records
  for Pi launches/resumptions, and role-bound `AgentConversation` records for protected Pi session lineages.
  Preserve one recoverable Coordinator lineage and normally one Builder lineage through implementation, pause,
  retry, and safe recovery. A missing/incompatible session creates a linked successor; no role resumes another
  role's conversation.
- Before launch, persist process identity, role/phase, Agent/session, checkout/worktree, bounded command,
  redacted-environment manifest, lease owner, start time, and checkpoint. Add PID/process-group evidence after
  spawn. Supervise complete process groups, redact/checkpoint output before observation, and store large safe
  output as private Artifacts rather than unbounded event payloads.
- Use a renewable Coordinator lease only to establish who may advance the durable Workflow. Lease expiry pauses
  dispatch and enables authorized recovery of the same Workflow; it never releases the TASK or creates another
  attempt. Transport keepalive and delivery state do not replace the application lease.
- Permit one initial Pi process launch plus up to two safe resumptions per phase by default. Snapshot the effective
  authorized installation limit when queued. Do not blindly retry authentication, Permission, configuration,
  exhausted-budget, missing-evidence, unsafe-repository, or uncertain-side-effect failures. Exhaustion retains
  the claim and evidence in Needs Human.
- Make pause, cancel, disable/halt Runner, disable/halt all Runners, resume, takeover, terminal failure, and cleanup
  distinct authorized operations. Pause preserves the claim and resources; cancellation releases the claim only
  after every child is stopped or proved absent; disable drains current work; halt requests safe pauses. Failed or
  interrupted work is never silently deleted.
- On graceful or abrupt restart, reconcile durable Workflow, claim, lease, transport, process, Git/worktree, Pi
  session, checkpoint, external-effect, Artifact, and handoff evidence before resuming. Never launch a duplicate
  while an earlier effect or process outcome is uncertain; safe cases resume automatically and uncertainty enters
  Needs Human with a concrete next action.
- Require the Builder handoff to identify Workflow, TASK and revision, Repository/Checkout/Worktree, Builder role
  and session, immutable context/Harness snapshots, configured base, full base/head commit IDs, branch, complete
  status and changed-tree manifests, selected ignored Artifacts/digests, required commands/checks with fresh
  results, warnings, limitations, evidence, and the next role's bounded authority.
- Treat a branch name, moving branch head, chat transcript, process result, or future PR as insufficient handoff
  identity. The Coordinator rereads authoritative state and fails closed on stale, partial, ambiguous, mismatched,
  or superseded input before transitioning to Awaiting review.
- Keep authoritative Workflow events compact and semantic. Store sanitized operational activity in a separately
  identified observation ledger where useful; observations may be delayed, duplicated, missing, reordered, or
  purged and can never grant authority. Recovery depends on authoritative state and reconciled evidence, not
  complete telemetry.
- Keep Pi's persisted JSONL tree authoritative only for reconstructing Pi model context. Store an opaque
  runner-resolvable reference plus role, Agent, profile/Harness/context revisions, format version, lineage,
  lifecycle, and integrity facts. Do not ingest, index, search, or expose raw prompts, model responses, hidden
  reasoning, provider signatures, complete transcripts, or unsanitized payloads in the Dashboard.
- Store non-trivial evidence bytes behind the application-owned private S3-compatible Artifact capability backed
  locally by SeaweedFS. PostgreSQL owns immutable Artifact identity, digest, size, media type, provenance,
  sensitivity, links, holds, and purge tombstone. Replacing content creates another Artifact; permission-filtered
  bounded previews/downloads never expose private storage directly.
- Retain authoritative Workflow history, grants, handoffs, Git/commit references, verification summaries, usage
  totals, and Artifact metadata as project history. Hold evidence while active Planning requires it. Give Pi
  resume material, bulky observations, and logs a configurable post-terminal cleanup grace period, initially 30
  days, subject to explicit holds, early authorized deletion, prohibited-content redaction, backup limits, and
  immutable tombstone evidence.
- Record provider, requested/reported model, Harness/profile/context revisions, Pi version, available response or
  session identity, and provider-reported input/output/cache/reasoning/token/cost facts with provenance. Distinguish
  unavailable from zero and separate wall elapsed, known active, queue, interrupted, and human-wait time rather
  than manufacturing precision.
- Build idempotent rebuildable Workflow list/detail/live projections and publish only committed projection updates
  through Mercure. Reconnecting clients reload durable queries before following updates. Projection or live-update
  failure does not alter aggregate state.
- Deliver the accepted sessions-first browser experience: compact repository-scoped current/archive Workflow
  lists with stable cursor pagination; independently loaded Summary, Changes, Activity, and Evidence sections;
  immutable bounded syntax-highlighted `base…head` changes; visible authoritative-versus-observational distinction;
  and explicit loading, empty, denied, stale, partial, interrupted, cancelled, failed, purged, and unavailable
  states.
- Keep archive/restore as visibility only. It never pauses, resumes, cancels, approves, or executes a Workflow. A
  running archived Workflow remains visible in an independent Running now summary; if that cannot be guaranteed,
  disallow active archive. Planning conversations remain in Planning and are linked, not presented as execution
  history.
- Show an updating remaining-time range through Awaiting review with confidence, last update, and a concise reason
  after material change. It may use phase/queue state, attempts, observed activity, failures/retries, comparable
  phase history, and broad defaults; it may increase. Show Waiting for human, Paused, or Unable to estimate when a
  range would be dishonest, separate active work from queue/human wait, and never treat Agent self-report as
  measured fact.
- Retain actual-versus-predicted duration needed to calibrate later forecasts without making forecasts Workflow
  authority. Exact cohorts, defaults, confidence thresholds, algorithms, and copy remain downstream requirements
  and implementation choices.
- Test important owned authorization, eligibility, claim exclusivity, semantic transition, command idempotency,
  stale handoff, durable dispatch, bounded retry, cancellation/quiescence, recovery, Artifact/privacy, and
  projection behavior. Manually run the integrated production path on one real Fight Agent OS TASK and preserve
  its ordinary evidence. Distinguish automated, manual, historical, and incomplete verification honestly.
- Exclude Reviewer execution, Review verdicts, Builder revision cycles driven by findings, acceptance, Publisher,
  push/PR creation, merge observation/reconciliation, post-publication cleanup, multi-TASK continuation, stacked
  PRs, remote Runner fleets, hostile multi-tenant isolation, dynamic preview environments, merge automation,
  release, deployment, and certification. EPIC-00008 extends this same Workflow rather than replacing it.
- Defer exact schemas, Commands/events, API routes, Permission identifiers, queue/lease/grace intervals, model and
  provider assignments, budget values, sandbox package, egress configuration, resource-lock catalog, forecast
  math, cursor encoding, diff thresholds, UI components, and implementation slices to TICKET and TASK
  decomposition. Open a new Wayfinder decision only for genuinely new product uncertainty.
