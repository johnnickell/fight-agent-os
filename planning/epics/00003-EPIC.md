# Establish the web application architecture foundation

## Destination

Establish the architecture and delivery conventions for the first usable Fight Agent OS web application so authentication, authorization, sessions, and the early dashboard can be planned and implemented against explicit boundaries. Use Fight Access Control as the authoritative identity and authorization Domain/Application model while Agent OS owns framework integration, persistence, HTTP delivery, external effects, composition, and genuinely application-specific orchestration.

Deliver a versioned Slim JSON API and React client foundation with contract-first PostgreSQL persistence, layered validation and safe error handling, explicit CQRS and Adapter organization, deterministic behavior-focused tests, and a production-backed component catalog. Keep exact authentication journeys and tenant policy for the next Wayfinder decision.

## Decisions and exclusions

- Resolve [WF-004](../wayfinder/tickets/WF-004-define-application-foundation-architecture.md) using the conventions below; retain the reviewed source conventions from [WF-001](../wayfinder/tickets/WF-001-recover-source-conventions.md) and the dependency direction from [WF-003](../wayfinder/tickets/WF-003-qualify-dependency-baseline.md).
- Use Fight Access Control Domain/Application commands, queries, entities, policies, views, and capability interfaces directly for package-owned behavior. Do not recreate or wrap package types merely to rename them. Add `App\Application` orchestration only for application-specific or cross-boundary use cases.
- Organize owned Domain and Application code by context and feature or aggregate. Use imperative command names, intent-revealing query names, past-tense event names, and matching `Handler` classes.
- Organize Adapter code capability-first, then subdivide semantically when directories grow. Expected roots include `src/Adapter/Repository`, `src/Adapter/Http/Api/V1`, `src/Adapter/Http/Web`, `src/Adapter/Http/Mcp`, `src/Adapter/Http/Middleware`, and `src/Adapter/Console`. API-v1 Actions are FQCN route handlers; `/mcp` has a separate future HMAC boundary, not a JWT exception.
- Use one final Action per HTTP interaction. An Action maps transport input and dispatches one command, query, or explicit orchestrator; it contains no business policy or persistence. An endpoint-specific Responder owns the successful representation.
- Add a Slim post-routing, pre-Action validation middleware that evaluates `#[Validation]`. Invalid JSON, request shape, and declared transport constraints return sanitized `400 Bad Request` JSend `fail` responses with dotted field paths and message lists. Domain types still enforce invariants outside HTTP.
- Use a shared `ErrorResponder` and centralized exception mapping for known validation, authentication, authorization, conflict, and resource-not-found failures. Do not map generic `LookupException` to `404`. Log unknown `Throwable`s with correlation context and return a generic sanitized `500`; never expose arbitrary exception messages. Actions catch only documented endpoint-specific overrides.
- Serve JSON APIs under `/api/v1`. After Slim routing inspect matched FQCN Action security metadata without eager Action instantiation; JWT is the default for protected operations, with explicitly marked credential-flow exceptions. Route attributes provide early authentication/permission checks; Agent OS Application authorization and package actor/target/intrinsic safeguards protect the actual use cases, including non-HTTP callers. Use JSend envelopes, explicit safe View/response models rather than entities, `snake_case` transport fields, and explicit mapping to camelCase PHP/TypeScript properties. Describe endpoints and schemas in OpenAPI; restrict Swagger UI appropriately.
- Consider a proven generally reusable Slim validation/error adapter for later promotion to Fight Common through separately authorized package work. Agent OS must not depend on an unreleased upstream change.
- Standardize PostgreSQL as the durable local, integration-test, and production database contract. SQLite is allowed only for genuinely database-independent unit or explicitly portable tests; it is not evidence for production persistence or concurrency.
- Use Doctrine Migrations as the sole schema-evolution mechanism. Do not create schemas during application requests. Use `snake_case` database identifiers and enforce authoritative uniqueness and references in the database.
- Use `DoctrineTransactionalUnitOfWork::commitTransactional()` as the canonical transaction boundary. Implement repositories contract-first: prefer ORM mappings when they faithfully enforce the contract, and use ORM versioning, pessimistic locking, conditional updates, or targeted DBAL on the same connection where required. Prove concurrency-sensitive contracts against PostgreSQL.
- Do not event-source Access Control state. Keep event sourcing available for a later demonstrated need, including potentially mineable agent-session activity, without introducing an event store, projectors, or workers speculatively.
- Commit database invariants and required durable delivery intent together. Do not perform email, HTTP, filesystem publication, or other external effects inside the database transaction. Dispatch post-commit events for immediate coordination; required effects need durable recovery for the commit/dispatch crash window. Document retry, idempotency, and at-least-once behavior without claiming exactly-once delivery.
- Structure the React client by responsibility: Routes own matching and navigation guards; Layouts own shell/navigation/outlets; Pages coordinate one journey and local state; Components/forms own interaction and feedback; feature API services own typed operations and boundary mapping; one shared API client owns transport, credentials, refresh coordination, cancellation, and common error normalization.
- Expose an authoritative safe current-principal projection to a shared client authorization service. Route metadata declares complete-route permissions, while Layouts, Pages, and Components use the same service for fine-grained visibility or disabled states. Unknown permission state fails closed. Client checks never replace server authorization.
- Give client state its narrowest authoritative owner: URL state for shareable navigation/filter/sort/page state, local state for transient interaction, an API cache for server-owned data and the current principal, and shared context only for true application-wide concerns. Persist preferences only for a defined requirement; never keep business/workflow state solely in browser storage.
- Use Storybook as the durable browser catalog for accepted React/Bootstrap components, semantic tokens, themes, assets, and relevant states. Keep disposable design specimens as exploration evidence and recreate accepted decisions in production components. Use Vitest and React Testing Library as the primary frontend test surface; keep automated browser tests limited to critical smoke journeys and behavior that cannot be proved below the browser boundary.
- Make unit tests the dominant suite and require 100% line coverage for meaningful owned Domain/Application behavior, including rejection and failure paths. Measure Adapter coverage separately with an honest threshold and exclude only generated or explicitly justified composition code.
- Use focused PostgreSQL integration tests for mappings, migrations, constraints, transactions, locking, and competing writes. Use deterministic clocks, ID generators, builders, and null/in-memory outbound adapters in a testing container. Maintain a small functional suite for critical HTTP journeys, middleware/error behavior, boot, unknown-route, and safe-error boundaries. Test databases must be isolated, migrated, reset deterministically, and structurally unable to target development or production.
- Remove inherited support-receipt tests and fixtures only as meaningful application tests replace them. Do not repeat Fight Common or Fight Access Control package suites inside Agent OS, and do not accept network-, timing-, ordering-, or shared-state-dependent flaky tests.
- Defer registration, login, refresh/logout, session lifetime, cookies/tokens, CSRF, tenant/workspace/project scope, initial roles and permissions, and dashboard contents to [WF-005](../wayfinder/tickets/WF-005-design-authentication-and-authorization-journeys.md).
- Defer exact schemas, migrations, dependency/tool versions, Adapter coverage threshold, durable-delivery mechanism, and implementation slicing to TICKET/TASK decomposition after the remaining Wayfinder decisions close.
