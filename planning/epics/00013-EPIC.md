# Support release TASKs and project-specific release Workflows

## Destination

Give a registered project one recoverable, Team Lead-coordinated Workflow for each concrete release candidate:
a library version to sign, tag and publish on GitHub, or an application revision to deploy to a named production
environment. Introduce `release` as a standalone Planning TASK kind rather than creating an EPIC or TICKET for
each version/deployment. Team Lead prepares and coordinates every authorized non-human step; a qualified,
project-owned release policy/runbook supplies the actual procedure. The human signs where required and may give
one bounded approval for the named external effects of an exact certified candidate. Only verified completion of
all required effects, checks and project-specific follow-through makes the release TASK `done`.

Deliver both library and application paths in stages after their relevant project policies and runtime
capabilities are qualified. No generic deployment operation, signing capability or release authority is
assumed merely because this EPIC is approved.

## Decisions and exclusions

- Consume the closed [SDLC intake triage map](../wayfinder/sdlc-intake-triage-map.md), especially
  [WF-028 — Define triage dispatch and hotfix role boundaries](../wayfinder/tickets/WF-028-define-triage-dispatch-and-hotfix-role-boundaries.md)
  and [WF-027 — Define TASK triage readiness and classification](../wayfinder/tickets/WF-027-define-task-triage-readiness-and-classification.md).
  Extend [Planning conventions](../CONVENTIONS.md) and the eventual canonical eligibility capability for a
  standalone `release` kind. This is a prospective, approved category/route addition to the initial
  feature/bugfix/chore catalog of [EPIC-00012](00012-EPIC.md), not a reinterpretation of `chore` or a second
  readiness gate. Until the kind, route and release policy exist, return unsupported instead of silently
  dispatching a release through an ordinary implementation Workflow.
- One release TASK identifies a concrete version or named deployment target and intended project. Preparation,
  documentation, source integration, certification, human interventions, permitted external effects,
  post-effect verification and recovery are stages of the **same** Workflow and TASK. Resolve the exact source
  commit and target identities before effect approval; do not pretend an early candidate or clean working tree
  is certified release evidence. Do not generate one TASK for signing, tagging, publishing, deploying, or
  merge-back. Record partial, failed and uncertain stages honestly rather than marking a TASK `done` on an
  attempted tag/deploy or requiring a new TASK to resume.
- At Repository setup, configure and version the project's release type, release line/branching strategy,
  required environment or registry/host identities, supported procedure and named verification and rollback
  expectations. Resolve a project-owned runbook for that exact release; missing, incompatible, stale or
  unqualified configuration prevents effects. A library may require an accepted release PR, an exact certified
  merge commit, an interactively signed tag, a verified remote tag and GitHub release, plus registry projection
  if its runbook requires it. An application may require an exact deployable build/commit, separately authorized
  production deployment, health verification and rollback/forward options. Do not assume all projects have
  GitHub releases, Packagist, or the same deployment mechanism.
- Reuse [WF-015's single-TASK Workflow authority](../wayfinder/tickets/WF-015-define-coordinated-task-authority-protocol.md),
  [EPIC-00007](00007-EPIC.md)/[EPIC-00008](00008-EPIC.md)'s durable start, evidence, independent assessment,
  isolated execution and recovery boundaries, and the separate [Team roles](../../docs/engineering/TEAM.md).
  The human's authorized release start request may pass Triage automatically into the distinct release Workflow
  once supported. Triage/Jev can classify but cannot invent a runbook, release plan or Permission, approve a
  release, claim on its own, or turn a TASK landing grant into signing, tagging or deployment authority.
- Team Lead is the accountable coordinator and human contact. It prepares all non-human work within granted
  authority: inspect current repository/provider state, plan the release, arrange required independent review
  of changed material, run project-owned readiness checks and certification, assemble exact effect requests,
  monitor/reconcile outcomes and report blockers. A separate Release Manager performs only the publication or
  deployment effects covered by its direct Permissions and current grant; Team Lead's role/prompt does not
  confer Release Manager credentials. An Agent cannot independently accept its own implementation or certify
  evidence it materially contributed to. Human signing uses the operator's own trusted terminal/key; neither
  Team Lead nor Release Manager receives signing secrets or treats a signature claim as verified proof.
- Once the candidate is certified, offer **one bounded human approval** that names its exact version/tag or
  deployable commit, repository/environment, permitted effects, limits and relevant release evidence. The
  human's separate interactive signing step remains where required. Do not demand another routine confirmation
  per approved stage: Team Lead continues autonomously within that grant and current project policy. Require
  renewed authorization only for a changed subject/target, a new external effect, a specific risk/check
  exception or an exhausted grant. Signing, local tag, remote tag, GitHub release, deployment and registry
  visibility are separate observed facts, not interchangeable evidence or implied permission. Human PR merge,
  signing and effect approval are not supplied by starting the Workflow.
- Apply the Repository's configured GitFlow, trunk-based or custom strategy. When policy requires merge-back or
  forward-port after a verified release, keep it in the **same release Workflow**, without another TASK. Use
  only an applicable bounded approval and verified source/target identity; protected-branch rules, conflicts
  and changed authority pause the operation. Trunk-based repositories with no separate development branch
  have no automatic GitFlow merge-back. Do not force-push, retarget signed tags, merge unrelated unfinished
  changes, or assert a merge from an unverified provider observation.
- Persist stage identity, current TASK/Repository/runbook/configuration and grant revisions, exact candidate,
  certification, human signing handoff, effect intents and verified results for resume. Duplicate delivery or
  an uncertain network/process outcome must inspect authoritative/provider state before retrying; it must not
  create duplicate tags, GitHub releases or production deployments. Permission revocation, failed certification,
  failed required checks, unverified health or unavailable effect status enter a visible blocked/recovery state
  with a concrete next action. Record publication and deployment provenance separately from TASK implementation
  acceptance and ordinary PR landing.
- Validate owned release-kind eligibility, catalog selection, scoped start/approval, exact-candidate drift,
  human-signing handoff, independent acceptance, idempotency, observed provider effects, deployment/health
  outcomes, partial failure and safe recovery against representative library and application runbooks. Qualify
  external signing, provider, registry and deployment contracts with their owning tools and actual evidence;
  never test planning Markdown, migration syntax, configuration wiring or test infrastructure as product
  behavior. Defer exact provider adapters, runbook schema, phase/event names, UI controls and delivery slices to
  TICKET/TASK decomposition; do not generalize one project's release commands into a universal executor.
- Exclude automatic signing, autonomous PR approval/merge, open-ended publication/deployment rights, automatic
  rollback without scoped authority, retroactive alteration of existing TASK landing, extra release-stage TASKs,
  and changes to [EPIC-00012](00012-EPIC.md)'s hotfix route. Application deployment is distinct from publishing
  a library and from merging an implementation PR. A release EPIC is not itself a live release or production
  enrollment.
