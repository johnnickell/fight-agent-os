# Deliver browser Planning Agents and the trusted Harness

## Destination

Deliver the production Harness and browser Agent foundation on top of the registered PostgreSQL-authoritative
Planning workspace. An authenticated authorized user can start or resume a durable repository-scoped Planning
conversation, work with a managed Project Manager or Explorer, review editable structured proposals, and explicitly apply
accepted Wayfinder or EPIC → TICKET → TASK changes through the same semantic Planning operations used by direct
editing.

Distribute one exact versioned Pi Harness package, resolve immutable repository and Harness snapshots, serve
verified trusted Skills through the first-party Agent OS MCP origin, and support managed and authorized custom
Workspace resources without allowing instructions or profiles to grant authority. Initially verify OpenRouter and
Pi's local `openai-codex` subscription path as independent provider choices. The browser receives no provider or
Agent credentials.

The completed EPIC is used for real Fight Agent OS Planning rather than a disposable conversation proof. It
establishes the trusted package, identities, profiles, resources, provider boundary, durable proposals, and
conversation continuity later coding and support EPICs consume, but it runs no coding workflow itself.

- Implement Harness as its own bounded context. It owns type-specific Skills, Themes, prompts, Agent personas,
  Agent profile templates, trusted MCP origins, releases, user Harness profiles, and deterministic session resource
  snapshots. It does not own Repository policy, Planning authority, Access Control, or Execution.
- Keep `fight-agent-os` as the canonical monorepo and place independently versioned Pi npm package source under

  only as an explicit visibly mutable development mode.

  **Fight Agent OS** wordmark on its welcome screen, drawing from the existing light/dark assets in `docs/assets/`.
  Compare expressive ASCII/Unicode art with a rendered logo where the selected terminal and Pi renderer support

- Separate machine-local connection profiles from revisioned database-backed user Harness profiles. Connection

  release/development mode. User profiles contain only non-secret resource, theme, alias, persona, model-default,

- Resolve one immutable `HarnessSnapshot` beside the `RepositoryContextSnapshot` for each Agent session. Record
  connection/profile revisions, package version and digest, selected resource revisions and aliases, provider,
  requested/reported model, origin identities, and Skill manifests. Never silently refresh an active snapshot;
  drift requires an explicit linked continuation.

  identity—not `localhost`, hostname, repository content, or transport location—is authority. Reject dynamic,
  unverifiable, digest-mismatched, oversized, cross-origin, silently substituted, or manifest-extending Skills.

  resolve supporting resources only within that held manifest/origin, and keep origin-separated cache outside Pi
  filesystem Skill discovery. Cache is disposable and never authority.
- Reserve `agent-os-*` names for packaged bootstrap resources. Keep general development Skills database-authoritative
  and MCP-served, with immutable revisions and managed/custom distinction. Reconcile reviewed managed definitions
  idempotently without overwriting custom resources; make retirement, rollback, and any later purge explicit.
- Preserve useful short aliases while surfacing every personal/project/MCP collision. Filesystem resources win a
  bare alias over MCP only with visible collision evidence and access to the qualified alternative; personal versus
  project collisions require a picker or saved choice rather than silent Pi discovery order.
- Include the reusable instruction-writing Skill adapted with attribution from Matt Pocock's MIT-licensed
  `writing-for-agents`. It may support Planning prose now and later instruction editing, terminal use, and Skill
  authoring, but this EPIC does not deliver a general browser-assisted Skill-authoring product or mutate repository
  instruction files.
- Define the eight managed Agent profile templates in [Team roles](../../docs/engineering/TEAM.md): Project
  Manager, Explorer, Team Lead, Software Engineer, Senior Engineer, QA Engineer, Release Manager and Hotfix Engineer.
  Provision and run only the separately authenticated Explorer and Project Manager identities in this EPIC;
  later coordinated-execution EPICs activate the other profiles under their accepted authority and independence
  rules.
- Keep profile templates semantic and revisioned. They may request resources, model defaults, operating constraints,
  repository applicability, and direct Permissions, but they are not Access Control Roles and cannot grant
  authority. Managed-bound Agents reconcile only through reviewed complete desired Permission sets; custom-template
  inheritance changes require explicit proposals and choices.
- Use separate Agent identities and exactly one active HMAC credential per real credential-holder boundary.
  Provision, store, verify, rotate, and remove interactive Agent keys through an injected operating-system
  credential-store capability without displaying or copying raw secrets. Never place raw keys in packages,
  repository files, database profiles, transcripts, session files, logs, events, evidence, or environment files.
- Preserve Skills and `allowed-tools` as non-authoritative requests. Effective tools remain the intersection of
  live permission-filtered discovery, server authorization, delegated conversation authority, and session/host
  constraints. Live Permission revocation overrides every pinned snapshot immediately.
- Deliver durable repository-scoped Planning intake and conversations as accepted by
  [WF-012](../wayfinder/tickets/WF-012-define-browser-planning-and-conversation-ownership.md). Keep one bounded Agent
  turn active per conversation; preserve transcript, accepted answers, progress, proposal state, context/Harness
  snapshots, initiating user, acting Agent, and internal Pi-session lineage across browser disconnects and process
  replacement.
- Preserve Wayfinder, grill, `to-tickets`, and `to-tasks` as distinct operations even when browser navigation is
  continuous. An intake does not create a map automatically; completing a Wayfinder interview does not create an
  EPIC until the separate grill proposal is accepted; decomposition never silently follows artifact creation.
- Keep Agent-authored proposals separate from authoritative Planning revisions. Show editable structured previews,
  require explicit human Create/Apply actions, submit expected revisions, apply multi-record decomposition
  atomically, reject stale proposals without losing conversation history, and require review of any AI-assisted
  reconciliation.
- Let Agents perform factual inspection and bounded preparation while the user is away, but never choose product,
  priority, boundary, or risk preferences; accept their own proposal; invoke guarded lifecycle operations; or begin
  another Planning operation without required authority and human action.
- Make conversation visibility owner-first. Other authorized repository planners see accepted artifacts, accepted
  decisions, and progress by default; transcript/drafts require explicit share or handoff. Preserve completed and
  abandoned history, allow explicit Stop and confirmed Abandon, and provide only narrowly authorized redaction or
  retention operations.
- Initially support OpenRouter through a protected installation-held API key and administrator-managed allowed-model
  catalog. Support local Codex through Pi's authenticated `openai-codex` provider and the accepted local
  credential-store/Pi ownership boundary. Neither path is mandatory when the other is configured, but both paths
  must be independently qualified before claiming initial support.
- Let installation administrators configure connections and allowed models, profiles choose defaults, and
  authorized users select another allowed provider/model when a conversation starts. Do not silently fail over or
  replace a provider in an active conversation. An explicit provider change creates a linked continuation with a
  newly resolved immutable snapshot.
- Record provider, requested/reported model, profile and Harness revisions, available response/session identity,
  and provider-reported token, cache, reasoning, usage, currency, and cost facts when available. Distinguish
  unavailable from zero, retain provenance, and never invent pricing or sum cumulative streaming values repeatedly.
- Present honest Planning progress using known decision units and operation stages rather than tokens, turns,
  elapsed time, or fabricated percentages. Show interruption, retry, stale context, unavailable provider, denied
  authority, and uncertain command outcomes explicitly and resolve an uncertain apply before offering another.
- Test important owned trust, manifest, collision, revision, delegation, authorization, idempotency, stale proposal,
  provider-continuation, credential-boundary, and recovery behavior. Exercise both provider paths and a real Fight
  Agent OS Planning operation manually. Do not duplicate browser/framework/package-manager/configuration tests or
  build a disposable proof/certification path.
- Exclude Software Engineer coding, Runner dispatch, Workflow claims or execution history, review/publication, completion
  forecasting, starter-based project creation, repository instruction mutation/publication/synchronization,
  arbitrary third-party MCP origins, dynamic Skills, additional provider qualification, simultaneous co-editing,
  comments/mentions, persistent direct-edit drafts, and automatic proposal acceptance.
- Defer exact schemas, API routes, MCP wire DTOs, package/registry names, model allowlists, budgets, UI components,
  permission identifiers, process topology, cache paths, release automation, and implementation slices to TICKET

### First milestone: deterministic controls and Jev screening

- Apply operator-selected, versioned restrictions to supported tools, allowed working roots, protected paths and
  destructive/external effects. Keep permissions and deterministic denials authoritative; a model judgment cannot
  expand them. Protect policy and extension resources from Agent writes. A working directory setting alone does
  not confine a shell, scripts or subprocesses.
- Intercept supported tool calls before execution and use Jev to assess semantic risks after deterministic checks.
  Block denied operations and stop an action when its required evaluation fails, times out or returns malformed
  output. Surface uncertainty for the configured operator decision; never silently allow it or retry an equivalent
  effect through another tool. Do not reuse the file relevance threshold as a safety or authorization threshold.
- Declare and directly qualify interception coverage, including read/write/edit/bash and execution nested inside
  other tools where supported. Report unsupported routes, extension disablement and residual shell risks explicitly.
  Prompt instructions alone are not enforcement and interim protection is not full sandbox qualification.
- Show permitted/blocked decisions with useful reasons and redacted evidence. Bind evaluations to the actual
  proposed operation and relevant revisions; reject stale results. A denial is distinct from an unavailable
  evaluator. Qualification must exercise the real supported Pi integration and failure behavior.

### First milestone: required file relevance screening

Provide `jev_read_file` for a path, a bounded set of paths or a glob, the information sought, and a typed question.
Use a specific yes/no question by default, such as "Does this file define how execution grants are revoked?"
Allow explicit classification choices with an unknown/other exit. The tool reads authorized content for Jev;
its response keeps that content out of the main Agent context and returns judgments with provenance instead.

- Require all participating Agents and sub-agents to screen files before discovery reads, singly or in batches.
  Establish the rule in the shared Harness system instructions and reinforce it in skills that prescribe file
  investigation, once the tool is available. Prefer metadata/frontmatter and path/symbol/graph candidates before
  screening a broad corpus. This requirement governs Agent behavior initially; it does not claim enforced read
  interception. Later enforcement may require a screening receipt for the same file revision and information need.
- Set the initial positive-read bar to **0.70**. For a yes/no relevance question, require `noul >= 0.70`, the
  reported probability of Yes. For classification, require a predeclared relevant choice with reported confidence
  at least 0.70. A confident irrelevant/No result never satisfies the bar. These are distinct provider measures,
  not a proven 70% accuracy guarantee; qualify both and version any later policy changes.
- A complete positive result permits reading the relevant sections; load the whole file only when the work needs
  it. A result below the bar does not automatically permit a full read. Narrow the information need, consult
  metadata or structural search, or use a documented required-evidence exception; do not repeatedly rephrase the
  same question until it passes. Failed, unknown or partial evaluation is explicitly unresolved, never evidence
  that the file lacks the answer.
- Preserve direct loading of mandatory governing instructions and selected skill instructions. Allow bounded,
  exact-source reads needed to edit, quote or verify known evidence. If that obligation requires a full file despite
  a negative/unavailable screen, record the obligation and reason; ordinary discovery cannot silently use this
  exception. Do not make a model relevance judgment the authority for whether an Agent follows instructions or
  verifies acceptance evidence. During an outage, report degraded screening and use only the documented bounded
  search/required-evidence path, not an unreported bulk-read fallback.
- A known-target direct read may skip screening when an explicitly assigned file, verified symbol/search result
  or established edit/quote/verification target supplies concrete evidence of the exact file needed. Record the
  path, purpose and evidence in the working trace; read the smallest useful range, and the whole file only when
  required by that purpose. Self-reported certainty, familiarity or a plausible filename is not evidence. Reassess
  if the target/source/need changes; uncertainty returns to screening. Each file needs its own justification,
  including in a batch. This exception never overrides permissions or sensitive-file restrictions. See the
  [file-screening requirement](../tickets/00039-TICKET.md) for the owning contract.
- Return the question, judgment, reported probability/confidence as applicable, exact content digest/revision,
  coverage and skipped/error reasons. Evaluate each file independently for batch permission; a positive result
  for one file does not authorize the whole batch. Identify any chunking or incomplete coverage. A partial
  evaluation cannot claim a complete negative or qualify a whole-file read through the normal positive path.
- Enforce authorized roots and canonical containment, including symlink escape prevention, before reading or
  sending content. Restrict sensitive files and provider egress according to the configured policy. Bound files,
  bytes/tokens, concurrency, elapsed time and spend; report exclusions instead of claiming a complete corpus scan.
  Provider access is separate from permission to read a file locally.
- Cache by authorized scope, content digest, question/choices, evaluator identity and policy version. Recheck current
  access before serving results; content, question or policy changes invalidate reuse. Keep source revisions
  inspectable and do not fabricate supporting quotations or line references from a typed answer.
- Measure main-Agent context saved alongside total evaluator cost/latency, missed relevant files, unnecessary reads,
  incomplete coverage and outage behavior. Include threshold boundary cases and representative multi-file work.
  Treat 0.70 as the initial operating policy to evaluate, not measured savings or a reason to hide false negatives.
