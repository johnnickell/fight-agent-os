## Destination

Deliver the production Harness and browser Agent foundation on top of the registered PostgreSQL-authoritative
Planning workspace. An authenticated authorized user can start or resume a durable repository-scoped Planning
conversation, work with a managed Project Manager or Explorer, review editable structured proposals, and explicitly apply
accepted Wayfinder or EPIC → TICKET → TASK changes through the same semantic Planning operations used by direct
editing.

Distribute one exact versioned Pi Harness package, resolve immutable repository and Harness snapshots, serve
verified trusted Skills through the first-party Agent OS MCP origin, and support managed and authorized custom
Workspace resources without allowing instructions or profiles to grant authority. Initially verify OpenRouter and
Pi's local `openai-codex` subscription path as independent provider choices. The browser receives no provider or
Agent credentials.

The completed EPIC is used for real Fight Agent OS Planning rather than a disposable conversation proof. It
establishes the trusted package, identities, profiles, resources, provider boundary, durable proposals, and
conversation continuity later coding and support EPICs consume, but it runs no coding workflow itself. The later
Jev amendments also deliver incremental terminal safeguards, context continuity and advisory assessment for
human-operated sessions; review assistance does not implement managed review acceptance or publication.

### First milestone: deterministic controls and Jev screening

- Apply operator-selected, versioned restrictions to supported tools, allowed working roots, protected paths and
  destructive/external effects. Keep permissions and deterministic denials authoritative; a model judgment cannot
  expand them. Protect policy and extension resources from Agent writes. A working directory setting alone does
  not confine a shell, scripts or subprocesses.
- Intercept supported tool calls before execution and use Jev to assess semantic risks after deterministic checks.
  Block denied operations and stop an action when its required evaluation fails, times out or returns malformed
  output. Surface uncertainty for the configured operator decision; never silently allow it or retry an equivalent
  effect through another tool. Do not reuse the file relevance threshold as a safety or authorization threshold.
- Declare and directly qualify interception coverage, including read/write/edit/bash and execution nested inside
  other tools where supported. Report unsupported routes, extension disablement and residual shell risks explicitly.
  Prompt instructions alone are not enforcement and interim protection is not full sandbox qualification.
- Show permitted/blocked decisions with useful reasons and redacted evidence. Bind evaluations to the actual
  proposed operation and relevant revisions; reject stale results. A denial is distinct from an unavailable
  evaluator. Qualification must exercise the real supported Pi integration and failure behavior.

### First milestone: required file relevance screening

Provide `jev_read_file` for a path, a bounded set of paths or a glob, the information sought, and a typed question.
Use a specific yes/no question by default, such as "Does this file define how execution grants are revoked?"
Allow explicit classification choices with an unknown/other exit. The tool reads authorized content for Jev;
its response keeps that content out of the main Agent context and returns judgments with provenance instead.

- Require all participating Agents and sub-agents to screen files before discovery reads, singly or in batches.
  Establish the rule in the shared Harness system instructions and reinforce it in skills that prescribe file
  investigation, once the tool is available. Prefer metadata/frontmatter and path/symbol/graph candidates before
  screening a broad corpus. This requirement governs Agent behavior initially; it does not claim enforced read
  interception. The approved TASK-00309 follow-up below requires current screening receipts or validated
  exceptions in a qualified local profile; initial TASK-00162/00163 delivery remains instruction-based.
- Set the initial positive-read bar to **0.70**. For a yes/no relevance question, require `noul >= 0.70`, the
  reported probability of Yes. For classification, require a predeclared relevant choice with reported confidence
  at least 0.70. A confident irrelevant/No result never satisfies the bar. These are distinct provider measures,
  not a proven 70% accuracy guarantee; qualify both and version any later policy changes.
- A complete positive result permits reading the relevant sections; load the whole file only when the work needs
  it. A result below the bar does not automatically permit a full read. Narrow the information need, consult
  metadata or structural search, or use a documented required-evidence exception; do not repeatedly rephrase the
  same question until it passes. Failed, unknown or partial evaluation is explicitly unresolved, never evidence
  that the file lacks the answer.
- Preserve direct loading of mandatory governing instructions and selected skill instructions. Allow bounded,
  exact-source reads needed to edit, quote or verify known evidence. If that obligation requires a full file despite
  a negative/unavailable screen, record the obligation and reason; ordinary discovery cannot silently use this
  exception. Do not make a model relevance judgment the authority for whether an Agent follows instructions or
  verifies acceptance evidence. During an outage, report degraded screening and use only the documented bounded
  search/required-evidence path, not an unreported bulk-read fallback.
- A known-target direct read may skip screening when an explicitly assigned file, verified symbol/search result
  or established edit/quote/verification target supplies concrete evidence of the exact file needed. Record the
  path, purpose and evidence in the working trace; read the smallest useful range, and the whole file only when
  required by that purpose. Self-reported certainty, familiarity or a plausible filename is not evidence. Reassess
  if the target/source/need changes; uncertainty returns to screening. Each file needs its own justification,
  including in a batch. This exception never overrides permissions or sensitive-file restrictions. See the
  [file-screening requirement](../tickets/00039-TICKET.md) for the owning contract.
- Return the question, judgment, reported probability/confidence as applicable, exact content digest/revision,
  coverage and skipped/error reasons. Evaluate each file independently for batch permission; a positive result
  for one file does not authorize the whole batch. Identify any chunking or incomplete coverage. A partial
  evaluation cannot claim a complete negative or qualify a whole-file read through the normal positive path.
- Enforce authorized roots and canonical containment, including symlink escape prevention, before reading or
  sending content. Restrict sensitive files and provider egress according to the configured policy. Bound files,
  bytes/tokens, concurrency, elapsed time and spend; report exclusions instead of claiming a complete corpus scan.
  Provider access is separate from permission to read a file locally.
- Cache by authorized scope, content digest, question/choices, evaluator identity and policy version. Recheck current
  access before serving results; content, question or policy changes invalidate reuse. Keep source revisions
  inspectable and do not fabricate supporting quotations or line references from a typed answer.
- Measure main-Agent context saved alongside total evaluator cost/latency, missed relevant files, unnecessary reads,
  incomplete coverage and outage behavior. Include threshold boundary cases and representative multi-file work.
  Treat 0.70 as the initial operating policy to evaluate, not measured savings or a reason to hide false negatives.
