# Run four independently cached verification passes with PHP-native tooling

## Destination

Reduce the time humans and agents wait for checks without weakening what those checks prove. Pilot four independent passes in Fight Agent OS. Local skills select the checks affected by the change; GitHub runs the passes in parallel. A planning-only change needs no application stack or application tests. Preserve the current checks and measure the improvement before using the pilot as the standard for other projects.

## Decisions and exclusions

### Four passes, one set of owning checks

| Pass | Owns |
|---|---|
| PHP | PHP syntax, style, static analysis, dependency rules, generated API contract freshness, and PHPUnit. Enforce 100% Unit-only line coverage of owned unit-testable behavior. Keep integration and functional coverage; combined results do not satisfy the Unit target. |
| Frontend | Client type, style, test, production build, and Storybook checks. Own the real HTTPS browser smoke tests and run them once when a change on either side can affect the journeys they cover. Preserve the database and mail-catcher behavior those journeys verify. |
| Pi Harness | Harness and vendored subagent engine checks, including affected native behavior and packaging checks. Checks and probes may use Node and TypeScript; they do not have to be PHP. |
| Planning | Fast Markdown record and generated-view validation. Validation is read-only by default; refreshing views remains explicit. |

Assign other live repository checks to the pass whose contract they verify. A shared input can select more than one pass. Use one change-selection policy for skills and CI. Report the comparison base and why each pass was selected or not affected. If history or input classification is uncertain, run the affected checks conservatively rather than reporting a skip. Keep an explicit full run for broad changes and qualification.

Give each pass its own input fingerprint and verifiable successful-run receipt. Include relevant source, tests, shared inputs, configuration, dependency and tool identity, and the evidence needed to validate reuse. Missing, failed, interrupted, or unverifiable evidence is not a hit. A pass can be forced fresh. Distinguish ran, reused, and not affected. Work, Review, QA, and Land may reuse checks without inheriting one another's judgments. In the pilot, reuse dependency downloads on GitHub where appropriate; do not use cross-run check-result caching to decide merges.

### Local Docker and native GitHub runners

- Keep `bin/*` as thin host entry points for humans and agents. Generally invoke the owning PHP entry point under `scripts/*` inside the running local Docker container. Do not require host PHP or Composer.
- Run `./bin/planning-check` in a lightweight one-shot container with no web stack, database, or frontend setup. Prepare the tooling image and any locked Composer dependencies explicitly; routine validation does not install them. PHP tooling may use namespaces, Composer autoloading, and third-party libraries where they simplify maintenance.
- Run four separate GitHub workflows with stable check names. Install each pass's required software on the runner and invoke its owning entry points directly, without starting Docker containers. Preserve the browser smoke environment with native services and disposable fixtures. Each workflow reports an explicit result even when not affected; a missing check is not a pass.
- After the Agent OS pilot proves selection and outcomes, require all four checks for merges into `develop` and `main`. Activation requires the actual repository setting and evidence that affected, unaffected, failed, and missing results behave as intended.

### Retire repository-owned Python tooling

Port live tools to PHP by responsibility, including planning, browser-smoke setup, Harness, QA, and local runtime. Trace callers before each port or removal. Preserve live entry points and safeguards, including resource ownership, isolation, failure handling, and cleanup. Remove obsolete tools instead of translating them; remove replaced implementations and their Python prerequisites once the replacement is verified. Keep the TypeScript client and Pi engine in TypeScript.

Keep the Python Diagrams authoring and rendering tools, maintained diagram sources, and their Graphviz dependency under [EPIC-00022](00022-EPIC.md). This is an explicit exception to Python removal and adds no Python prerequisite to the four verification passes or routine Harness operation. A PHP/Graphviz replacement is out of scope unless separately approved after it demonstrates comparable diagram quality and maintainability.

Do not make the full Python migration a prerequisite for splitting the checks. Move Python dependencies that directly affect a pass with that pass where practical. Do not depend on the unfinished Fight Access Control refactor or treat it as qualified. Compare actual entry points and CI behavior when its PHP implementation is runnable. Standardize check names, selection, evidence, and pass criteria first; share implementation only where real consumers need the same behavior. No automatic adoption in other repositories.

## Acceptance evidence

- Demonstrate PHP-only, frontend-only, Pi-only, planning-only, and shared-input changes on the pilot. Show that changes affecting a cross-stack journey select smoke, unrelated edits can reuse a valid local receipt, and a missing or uncertain result cannot create a false pass.
- Compare local and GitHub turnaround on representative changes and a cold run. Record durations, warnings, and gaps. Account for every existing mandatory check before retiring the old layout; do not leave both layouts as permanent gates.
- Show Unit-only coverage against the stated denominator and preserve integration and functional verification. The [current combined coverage gate](../../docs/engineering/BACKEND_TESTS.md#reports-and-policy) is not evidence of Unit-only compliance.
- Demonstrate planning on a local Docker host without PHP, all four workflows on container-free GitHub runners, and the replacement of live Python tooling outside the diagram-authoring exception through its supported entry points. Verify through owning commands and real use, not added product tests of wrappers or quality tools.
