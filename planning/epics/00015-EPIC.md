# Deliver mailbox-confirmed human email change

## Destination

An active Fight Agent OS user can request a change from their current sign-in email to a different address,
inspect its safe pending status, cancel it, receive a confirmation link at the **new** mailbox and complete the
change using the link's secret credential. An authorized Super Admin can request or cancel a change for another
active user under a distinct managed Permission, but cannot bypass confirmation at the new mailbox or directly
set the account's active email. The **old** mailbox receives security notifications when the change is requested
and when it completes, including for administrator-initiated changes.

The confirmation link carries a purpose-bound secret used in **two requests**: opening a safe confirmation page
does not consume the credential or mutate the account; an explicit user action submits that same credential
again and confirms the change exactly once. Confirmation promotes the new email, consumes the credential and
revokes existing sessions under Fight Access Control's package-owned policy. The result links to login; the user
must sign in with the **new email and existing password**, or initiate the separate password-reset journey if the
password is forgotten. Confirmation is not login, password reset, or a second mailbox-approval process.

## Decisions and exclusions

- This EPIC consumes the approved [WF-032 email-change resolution](../wayfinder/tickets/WF-032-reconcile-accesscontrol-coverage-and-accepted-scope.md)
  and the [consumer capability matrix](../wayfinder/research/WF-032-accesscontrol-consumer-capability-matrix.md)
  within the [AccessControl adoption map](../wayfinder/accesscontrol-consumer-adoption-map.md). It is an
  **explicit later extension** of [EPIC-00004](00004-EPIC.md)'s direct active-email-change deferral, not a
  retroactive change to that EPIC or to its accepted [user administration](../tickets/00030-TICKET.md),
  [invitation](../tickets/00021-TICKET.md) or [password recovery](../tickets/00019-TICKET.md) TICKETs. Reuse
  their real secure login, current principal, authorized user detail, shared browser/client security, existing
  password-reset journey and protected credential-delivery infrastructure. Do not claim they are already live.
- Use installed, qualified Fight Access Control public `RequestEmailChange`, `CancelEmailChange`,
  `DeliverEmailChange`, `ExpireEmailChange` and `AuthenticationService::confirmEmail()` contracts, the package
  User/reservation/grant authority, and its current single-use, time-limited credential and session-invalidation
  policy. Agent OS owns only necessary actor/target authorization, UI/API, composition, provider, operational
  recovery and justified cross-boundary orchestration per [ADR 0001](../adr/0001-application-ownership-and-orchestration.md)
  and [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md). At implementation, inspect the
  actual tagged/locked public contract, record its version/source and qualify the integration rather than
  treating this planning or an installed package test as working consumer evidence.
- Self-service request and cancellation derive the target from the authenticated **active** user; a caller
  cannot supply another user's ID on a self-service path. Cross-user request/cancel require a distinct managed
  `SUPER_ADMIN_ONLY` email-change administration Permission, initially granted only to `ROLE_SUPER_ADMIN`,
  and fresh server-side actor/target/scope checks at **every** HTTP and non-HTTP entry path, including the
  package's `EmailChangeAdministrationAuthorization` callback. Do not authorize by a role name, a client
  projection, generic `READ_USERS`/`UPDATE_USERS` or possession of an invitation-management Permission.
  Replace the current `UnavailableEmailChangeAdministration` denial only when the policy and integration are
  qualified. No future Workspace/Repository Admin gains an implicit right over another user's email.
- Require a new canonical destination distinct from the active address. Package-owned reservations, revisions,
  latest-grant succession, expiry and transaction fencing guard conflicts with other Users, pending invitations,
  other email changes, retry/delivery, cancellation and confirmation. Never silently overwrite a pending
  change, automatically switch an unverified address, or turn a pending invitation correction into an active
  user email change. Request/cancel/status interactions return bounded, authorized, safely redacted results;
  stale, already used, unavailable and expired changes have truthful recovery guidance. Provide appropriate
  confirmation and accessible loading/error/success states in the authenticated account and authorized user
  administration surfaces without inventing a general profile-edit API.
- The emailed new-mailbox link is a **bearer credential for this email-change confirmation only**. Opening its
  landing page may check validity to present a safe state but must not consume it, change the email, send a
  confirmation notice, sign the user in or expose private account data to scanners/prefetchers. The explicit
  confirmation action submits the **same** credential as protected input; the owning package atomically
  validates, consumes, promotes the address, invalidates authentication authority and revokes active sessions.
  A second visit/post, competing cancel, stale reservation, replaced grant or expired link cannot repeat the
  effect. The user need not already be signed in or supply their password to confirm: possession of the
  new-mailbox secret is the approved confirmation proof. Do not turn it into a reusable login or password-reset
  credential. No state-changing GET, automatic submit on page load, or extra password/new-email form.
- Protect token-bearing URLs as in the existing invitation/reset journeys: exact trusted HTTPS origin,
  no-store responses, restrictive referrer behavior, prompt removal of captured secret from visible history,
  bounded retry/throttling and no credential in page markup after capture, analytics, browser error telemetry,
  server/access logs, audit, screenshots or diagnostic output. Keep the token only as long as needed to perform
  the user-initiated confirmation, including safe failure/retry handling. Expired/invalid/used links receive
  generic non-enumerating guidance; any new request must use current authorized account/administrator controls.
- Deliver the purpose-bound confirmation credential **only to the new address** through package-owned encrypted
  recoverable delivery, with real configured provider, guarded due-work/retry, bounded expiry and sanitized safe
  operational status. Existing PostgreSQL grant/reservation storage and key-free expiry and the internal human
  delivery runner are partial infrastructure; email-change issuance/provider delivery is currently not
  registered, the runner skips that purpose, and no deployed schedule or production provider is enrolled.
  A locally simulated/null provider or issued grant is not proof that a person can complete the journey. Keep
  claims, raw material, ciphertext, worker state, retry controls and key operations off public/browser routes.
- Notify the **current/old** mailbox upon the accepted request and again after successful confirmation, for
  both self and administrator initiation. Notices are informational, secret-free and **not** required to
  confirm, approve or undo the change; the new-mailbox credential is never copied to the old address. A
  changed canonical address must not cause the completion notice to go to the new address instead. Provide a
  durable, recoverable, attributable intent/dispatch boundary for these *Agent OS-owned informational notices*,
  with stable notice identities and provider idempotency where qualified; an ambiguous provider outcome may
  still duplicate a notice and must not be reported as exactly-once delivery. Do not move package credential
  authority into a consumer outbox, perform a provider call inside a database transaction, or claim delivery
  succeeded when it has not. If the
  installed contract cannot safely coordinate an accepted request/confirmation with these notices, stop for
  explicit contract/owner resolution rather than silently dropping them or opening a crash window. Exact
  provider/schedule and failure policy belong to TICKET/TASK design, but a working product must not advertise
  notifications it cannot actually deliver.
- Preserve package attribution and an appropriately durable, redacted audit for own and administrator
  request/cancel, delivery outcomes and confirmation; admin activity remains distinguishable from target
  action. Show honest current pending/delivery status only to the owner or authorized administrator. Delivery
  success does not imply confirmation. On confirmed change, discard client authority, route to a login link,
  and use the existing password-reset request at the **new** address only if needed; never preserve an old
  session or grant a new one from the email-change token. Old-address notices are not password-reset links.
- Verify real PostgreSQL conflicting reservations and session invalidation, concurrent cancel/expiry/confirm,
  one-time token and safe GET/POST browser behavior, new/old mailbox recipient correctness, provider failure,
  restart/retry, redaction, both actor/target authorization paths and accessible complete UI states. Test
  owned behavior and important package/provider integration contracts with the actual qualified dependency,
  plus `./bin/build`; do not add product-suite tests of configuration, migrations, generated artifacts or
  planning/tooling text. Record redacted real consumer evidence and gaps; package fixture tests, existing grant
  rows and worker `status` do not establish live email change or a production email provider.
- Exclude public registration, arbitrary direct email editing, admin bypass of the new mailbox, general User
  profile mutation, changing another user's address with a self-service credential, login via confirmation
  link, reuse of that link for reset, credentials in old-address notices, automatic cancellation from old-mail
  links, an unqualified mail provider, or changes to existing invitation/password-reset owners beyond required
  shared integration. Exact routes, schema/notification mechanism, permission identifier, provider, schedule,
  page layout and implementation/PR slices follow in TICKET/TASK planning; the approved two-request
  confirmation and both old-mail notices do not.
