# Deliver the working managed Agent team

## Destination

Give Fight Agent OS a **usable, fully authorized Agent team**, not a seeded catalog, storage-only Agent row,
model demonstration or standalone security proof. An authorized Super Admin can establish a Team for a registered
Repository, instantiate distinctly named Agents from all eight reviewed managed SDLC templates, provision each
Agent's protected holder-bound credential, manage its lifecycle and roster, and use the first Team-assigned
Explorer to investigate the real Fight Agent OS designated checkout through its own authenticated, scoped tools.
The first Explorer can work from registered Markdown-authoritative context without waiting for the complete
browser Planning conversation or database Planning cutover. It never runs without a Team, and its initial real
work is not an isolated disposable harness.

**The completion bar is stronger than the first Explorer:** all eight roles must actually perform their intended
work under current authorization in integrated product journeys before the *managed Agent team* can be declared
operational. Project Manager performs real human-governed Planning; Team Lead and Software Engineer produce an
implementation handoff; Senior Engineer independently reviews; QA Engineer exercises reviewed behavior; Release
Manager handles qualified PR publication and applicable project-specific release effects; Explorer returns cited
research; Hotfix Engineer follows the confirmed emergency route with independent review and human PR control.
The separately approved Triage profile routes a human-selected TASK through the same authoritative start. A
versioned template or authenticated idle Agent alone does **not** satisfy any role's working outcome. Deliver the
Team/Agent capability and integrate the existing owned Workflow outcomes without creating another Workflow,
claim, review, release or certification engine in this EPIC.

## Decisions and exclusions

### Ownership and initial product journey

- Consume the [Complete AccessControl consumer adoption map](../wayfinder/accesscontrol-consumer-adoption-map.md),
  especially [WF-033](../wayfinder/tickets/WF-033-define-agent-operation-adoption-boundary.md) and
  [WF-035](../wayfinder/tickets/WF-035-define-project-teams-and-agent-selection.md), and its traceable
  [capability matrix](../wayfinder/research/WF-032-accesscontrol-consumer-capability-matrix.md). **Explicitly
  supersede their handoff split and no-Team prerequisite** at this EPIC boundary by maintainer approval: one
  combined Agent/Team destination; every instantiated Agent belongs to exactly one Team, including the first
  Explorer. The closed decision records remain historical. This does not silently amend their server authority,
  strict same-Team delegation, pending-intent or first-party trust protections.
- Depend on [EPIC-00005](00005-EPIC.md)'s real registered Repository, designated Checkout/Worktree, approved
  roots and effective versioned Repository context for repository-bound Agent work. First register Fight Agent
  OS itself, associate a Team, instantiate an Explorer from a versioned managed template and manually launch a
  bounded authenticated Pi Harness exploration of that designated checkout. Return source-cited findings and
  uncertainty without authoritative Planning edits, Workflow claims or unapproved repository mutations. This
  first working use does **not** require full Planning database cutover, browser Planning conversation or TASK
  Workflow; those are required where the later role-specific journey actually consumes them.
- Supply the shared identity, credential and Team boundary to [EPIC-00006](00006-EPIC.md)'s Harness, browser
  Planning Agents, templates, trusted first-party MCP resources and provider work; reuse their approved owners
  instead of duplicating a template registry, session platform or browser conversation engine. Coordinate real
  Team Lead/Engineer execution with [EPIC-00007](00007-EPIC.md), independent review/QA/PR handoff with
  [EPIC-00008](00008-EPIC.md), Triage/direct hotfix with [EPIC-00012](00012-EPIC.md), and actual qualified
  library/application release paths with [EPIC-00013](00013-EPIC.md). Those accepted records retain their
  implementation authority; this EPIC owns **missing Agent/Team integration and the complete role-use outcome**,
  not duplicate TASKs. An EPIC's terminal metadata or a local Skill is not evidence that a managed role is live.
- Establish all eight managed, reviewed, immutable template revisions (Project Manager, Explorer, Team Lead,
  Software Engineer, Senior Engineer, QA Engineer, Release Manager, Hotfix Engineer) as real Harness resources,
  with distinct purpose, applicable scope, requested tools/direct Permissions and safe model/provider choices.
  Also supply the separately approved distinct Triage template for actual human-selected routing. A template is
  not an AccessControl Role, Agent, credential or grant. All supported templates can create separately named
  Agent identities and truthful safe sessions; mark unavailable role actions clearly until their required live
  Workflow exists rather than offering a nonfunctional control. Do not wait for eight independent credential
  qualification ceremonies: every Agent uses the same fully qualified shared lifecycle.

### Team and Agent authority

- A Team may serve several explicitly associated registered Repositories; a Repository has one preferred
  default Team and may have others. Every Agent belongs to one Team at a time. Authorized Super Admin creation
  selects a reviewed template revision, friendly Agent name, Team and intended permitted Repository scope,
  previews a complete managed-template desired Permission set, and confirms provision intent. Distinct managed
  Team, Agent-creation/lifecycle and template-management Permissions are initially granted only to
  `ROLE_SUPER_ADMIN` and checked through current package/application actor/target authority, **not** role-name
  shortcuts; introducing them requires an explicitly authorized policy extension, not a silent edit to
  [TICKET-00015](../tickets/00015-TICKET.md)'s exact earlier catalog. Future Workspace/Repository/Project
  administrators need a separately approved scoped grant model; this EPIC neither creates those Roles nor
  pre-grants `ADMIN_SAFE` to arbitrary custom Roles or Agents.
- Offer an authorized safe Agent directory/detail, distinct Agent creation and name management, managed-template
  selection/Permission preview, guarded rotation/revocation and operation status, plus Team creation,
  Repository/default associations, membership and safe idle transfer with attributable history. Keep active
  sessions bound to their recorded Team/Agent and current revocation effective; no silent transfer, shared
  credential, forced activation, authority expansion or double booking. Admin pages and prompts never expose
  raw credentials, operation claims, sink material or maintenance internals. Human-edited AI-assisted *custom*
  template authoring remains the separately approved later map destination; this EPIC must still deliver the
  complete reviewed managed catalog required for real named Agents.
- At TASK intake, the application uses current Team/Repository association, role suitability, idle capacity,
  grant, resource and dependency facts to support an eligible default-Team Lead or a fair, repeatable alternate
  **whole-TASK** handoff to another associated Team when safe parallel work is available. A real ambiguity or
  missing qualified member holds visibly, not an AI guess. Once a Team receives a TASK, its Team Lead may
  delegate only to eligible **same-Team** Agents, including an independent reviewer; sharing a Repository never
  authorizes cross-Team peer assignment. Triage recommends; the owning Workflow operation alone claims/starts.
  Provide this deterministic selection/roster-authority capability for existing Workflow owners; do **not**
  count it as a working dispatch until those owners exercise the real path. Preserve the human-selected Ready
  TASK, visible withdrawable *Pending start* distinct from a claim/queued Runner/actual work, and the
  revalidated single start when eligible under WF-035 and EPIC-00008. Kanban drag, Triage route, claim and
  subsequent workflow transitions stay with their accepted owners; autonomous Triage TASK selection is v2,
  not a requirement of this EPIC.

### Qualified package integration and use

- Keep Fight AccessControl Domain/Application in the package, Agent OS-owned orchestration in Application and
  transport, PostgreSQL, keys, sink, provider and worker adapters in Adapter under [ADR 0001](../adr/0001-application-ownership-and-orchestration.md)
  and [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md). The latter's v0.2.0 baseline is
  historical: explicitly supplement its Agent deferral with the **actual qualified installed** contract,
  without rewriting old receipts or inventing a prospective package release. Inspect tagged capabilities and
  deliberately lock the selected version/source before implementation. The installed v0.5.0 contract is the
  current planning evidence, not permission for an unqualified runtime or legacy-migration backfill.
- Implement both real operation-aware repositories, original-key/request and replacement correlation,
  current-only canonical cohort contract, positive monotonic generation, independent restoration/admission
  witness and actual shared PostgreSQL transaction-duration fences. Inventory and fence **every** direct,
  CLI, worker, Agent, Permission/Role/managed-policy, destination and key writer, including incompatible
  restarted binaries. Leave `PostgresAgentRepository::getOperationContract()` sanitized `UNAVAILABLE` until
  actual consumer participants and persistence are qualified; a row insert, declared capabilities, package
  fixture pass or startup flag cannot advertise live operations. Wrong/missing/uncertain evidence holds.
- Provision one holder-bound Agent credential via the installed package's public lifecycle services and a
  server-registered fixed protected sink, with separate authenticated encryption of authentication envelopes
  and delivery copies. Enforce exact immutable staging/receipt, global delivery-ID deduplication and stable-slot
  order, enrolled holder/key isolation and finite due-work scheduling. Worker claim, admission, sink invocation
  **outside** transactions, receipt acknowledgement, rotation, revocation, maintenance, expiry, key-reference
  closure, cleanup and independent restoration recovery need current scope and durable reconciliation. Issued,
  delivered, activated and usable are distinct outcomes. On lost/uncertain results, resolve the original
  retained operation without blind new issuance, material reread, false success or raw secret disclosure.
- Authenticate real Agent and broker/MCP use with its distinct HMAC holder, replay controls, current direct
  Permissions, delegated human/Workflow authority where relevant, Repository/Team/context/host limits and
  bound destination/credential. Recheck on **each use**: neither the template, Team membership, a signed request,
  activation receipt, stale session snapshot nor model-produced instruction grants power. Protect raw keys,
  source-host/provider credentials, ciphertext, nonces, lease/sink/restore internals and tool invocation data
  from HTTP/client, Pi child environment, logs, transcripts, Artifacts and diagnostics. Permit limited
  separately authorized authenticated self-profile Tools; privileged delivery, receipt, cohort, restoration and
  key maintenance are protected non-UI operations.
- Reconcile the historical one-time-raw-secret wording in
  [WF-014](../wayfinder/tickets/WF-014-define-skill-trust-and-harness-distribution.md) and the
  operating-system credential-store direction in EPIC-00006 with the current fixed-sink/package contract;
  do **not** convert either into a browser secret route, unconstrained key export or shared Agent credential.
  If supported host/key/sink, origin or sandbox controls cannot be qualified, keep that operation unavailable
  and describe the real blocker rather than invoking an insecure fallback.

### Working outcomes, evidence and limits

- Prove the **actual product paths**, not a disposable Explorer test harness or tests that tests fail. Use one
  real Team-assigned Explorer on the registered Fight Agent OS checkout to answer a bounded question with
  cited source and current authenticated tools; separately exercise a real Project Manager through the
  authorized browser/Planning path. Run a human-selected eligible TASK through Team Lead and distinct Software
  Engineer to immutable Awaiting review, then an independent same-Team Senior Engineer, applicable QA and
  Release Manager to a verified PR handed back to a human. Exercise a confirmed direct Hotfix Engineer route
  with a non-contributing same-Team reviewer and guarded PR handoff. Exercise project-specific library and
  application release role paths only with **actual** qualified targets/runbooks, exact human approval and
  signing/health evidence where applicable; a PR landing alone is not a library release or deployment. If a
  required target, reviewer, provider, registered context, credential boundary or managed Workflow is absent,
  this EPIC's corresponding working outcome is **not accepted**, regardless of a parent EPIC's `done` status.
- Record per-role Agent identity, Team/Repository association, managed-template/profile/context revision,
  credential operation/delivery/activation/continuing-use status, actual tools/permissions and authenticated
  session/Workflow provenance. Preserve distinct independent Review/QA, human PR merge/signing/production-effect
  approvals and bounded uncertainty/recovery. Record test and real-run evidence with limitations; never label
  modeled package tests, storage-only TASK-00126, or inherited EPIC/TASK receipts as fresh consumer proof.
- Qualify actual PostgreSQL contention/writer exclusion, crypto/sink/receipt/order, scheduled recovery, host
  credential isolation, Agent authentication/revocation, fresh tool use, restart and independently witnessed
  physical restore with safe redacted observations and owning tools. Verify real UI authority/denial and
  working-role handoffs against actual product behavior with focused owned tests and `./bin/build`; do not add
  product-suite tests for migrations, configuration, wiring, generated artifacts, wrappers or planning machinery.
  Manual dogfooding informs iterations but cannot replace mandatory security qualification. Publish no claim
  of a complete eight-role managed team while any required role path or security gate remains unavailable.
- Exclude a second Planning authority, browser raw-secret console, template- or Team-derived grants,
  cross-Team peer delegation inside a TASK, automatic Agent selection of unrelated TASKs, agent-originated
  scope expansion, approval of own work, automatic PR merge, general unapproved release/deployment authority,
  starter implementation/certification/release, and the separate later AI-assisted custom-template editor.
  Preserve EPIC-00009's per-starter eligibility; no AccessControl 1.0.0 or all-five starter gate is introduced.
  Defer exact schema, API route, Permission identifier/tier, UI layout, credential-store/sink technology,
  worker scheduling, tool DTO, Team selector algorithm and implementation/PR slices to TICKET/TASK planning;
  **not** whether the end-to-end Agent team must work.

## Progress

Approved after the [closed AccessControl adoption map](../wayfinder/accesscontrol-consumer-adoption-map.md)'s
WF-033/WF-035 handoffs were explicitly consolidated in this grill. The maintainer rejected an unassigned,
manual-only Agent shortcut and the earlier separate Agent-versus-Team EPIC split, then raised acceptance from
"first Explorer works" to **all eight real role outcomes**, with existing Workflow owners supplying their
working paths and this EPIC owning missing Agent/Team integration and completion across them. This EPIC creates
no Agent, Team, credential, Workflow, template, host/provider enrollment, security qualification, release,
TICKET or TASK. Requirement decomposition is a separate operation; external owners' completion metadata is not
accepted as runtime evidence without real integrated use.

The maintainer approved seven cohesive requirement areas in the subsequent `to-tickets` pass:
[TICKET-00059](../tickets/00059-TICKET.md) persists/fences actual current Agent operations;
[TICKET-00060](../tickets/00060-TICKET.md) delivers protected credential lifecycle/recovery;
[TICKET-00061](../tickets/00061-TICKET.md) authenticates/authorizes Agent tool use;
[TICKET-00062](../tickets/00062-TICKET.md) administers Teams and roster;
[TICKET-00063](../tickets/00063-TICKET.md) administers named Agents using the existing reviewed catalog;
[TICKET-00064](../tickets/00064-TICKET.md) supplies deterministic Team/Agent selection without another
Workflow owner; and [TICKET-00065](../tickets/00065-TICKET.md) integrates all eight real role outcomes through
their separately owned product journeys. These are requirement TICKETs, not seven implementation PRs. No
Agent, credential, Team, product route, runtime gate, TASK or real role-use evidence was created by decomposition.
