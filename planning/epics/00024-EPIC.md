# Sync an accepted TASK with its updated base and refresh its PR

## Destination

Parallel agents frequently advance `develop` while another TASK is awaiting human merge. Provide
`/skill:sync TASK-NNNNN` as a local Pi coordination workflow, similar to Build, that integrates the updated
base into the selected TASK checkout and updates its existing PR without manually repeating the delivery
sequence or routinely repeating independent Review and QA.

The useful outcome is one accepted TASK brought current with its base, both sets of intended behavior retained,
the integrated candidate verified, and its existing PR refreshed through Land. This is a new workflow using
existing Engineer and Land roles, not another implementation/review engine or a Git-only helper.

## Decisions and exclusions

### Intake and integration

- Bind one TASK, its selected checkout/feature branch, repository, current base and existing open PR. Reuse the
  operator's checkout choice; ask when missing. Preserve unrelated local work and other agents' active work.
- Require prior independent Review ACCEPT and applicable QA PASS or justified criterion-specific N/A covering
  the work being synchronized. Match the original acceptance subject to the current branch and any intervening
  changes; a historical pass cannot override a later failure or accept unrelated unreviewed work.
- Merge current fetched `origin/develop` into the TASK branch. Merge is the chosen strategy, not rebase, including
  for published branches. Retain published history and use ordinary non-force pushes. Do not silently retarget
  an existing PR; retain Land's target identity and base-policy checks.
- The coordinator delegates to a fresh Engineer context, then a fresh Land context. Reuse the existing qualified
  role dispatch, subject binding, observation and resource lifecycle rather than introduce parallel machinery.
- Engineer reads incoming changes and the existing TASK intent, inspects relevant interactions even when Git
  reports no conflict, and resolves conflicts to retain both intended behaviors. Never resolve by blindly
  choosing an entire side. Regenerate derived planning views from authoritative records while preserving
  independently authored changes.

### Integration-only acceptance reuse

The approved fast path is integration of previously accepted work, not new independent acceptance of a repair.
A code conflict alone does not require another Review/QA cycle. Engineer inspects the integrated diff, runs
useful focused checks and the canonical gate, and briefly records nontrivial resolutions. Land checks the
integration scope and evidence before updating the PR; this is not a disguised full Review or QA stage.

Do not add a requirement for Engineer to independently prove their own resolution, a separate approval ceremony,
or new proof machinery. Preserve original Review/QA reports and their actual subjects; record old/new base/head
identities and concise integration decisions in the existing handoff/evidence conventions, not by rewriting
reports to claim they independently assessed the new HEAD.

Stop the fast path for incompatible intended behaviors requiring a decision, a discovered defect, failed
verification, or genuinely new behavior beyond accepted work. Name the concrete blocker and its owning decision,
repair or evidence action. New implementation work requires its normal verification and independent acceptance;
Sync does not silently expand into unrelated repair or treat a green build as blanket acceptance. Missing intake
identity, authority or required prior evidence also prevents advancement, rather than being inferred as satisfied.

This destination sharpens the existing [advancing-base reconciliation policy](../../docs/engineering/LANDING.md#reconcile-an-advancing-base):
behavior-preserving integration can include code conflict resolution, without automatically launching Review/QA
solely because code overlaps. The implementation must reconcile the participating workflow instructions with
this boundary while retaining independent acceptance for genuinely new implementation. Approval of this EPIC
records the intended amendment; it does not claim the new command or amended instructions already exist.

### Verification and automatic delivery

- Commit the integrated candidate, inspect the effective result and run useful focused checks plus ordinary
  `./bin/build`. Its normal automatic evidence validation/reuse is sufficient, including when only planning
  changes require fresh validation. Do not force a full rerun merely because HEAD changed.
- Report freshly executed checks separately from reused application results, including original receipt
  provenance, warnings and incomplete verification. A failed or unavailable required gate cannot advance to
  successful publication. Preserve applicable required hosted/final-head delivery checks.
- After successful integration and verification, proceed directly to Land within the same invocation, without
  asking the operator to invoke Land separately. Land may reuse the qualifying gate result rather than execute
  unchanged application phases again.
- Land updates the existing PR without force, performs normal exact-head delivery verification, applicable
  current-record closeout and eligible owned cleanup, and returns the actual human review/merge handoff. Reuse
  the existing resource procedure; active consumers, main data, unique work and shared resources remain protected.
- Keep publication, cleanup and human merge distinct. A blocked or partial result names the actual remaining
  action and preserves completed effects, rather than declaring success or repeating publication blindly.

### Exclusions

- Routine new Review/QA stages for integration-only synchronization, or a new independent acceptance protocol
- Genuinely new feature behavior, unrelated defect repair, requirement changes or speculative refactoring
- Rebase/history rewriting, force-push, PR approval/merge or automatic replacement of an ended PR
- Release, deployment, remote-branch deletion or a sweep of other TASKs
- Managed/database/browser workflow expansion or designated-default-checkout synchronization; this is the local
  accepted TASK/feature-branch delivery journey, not the separate default-branch fast-forward feature
- Parallel role launchers, resource registries, permanent delivery queues or routine post-merge planning chores

## Observable outcome

Qualification must exercise the real owning workflow/tools for clean integration, conflict resolution retaining
both sides' intent, regenerated planning views, normal build-cache reuse, existing-PR update and concrete blocked
cases. Original acceptance reports remain intact and no routine Review/QA child launches on the fast path.
Validate tooling directly rather than add product-suite tests of workflow text or build/planning mechanisms.
Detailed requirements, qualification scenarios and implementation slicing belong to subsequent decomposition.
