# Complete independent review and PR publication

## Destination

Extend the production Workflow delivered by EPIC-00007 from **Awaiting review** through independent review,
bounded Builder revision, commit-specific acceptance, controlled publication, and human pull-request handoff.
Continue an eligible existing Awaiting review Workflow without replacing its identity, claim, grant history,
implementation evidence, branch, worktree, or sessions; new coordinated Workflows use the same complete state
machine.

A distinct Reviewer evaluates one immutable implementation snapshot in a fresh isolated session, records findings
and a verdict without repairing the target, and sends only blocking findings through the bounded Builder revision
loop. A distinct Publisher consumes a current acceptance, finalizes permitted Planning and delivery facts through
authoritative application operations, performs deterministic final verification, pushes without force, creates or
updates the GitHub pull request, safely cleans exact Workflow-owned resources, and returns merge control to a
human.

The Dashboard presents the complete Review, revision, acceptance, publication, PR, usage, interruption, recovery,
and evidence history, while the dynamic forecast extends honestly through PR handoff. Trusted post-merge
observation may update delivery projections, dependent-TASK eligibility, and safe local reconciliation without
claiming that Agent OS approved or performed the merge.

## Decisions and exclusions

- Consume the closed [Complete Fight Agent OS vision map](../wayfinder/complete-agent-os-vision-map.md), especially
  [WF-015](../wayfinder/tickets/WF-015-define-coordinated-task-authority-protocol.md) through
  [WF-019](../wayfinder/tickets/WF-019-select-end-to-end-proof-and-epic-handoff.md), without reopening their role,
  independence, revision, acceptance, publication, recovery, evidence, privacy, or human-control decisions.
- Depend on [EPIC-00007](00007-EPIC.md) for the Workflow/claim, Coordinator and Builder, enrolled Runner,
  isolated worktree, durable dispatch/recovery, Execution events, observations, Artifacts, commit-specific Builder
  handoff, sessions-first Dashboard, and Awaiting review state. Preserve EPIC-00005 PostgreSQL Planning authority
  and EPIC-00006 Harness, Agent identity/profile, Skill, provider, credential, and immutable snapshot boundaries.
- Reuse the behavioral standards and terminal entry points established by
  [EPIC-00002](00002-EPIC.md), including independent adversarial `review` and controlled `land`, without recreating
  its project-local Skills or retaining their historical Markdown-authority assumptions. Browser and terminal
  entry points invoke the same database-authoritative Commands, Queries, grants, and evidence contracts.
- Complete the accepted single-TASK state machine:

  ```text
  Requested → Claimed → Implementing → Awaiting review
    → Revising → Awaiting review
    → Accepted → Publishing → PR handed off → Stopped
  ```

  Keep Paused, Needs Human, Cancelling, Cancelled, and Failed as explicit side paths. Do not scan for, claim, or
  continue to another TASK after PR handoff.
- Activate Reviewer and Publisher as separately authenticated Agents with distinct direct Permissions, HMAC
  credentials, profile/Harness/context snapshots, tool sets, and isolated Pi sessions. They never inherit the
  Coordinator or Builder credential, and no role change occurs inside a session.
- Require Reviewer independence: its Agent/session must not have contributed to the implementation or its
  acceptance evidence. Every Review attempt starts a fresh Reviewer conversation and Pi session, including
  re-review by the same managed Reviewer identity. Reviewer receives read/verification authority over the exact
  subject and write authority only for Review-owned reports, immutable findings/history, and append-only
  annotations; it never repairs the target.
- Create one independently identified append-only `Review` for each evaluated immutable subject. Bind it to the
  Workflow, TASK and revision, configured base and full base/implementation commit IDs, complete changed-tree and
  status manifests, selected ignored Artifacts/digests, checks, criteria, evidence, Reviewer Agent/session, ordered
  findings, criterion dispositions, and exact verdict.
- Require the Review consumer to reread authoritative Workflow and Git/evidence state. Reject stale, partial,
  ambiguous, mutable, mismatched, superseded, or independence-violating handoffs. A branch, latest head, PR, chat
  transcript, unverified diff, or process-local result is never enough to identify the Review subject.
- Present a bounded syntax-highlighted `base…head` patch for the exact immutable Review subject, keeping every file
  discoverable and routing oversized/binary content to digest-verified private Artifacts. A live worktree diff is
  explicitly mutable observation and cannot replace accepted evidence.
- Record findings with stable identity, severity, affected requirement/criterion, traceable evidence, required
  disposition, and blocking classification. Subjective preference cannot become a blocking defect without a
  violated accepted requirement, invariant, or safety boundary. Contradictory findings, unavailable required
  evidence, scope expansion, exception requests, unsafe repository state, or ambiguity enter Needs Human.
- Let only persisted unresolved blocking findings authorize automatic Builder revision. Non-blocking findings are
  retained for human judgment and do not trigger or consume a revision cycle. One cycle lets the existing Builder
  lineage address the current blocking set, append explicit dispositions, run required checks, and create a new
  implementation commit before a fresh independent Review evaluates that exact snapshot.
- Default to three revision cycles. Permit one explicit positive per-Workflow override at start within a
  server-side installation maximum initially defaulting to ten. Display default, requested, effective, consumed,
  and remaining cycles. Time, cost, process-attempt, and revision limits remain independent and never expand
  automatically.
- Stop in Needs Human when any effective limit is reached or continuing would require a new scope, exception,
  authority, unsafe operation, or unsupported judgment. Continuation requires a new reasoned human grant after
  reviewing the TASK, instructions, findings, evidence, consumed resources, and proposed limits; it resumes the
  same recoverable Workflow only where its accepted terminal-state rules allow.
- Define acceptance for one immutable reviewed snapshot. Every TASK criterion must be satisfied or validly waived,
  every required check must pass with fresh attributable evidence, evidence must be sufficient, and no blocking
  finding may remain unresolved. Acceptance is not a defect-free guarantee, human PR approval, merge, release,
  deployment, or certification.
- Let only an authorized semantic Workflow Command determine that a finalized Review satisfies acceptance. It
  revalidates current grant, live authority, Review subject, TASK revision, base/head commits, tree/status,
  evidence, criteria, checks, findings/dispositions, limits, and expected aggregate revisions before appending
  acceptance. A Review verdict or observational event cannot transition the Workflow by itself.
- Invalidate current acceptance after any material change to implementation, tests, configuration, reviewed
  Artifact bytes, TASK revision, amend, rebase, conflict resolution, base/head subject, or later-established
  unresolved blocker. Preserve the original Review and acceptance history; never transfer a verdict to another
  commit or silently reinterpret a floating branch/PR.
- Preserve finalized Review bytes and events. Permit only separately attributed append-only annotations for
  correction, omission, supersession, or links to later findings. If a correction undermines the acceptance in
  current use, Coordinator invalidates it and returns to the bounded revision/Review path; historical annotation
  alone does not manufacture another model run.
- Activate Publisher only after current independent acceptance. Publisher rereads Workflow, Review, Planning,
  Git/worktree, checks, branch/remote, grant, live authority, and publication evidence; it does not repeat Review,
  repair unresolved implementation, approve its own work, merge, or expand scope.
- Keep PostgreSQL Planning as sole authority. Publisher marks TASK implementation acceptance `done`, records
  acceptance/evidence/delivery facts, updates generated database projections, and performs closeout bookkeeping
  only through intent-specific semantic application operations against expected revisions. It never edits frozen
  source Markdown or treats generated Markdown as a writer.
- Allow narrowly mechanical post-acceptance changes only within the WF-015 envelope: completion/publication facts,
  approved evidence references, deterministic generated delivery bookkeeping, links, provenance, and harmless
  corrections that do not alter requirements, implementation, tests, configuration, Permissions, authority,
  reviewed Artifacts, or the substance of acceptance. Record a complete manifest and verify deterministically.
  Material or ambiguous change preserves the accepted implementation commit but returns to Review or human
  judgment.
- Run the accepted required final checks against the exact publication tree and preserve fresh results, warnings,
  incomplete checks, tree/status, and commit evidence. Never relabel inherited, Builder-only, or historical
  receipts as fresh Publisher evidence. A failed or stale required check blocks publication without erasing the
  current accepted implementation subject.
- Give only Publisher the bounded source-host publication capability and credential broker path. Builder and
  Reviewer cannot discover or use source-host push/PR credentials. Raw SSH keys, tokens, Agent secrets, provider
  credentials, signing material, and broker internals never enter child environments, files, prompts,
  transcripts, logs, events, observations, Artifacts, or browser responses.
- Record durable publication intent before GitHub effects. Push the accepted implementation plus any accepted
  mechanical landing commits to the Workflow feature branch without force, verify the exact remote commit, and
  create or update one pull request against the configured base through idempotent provider operations. Reconcile
  uncertain push/PR outcomes before retrying; never report success from a queue acknowledgement or lost process.
- Require the published PR base, head, remote commit, Repository/source identity, Workflow, TASK, and accepted
  implementation commit to match. Persist the provider-native identity and canonical URL as evidence rather than
  treating a mutable title, branch name, or URL as authority.
- After verified publication, remove the isolated local worktree only when ownership, cleanliness, accepted/pushed
  commits, absence of unrelated changes, and safe Git administration are proved. Retain uncertain, failed,
  cancelled, or Needs Human resources. Cleanup never reaches human-owned checkouts, shared services, unrelated
  branches, ambiguous scratch, durable evidence, or remote branches.
- Transition to **PR handed off**, release the active TASK claim under the accepted terminal rules, present the
  canonical PR URL and retained actions, and stop the Workflow. The grant never authorizes force-push, PR approval,
  merge, remote-branch deletion, unrelated cleanup, archive, release, deployment, certification, or another TASK.
- Keep Planning `done`, independent acceptance, PR publication, human approval, merge, release, and deployment as
  distinct facts. A dependent TASK remains ineligible when its prerequisite change is not verified on the
  dependent TASK's configured base, even if its blocker TASK is Done. Independent eligible work remains available.
- Observe merge only through a trusted GitHub refresh that verifies provider-native repository/PR identity, base,
  accepted/published head, actual merge result, and base-branch inclusion across merge-commit, squash, or rebase
  strategies. Provider webhooks or polling results are observations until an authorized reconciliation Command
  validates and records them.
- Project a verified merge into the Kanban Complete lane and recompute direct downstream prerequisite availability
  without appending another TASK-completion event or rewriting Workflow/Review history. Unknown, closed-unmerged,
  retargeted, replaced-head, inaccessible, or ambiguous provider state remains explicit and cannot unblock work.
- Permit post-merge local reconciliation only for an explicitly enrolled main Worktree that is clean, idle,
  unreserved, and not preserving unrelated work. Fetch/prune and switch to configured base only under explicit
  authority; update by fast-forward only. Remove only the merged Workflow's local branch after proving merge,
  remote state, commit inclusion, and absence from every Worktree. Report other gone branches rather than deleting
  them.
- Complete merge/delivery projections and dependent eligibility even when checkout maintenance must remain
  pending. A dirty, busy, missing, moved, divergent, detached, unavailable, or ambiguous checkout never triggers
  stash, reset, rebase, merge, force, discard, or broad cleanup.
- Extend the sessions-first Dashboard Summary, Changes, Activity, and Evidence sections with current Review state,
  immutable subject, criteria, findings, dispositions, revision cycles, acceptance/invalidation, final checks,
  publication intent/result, GitHub PR, human action, merge observation, and cleanup/reconciliation state. Preserve
  independent pagination, partial/denied/stale/purged states and the authority-versus-observation distinction.
- Keep browser code inspection and intervention optional rather than a mandatory publication gate. Authorized
  humans may pause, halt, cancel, annotate, grant continuation, or take over under the existing Workflow rules;
  reconnecting never approves, retries, accepts, publishes, or reconciles automatically.
- Extend the dynamic remaining-time range through PR handoff. Include active Review, expected bounded revision,
  recheck, publication, queue, retry, and known external-operation facts while retaining confidence, last update,
  material-change explanations, actual-versus-predicted calibration, and honest Waiting for human, Paused, or
  Unable to estimate states. Do not forecast human merge as part of Workflow completion.
- Test important owned Reviewer independence, immutable subject, finding/disposition, acceptance/invalidation,
  revision cap, stale handoff, Publisher authorization, database-authoritative Planning closeout, idempotent
  push/PR effects, uncertain-effect recovery, cleanup ownership, merge reconciliation, and downstream eligibility
  behavior. Manually continue a real production Workflow through independent Review and PR handoff and retain its
  ordinary operational evidence.
- Prefer focused tests for owned invariants and integration boundaries plus direct integrated use. Do not duplicate
  browser, Git, GitHub, framework, queue, configuration, package-manager, Skill prose, or quality-gate mechanics;
  distinguish automated, manual, provider-observed, historical, and incomplete evidence honestly.
- Exclude autonomous PR approval/merge, force-push, stacked PRs, unlimited or silent revision, Reviewer repair,
  Publisher implementation/review, remote-branch deletion, unrelated cleanup, automatic archive, multi-TASK
  pipelines, release, deployment, certification, remote Runner fleets, and operation after merge beyond the safe
  observation/reconciliation boundary above.
- Defer exact schemas, Commands/events, API/provider DTOs, Permission identifiers, model assignments, budget and
  limit values beyond accepted defaults/ceilings, finding severities, check inventory, GitHub transport,
  reconciliation schedule, forecast math, UI components, and implementation slices to TICKET and TASK
  decomposition. Open a new Wayfinder decision only for genuinely new product uncertainty.
