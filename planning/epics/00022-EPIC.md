# Make feature architecture reviewable with Python diagrams

## Destination

Help human reviewers understand where a feature's responsibilities belong and how its important runtime paths
work without needing to reconstruct the whole design from source code. For a feature that materially changes
architecture, the maintained documentation and pull request give a concise visual account of the affected
ownership, dependencies, and behavior, with references to the actual source. In Pi, a user can ask to see the
current or proposed design as a focused diagram.

Deliver this through one shared diagramming standard, an on-demand Pi show-me skill, and a repeatable way to
author, render, review, and maintain feature diagrams. Qualify the complete experience on one representative
existing PHP feature: a reader can find its diagrams beside its feature documentation, inspect them in the
pull request, and ask Pi to show a useful view.

## Decisions and exclusions

- Give maintained feature documentation, useful pull-request views, and the Pi show-me skill equal weight.
- Use Python Diagrams as the primary authoring format. Keep the Python source beside the owning feature
  documentation and maintain a rendered image for documentation and pull-request display. Provide a supported,
  repeatable local rendering path with the Python and Graphviz requirements qualified; do not assume a developer
  has installed global packages.
- Select views per feature instead of drawing every possible view each time. Useful views include system or
  infrastructure context, class and layer ownership, dependencies, request or data flow, and a before/after
  comparison where it clarifies the change.
- Require a diagram in pull requests when a change materially affects class placement, dependency direction, or
  runtime flow. Omit diagrams for changes where they add no useful information.
- The show-me skill can explain an existing or proposed design on demand and render a focused image in Pi when
  the terminal supports it; provide a browser preview when inline image display is unavailable or the diagram
  needs more space. Qualify the currently installed Pi image-display behavior as evidence, not a version pin
  or future compatibility guarantee.
- Verify each diagram against the source revision being described. Use real class and file names, link to the
  relevant source, distinguish static dependencies from runtime interactions, and identify uncertainty or
  omitted details. Label proposed architecture as proposed. A diagram supplies review context; it does not prove
  correctness or replace tests and independent review.
- Qualify a PHP class-ownership view as part of the example. Python Diagrams provides C4, programming flowchart,
  and custom-node building blocks; the qualification must show that labeled nodes, clusters, and edges explain
  the relevant Domain, Application, and Adapter placement clearly. If they do not, surface the representational
  gap for an explicit decision rather than presenting an unclear diagram as proof.
- This is documentation and agent-workflow guidance. It introduces no product command, API, event, database
  behavior, permission, or runtime side effect. The skill inspects source and writes only the authorized diagram
  sources and rendered documentation assets.
- Do not require diagrams for every pull request, draw unrelated code, move classes merely to match a picture,
  or treat diagram generation as acceptance evidence by itself. Do not expand this destination into a general
  graphing platform or implement feature behavior solely to make a demonstration.
- TICKET decomposition will settle the concrete renderer setup, documentation and image locations, pull-request
  handoff, Pi display fallback, and the example feature. This EPIC does not create TICKETs or TASKs.
