# Deliver durable scoped Agent memory

## Destination

Give stable Agent identities durable, database-backed private working memory and authorized shared learning across
sessions, Workflow attempts and TASKs. An Engineer can remember and correct its own working notes; a Team Lead
can publish attributed Workflow and TASK lessons; separately authorized owners can review proposals and publish
broader Repository or Workspace guidance without turning lower-scope prose into authority. Later assigned work
can use permitted shared lessons without inheriting another Agent's private session or reasoning.

Deliver the complete capability in stages: private memory, shared Workflow/TASK learning, broader promotion and
Jev-assisted on-demand lookup. Include basic authorized human inspection, correction, promotion-history review
and exceptional prohibited-content removal. The sequence is a delivery path, not a separate formal test ceremony
at every stage. Qualify important owned behavior and trust boundaries as those features are delivered.

## Decisions and exclusions

- Consume the closed [hierarchical memory map](../wayfinder/hierarchical-agent-memory-map.md) and
  [WF-024 ownership and scope](../wayfinder/tickets/WF-024-define-memory-ownership-and-scope-authority.md),
  [WF-025 lifecycle and promotion](../wayfinder/tickets/WF-025-define-memory-lifecycle-and-promotion.md), and
  [WF-026 MCP retrieval](../wayfinder/tickets/WF-026-define-sandbox-memory-retrieval-and-mcp-access.md). Do not
  reopen their accepted policies during implementation slicing.
- Reuse [EPIC-00005](00005-EPIC.md)'s registered Repository identity and applicable Planning/context authority,
  [EPIC-00006](00006-EPIC.md)'s Harness templates, protected first-party MCP and bounded Jev judgments,
  and [EPIC-00007](00007-EPIC.md) and [EPIC-00008](00008-EPIC.md)'s actual coordinated Workflow, phase and
  independent-review authority when those integrations are available. These are capability dependencies, not a
  new blocker on the approved first Team Lead → Software Engineer execution slice or a change to Board priority.
  Memory is not a copy of Pi checkpoint/session state, nor a substitute for required Workflow handoffs.
- Project memory uses the stable registered `RepositoryId`, not a new Project identity. Keep a small
  Workspace-private general bank for each Agent and repository/assignment-partitioned private working memory;
  shared Workflow memory belongs to its Team Lead, TASK memory exists from the first Workflow and survives
  distinct attempts, and authorized project/workspace stewards own broader published memory. Agent profile
  templates and friendly names do not grant access; instantiations have separate identities and one active
  session per identity.
- Treat every entry as an attributed plain-language claim with source links, applicability, verification state
  and relevant assignment/phase/Workflow provenance. Memory never grants execution authority or approval.
  Source code establishes current behavior; published Planning establishes approved intent. A discrepancy
  remains visible rather than allowing memory to override either source.
- An owner may replace its own current private working text without retaining prior text by default. Shared
  corrections, supersession and retractions keep attributed linked history; retracted claims do not appear as
  current guidance. Entries do not expire because of age. TASK/Workflow completion retains memory for permitted
  historical learning, metrics and later skill, workflow and handoff improvement; it is not an archive trigger.
- Lower-scope Agents may propose broader publication, including direct target scopes, but only an owner currently
  authorized at the target scope may publish a new attributed entry after independently checking underlying
  evidence and applicability. Keep rejected proposals for authorized learning, not ordinary Agent guidance;
  resolve duplicate retries without duplicate entries and assess contradictory claims rather than merging them
  automatically. A correction to a linked source alerts owners of derived entries without silently rewriting
  independently supported conclusions.
- Use the exact managed `READ_PRIVATE_AGENT_MEMORIES` Permission and current target access for private oversight,
  without making it `SUPER_ADMIN_ONLY`. Audit Agents additionally need an explicit scoped audit TASK. Ordinary
  Team Lead, reviewer and peer access does not include another Agent's private notes, searches or reasoning.
  Revocation and assignment changes affect subsequent operations without automatically deleting stored history.
- Once a Workflow completes, an Engineer cannot ordinarily read that Workflow's memory through another
  assignment. The assigned Team Lead may read completed Workflows while its TASK remains active, but its normal
  Workflow/TASK reads end when the TASK completes. A Project Manager with current repository authority may
  inspect completed Workflow memory for estimation; permitted humans and scoped audit Agents retain their
  distinct historical paths. Successor Workflows consume TASK summaries and mandatory handoffs, not prior
  private memory or automatic predecessor Workflow reads.
- Agents begin with a short memory-use instruction and their authoritative task handoff; no bulk startup
  memory fetch is required. Expose explicit, HMAC-authenticated first-party MCP read/write operations with
  scope IDs, current application ownership checks, exact entry reads and idempotent write recovery. No sandbox
  direct database connection, shared writable host-memory mount or raw transcript ingestion is authorized.
- Support typed Jev yes/no and declared-choice questions about one entry or an authorized memory scope, including
  Level 9-style narrowing to matching record IDs for separate exact reads. Jev provides judgments, not summaries,
  independent Agent permissions, scope grants or a new source of truth. Do not copy the file tool's threshold
  or example's file cap into memory without qualification; use no memory-specific judgment cache. A Jev timeout,
  provider failure or input limit is reported as that failure, never a fabricated negative or silent unqualified
  fallback. An ordinary known-ID read still works while the application is healthy; database unavailability
  stops application operations, not a transition to offline memory authority.
- Protect secrets and prohibited content: separately authorized safety removal deletes offending payload from
  affected entries and copies, exports and derived views while retaining only safe audit metadata. Qualify
  permitted provider disclosure for memory judgments without giving Jev independent database access. File-system
  `.env` exclusions, general SQL/repository analysis and their future access routes remain with their existing
  Harness use cases; this EPIC does not invent new restrictions on those capabilities.
- Provide a basic human path to inspect authorized shared and permitted private entries, correct or retract
  where the actor owns the scope, inspect proposal/publication lineage, and invoke separately authorized safety
  removal. Choose the detailed browser UX and any MemorySpace aggregate boundary during TICKET decomposition;
  neither a polished memory dashboard nor a new aggregate is presumed by approving this EPIC.
- Validate meaningful owned lifecycle, access and lineage behavior, including role/assignment changes,
  completed-work visibility, retry safety, rejected proposals, independent review isolation, secret removal and
  accurate Jev/known-ID outcomes. Qualify actual MCP/HMAC, provider disclosure, lookup usefulness, cost/latency
  and failure behavior with the owning tools and relevant integration evidence. Do not add product tests for
  schema wiring, migrations, planning Markdown or build infrastructure.
- Defer routine scheduler-based archival/removal policy, generated Agent names and Director/CTO template naming
  to separate future decisions. No vector store, automatic import of personal/host memory, live Pi transcript
  copying, bulk provider disclosure, hidden model reasoning sharing, Planning-authority change, automatic
  approvals, Git/PR publication or merge is part of this EPIC.
