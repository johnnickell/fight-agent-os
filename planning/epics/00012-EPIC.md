# Introduce TASK Triage and the direct hotfix route

## Destination

An authorized person selects one TASK through a terminal start request or, when available, a browser Ready → In
Progress gesture. Triage classifies it with bounded Jev judgment and hands it to an approved, versioned Workflow
route. Normal feature, bugfix and chore work starts **automatically from that single authorized request** through
the existing Team Lead → Software Engineer Workflow; no second readiness check, queue or confirmation is introduced.
A confirmed emergency bugfix takes a distinct direct Hotfix Engineer route from the Repository-configured
production base, preserving independent review, applicable QA and PR handoff. Where the configured branching
strategy requires it, a verified production hotfix merge can be merged back through one separately authorized
Yes/button action in the same hotfix history, without another TASK.

Deliver this as a **later execution extension** to the accepted first Team Lead → Software Engineer slice and its
independent review/publication path. Use the existing single-TASK, authoritative PHP start/claim and recovery
contracts; do not make Triage a retroactive prerequisite for earlier milestones.

## Decisions and exclusions

- Consume the closed [SDLC intake triage map](../wayfinder/sdlc-intake-triage-map.md),
  [WF-027 — Define TASK triage readiness and classification](../wayfinder/tickets/WF-027-define-task-triage-readiness-and-classification.md)
  and [WF-028 — Define triage dispatch and hotfix role boundaries](../wayfinder/tickets/WF-028-define-triage-dispatch-and-hotfix-role-boundaries.md).
  Reuse [canonical TASK eligibility](../tasks/00096-TASK.md), [WF-015 Workflow authority](../wayfinder/tickets/WF-015-define-coordinated-task-authority-protocol.md),
  [team responsibilities](../../docs/engineering/TEAM.md), [template planning](../tickets/00034-TICKET.md),
  [EPIC-00007](00007-EPIC.md), [EPIC-00008](00008-EPIC.md) and the bounded Jev capability planned in
  [TICKET-00037](../tickets/00037-TICKET.md). Qualify the actual dependencies at delivery; planning records are
  not evidence that those runtime capabilities already exist.
- Introduce a distinct, permission-limited Triage Agent profile as a **team template**, not an Access Control
  Role. Triage preflights a human-selected TASK without claiming it or approving readiness anew. A separately
  requested diagnosis of an incomplete TASK cannot make it executable. Apply permission-filtered, bounded,
  revision-bound Jev classification on **every selection**, including declared kinds that appear clear. Treat
  TASK prose as untrusted; return feature/bugfix/chore or explicit unknown and a configurable advisory
  low/medium/high/urgent priority band, without changing Planning kind, status, authored order or scope.
  Enhancement belongs to feature; the existing `bug` kind maps to routing label `bugfix`. No new Planning kind
  is added by this EPIC.
- Route by a versioned deterministic catalog after classification, without an extra Jev route-selector or
  normal-route confirmation. A material conflict between Jev's category and the accepted TASK kind pauses for
  human resolution. For unavailable/unknown Jev classification, use a **labeled declared-kind fallback** only
  for a supported normal route, with unknown priority and no inferred hotfix. Unsupported/stale/unauthorized
  inputs stop with safe reasons. Preserve classification provenance, evaluator/rubric identity and human
  disposition; never confuse an unavailable evaluator with an ineligible TASK.
- The terminal start request and browser drag are entry points to the **same server-authoritative** start.
  Before claiming, revalidate the canonical eligibility result, TASK/context/Repository configuration and
  catalog revisions, live grants and identities, role availability, base, limits and route. Atomically create
  one durable Workflow/dispatch intent and exclusive TASK claim or report a safe refusal; an intent or UI gesture
  is not evidence of a completed state transition. Honor WF-015 idempotent starts, owner conflicts,
  cancellation/quiescence and uncertain-effect reconciliation. Triage cannot grant permissions or claim a TASK.
- Extend versioned Repository setup with a declared GitFlow, trunk-based or custom branching strategy and
  explicit route base/target mappings. Verify the resolved base rather than guessing branch names: GitFlow
  ordinary work commonly uses `develop` and hotfixes commonly use `main`. Missing/invalid configuration blocks
  the affected route. Show the resolved production base in the **one quick human emergency confirmation** of
  scope and hotfix start; never request a second branching-strategy confirmation or quietly branch a hotfix
  from `develop`.
- Route a human-confirmed urgent bugfix directly to the existing senior-capability **Hotfix Engineer** for a
  bounded incident repair. The initiating human or named incident owner is its contact; the application owns
  state and escalation without inserting Team Lead into this direct route. Preserve isolated work, incident
  scope, regression evidence, required checks, a separate non-contributing Senior Engineer's independent review,
  applicable targeted QA and Release Manager PR handoff. A specific human-authorized check exception records
  risk and containment; urgency never grants self-approval, merge, signing, release or deployment authority.
- If a normal bugfix becomes an emergency after start, pause its Workflow; on a new bounded emergency grant,
  safely reconcile effects and claim ownership and create a **linked hotfix Workflow on the same TASK**. Do not
  switch an Agent's role mid-session, retarget a `develop` branch or bring other unfinished `develop` work into
  production. Retain prior evidence with exact provenance and requalify what applies. Unknown process/effect
  outcomes prevent duplicate execution or a false transfer.
- After trusted verification that a GitFlow hotfix was merged into its configured production base, offer one
  Yes/button authorization to merge that fix back to the configured development base **within the same hotfix
  history**, with no new TASK or Workflow. Revalidate the exact source, target and effect grant, verify result
  and applicable checks, and reconcile uncertain outcomes before retry; conflicts pause with a concrete human
  resolution path. This requires an explicit, narrowly scoped extension to the existing PR-handoff stop policy;
  it does not grant automatic PR approval/merge or a generic branch-merging permission. A trunk-based repository
  with no separate development base has no merge-back action.
- Exclude the separate [release TASK and project-specific release Workflow EPIC](00013-EPIC.md):
  no `release` Planning kind, package tag/signature, GitHub release, application deployment, or inferred release
  authority is delivered here. Release Manager PR landing remains distinct from release. Do not rewrite
  historical Workflow approvals, replace canonical eligibility, create a competing work queue, auto-merge a
  hotfix PR, skip sandboxing/review/QA, or alter already accepted first-slice start behavior retroactively.
- Verify owned classification and fallback behavior, category conflicts, bounded disclosure and evaluator
  failure, route/configuration drift, authority and claim races, duplicate starts, rerouting, independent-review
  separation, post-PR merge-back authority and uncertain-effect recovery using appropriate focused and
  integration evidence. Qualify real Jev suitability, latency and spend separately from deterministic fixtures;
  do not add product-suite tests for Planning Markdown, configuration wiring or test infrastructure. Keep exact
  schema, Commands/events, UI controls, run budgets and delivery slicing for TICKET/TASK decomposition.
