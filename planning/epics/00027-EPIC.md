# Release a shared React and Bootstrap frontend for the application suite

## Destination

Let nickell-financial (called nickell-finance in the request), creatively-social, nickell-home and later
applications install and extend one versioned frontend rather than copy account screens and controls.
Deliver human authentication and user/Role/Permission administration, white-label branding and a stateful,
sortable, paginated table with optional search and URL-restorable state. Fight Agent OS consumes the library
first; project-symfony is the first external consumer because nickell-financial already selects Symfony.
The other four framework skeletons adopt independently after the first release.

John approved this earlier destination, the React/Bootstrap suite convention, table ownership and changed
TASK progression on 2026-11-17. This is a distinct qualified product release, not a partial claim of the
complete AccessControl reference-consumer handoff in [EPIC-00018](00018-EPIC.md).

## Decisions and exclusions

### Shared package and suite conventions

- Start with one independently versioned npm library, working name `@fight/react`, with focused public
  controls, account and styling entry points. Keep source initially at `packages/react/` in this repository;
  `client/` is a consuming application. Registry/name availability and publishing identity are verified by
  the release owner before publication. Do not create several packages or a new repository merely for layering.
- React, strict TypeScript, Bootstrap styling and React-Bootstrap mechanics are the shared suite direction.
  No Tailwind dependency, utility-class convention or parallel styling system enters this release. Existing
  receiving-project Tailwind inputs are removed with their actual replacement and caller verification.
  Framework-native server rendering may serve the application shell; it does not replace the React UI.
- Share actual controls, account flows, typed API/session integration and default styling. Applications own
  business screens, navigation composition, branding and backend adapters. Use components, hooks, explicit
  callbacks and composition; do not require inheritance, deep internal imports or modifications in node_modules.
  Do not export Agent OS Planning, managed execution, Swagger internals or its product-specific catalog defaults.
- Use one application-supplied React instance, supported peer ranges, compiled JavaScript/types and deliberate
  CSS exports. The host retains its build tool; no mandatory Agent OS bundler, router, global application store
  or post-install source rewrite. Only real integration needs justify additional public configuration.
- Each backend implements the documented, versioned HTTP/session/authority contract using qualified Fight
  Common and Access Control packages. npm does not install PHP endpoints or confer server authorization.
  Shared frontend releases record tested backend/API compatibility, not equality with Composer version numbers.
- White-label name, logo, accessible logo text, page titles and semantic colors/type/spacing work on public,
  account and administration screens in both themes. Retain an accessible default, local assets, CSP and
  reduced-motion behavior. No runtime CSS upload, database theme editor, arbitrary HTML or remote font loader.

### Table and address-bar contract

[TICKET-00143](../tickets/00143-TICKET.md) owns the detailed contract. The wrapping table owns pagination,
page-size, sorting, committed search and filter state, including nested pagination, page-count and optional
search controls. It emits normalized state changes through callbacks. The page owns authorized data fetching
and browser URL/history synchronization; URL restoration is an explicit input, not a second competing state owner.

Use `page=X&per_page=Y&sort=ID&order=desc&search=gmail&filters=<base64url-json>` for meaningful list state.
Reload, copied URLs and Back/Forward restore equivalent authorized results. Search and sort operate over the
whole authorized server dataset before pagination. Base64url is encoding, not encryption or trusted input.
Never put credentials, tokens, permission snapshots or mutation forms in this state.

Free-text search is disabled for all Access Control features, including Users, Roles and Permissions.
Optional search remains a required shared-library capability for application-specific pages; each application
owns its searchable queries, fields and server-side behavior. Do not add Access Control search endpoints or
read projections. Access Control lists use pagination, ordering and only filters supported by their qualified
contracts; manually supplied search state cannot enable search.

### First-release scope and readiness

Include login, invitation activation, reset/change password, refresh/logout, current principal and owned
sessions, ordinary/elevated invitations and recovery, user detail/lifecycle/Role assignment and cross-user
sessions, custom Roles and eligible Permission assignment, and the read-only Permission catalog. Existing
owners retain server authorization, protected managed Roles, required audit and self/last-admin policy.
No permission-definition CRUD, managed-role editor, new self-registration, MFA or email-address change is implied.

The first handoff requires a real installed package in Agent OS and project-symfony, real backend contracts,
accessible branded journeys and whole-dataset list behavior. A Storybook example or installed dependency alone
does not qualify a skeleton. Use local captured email for local acceptance and report it honestly. Real mail
enrollment, production security/operations and project-specific deployment remain receiving-project work;
[TASK-00284](../tasks/00284-TASK.md) remains Agent OS's real-mail owner, not a new first-package dependency.

Do not wait for managed Agents/Teams, browser Planning/database cutover, Features, templates, all five starter
releases or TASK-00305/00307/00308. Preserve those owners and EPIC-00009's separate stable-starter generation
eligibility. The first library release and qualified Symfony skeleton unblock application integration; the
remaining skeletons have independent adoption TASKs and do not reverse-block that milestone.

### Later Agent provisioning and one-time HMAC display

John wants a later library addition for named Agent provisioning and one-time display of the issued HMAC
secret, with safe permission and credential lifecycle controls. It is explicitly outside this first release
and needs no speculative stub, disabled screen or dependency on managed workflow execution now.

Inspected Access Control develop uses secret-free `ProvisionAgent` dispatch, safe operation-status Queries and
protected destination delivery; it does not return a raw secret to a browser. Before decomposing that later
release, qualify a supported protected destination/disclosure composition or obtain the required upstream
contract. Do not add a raw-secret command result, expose storage ciphertext/key material or weaken the existing
Agent OS protected-Harness delivery path. Keep generic application Agent provisioning distinct from Team-bound
managed SDLC Agents and their existing enrollment/runtime prerequisites.

The later acceptance must define authenticated operator/target admission, required audit, at-most-one successful
application disclosure, ephemeral display and explicit copying, no URL/log/analytics/browser-storage retention,
refresh/replay refusal, rotation/revocation and honest response-loss recovery. A browser cannot prove that a
human saw or saved a secret; uncertain delivery must not trigger re-reveal or automatic reprovisioning. The
later planning owner must settle these guarantees against the actual supplier, not infer support from a tag.
This retained destination is not an executable TASK or a first-release blocker.
