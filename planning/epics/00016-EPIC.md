# Deliver usable Feature Flags management and enforcement

## Destination

Deliver the complete Fight Agent OS Feature Flags capability for staged rollout, not a storage-only catalog or a
dummy Feature installed to demonstrate it. An authorized administrator can inspect and manage immutable-name
Features, choose or change the testing Permission, move among `OFF`, `PREVIEW` and `ON`, and retire an unreferenced
Feature safely. The application discovers real code references, provisions missing definitions `OFF`, validates
candidate readiness, checks current availability at each registered runtime entry point, and guards deletion
against **all** current references. A fresh installation can have an honest empty list; the first actual
product capability to be flagged is selected when there is one, not invented by this EPIC as a separate proof.

For a matched HTTP Action declaring the package's method-level `#[FeatureFlag]`, a `FeatureFlagMiddleware`
uses the authoritative request principal and Fight Access Control's `FeatureAvailability`: `OFF` denies with
404, `ON` continues, and `PREVIEW` continues only when the User's Role-derived or Agent's direct Permissions
include the Feature's **bound testing Permission ID**; otherwise it denies with 404. A successful Feature check
never replaces the Action's ordinary authentication, permission, target or business authorization. Non-HTTP
entry points for a flagged capability must enforce the same registered check through their own server boundary;
HTTP middleware alone cannot make a multi-entry use case safe.

One authenticated read endpoint provides **every Feature's** safe name, current status and bound testing
Permission for the signed-in browser user, plus server-computed `available` for that user. The frontend uses
`available` for routes, navigation, controls and forms, together with `/api/v1/me`'s **planned** current
permission-name projection for *ordinary Action permissions*. The backend always rechecks on the actual
operation. In `PREVIEW`, an eligible tester sees and uses a complete feature; other callers neither see its
controls nor reach the flagged operation. Enabling a Feature does not automatically remove its checks:
when it is ready to become permanent, plan a separate chore TASK to remove **all** its code declarations,
registrations and checks, deploy that removal, confirm complete CURRENT-code absence, then perform a separately
authorized, revision-checked database retirement.

## Decisions and exclusions

- Consume [WF-032's approved Feature lifecycle](../wayfinder/tickets/WF-032-reconcile-accesscontrol-coverage-and-accepted-scope.md)
  and the [AccessControl consumer adoption map](../wayfinder/accesscontrol-consumer-adoption-map.md)'s
  [capability matrix](../wayfinder/research/WF-032-accesscontrol-consumer-capability-matrix.md). This is the
  separate, explicitly approved later Feature Flags destination dependent on [EPIC-00004](00004-EPIC.md)'s
  authentication, current-principal, managed-policy and API/client security foundation. It does not rewrite
  EPIC-00004 or [TICKET-00030](../tickets/00030-TICKET.md)/[TICKET-00031](../tickets/00031-TICKET.md),
  and it does not implement a generic Permission CRUD service. Package Domain/Application owns Feature semantics;
  Agent OS owns composition, current/candidate discovery, PostgreSQL, transport, front-end behavior and
  required Application orchestration per [ADR 0001](../adr/0001-application-ownership-and-orchestration.md)
  and [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md).
- Use the public, actually qualified Fight Access Control `FeatureFlag`, `FeatureReferenceDiscovery`,
  `ProvisionFeatures`, `ValidateFeaturePreparation`, `FeatureAvailability`, management queries/commands and
  `RemoveFeature` contracts. At implementation inspect the available tagged release and lock/source, qualify
  consumer adapters and record actual evidence; the installed v0.5.0 package scenarios, existing
  `PostgresFeatureRepository` storage and Permission-reference checks are **not** a complete scanner, Action
  middleware, admin UI or Feature runtime. Do not import upstream implementation policy into Agent OS Domain.
- Supply complete discovery for both supported method Attributes and explicit registrations, including
  failures/malformed declarations and the identity of the **CANDIDATE** code or actual **CURRENT** running
  code. A complete empty inventory is valid; an inaccessible, partial, wrong-scope, stale or failed discovery
  is not. Protected setup/provisioning only creates missing definitions `OFF`, retaining existing identity,
  status, binding and revision; it cannot create Permission definitions or grants. Validate preparation by
  fresh authoritative reads against the intended target after provisioning and **before** considering code
  activation. Prepared `OFF` means the candidate is safe to consider for deployment, not that the Feature is
  available, the deployment is approved or the action is authorized. Keep discovery/provisioning/preparation
  behind qualified protected operator/deployment paths, not general browser edit controls.
- An administrator with a distinct managed `ADMIN_SAFE` Feature-management Permission, initially granted only
  to `ROLE_SUPER_ADMIN`, can create an immutable-name `OFF` Feature with an existing testing Permission,
  read its safe state, rebind to an existing Permission, choose `OFF`/`PREVIEW`/`ON` and request guarded removal.
  Check current actor/target/intent on **every** HTTP, CLI, worker and direct-bus entry path: neither a Role name,
  a testing Permission, a Feature being ON nor browser visibility grants management authority. Later eligible
  delegation under the tier needs deliberate scope/actor checks; no automatic custom-Role or Agent grant.
  Reject malformed names, unknown/removed Permission bindings, stale positive expected revisions, concurrent
  mutations and unsafe reference changes. No-op edits must still validate expected state and binding without
  incrementing revision or publishing a false success. Show safe confirmation before leaving `ON`, refresh
  after conflicts and reconfirm any still-dangerous transition; guard enabling with preparation/current-policy
  checks and separate action authorization, not scanner success or an unqualified checkbox.
- Provide **one authenticated, read-only complete catalog** for signed-in browser users, including `OFF`
  records: safe name, `OFF`/`PREVIEW`/`ON` status, bound testing Permission and server-computed `available` for
  the current request's authoritative User principal. This is an explicit grill-approved extension of
  WF-032's admin-only management reads: the maintainer accepts disclosure of Feature names/status/bindings
  to other signed-in users for simple frontend gating. Anonymous requests receive no catalog; mutating
  management commands remain separately permission-controlled. Provide complete listing semantics (not an
  unnoticed first page) with operational bounds and safe failure if completeness cannot be established;
  choose pagination/limits in TICKET design. On missing bindings, authorized management reads retain an
  explicit safe repair marker and the runtime/client decision fails closed; do not fabricate a testing
  Permission, use a same-named replacement ID or treat infrastructure failure as an empty catalog.
- Keep `/api/v1/me` as the **only** client source of User roles and ordinary Permission **names** under
  [ADR 0004](../adr/0004-client-authority-and-runtime-state.md) and
  [TASK-00049](../tasks/00049-TASK.md); it is planned, not presently connected to the browser. The Feature
  endpoint's `available` uses the package's bound-ID evaluation for its current principal rather than the
  client attempting to equate a Permission name with the stored Feature Permission ID. Frontend controls and
  protected route presentation combine that Boolean with current `/me` permissions and fail closed on unknown,
  stale, incomplete or failed reads. Refetch on setting/authority changes and use the existing bounded
  volatile cache/invalidation rules; never persist or broadcast Feature/authority snapshots as credentials or
  use UI state as an authorization decision. For Agent tools, evaluate fresh authenticated Agent principal
  authority at their own server boundary; `/me` is a human browser projection, not Agent authentication.
- Integrate `FeatureFlagMiddleware` **post-route, pre-Action** with the final matched FQCN Action method and
  package Attribute placement, consistent with [TASK-00117](../tasks/00117-TASK.md)'s separately planned
  `RequiresPermission`/JWT-by-default gate. Resolve the already-authorized User/Agent principal, or `null`
  only for an explicitly approved public route, and call package `FeatureAvailability` against current stored
  Feature and Permission state at each guarded invocation. For a declared Feature, return 404 without
  constructing/dispatching the Action when `OFF` or `PREVIEW`-ineligible, continue when `ON` or
  `PREVIEW`-eligible, and still enforce *all* ordinary route and use-case authorization. Do not duplicate the
  package's OFF/PREVIEW/ON policy inside middleware. Unknown Features, broken bindings, malformed declarations
  and storage outages **never** pass through or silently become OFF; use safely classified failures/internal
  diagnostics without revealing arbitrary repository details. Feature settings must be observed fresh on
  successive checks, including reused workers; an already-admitted operation need not be retroactively
  cancelled when a later setting changes.
- A plain method declaration is metadata, not enforcement. Every supported flagged HTTP Action must pass
  the middleware, and any CLI, worker, Agent/MCP or other entry path to that *same* flagged capability must
  register and enforce its own equivalent server-side availability check as well as action authorization.
  Declaring a Feature on a route must not unintentionally broaden access to anonymous users when `ON`, or
  bypass CSRF, target checks, trusted origins, sandbox/workflow grants or authentication. If a path cannot be
  covered, do not declare its capability safely rolled out. Exact first product Feature and any ownership
  handoff for that future feature remain a **later explicit decision**, not a synthetic EPIC acceptance gate.
- Feature retirement requires a human-approved cleanup chore removing declarations **and** explicit
  registrations and runtime checks from source; it is not created automatically when status becomes `ON`.
  Deploy the change, verify that all actual running versions/modules have no references and obtain a fresh
  complete `CURRENT` discovery. Only then may a separately authorized admin confirm `RemoveFeature` against
  stable ID and current positive revision. A referenced Feature is not removable at any status, including
  `OFF` or `ON`. Incomplete discovery, stale record, deployment overlap, retained paths or operational
  uncertainty holds; no force-delete or substitution of candidate absence for current absence. Removal
  releases only its bound Permission reference; a later use of that name creates a **new** identity `OFF`
  through authorized provisioning, never resurrecting the old state or audience.
- Preserve exact PostgreSQL expected-state changes and permission-reference fences across create, rebind,
  removal, Role/Agent assignments and managed-policy reconciliation on the shared transaction boundary.
  Authorize privileged setup/retirement separately from ordinary management; read errors and uncertain
  commits are not successful activation or deletion. Qualify actual simultaneous races, rollback, complete
  discovery, current/candidate identity, fresh repository reads, Action and frontend gates, authorized direct
  calls and safe errors with owned tests and `./bin/build`. No dummy Feature, fabricated live Action, extra
  proof-only project, test of test infrastructure or staged half-release is required. Normal owned behavior
  and integration-contract tests still apply. Until a real flagged capability is deliberately selected and
  integrated by its owner, do **not** claim one is currently enabled or beta-tested merely because the complete
  reusable infrastructure is ready.
- Exclude public/unprotected Feature catalogs, generic Permission mutation, Feature testing Permission as
  management grant, client-only security gates, automatic registration or on-demand creation at runtime,
  forced deletion of referenced Features, blind toggles after stale conflict, guessed scanning scope, Feature
  status as a substitute for ordinary action authorization, and automatically created cleanup TASKs. Defer
  exact Permission identifier, routes, catalog pagination/limits, scanner wiring, deployment-runbook mechanics,
  error response envelope, UI design and implementation/PR slices to TICKET/TASK planning; the full catalog,
  per-principal availability and package-backed middleware outcomes do not.

## Progress

Approved after the WF-032 handoff through this grill. The maintainer selected package-backed HTTP Action
`FeatureFlagMiddleware` and a **single** authenticated complete Feature catalog with status, bound testing
Permission and server-computed `available` for each signed-in User. `/me` remains the planned source for
ordinary User permission names; a Feature's bound testing Permission is checked by **ID** on the server. The
maintainer rejected selecting a fake or arbitrary Feature just to demonstrate readiness: the first real
capability is flagged when its owner needs staged rollout, with normal defect repair if actual use exposes a
problem. When an enabled Feature becomes permanent, a later chore removes all checks and deployments before
separately authorized record deletion. No Feature, gate, admin screen, endpoint, chore TASK, runtime validation
or deployment was implemented in this grill. TICKET/TASK decomposition is separate.

The maintainer subsequently approved five requirement areas through `to-tickets`:
[TICKET-00070](../tickets/00070-TICKET.md) owns complete code-scope discovery, atomic OFF provisioning,
fresh preparation and shared reference integrity; [TICKET-00071](../tickets/00071-TICKET.md) owns package-backed
HTTP and registered non-HTTP availability checks; [TICKET-00072](../tickets/00072-TICKET.md) owns the single
complete authenticated catalog and fail-closed browser visibility; [TICKET-00073](../tickets/00073-TICKET.md)
owns authorized creation/rebinding/status management; and [TICKET-00074](../tickets/00074-TICKET.md) owns
CURRENT-code guarded retirement and safe reintroduction. These are cohesive requirements, not five TASKs or
PRs. They retain the honest empty catalog and later owner-selected real Feature; no Feature, gate, product
route, cleanup TASK or deployment was created during decomposition.
