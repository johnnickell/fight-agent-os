# Establish project-local execution and design skills

## Destination

Create the first project-local execution and design skill suite so agents can implement, review, land, and design approved Fight Agent OS work without importing Factory workflow machinery. The suite includes `work`, `review`, `land`, `design`, and `design-review`, supported by concise project-owned standards docs that the skills can load.

The outcome is a safe handoff path from approved TASK scope through implementation, independent review, landing documentation, bounded cleanup, and human PR merge control. It also establishes disposable evidence-first UI exploration and independent visual/design critique before authentication, authorization, and dashboard work depends on UI decisions.

## Decisions and exclusions

- Resolve [WF-002](../wayfinder/tickets/WF-002-shape-agent-skill-suite.md) by creating short project-local skills named `work`, `review`, `land`, `design`, and `design-review`; do not use a `fight-` prefix.
- Keep execution and design skills below planning authority: they consume approved planning records and may recommend follow-ups, but they do not create or decompose EPIC, TICKET, or TASK records.
- Do not import previous Factory workflows, `fight-*` commands, coordinators, approvals, runtime machinery, or historical planning records.
- `work` implements approved TASKs, coordinates main-checkout versus isolated-worktree choice, uses `feature/*` branches from `develop`, keeps worktrees under `.runs/worktrees/`, commits implementation work, preserves unrelated local work, follows Domain/Application/Adapter and CQRS boundaries, uses Action-Domain-Responder for HTTP interactions, adds testable code and tests, reproduces bugs first, runs focused checks and `./bin/build`, records evidence and warnings, and avoids unrelated edits.
- `review` independently reviews a local branch or PR against the TASK, diff, tests, and evidence; attempts to disprove the implementation; verifies scope, architecture, CQRS, HTTP boundaries, security and authorization concerns, test coverage, warning disclosure, and planning updates; and reports blocking and non-blocking findings without approving its own work.
- `land` does not re-review code. It verifies review signoff, finalizes planning and documentation, marks the TASK `done`, refreshes generated views, runs final required checks, commits and pushes landing documentation if needed, opens or updates the PR, and hands control back for human PR review and merge.
- TASK `done` means implementation acceptance, verification, and required review fixes are complete. Merge, deployment, release certification, and archive remain separate states and require separate human authority or later planning.
- `land` may perform bounded cleanup only for resources demonstrably owned by the TASK, such as task-specific `.runs/` material, worktrees, temporary prototype folders, browser servers, captured PIDs, test databases, and task-specific Docker containers or volumes. It must not delete shared services, source files, non-scratch evidence, or ambiguous resources without asking.
- `design` performs evidence-first disposable UI/design exploration under `.runs/prototypes/<scope>/`: inspect context, frame the brief, cite references and licenses, explore meaningful alternatives, use fake data only, capture responsive and state screenshots when fidelity warrants, record accessibility and interaction checks, and end with a verdict or handoff. Prototype code is never production code.
- `design-review` runs independently from `design`, renders artifacts when possible, checks the brief, responsive behavior, states, keyboard and focus behavior, semantics, contrast, copy, error and recovery paths, accessibility evidence limits, source/provenance, and implementation handoff; it returns accept, revise, or reject with blocking findings separated from subjective critique.
- Visual taste is a project-owned design-language decision, not delegated to OpenDesign or another external tool as the source of truth. OpenDesign remains inspiration only.
- For visual-language work, `design` should support a disposable Bootswatch-like browser specimen showing controls, typography, colors, spacing, focus states, form states, navigation, cards, tables, alerts, logo and artifact comparisons, variant notes, and recommended semantic token and Bootstrap variable mappings.
- Create concise shared engineering and design standards docs as needed so the skills load consistent rules rather than duplicating long instructions.
