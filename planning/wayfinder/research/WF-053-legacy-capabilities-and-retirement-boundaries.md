# Legacy capabilities and independent retirement boundaries

## Question

For [WF-053](../tickets/WF-053-inventory-legacy-capabilities-and-retirement-gates.md), what useful Local Development,
Omphalos, Ideaverse, `$aios` and `$fight` capabilities must remain while Fight Agent OS reaches first production,
and what evidence and separate authority would a later replacement require?

## Short answer

**Preserve all five surfaces. First production replaces none of them by implication.**

The shared router has its own operator/lifecycle contract; Omphalos has a personal homepage and supporting
application capabilities; Ideaverse is a knowledge vault, not just an engineering backlog; `$aios` routes personal
and engineering workflows; `$fight` routes an independent engineering suite, with an optional Factory execution
layer. A browser Wayfinder release does not establish parity with that collection.

This bounded source inventory resolves WF-053's research question. Missing replacements remain **preserve/hold**,
not new launch dependencies or instructions to rebuild every capability. Potential Nickell applications remain
separate, unapproved replacement investigations. No ownership transfer, source import, route/data migration,
command replacement, startup change or retirement is approved.

## Important counterchecks

### Homepage is not the shared router

Local Development explicitly owns the router independently of Omphalos. Omphalos can stop without intentionally
stopping other routes, while its own homepage still depends on its application and needed services. A later Agent
OS domain wizard must preserve this independence rather than move ingress supervision into the browser/server
process. The shared-domain dispatcher corroborates the existence of the operator interface; its nested apply/
rollback/supervisor implementation was not fully audited. [S1–S2]

### Homepage data is not only a browser bookmark list

The inspected homepage consumes brief, daily-note, health and commitment data and links to other tools. Base
configuration declares durable database storage and controlled vault mounts. Retiring an application container
therefore cannot be equated with deleting an obsolete HTML landing page. A future data inventory would need
separate authority; no bookmarks, daily notes, inboxes, tokens, encryption keys or stored personal records were
read for this research. [S3–S6]

### Skills, runtime and authoritative records are distinct

The AIOS map already routes Fight engineering into the standalone suite; the installed Fight router says the
Factory is optional and does not recursively start another harness merely to route a skill. Removing Factory
containers cannot prove that `$fight` is replaced, and replacing `$fight` cannot retire the personal `$aios`
workflows. Direct skill routing may work without the old application database, but that is not permission to
remove runtime traces or ongoing operations. [S8–S11]

Agent OS's own foundation explicitly chose new project-local skills and project-owned rules instead of importing
Factory machinery/history/approvals. Its current standards and individual workflow instructions remain the
receiving contract; old names, release terminology or historical approvals do not override them. No instruction
from the inspected legacy routers was invoked as this session's workflow. [R2]

### Source presence is not live qualification

The inspected source contains a real homepage component and authenticated brief endpoint, as well as concrete
routing dispatch and declared service configuration. None proves current listener ownership, certificate validity,
background-job freshness, credential usability, loaded startup jobs, browser preferences or successful restart.
No HTTP request, browser session, Docker/Compose command, launchctl operation, database query, installer, skill
invocation, health command or provider request was performed.

## Four independent transitions

1. **Infrastructure ownership/lifecycle:** a future change can relocate implementation or supervision while
   preserving route/CA/application owners. It needs a named target supplier, authoritative configuration/receipt
   continuity, controlled handover without competing supervisors and independently usable rollback/recovery.
2. **Route/data migration:** moving an application's hostname, backend or persistent state is a separate effect.
   Preview exact affected scope, preserve unrelated routes/data, handle TLS/origin/cookie implications and establish
   recoverable source/destination state. Router ownership alone grants none of this. Application database restore
   or rewind remains explicit, not an assumed rollback side effect.
3. **Engineering entry-point replacement:** map selected old invocations to current target-project workflows and
   harness capabilities; preserve required human approvals, independent review, command recovery and history.
   Test relevant normal and failure paths without replacing all personal workflows or importing old policies.
4. **Retirement:** only after the selected capability has a verified usable replacement, request separate human
   authority for exact obsolete commands/services/files and retained history. Check shared references, active work and data recovery. A new installation, passing build, map closure
   or name similarity is not retirement approval. Deletion and credential/trust revocation are separately scoped.

These are concrete future change criteria, not a readiness framework, certification project or production-before-
implementation requirement. Actual legacy verification blocks only the proposed transition—not ordinary Agent OS
local development, staging or the first OpenRouter browser Planning milestone.
