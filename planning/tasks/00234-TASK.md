# Enroll protected holders destinations and worker authority

## Outcome

Provide protected enrollment and revocation of distinct credential holders, server-registered fixed destinations
and explicitly delegated delivery/maintenance workers. Current caller, target and historical-destination policy
supplies real shared-transaction authorization participants, not a registry whose mere presence grants access.

## Scope

- In scope: Supported holder/host and destination registration, immutable binding revisions, bounded original
  scope delegation, separate delivery and maintenance authority, worker/operator authentication, safe inspection
  and revocation; actual package authorization adapters and their fenced policy writers.
- Out of scope: Credential generation or export, sink material, Agent activation/tool use, public UI, arbitrary
  remote destinations, provider accounts, a second Harness trust registry or expansion of human managed rights.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Enroll or revise a protected holder/destination | Authorized operator enrollment/reassignment using expected registration state | Actual supported host, owner, stable destination and current binding | Attributable registration change, not credential issuance | Durable registration/epoch change, preserving stable-slot order and historical ownership |
| Delegate or revoke worker authority | Explicit bounded operator grant/revocation for original scope, target and destination | Current real worker, grant and expiry | Secret-free grant/revocation fact only after commit | Shared-fence epoch advancement; no originating-caller impersonation |
| Authorize package work and reads | Package `AgentOperationAuthorization`, `AgentDeliveryAuthorization`, `AgentMaintenanceAuthorization` methods | Current invocation, original scope/target/binding and policy | N/A for reads; no duplicate package lifecycle events | Current fenced allow or sanitized denial, not materialization/activation authority |

## Validation and permissions

Follow TASK-00227's accepted ownership, lock and transition design. Select and document actual supported host,
protected operator/worker identity and destination registration mechanisms compatible with the existing Harness
boundary. Reuse authoritative context and trust owners; never infer enrollment from local files, process ownership,
an actor string, a Super Admin label or model instructions. This TASK implements protected operational grants;
TICKET-00063 owns human management Permissions/UI. Do not silently extend TASK-00036's original policy catalog.

Authenticate workers as themselves, with explicit current delegation to retained original scope and target. Bind
authority epochs to real worker, policy revisions, target, binding and earliest expiry; revoke/regrant cannot
recreate an old epoch. Cohort-first fences and all relevant policy writes share the package transaction connection
through completion without nested transactions. A trustworthy clock must not extend authority on rollback.

Delivery authority does not imply maintenance or global accounting authority. Historical destination maintenance
requires explicit predecessor access, not current ownership of a reassigned slot. Read authorization runs before
lookup/selection and again before target disclosure, including empty results; denied items reject a whole batch.
Reads neither mutate nor start a Unit of Work. No supplied URL/path/receipt/key handle chooses a sink or holder.
Unknown host/enrollment, unavailable policy or stale state denies without existence or provider detail disclosure.

## Acceptance criteria

- [ ] Actual protected enrollment/inspection/revocation works for distinct holders and registered destinations;
  stale changes conflict, immutable bindings and stable slot identity survive reassignment, and no raw key is returned.
- [ ] Worker/delegation identity remains distinct from original caller scope; wrong holder, forged origin, expired
  grant and unauthorized target or historical binding deny across direct, console and worker paths.
- [ ] Current transaction-bound authorization and writer epochs serialize on PostgreSQL in both winner orders;
  rollback restores grants/epochs and revoke/regrant rejects old authority, including desired-state no-ops.
- [ ] Discovery/status/maintenance reads preserve separate current visibility policy without side effects; empty
  and partial-denial cases cannot disclose existence or masquerade as successful work selection.
- [ ] Actual supported host/trust integration and safe clock behavior are recorded; unsupported participants remain
  unavailable. Registration alone neither issues a credential nor enables an incomplete operation composition.
