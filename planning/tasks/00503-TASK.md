# Launch the Pi terminal workspace globally from any project

## Outcome

Install a global `fight-terminal` command that opens the Pi terminal workspace in the caller's project or
worktree. Replace the repository-local `bin/terminal` entry point. Users should not copy scripts into projects
or reference an Agent OS checkout path each time they start the workspace.

## Scope

Deliver the package-owned executable, a documented supported user-level installation/update/removal flow and
migration of current workspace launch/resume instructions. Reserve repository `bin/*` for its existing
Docker-oriented operations; do not add another host UI launcher there. Retire `bin/terminal` in this TASK,
updating executable callers and current documentation while preserving historical task receipts.

Use `fight-terminal` as the command name. Install against the trusted Harness package source; qualify the actual
package-manager/Pi installation behavior rather than assuming `pi install` places executables on PATH. No registry
publication is required. Support the existing local-source distribution and explain whether it links to or copies
the source, how updates take effect, and how to recover after the source moves or disappears. Installation should
not require administrator privileges or silently replace an unrelated command with the same name.

Keep child-following/worktree-log behavior with TASK-00502 and the Docker reader with TASK-00449. Neither is a
blocker for this launcher. No global installation, shell-profile mutation or runtime implementation occurs as a
side effect of this planning approval.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Install or update the workspace launcher | Documented explicit user-level package installation/update | Resolved command and trusted package source | N/A — local installation | Package-owned executable available on PATH |
| Start or resume in another project | `fight-terminal` with existing supported options, including `--session` | Caller directory, actual Pi session and active Harness status | Existing Pi RPC lifecycle | Start the existing client in the caller's directory |
| Remove or recover the installation | Documented removal/reinstallation | Missing source, dependency or command collision diagnostics | N/A — local installation | Remove only owned launcher artifacts; preserve user sessions/settings |

## Validation and permissions

Preserve the caller's working directory through executable/symlink resolution, including paths with spaces.
Load implementation assets from the installed package, never by searching the target project's executable files.
Retain normal Pi resource discovery, protected Harness startup/status checks, project enrollment and tool policy;
installing or launching the UI grants no project access or model spending. Do not automatically enroll projects,
copy credentials, force providers/models or override the user's `pi` command.

Keep runtime/session state at the existing documented target-project `var/` boundary, not the provider checkout
or `.runs/`. Missing Node/Pi, duplicate or unavailable Harness resources, unwritable runtime state and moved package
sources must produce actionable errors rather than bypass policy or silently switch project directories.
Qualify supported installed Pi APIs without adding a Pi version pin. Package installation must retain the current
private-publication guard; do not publish a package to deliver a local global command.

## Acceptance criteria

- [ ] Following the documented installation flow makes `fight-terminal` available on PATH without adding a script to the target project or requiring administrator privileges.
- [ ] Launching from another project and an isolated worktree preserves the caller directory, normal Harness discovery/policy and supported session-resume behavior; paths with spaces work.
- [ ] The executable resolves its own installed assets independently of the target project's contents. Missing dependencies/source and command collisions have actionable recovery instructions.
- [ ] `bin/terminal` is removed and current launch/resume help, runbook examples and maintained executable callers use the global entry point; historical evidence remains unchanged.
- [ ] Update/removal behavior is qualified and documented. Removal preserves Pi credentials/settings unrelated to this installation, project enrollment and saved sessions.
- [ ] No new Docker lifecycle operation, shell capability, automatic enrollment, model selection or privilege expansion is introduced.

## Verification and evidence

Verify installation, PATH resolution, package/symlink asset resolution, update and removal directly with the
owning package tools in an isolated user prefix. Do not add product tests for packaging/wrapper wiring. Exercise
the real launcher from a separate project and linked worktree, including a path with spaces, and confirm session
identity/resumption, protected startup and error behavior. Inspect actual terminal evidence for the entry-point
migration; do not treat a help screen as successful protected startup. Record the supported installation commands,
tested tool versions and limitations without secrets. Run focused checks and full `./bin/build` before publication.
