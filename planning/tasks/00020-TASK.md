# Centralize correlated and sanitized API failures

## Outcome

One centralized HTTP failure boundary classifies known validation, authentication, authorization, conflict, explicit not-found, and framework routing failures while producing correlated secret-safe diagnostics and generic sanitized responses for unknown throwables.

## Scope

- In scope: Explicit exception-to-status/JSend classification; transport and Domain validation categories; authentication/authorization/conflict/explicit resource-not-found mappings; unknown route/method handling; explicit exclusion of generic `LookupException` from automatic 404; correlation ID validation/generation/propagation policy; PSR logging of unknown failures; safe generic 500; middleware ordering; representative functional tests.
- Out of scope: Product-specific exceptions/endpoints, authentication implementation, observability backend, tracing platform, CORS, debug UI, exposing stack traces, and broad retry policy.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Map known failure | No additional command | Inspect explicit exception category/context | No new event | Documented safe status and JSend envelope are returned centrally |
| Handle route/method miss | No command | Inspect framework HTTP exception safely | No event | Sanitized not-found/method response contains no arbitrary framework message |
| Handle unknown throwable | No additional command | Validate/generate correlation and inspect throwable for logs only | No event | Generic 500 reaches client; structured secret-safe correlated diagnostic is logged |
| Reject malicious correlation input | No command | Validate allowed format/length and trust policy | No event | Invalid external value is replaced/rejected and cannot inject logs/headers |

## Validation and permissions

Build an explicit allowlisted mapping rather than status inference from arbitrary exception code/message. Keep malformed transport and declared validation distinct where the API contract requires, while using safe envelopes. Authentication, authorization, stale/conflict, and resource-not-found mapping must rely on explicit types/context. Generic `LookupException` must not become 404 automatically.

Unknown throwable responses may contain only the generic public message and correlation reference allowed by policy. Never return arbitrary messages, traces, file paths, SQL, credentials, grants, tokens, payloads, provider details, internal IDs, or debug data. Logs retain sufficient exception/correlation/request metadata for diagnosis but redact credentials/bodies/sensitive headers and resist newline/structured-log injection.

Define accepted inbound correlation format/length, generation, replacement, response header/body behavior, propagation, and trusted/untrusted handling. Middleware order must catch Action, validation, JSON, and Slim routing failures without converting known client errors to generic 500 or leaking framework text.

No user-facing permission is introduced. Central error and logging composition are authorized; product handlers are not.

## Acceptance criteria

- [ ] A centralized allowlisted mapper defines safe statuses/envelopes for transport/Domain validation, authentication, authorization, conflict/stale state, and explicit resource not found.
- [ ] Generic `LookupException` is demonstrably excluded from automatic 404 mapping.
- [ ] Unknown routes and unsupported methods return deterministic sanitized API responses.
- [ ] Unknown throwables return generic 500 output without arbitrary exception/internal/sensitive data.
- [ ] Unknown failures produce structured logs with sufficient correlation and exception context but no request credentials/body or log injection.
- [ ] Correlation IDs are validated/generated under explicit format, length, trust, propagation, response, and logging rules.
- [ ] Malformed/oversized/injection correlation values cannot control diagnostics or response headers unsafely.
- [ ] Middleware ordering preserves TASK-00019 validation and TASK-00018 successful responses.
- [ ] Production configuration cannot enable stack traces or arbitrary exception-message responses.
- [ ] Focused mapping/logging/functional checks and `./bin/build` pass with fresh evidence.
