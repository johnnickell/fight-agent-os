# Gate browser Feature presentation with current catalog availability

## Outcome

The authenticated application frame consumes the real complete catalog and combines server `available` with
current `/me` ordinary Permissions for Feature-dependent routes, loaders, navigation, controls and forms.
Unknown/stale/incomplete/failed observations suppress presentation and effects until current reads succeed.

## Scope

- In scope: Typed production catalog service/codec, one volatile context-scoped catalog owner, existing authority/
  frame integration, shared guarded presentation/action behavior, invalidation/freshness/races and accessibility.
- Out of scope: Another principal/evaluator policy, persisted or broadcast Feature authority, management screens/
  mutations, Agent auth, push service, fake flagged product route, automatic operation replay and server enforcement.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Load current Feature presentation | N/A — shared authenticated GET | TASK-00295 catalog and existing sole `/me` projection | Local load-state notification only | Publish one strictly decoded complete catalog for the current context |
| Enter or activate a Feature-dependent surface | Only the owning operation after current presentation checks | Server `available` plus shared exact ordinary Permission evaluation | Owning operation facts only | Denied outlet/loader/control/form cannot mount or dispatch protected work |
| Retire stale presentation | N/A — local invalidation | Current context, catalog generation and monotonic freshness | Bounded local/cross-tab invalidation intent only | Retire usable catalog/private data and late requests; bounded refetch or explicit retry |
| Observe authoritative server denial | No replay of the denied operation | Fresh authority/catalog when appropriate | Local invalidation only | Preserve the actual rejection, safe recovery and no accidental reauthentication |

## Validation and permissions

Consume TASK-00295's single real catalog and TASK-00051's authenticated frame, with TASK-00049's production `/me`
service, TASK-00048's authentication coordinator and TASK-00028's cache/guard primitives transitively. The current
foundation has an injectable `AuthorityCache`, generation-scoped private data, `GuardedRoute` and a
`PermissionButton` that rechecks at activation; these are supplier seams, not proof of production Feature use.
Use the shared same-origin API client and volatile credential owner. Do not create another fetch/authentication
client, token decoder, User/Permission store or pretend that the present public shell is already authenticated.

Create one catalog cache entry owned with private server data for the tab's active authentication context.
Components subscribe to that owner rather than copying mutable catalogs, principals or derived grants. `/me`
remains the only User/role/ordinary Permission-name source; Feature data is not another principal projection.
Do not add permissions, identity, tokens or session IDs to the catalog protocol merely to correlate responses.
Capture the existing authority scope and a catalog request generation locally; raw tokens are not cache keys.

Strictly decode the exact JSend complete-response shape and snake_case-to-camelCase mapping. Require
`complete: true`, exact total/list agreement, finite bounds, unique valid Feature IDs/names, valid status,
original Permission IDs, nullable names/consistent missing-binding marker and actual Boolean availability.
Reject malformed, duplicate, extra/unsupported or incomplete shapes atomically, never salvage a first page or
partial set. Enforce bounded response consumption through the shared transport where needed; a header or a
post-allocation size check alone is not a memory bound. No successful empty substitute for errors. A confirmed
complete empty catalog is valid, but cannot satisfy a required Feature absent from that catalog.

Use the server Boolean, not a browser copy of OFF/PREVIEW/ON policy or a Permission-name-to-ID comparison.
Compose with the existing exact ordinary Permission evaluator and complete ancestor/leaf route requirements.
Role names remain display data; neither Super Admin nor ON bypasses ordinary rights. Add explicit static Feature
requirements at existing presentation seams; missing/malformed declared Feature metadata fails closed rather than
becoming public. Unflagged routes and controls retain their existing semantics without an unnecessary catalog
prerequisite, and public login/recovery must not wait for a private catalog.

Gate protected route outlets, lazy imports and loaders before mounting, as well as navigation, action handlers,
form submission and keyboard activation. Recheck both current owner states at activation and fence resulting
private requests against authority and Feature invalidation. Retire/unmount affected data and volatile drafts on
lost availability; a stale callback cannot dispatch merely because a button was once rendered. Feature invalidation
must prevent late protected results from restoring data even when the principal context has not changed.

Mount the real production catalog service/owner into the authenticated frame without a dummy Feature/route.
Reusable guard/component contracts may use controlled fixtures; those do not install synthetic product endpoints
or establish a complete real beta journey. TICKET-00077 now owns the selected `ai-template-proposals` integration
at actual Generate/Regenerate controls and all alternative admission paths; it preserves manual editing/publication
and safe handling of admitted attempts when OFF. TICKET-00073 owns Feature Flags list/detail/edit management;
standalone manual-create UI/API is deferred. Do not add a duplicate or demonstration management page here.

Freshness is at most 60 seconds on a monotonic clock from the catalog request's start, not delayed receipt, and
never outlives the current `/me` authority scope/budget. Both observations must remain current; neither extends
the other's deadline or proves a shared server snapshot. Check deadlines at render/action even if timers were
suspended. On expiry, clock discontinuity or return from hidden/suspended/bfcache state, invalidate before protected
presentation resumes. Coalesce finite on-demand refetch; no polling requirement, renewed deadline on read/failure,
stale-while-revalidate authority or endless automatic retry. Keep explicit accessible retry for recoverable failure.

Retire catalog, affected private data and requests on refresh start, credential/context change, authority
invalidation, logout and terminal failure through existing owners. Refetch only under current eligible authority;
login/token receipt alone is insufficient. Setting/binding/create/remove/reintroduction completion or uncertain
outcome invalidates rather than patching authoritative availability from a command result or package event.
Expose the narrow existing-style invalidation seam for later TICKET-00073/00074 operations; their actual mutation
integration and affected races belong to those owners, not a reverse prerequisite here.

Accept only current-scope/current-generation successes and errors; abort alone is insufficient. Old catalog,
`/me`, protected-data or HTTP error responses cannot restore invalidated data or terminate a newer explicit login.
A current `401` follows existing bounded authentication recovery; Feature false/missing or a catalog outage is not
anonymous authority or a reason to logout/refresh repeatedly. Current server `403` or Feature denial remains final
for that attempt; invalidate/refetch appropriate data without automatically repeating the business operation.
Do not assume every 404 is a Feature denial or override a target-policy rejection with a refreshed catalog.

Cross-tab messages carry only bounded invalidation intent, never Feature settings, availability, principal,
credentials beyond the already accepted auth protocol, drafts or identity. Use existing coordinator/fallbacks;
no new broadcast bus or trusted peer cache. There is no push-delivery or instant cross-tab consistency promise:
unsignalled changes can remain present only within the bounded freshness window, while server checks remain current.
No catalog authority in storage, service workers, URLs/history, HTML/config, logs, analytics or retained devtools.

Retain accessible safe loading/unavailable/forbidden/error/retry semantics without flashing protected content or
login redirect loops. When withdrawing a focused control/outlet, provide safe focus/announcement recovery without
revealing protected content. Safe intended-route restoration also rechecks current Feature requirements; an absent,
false or unavailable Feature cannot be entered merely because `/me` allows it. Preserve the existing bounded
volatile intent and no secret/draft restoration rules.
