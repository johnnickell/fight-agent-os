# Establish authorized Teams on registered Projects

## Outcome

A currently authorized administrator can create, inspect, list and rename a stable Team through protected server
operations, starting with an explicit registered-Project association and valid preferred-Team selection.
Team identity and associations confer no Agent, Project, Permission or Workflow authority.

## Scope

- In scope: Team identity/current state and safe history, initial Project association/default, name management,
  complete authorized list/detail queries, PostgreSQL persistence, required audit and post-commit facts; protected
  API/direct entry, expected-state checks and an explicit managed Team-management policy extension.
- Out of scope: Agent creation or membership, additional association management, destructive unlink/removal,
  browser product pages, template management, selection/dispatch, another Project registry or administrator Role.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Establish Team on a Project | ID-bearing void CreateTeam command with initial association and explicit default choice | Current registered Project/scope, associations/default and expected state | Owned Team/association/default facts after commit | Team, link, default and required audit commit together or not at all |
| Inspect Team administration | N/A — read-only | Safe current Team/list/detail and initial association/default with stable pagination | N/A — viewing emits no business event | Authorized bounded Views, not a credential or grant projection |
| Rename Team | Owned expected-state name update | Current Team identity/revision and actor authority | Owned name-change fact only for committed change | Stable identity and history retained; no effect on grants or session bindings |
| Reconcile an uncertain creation | No automatic replay | Fresh authorized Team list/detail query and existing uniqueness constraints | No invented original-result fact | Current state and known Team ID or explicit uncertainty; a new attempt may conflict |

Names describe semantic use cases, not guessed existing package APIs. Team policy belongs to Agent OS; use
AccessControl's actual current principal/Permission and managed-policy contracts rather than copying them.

## Validation and permissions

Extend TASK-00036's complete managed policy explicitly with stable library/factory-generated Team-management
Permission identities and code references, preserving all existing definitions and memberships. Rights are
`SUPER_ADMIN_ONLY`, initially only through the managed Super Admin Role. Do not silently replace its historical
exact catalog, assign these rights to Agents/custom Roles or add Workspace/Project administrator Roles.
Actual Permission and target/scope checks protect HTTP and direct paths; a role name or UI visibility grants nothing.
Agent/template administration remain distinct intent-specific capabilities, not implied by Team management.

The entry adapter generates typed stable `TeamId` with its owning factory and puts it in a void `CreateTeam`
command. The aggregate accepts that ID; after successful dispatch the adapter returns the known ID without a
result DTO or identity-recovery fetch. Use aggregate-first Team ownership with a collection-like TeamRepository and matching registered Application
CommandHandler/QueryHandlers, not a mixed Team Store. Each entry admits caller/
Project/target scope before configured bus dispatch; no duplicate Application gate or ordinary caller-revocation
lock. Registered handlers coordinate persistence and required audit through the generic transaction boundary;
validate bounded names, expected revisions and
registered Project identity using TASK-00080's lifecycle/reference authority. Never infer identity or scope
from name, path or slug. A new Team has a real initial Project link; a Project with assigned Teams has
exactly one linked preferred Team. The first association requires an explicit default choice. Adding another Team
preserves the existing default unless an explicit authorized replacement is included. No implicit arbitrary default.

Use PostgreSQL constraints and cohort-first shared reference fences before subordinate locks on the canonical
connection. Serialize creation/default choice with competing registration lifecycle and association writes.
State, references and required audit commit or roll back together. Events follow confirmed commit, not an external
call within it. Validate no-ops too. Apply TASK-00227/00228's safe transition/fence contract without claiming that
Team setup qualifies an incomplete Agent operation cohort or silently bypassing required admission.

Expose safe explicit typed camelCase PHP Views; HTTP Data/Responders map snake_case and documented HTTP validation/errors through one Action per interaction.
Do not expose credentials, private tool/session data, database errors or hidden Project detail. Storage failure
is not an empty list. After uncertain creation use uniqueness and fresh authorized queries, not an original-response journal or
transparent replay. An error or post-commit event failure does not prove rollback or authorize compensation.

## Acceptance criteria

- [ ] Protected creation establishes a stable Team, its real initial Project association, exactly one valid
  preferred Team where needed and attributable audit, with no Agent or grant side effect.
- [ ] Controlled PostgreSQL creation/default and Project-lifecycle races, stale edits, no-ops and rollback
  preserve association/default invariants and known safe conflicts without partial state.
- [ ] Authorized list/detail/name updates preserve identity/history and deterministic bounded reads; forbidden,
  hidden-scope, missing, unavailable and uncertain results are truthful and secret-free.
- [ ] Actual current Permission removal denies direct and HTTP operations. The explicit complete-policy extension
  preserves existing authority, rejects protected-tier delegation and grants no implicit administrator shortcut.
- [ ] Lost acknowledgement and post-commit failure use fresh authorized queries and existing uniqueness,
  without original-result replay or an idempotent duplicate-request guarantee. A new creation attempt may conflict;
  do not fabricate success, infer rollback or perform external effects inside the transaction.
