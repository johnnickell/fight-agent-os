# Dispatch one notice with protected recoverable outcomes

## Outcome

A protected worker processes one exact accepted old-mailbox notice through committed claim, external send and
fenced outcome phases. Both request and completion stages use fixed informational content and stable identities;
crashes and ambiguous provider responses remain recoverable and never imply exactly-once mailbox delivery.

## Scope

- In scope: Owned notice claim/attempt/outcome behavior and PostgreSQL persistence; bounded retry/failure policy;
  fixed text/HTML notice mapping to the shared mail capability; safe exact-notice inspection and denial behavior.
- Out of scope: New credential-delivery queue, generic job/template platform, product resend/enqueue routes,
  production provider enrollment, deployed schedule, source changes to invitation/reset lifecycle policy or UI.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Admit one notice attempt | Owned protected exact-notice dispatch operation | Current committed intent, due state, immutable payload and worker authority | Owned attempt fact after committed claim | One bounded revision/token-fenced claim; no network effect in the transaction |
| Send the informational message | Fixed mail-capability invocation outside business transaction | Only required immutable notice content/recipient and provider readiness | No package request/confirmation event is re-emitted | Provider attempt reuses stable notice identity |
| Record or reconcile the result | Owned matching-outcome/reconciliation operation | Exact original attempt and qualified provider evidence where available | Owned safe outcome fact after matching commit | Fenced status/backoff or explicit uncertainty, not false success |

## Validation and permissions

Consume TASK-00274's immutable identity/recipient/change/stage model and TASK-00040's shared mail capability;
do not clone its mail abstraction or add notice work to package credential due discovery. Package grant delivery
remains the sole credential queue. This separate Agent OS persistence tracks only demonstrated informational
effects, under [ADR 0001](../adr/0001-application-ownership-and-orchestration.md) and
[ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md).

Only qualified internal worker authority can claim/invoke/record. An `--internal` flag, notice ID, user email or
ordinary browser Permission is not authentication or send authority. Fix eligible operation/stage/provider in
composition; reject caller-supplied recipient, template, URL, arbitrary mail body or executable handler. Recheck
current worker authority and expected state before use. No credential decryption is needed for these notices.

Commit a short exact claim with bounded lifetime and expected revision before external mail. Provider invocation
has finite timeout outside the transaction; a later transaction accepts only the matching current attempt.
Competing claims and expired/replaced claimants cannot overwrite current outcomes. A lease cannot recall an
already-started external call; disclose that residual duplicate risk rather than promise exactly once.

Define and document finite notice-specific retry/backoff/attempt bounds and explicit permanent/exhausted/uncertain
handling. Do not borrow the credential's one-hour expiry, delete work on cancel, reset budgets on reads/restart,
spin indefinitely or reissue an email-change request. Retry/reconciliation keeps the same notice identity and
immutable provider payload semantics, including content version. Provider idempotency is used only to its
qualified scope, retention and exact-payload rules; outside those guarantees duplicate mail remains possible.
Lost response or failure after acceptance before outcome commit is uncertain, never certainly unsent or delivered.

Render fixed, escaped deterministic text/HTML conveying the historical requested/completed fact, not current
pending authority. No tracking, remote active content, new-mail credential/link, approval, cancellation or undo
control. Do not assume delivery order between stages or put the new destination in a notice merely because the
package event carries it. Minimize recipient/content lifetime and prohibit bodies, personal addresses, provider
secrets and arbitrary SDK errors in ordinary logs, metrics, audit or safe status. Typed provider acceptance,
confirmed delivery where actually supported, retryable/permanent failure and uncertainty remain distinct.

## Acceptance criteria

- [ ] Only a protected exact committed notice can invoke the shared mail capability, after claim commit and
  outside a business transaction, using the original old recipient and stable stage-specific identity.
- [ ] Fixed safe content handles both stages without secrets, account mutation links, dynamic templates,
  arbitrary recipients or a duplicate mail/credential platform.
- [ ] PostgreSQL contention, stale claimant, timeout, provider rejection and acceptance/outcome-commit loss
  preserve fenced truthful state and finite same-identity recovery; accepted is not necessarily mailbox-delivered.
- [ ] Cancellation/credential expiry do not suppress accepted notices; restart does not renew budgets, and
  permanent/exhausted/uncertain work is observable rather than silently discarded or labeled successful.
