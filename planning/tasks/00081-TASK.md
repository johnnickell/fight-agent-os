# Version repository configuration and rollback

## Outcome

Authorized users can preview, append and inspect validated immutable Repository configuration revisions and restore prior values by appending a new attributable revision, while ordinary configuration changes cannot switch Planning authority or rewrite local instructions.

## Scope

- In scope: Closed versioned Repository configuration schema; current state plus immutable revisions; Repository binding; explicit planning-mode representation; base branch and allowed branch patterns; ordered named verification commands; known restrictions; required/recognized instruction locations; optional versioned sections for future owned references; actor/time/reason/provenance; expected revision; validation/impact preview; `ReviseRepositoryConfiguration`/`RepositoryConfigurationRevised`; `RestoreRepositoryConfigurationRevision`/`RepositoryConfigurationRevisionRestored`; current/history/compare queries; PostgreSQL migrations/repository/concurrency; audit evidence; independent view/revise/rollback permissions; versioned JSend API/OpenAPI.
- Out of scope: Markdown-to-database authority cutover, arbitrary JSON/plugin configuration, instruction-file editing, Git mutation, context resolution/snapshot creation, session conflict choices, browser UI, Workflow limits not yet owned, Harness/Pi transport, multi-workspace administration and interpreting prose as policy.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview a configuration revision | N/A — read-only validation | Compare proposed typed values with current revision and affected context fields | N/A — preview emits no Domain event | Safe validation, normalized proposal and known impact are returned without persistence |
| Revise Repository configuration | `ReviseRepositoryConfiguration` | Revalidate current expected revision and proposal | `RepositoryConfigurationRevised` | A new immutable revision and current pointer, actor/reason/provenance and audit evidence commit atomically |
| Compare revision history | N/A — read-only interaction | Get current/history/detail/compare configuration revisions | N/A — reads emit no Domain event | Authorized user sees typed differences and attribution without deleted/rewritten history |
| Restore prior configuration | `RestoreRepositoryConfigurationRevision` | Compare selected prior content with current revision and current validation | `RepositoryConfigurationRevisionRestored` | A new revision copies validated prior values; the selected and intervening revisions remain unchanged |

## Validation and permissions

Bind every configuration to one active Repository from TICKET-00024 and a versioned schema identifier. Use closed typed sections rather than arbitrary JSON. Validate canonical base-branch syntax, bounded allowed-branch patterns, unique ordered verification names and bounded executable command descriptors, recognized instruction locations, planning mode and known restriction types. Reject unknown fields/types, duplicate names, empty or unsafe patterns, secret-bearing values, internal service URLs, credential locators and unsupported future sections.

Represent all three accepted modes, but enforce their ownership: an unregistered/local context has no registered configuration authority; initial registration may be explicitly Markdown-authoritative; database-authoritative transition occurs only through TICKET-00028's guarded cutover. `ReviseRepositoryConfiguration` and rollback cannot perform, reverse or disguise that authority transition. Missing/unavailable authority never changes mode automatically.

Registered configuration may narrow application restrictions but cannot widen or disable non-overridable application safety, live authorization, approved-root containment, Repository lifecycle or later Workflow constraints. Validation reports prohibited widening as a safe structured failure. Local instruction and Skill text is not ingested into this schema.

Use expected current revision and active Repository revision where required. Preview is advisory only; command execution repeats all validation and authority checks transactionally. Persist current state, immutable revision, actor/time/reason/provenance, event effect where required by the accepted model, and audit evidence through one PostgreSQL transaction. Known stale/constraint conflicts map safely; no update or delete path rewrites revision history.

Restore accepts a prior revision identity plus current expected revision, revalidates copied values against current schema/application restrictions, and appends a new revision with restoration provenance. It does not move a pointer backward, erase later history or restore a now-prohibited value silently.

Require separate authoritative Permissions for viewing, revising and restoring configuration. Scope queries to authorized Workspace/Repository and lifecycle. HTTP Actions dispatch one command/query, Responders map safe explicit Views to JSend `snake_case`, and errors/OpenAPI follow the established API contract. Never expose raw command strings beyond authorized bounded display, secrets, persistence rows, SQL/constraints or hidden repository data.

## Acceptance criteria

- [ ] A closed versioned schema validates Repository binding, planning-mode representation, branch/base guidance, ordered named checks, restrictions and instruction locations without arbitrary JSON.
- [ ] Preview normalizes and explains validation/known impact without persistence; execution repeats every check against current revisions and authority.
- [ ] Revision appends immutable content, actor, time, reason and provenance atomically with current state, event effect and audit evidence.
- [ ] Stale expected revisions and competing writes fail safely; no accepted revision or current pointer is partially committed.
- [ ] History/detail/compare queries return stable permission-filtered Views without rewriting or omitting intervening revisions.
- [ ] Rollback appends a newly validated attributable revision copied from prior content and never rewrites/deletes history.
- [ ] Ordinary revision/rollback cannot enter, leave or counterfeit database-authoritative Planning mode.
- [ ] Registered configuration may narrow but never widen application safety, authorization, root, lifecycle or later authority constraints.
- [ ] No command edits instruction/Git files, parses prose, creates a context snapshot or grants Planning/Execution authority.
- [ ] Focused Domain/Application/PostgreSQL/concurrency/API/redaction tests and the canonical build pass with fresh evidence.
