# Screen permitted tool effects with Jev and resolve uncertainty

## Outcome

Every bash operation and mutating tool call in the protected profile receives bounded Jev screening after passing
deterministic checks. Only a current permitted operation can execute, with explicit operator resolution for valid
uncertainty and redacted evidence of the result. Deliver the semantic guard path of
[TICKET-00038](../tickets/00038-TICKET.md), normally in one independently reviewable PR.

## Scope

- Integrate [TASK-00159](00159-TASK.md)'s typed judgment capability into
  [TASK-00160](00160-TASK.md)'s qualified admission boundary. Deterministic denials stop before an upstream request.
  Screen every bash call and mutating tool call, including supported nested routes, after deterministic admission.
  Ordinary reads retain deterministic access checks; relevance screening belongs to TICKET-00039.
- Define a versioned rubric that classifies the actual proposed effect as `allow`, `deny` or `uncertain` against
  the operator-selected assignment scope and effect policy. Include the operation, arguments, working directory,
  relevant bounded context and revisions; missing context must not become an unsupported safe assertion.
- Initial automatic admission requires `allow` with reported classification confidence at least 0.95. A valid
  `deny` blocks regardless of confidence. `uncertain` or an `allow` below 0.95 remains unresolved and cannot execute
  automatically. The confidence measure is not a calibrated probability of safety. Qualify the provisional policy
  with representative cases and make later rubric/threshold changes explicit operator-controlled revisions.
- Let the human resolve a valid uncertain result through a trusted operator interaction: cancel or approve only
  that exact still-current operation once. Model text/tool output cannot impersonate that interaction. A semantic
  denial requires correcting the operation and reevaluation; it is not a reusable override opportunity.
- Missing/denied Jev access, billing/provider failure, timeout, malformed or incomplete output and budget exhaustion
  stop the operation. Operator approval cannot replace a failed required evaluation; recovery needs explicit
  reevaluation of a still-current operation. There is no automatic retry or duplicate execution.
- Bind each evaluation and human decision to operation identity, arguments, working directory, relevant source,
  policy/rubric/evaluator/configuration revisions and session. Revalidate immediately before release to execution;
  changed inputs, cancellation, reload or replacement session invalidate pending decisions and approvals.
- Provide bounded redacted receipts and visible profile status: permitted, denied, uncertain, evaluator unavailable,
  stale or cancelled are distinct. Do not label presentation-only or deterministic-only sessions as Jev-protected.
- Use the shared disclosure, payload, count, concurrency, timeout and spending controls. No extra provider client,
  unbounded rubric context or raw command/source logging is introduced by this consumer.
- Out of scope: changing deterministic permissions, full shell/process containment, relevance policy or its 0.70
  threshold, autonomous launch, Workflow grants/dispatch, post-result injection screening and deployment/publication.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Screen a permitted effect | Evaluate a deterministically admitted operation | Inspect typed judgment and receipt | Permitted/denied/uncertain observation | Bounded provider call; effect executes only after final admission |
| Resolve valid uncertainty | Explicit scoped human approval or cancellation | Inspect exact proposal, context and reasons | Operator resolution observation | At most one still-current effect may start |
| Recover from evaluator failure | Explicit reevaluation after recovery | Inspect failure, readiness and current proposal | Recovery/evaluation observation | No automatic execution or retry; bounded new evaluation when allowed |
| Cancel or invalidate work | Cancel pending operation on lifecycle/input change | Inspect cancelled/stale result | Cancellation/invalidation observation | Late responses and approvals cannot release obsolete effects |

These observations are not Workflow transitions, permissions or independent acceptance receipts.

## Validation and permissions

Deterministic restrictions and independent runtime permissions remain authoritative. Neither a high-confidence
judgment nor an operator uncertainty decision can override them. Apply current provider disclosure permissions
before dispatch; an operation whose required context cannot be disclosed remains unresolved without sending it.
Treat commands, source and provider results as untrusted data rather than executable instructions.

The operator must see the actual proposed operation and bound scope in the trusted interaction, while persisted
receipts/logs retain redacted metadata by default. No noninteractive session may silently approve an uncertain
operation. Each operator decision is consumed at most once, is invalid after cancellation or changed bindings,
and cannot be inherited by another operation or child session. A timeout or process restart does not prove that
an already-started external effect was undone; never automatically replay it.

Preserve TASK-00160's declared coverage and local trust limitations. Required hook/configuration failure stops
claiming active protection to the extent the runtime can detect it; document the limits of detecting extension
disablement from inside the extension. This TASK does not satisfy TASK-00138 or authorize a broader execution route.

## Acceptance criteria

- [ ] Deterministic denials make no upstream request. Each supported bash/mutating operation that passes those
  checks receives required semantic screening before its effect; ordinary read access remains deterministic.
- [ ] The initial policy admits valid `allow` at 0.95 and above, holds lower-confidence `allow`/`uncertain`, and
  blocks `deny`. Test boundary values and malformed/missing measures without treating confidence as accuracy.
- [ ] A real supported Pi interaction demonstrates semantic denial and valid uncertainty resolution, with exactly
  the bound operation shown to the human. Cancellation or absence of human input retains the block.
- [ ] Provider/billing/access failure, timeout, malformed/partial output, forbidden disclosure and exhausted budget
  prevent execution. Recovery requires explicit reevaluation and cannot silently downgrade protection.
- [ ] Changed arguments, working directory, relevant source, policy or session invalidate prior results/approvals.
  Concurrent replies, repeated operator input and late completions cannot release the same effect twice.
- [ ] Reload/shutdown cancels pending evaluations and resolution prompts; replacement sessions cannot receive stale
  approvals. Supported nested/child routes retain the same boundary and unavailable coverage is explicit.
- [ ] Redacted receipts and profile status distinguish denial, uncertainty and service failure without leaking
  credentials/sensitive source. Live rubric/evaluator qualification is separate from controlled transport tests.
- [ ] Operator guidance covers configuration, threshold meaning, one-operation resolution, recovery and residual
  risks. Installing presentation resources alone never implies protection is active.
