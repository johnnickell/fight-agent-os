# Deliver the permission-controlled user directory

## Outcome

A versioned API and accepted responsive Users route require exact `READ_USERS`, dispatch package `ListUsers`, and present a bounded installation-wide directory containing only canonical identity, lifecycle, authoritative role presentation, timestamps, and permission-appropriate links to the already established invitation operations.

## Scope

- In scope: Bearer-authenticated list route/Action; exact permission authorization; validated bounded pagination and fixed ordering; package `ListUsers` dispatch; exact role-reference resolution and safe role presentation; explicit paginated View/JSend/OpenAPI/cache policy; typed client service; replacement Users landing page; permission-aware invite/status/elevated links through shared evaluator; responsive list/card/table, empty/loading/error/pagination states; PostgreSQL/permission/HTTP/client/accessibility/redaction tests.
- Out of scope: User lifecycle mutation, password/session access, arbitrary/custom-role administration, active-user promotion, email change, raw invitation credentials, cross-user sessions, workspace membership, free-form database sorting/filtering, client-only filtering of partial pages, and duplicating invitation APIs.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| List installation users | N/A — read-only API | `ListUsers` with bounded fixed pagination | N/A — no domain event | Authorized actor receives one deterministic page of explicit safe user Views |
| Resolve role presentation | N/A — Application projection | Resolve every assigned role ID to authoritative name/managed marker | N/A — no domain event | Page reports current assignments without exposing permission internals or enabling edits |
| Navigate invitation operations | N/A — client navigation | Evaluate exact shared permissions and target lifecycle | Client navigation signal | Only permitted Invite/Status/Elevated links render and all resolve to registered routes |
| Reject unauthorized directory | N/A — authorization guard | Resolve request-scoped current principal and exact `READ_USERS` | N/A — no domain event | Sanitized `401`/`403`; package list query is not dispatched |

## Validation and permissions

Declare GET pagination through [TASK-00155](00155-TASK.md)'s source-only `QueryString` plus Validation fields/rules
and consume checked request values without input-only DTOs. Follow [canonical attribute ordering](../tickets/00010-TICKET.md#canonical-action-and-responder-attribute-ordering).
Prove valid/boundary/duplicate/encoded/unknown pagination input and no dispatch on rejection through this real
route. Examples such as `sort`, `order`, filters and `include_deleted` in the shared foundation do not expand
this TASK's fixed ordering, permitted fields or visibility policy.

Require TASK-00044 Bearer authentication and one request-scoped `CurrentPrincipalProvider`. Server authorization checks exact `READ_USERS` through the shared capability before dispatch; the API-v1 attribute is the early gate and Agent OS Application owns the authoritative permission check before calling the package query. Never grant from `ROLE_SUPER_ADMIN`, JWT/HTML claims, route visibility, or submitted actor. Unknown/stale/non-active authority fails closed. The client uses the same exact permission name for presentation only.

Accept only bounded page/per-page values and one fixed allowlisted deterministic ordering with stable tie-break. Do not pass arbitrary column/direction expressions into package persistence. Initial scope supports no misleading client-only filter over one page and no unapproved broad search; document the explicit absence or any later narrowly supported safe field truthfully. Query/body cannot select workspace, authority scope, included relations, actor, role, or hidden fields.

Dispatch package `ListUsers` and map package `UserView` through an Application projection/explicit HTTP View. Resolve every role ID exactly through authoritative role repository/capability; missing/duplicate references fail closed rather than being silently omitted. Return safe role name and managed/custom marker only as needed to describe assignment; do not include permission memberships or imply custom-role editability. Deterministically order/deduplicate role presentation.

Return only stable user ID, canonical email, lifecycle state, safe roles, created/updated timestamps, and pagination metadata. Exclude password hash, authentication/authorization revision, refresh sessions, grants/digests/ciphertext/links, pending secret values, email reservations, audit/delivery/provider internals, repository/entity objects, and derived permission snapshots. Apply no-store/private caching according to accepted API policy.

Replace TASK-00051's truthful Users landing state. A pending user's status link appears only when exact `MANAGE_USER_INVITATIONS`; ordinary invite control only with `INVITE_USERS`; elevated invite control only with both `INVITE_USERS` and `ASSIGN_SUPER_ADMIN`. Complete route metadata enforces each destination independently. No hidden/focusable forbidden controls and no claim that client gating is enforcement.

Recreate accepted responsive semantics for long canonical email, lifecycle/role labels, table/card reflow, pagination, loading/empty/forbidden/system states, keyboard/focus, announcements, target sizes, themes, and reduced motion. Escape all presentation values and avoid color-only state.
