# Deliver trusted ordinary-user console invitations

## Outcome

A trusted console operation accepts a bounded operator identity and canonical email, creates a pending identity through Fight Access Control `InvitePendingUser`, assigns only the managed `ROLE_USER`, records secret-free operator evidence, and enters the normal recoverable invitation-delivery path without displaying or logging grant credentials.

## Scope

- In scope: Application-owned ordinary console-invitation orchestration; trusted console adapter; explicit operator identity/email input; canonical validation; managed `ROLE_USER` resolution; direct package invitation/assignment behavior; coherent transaction/event/delivery sequencing; audit actor distinction; safe output/exit codes; composition; focused unit/PostgreSQL/console/delivery/failure tests; operator documentation.
- Out of scope: Super Admin bootstrap, arbitrary role selection, public/web invitation, activation UI/completion, provider choice, custom roles, administrator passwords, bulk import, retry/resend UI, and cross-workspace authority.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invite ordinary user from console | `bin/console user:invite` dispatches owned `InviteOrdinaryUser`; its handler dispatches `InvitePendingUser` and `AssignRoleToUser` through the configured bus | Resolve canonical email conflict and exact managed `ROLE_USER` | `UserInvited`, `RoleAssignedToUser` as applicable | Pending ordinary identity, grant/delivery state, assignment, audit, and durable delivery work reach one consistent outcome |
| Reject invalid invitation | N/A until input validates | Validate operator/email/policy/current identity | Safe command failure only when dispatched | No identity, grant, assignment, audit success, or delivery work is created |
| Recover delivery | Existing delivery processing commands | Inspect persisted invitation delivery state | Existing package/delivery events | Post-commit delivery is retryable and at-least-once without credential output |

## Validation and permissions

The operation is available only through trusted local console composition and never routed over public HTTP. Require a bounded nonempty operator identity from an explicit option/input and a canonical valid email. Do not infer operator identity from an untrusted environment field without validation. Resolve the stable managed `ROLE_USER` ID from TASK-00036's policy; the command offers no role ID/name/permission option and cannot assign `ROLE_SUPER_ADMIN`.

Reuse package commands, handlers, entities, repositories, events, and delivery contracts directly. Do not copy invitation/grant/assignment policy or insert role rows/assignments directly. Ensure orchestration reaches a coherent accepted outcome: no reported success with an unassigned identity, missing required audit, or unrecoverable delivery state. Failures at invitation, assignment, audit, originating transaction, package claim, or delivery-outcome boundaries must not leave an apparently successful partial workflow; document any package transaction-composition constraint and solve it without external provider work inside a transaction or consumer delivery registration.

Invitation delivery remains post-commit, recoverable, idempotently identified, and honestly at-least-once through established grant/delivery processing. A provider failure does not print or regenerate credentials and is represented by safe persisted delivery state. Console output may contain the canonical email, safe user ID, and status only when justified; never emit password, activation credential/digest/ciphertext, credential-bearing link, cookie/token, provider secret, SQL, or stack trace.

Audit evidence distinguishes the trusted operator actor from the target user with bounded approved context. It must not pretend the invited user authorized the assignment. Local shell access is the trust boundary; no end-user runtime permission is claimed.

## Acceptance criteria

- [ ] Adapter Symfony Console `bin/console user:invite` accepts explicit bounded operator identity and email through injected buses and is absent from public HTTP routes.
- [ ] Email is parsed/canonicalized before dispatch and malformed/oversized input produces a controlled nonzero result without writes.
- [ ] The operation resolves the version-controlled managed `ROLE_USER` and exposes no arbitrary/elevated role selector.
- [ ] Owned orchestration and nested public package invitation/assignment messages traverse configured bus pipelines, without direct handler calls, copied policy or persistence shortcuts; stateless services/handlers/Console commands are shared registrations in the same container.
- [ ] The committed user is pending activation and assigned exactly `ROLE_USER`, with no elevated permission/role.
- [ ] Grant/delivery state uses the normal seven-day activation and recoverable post-commit delivery pipeline.
- [ ] Pending identity, assignment, audit, and required delivery state reach one coherent result; injected orchestration failures cannot be reported as success or leave unowned partial behavior.
- [ ] Duplicate/canonical conflict, missing/drifted policy, stale role reference, repeated invocation, and delivery failure have controlled outcomes.
- [ ] Secret-free audit evidence identifies the trusted operator and target without misrepresenting the invited user as actor.
- [ ] Output, logs, diagnostics, events exposed to operators, and test snapshots contain no raw/ciphertext/digest credential, password, link, token, provider secret, SQL, or stack trace.
- [ ] No public registration, web invitation, Super Admin assignment, provider invocation inside transaction, or administrator-selected password is introduced.
- [ ] Focused unit/PostgreSQL/console/delivery/redaction and filter veto/transformation tests plus `./bin/build` pass with fresh evidence; Symfony errors/verbose modes remain secret-safe and invocation state is isolated.
