# Deliver trusted ordinary-user console invitations

## Outcome

A trusted console operation creates a pending identity through package-owned invitation behavior, then normally assigns managed `ROLE_USER` in an independent package-owned transaction. Truthful partial/uncertain results support correction through trusted `user:role:add` for an existing user and existing non-Super-Admin role, without reinvitation or credential output. Preserve secret-free operator/target audit evidence and package-owned recoverable delivery.

**Current delivery state:** revision 6 implements the approved separate package commits and `user:role:add`, including terminal payload/state policy, inspected partial output and separate membership-confirmation audit. TASK remains **in-progress**, pending fresh independent Review and affected behavioral QA. Canonical REVISE R2/R3/R4 at `70f2768` is repair input, not acceptance of this candidate; QA at `2227c4b` is historical. The alternate-policy diagnostic below is conditional history, not an in-scope capability prerequisite.

## Scope

- In scope: Application-owned invitation sequencing/partial-result policy; trusted Symfony Console adapters; explicit internal acknowledgement/operator attribution; bounded canonical invitation input; managed `ROLE_USER` resolution; independent package invitation/assignment commits; safe state inspection after postcommit exceptions; additive/idempotent existing-role correction by user/role UUID; no-Super-Admin policy before mutation of the actual dispatched payload; honest audit boundaries; shared composition/configured buses; meaningful behavior tests and focused operator docs.
- Out of scope: Super Admin/bootstrap assignment; role selection on invitation; public/web administration; role creation/removal or custom-role administration; registration, activation UI, resend/password actions, provider choice, bulk import, and cross-workspace authority. Assigning an already-existing eligible custom role does not expand TICKET-00031.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invite ordinary user from console | `bin/console user:invite` dispatches owned sequencing; public `InvitePendingUser`, then `AssignRoleToUser`, traverse configured buses | Resolve canonical conflict/exact managed `ROLE_USER`; inspect safe actual state on uncertainty | Normal package success events after each commit | Invitation may commit/start delivery before assignment; assignment failure retains the invitation, with truthful non-success and correction guidance |
| Add an existing eligible role | `bin/console user:role:add --internal --operator=UUID --user=UUID --role=UUID`; public `AssignRoleToUser` through configured pipelines | Public existing-user/role safe queries and authoritative non-Super-Admin policy | `RoleAssignedToUser` only when applicable | Additive/idempotent assignment; preserve existing roles/operator/target; no invitation, grant, delivery, role creation/removal or web effect |
| Reject invalid input or unsafe assignment | No mutation before validation/owned prohibition | Validate operator/target/role and actual filtered payload | Safe rejection | No wrong-target, changed-actor or new elevated assignment; invitation's independently committed first step may already exist |
| Recover delivery | Existing delivery processing commands | Inspect persisted invitation delivery state | Existing package/delivery events | Post-commit delivery is retryable and at-least-once without credential output |

## Validation and permissions

Both operations are available only through trusted local console composition, never public HTTP, with explicit bounded operator attribution. Invitation additionally requires canonical valid email and resolves the stable managed `ROLE_USER` ID from TASK-00036's policy; `user:invite` offers no role ID/name/permission option and cannot assign `ROLE_SUPER_ADMIN`. Do not infer the operator from an untrusted environment field without validation.

Reuse public package commands/queries through configured buses, normal `TransactionalUnitOfWork` and `EventDispatcher`. Remove the consumer participant/deferred origin events when implementing the approved replacement. No outer/nested/joining transaction decorator, direct injected handler call, copied policy, repository audit hook or consumer delivery workaround is permitted; ADR 0001/0002 remain unchanged.

The corrective command requires `--internal`, an explicit bounded operator UUID, and existing target-user/role UUIDs. Reject authoritative Super Admin by stable managed identity and package meaning, including renamed roles/managed-ID aliases/stale state. Preserve package protected-tier/reference rules. Check the actual dispatched payload after relevant filter transformations before mutation; never grant elevated authority or silently change operator/target. A missing supported contract is a stop condition, not authority for an upstream edit or locking workaround.

The owner accepts independently committed invitation and assignment: delivery can begin after invitation commit, and a later failure must not claim rollback. Report known persisted invitation versus missing/uncertain assignment, safe target ID and correction guidance; inspect safe actual state after postcommit exceptions before asserting what committed. Do not blindly reinvite. Non-success also covers missing/uncertain mandatory audit evidence. Any separate postcommit role-audit transaction and crash window must be explicit; do not claim assignment/audit atomicity or silently drop operator/target evidence. Recovery must work in a fresh process after a failed manager without duplicate identity/grant/delivery.

Invitation delivery remains post-commit, recoverable, idempotently identified, and honestly at-least-once through established grant/delivery processing. A provider failure does not print or regenerate credentials and is represented by safe persisted delivery state. Console output may contain the canonical email, safe user ID, and status only when justified; never emit password, activation credential/digest/ciphertext, credential-bearing link, cookie/token, provider secret, SQL, or stack trace.

Audit evidence distinguishes the trusted operator actor from the target user with bounded approved context. It must not pretend the invited user authorized the assignment. Local shell access is the trust boundary; no end-user runtime permission is claimed.
