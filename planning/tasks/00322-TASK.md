# Configure trusted machine-local connections

## Outcome

A user explicitly configures and inspects a machine-local Agent OS connection pinned to the expected
host-assigned installation/origin, without trusting repository content, a hostname or a stored credential handle.

## Scope

- In scope: Bounded local connection create/revise/select/remove and immutable revision facts, expected
  installation/origin verification, environment/release-mode identity, protected-handle references and safe
  local/server inspection through the owning Harness boundary and protected API interactions.
- Out of scope: Secret material access, credential enrollment/issuance, full current-use readiness, database user
  preferences, live-session switching, trusted Skill loader/cache and a second trust or credential registry.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Configure a connection | Explicit local create/revise with expected prior state | Endpoint, expected installation/origin, environment, mode and private handle metadata | Safe attributed local change observations, not fabricated database Domain events | One deliberate machine-local revision, never repository-injected trust |
| Verify identity | Authorized bounded identity inspection | Actual host-assigned installation/origin against configured expectation | N/A for read-only inspection | Match or safe denied/unavailable/mismatch reason |
| Select future connection | Explicit local selection | Exact connection revision and active-session presence | Attributed selection observation | Intended future selection only; active-session changes require owning continuation |
| Remove local connection | Explicit exact local removal | Current revision and linked active/retained state | Safe local removal observation | Local configuration removed without unrelated credential/cache/history deletion |

## Validation and permissions

Separate connection profiles from database-backed user Harness profiles. Bound names, endpoint configuration,
expected installation/origin identities, environment labels, release/development mode and protected credential-store
references. Handles remain private local metadata, never raw keys or ordinary model/browser/session data. A saved
handle proves neither credential delivery nor activation, current Permissions or supported runtime readiness.

Only explicit user/operator configuration establishes the expected first-party installation/origin. Repository
files, transport location, `localhost`, matching names and discovered metadata cannot register or redirect trust.
Validate the authenticated protected server interaction under TASK-00117 and current caller scope. Define the
bounded identity-verification contract within the existing Harness owner, not an unrestricted probe or competing
origin registry; TICKET-00087 must reuse it for Skill trust. Reject origin substitution, unexpected redirects,
unsupported endpoint configuration and mismatched actual identity rather than silently rebinding credentials.

Read/revise local state with expected revisions and safe atomic replacement; uncertain mutations reconcile the
original exact state before retry. Preserve unrelated personal configuration and history. Inspect only declared
endpoints and needed metadata, never scan home directories, dump environments or read keyring contents. Persist
required owned server state/audit atomically under ADR 0002; external identity/package/store effects stay outside
business transactions. Safe errors omit credentials, unnecessary machine paths and arbitrary provider messages.

A local selection changes future intent, not an active session's connection or authority. If a session is active,
require the separately owned linked-continuation path before applying the change; unavailable continuation support
means visible refusal, not in-place mutation. Removing local configuration is not credential revocation, origin
cache cleanup or erasure of retained session evidence. TASK-00324 owns integrated safe disconnection through those
owners. Configuration remains useful before managed readiness but must report that boundary truthfully.

## Acceptance criteria

- [ ] Explicit create/revise/inspect/select/remove handles exact local revisions and safe recovery without
  automatic personal changes or overwriting unrelated connections.
- [ ] Host-assigned installation/origin matches configured expectation through a protected interaction; wrong
  installation, substituted origin, redirect and stale state reject without reusing another installation's authority.
- [ ] Repository content and hostnames cannot establish or redirect trust; only private handle references are
  retained and saved configuration never advertises delivered/activated/usable credentials.
- [ ] Selection/removal cannot mutate active-session identity or erase historical evidence; unsupported active
  continuation is held and integrated credential/cache disconnection remains with its owners.
- [ ] Safe terminal/API diagnostics distinguish configured, unsupported, denied, mismatch, stale and unavailable
  states without secret or unnecessary private-configuration disclosure.

## Verification and evidence

Test owned identity pinning, local expected-state/selection behavior, protected server authorization and important
transport/redaction contracts. Use PostgreSQL concurrency where authoritative server state changes. Qualify actual
endpoint/identity interactions and local configuration recovery directly on explicit disposable targets; do not
product-test configuration text, filesystem wrappers or package-manager internals. Record exact source/runtime,
connection revisions and observed identity safely. Run focused checks and `./bin/build`; label controlled fixtures,
real interactions and unqualified managed-use behavior separately.
