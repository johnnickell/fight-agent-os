# Enforce complete access-token authentication

## Outcome

Application-owned JWT issuance and request authentication enforce the accepted browser-security profile end to end: externally configured signing/rotation, fifteen-minute memory-only Bearer tokens, complete registered/custom claim validation, and request-scoped authoritative user/session/version resolution without roles or permissions in tokens.

## Scope

- In scope: Issuer/consumer adapters around package token ports, verified against package-created active user/session state in integration tests without inventing an HTTP endpoint; pinned algorithm/key identifiers and external keyring configuration; required claim issuance including issuer/audience/JTI; independent signature/algorithm/key/claim/time/type validation; bounded clock skew; strict Bearer extraction; authenticated request context/middleware; authoritative user/session/version/state resolution; generic correlated `401`; redaction; key-overlap tests and production startup guards; OpenAPI security alignment.
- Out of scope: Login/refresh/logout Actions/UI, refresh-cookie and CSRF controls, principal role/permission projection, key-management service deployment, asymmetric migration not selected by ADR, credentials in browser persistence, and package source modification unless a proven contract gap is separately authorized.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Issue access JWT | Package `AuthenticationService` calls `TokenEncoder` | Read external active signing configuration and supplied package claims | Package authentication event remains package-owned | Signed token receives required consumer claims and expires after exactly 15 minutes |
| Authenticate Bearer request | N/A — HTTP authentication middleware | Decode/validate token then resolve user/session authoritative state | N/A — no domain event | Valid request-scoped authentication context is established; invalid input returns safe `401` |
| Rotate verification key | N/A — configuration operation | Resolve `kid` against accepted active/overlap keyring | N/A — no domain event | New tokens use active key; bounded prior-key overlap validates only as configured |
| Reject stale authority | N/A — request validation | Compare subject/session/authentication version/state/expiry to PostgreSQL | N/A — no domain event | Revoked/expired/stale/deactivated authority fails closed despite valid signature |

## Validation and permissions

Follow TASK-00017's explicitly accepted ADR rather than Fight Common `JwtDecoder` signature-only behavior. Pin the allowed algorithm and reject token-selected alternatives/`none`. Validate key ID/rotation policy, signature, `iss`, `aud`, `sub`, `sid`, `jti`, `type`, `iat`, `nbf` where required, `exp`, and `auth_version`, including exact scalar/container/type/format/cardinality rules and bounded clock skew. Unknown/missing/duplicate/malformed claims fail closed.

The encoder may enrich package-supplied claims with consumer-owned issuer/audience/JTI/key metadata but cannot change package-owned subject/session/version/type/issued-at or put roles, permissions, email, password, refresh credential, or private data in the JWT. Access expiry remains exactly fifteen minutes under the accepted clock policy. JTI is unpredictable and unique.

Read signing keys/key IDs/issuer/audience only from external typed configuration. Validate encoding, entropy/length, algorithm compatibility, unique key IDs, one active signer, overlap window, and production requirements at startup. Never commit, log, dump, expose, or place key material in diagnostics/runtime HTML.

Accept exactly one syntactically valid `Authorization: Bearer` credential. Reject query, cookie, form, duplicate/comma-folded, wrong-scheme, whitespace/control-character, and oversized sources. After cryptographic/claim validation, resolve session by `sid` and user by `sub`; require ownership, active lifecycle, usable session, matching authentication version, and claim/session consistency. Do not treat claims as authoritative roles/permissions.

Known authentication failures map to one sanitized correlated `401` without token/claim/decoder/database detail. No user-facing permission is granted here; valid authentication precedes endpoint-specific authorization.

## Acceptance criteria

- [ ] Issuer and consumer implement accepted pinned algorithm/key profile and reject token-selected alternatives or unknown keys.
- [ ] Production startup fails for missing/malformed/weak/incompatible keys, duplicate IDs, invalid issuer/audience, or absent active signer.
- [ ] Issued access JWT includes validated issuer/audience/subject/session/JTI/type/issued/time/expiry/auth-version claims and lasts exactly fifteen minutes.
- [ ] JWT contains no roles, permissions, email, refresh credential, password, or private configuration.
- [ ] Consumer independently validates signature plus every required claim's presence, type, format, value, and accepted clock-skew policy.
- [ ] Bearer extraction accepts exactly one approved header and rejects query/cookie/form/duplicate/folded/wrong-scheme/control/oversized credentials.
- [ ] Request authentication resolves authoritative active user, owned usable session, and matching authentication version before establishing context.
- [ ] Validly signed but revoked/expired/wrong-owner/stale-version/non-active authority fails closed.
- [ ] Active-key issuance and bounded prior-key verification overlap behave exactly as the ADR without indefinite old-key acceptance.
- [ ] Failures return generic correlated `401`; tokens, claims, keys, SQL, stack traces, and decoder details are absent from all diagnostics.
- [ ] OpenAPI Bearer semantics match implemented behavior and do not describe refresh cookies as Bearer tokens.
- [ ] Focused claim/key/Bearer/authoritative-resolution/HTTP/redaction checks and `./bin/build` pass with fresh evidence.
