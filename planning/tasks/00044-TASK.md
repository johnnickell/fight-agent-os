# Enforce complete access-token authentication

## Outcome

Application-owned JWT issuance and request authentication enforce the accepted browser-security profile end to end: externally configured signing/rotation, fifteen-minute memory-only Bearer tokens, complete registered/custom claim validation, and request-scoped authoritative user/session/version resolution without roles or permissions in tokens.

## Scope

- In scope: Issuer/consumer adapters around package token ports, verified against package-created active user/session state in integration tests without inventing an HTTP endpoint; pinned algorithm/key identifiers and external keyring configuration; required claim issuance including issuer/audience/JTI; independent signature/algorithm/key/claim/time/type validation; bounded clock skew; strict Bearer extraction; authenticated request context/middleware; authoritative user/session/version/state resolution; generic correlated `401`; redaction; key-overlap tests and production startup guards; OpenAPI security alignment.
- Out of scope: Login/refresh/logout Actions/UI, refresh-cookie and CSRF controls, principal role/permission projection, key-management service deployment, asymmetric migration not selected by ADR, credentials in browser persistence, and package source modification unless a proven contract gap is separately authorized.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Issue access JWT | Package `AuthenticationService` calls `TokenEncoder` | Read external active signing configuration and supplied package claims | Package authentication event remains package-owned | Signed token receives required consumer claims with integer `exp - iat = 900`; only serialized expiry is normalized downward |
| Authenticate Bearer request | N/A — HTTP authentication middleware | Decode/validate token then resolve user/session authoritative state | N/A — no domain event | Valid request-scoped authentication context is established; invalid input returns safe `401` |
| Rotate verification key | N/A — configuration operation | Resolve `kid` against accepted active/overlap keyring | N/A — no domain event | New tokens use active key; bounded prior-key overlap validates only as configured |
| Reject stale authority | N/A — request validation | Compare subject/session/authentication version/state/expiry to PostgreSQL | N/A — no domain event | Revoked/expired/stale/deactivated authority fails closed despite valid signature |

## Validation and permissions

Follow TASK-00017's explicitly accepted ADR rather than Fight Common `JwtDecoder` signature-only behavior. Pin the allowed algorithm and reject token-selected alternatives/`none`. Validate key ID/rotation policy, signature, `iss`, `aud`, `sub`, `sid`, `jti`, `type`, `iat`, `nbf` where required, `exp`, and `auth_version`, including exact scalar/container/type/format/cardinality rules and bounded clock skew. Unknown/missing/duplicate/malformed claims fail closed.

The encoder may enrich package-supplied claims with consumer-owned issuer/audience/JTI/key metadata but cannot change package-owned subject/session/version/type/integer issued-at or put roles, permissions, email, password, refresh credential, or private data in the JWT. Under the [approved ADR precision clarification](../adr/0003-browser-authentication-security-profile.md#approved-access-expiry-precision-clarification), normalize **only serialized JWT expiry downward** to integer UTC seconds and require `exp = iat + 900`; genuinely inconsistent expiry still fails closed. Package DateTime/TokenSet expiry may retain fractional precision, with matching whole-second timing and JWT expiry less than one second earlier, never later. Preserve precise shared validation/outcome clocks and persisted session/grant/lease/delivery deadlines; no clock flooring or deadline grace. Any emitted whole-second timing metadata must agree with JWT timing. This adds no endpoint or response feature. JTI is unpredictable and unique.

Read signing keys/key IDs/issuer/audience only from external typed configuration. Validate encoding, entropy/length, algorithm compatibility, unique key IDs, one active signer, overlap window, and production requirements at startup. Never commit, log, dump, expose, or place key material in diagnostics/runtime HTML.

Accept exactly one syntactically valid `Authorization: Bearer` credential. Reject query, cookie, form, duplicate/comma-folded, wrong-scheme, whitespace/control-character, and oversized sources. After cryptographic/claim validation, resolve session by `sid` and user by `sub`; require ownership, active lifecycle, usable session, matching authentication version, and claim/session consistency. Do not treat claims as authoritative roles/permissions.

Known authentication failures map to one sanitized correlated `401` without token/claim/decoder/database detail. No user-facing permission is granted here; valid authentication precedes endpoint-specific authorization.

### Implemented boundary

- `AccessJwt` implements the package token ports with pinned HS256, 2048-byte compact tokens, canonical
  base64url, exact protected header and claim sets, duplicate/escaped-duplicate member detection, strict
  package ID factories/types, random 128-bit lowercase-hex JTI, exactly 900 seconds, and 30-second future-only
  tolerance. Package claims are preserved; serialized expiry alone is normalized downward under the approved
  clarification; genuinely inconsistent expiry or caller enrichment is refused.
- External `APP_ACCESS_TOKEN_CONFIG` validates one signer and optionally one previous verifier, strong hex
  material, unique IDs/secrets, HTTPS issuer and bounded audience, and finite `last_issued_at + 900` cutoff.
  It fails boot in every environment, not only production. No fallback to the old request-HMAC secret.
- `AuthenticateAccessToken` reloads PostgreSQL session/user every request and returns package
  `AuthenticationContext` only after ownership, active state, version, session deadlines and issuance consistency
  checks. It rechecks access expiry after store access. No roles, permission projection or shared mutable context.
- `BearerCredential` accepts one exact case-sensitive header, inspects alternative raw/parsed sources and
  preserves the body cursor. Protected request bodies are limited to 16 KiB and seekable streams. Raw
  `HTTP_AUTHORIZATION` is checked when available; deployment ingress must preserve raw values/reject duplicate
  physical headers rather than relying on PSR normalization. `AccessTokenAuthentication` is available for
  protected pipelines; no public read was changed into a protected endpoint and no fake route was registered.
- The existing API failure boundary produces generic correlated no-store `401` without authentication logs,
  claims, token/key material, SQL or exception chains. OpenAPI's reusable `AccessBearer` now describes this
  boundary, not refresh cookies; no protected operation is advertised. Configuration and integration guidance:
  [access tokens](../../docs/engineering/ACCESS_TOKENS.md). CI setup generates private ephemeral keys explicitly.
