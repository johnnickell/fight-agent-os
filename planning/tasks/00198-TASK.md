# Inspect and correct authorized memory in the browser

## Outcome

A signed-in human can use a basic accessible browser journey to inspect its permitted shared and, with
separate private oversight authority, Agent-private memory; distinguish current from historical claims and
review promotion accept/reject lineage; correct or retract only within its own authorized scope; and invoke
exceptional prohibited-content removal through a separately authorized action. Server-side Application
operations enforce every target decision and safely audit private disclosure. This is a complete, bounded
human oversight path, not a general memory dashboard or a new approval authority.

## Scope

- Build on [TASK-00051](00051-TASK.md)'s authenticated application frame, `/me` authority and guarded
  API-v1 Actions under ADR 0003/0004. Give users a scoped entry/history and proposal/publication view with
  ownership, scope, status, attribution, source links and relevant verification/applicability. Explicit
  selected Repository/Workspace/TASK/Workflow IDs are validated targets, not authorization. Use server-
  filtered bounded pagination; do not fetch all private text and hide it only in the client.
- Reuse [TASK-00189](00189-TASK.md)'s qualified shared historical authority,
  [TASK-00186](00186-TASK.md)'s `READ_PRIVATE_AGENT_MEMORIES` plus current target permission and safe
  audited inspection, and [TASK-00191](00191-TASK.md)'s proposal decision/published lineage (transitive
  through TASK-00197). Show accepted/rejected results only where separately permitted, without placing
  rejected drafts in ordinary Agent guidance. A Project Manager's estimation/history access does not imply
  private oversight, and a Team Lead/reviewer title cannot grant another Agent's private reasoning.
- Provide server-owned, separately validated human intents for linked correction, supersession or
  retraction at an actually owned shared target, following the same append-attributed history as Agents.
  A human oversight read alone does not permit rewriting a different author's original text or an Agent's
  private working entry; if no actual human target-write ownership is qualified, keep that control
  unavailable rather than infer authority from an administrator label. Explain current/historical effect
  before confirmation, bound rationale, recheck revision and live Permission when submitting.
- Present a distinct confirmed safety-removal control invoking TASK-00197's guarded removal path and
  showing safe pending/verified/blocked remediation status. Require its own Permission and target scope;
  ordinary correction/retraction is never presented as permanent deletion. No prohibited payload, raw
  source snippet, secret link, provider receipt or removal reason that repeats forbidden text may enter
  notifications, browser URL/history, analytics, diagnostics or audit. Preserve safe owner links only.
- Keep human content in volatile, generation-fenced protected client state. Clear it on logout, identity
  change, stale/revoked `/me`, denied target, removal, tab/context teardown and uncertain mutation;
  late responses cannot repopulate a different principal's private view. Use no browser persistent
  private cache, service worker/offline copy or local authority store. Provide basic loading, empty,
  forbidden, removed/pending, invalid, offline and conflict states; controls are presentation only,
  with server authorization required for each API interaction.
- Out of scope: polished dashboard, broad search/embeddings, general repository-file editor, automated
  approval/publication, routine archival, external provider deletion guarantees or Pi transcript export.

## Validation and permissions

Use a single HTTP Action per operation with validated JSend/snake_case transport and safe error mapping;
Application, not Actions, components, role labels or routes, enforces actor/target authority. Every
protected read and write requires live authenticated User context, effective Permission, target access
and current lifecycle. The UI follows current `/me` for presentation but a stale or spoofed client
permission never authorizes the server. Private inspection remains attributed as an audited operation,
not a mutating CQRS query masquerading as a pure read. An audit Agent's separate audit-TASK requirement
from TASK-00186 is not replaced by this human interface. Read-only history cannot bypass closure or
private boundaries. Disallow secret-bearing URLs, browser persistence, cached responses and error payloads;
on uncertainty invalidate private client data rather than retry a removal or correction implicitly.

## Acceptance criteria

- [ ] A signed-in human with actual scope and Permission can inspect bounded current/shared and retained
  history, source/verification/status and accepted/rejected proposal outcomes; out-of-scope human, peer
  and reviewer paths cannot browse another Agent's private content or hidden titles/snippets.
- [ ] An actually authorized private inspector reads one Agent entry with safe attributed access audit;
  revocation and target change deny later requests and discard stale client results. An audit Agent still
  needs the separately qualified audit-TASK path outside this human journey.
- [ ] A human target owner appends a correction/retraction without overwriting someone else's original
  or editing an Agent's private value merely due to oversight; stale/conflicting/denied writes fail safely.
- [ ] A separately authorized safety operator invokes removal, sees honest verified/pending/blocked status,
  and cannot mistake retraction for deleting forbidden shared history. Stale client results cannot return
  removed content after a different identity, logout or remediation.
- [ ] Basic accessible loading, empty, forbidden, offline and conflict states work without a persisted
  private cache or role-name grant; no live journey is enabled if required safety/authority paths are
  unqualified.
