# Explore the authentication and dashboard design language

## Outcome

The approved `design` workflow produces a sourced, disposable, review-ready candidate for every initial authentication, account-security, dashboard, and Super Admin journey, including a Bootswatch-like specimen, responsive and state evidence, semantic light/dark tokens, Bootstrap mappings, safe copy/interactions, and an implementation handoff without changing production UI.

## Scope

- In scope: Bounded brief; journey/route/state matrix; sourced references and license/provenance record; meaningful structural/interaction alternatives; selected candidate rationale; runnable disposable specimen; login, activation, reset request/completion, dashboard, account/security, password change, active sessions, users, invitation, and invitation-status/recovery views; root/unknown/forbidden/expired states; fake data; narrow/wide captures; system/light/dark behavior; semantic tokens and Bootstrap mappings; accessibility/interaction observations; candidate production handoff.
- Out of scope: Production React/components/assets, backend/API implementation, final design acceptance, fake dashboard capabilities/data, private data, localization/RTL, extra themes, universal WCAG certification, deployment, and promotion of prototype code into production.

## Validation and permissions

Cover Login, Activate Invitation, Request Password Reset, Complete Password Reset, Dashboard, Account/Security, Change Password, Active Sessions, Super Admin Users, Invite User, and Pending Invitation Status/Recovery, plus `/` routing and safe unknown/forbidden/recovery behavior. Include loading, empty, validation, authentication failure, delivery failure, system error, success, expired-link, and expired/revoked-session states where applicable.

Alternatives must differ meaningfully in hierarchy, layout, navigation, density, flow, or interaction. Compare them against approved user tasks and constraints before selecting a candidate. The specimen covers typography, color, spacing, controls, focus/forms, navigation, cards, tables, alerts/status, and logo/asset treatment. Use semantic tokens with explainable Bootstrap mappings rather than scattered literal styling.

Specify `system`, `light`, and `dark`; system defaults and tracks OS changes, explicit overrides alone may persist in `localStorage`, and bootstrap avoids a visible theme flash. The compact selector has an accessible name, keyboard operation, and visible current state. No credential, authority snapshot, or business workflow state may enter persistence, HTML, URL, artifact logs, or captures.

Use deterministic fake/sanitized identities, sessions, delivery statuses, and errors only. Protected/Admin variants show permission-aware visibility but state that server authorization remains authoritative. The dashboard honestly explains unavailable planning/observability capabilities and contains no fake records, charts, metrics, or agent/session data.

Observe WCAG 2.2 AA-oriented contrast, semantics, labels, keyboard operation, visible/unobscured focus, target sizes, reflow/zoom, accessible authentication, reduced motion, and error/recovery behavior. Separate automated results, manual observations, subjective critique, and unverified claims.

All source, dependencies, captures, checks, handoff drafts, process records, and viewers remain under `.runs/prototypes/<scope>/`. Viewers are loopback-only, prototype-scoped, PID/port tracked, and stopped. No runtime permission applies; this TASK authorizes disposable design work and completion evidence, not production changes or final acceptance.
