# Deliver pending-invitation status and recovery

## Outcome

The accepted Pending Invitation route uses TASK-00041/TASK-00042's exact-permission APIs to inspect credential-free authoritative status, retry the same failed delivery generation, confirm replacement resend, or atomically confirm a canonical pending-email correction, then refetches authoritative user/delivery state after every success or safe conflict.

## Scope

- In scope: Protected status/recovery route and complete exact permission metadata; typed existing-API services/runtime decoding; user/status projection composition; delivery/lifecycle/expiry presentation; retry action; resend confirmation; correction form/confirmation; operation-specific pending/success/conflict/throttle/system states; cache invalidation/refetch and stale-response suppression; list integration; responsive production components/Storybook/accessibility; integrated PostgreSQL/HTTP/UI/redaction tests.
- Out of scope: New backend recovery commands/routes, raw grant/link access, active-user email change, provider administration, arbitrary resend/reset, manual database repair, user lifecycle mutation, optimistic delivery claims, exactly-once claims, and broad browser automation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect pending invitation | N/A — client invokes existing API | `FindInvitationDeliveryStatus` and safe user projection | N/A — no domain event | Authorized operator sees canonical pending identity, safe status, and expiry only |
| Retry failed delivery | Existing `RetryInvitationDelivery` API | Resolve latest retryable failed generation | `InvitationDeliveryRetryRequested` | Same generation/idempotency returns to pending delivery; page refetches |
| Resend invitation | Existing `ResendInvitationDelivery` API after confirmation | Resolve latest issued grant and current revisions | `InvitationDeliveryResent` | Predecessor revokes and fresh seven-day generation commits; page refetches |
| Correct pending email | Existing `CorrectPendingInvitation` API after confirmation | Resolve pending user/latest grant/canonical destination claims | `PendingInvitationCorrected` | Email and invitation generation replace atomically; page/list refetch |

## Validation and permissions

Require Bearer authentication and complete route requirement of exact `MANAGE_USER_INVITATIONS`; every existing server Action independently enforces the same permission. Do not require or infer `ROLE_SUPER_ADMIN`; unknown/stale authority fails closed. A validated bounded user ID comes from route, while actor always comes from current principal. Direct route remains usable for a principal with manage permission even if `LIST_USERS` is absent; directory links separately require list access.

Strictly decode TASK-00041 status and TASK-00042 outcomes. Display only canonical email from authorized safe user View, lifecycle, package delivery status, expiry, and bounded durable provider state if already approved by the API. Distinguish invitation grant/delivery handoff, provider attempt, and recipient receipt honestly. Never render or retain raw credential/digest/ciphertext/link, destination history, provider payload/message/key, audit internals, SQL, stack, or package exception.

Enable Retry only for package-defined retryable failed work and explain that it preserves the current invitation/link/generation. Resend requires explicit confirmation that the old link becomes invalid and a new seven-day invitation is created; do not claim delivery. Correction validates canonical email client-side for usability and server-side authoritatively, requires confirmation of old/new safe addresses, and explains that email and invitation generation both replace atomically. Never preserve correction form through navigation/persistence.

Treat server state as authoritative. Disable only the submitted action while pending, reject duplicate accidental activation, and use cache generations so stale responses cannot overwrite newer status/correction. After success, conflict, not-retryable, activated, expired, used, replaced, throttled, email claim, or network recovery, invalidate/refetch status and relevant user-list data according to bounded policy. Do not fabricate optimistic terminal status.

Recreate accepted responsive status/expiry/recovery hierarchy and dialogs/forms with semantic headings/definitions/status, labels/instructions, keyboard/focus/escape/return, announcements, visible focus, target/reflow, themes, reduced motion, long/Unicode email, and explicit safe next steps. Credential-bearing values cannot enter analytics, screenshots, snapshots, error state, URLs, or browser persistence.
