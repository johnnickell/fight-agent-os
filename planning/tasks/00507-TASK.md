# Assess low-friction native-session origin hardening

## Outcome

Deliver a sourced, independently reviewable **go / no-go / needs-upstream** feasibility decision on strengthening
bootstrap/session origin without cumbersome installation or daily operation. This is John's explicitly requested
follow-up to the demonstrated [TASK-00502 R1 limitation](00502-TASK.md#owner-approved-trusted-local-process-amendment--2026-10-21),
not production hardening or a generic infrastructure demonstration. It lets John judge the security/UX trade-off
before authorizing any installation or trust change.

## Scope

- Compare **at most two** plausible approaches against explicit supported platform, installed public API and trust
  assumptions. Qualify **at most one**, the strongest candidate, with a task-owned disposable proof if viable.
- Identify the independent primitive binding genuine native Pi launch/session-file lifetime to bootstrap/key and
  resumed discovery; distinguish it from caller assertions and self-issued signatures. Reuse historical R1 as input,
  but obtain fresh qualification for every new capability or behavior claim. Record tested versions as evidence,
  never Pi version equality gates or future compatibility promises.
- If no candidate is viable, name the concrete missing primitive and stop. Negative feasibility is a valid completed
  investigation, not a reason to fabricate success, add approaches or implement an unapproved architecture.
- Exclude production hardening, rollout, global software/security/trust changes, upstream changes/publication,
  managed execution redesign and removal of the current feature. An elevated helper, global trust/install change
  or upstream integration must remain a proposal pending explicit authority, not an applied experiment.
