# Carry TASK summaries across Workflow attempts

## Outcome

An assigned Team Lead reads permitted lessons from the TASK's earlier Workflow attempts while that TASK
remains active, appends an attributed TASK summary, and a successor Team Lead/Engineer on another authorized
Workflow receives relevant TASK guidance alongside the separately authoritative handoff. Neither role
inherits predecessor private memory or unrestricted predecessor Workflow reads. The path starts with the
first Workflow and survives distinct failed, resumed and successive attempts.

## Scope

- Build on [TASK-00187](00187-TASK.md)'s shared entry, linked correction/retraction, ordered append and
  authenticated MCP/Application operations. TASK memory is a separate scope under a stable TASK identity and
  registered Repository, available from the first Workflow even if initially empty; do not invent a distinct
  Project identity or infer TASK ownership from its string ID or an Agent template.
- Let a currently assigned Team Lead inspect completed Workflows **within its active TASK** to prepare another
  attempt or summarize verified learning, and append its own attributed TASK-scoped entry. Keep original
  Workflow entries, authorship, distinct attempts and their source evidence separate; a TASK summary is a new
  claim, not an approval or a rewritten predecessor entry. Support linked correction/retraction of TASK
  summaries under the same owner and attribution rules as Workflow entries.
- Expose bounded TASK guidance to a later Team Lead and Engineer only through their own current assignment.
  An Engineer sees relevant Phase/Workflow/TASK memory for its current work, not an earlier completed Workflow's
  entries merely because the TASK ID is the same. The later role separately receives mandatory exact handoff,
  criteria, checks and findings from their execution/review owner, not from memory as a replacement.
- On TASK completion, close ordinary Team Lead Workflow/TASK reads; retain entries and associations for
  TASK-00189's separately authorized historical path. Completion or age does not delete, archive or expire
  content; invalidated authority is rechecked for each read/write.
- Out of scope: cross-TASK Repository/Workspace publication (TICKET-00048), Jev lookup (TICKET-00049),
  Project Manager/human/audit historical access (TASK-00189), formal Workflow handoff implementation,
  private session resumption, UI and exceptional safety removal (TICKET-00050).

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Publish TASK learning | Append attributed TASK lesson or linked correction/retraction | Resolve current Team Lead, TASK claim, assignment and evidence | TASK lesson/linked change appended after commit | Durable ordered summary, with source Workflow(s) retained |
| Prepare a later attempt | N/A — read-only | Current Team Lead's permitted completed Workflows within active TASK | N/A — no business mutation | Prior Workflow lessons available only to that TASK's assigned Lead |
| Read successor context | N/A — read-only | Resolve successor assignment, active TASK guidance and mandatory handoff separately | N/A — no change fact | TASK lessons available; predecessor Workflow/private content not inherited |
| Close ordinary execution access | N/A — read-only denial | Recheck TASK/Workflow lifecycle and current actor | N/A — no deletion | Team Lead's normal memory reads end while retained history remains guarded |

## Validation and permissions

Use actual TASK/Workflow claim and phase records from the coordinated execution owner, not memory prose,
worktree names, stale context snapshots or a caller-selected TASK ID as authority. A Team Lead may publish for
the TASK it currently owns, without editing a predecessor's Workflow entry or another author's original
text. Require current direct/effective Permission, current assignment and scope per operation. Cross-repository,
other-TASK, former Engineer, completed-TASK and stale/revoked access fail closed; a previous access receipt
cannot revive a completed Workflow. Bound result size and source references; linked retraction remains
historical, not ordinary guidance or prohibited-content removal. No automatic predecessor Workflow import
into a successor context. Keep PostgreSQL writes, idempotency and ordering under ADR 0002 and the existing
MCP/HMAC caller contract; do not turn a query into a Workflow state transition.

## Acceptance criteria

- [ ] On the first assigned Workflow a Team Lead publishes a TASK summary; an exact retry cannot duplicate it.
  Distinct later attempts retain their Workflow identities and can receive separately attributed TASK learning.
- [ ] A currently assigned Lead sees permitted completed Workflow lessons while the TASK is active and writes
  a linked TASK summary without rewriting the source or another author's original claim. Subsequent correction
  or retraction remains attributed and changes ordinary guidance, not historical original text.
- [ ] A successor's assigned Engineer reads relevant TASK summary and its mandatory handoff through separate
  authorities; predecessor Workflow memory and private notes are not automatically present or readable.
- [ ] An Engineer loses ordinary Workflow access at closure and a Team Lead loses ordinary Workflow/TASK reads
  after TASK completion, even when earlier entry IDs are known; content remains stored for qualified history.
- [ ] Memory remains contextual evidence, never a check result, review verdict, permission or Planning approval;
  live ingestion stays off until TICKET-00050's safety-removal path is available.
