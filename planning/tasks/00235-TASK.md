# Protect Agent credentials with independent encryption and key admission

## Outcome

Supply actual protected Agent credential generation, independent authentication-envelope encryption and exact
issuance-bound delivery encryption/decryption/rewrapping, with versioned key access, durable write-admission
closure and in-flight accounting. No generic plaintext retrieval or human-delivery cipher shortcut is introduced.

## Scope

- In scope: Actual `HmacSharedSecretGenerator`, authentication cipher/decipher and `AgentDeliveryCipher`,
  `AgentDeliveryDecipher`, `AgentDeliveryRewrapper` adapters; protected key selection/enrollment references,
  cryptographic representation, version write/use fences, bounded use accounting and safe failure translation.
- Out of scope: Agent HMAC request verification/activation, package lifecycle duplication, sink transport, general
  key-vault platform, plaintext export, physical key destruction, automatic provider enrollment or production grants.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Protect one holder's issuance | Package-requested random generation and separate authentication/delivery encryption | Current protected key versions and admitted write/use state | N/A — crypto ports do not publish issuance | Protected values only; independent lifetimes and exact delivery associated data |
| Materialize or rewrap original delivery | Package-admitted decipher or fenced rewrap | Original material/version, exact issuance tuple and current source/target key access | N/A — owning package service records outcome | Invocation-lifetime bytes or protected replacement at the requested version, never a public secret |
| Close key-version write admission | Protected operator key-control operation under shared fences | Authoritative references and in-flight users, including authentication envelopes | Attributable key-admission observation, not a destruction receipt | Durable closure prevents new references; existing authorized recovery remains possible |

## Validation and permissions

Use TASK-00234's real protected identity/host boundary and TASK-00227's accepted key-reference lock design. Keys
remain external to source, browser, Pi child, prompts, environment files and ordinary logs; supported secure
transport/loading must not leak them through arguments, process state or debug output. Generate cryptographically
random per-holder credentials, never a shared installation Agent credential. Independently encrypt authentication
envelopes and delivery copies; existing human invitation/reset encryption is not this contract.

Authenticate a versioned associated-data representation covering every `AgentIssuance::toArray()` field before
materialization or rewrap. Rewrap preserves original plaintext, identity/order and policy/history; a target label
change alone is not encryption. Missing/corrupt/swapped data denies with sanitized typed failures. Source-key loss
is distinct from temporary target unavailability. No authentication-envelope fallback may recover a delivery copy.

All new references and key-use admission obey the shared cohort-first protocol. A prepared copy cannot commit
into a version closed after a stale check. Track admitted/in-flight uses and authentication dependencies separately
from delivery-copy counts; close-to-new-writes does not prematurely prevent recovery away from the old version.
Bound key-provider work: rewrap occurs within its owning bounded fenced transaction, while sink invocation does
not. An unbounded/nonparticipating key integration is unsupported, not permission for unfenced rewrap writes.

Concrete sensitive parameters and transaction callbacks require effective redaction with argument capture enabled.
Never chain/log provider exceptions or retain invocation objects. No claim of physical memory erasure in PHP.

## Acceptance criteria

- [ ] Actual independent encryption and authenticated decryption reject changed ciphertext and each swapped
  issuance field; restart preserves original bytes and binding without public output or envelope fallback.
- [ ] Real source/target key outage, denied access, permanent source loss and wrong returned version have distinct
  safe outcomes; only exact authorized target rewrap can be persisted by its owning service.
- [ ] Shared write/use admission and irreversible closure survive restart and race safely with new references,
  rollback and uncertainty. Existing references remain truthfully accountable; no zero-count destruction claim.
- [ ] Key access stays bounded under the package transaction/time contract; unsafe latency or clock state denies
  rather than extending lease/retention or inventing a successful materialization.
- [ ] Actual logging/tracing/debug/exception surfaces with arguments enabled contain no keys, material, handles or
  provider details. Crypto adapter acceptance alone cannot advertise complete Agent operation readiness.
