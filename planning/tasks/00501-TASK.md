# Restore local PHP diagnostics and bound development processes

## Outcome

A developer can diagnose local HTTP startup failures from Docker logs and explicitly attach an IDE debugger,
with predictable PHP/FPM memory and process limits. John authorized this repair and an isolated worktree on
2026-10-20 after an HTTP 500 hid missing authentication-rate configuration.

## Scope

- Shared development PHP settings for CLI HTTP and optional FPM, explicit worker-log forwarding, bounded FPM
  concurrency, and disabled-by-default triggered Xdebug with local operating instructions.
- Reference existing local Docker patterns while qualifying current PHP behavior directly.
- No application key repair in the shared checkout, production deployment, application error-middleware changes,
  APP_DEBUG/Swagger implementation, external observability service or browser capability implementation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Diagnose failed HTTP boot | Existing local startup/log commands | Docker stderr and PHP/FPM effective settings | No business event | Operator-visible errors; generic browser failure |
| Debug local execution | Explicit Xdebug mode and request trigger | IDE protocol and current runtime settings | No business event | Local debugger connection only when selected |
| Serve bounded local HTTPS | Existing FPM foreground command | Worker count, exit and request status | No business event | At most two workers; request and container limits |

## Validation and permissions

Keep logs local, exception arguments omitted and browser error display off. Do not log secrets as verification
fixtures. The human-selected isolated checkout owns its Compose project, disposable database and ports. No
changes to unrelated runtime or dependencies, no automatic key generation in application startup.

## Acceptance criteria

- [x] Actual CLI HTTP startup warnings/fatal errors reach Docker logs without browser traces.
- [x] Actual FPM worker warning/fatal/structured stderr and long records are captured cleanly; shutdown and
  failed startup retain honest process status without an orphan tail process.
- [x] Effective CLI/FPM PHP settings show all-level logging, 512 MiB, UTC, omitted exception arguments, and
  opt-in trigger-based debugging; bounded FPM workers fit the explicit container budget.
- [x] Direct runtime checks, planning checks and the complete `./bin/build` pass; warnings and limits are recorded.

## Verification and evidence

Before repair, the existing CLI image reported `log_errors=0`, an empty `error_log`, `memory_limit=128M`, and
exception arguments enabled. The root HTTP request returned 500 without its startup exception in Docker logs.
Existing FPM already inherits native worker forwarding from the official image; the old external FIFO pattern
is not evidence of a current FPM bug. Validate its explicit profile using real FastCGI requests.

This is container/configuration tooling: use direct PHP/FPM/Docker probes in ignored `.runs/tasks/TASK-00501/`,
not product-suite tests of configuration text or deliberately seeded quality-tool failures. Run the full gate
in the isolated Compose project after explicit dependencies/setup; never reset the shared test database.
