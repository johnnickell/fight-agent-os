# Manage custom role definitions without changing managed roles

## Outcome

Installation operators can create, rename and remove custom role definitions through guarded Agent OS Application services and package commands, while managed roles and existing assignments remain protected.

## Scope

- In scope: `POST /api/v1/roles` (`CREATE_ROLES`), `PATCH /roles/{roleId}` (`UPDATE_ROLES`) and `DELETE /roles/{roleId}` (`DELETE_ROLES`); FQCN Actions; explicit name/ID/revision/confirmation; package `CreateCustomRole`, `RenameCustomRole`, `RemoveCustomRole`; safe outcomes/OpenAPI/audit and client authority invalidation.
- Out of scope: Managed policy change, granting/revoking role permissions, user-role assignment, general role-to-role inheritance, arbitrary permission creation, scoped Workspace/Repository admin.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create role | `CreateCustomRole` through authorized service | Check actor/catalog/name | Package role event and audit | Unique custom role created |
| Rename role | `RenameCustomRole` through authorized service | Check actor/custom target/revision | Package role event and audit | Only custom name changes |
| Remove role | `RemoveCustomRole` through authorized service | Check actor/target/references | Package role event and audit | Only eligible custom role removed, references fenced |

## Validation and permissions

Early attribute and authoritative Agent OS Application checks require exact respective `SUPER_ADMIN_ONLY` permission for HTTP and non-HTTP callers. Never delegate global security authority through custom roles. Package managed-role/assignment/reference invariants remain binding, even if v0.4.0 removes handler permission gates; do not copy verified intrinsic checks into Agent OS. Application owns actor permission/scope and self-admin safety; the package must reject race, stale revision, duplicate/conflicting name and managed targets safely. Reject injected grant fields at transport. Confirm destructive remove, audit without raw secrets or serialized entities.

## Acceptance criteria

- [ ] Each mutation requires only its exact authorized permission and valid custom target; managed roles never mutate.
- [ ] Conflicting, stale, referenced or concurrently changing targets fail atomically and safely; actor cannot be spoofed.
- [ ] Successful package event/audit, no-store JSend/View/OpenAPI and authority refetch reflect actual state.
- [ ] Focused application/HTTP/PostgreSQL/race/security checks and `./bin/build` pass with warnings recorded.

## Verification and evidence

Exercise disjoint permissions, managed/custom/name collisions, references, stale/concurrent removes and actor spoofing. Inspect transaction, audit and safe response; run focused checks, `./bin/planning-check`, `git diff --check`, `./bin/build`; record counts and warnings.
