# Publish the canonical architecture contract and reconcile its callers

## Outcome

Remove the concrete instruction conflict blocking consistent delivery of
[TICKET-00131](../tickets/00131-TICKET.md) and [EPIC-00023](../epics/00023-EPIC.md). Builders and reviewers must reach
one approved architecture contract through normal project instructions, rather than choosing between old ADRs,
current code and a private interview summary. Deliver the shared rules, visible decision amendments and affected
instruction callers together in one coherent documentation PR; do not leave contradictory authorities between
layer-based documentation deliveries.

John approved this single-TASK decomposition, `kind: chore`, no blockers and `order: 1`, explicitly ahead of
currently ready PHP feature work. This priority is authored metadata, not a rewrite of other TASK priorities or a
permission to interrupt active work. No upstream release or completed application refactor is a prerequisite.

## Scope

In scope:

- Make [engineering standards](../../docs/engineering/STANDARDS.md) the shared normative rule owner. Keep decision
  rationale/history in the accepted ADRs and scoped references; link rather than copy the full contract into every
  instruction. Use existing documents, not a parallel architectural manifesto or permanent reconciliation queue.
- Specify `Domain/{BoundedContext}/{Aggregate}` roots, typed IDs, collection-like repository interfaces, owned
  values/nested entities and Command/Query/Event homes; matching Application handlers/cohesive capabilities;
  capability-first adapters; and justification for additional Domain building blocks or package exceptions.
- Specify Project as the business collaboration/publication target, preserving qualified Git repository language,
  source/fork meaning and separate Host/Checkout/Worktree identities. Document the intended naming contract without
  falsely advertising renamed runtime commands, routes or tables that remain unchanged by this TASK.
- Specify registered handler-owned coordination, generic `TransactionalUnitOfWork`, aggregate persistence,
  shared-connection required audit and actual business consistency, and successful event dispatch after commit.
  Repositories do not own transaction completion or unrelated admission/response/recovery orchestration. Qualified
  Doctrine/DBAL implementations are alternatives for real needs, not two transaction authorities or a mandate to
  replace ORM. Keep post-commit uncertainty and actual external-effect guarantees truthful.
- Specify adapter-owned authentication, permission/target-scope admission and bus dispatch at every entry, with a
  trusted internal bus. Remove the normative second blanket Application/bus admission requirement and ordinary
  permission-revocation/commit serialization; preserve Domain/package invariants and justified consistency locks.
- Specify adapter-generated typed creation IDs in void commands and ordinary uniqueness/fresh-query reconciliation.
  Remove ordinary original-response/replay requirements without discarding required audit or separately justified
  filesystem/Git/remote-publication intent, fencing and recovery. Keep physical confirmation and authority separate.
- Specify descriptive injected collaborators, supported inward dependencies including PSR in Application, direct
  canonical Fight contracts without forwarding aliases, safe typed Views, adapter-owned representations and shared
  intentional failures/safe transport handling. Preserve Domain exception ownership, required-absence versus
  optional-discovery meaning, non-disclosure, one reporting owner and protocol-specific metadata/mappings.
- Preserve the actual upstream synchronous non-serializable sensitive-input exception; do not require passwords or
  tokens in messages for superficial uniformity. Distinguish package ownership/availability from desired APIs.
- Specify that Agent OS is an application with deliberate breaking changes allowed at any stage. Update owned
  consumers together and remove superseded paths after verification; no standing application compatibility facade,
  alias, dual mode or deprecation obligation. Needed durable data still requires preservation, migration or explicit
  authorized disposal. Upstream packages retain their own compatibility obligations.
- Visibly amend [ADR 0001](../adr/0001-application-ownership-and-orchestration.md),
  [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md),
  [ADR 0005](../adr/0005-repository-identity-and-link-consistency.md),
  [WF-008](../wayfinder/tickets/WF-008-establish-repository-identity-and-registration-boundaries.md), and the binding
  [identity/linking technical note](../../docs/engineering/REPOSITORY_LINK_CONSISTENCY_PROPOSAL.md) where they conflict.
  Make the amended current requirements explicit; a vague global disclaimer is insufficient. Preserve historical
  approvals, exact historical receipts and non-conflicting business/security/physical-recovery requirements.
- Reconcile [ARCHITECTURE](../../ARCHITECTURE.md), [ownership guidance](../../docs/engineering/OWNERSHIP.md), root
  [AGENTS](../../AGENTS.md), affected local skills and linked architecture/quality references. Inspect actual
  instruction callers, change genuine drift and justify unchanged callers rather than rewriting every skill.
  Keep triggers, completion, uncertainty and the next permitted action consistent with the shared authority.
- Keep approved target, implemented behavior and unqualified/unavailable upstream capabilities distinguishable.
  Capability runbooks may link the new target, but their live instructions must remain executable against current
  source until the owning source TASK updates them. Preserve unrelated product and delivery policies.

Out of scope:

- PHP, frontend, configuration, executable architecture/dependency-rule or runtime changes; package updates;
  schema/data mutation; new permissions, endpoints or grants; vendor/sibling changes or releases.
- Rewriting unfinished individual product plans: [TICKET-00132](../tickets/00132-TICKET.md) owns the full portfolio.
  This TASK amends governing authorities and their instruction callers, not every product record that cites them.
- Completing the code correction, contract qualification or feature delivery owned by
  [TICKET-00133](../tickets/00133-TICKET.md) through [TICKET-00136](../tickets/00136-TICKET.md).
- New policy beyond the approved EPIC, deleting historical decisions, speculative architecture enforcement,
  product tests of instructions, broad Pi/frontend restructuring, or a permanent duplicate coverage checklist.
