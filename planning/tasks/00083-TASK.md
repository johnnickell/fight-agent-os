# Record narrowing context choices

## Outcome

An authorized interactive caller can inspect recognized structured context conflicts and bind one immutable session-local choice to an exact Repository context snapshot while every accepted choice preserves or narrows authority; authorized future defaults are saved only through a new Repository configuration revision.

## Scope

- In scope: Safe recognized-conflict preview; structured source/provenance comparison and recommended narrowing choice; closed choice types; short-lived confirmation bound to actor/snapshot/configuration/instruction/Git observations; immutable context-binding identity and state; `RecordSessionContextChoice`/`SessionContextChoiceRecorded`; bound snapshot/result query; save-for-future handoff through `ReviseRepositoryConfiguration`; PostgreSQL persistence/concurrency/audit; separate view/session-choice/configuration permissions; versioned API/OpenAPI; later Harness-consumable binding contract without a conversation implementation.
- Out of scope: Browser wizard UI, arbitrary prose conflict resolution, rewriting instruction files, full Pi/Harness session persistence, model invocation, widening application Permissions, silent default choices, automatic configuration updates, context drift enforcement, Planning cutover and Workflow/Runner execution.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview a recognized conflict | N/A — read-only interaction | Compare structured sources in one exact unresolved snapshot | N/A — preview emits no Domain event | User sees safe source/provenance, allowed choices, recommendation and authority effect without persistence |
| Choose for one session | `RecordSessionContextChoice` | Revalidate actor, snapshot, observations, revisions and choice | `SessionContextChoiceRecorded` | One immutable binding preserves/narrows the selected snapshot for a later session; configuration/files remain unchanged |
| Inspect a bound choice | N/A — read-only interaction | Get context binding and resulting safe snapshot/projection | N/A — reads emit no Domain event | Authorized caller sees exact lineage, choice, result and unresolved blockers |
| Save a choice for future sessions | `ReviseRepositoryConfiguration` | Preview the equivalent typed configuration revision | `RepositoryConfigurationRevised` | A separately authorized new configuration revision is appended; no instruction file or existing binding changes |

## Validation and permissions

Only conflicts explicitly recognized by TASK-00082 are eligible. Use a closed choice model tied to the exact structured field and listed sources; never accept free-form replacement policy, arbitrary JSON, instruction text or client-computed authority. Compatible prose is not a conflict. Missing or unsupported choice types fail safely.

Bind confirmation and command to authenticated actor, Workspace/Repository, exact snapshot identity/schema/token, current Repository/configuration/designation revisions, instruction paths/digests, relevant Git observations, proposed choice, authority effect and short expiry. Preview is advisory; command revalidates every current fact and permission. Any changed observation, resolved/added conflict, stale revision, lifecycle/availability change, expiry or actor mismatch refuses without a binding.

Define authority comparison for each recognized field. A session choice may preserve an existing effective value or select a demonstrably stricter/narrower allowed value. It cannot weaken application safety, add Permission, enter database Planning mode, broaden branch patterns, remove mandatory verification, increase access, conceal an unresolved conflict or infer authority from local prose. If narrowing cannot be proven structurally, refuse and require a separately authorized configuration revision or human planning decision.

Persist an immutable binding/result that references the exact original snapshot and contains the selected structured choice, safe rationale/provenance, actor/time and resulting snapshot/projection identity. Do not mutate the original snapshot. This is a context-binding contract for later Harness sessions, not a general conversation/session aggregate. Do not create model requests, transcripts, Pi files or Workflow authority.

Require separate permission to view conflicts/bindings and to record a session choice. Saving for future sessions requires TASK-00081's configuration-management permission and command, expected revision, reason and validation; `RecordSessionContextChoice` cannot persist a default indirectly. Existing sessions/bindings never change after a future revision.

Use one PostgreSQL transaction for binding/result, event effect and audit evidence; enforce one accepted result per command/idempotency identity and expected snapshot subject under competing requests. Safe Views/API omit instruction contents, credentials, service URLs, unnecessary paths/IDs and unauthorized bindings.

## Acceptance criteria

- [ ] Preview operates only on recognized structured conflicts in one exact unresolved snapshot and persists nothing.
- [ ] Allowed choices and recommended option show safe provenance and authority impact without arbitrary prose or client-computed policy.
- [ ] Confirmation binds actor, Repository, exact snapshot/configuration/instruction/Git facts, choice/effect and expiry; changed facts fail stale.
- [ ] Every accepted session choice is structurally proven to preserve or narrow authority; widening, hidden-conflict and unsupported choices fail closed.
- [ ] Original snapshot remains immutable; accepted binding records exact lineage, attribution, choice and resulting immutable snapshot/projection.
- [ ] Binding creates no conversation, model call, Pi file, Planning transition, Workflow authority or automatic configuration update.
- [ ] Save-for-future invokes a separately authorized validated `ReviseRepositoryConfiguration` and appends a revision without changing existing bindings/files.
- [ ] View, session-choice and configuration-management permissions remain distinct and authoritative server-side.
- [ ] Competing/retried/stale commands yield one idempotent result or safe conflict with no partial event/audit state.
- [ ] Focused Domain/Application/PostgreSQL/concurrency/API/redaction tests and the canonical build pass with fresh evidence.
