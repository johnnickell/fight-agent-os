# Establish and prove independent implementation review

## Outcome

The repository has a concise project-local `review` skill and shared review standards that independently challenge implementation claims against approved scope, the actual diff, tests, architecture, security, and fresh evidence. A bounded adversarial demonstration proves that the workflow reports a seeded defect or unsupported claim without repairing or landing the work.

## Scope

- In scope: Add `.pi/skills/review/SKILL.md`; add or refine concise shared review standards; define intake, independence disclosure, baseline selection, diff inspection, adversarial verification, finding classification, evidence provenance, and verdict behavior; review the completed TASK-00002 implementation before `work` is trusted for production application changes; demonstrate detection of at least one seeded defect or unsupported acceptance claim; record honest proof and limitations.
- Out of scope: Implementing or repairing reviewed work, design critique, planning decomposition/finalization, landing, push, PR approval, merge, deployment, release certification, and presenting self-review as independent evidence.

## Validation and permissions

Stop or qualify the verdict when approved scope, target, baseline, claimed evidence, local state, or reviewer independence is ambiguous. Each actionable finding identifies severity, evidence, affected requirement, and required correction; subjective preferences remain explicitly non-blocking unless tied to an approved requirement. Review scope covers unauthorized changes, Domain/Application/Adapter and CQRS boundaries, Action–Domain–Responder behavior where applicable, dependency direction, authorization, sensitive data, regression coverage, warnings, evidence provenance, and truthful planning status.

The reviewer may run focused checks and the canonical gate when required, but must distinguish fresh output from inherited receipts and disclose skipped, unavailable, or inconclusive verification. Preserve unrelated local work and perform no write operation except explicitly authorized review evidence under ignored `.runs/` paths.

No application permission model applies. Review authority permits read-only inspection, fresh verification, and reporting for the authorized branch or PR. It does not permit implementation fixes, planning finalization, status completion, landing, push, merge, deployment, release certification, or approval of the reviewer’s own implementation.
