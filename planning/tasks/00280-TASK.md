# Request an own-address change through the account journey

## Outcome

An active owner deliberately requests a different canonical email through the real Account/Security form and
protected package-backed operation. The old address remains active until mailbox confirmation; request success
means an accepted change with durable notice/credential work, not mail receipt or completed address promotion.

## Scope

- In scope: Self-service request form, validation/confirmation, trusted actor/target dispatch, supported atomic
  request-notice integration, new-mail delivery readiness gate, scoped status and honest acknowledgement recovery.
- Out of scope: Cross-user UI, cancellation implementation, confirmation landing/submit, password reset, direct
  address edit, second credential queue, public resend/worker endpoints or automatic mutation replay.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Request own change | Package `RequestEmailChange` through the qualified notice/authority boundary | Current active principal, canonical address, reservation and qualified delivery readiness | Package request fact plus TASK-00274's committed notice/audit facts | One accepted reservation and one-hour encrypted confirmation grant; active email unchanged |
| Reject conflict or lost authority | Same owning operation after validated transport and current policy | Current package reservation/identity and TASK-00278 checks | No success fact for rejected transition | Safe conflict/denial without overwriting pending work or partial notice/grant state |
| Resolve uncertain acknowledgement | Supported read of the original accepted transition and TASK-00279 status | Exact original result where established, otherwise explicit uncertainty | N/A for observation | No automatic new request, secret disclosure or false delivery success |
