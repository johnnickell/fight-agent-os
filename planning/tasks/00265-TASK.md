# Operate withdrawable Pending start through existing entry paths

## Outcome

Integrate actual Team selection and a durable, visible, withdrawable human-selected Pending start intent into the
existing terminal/Triage/browser Workflow path. Reconsider only that TASK within valid bounded consent and use
one authoritative start. Pending intent, confirmed claim/queued Runner and actual Agent work remain distinct.

## Scope

- In scope: Team-specific extension of existing Execution intent/start/inspection/withdrawal ownership and
  TASK-00204/00205's terminal/browser interactions, durable bounded pending intent, current selection/consent,
  honest status, race/restart recovery and accessible real selected-TASK intake evidence.
- Out of scope: Second work queue/starter/scheduler, autonomous TASK selection, client eligibility or generic
  status mutation, replacement Triage/classifier/route/claim/Runner, extra normal-route prompt, hotfix confirmation,
  PR merge, release, deployment or full eight-role completion.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Request selected work | Existing selected-TASK start interaction records bounded intent or invokes TASK-00263 admission | Current TASK/route, exact consent, Team recommendation and actual eligibility | Existing owning pending or admitted facts only for durable effects | One human-selected intent; a hold creates no TASK claim or Runner dispatch |
| Reconsider pending intent | Existing owner retries only within its valid bounded intent | Fresh TASK/parent/context/base, authority, roster/capacity and original outcome | Accepted start only on actual commit, otherwise truthful pending/Needs Human | One atomic start through the existing owner or no new effect |
| Withdraw owned pending intent | Existing owner withdraws the exact still-pending intent | Current actor/intent/state and original start outcome | Durable withdrawn fact only if withdrawal wins | Stops pending start only; does not cancel an already claimed Workflow |
| Inspect terminal/browser progress | N/A — read-only | Authoritative intent, Workflow/claim, Runner and process observations | N/A | Separate pending, queued/preparing, working, held/uncertain and withdrawn states |

## Validation and permissions

Reuse TASK-00204's selected-TASK Triage/normal-route path and TASK-00205's pointer/keyboard start interaction.
Triage may recommend Team/Lead using TASK-00262 but cannot choose another TASK, claim it, infer hotfix authority or
issue grants. Preserve the existing normal-route consent model: no routine second confirmation just to break a
fair equivalent tie. Explicit hotfix/changed-scope consent stays with its existing owner. The core selector/start
continues to support the pre-cutover Markdown path; the browser/Triage consumers retain their actual database
Planning prerequisites without imposing them on manual Explorer use or earlier terminal primitives.

Persist pending identity, exact original request binding, selected TASK/actor/scope/revisions, permitted Team
alternatives, explicit limits/deadline and original-outcome correlation within existing Execution ownership.
A pending intent is not a Workflow start, exclusive TASK claim, Agent reservation, queued Runner or persisted
Planning In Progress status. Do not duplicate the canonical queue, create another credential/claim store or infer
progress from a drag animation. Reading status is not a trigger granting execution.

Use a finite server-enforced intent lifetime no later than its originating authority, with bounded owning retry/
reconsideration and no renewal through reads, repeated gestures or process restart. Document and qualify the
supported owning trigger and bounds; no unbounded polling or separate automatic starter. Each reconsideration
rechecks live scope, TASK/parent/dependencies, configured base inclusion, current grants/credentials, roster,
capacity and exclusive claim before TASK-00263's single admission. Preserve exact original intent under duplicate
delivery. Changed scope, expired/revoked consent or uncertain earlier effects holds for human decision or original-
outcome reconciliation; a fresh command ID cannot bypass it. No automatic browser mutation replay on 401/reload.

Serialize withdrawal against admission on the actual owning intent/claim boundary. If withdrawal commits first,
no later stale trigger may start work. If start commits first, return its authoritative Workflow/claimed state;
withdrawal cannot report success or silently cancel running work. Actual cancellation remains the separate owning
Workflow operation with current authorization and quiescence rules. Unknown winner is unresolved, not withdrawn.
No sandbox/provider effect runs inside the admission/withdrawal database transaction.

Use the existing authenticated frame and ADR 0003/0004's single current-principal and request-generation fences.
Current server permissions/ownership protect every terminal, API and direct path; UI visibility grants nothing.
Keep browser business input volatile, clear protected stale responses and never store pending truth or confirmations
in local/session storage, URLs, history or base HTML. Durable server intent survives caller loss and is inspectable
only under current authority. Safe output/captures exclude grants, credentials, claim/lease/holder internals,
private tool/session contents and hidden TASK/member details.

Show safe hold reasons and next actions with text, labels, focus and announcements, not color/motion alone.
Keyboard and pointer use the same operation as terminal. A known refusal or uncertainty refetches authoritative
placement; it never fabricates In Progress or rewrites Board priority. Preserve current original-operation state
through reconnect/refresh and retire late responses after auth/context changes.

## Acceptance criteria

- [ ] A real authorized selected TASK consumes current Team selection through existing terminal and browser
  paths; no capacity/unverified prerequisite yields visible durable Pending start without a claim or dispatch.
- [ ] Valid bounded reconsideration revalidates all current facts and starts at most once; changed/expired consent,
  unknown liveness, base drift, revoked authority and uncertain earlier outcome never cause hidden new work.
- [ ] Withdrawal versus admission in both winner orders, duplicate triggers and restart preserve the original
  result; withdrawal of pending intent never reports cancellation of an already-started Workflow.
- [ ] Real observations distinguish pending, claimed/queued, preparing and actually working; no gesture, Triage
  recommendation, stored row or historical receipt is accepted as launch evidence.
- [ ] Keyboard/pointer/terminal outcomes agree; accessible safe states cover stale/denied/unavailable/disconnect/
  uncertainty and late responses without client grants, persistent drafts, automatic replay or priority changes.
