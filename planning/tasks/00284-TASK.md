# Enroll one shared real mail transport

## Outcome

Implement and qualify one approved real provider through the existing mail capability for both credential mail
and secret-free notices. Protected credentials, sender/mailbox scope, bounded invocation and truthful provider
outcomes become a reusable primitive rather than duplicate providers in the two email-change pipelines.

## Scope

- In scope: Selected real provider adapter, protected runtime configuration, approved sender/recipient test scope,
  failure classification, original-identity idempotency/reconciliation limits and actual mailbox observations.
- Out of scope: New mail abstraction/queue, credential claims/backoff, notice retry policy, arbitrary public send
  controls, completed notice/credential journeys, scheduler enrollment or automatic production rollout.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Send an approved message | Existing shared mail capability with fixed owning content and stable identity | Current authorized provider/sender/target configuration | Owning caller records its own outcome | One bounded external provider attempt outside every business transaction |
| Observe or reconcile original acceptance | Supported provider operation, if qualified | Same original identity and safe provider evidence | No fabricated delivery/business event | Typed accepted/retryable/permanent/unknown result within actual provider guarantees |
| Reject unsafe enrollment | N/A — protected configuration/preflight | Exact provider endpoint, credentials, scope and policy | N/A | Fail closed without fallback to null/catcher or unintended recipient |

## Validation and permissions

**Needs info:** provider/vendor, account, sender identity, permitted mailbox targets, environment and external-
effect authority remain unselected. Obtain explicit owner selection and bounded enrollment permission before
network changes or sends. Inspect primary provider contracts and record relevant SDK/API version and configured
scope. Do not infer production authority from local Compose credentials, `--internal`, a browser Permission or a
completed TASK-00040 catcher integration.

Reuse TASK-00040's generic mail capability and deterministic content conventions. Add only the actual provider
adapter/configuration needed for these consumers. Keep provider secrets in approved external secret storage;
restrict runtime OS/service/provider identities, sender scope and egress. Validate exact TLS endpoint and safe
timeouts without arbitrary caller-controlled hosts/headers or recipient overrides. Do not persist a consumer
mail queue or plaintext payload to retry independently of the owning notice/package lifecycle.

Qualify provider data handling for credential-bearing messages: disable tracking/link rewriting and unsafe SDK
body/error logging, minimize retention where supported, and disclose unavoidable provider/mailbox retention.
Bodies, personal addresses, credential URLs, authorization headers and arbitrary provider messages never enter
ordinary logs, exceptions, metrics, audit or retained test evidence. No console emits raw mail or grant material.

A provider acceptance is not verified mailbox receipt. Define precise safe result mapping from the supported
provider contract; timeout/lost acknowledgement is not certainly unsent or delivered. Do not invent success or
permanent recipient failure from an unavailable provider. Preserve immutable owning identities on retries;
qualify idempotency namespace, retention, payload-equality requirements and duplicate behavior. A Message-ID alone
is not an idempotency guarantee. Transport/SDK retries must be disabled or explicitly bounded and accounted for;
they cannot become a second lifecycle or multiply invisible attempts. No exactly-once claim is permitted.

Enrolling the transport does not enroll schedules, enable request routes or authorize all existing invitation/reset
senders. Record exact affected capabilities and their separate operational permissions. TASK-00277 retains
notice-specific readiness; TASK-00287 retains actual credential recovery operation and recipient proof.

## Acceptance criteria

- [ ] The approved provider actually sends through the existing capability to authorized controlled mailboxes;
  safe evidence distinguishes provider acceptance from observed receipt and labels scope/retention limits.
- [ ] Missing/invalid authority, endpoint, credentials or sender scope fails closed; no production null/catcher
  fallback, arbitrary send path or duplicate transport/queue is introduced.
- [ ] Rejection, rate limit, timeout, lost acknowledgement and repeated original identity have bounded truthful
  outcomes, documented idempotency limits and no credential/body/provider-secret leakage.
- [ ] Both notice and credential consumers can reuse the transport without sharing their lifecycle authority,
  and provider configuration does not silently enable unrelated effects.
