# Deliver recoverable secret-safe invitation email

## Outcome

Fight Access Control invitation delivery registers an allowlisted invitation-mail intent in the established durable-effect pipeline, later materializes a canonical HTTPS activation link only for provider invocation, delivers deterministic text/HTML mail to a loopback development catcher, and fails closed in production when no real provider is configured.

## Scope

- In scope: Production `InvitationDeliveryInvoker` integration; allowlisted durable invitation intent schema/mapper/handler; protected credential payload handling and decryption-at-invocation boundary; stable idempotency; canonical activation URL builder; deterministic text/HTML template; security/privacy headers/content conventions; generic mail capability mapping; development mail-catcher service/config/wrappers; production provider absence guard; delivery/retry/crash/redaction/no-network tests; operator/developer documentation.
- Out of scope: Selecting/enrolling a production mail vendor, invitation HTTP/admin UI, public activation form, generic template engine, arbitrary persisted templates/endpoints/callables, analytics/tracking, scheduler enrollment, and another outbox/queue.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Register invitation delivery | `DeliverUserInvitation` invokes package port | Read bounded `ActivationDelivery` work | Package delivery outcomes remain package-owned | Existing durable-effect store receives one allowlisted idempotent invitation intent; no provider call occurs in business transaction |
| Process invitation intent | Existing durable-effect runner | Resolve allowlisted schema, protected credential, destination, canonical base URL, and template | N/A — provider result updates durable effect | Credential is decrypted transiently, mail capability invoked, and typed outcome persisted |
| Inspect development mail | N/A — development tool | Read catcher mailbox through loopback UI/API | N/A — no domain event | Developer can retrieve intended invitation mail without console credential output |
| Reject unsafe composition | N/A — startup/composition | Validate key/base URL/provider/catcher mode | N/A — no domain event | Production-like boot fails when required secure delivery capability/configuration is absent |

## Validation and permissions

Implement the package `InvitationDeliveryInvoker` directly and map to TASK-00016/TASK-00023's existing durable intent; do not add an invitation outbox. Persist only the allowlisted versioned fields needed for this effect, with stable idempotency identity derived from the delivery generation. Persisted values cannot resolve arbitrary services, classes, templates, endpoints, or callables.

Credential material remains encrypted/protected at rest and is decrypted only in the worker invocation lifetime. Do not retain plaintext in intent status, retries, logs, exceptions, audit evidence, mail-adapter test records, dumps, metrics, or snapshots. Zeroization cannot be guaranteed by PHP; record that limitation honestly and minimize references/lifetime.

Build activation URLs from explicitly configured canonical HTTPS origin/path, never request `Host`, forwarded headers, or user input. Prefer a fragment carrying credential material so it is not sent in the HTTP request line/referrer; include only necessary safe identity routing data. Validate origin/path at startup and prohibit userinfo, non-HTTPS outside explicit test/development, and ambiguous host forms.

Templates are fixed/versioned, escape interpolated values, include expiry/recovery guidance, and have deterministic text and HTML alternatives. No remote images/fonts/scripts, tracking pixels, analytics parameters, or unnecessary private data. Development mail catcher binds to loopback or private development network only, uses disposable storage, and is never a production fallback. Its mailbox intentionally contains test activation links; scope/access/cleanup must be explicit.

Provider call occurs only after originating commit through the accepted claim/invoke/outcome phases. Preserve at-least-once semantics and stable idempotency. No end-user permission applies to internal registered intent processing.
