# Create and revise implementation TASK artifacts

## Outcome

Authorized planners can create, inspect and semantically revise event-sourced implementation TASKs with immutable Project-local references, valid optional TICKET parentage, explicit standalone bug/chore semantics and delivery evidence that never conflates implementation acceptance with review, publication or merge.

## Scope

- In scope: Separate `Task` aggregate/stream; adapter-generated typed COMB ID in void commands and immutable Project-local TASK reference allocator; active Project ownership; optional same-Project requirement TICKET parent; closed feature/bug/chore kind and standalone rules; accepted machine status representation; title/outcome/scope/contracts/validation/verification/coordination/completion sections; typed verification requirements and delivery-link/reference metadata; semantic create/section/delivery-link commands/events; expected versions/required audit; transactional parent/reference/current projections; Project/TICKET hierarchy/detail/history Views; view/create/revise/delivery-link Permissions; PostgreSQL/concurrency; versioned API/OpenAPI.
- Out of scope: Generic documents, reparenting, dependency edges, priority/order and executable queue, claims, criteria/evidence satisfaction, lifecycle completion/Won't Fix, review workflow, PR publication/merge control, GitHub synchronization, Markdown import, browser UI and execution attempts.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create a parented TASK | `CreateTask` | Preview active Project/TICKET, kind, reference and initial status/content | `TaskCreated` | One stream, immutable reference, parent/allocator/current constraints commit atomically |
| Create standalone work | `CreateTask` with no TICKET | Validate explicit bug/chore kind and reason | `TaskCreated` | Valid standalone bug/chore is Project-owned without inventing a TICKET; standalone feature is rejected |
| Revise TASK intent | Section-specific revise commands | Compare normalized section and expected stream version | Type-specific semantic revision event | Complete changed value appends without generic replacement or changing parent/status implicitly |
| Link delivery observations | Explicit add/supersede delivery-link command | Validate typed branch/commit/review/PR/merge/artifact observation and provenance | Type-specific delivery-link event | Multiple attempts and superseded links remain; no observed provider state changes TASK status |
| Inspect TASK history | N/A — read-only interaction | Get hierarchy/detail/version/history and delivery attempts | N/A — reads emit no Domain event | Safe rebuildable Views explain work and delivery evidence without becoming authority |

## Validation and permissions

Use a dedicated Task aggregate and semantic commands/events, not an EPIC/TICKET parameterization or generic Planning artifact. Allocate immutable TASK references atomically per Project and never reuse them. A parented TASK has exactly one active same-Project TICKET. A TASK with no TICKET must be explicitly `bug` or `chore` with standalone rationale; standalone feature and arbitrary missing-parent cases fail.

Use closed typed fields for kind, parent, initial status, verification requirements and delivery-link classes. Narrative sections are bounded complete Markdown-capable values. Section revisions neither change parent nor status. Initial status must be an accepted lifecycle value valid for creation/import boundaries; no generic status setter is exposed. TASK order/priority is intentionally deferred to TICKET-00027.

Delivery links record typed observation identity, locator/reference, actor/source/time and supersession. Git branch names/provider IDs are discovery/relationship evidence, never TASK identity or authority. Preserve multiple branches, commits, reviews and PR attempts. Do not infer Done, acceptance, publication, merge, release or deployment from GitHub/provider state. No external provider call occurs in the transaction.

Entries admit caller, operation Permission and Project/parent scope before configured bus dispatch. The entry
adapter generates the typed Task ID with its owning factory into the void create command; the aggregate accepts
it. Lost acknowledgement uses fresh authorized list/detail/history and uniqueness conflicts, not original-result
replay. Registered handlers own aggregate/repository/required audit coordination through generic UoW on the exact
shared connection. Stream append, allocator/parent constraints, audit and current projection commit together;
success events dispatch after commit. Stale expected-state commands expose safe intervening facts without merge.
Unrelated TASK edits do not conflict through a Project-global version.

Require separate view/create/revise/delivery-link Permissions admitted for Project and parent. HTTP Actions dispatch one command/query; Responders serialize explicit safe Views; transport/API omits hidden parent existence, credentials, provider tokens, unsafe URLs, arbitrary metadata and persistence details.

## Acceptance criteria

- [ ] Task is a separate event-sourced root with COMB identity, immutable Project-local reference and semantic history.
- [ ] Parented TASKs require an active same-Project TICKET; only explicitly reasoned bug/chore TASKs may be standalone.
- [ ] Closed typed and bounded narrative content replays exactly; revisions cannot smuggle parent/status/dependency/priority changes.
- [ ] Void creation carries the adapter-generated ID; lost response uses fresh authorized state and uniqueness,
      not replayed original TASK results. Stale expected state fails without append or projection drift.
- [ ] Stream append, reference allocation, parent/standalone constraints, required audit and current projection commit or roll back together.
- [ ] Typed delivery observations retain multiple/superseded attempts and never infer lifecycle, review, publication, merge, release or deployment state.
- [ ] Unrelated TASK edits proceed without a Project-global lock/version.
- [ ] Detail/hierarchy/history/delivery Views are rebuildable, non-authoritative and permission-scoped.
- [ ] APIs expose no generic document/status path or provider credential/unsafe metadata.
- [ ] Focused Domain/Application/PostgreSQL/concurrency/API tests and the canonical build pass.
