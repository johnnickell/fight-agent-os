### Required capabilities and ownership

- **Permission tiers and managed authority:** Every Permission has a non-null known tier; custom Permissions start `ADMIN_SAFE`. Only the exact-name managed `ROLE_SUPER_ADMIN` may hold `SUPER_ADMIN_ONLY` Permissions, and their authority reaches human Users through that Role, never custom Roles or direct Agent grants. Reserved Role naming, managed reclassification, intrinsic references and managed membership remain package-owned invariants. Agent OS classifies installation-wide security Permissions correctly; the package cannot infer that a misclassified `ADMIN_SAFE` Permission should be protected.
- **Authorization boundaries:** Agent OS owns one current actor/permission/scope decision for every exposed HTTP, console, worker or future Agent entry path. An HTTP attribute is only an early gate. Inspect actual changes to actor-only Role, User-role and Agent-permission handler checks; do not depend on duplicate package permission gates. Retain the package's cross-user session, email-change administration and pending-invitation correction actor/target callbacks. Future Workspace/Repository admins need separately bounded consumer team scope, not implicit installation-wide authority. Do not duplicate verified intrinsic package Role/tier/reference rules in Agent OS.
- **Persistence and concurrency:** PostgreSQL adapters must honor the qualified public repository contracts for non-null tiers, managed references, custom-role grants and direct Agent assignments. Prove atomic grant-versus-protected-promotion outcomes on the canonical connection with shared tier/membership fences: a race cannot commit forbidden membership, including desired-state no-ops. Unknown, malformed or unsupported tier state fails closed. Until safe intrinsic grant eligibility is proven, no custom-role permission grant operation is exposed.
- **Migration and compatibility:** Inventory actual owned target rows, null/custom/managed tiers, role memberships and Agent assignments before migration. Generate a new Doctrine version at execution time and preserve historical migrations. Map only validated supported legacy state; do not silently treat malformed/unknown tiers as `ADMIN_SAFE`, rewrite live authority or assume an empty production database. Define safe rejection/reconciliation and recovery for incompatible state before applying a guarded migration. Inspect all public API changes in the chosen release that affect existing consumer integrations, not only the desired authorization change; unresolved compatibility blocks adoption.

Upstream closed WF-011–WF-016 and EPIC-00008/TICKET-00009–00011/TASK-00041–00045 are ownership/design traceability, not release evidence. In particular WF-016's grant-versus-promotion guarantee needs both upstream package proof and Agent OS PostgreSQL integration proof.
