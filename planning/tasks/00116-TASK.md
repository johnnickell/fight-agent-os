## Proposed permission decisions to reconcile

- Use consistent CRUD-named **plural** resource permissions, e.g. `CREATE_USERS`, `READ_USERS`, `UPDATE_USERS`, `DELETE_USERS`, instead of mixing `LIST_USERS` with `VIEW_PERMISSIONS`. `UPDATE_USERS` means permitted user field changes only: it does **not** grant role assignment, lifecycle transitions, sessions, elevation or a direct active-email replacement. Define `READ_ROLES`, role CRUD permissions and `READ_PERMISSIONS` only for product journeys actually approved. Define invitation and lifecycle permissions by explicit operation; do not guess that one CRUD permission covers credential recovery or irreversible state changes.
- Provide separately checked self-service `READ_PROFILE`, `UPDATE_PROFILE`, `READ_OWN_SESSIONS` and `DELETE_OWN_SESSIONS`; the same underlying package user/session operations must still enforce actor/target ownership. Current-session logout has its own cookie/CSRF semantics.
- Give the managed `ROLE_SUPER_ADMIN` the sole initial membership for installation-wide security administration, while regular users have only agreed self-service/dashboard permissions. Authorize by current authoritative permission, never role name, JWT role claim, URL or client state. Mark global user/role/permission, cross-user session, `MANAGE_USER_ROLES`, `MANAGE_ROLE_PERMISSIONS` and `ASSIGN_SUPER_ADMIN` as `SUPER_ADMIN_ONLY` where appropriate. Future workspace/repository reads and custom-role work require separately scoped, `ADMIN_SAFE` permissions and scope enforcement, not an installation-wide grant by accident.
- For ordinary user-role associations require `MANAGE_USER_ROLES`. Assigning the managed Super Admin role requires **both** `MANAGE_USER_ROLES` and `ASSIGN_SUPER_ADMIN`, explicit confirmation and audit. Decide removal, last-admin and self-change safeguards independently. The installed package role-assignment authorization port takes only actor ID, so an HTTP attribute alone cannot enforce target-role authority for every command caller.
- `MANAGE_ROLE_PERMISSIONS` may not delegate `SUPER_ADMIN_ONLY` permissions to custom/scoped roles. The installed Fight Access Control package defines `PermissionTier::ADMIN_SAFE`/`SUPER_ADMIN_ONLY` but its custom-role grant handler does not enforce tier eligibility. Treat this as a hard upstream integration gate, not something solved by an HTTP-only check. The [Fight Access Control v0.4.0 recommendation](../../docs/engineering/fight-access-control-v0.4.0-recommended-addition.md) is guidance for the separate Fight Access Control Wayfinder, not an accepted upstream requirement; upstream acceptance/tag and deliberate consumer update are separate work.
- Distinguish global versus future workspace/repository authority. Decide whether non-managed/null-tier custom permissions can be delegated; fail closed until the owning package approves policy. No implicit broad admin role bypass, no silent permission rename that strands existing references or client checks.

## Validation and permissions

The Slim `/api/v1` group should authenticate Bearer requests by default after routing; only explicitly marked public/credential-controlled actions bypass JWT. A matched FQCN Action can carry `#[RequiresPermission(...)]` (including conjunctive multiple permissions), or an explicit authenticated/public marker. Missing/invalid metadata on a protected API route must fail closed before Action instantiation/dispatch. Route/method misses, non-API root/web behavior, and future `/mcp` HMAC behavior must not be accidentally turned into JWT bypasses or falsely authenticated operations. The middleware checks current authoritative request-scoped principal/permissions, not role names or JWT claims. Package/application target-ownership and role/tier checks remain necessary even when route metadata permits entry.

Exact HTTP authorizations are **proposals** until affected EPIC/TICKET decisions and upstream constraints are approved; do not treat this record as permission to ship an endpoint.
