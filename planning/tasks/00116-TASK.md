## Proposed permission decisions to reconcile

- Use consistent CRUD-named **plural** resource permissions for actual supported generic operations, not blanket CRUD for every resource. Rename the *planned, not deployed* `LIST_USERS` to `READ_USERS`; retain `INVITE_USERS` because inviting a pending user is not unrestricted `CREATE_USERS`. Do not define `CREATE_USERS`, `UPDATE_USERS` or `UPDATE_PROFILE` without concrete safe supported fields/commands. Define distinct `DISABLE_USERS`, `ENABLE_USERS`, `DELETE_USERS`, `RESTORE_USERS`, `MANAGE_USER_ROLES`, `READ_SESSIONS`, `DELETE_SESSIONS`, custom-role CRUD, `READ_ROLES`, `READ_PERMISSIONS` and `MANAGE_ROLE_PERMISSIONS` for approved use cases. `DELETE_USERS` means package soft deletion; none of these grants direct active-email replacement or credential recovery.
- Provide separately checked self-service `READ_OWN_SESSIONS` and `DELETE_OWN_SESSIONS`; package session operations must still enforce actor/target ownership. `/api/v1/me` remains authenticated without a dashboard/profile permission; defer distinct `READ_PROFILE` and `UPDATE_PROFILE` until a specific own-profile operation/field is approved. Current-session logout has its own cookie/CSRF semantics.
- Give the managed `ROLE_SUPER_ADMIN` the sole initial membership for installation-wide security administration, while regular users have only agreed self-service/dashboard permissions. Authorize by current authoritative permission, never role name, JWT role claim, URL or client state. Mark global user/role/permission, cross-user session, `MANAGE_USER_ROLES`, `MANAGE_ROLE_PERMISSIONS`, `ASSIGN_SUPER_ADMIN` and `REMOVE_SUPER_ADMIN` as `SUPER_ADMIN_ONLY` where appropriate. Future workspace/repository reads and delegated administration require separately scoped, `ADMIN_SAFE` permissions and actor/target scope enforcement, not an installation-wide grant by accident. Tier labels alone do not enforce eligibility.
- For ordinary user-role associations require `MANAGE_USER_ROLES`. Assigning the managed Super Admin role requires **both** `MANAGE_USER_ROLES` and `ASSIGN_SUPER_ADMIN`; removing it independently requires **both** `MANAGE_USER_ROLES` and `REMOVE_SUPER_ADMIN`. Each needs explicit confirmation and durable audit. Guard last-admin and self-change in Agent OS Application. The installed v0.3.0 package role-assignment authorization port takes only actor ID; v0.4.0 is expected to remove some redundant handler permission checks, not the package's cross-user session/email-change administration/pending-invitation correction actor/target authorization callbacks. Neither an HTTP attribute nor an old package actor-only port can enforce all target-role rules for every caller.
- `MANAGE_ROLE_PERMISSIONS` may not delegate `SUPER_ADMIN_ONLY` permissions to custom/scoped roles. The installed Fight Access Control v0.3.0 defines `PermissionTier::ADMIN_SAFE`/`SUPER_ADMIN_ONLY` but its custom-role grant handler does not enforce tier eligibility. A shared Agent OS Application authorization boundary must enforce current actor permission and scope for every HTTP, console or future MCP entry adapter. The qualified Fight Access Control package must enforce its intrinsic custom-role/managed-reference/tier rules; do not duplicate verified package checks in Agent OS. Treat the unverified v0.4.0 release and its exact intrinsic/tier contracts as a hard integration gate; if that release lacks a required invariant, keep grants blocked pending an explicit owner decision, not an HTTP-only fallback. The Fight Access Control v0.4.0 recommendation was passed to the owning project as separate Wayfinder input; its local copy under ignored `.runs/notes/TASK-00018/` is not an accepted upstream requirement. Upstream acceptance/tag and deliberate consumer update are separate work.
- Distinguish global versus future workspace/repository authority. Under locked v0.3.0 custom Permissions may have null tier and cannot be safely delegated by this consumer. The upstream closed WF-012 proposes **non-null** tiers, with new custom Permissions starting `ADMIN_SAFE`; TASK-00126 must verify the tag and adapt the nullable consumer schema/repository. A malformed null or inconsistent tier still fails closed; no null-as-`ADMIN_SAFE` fallback. No implicit broad admin role bypass, no silent permission rename that strands existing references or client checks.

## Validation and permissions

The Slim `/api/v1` group should authenticate Bearer requests by default after routing; only explicitly marked public/credential-controlled actions bypass JWT. A matched FQCN Action can carry `#[RequiresPermission(...)]` (including conjunctive multiple permissions), or an explicit authenticated/public marker. Missing/invalid metadata on a protected API route must fail closed before Action instantiation/dispatch. Route/method misses, non-API root/web behavior, and future `/mcp` HMAC behavior must not be accidentally turned into JWT bypasses or falsely authenticated operations. The middleware checks current authoritative request-scoped principal/permissions, not role names or JWT claims. Package/application target-ownership and role/tier checks remain necessary even when route metadata permits entry.
