# Validate explicit JSON and query input without transport DTOs

## Outcome

API Actions declare argument-free `#[JsonBody]` or `#[QueryString]` source markers and Fight Common
`#[Validation]` fields/rules. Post-routing middleware exposes only successfully checked values on the request
before Action execution; it no longer requires a class used only to describe input. Declared GET query values
receive the same safe validation boundary as declared JSON body values. Action/Responder attributes follow
one documented source-order convention without changing middleware execution or policy ownership.

## Scope

- In scope: Replace owned `JsonBody`'s DTO argument with a source-only marker; add `QueryString`; qualify installed
  Common rule/field semantics for both sources; bounded source selection/parsing, field allowlisting, validation
  and checked request access; safe failures/no-dispatch; current CSRF compatibility; canonical Action/Responder
  attribute grouping; accurate engineering/API docs, direct contract evidence and owning behavior tests.
- Out of scope: Input-only DTO/schema classes, generic typed hydration, merging multiple input sources, a new
  validation DSL or Common package fork, implicit form-schema publication, product list/authentication endpoints,
  arbitrary filter languages, new domain behavior, permission/CSRF policy changes, frontend implementation,
  per-request OpenAPI generation, broad refactors and product tests of tools or attribute source formatting.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Validate declared JSON input | Owning operation only after validation/authorization | Read actual `JsonBody`/`Validation` metadata and request body | None from validation | Checked field map on the request; no DTO construction or dispatch on rejection |
| Validate declared GET query input | None from validation | Read actual `QueryString`/`Validation` metadata and query input | None | Checked pagination/order/filter values only when declared by the endpoint; no implicit body fallback |
| Reject malformed/ambiguous input | No command dispatch | No application query dispatch | None | Sanitized bounded 400 JSend fail; submitted values/private rule details remain undisclosed |
| Reject invalid declaration | No command dispatch | No application query dispatch | None | Safe configuration/server failure; never bypass validation or mislabel it as bad client input |
| Maintain endpoint metadata | No domain command | Inspect affected Action/Responder declarations and owning contracts | None | Consistent attribute order and honest current versus future API documentation |

## Validation and permissions

Implement [TICKET-00010's explicit-source contract](../tickets/00010-TICKET.md#explicit-request-input-sources)
and [canonical attribute order](../tickets/00010-TICKET.md#canonical-action-and-responder-attribute-ordering).
Those sections own the accepted semantics; do not recreate a second policy in a helper or DTO registry.

Use installed Fight Common `Validation`, `RulesParser` and validation capabilities directly. Record actual
versions/source references and qualify required/optional/empty/null/type/range/enum/comparison behavior for
JSON-native and query-string representations before claiming support. Field names/keys and constraints come
from `Validation`, not PHP constructor properties, OpenAPI reflection or a second schema class. Missing or
ambiguous metadata and unsupported declared rules fail closed. A source marker requires valid Validation
metadata; an empty declared field set does not mean unrestricted input. Do not patch vendor or silently substitute
weaker local rules when a required package capability is missing; surface the exact qualification blocker.

Keep source selection explicit and single-source. `QueryString` admits declared GET query input; `JsonBody`
admits declared JSON input for supported mutation methods. Reject conflicting/repeated markers, unsupported
method/source combinations and nonselected body/query input rather than merging, falling back or ignoring it.
An Action without a source declaration remains a no-input Action; GET does not implicitly opt it into query
validation. Preserve current no-input CSRF behavior, including its endpoint-owned query rejection and
cookie/HTTPS/origin/Fetch Metadata controls.
Route parameters, cookies/headers and authoritative principal context remain separately owned inputs.

Retain the existing 64-KiB JSON-body bound, JSON-object/unique-key/content-type policy and safe no-body checks.
Define finite query byte/field/depth limits and reject malformed encodings, duplicate decoded names, normalized
key collisions and parser truncation before a lossy parameter bag can hide them. Accept only declared field
names and supported value shapes. Flat scalar pagination, direction, boolean and filter parameters are the
initial concrete use cases; nested/list filters need explicitly qualified rules and an owning endpoint contract,
not inference from bracket syntax or a general query language. Missing, empty, null and malformed values must
remain distinguishable. Defaults and conversions are explicit in endpoint rules/mapping, never silent global
trimming, truthy casts or fallback on malformed input. No strongly typed input object is required.

Expose the checked map through a documented request access point for each source; Actions consume that map,
not unvalidated raw input reread after middleware. Convert validated values to the actual package/owned use-case
contract only where needed, without replacement message aliases. Validation never authorizes `include_deleted`,
selects an actor/tenant or permits raw sort/filter expressions. Endpoint permissions and Domain invariants apply
independently. Do not add these example fields to an endpoint that has not approved them.

Preserve safe 400 JSend field-message lists and existing `body` paths; use `query` paths for declared query
fields. Never echo arbitrary field names, parser/rule prose, submitted credentials or raw values. Invalid
metadata uses the existing correlated generic server-failure boundary. Rejected input cannot execute the Action,
dispatch an application message, issue a credential or cause business writes/events.
