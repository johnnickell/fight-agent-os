# Grant and revoke Repository access for Users and Agents

## Outcome

An authorized caller can inspect, grant and revoke explicit User or Agent access to a registered Repository through
one shared Application contract and versioned API. Configuration and Start consume that same current-access policy,
removing their missing access-writer dependency without another Role system or execution engine.

## Scope

- In scope: Repository-owned explicit access relationships, typed User/Agent targets, current access decisions,
  expected-state grant/revoke, monotonic revisions, safe inspection/history and original-operation recovery;
  atomic persistence/audit/results; versioned API and shared Application enforcement; the two approved access
  Permissions; `ROLE_WORKSPACE_ADMIN` definition through the existing managed catalog and integration with existing
  Role assignments; consumer-facing access checks that work correctly with concurrent authority changes.
- Out of scope: User/Agent creation, a new Role-assignment mechanism, implicit Permission memberships or principal
  assignments, Repository configuration/policy publication, Team membership, Start/dispatch, provider execution,
  full MCP/console/UI delivery, multi-workspace assignment and another generic authorization platform.
- `ROLE_REPOSITORY_ADMIN` and `ROLE_DEVELOPER` are human vocabulary in
  [the ubiquitous language](../../docs/UBIQUITOUS_LANGUAGE.md#human-roles). This TASK does not invent their Permission
  bundles, assign them to Users or treat them as new all-Repository access paths.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect access | N/A — read-only | Exact relationship, effective access paths, bounded history and paginated explicit grants | None | Authorized scoped facts, not a reusable grant or unrestricted User/Agent directory |
| Grant explicit access | Grant Repository access to an exact typed principal, with expected relationship revision and original operation identity | Current issuer authority, Repository and target state | Repository access granted, only on an actual transition | Relationship/revision, attribution and original result commit together; no operation Permission or execution grant |
| Revoke explicit access | Revoke the exact relationship with expected revision and original operation identity | Current issuer authority and remaining effective access paths | Explicit Repository access revoked, only on an actual transition | Explicit access is removed; retained revision/history and any independent administrator path remain |
| Resolve an uncertain operation | N/A — read-only | Original payload-bound operation result under current disclosure authority | None | Known original result or an honest unavailable/unknown outcome; never an automatic replacement mutation |

These are owned use-case contracts, not a second messaging protocol or wrappers around package Role commands.
Exact PHP and transport names belong to implementation. HTTP Actions map validated input and trusted authentication
into the shared use cases; future console/MCP/worker callers use the same authorization, not a privileged bypass.

## Validation and permissions

### Ownership

The Agent OS Repository domain owns explicit access relationships and the Repository access policy. Application
handlers coordinate current authority, references, writes and results. PostgreSQL adapters implement persistence
on the shared connection. Follow [ADR 0001](../adr/0001-application-ownership-and-orchestration.md) and
[ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md).

Fight Access Control retains User/Agent identities, Roles and Permissions. TASK-00078/00080 retain Repository
identity and lifecycle. Use their real identifiers and state rather than copying principals, creating another
Repository registry or making configuration/Team membership the access writer.

### Approved operation Permissions

| Permission | Tier | Authority |
|---|---|---|
| `READ_REPOSITORY_ACCESS` | `ADMIN_SAFE` | Inspect scoped relationships, effective access explanations and access history |
| `MANAGE_REPOSITORY_ACCESS` | `ADMIN_SAFE` | Grant or revoke explicit access for an exact Repository and typed target |

Both require the caller's current Repository access independently. Possessing an operation Permission alone does
not authorize access to an arbitrary Repository; Repository access alone does not authorize its administration.
Read and management remain distinct rights. A UI or caller that inspects before changing access needs the read
right for that inspection; a mutation returns its bounded result, not an unrestricted roster/history projection.

Humans and Agents use their own authenticated identities and actually assigned Permissions. No human-only gate or
Agent-specific assignment exclusion is added. Caller-supplied actor IDs, Role names, shell access and `--internal`
are not authentication. Do not expose an entry path that cannot establish the caller's real current authority.

Permission eligibility never implies assignment. Add these definitions through the one managed catalog, separating
explicit tiers, Role memberships and application references as required by
[MANAGED_POLICY.md](../../docs/engineering/MANAGED_POLICY.md#permission-eligibility-is-not-assignment).
Preserve existing approved definitions and memberships. This approval creates no default memberships, including
Super Admin defaults, and no User/Agent assignments. Use existing authorized Role/Permission assignment paths for
actual grants. Generate stable catalog IDs with the owning factory during implementation, not in this plan.

### Effective access and human Roles

Current Repository access is **authoritative Super Admin OR authoritative `ROLE_WORKSPACE_ADMIN` in the initial
Workspace OR an explicit active Repository access relationship**. Each protected operation independently checks
its Permission and applicable lifecycle rules.

Define `ROLE_WORKSPACE_ADMIN` through the existing managed Role/catalog contracts, with stable identity and no
implicit Permission memberships or User assignments. Use existing Role assignment/removal, including TASK-00121's
`MANAGE_USER_ROLES` checks and existing protected Super Admin safeguards where applicable. Repository access
management does not authorize Role changes. Do not trust a custom Role with a similar name or caller-provided labels.
Separate Workspace assignment waits for multi-workspace functionality; no separate membership store is added now.

An administrator may also hold an explicit Repository grant. Creating that relationship is a real change even
when administrator access already makes the Repository accessible. Revoking the explicit grant does not remove
administrator access; removing an administrator Role does not delete explicit grants. Report the relationship
change separately from effective access so that 'grant removed' cannot falsely mean 'all access removed'.

### Relationship transitions and retries

Bind a relationship to one Repository ID and one typed User or Agent ID. Do not accept an untyped identity, a Role,
Team, slug or checkout path as the target. Grant validates the target's existence and current lifecycle through
its owning contracts; revocation can remove an existing relationship for an inactive target. Granting access does
not require or supply a target operation Permission, Role assignment, Team membership or execution grant.

A command carries the expected relationship revision and an original operation identity bound to the authenticated
issuer and normalized action/Repository/target/payload. Distinguish never-granted absence from a retained revoked
relationship. Revisions advance on actual transitions and never reset on revoke/regrant; keep enough retained state
to reject changed-away-and-back observations. Concurrent first grants cannot create duplicate relationships.

Validate the expected state even for a fresh request whose desired state already holds. A stale request conflicts;
a fresh no-op reports unchanged without emitting a fictional grant/revoke transition. Retain its original result
and attribution without advancing the relationship revision. Reusing an operation identity with a different payload
fails. Repeating an already committed operation returns its historical result, not another transition or a claim
that the recorded access still holds now.

Original-result disclosure still checks current authority. If the caller has since lost access, a denied or
unavailable result is not proof that the write rolled back; an authorized access manager can resolve it. Do not
create a replacement operation or replay an uncertain mutation merely to discover whether it succeeded.

### Atomic changes and current use

Commit the relationship change, revision, required bounded audit and original result together through one owning
Application transaction on the canonical connection. Include typed issuer/target, Repository, action, outcome and
old/new relationship revisions without credentials or copied Permission snapshots. Keep Repository access audit
with this owner; do not fabricate User IDs for Repository subjects or widen unrelated package audit contracts.
A rollback leaves no successful change/result/audit; external effects never run inside this transaction.

Access decisions used by a protected mutation/admission must remain valid through that operation's transaction.
Coordinate the actual access, Role-assignment, Role/Permission, principal/session and Repository-lifecycle writers
so competing operations have a consistent outcome. Use compatible lock ordering across those writers; a snapshot
or middleware preflight alone is insufficient. This is implementation work within the use case, not a separate
qualification phase, approval process or additional planning prerequisite.

When revocation commits first, an operation with no remaining access path cannot be admitted. When the protected
operation wins first, record that order honestly; revocation does not retroactively cancel an already-admitted
external effect. Regrant never makes an old observation current. Start adds its own grant/claim/reservation/dispatch
inside its transaction; this supplier does not own those effects or require completed Start to be delivered.

Keep access separate from lifecycle: archived Repositories reject new grants but allow authorized inspection and
revocation. Retain access history through archive/restore. TASK-00080's lifecycle changes and consumers use the same
current-state boundary; archived-state inspection is not permission to perform ordinary active-Repository work.

## Acceptance criteria

- [ ] An authenticated caller can inspect and grant/revoke exact User/Agent Repository relationships through the
  shared Application contract and versioned API, with independent access/read/manage checks and safe bounded output.
- [ ] Current Super Admin, initial Workspace Admin and explicit access paths work independently; removing one path
  preserves any other valid path. Role assignment remains with the existing Role owner.
- [ ] Permission definitions and the Workspace Admin Role do not infer memberships or assignments; existing approved
  catalog contents remain intact. Human Role terminology is not mistaken for Agent profiles or an authority bypass.
- [ ] Stale commands, concurrent initial grants, no-ops and revoke/regrant behave as specified; revisions do not reset,
  relationships do not duplicate and changed-away-and-back state cannot admit stale requests.
- [ ] Relationship, revision, audit and original result commit or roll back together. Duplicate payload-bound commands,
  conflicting identity reuse and lost acknowledgements cannot repeat a mutation or falsely report rollback.
- [ ] Concurrent access/Role/Permission/authentication/lifecycle changes and protected operations produce consistent
  outcomes through the actual writers. HTTP and supported non-HTTP paths cannot bypass the shared access contract.
- [ ] Archived Repositories reject grants and allow authorized inspection/revocation; revocation can remove retained
  access for an inactive target without silently changing Roles, Permissions or other access paths.
- [ ] No configuration, Team, execution, provider or Git effects follow from an access mutation. Focused behavior tests
  and the normal implementation build pass, with failures and unsupported entry paths reported honestly.
