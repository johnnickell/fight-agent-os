# Grant and revoke Project access for Users and Agents

## Outcome

An authorized caller can inspect, grant and revoke explicit User or Agent access to a registered Project through
registered Application handlers and a versioned API. Configuration and Start consume the same Project-owned
access policy without another Role system or execution engine.

## Scope

- Project-owned explicit access relationships; typed User/Agent targets; effective-access decisions; expected-state
  grant/revoke; monotonic revisions; bounded inspection/history; atomic relationship/revision/required audit.
- Versioned API with entry-owned authentication, operation Permission and Project/Workspace scope admission before
  configured bus dispatch. Future Console/MCP entries must establish their own real caller and admission; this
  TASK does not deliver them, an execution engine or a generic authorization platform.
- Two access Permission definitions and `ROLE_WORKSPACE_ADMIN` through the existing managed catalog. Role
  assignments, Permission memberships and principal grants remain separately authorized operations.
- Exclude User/Agent creation, configuration/policy publication, Team membership, Start/dispatch, provider or Git
  effects, full UI, multi-workspace assignment and another access registry.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect access | N/A | Exact relationship, effective paths, bounded history and paginated explicit grants | None | Safe typed scoped Views, not a reusable grant or unrestricted principal directory |
| Grant access | Void expected-state grant to exact Project and typed principal | Current Project/target facts and relationship revision | Access granted only on an actual transition | Relationship/revision/attribution/audit commit together; no operation Permission or execution grant |
| Revoke access | Void expected-state revoke of exact relationship | Remaining effective paths and relationship revision | Access revoked only on an actual transition | Explicit grant ends; retained history and independent administrator paths remain |
| Recover lost acknowledgement | N/A | Fresh authorized relationship/effective-access/history query | None | Current authoritative state and attribution, not an immutable original response or blind replay |

Exact PHP message and transport names belong to implementation under the
[architecture contract](../../docs/engineering/STANDARDS.md#architecture); do not invent a second protocol or
forward package Role commands. These are target Project contracts, not delivered renames of today's Repository
APIs/catalog. TASK-00575 owns existing registration cutover; this TASK owns its access consumers/catalog together.

## Validation and permissions

### Ownership

The Workspace Project domain owns explicit relationships and access policy. Access Control retains canonical
User/Agent IDs, lifecycle, Roles and Permissions. Use Project identity/lifecycle from its existing owner; do not
copy principals or make configuration, registration, linking, Teams or Start alternative access writers.

Registered handlers coordinate aggregate behavior, collection-like persistence and bounded owned audit through
injected generic `TransactionalUnitOfWork` on the exact shared connection. Keep inward dependencies and descriptive
collaborators. Repositories do not own admission, transaction completion, responses or recovery. Success facts
are dispatched only after commit; dispatch failure is post-commit uncertainty, not proof of rollback. No external
effect runs in the transaction. Do not cast Project subjects into package User/Agent audit or widen that allowlist.

### Approved operation Permissions

| Target Permission | Tier | Authority |
|---|---|---|
| `READ_PROJECT_ACCESS` | `ADMIN_SAFE` | Inspect scoped relationships, effective paths and history |
| `MANAGE_PROJECT_ACCESS` | `ADMIN_SAFE` | Grant/revoke explicit access for exact Project and typed target |

Both independently require current Project access. Project access alone grants no administration Permission;
management alone grants no roster/history reading. A caller inspecting before mutation needs the read right.
Mutation acknowledges void completion without a roster or manufactured historical-result DTO. Read outcomes
through separately admitted queries. HTTP Data/Responders own snake_case JSON and safe error mapping from typed
Views; future transports own their own representations. Qualify shared failures under standards without assuming
that Common adoption already changes today's wire format.

Humans and Agents use their actual authenticated identities and assigned rights; no human-only gate or Agent
assignment exclusion is added. Claimed actor IDs, Role labels, shell access and `--internal` are not authentication.
Do not expose an entry unable to establish actual current authority. No second blanket Application/bus permission
gate or ambient trust flag is required.

Add definitions through the single [managed catalog](../../docs/engineering/MANAGED_POLICY.md#permission-eligibility-is-not-assignment).
Keep tiers, Role memberships and assignments independently explicit. Preserve unrelated catalog contents. Approval
creates no default Permission memberships, including Super Admin defaults, or User/Agent assignments. Generate
stable catalog IDs through their owning factory at implementation. Reconcile actual API/catalog callers deliberately,
preserving needed durable identities/history; no alias/dual mode is required solely for abandoned names.

### Effective access and human Roles

Effective access is authoritative Super Admin OR authoritative `ROLE_WORKSPACE_ADMIN` in the initial Workspace OR
an explicit active Project relationship. Define Workspace Admin with stable identity through existing managed Role
contracts, without implicit Permission memberships or User assignments. Use existing Role assignment/removal,
including TASK-00121's `MANAGE_USER_ROLES` checks and protected Super Admin safeguards. A custom lookalike name
is not authority. Separate Workspace assignment remains deferred; add no membership store.

An administrator's explicit grant is a real relationship even when another path already supplies access. Removing
that grant does not remove administrator access; removing a Role does not erase explicit grants. Queries distinguish
relationship changes from effective access. Existing `ROLE_REPOSITORY_ADMIN` and `ROLE_DEVELOPER` are shared human
[vocabulary](../../docs/UBIQUITOUS_LANGUAGE.md#human-roles), not Agent profiles, new all-Project bypasses or new bundles.

### Expected-state transitions and recovery

Bind one relationship to one `ProjectId` and a typed User or Agent ID, never an untyped ID, Role, Team, slug or path.
Grant validates target existence/current lifecycle through its owner; revoke may remove an existing relationship
for an inactive target. Neither operation grants target Permissions, Role assignment, Team or execution authority.

Commands carry complete expected relationship state/revision. Distinguish never-granted absence from retained
revocation. Advance revision only on a real transition; never reset it on revoke/regrant, so changed-away-and-back
observations remain stale. Concurrent first grants cannot duplicate a relationship. Validate expected state even
when desired state already holds: stale intent conflicts; fresh no-op emits no fictional transition or revision.
Keep required bounded audit/attribution for accepted operations independently of transition events.

There is no original-operation result journal, payload-bound replay or immutable original-response guarantee for
these ordinary database mutations. After lost response or post-commit failure, inspect fresh authorized state and
history; do not infer rollback or silently retry against new revisions. Current authority governs disclosure. If
self-revocation removes the last path, an authorized access manager can inspect retained history. Concurrent later
changes may mean current state differs from the attempted transition; history explains attribution, not a replayed
claim that access still holds.

### Admission timing and business consistency

Every entry admits current caller/operation/target scope before dispatch. Ordinary admitted requests may finish
after concurrent access/Role/Permission/session revocation; the next request rechecks and refuses if no path remains.
Do not lock all authority writers through an ordinary protected commit or require such a test. Regrant does not
validate a stale expected relationship revision. Genuine lifecycle/target/reference consistency, uniqueness and
complete expected-state comparisons remain transactional business invariants.

Start retains its separately owned grant/claim/reservation/dispatch and generation fences; this access supplier
does not own them or require completed Start. It supplies reusable Project access policy to entry admission, not a
second transport authentication engine. Stronger physical or execution-phase guarantees retain their specific owners.

Archived Projects reject new grants but allow authorized inspection/revocation. Preserve access history through
archive/restore and independent administrator paths. Archived inspection does not authorize active-Project work.
