# Establish qualified consumer coverage for the maintainer handoff

## Outcome

Starter maintainers receive a trustworthy account of the actual Agent OS AccessControl consumer they may reuse.
This removes EPIC-00018's coverage/publication blocker by establishing one exact-subject matrix and complete-
journey readiness assessment from existing implementation owners' evidence. It is one unranked documentation/
readiness chore, normally one PR, not new product features, a parallel scorecard or another certification campaign.

## Scope

- In scope: Current public-contract/use-case accounting, exact implementation/entry ownership, attributable
  qualification and approved dispositions, safe evidence references, change-impact assessment and the coverage
  input to TICKET-00081's references and TICKET-00082's final handoff.
- Out of scope: Product or package implementation, new endpoints/UI for coverage, a test/certification platform,
  duplicated scenarios or proof products, Swagger implementation, reference-guide authoring owned by TICKET-00081,
  archive/manifest/distribution owned by TICKET-00082, starter changes/certification/releases and live enablement.

### One current consumer matrix

Inspect the selected installed tag/source and exact Composer lock/reference at implementation. Map its public
contracts against the approved v0.5.0 planning coverage without presuming the eventual qualified release is still
v0.5.0. A constraint such as `^0.5.0`, package name, clean build or source directory is not the complete subject.
Record the actual Agent OS implementation commit and relevant configuration/deployment/tool identities; distinguish
these from later documentation commits. No manifest/lock upgrade is authorized by this accounting TASK.

Preserve [WF-032's planning matrix](../wayfinder/research/WF-032-accesscontrol-consumer-capability-matrix.md) as
historical planning evidence. Produce one maintained Agent OS-owned consumer matrix, linked from that history and
the existing handoff, rather than relabeling the old snapshot as present-tense qualification or creating another
planning queue. Use ordinary Markdown and reviewed evidence references; no new database, status dashboard,
per-method HTTP rule, package wrapper or general-purpose inventory engine is required.

Account for every relevant supported public use case individually within its family. Record package contract,
Agent OS owning TICKET/TASK and actual implementation/entry path, actor, target, current Permission/authorization,
transaction/effect boundary, appropriate authorized UI or qualified protected operational surface, observed
implementation, qualification provenance, limitations and explicit exclusion/unsupported disposition where approved.
One operation may have several entries or be deliberately unavailable at some entries; state that boundary rather
than claiming all transports or treating an unregistered handler as a protected callable surface.

Keep implementation and qualification distinct. Internal preparation may identify implemented, planned, excluded,
unsupported and unassigned facts, including partially implemented behavior. An implemented claim alone does not
mean qualified. A final in-scope row must identify actual consumer evidence; excluded/unsupported operations need
an explicit approved disposition with rationale/scope/authority. No unassigned or merely planned in-scope operation
may pass final acceptance. Missing authority, an inaccessible receipt or unknown coverage is not successful absence.

### Evidence attribution and change impact

operation/cohort/restore/credential/current-use, Team/role journeys, Feature lifecycle and template administration
through the owners below and their upstream contracts. Assess actual significant PostgreSQL races, restart,
restoration, revocation, current entry authorization and browser continuity where those contracts require them.
Do not create new requirements for unrelated product areas or an all-EPIC status gate.

Reuse attributable receipts only for their unchanged evidenced subject and guarantees. Record source, relevant
configuration/runtime/participant/tool identities, scenario, actual observations, limits and why any reused result
still applies. Distinguish package fixtures, storage-only tests, historical integration runs, fresh observations
and outstanding qualification. A run's date, a release label, an EPIC/TASK marked done or a successful build cannot
upgrade its evidence class. Package consumer-bindable tests support claims only when bound to real Agent OS ports
with the owning consumer observations; they do not replace actual provider, host or protected sink evidence.

Refresh affected claims through their existing owners when package, lock, consumer source, API, configuration or
operational participation changes. A mixed set of receipts must be shown applicable to the same identified
consumer subject; do not combine incompatible releases/environments into fictional end-to-end qualification.
Unchanged receipts retain their original identities and explicit applicability rationale, never a relabeled fresh
run. A failure or uncertainty holds the affected claim and final handoff, not authorization to replay effects or
start a second qualification ceremony. Repairs stay with their owning TASKs, with regression-first treatment for
confirmed bugs.

Account separately for reusable Feature infrastructure and TASK-00302's selected real `ai-template-proposals`
provider/browser/admission journey. Reuse its actual evidence instead of inventing a dummy Feature, extra provider
call or second acceptance demonstration. TASK-00298's guarded retirement capability neither authorizes retirement
of that Feature nor reverse-blocks shipping it. Current Feature and Agent snapshots, role journeys and template
use remain product-owner evidence, not new work commissioned by a matrix row.

### Confidentiality and readiness

Source/receipt access, private API documentation and operational observations remain independently authorized.
Use reviewed safe references and redacted evidence, not credentials, raw transcripts, secret-bearing operation
payloads, hidden provider configuration or unauthorized personal/source data. A receipt URL does not authorize
redistributing its contents, and inaccessible source cannot be assumed inspected. Preserve controlled access and
identify retention/access needs for TICKET-00082; ignored local `.runs/` receipts alone cannot supply an accessible
external handoff. This TASK does not upload artifacts, grant access or contact maintainers.

Reading or accounting for a receipt does not authorize replaying it. Any necessary fresh operation must remain
within its owning actor/target/delegation, confirmation, effect budget, environment and recovery rules under
separate implementation authority. Documentation introduces no Permission, principal, transaction, outbox or
synthetic certification event. ADR 0001/0002 remain authoritative for package ownership and atomicity claims.

The final assessment identifies the exact subject, complete qualified scope, explicit approved dispositions,
known limits and actual maintainer decision. A preliminary held assessment is useful internal progress, not TASK
completion or a staged final handoff. Readiness here clears only coverage: TICKET-00081's actual reproducible
references and TICKET-00082's authorized immutable packaging/delivery remain separate. No circular dependency on
completed reference writing/publication, starter acknowledgement or release is introduced.
