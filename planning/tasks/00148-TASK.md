# Adopt separated frontend tests and consistent import and style conventions

## Outcome

Keep production components free of colocated tests, use readable application-root imports, and enforce a
small, consistent frontend lint/format standard with a separate, modular SCSS tree, without changing runtime
behavior or visual design. This standalone chore adapts the human-approved Omphalos conventions to Agent OS
rather than copying its application or workflow.

## Scope

- In scope: Move existing frontend behavior tests into a mirrored `client/tests/` tree; configure and migrate
  application-root imports; deterministic import ordering and type-aware ESLint; explicit Prettier settings;
  affected test discovery, mock resolution, coverage and tool configuration; SCSS compilation and migration of
  owned styles into lean responsibility-named files; Bootstrap Sass composition; concise convention documentation.
- Out of scope: Product behavior changes, component redesign, production TypeScript directory renaming, new
  barrel modules or per-directory alias registries, broad dependency upgrades, copying Omphalos application
  code or planning workflow, PHP changes, new coverage thresholds, new end-to-end suites, React-Bootstrap
  component replacement (owned by [TASK-00149](00149-TASK.md)), and final combined-gate integration owned by
  [TASK-00032](00032-TASK.md)/[TASK-00033](00033-TASK.md). Theme loading/selection, database-backed theme
  management, arbitrary CSS upload and CSP/HTTP delivery changes are also deferred.

## Accepted conventions

The human approved these choices after a bounded source comparison. The source project is inspiration, not a
new authority or implementation dependency. The local assessment is retained under ignored
`.runs/notes/frontend-conventions-adoption/`; this TASK is self-contained for another checkout.

### Separate production, tests and stories

Keep `client/src/` for production source, `client/tests/` for behavior tests and test-only support, and
`client/stories/` for production-backed catalog examples. Mirror source-relative paths beneath `tests/`:

```text
client/
  src/components/Button.tsx
  src/components/forms/TextField.tsx
  src/api/ApiClient.ts
  tests/components/Button.test.tsx
  tests/components/forms/TextField.test.tsx
  tests/api/ApiClient.test.ts
  tests/setup.ts
  tests/apiFixtures.ts
  stories/Button.stories.tsx
```

Move every existing `src/**/*.test.{ts,tsx}` file, not just component tests. Retain descriptive `.test.ts` and
`.test.tsx` names. Do not create `src/__tests__/`, rename `src/` to match another project, or mix test helpers
into production modules. Stories stay separate; their existing interaction assertions remain appropriate.

### Use one application-root alias

Map `@/*` to `client/src/*`. Use `@/` for application-module imports/re-exports from production source,
tests and stories, including applicable dynamic imports and mock targets. For example:

```tsx
import { Button } from '@/components/Button';
```

TypeScript and runtime tooling own resolution; Prettier does not. Make the alias work in production ESBuild,
Vitest, Storybook development/static build and browser story tests. Prefer existing tool capabilities and
minimal shared configuration over new resolver machinery. Enforce the application-import convention through
the lint tool where applicable, not a product-suite test. Relative paths remain valid for local test-only
support, tooling configuration and asset/stylesheet references; preserve side-effect import order.

### Organize imports and apply semantic lint

Adopt grouped, alphabetized imports with blank lines between groups: React-family runtime imports first,
other built-in/external imports, internal `@/` imports, permitted relative imports, then type-only imports.
Use deterministic, fixable lint rules at error severity, retaining the existing zero-warning gate. Preserve
side-effect ordering and current explicit type-only import semantics; do not reorder CSS to satisfy a sorter.

Adopt supported TypeScript type-aware ESLint recommendations with correct production/test/catalog project
scopes. Retain React Hooks and JSX accessibility checks and the destination's strict TypeScript settings,
including exact optional properties and unchecked-index protection. Do not copy the reference project's
blanket tooling ignores, loosen strictness, or add broad suppressions to make checks pass.

Qualify necessary import-order and Sass/build integrations against the installed tool stack and commit exact
manifest/lock additions. Preserve existing dependency versions unless a concrete compatibility blocker needs
an explicit human decision. No forced peers, silent downgrade, or unrequested application-library adoption.

### Format consistently

Make these Prettier choices explicit and apply them to the owned frontend scope:

- `printWidth: 100`
- `singleQuote: true`
- `semi: true`
- `tabWidth: 2`, using spaces rather than tabs
- `trailingComma: "none"`

Prettier owns formatting; ESLint owns semantic/import rules. Retain separate check and explicit write modes.
Document the conventions in `client/README.md` and link them from the relevant engineering standards rather
than duplicating detailed configuration or adding speculative scaffolding.

### Keep SCSS separate and responsibility-focused

Keep owned application-default SCSS in `client/styles/`, separate from production TypeScript and tests.
Custom theme authors may supply plain CSS; the SCSS source convention does not require themes to use Sass. Use a thin
`app.scss` composition entrypoint and small partials with clear owners. A suitable shape for current needs is:

```text
client/styles/
  app.scss
  settings/_bootstrap.scss
  base/_tokens.scss
  base/_document.scss
  base/_accessibility.scss
  layouts/_shell.scss
  components/_button.scss
  components/_text-field.scss
  components/_notice.scss
  components/_content-panel.scss
  components/_content-state.scss
```

This illustrates responsibilities, not a requirement to create every listed file. Add directories/partials
only for actual styles; keep related rules together and split when a distinct responsibility improves
readability. No empty taxonomy, per-selector files, monolithic catch-all stylesheet, arbitrary line-count
limit or generic mixin framework. Catalog-only presentation stays under `.storybook/` in a small SCSS file
and must not enter the production entrypoint. Both builds consume the same production style entrypoint.

- Use Bootstrap's Sass source and build-time variables for deliberate static customization. Do not also load
  the precompiled Bootstrap CSS, emit Bootstrap more than once per entrypoint, or introduce its JS plugins.
- Preserve CSS custom properties for runtime semantic tokens and explicit light/dark modes; Sass variables
  are build-time settings, not replacements for runtime theme values. Do not introduce a theme selector.
- Use namespaced Sass modules (`@use`/`@forward`) for owned dependencies, with explicit composition order.
  Isolate any Bootstrap-version-required legacy Sass imports at its integration boundary. Record compiler
  deprecations and compatibility limits rather than silently forcing upgrades or blanket suppression.
- Put custom component styles in component-named partials, layout rules in layout-named partials, and shared
  tokens/base/accessibility rules with their owner. Add page-specific styles only when a real page needs them.
- Reusable styles use classes. Stable singleton IDs such as the existing `#app` may be targeted from their
  owning layout file; keep selectors shallow and specificity low. Do not generate IDs to style repeated
  components, couple styles to React-generated accessibility IDs, or use broad ID-descendant overrides.
- “Modular” means cohesive, scoped responsibilities here; it does not mandate CSS Modules or CSS-in-JS.
  Avoid deep nesting and specificity escalation; retain justified accessibility overrides such as existing
  reduced-motion behavior rather than weakening them to satisfy a style preference.

Migrate the existing production CSS and applicable preview styles without changing computed appearance,
Bootstrap semantic mappings, stylesheet order, asset delivery, responsive layout, focus or reduced motion.
SCSS must compile through the existing pinned Docker toolchain in ESBuild and Storybook/Vite; no CDN, runtime
Sass compilation or host-only tool installation. Document public stylesheet entrypoints and permitted
exceptions in the client conventions.

### Preserve simple theme customization; defer the engine

The human wants family-authored themes to be able to override default colors, fonts and component styles
without modifying React components or rebuilding the application's Sass source. Preserve semantic CSS custom
properties, predictable stylesheet order and low-specificity component selectors as the extension surface.
Document which token scopes apply to the document and explicit light/dark regions, so overriding a root token
is not falsely presented as overriding every scoped value. Direct component-style overrides are permitted;
themes are not restricted to a color-palette form or token-only API.

A theme may ultimately be supplied as one plain CSS file loaded in the base HTML after the default stylesheet,
or as a deliberate theme `<style>` block. The default source tree can remain lean modular SCSS while its
output and a theme's distribution are each a single CSS asset. Do not introduce scattered inline component
styles or high-specificity overrides that defeat this extension surface.

This TASK documents and preserves that direction; it does not implement a theme loader, HTML hook, upload,
selector, storage model or policy relaxation. The current shell uses `style-src 'self'` and does not permit
inline style blocks; adopting one requires a separately designed CSP-compatible delivery path, not adding
`unsafe-inline`. Custom font loading also needs explicit asset provenance and font/CSP support; font-family
overrides alone do not authorize arbitrary remote resources.

**Future Wayfinder topic: database-driven theme management.** Explore authoring/import, trusted versus
untrusted CSS, theme assets/fonts, installation versus user selection, preview, versioning/rollback, safe
fallbacks, cache invalidation, pre-paint delivery and accessibility boundaries. Decide whether the database
stores token values, source CSS, asset references or a combination rather than choosing a schema here. Keep
custom theme identity distinct from the accepted system/light/dark preference contract and coordinate with
[TASK-00050](00050-TASK.md). No database, theme-editor framework or Wayfinder map is created by this chore.
