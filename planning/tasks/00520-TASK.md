# Manage your protected OpenRouter connections

## Outcome

An authenticated authorized user creates, lists, inspects, replaces and disconnects their own environment-scoped
OpenRouter connections through a complete browser/API path. Keys remain in encrypted protected server custody;
consumers receive exact current connection/generation authority rather than ambient access or a shared household key.
This is one provider-specific lifecycle outcome, not a generic credential platform or live-provider qualification.

## Scope

- In scope: Connection lifecycle Domain/Application behavior, encrypted PostgreSQL persistence and protected
  service-only key consumption, separate encryption-key custody, authorized HTTP interactions, safe views, browser
  self-service, generation/currentness fences, original-mutation reconciliation and concise setup/recovery guidance.
- Out of scope: Provider requests or enrollment, generation/metadata/allowance adapters, model/default controls,
  accounting or budget stores, Agent credential delivery, local Pi/Codex credentials, hosted ChatGPT, production
  provisioning, automatic key purge/rotation, a runtime vault integration and final browser Planning execution.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Connect your OpenRouter key | Owned authorized connection creation with original operation identity | Current user/environment, permitted provider and protected custody capability | Committed nonsecret connection-created fact and required audit | Encrypt deliberately submitted key and persist one owned connection/generation; no provider call |
| List or inspect your connections | N/A — current-authorized bounded reads | Safe connection IDs, provider/environment, status and exact revision/generation | N/A | Read-only safe state, never plaintext/ciphertext/key handles or a live-readiness claim |
| Replace a connection key | Owned expected-state replacement of the exact connection | Current ownership, prior generation, original mutation and required retained versions | Committed nonsecret replacement fact and audit | Install a new generation atomically and fence future old-generation use without rebinding admitted work |
| Disconnect locally | Owned expected-state disconnect | Current ownership, original operation and connection state | Committed nonsecret disconnected fact and audit | Deny future use; retain required historical references/custody without claiming upstream revocation |
| Reconcile an uncertain mutation | No blind retry or replacement | Safe outcome of the original operation under current authority | N/A from inspection | Resolve committed/rejected/unknown state without resubmitting a secret or creating a duplicate connection |
| Supply protected current use | Narrow service-owned consumption for an exact authorized operation, not a browser command | Current owner/environment/connection/generation and required intent-specific authority | Existing consumer-owned operation facts only | Reveal key only within the qualified protected owner; safe callers receive no reusable grant or secret |

## Validation and permissions

Use TASK-00072's service-specific protected runtime/configuration and TASK-00343's allowed-provider policy facts.
Reuse current Access Control authentication/permission contracts directly under ADR 0001; server-derived user and
environment identity, not client/model IDs, govern every read and mutation. Administrators manage installation
policy, not automatic access to another user's key or connection. Conversation/Repository sharing grants neither
connection management nor allowance disclosure. Keep Agent OS connection profiles and Agent credentials distinct.

Preserve `/api/v1/me/provider-connections` as the approved resource direction; choose exact methods/payloads and
lifecycle routes during implementation through normal owned Actions/Responders. Validate bounded input, unknown
fields, stale expected state, origin/authentication and current permission at the actual API boundary. Use safe
no-store responses and sanitized failures; no secret-bearing entity, ciphertext, storage handle or arbitrary error
crosses into ordinary views, audit, logs, traces or evidence. List/inspection and mutation reconciliation perform
no provider request, automatic repair or configuration change.

Use qualified authenticated encryption with identity/environment/generation binding and explicit key-version
metadata, not bespoke cryptography. Encryption keys remain separately protected from database ciphertext, mounted
only to the owning service through explicit configuration, never generated opportunistically or stored in browser,
image, repository or ordinary runtime diagnostics. Missing/invalid required key versions fail closed for affected
operations without silently deleting state or selecting another key/account. Preserve versions required by retained
records, outstanding operations and approved recovery points. Document custody/recovery requirements for deployment
owners; actual backup/restore and human Bitwarden custody remain EPIC-00021 work.

Allow deliberate one-time entry in a transient secret field and protected submission. Never read it back, autofill
from server state, put it in a URL/global cache/storage/telemetry, or retain it for automatic retries. Clear secret
form state on completion, cancellation and authority/context teardown, including failed/uncertain submissions;
resolve the original operation before asking for another submission. ADR 0003/0004 authentication and response
fences reject stale successes/errors after logout, user/environment change or connection mutation. Show clear
confirmation, permission/conflict/failure/unknown states, accessible focus and recovery actions.

Connection state, monotonic generations, original-mutation identity and required audit share the canonical
PostgreSQL transaction. Concurrent replacement/disconnect and changed-away-and-back state cannot revive prior
current-use authority. Define the actual connection-writer/reference fence consumed by TASK-00344 and protected
adapters; a saved ID, cached view or historical revision is not a credential grant. Do not hold a business
transaction open across provider effects. Document the admitted in-flight boundary honestly: disconnect cannot
prove already dispatched work was unsent or cancel a provider request by deleting local state.

Keep immutable original connection/generation references and required historical custody. Lifecycle operations
must not reset reservations, erase charges/uncertainty, substitute the new key for old attempts or authorize
retired-key use. Intent-specific original-outcome reconciliation remains with TASK-00345/00346 and must independently
authorize any protected historical access; retaining ciphertext itself grants no use. These consumers implement
accounting/dispatch integration against this early contract without reverse-blocking lifecycle delivery.

## Acceptance criteria

- [ ] The real browser/API path creates, lists, inspects, replaces and disconnects the current user's connection;
  other-user/admin-only access, forged environment/identity and stale state are rejected by server authority.
- [ ] Actual encrypted storage and separate service-owned key custody survive a supported restart; missing versions,
  invalid/tampered ciphertext and wrong identity/environment binding fail safely without fallback or secret disclosure.
- [ ] PostgreSQL competing mutations, rollback and lost acknowledgements preserve one coherent original outcome,
  monotonic generation and audit. No duplicate creation, stale replacement or blind resubmission occurs.
- [ ] Actual current-use checks deny disconnected/replaced generations and preserve original references/retained
  versions. Lifecycle changes neither rewrite admitted work nor invoke another provider/accounting system.
- [ ] Browser submission is transient and secret-safe across errors, teardown and identity changes; late responses
  cannot restore retired data. Keyboard/focus/announcements and narrow/wide light/dark states work.
- [ ] Saved configuration is visibly separate from qualified provider access; create/replace/list/reconnect trigger
  no inference, model refresh or allowance read. Disconnect clearly distinguishes local fencing from upstream revocation.
- [ ] Current-use and nonsecret contracts are available to admission/metadata owners without requiring completed
  generation, optional allowance, production deployment or the final Planning journey.
