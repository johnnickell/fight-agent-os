# Evaluate bounded typed questions with usage receipts

## Outcome

Trusted Harness consumers can submit authorized bounded state with typed yes/no, choice or score questions and
receive validated results, explicit uncertainty/failure and redacted usage receipts. Deliver the common capability
needed by command safeguards and required file relevance screening without assigning their decision policies to
this layer. This completes the shared judgment scope of [TICKET-00037](../tickets/00037-TICKET.md).

## Scope

- Build on [TASK-00184](00184-TASK.md)'s qualified local Pi access, protected credentials, configured limits and
  lifecycle. Keep an injected provider boundary suitable for later managed first-party MCP integration; do not
  build a second Workflow engine or an unrestricted Agent-facing general-purpose judgment tool.
- Accept explicitly authorized supplied state plus versioned typed questions/rubrics and caller/source identity.
  Preserve Yes probability, classification confidence and score semantics without treating them as interchangeable
  accuracy estimates. Consumers interpret the result under their own versioned policy.
- Validate inputs and provider outputs strictly: question/answer identity and completeness, declared choices,
  required measures and ranges, finite numbers, requested score bounds, evaluator and configuration identity.
  Reject malformed, missing, duplicate, mismatched or undeclared answers rather than substituting defaults.
- Enforce approved ceilings across consumers: 64 KiB serialized input, eight questions, sixteen choices per choice
  question, two concurrent requests, fifteen-second timeout and zero automatic retries, lowered by any tighter
  provider/operator limit. Require explicit per-request/session spending ceilings and conservative reservations.
- Define budget/concurrency scope as the participating Pi session in the qualified local runtime. Child sessions
  using this capability must have explicit bounded allocations; independent sessions do not inherit a shared
  aggregate guarantee. Document any unsupported propagation rather than claiming account-wide enforcement.
- Reconcile provider usage with reservations without double counting. Preserve uncertain billed outcomes and
  unavailable cost. Admission must stop when a remaining budget or trustworthy upper bound cannot be established.
- Return bounded redacted receipts identifying evaluation, question/rubric and policy versions, exact evaluator,
  supplied source revision/digest, configuration revision, outcome, latency and available usage. Receipts do not
  contain source bodies, credentials or fabricated supporting quotations. Inspection must itself be bounded.
- Propagate cancellation and prevent work from an obsolete session/configuration from updating current results or
  accounting incorrectly. Use idempotent lifecycle cleanup and no hidden retries after ambiguous dispatch.
- Out of scope: file enumeration/read/cache policy, the 0.70 relevance rule, tool authorization/risk thresholds,
  compaction, memory retrieval, workflow routing, general-purpose Agent tool delivery and sandbox qualification.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Evaluate supplied state | Submit authorized state and typed questions | Inspect validated results and uncertainty | Evaluation completed/failed observation | Bounded provider request and usage accounting |
| Refuse invalid or unauthorized input | N/A: reject before dispatch | Inspect bounded reason | Rejection observation; no Workflow mutation | No provider disclosure or billed request |
| Inspect evidence and usage | N/A: read-only presentation | Inspect redacted receipts, limits, latency and available cost | N/A: no domain transition | Bounded local presentation |
| Cancel an evaluation | Cancel owned in-flight work | Inspect cancelled/uncertain outcome | Cancellation observation | Transport cleanup; conservative billing reservation retained when needed |

## Validation and permissions

Require current permitted disclosure before upstream dispatch; local source access is not provider-egress permission.
The caller supplies state from its own authorized source operation; this capability cannot expand file/tool access
or select an unapproved endpoint/model. Reject stale configuration and authority context. Provider data and source
text are untrusted and cannot change policy, invoke tools or become instructions to the main Agent.

Keep absence, refusal, timeout, denied access, billing failure, unavailable service, cancellation and invalid
response explicit. A batch that cannot establish all required answers cannot claim a complete success or complete
negative; consumers receive an explicit incomplete/failure state. An unavailable service cannot fabricate a
judgment, choose another provider or relax a consumer's protection.

Retain TASK-00184's local trust boundary. Future authoritative PHP operations and first-party MCP grants remain
separate. Observational receipts are not workflow transitions, permission grants, independent review or execution
proof. No raw secret crosses the consumer-facing capability.

## Acceptance criteria

- [x] Supported consumers can obtain valid yes/no, choice and score judgments with their distinct meanings and
  identities intact. Unknown/refused/invalid results never become ordinary positive or negative answers.
- [x] Strict validation rejects missing, mismatched, duplicate, undeclared, out-of-range and non-finite results;
  partial results cannot qualify a complete batch. Controlled tests include valid boundary values.
- [x] Unauthorized disclosure, invalid input and stale configuration stop dispatch. Endpoint/model and limits
  remain operator-controlled and cannot be overridden through supplied state.
- [x] Payload/count/time/concurrency and spend limits hold under concurrent calls and cancellation. Ambiguous
  outcomes retain reservations, duplicate completion cannot double count, and unknown cost never becomes zero.
- [x] Redacted receipts preserve provenance and available usage; source bodies/secrets do not enter normal output
  or retained receipts. Inspection is bounded and unsupported session aggregation is explicit.
- [x] Actual Pi integration qualifies the supported question forms and pinned endpoint/evaluator contract with
  bounded synthetic input. Reload/shutdown prevent stale delivery, leaked work and duplicated resources.
- [x] The shared capability is documented for TICKET-00038 and TICKET-00039 without embedding their thresholds,
  claiming sandbox safety, or asserting savings/model accuracy from deterministic fixtures.
