# Expose permission-controlled invitation recovery

## Outcome

Versioned JSend API operations let an authoritative actor with exact `MANAGE_USER_INVITATIONS` retry failed delivery, resend with a replacement grant, or atomically correct a pending invitation address, using Fight Access Control behavior, durable audit/delivery, bounded rate limits, and safe recoverable conflict responses.

## Scope

- In scope: Retry, resend, and pending-address-correction routes/Actions/DTOs; exact authoritative permission implementation for package `InvitationAdministrationAuthorization` and Action-level operations; package command dispatch; canonical email validation; operation-specific production rate limits; safe status/result Views and error mapping; OpenAPI; durable audit/effect integration; PostgreSQL race/rollback/HTTP/redaction tests.
- Out of scope: Super Admin React UI, active-user email change, user lifecycle administration, arbitrary delivery reset, raw grant reads, provider selection, manual database repair, and treating retries as exactly-once delivery.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Retry failed delivery | `RetryInvitationDelivery` | Resolve authoritative actor, latest grant/delivery, limiter | `InvitationDeliveryRetryRequested` | Existing failed generation returns to pending and normal recoverable delivery is requested |
| Resend invitation | `ResendInvitationDelivery` | Resolve authoritative actor and latest issued grant | `InvitationDeliveryResent` | Predecessor is revoked and fresh seven-day grant/delivery generation commits atomically |
| Correct pending address | `CorrectPendingInvitation` | Resolve actor, pending user, latest issued grant, canonical email claims | `PendingInvitationCorrected` | User email and predecessor/successor invitation state change atomically; new delivery is requested |
| Reject stale/raced operation | N/A beyond attempted package command | Recheck expected state/revision and permission | Safe package/HTTP failure | No stale overwrite, secret disclosure, or misleading success occurs |

## Validation and permissions

All operations require request-scoped authoritative identity with exact `MANAGE_USER_INVITATIONS`; actor IDs are never accepted from JSON. Implement package `InvitationAdministrationAuthorization` through authoritative permission resolution and target validation without role-name shortcuts. Unknown/stale/mismatched authority fails closed. Authorization occurs before target details/status are disclosed.

Retry is allowed only for package-defined retryable failed work and preserves the same delivery generation/idempotency identity. Resend requires an issued latest grant, atomically revokes the predecessor, creates a fresh purpose-bound seven-day credential/delivery generation, and never returns it. Correction requires a pending-activation user and current issued invitation, canonicalizes the destination, rejects canonical/reserved email conflicts, atomically changes user email and replaces the grant/delivery.

Apply operation-specific atomic rate limits using secret-safe actor/action/target dimensions. A throttle denial writes no package state. Dispatch package commands directly and preserve their transaction/reference/revision fences, audit evidence, post-commit event/durable delivery integration, and at-least-once semantics.

Use controlled conflict/recovery responses for not retryable/resendable, stale revision, already active/used/expired/replaced, claimed email, concurrent operation, throttle, and missing safe target. Do not expose which credential won, raw grant/digest/ciphertext/link, destination beyond approved authorized View, provider payload/message/key, SQL, stack trace, or arbitrary exception details.
