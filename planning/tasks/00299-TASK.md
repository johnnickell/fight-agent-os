# Initialize database-owned Agent templates without source overwrite

## Outcome

Remove the missing database-template prerequisite for TASK-00249's exact profile resolution and named Agent
creation. An authorized administrator can initialize and inspect the complete reviewed template catalog in
Harness, with immutable history and database-owned current selections that later deployment cannot overwrite.
This is one protected setup/inspection use case, normally one PR, not separate schema, inspection or proof work.

## Scope

- In scope: Stable template/revision identities, current selections, scope, ancestry and provenance; protected
  atomic initial seed and bounded authorized inspection; managed template-administration Permission; preservation
  of installed data and references; prevention of recurring source overwrites; affected PostgreSQL and operational
  qualification. Reuse the single Harness resource boundary and registered Workspace/Repository identities.
- Out of scope: Browser publication/editor, AI assistance, full profile/resource/model resolution, Agent creation,
  grants/credentials, sessions, automatic reconciliation of Agents, new Workflow routes, general Skill/resource
  platform, Planning cutover, source-file deletion, production seeding/deployment or a ninth required starting role.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Initialize reviewed templates | Owned protected Harness initial-seed operation | Approved catalog identity/provenance, installed setup state and current reference facts | Owned committed seed/revision facts only after commit | Complete approved starting set, provenance and required audit commit together or roll back |
| Inspect database authority | N/A — read-only | Scoped template identity/current selection, exact immutable revisions, ancestry and managed origin | N/A — reads emit no business-change event | Bounded secret-free resource views for administration and the downstream resolver |
| Repeat initialization | Same protected initial-seed operation | Previously committed complete seed and installed history | None on a valid no-op | Preserve later database selections, custom templates and every historical byte |
| Prevent a source overwrite | Explicit authorized change/retirement of any actual old template writer, if present | Actual installed writer/data inventory and database authority | Attributable transition facts only where a transition exists | Later deploy/reconcile cannot select or append source-authored template revisions implicitly |

Interaction names describe owned behavior, not installed PHP message names or additional endpoints. Select the
smallest supported protected setup/inspection adapter; no browser dependency or alternative adapter merely for
coverage. TICKET-00076 owns publication and the browser inspection/editor journey over this same authority.

## Validation and permissions

### Current protected administration

Introduce the approved managed `MANAGE_AGENT_TEMPLATES` Permission with `SUPER_ADMIN_ONLY` tier, assigned only
through managed Super Admin. Extend TASK-00036's whole managed policy, preserving its original catalog and all
accepted extensions; do not reconcile a one-Permission replacement. Generate its stable ID once through the
owning factory/UUID library during implementation and version it, never at runtime.

Require current trusted human identity, intent, installation and scope for setup and administrative inspection.
Reuse the qualified installation authorization boundary without weakening its protected-tier checks. A Role name,
source file, caller-supplied actor ID, operator shell access or `--internal` flag is not the required current
management authority. Validate Workspace/registered-Repository scope through its owner rather than treating
installation-wide administration as permission for arbitrary remote installations or provider disclosure. Guard
all supported direct/adapter paths; unsupported entry modes remain unavailable. Profile resolution for authorized
Agents retains TASK-00249's separate scoped read authority, not this human-only management Permission as a grant.
Template management grants neither Agent creation nor direct-Permission assignment rights.

### One Harness identity and immutable history

Implement the type-specific Agent-template capability in Harness under ADR 0001, not a second template registry
or a generic aggregate for every resource type. TASK-00248 supplies human-reviewed definitions and historical
aliases; TASK-00078 supplies typed Workspace/Repository identities. Preserve stable logical IDs independently of
names/aliases and immutable revision IDs independently of current selection. Generate genuinely new identities
through their owning factory/UUID library, inspecting retained identities before allocating replacements.

Retain complete prompt/persona intent, requested Permission set, exact applicable resource references, model and
Repository constraints, managed origin, ancestry and provenance. Enforce bounded shapes, uniqueness, reference
identity/type/scope and unambiguous ancestry. Never substitute a same-name resource, omit an invalid requested
Permission or create an ID to make missing input appear resolved. Historical requested Permissions are not grants;
retain their original identities and report later unavailability through the resolver/assignment owners rather
than rewriting history or fabricating protected access. Resource/model availability is not established by storage.

Current selection uses expected-state protection with a generation that cannot accept a stale selection merely
because a pointer changed away and back. Revision bytes/references remain immutable; rollback selects retained
history through the future publication owner, never edits old content. The persistence contract must support
managed and custom history without adding a new custom-publication endpoint just to test it. Keep exact existing
Agent bindings and active session snapshots intact; future readers consume explicit pinned revisions, not a source
fallback or silently refreshed current pointer. No purge, detach, Agent update or grant propagation occurs here.

### Complete initial setup and truthful repetition

Inspect actual installation data and writer topology before mutation. The planning source inspection found no
implemented Agent-template store or recurring template reconciler under `src/`, `config/` or migrations; this is
not proof that every eventual target is empty. Refuse ambiguous populated, colliding or partially initialized
state. Do not silently adopt existing IDs/content, backfill invented provenance or reset history. Any required
legacy-data transition needs exact approved mapping and preservation evidence, not an invented migration solely
to demonstrate one exists.

Accept the entire reviewed eight-template catalog as one bounded initial operation. Establish complete setup and
its approved input provenance durably in the same canonical transaction as templates, initial revisions/current
selections and required audit. Qualify one shared PostgreSQL connection, uniqueness, reference fences and bounded
competing setup; a loser cannot leave a partial catalog. Repositories do not own hidden transaction or audit
side effects. No external provider/filesystem publication inside the transaction; change events follow commit.

A valid completed seed is recognized from its retained setup/provenance and coherent history, not equality of
current rows with today's source. Repetition preserves later human-selected revisions, custom templates and
historical bytes, even when source definitions changed. It creates no new revision/event or source reset. Validate
current actor/target and setup integrity even on a no-op. Inconsistent partial state is a visible hold, not an
automatic repair/import. Define finite input/read/transaction limits and safe collision/denial/unavailable results.

The package audit model currently has User/Agent subjects; do not disguise a template as either or loosen generic
audit validation. Supply narrowly owned Harness evidence for this actual use case on the same connection, with
bounded actor/target/revision/provenance metadata and no prompt bodies, credentials or arbitrary error context.
Do not add a general audit platform or external outbox. Lost acknowledgement or post-commit event failure is not
rollback: inspect authoritative setup/history before another explicit operation. Later matching state proves
current facts, not necessarily this caller's original outcome; no blind retry, compensating reset or false receipt.

### Database authority across deployments

Before browser publication can be enabled, qualify all applicable template writers, including deploy/startup/
reconcile and overlapping retained versions where present. Change or retire an actual recurring source writer
only for Agent templates and prevent it from selecting/appending source revisions after the transition. An
in-flight or restarted old writer cannot regain authority through an earlier check. If no such writer exists,
record that bounded inventory and establish seed-only behavior; do not build then disable a fictional reconciler.

Preserve other Skill/Permission-definition owners, seed files, immutable bytes and historical references. No
source deletion or Planning Markdown cutover is authorized. Use owning deployment/setup tools directly for exact
target qualification; a migration name, source search or fixture database is not deployed-writer exclusion.
Unknown installed state or writer participation holds the affected transition rather than permitting source
fallback. TICKET-00076 consumes this safety boundary; completed editing never reverse-blocks initialization.
