# Manage versioned standing execution policy

## Outcome

An authorized administrator can inspect, validate, publish, restore and explicitly revoke installation standing
execution policy through a protected application/console path. Autonomous Start and the visual editor consume
one versioned policy authority rather than hardcoded grants or browser-owned rules. This removes the concrete
policy-authoring blocker for TASK-00139 and TASK-00493 as one independently reviewable product path.

## Scope

- In scope: Execution-owned closed policy schema and mandatory constraints/defaults/ceilings; fixed-stage
  capability descriptions and bounded stage-instruction supplements; authorized inspection, validation/diff,
  publication, history, append-only restore and explicit revocation; immutable revisions, current selection,
  monotonic authority generations, original-operation recovery and required atomic audit.
- Supply shared validation/effective-policy results and policy reference/admission transaction participants
  to Start and Repository configuration. Installation policy defines permitted override fields; Repository
  configuration retains scoped override persistence. The editor consumes these contracts without another
  registry, validator or grant authority.
- Out of scope: Repository override persistence, visual/dynamic builder, arbitrary executable policy nodes,
  Agent/provider launch, runtime-host enforcement, another Workflow/grant/claim/dispatch engine, live enrollment,
  Team-level policy inheritance and active-run policy migration. A persisted policy enables no runtime by itself.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect policy and history | N/A — read-only | Current selection, exact immutable revision, safe history/diff and revocation state under current scope | None | Authorized configuration facts; no grant, Workflow or provider call |
| Validate a candidate or effective override | N/A — advisory validation | Closed candidate, exact baseline/reference generations, permitted overrides and provenance | None | Normalized effective values or typed failures; no policy publication or reusable authority |
| Publish installation policy | Owned expected-state publication with original operation identity | Current management authority, reviewed candidate, baseline and reference facts | Owned committed policy-publication fact | Immutable revision, current selection, original result and required audit commit together |
| Restore retained values | Owned expected-state append-only restore | Exact prior revision, current constraints/references and proposed impact | Owned committed restoration fact | A newly validated revision; no historical rewrite or revival of old authority |
| Revoke policy authority | Explicit scoped revocation under current management authority | Exact target, expected authority generation and safe impact | Owned committed revocation fact | New authority generation fences subsequent admissions; retained revisions remain unchanged |
| Resolve an uncertain operation | N/A — inspect original outcome before another command | Original request identity/payload binding and retained result | None from inspection | Original success/conflict/unresolved result, not a second publication or revocation |

These describe owned responsibilities, not invented PHP message names or a second protocol. The protected console
is an adapter to the same Application contracts that later API/editor consumers use; it is not a privileged bypass.

## Validation and permissions

### One policy owner and fixed semantics

Follow [ADR 0001](../adr/0001-application-ownership-and-orchestration.md) and
[ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md). Execution owns policy semantics and the
installation lifecycle. TASK-00081 owns typed Repository override revisions and TASK-00082 consumes coherent
context/provenance. Neither parses instruction prose into enforceable authority or supplies a competing policy
engine. TASK-00139 remains the sole Start/grant/claim/reservation/dispatch owner.

Use the [approved v1 decisions](00493-TASK.md#approved-v1-policy-decisions): fixed registered stage sequence,
versioned bounded instructions, mandatory gates and independent Review/QA, permitted Repository overrides and
run-specific narrowing only. Text cannot create capabilities, alter topology or grant Permissions. Preserve
stable stage/reference identity and reject missing, retired, cross-scope or unsupported required references.
Distinguish a described future stage from a qualified executable capability; later Review/QA/publication must not
become a prerequisite of the initial terminal Awaiting review milestone merely to describe their constraints.

Stage supplements belong to the policy revision, not an implicit global Agent-template mutation. Reference exact
role/template/resource identities through their owners; define deterministic composition before implementation.
Keep instruction bodies in authorized policy inspection, not Workflow history, telemetry, generic snapshots or
ordinary errors. Bound text, collections, history pages and validation work; unavailable required inputs hold
rather than silently dropping a restriction or substituting a profile/tool.

Installation constraints remain mandatory. Only explicitly configurable defaults may be overridden within their
ceilings. Effective values expose their installation/Repository/run provenance, separate from current granted
access. Retain the existing five-cycle shared technical/QA repair default and initial ten-cycle installation
ceiling, separately from the initial-launch-plus-two-safe-resumptions process profile and time/cost/concurrency
budgets. A run-specific choice cannot raise the effective standing allowance. Exact reconciliation with
TASK-00310/00373 remains a named prerequisite, not permission to reset consumed counts or add automatic extensions.

### Approved management authority

John approved this authority split in the planning follow-up:

- **Installation policy changes are Super Admin-only.** Publication, append-only restore and explicit policy
  revocation require current package-backed protected management authority, with the installation-management
  Permission classified `SUPER_ADMIN_ONLY` and assigned only through the managed Super Admin policy. A Role name,
  shell access or UI visibility is not an authorization check.
- **Repository overrides require both Repository access and the operation Permission.** Changes are limited to
  permitted overrides within installation constraints; Repository management cannot mutate installation policy.
  Enforce authorization per operation, not through a blanket human-only gate on the configuration capability.
- **Repository capabilities follow assigned Permissions for humans and Agents.** John clarified that likely
  read-only Agent configuration access is an assignment preference, not a capability or assignment prohibition.
  Agents may read, revise or restore Repository configuration when granted the corresponding Permissions and
  Repository access. Add no Agent-specific exclusion or blanket human-only gate to these operations.
- **Configuration management is not execution authority.** Neither management Permission grants Start/control,
  Agent assignment, tool use or provider access; those operations retain their own current checks. Viewing is
  separately authorized and cannot substitute for management rights.

TASK-00036 supplies managed-authority composition, not an implicit new Permission or replacement reconciler.
John accepted the five-name mapping below with the corrected Repository-access and assigned-Permission model. Exact stable IDs,
seed memberships and scoped-assignment implementation still need their bounded amendments and qualification.
No Permission or membership is installed by this plan. Every application, console and API/MCP path enforces
current authority, including revocation, without a general human-only Repository gate.

### Approved Repository access model

Repository access and operation Permissions are independent requirements:

| Current authoritative principal relationship | Repository access |
|---|---|
| Super Admin | All repositories; no individual Repository access grant required |
| Authoritative `ROLE_WORKSPACE_ADMIN` assignment | All repositories in the initial single Workspace; future multi-workspace access combines this Role with separate Workspace assignment |
| Other human or Agent | Explicit current Repository access grant |

Administrator scope is established by authoritative membership, never caller-supplied role names or headers.
Unfettered Repository access here removes the per-Repository grant requirement within that administrator's scope;
it does not grant every operation Permission or waive Repository lifecycle, installation constraints, required
checks or runtime safety. `ROLE_WORKSPACE_ADMIN` is a Role using the existing Role assignment/removal mechanism,
not a separate administrative-membership type or store. Workspace assignment, analogous to Repository assignment,
is deferred until multi-workspace functionality; it is not a prerequisite for the current single-Workspace scope.
Defining this Role does not automatically assign it or populate its Permissions. Current Role assignment changes
and Repository access grants/revocations participate in current-access fencing. Agents retain their own
authenticated identity; do not fabricate User
sessions or inherit human role credentials to obtain authorized Repository operations.

A Repository-access middleware may provide the HTTP gate separately from Permission middleware. The same owned
Application check must protect MCP, console, worker and direct entry paths; middleware alone cannot provide this
contract. This approves the access semantics, not a middleware implementation, a generic new RBAC platform, a
Role assignment or a qualified grant store. Allocate the Repository access writer and map the Role through existing
owners before readiness; do not introduce a separate Workspace-membership supplier or multi-workspace blocker.

**Lock-order finding:** no complete total order is established by this source trace. The installed package
`ReconcileManagedPolicyHandler` owns its transaction and removes Roles before applying Permissions; the former can
hold the Role-reference fence before later taking the Permission fence. Blindly prescribing Permission → Role
locks for the new policy path could therefore invert an existing caller's order. This is an observed ordering
risk, not a reproduced deadlock or a finding that all existing human operations are broken. Map the full enabled
writer set, row locks and shared fences before choosing/extending one compatible order; preserve ADR 0002 and
qualify any required package change rather than wrapping its handler or calling it directly. Row/CAS writes,
reference advisory locks and authentication locks protect different predicates; none is a universal grant lock.

Recommended operation composition, subject to that lock-order qualification:

1. Authenticate the invocation outside the business write; map bounded typed input and original command identity.
2. Enter the owning transaction, acquire the qualified authority/reference participants before their protected
   reads, and freshly resolve actor/session/Permission plus target scope. A previous principal/preview is advisory.
3. Hold the exact installation policy selection/revocation and applicable Repository/reference generations;
   validate the full candidate against current required constraints. Unknown or changed required inputs hold.
4. Publish/restore/revoke writes only owned policy/revision/current-state/audit/original-result facts. In the
   separate Start use case, the same policy participant composes with claim/grant/reservations/dispatch instead.
   An independent inner commit, event subscriber or post-commit recheck cannot supply atomicity.
5. Commit once; external effects follow their owning durable intents. Lost acknowledgements resolve the original
