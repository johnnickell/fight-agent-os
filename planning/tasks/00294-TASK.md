# Enforce registered Feature checks outside HTTP Actions

## Outcome

Registered CLI, worker, direct-use and Agent/MCP boundaries enforce the same package Feature restriction before
protected work, alongside their existing caller/target/grant authorization. Discovery cannot advertise a Tool
that invocation would deny under the same current conditions; later calls and jobs recheck rather than reuse admission.

## Scope

- In scope: Extension of the shared runtime composition to registered non-Action boundaries, actual Common Tool
  availability/discovery/invocation composition, trusted principal lifecycle, safe failures and worker reuse.
- Out of scope: Another MCP server, registry, evaluator or auth owner; new worker/Workflow platform; borrowed
  credentials, unmanaged direct dispatch, runtime provisioning, UI/catalog, deployment or fake product Tools.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Enter a registered non-HTTP capability | Existing owning operation only after checks | Current owning authority, exact registered Feature and package availability | Only actual owning operation facts | Denial precedes protected handling/effects; direct alternatives cannot bypass the restriction |
| Discover Agent Tools | No business command | Existing Common registry with combined ordinary and Feature availability | No business event for enumeration | Filter before pagination/disclosure; no separate Tool list or stale availability snapshot |
| Invoke or continue a supported Tool | Existing Common invocation/continuation and owning use case | Fresh Feature read plus same request's qualified Agent snapshot and scope checks | Owning facts only after actual operation success | Gate before protected argument validation, restoration/consumption, progress and handling |
| Process another request/job | Existing owning dispatch after fresh admission | New trusted authority context, current Feature and original Permission binding | No Feature fact for checking | No previous principal, setting, cursor or continuation serves as later authority |

## Validation and permissions

Consume TASK-00293's shared package availability/persistence/error qualification and TASK-00290's single reference
registration source. Associate each supported entry with its declared Feature through the owning registration/
metadata boundary; do not maintain a second catalog, scan source during invocation or infer Features from names.
A method Attribute alone cannot intercept a direct call. Trace each alternative HTTP/CLI/worker/bus/Tool entry to
its actual server-side guard; unsupported dynamic/unregistered paths stay unavailable for staged rollout.

Keep business authorization in the owning Application/package use case, not solely a transport wrapper. Compose
Feature restriction at the protected entry before work without copying package handlers or inventing forwarding
command aliases. Do not turn ordinary unflagged operations into flagged ones for proof, or require every existing
operation to declare a Feature. A future real capability's owner must register and gate all its alternative paths;
this reusable boundary neither chooses that capability nor declares unimplemented paths covered.

Use each entry's qualified current caller/target/delegation/grant authority. A local operator flag, job payload,
remembered User ID, role name, browser `/me` snapshot or client-supplied principal is not a trusted principal.
Do not borrow a privileged User/Agent or fall back to anonymous evaluation when worker authority is unknown.
Only explicitly approved anonymous entry semantics may supply `null`; unsupported principal/entry combinations
remain unavailable. ON cannot bypass sandbox, Workflow, target, current Permissions or effect authorization.

Extend TASK-00245's existing Common `McpToolAvailability` composition by intersecting the package Agent all-required
Permission decision and bounded-use scope with package `FeatureAvailability`. This is actual cross-boundary
restriction, not a replacement policy or a renaming wrapper. Use the same Common registry and Tool identity;
foreign/same-named metadata cannot acquire another Tool's registration. Only qualified static metadata may be
reused; request-bound Tools retain their existing registry/catalog lifetime rules.

Use TASK-00242's exact same request-bound `CurrentAgentPrincipalProvider`, signed request and correlation as the
existing Agent gate. Reusing the resolved immutable snapshot causes no second authentication/nonce transaction.
Feature checks themselves are read-only; required authentication replay evidence remains the authentication
owner's separate effect. A failed or uncertain authentication never becomes an anonymous check. Browser JWT and
Agent HMAC remain separate without cross-scheme fallback or a newly exposed Agent-on-JWT route.

Apply the combined decision before Tool listing order/limit/cursor creation, mirrors or other protected metadata,
and again on invocation. Keep Common's private zero-TTL catalog semantics; a prior page/cursor is not authority
and catalog changes may invalidate continuation. For supported interactive retries, fresh authorization and
Feature checking precede protected restoration, response validation, confirmation consumption, resume and progress.
Do not claim to prevent minimal bounded protocol parsing/state opening needed to identify the selected Tool.
Unsupported interaction modes remain unavailable under TASK-00245, not implicitly implemented here.

Legitimate OFF/ineligible PREVIEW is a normal denial through the owning safe protocol/CLI failure contract, not an
HTTP 404 imposed on every transport. Conceal unknown/denied Tool details as Common requires. Unknown Features,
broken/mismatched bindings, malformed metadata and storage outages never silently become ON or policy false.
In particular an operational failure must not silently filter discovery into a successful empty/partial catalog.
Use existing sanitized protocol/diagnostic ownership; do not expose arbitrary exceptions, request bodies, signed
material or principal snapshots. Denied work must not validate protected arguments, run handlers or emit progress.

Every explicit check rereads current Feature and original bound Permission ID, including a reused worker/service
or multiple checks during one request. The authenticated principal stays an immutable snapshot within that admitted
request; new requests/jobs obtain fresh authority through existing owners. Do not cache a per-principal Feature
result, preserve revoked grants across jobs, substitute same-named Permission IDs or promise a distributed snapshot.
Committed setting changes affect subsequent reads, not retroactive cancellation of work already admitted.
