# Make bin build the complete read-only application gate

## Outcome

`./bin/build` is the thin sole canonical entrypoint into a deterministic, non-interactive, PHP-orchestrated, read-only application acceptance gate running in the already-started Docker Compose PHP service. Named phases cover locked dependency validation/install/audit, planning validation, PHP syntax, PHPCS using the Fight Common 1.2 standard, PHPStan, Deptrac, Rector dry-run, one all-suite PHPUnit/coverage execution, bounded frontend checks, and clean production-install/artifact proof with clear failures and warning disclosure.

## Scope

- In scope: Replace the one-off image build with a thin `bin/build` that validates the running Compose PHP service and invokes `docker compose exec -T web php scripts/build.php`; implement the named PHP phase orchestrator; explicit phase ordering/environment/cleanup; strict Composer/lock validation and production audit; locked backend/frontend installs; read-only planning validation; PHP syntax/PHPCS Fight Common 1.2/PHPStan/Deptrac/Rector dry-run checks; one all-suite backend PHPUnit/coverage run with guarded PostgreSQL; bounded frontend format/lint/type/test/coverage/build/Storybook/audit; clean production copy/install/autoload/assets/source contract; tracked-tree mutation detection; one-time seeded phase-failure proof; final evidence format and documentation of focused-versus-canonical use.
- Out of scope: Automatic source/planning formatting, dependency updates, merge/release/deployment approval, provider/network product tests, lowest/candidate lanes, scheduler enrollment, broad E2E automation, and silently accepting warnings or unavailable mandatory phases.

## Validation and permissions

`bin/build` contains only host-side preflight and delegation: it verifies that the Compose `web` PHP service is running, then uses non-interactive `docker compose exec -T web php scripts/build.php`. It does not build an image or start an ad hoc container on every invocation. A missing/stale service fails with an actionable instruction rather than silently changing the environment.

The PHP orchestrator owns named phase execution, exit-code propagation, timing/evidence summaries, and cleanup. It may use a pinned process capability to invoke tools, but must not duplicate orchestration in shell or add Python quality-gate scripts. Existing `./bin/planning-check` remains the authoritative planning phase and may retain its implementation language.

The gate runs from committed locks without implicit updates and never invokes `planning-check --write`, format fixers, source generators that alter tracked files, migrations against non-test databases, or commands that rewrite manifests/locks. It records starting tracked state and fails if tracked files differ afterward, while caches/reports/temp copies/databases stay under ignored/disposable paths.

Include strict Composer validity/platform/lock checks, approved Composer production audit, locked development install, and clean `--no-dev` production install. Include frozen frontend install and production dependency audit under explicit network policy. Audit/install are the only approved network-sensitive phases; product tests remain network-independent and advisory/network failures are not hidden.

Run read-only planning validation, PHP syntax lint, PHPCS using the standard shipped by locked Fight Common 1.2, PHPStan, Deptrac, and Rector dry-run. Then run one PHPUnit invocation containing all configured Unit, Integration, Functional, and guarded PostgreSQL-backed suites with coverage enabled; validate Domain/Application and Adapter coverage from that same report without rerunning any suite. Run each accepted frontend format/lint/type/Vitest/coverage/production-build/Storybook phase once, then prove clean production autoload/assets/startup/source/development exclusion. Order should fail fast without skipping evidence needed to diagnose.

`./bin/build` is canonical. Focused wrappers remain supported iteration tools but cannot be cited instead of the full gate and are not called as duplicate passes by the orchestrator. Seeded-invalid scenarios prove phase wiring during implementation in disposable TASK evidence; they are not recurring gate phases. The gate reports/fails; it cannot approve review, merge, release, or deployment.
