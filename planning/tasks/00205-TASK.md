# Start normal work from a Ready-card intent

## Outcome

An authorized person can request the same normal start as the terminal from a browser Ready → In Progress
pointer gesture or accessible keyboard equivalent. The card shows the **server-confirmed** Workflow and TASK
state or restores its authoritative place on refusal; a drag is never itself a claim or Planning status edit.
This is one independently reviewable browser-to-existing-start interaction.

## Scope

- Add a deliberate, permission-aware normal-start action to [TASK-00111](00111-TASK.md)'s canonical Ready
  view. A Ready-card gesture and keyboard alternative send one request to [TASK-00204](00204-TASK.md)'s
  existing server-authoritative selected-TASK/Triage/start path with the same actor scope, expected revisions
  and bounded single start intent. Do not introduce client-side eligibility, classification, base resolution,
  second normal confirmation or a generic drag-to-status mutation.
- Display advisory classification/fallback, an actionable material conflict disposition path, the resolved
  route/base and safe reason when current facts permit. Preflight/pending states are not execution evidence.
  Show authoritative accepted Workflow identity, dispatch/preparation/Needs Human/denied status and current
  claim/eligibility observation only after the server responds; on uncertainty inspect owning operation before
  offering another attempt. Keyboard, pointer and terminal requests use the same idempotent operation.
- Preserve TASK-00111's derived lanes and provisional interaction rules: cancel/denial/stale/conflict/network
  uncertainty restores the server view with accessible announcements/focus, never persists a local status or
  reorders the Board. Do not move blocked or incomplete TASKs into In Progress. This is the later supported
  start action, not a retroactive change to TASK-00111's no-generic-status-drag contract.
- Out of scope: browser Repository strategy editing, hotfix confirmation/repair, release/deployment,
  independent review or PR landing, new Workflow commands and extra approvals for normal work.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Request normal start from Ready | Send one authorized start intent through the same server operation as terminal | Inspect current canonical candidate, advisory classification/route and Workflow state | Existing authoritative start/claim facts, never a client-generated status event | One Workflow if accepted; local movement alone changes nothing |
| Explain denial or uncertainty | Reinspect authoritative TASK/Workflow/owner and safe reason | Get current eligibility, claim and request identity | N/A — read-only inspection | Restore/refetch server state; no duplicate request or fabricated success |
| Use keyboard alternative | Same bounded start operation | Same accessible status and focus target | Same owned effects as pointer request | Equivalent action for users without drag input |

## Validation and permissions

Hide or disable unsupported actions with truthful reasons, but rely on the same PHP authorization, canonical
eligibility and atomic claim revalidation as terminal; browser visibility, permission flags or gesture cannot
establish a grant. Include expected TASK, Planning/context, classification/disposition and configuration/catalog
revisions; a stale or conflicting request must not succeed based on old client data. Avoid leaking unavailable
TASK facts or base names to unauthorized viewers. Start does not itself mark Planning `done`, merge a PR,
release or deploy. Retain server operation identity across ambiguous responses and reconcile before retrying;
do not turn optimistic UI movement into a second start.

## Acceptance criteria

- [ ] Pointer and keyboard Ready intents reach the **same** server request and produce equivalent accepted,
  refused and duplicate outcomes as terminal without a second normal-work prompt.
- [ ] A card remains provisional through classification and start; only current authoritative Workflow/claim
  observations affect derived In Progress presentation. Refusal, cancel, stale context, conflict and network
  uncertainty restore/refetch server state with accessible explanations and focus.
- [ ] Ineligible/hidden or unsupported work cannot be started from UI, even if a client sends a forged gesture;
  PHP rejects stale/grant/base conflicts at the existing claim boundary.
- [ ] No client-side queue/eligibility/priority copy, generic status mutation, inferred emergency or release
  route, duplicate execution or extra Jev route-selection call is introduced.
