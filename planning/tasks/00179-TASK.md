# Refresh assessments after changes with qualified reuse

## Outcome

When an Engineer changes the review subject, the advisory report is rebuilt for the current base/head. Affected
units are reassessed, and unaffected results are reused only when exact evidence, relevant context and current
authority still match. Current coverage preserves the original provenance of reused answers and never counts
removed units as assessed current code.

## Scope

- Extend [TASK-00178](00178-TASK.md)'s actual handoff integration, unit mapping, rubrics and report using
  [TASK-00173](00173-TASK.md)'s qualified reuse mechanics. Reuse the same evaluator, source resolver, cache and
  authority contracts; no second cache service or new assessment policy. Remain on Pi 1.1.0.
- Inventory the current exact base/head and applicable maintained-unit eligibility anew before constructing the
  report. Detect changed review base as well as changed head. Stable path/name or identical unit text is not
  sufficient: changed surrounding code, dependencies, requirements, conventions or scope can change the judgment.
- Bind each candidate result to the complete evaluated evidence/context manifest, question/choices/anchors,
  preset/rubric/evaluator and relevant configuration, source/disclosure/consumer policy, current caller/session
  and repository scope. Revalidate actual source identities and access before returning derived metadata.
- Identify affected units from qualified deterministic mapping and tracked context/dependency identities. If a
  dependency or contextual influence cannot be established, treat reuse as ineligible and reassess with bounded
  sufficient context or report incomplete coverage. Do not claim exact semantic impact analysis from a diff alone.
- Reassess changed/affected units under unchanged shared budgets and stage ceilings. Reuse a valid unchanged unit's
  result only with adequate coverage for the current question and subject. A cached unknown/partial/N/A result
  cannot become a determinate complete score. A high score is not a freshness or correctness signal.
- Rebuild current assessed/partial/pending/excluded/unavailable coverage and dimension denominators from the new
  inventory. Remove disappeared units from current population while retaining historical reports under the owning
  evidence policy. Handle additions, renames, splits/merges and exclusions without accidental double counting;
  require proven identity before mapping an old result to a new unit, otherwise reassess or mark a gap.
- Label fresh and reused results separately. For reuse retain original evaluation identity, rubric/evaluator,
  timestamp and source/context provenance alongside current validation time and subject binding. Do not restamp
  an older judgment as a new evaluation or bill a cache hit as another provider call.
- Respect TASK-00173's initially bounded session-local metadata cache and its lifecycle/scope restrictions. Cache
  eviction, reload or cross-session/independent-review boundaries may require fresh assessment; a historical
  handoff report is not a persistent shared cache or authority to transfer the Engineer's private context.
- Account for actual local rereads/revalidation work, cache misses and new provider usage. Conservative reservations
  and unknown billing remain intact. Do not silently increase budgets, bypass admission, replay operations or
  repeatedly rephrase/reassess unchanged units to obtain a preferred score.
- Publish a coherent report only for its verified current subject and active attempt. On concurrent edits, changed
  base, cancellation or reload, invalidate affected pending delivery; preserve valid historical evidence with its
  original subject, not a mixture of old/new inventories masquerading as one assessed change.
- Preserve advisory failure handling. A changed subject with exhausted budget receives explicit stale/unassessed
  gaps and can proceed through normal handoff if required gates permit it. No score-only waiver, automatic code
  repair, formal review acceptance or failure-to-zero-score conversion is introduced.
- Exclude live observation caching, new analyzer/MCP/SQL execution, cross-principal/session result sharing, policy
  tuning and automatic publication. General source-result reuse stays with TASK-00173; this TASK supplies the
  change-subject impact/coverage integration rather than duplicating its implementation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Refresh an Engineer assessment | Start a bounded refresh for current base/head | Current inventory, affected context and reusable-result eligibility | New/reused/ineligible/gap observations | Authorized source checks, optional new provider requests and rebuilt report |
| Reuse an unaffected result | N/A: reuse itself is read-only | Exact evidence/context/policy match and current authority | Reuse observation with original provenance | No new provider call; bounded local revalidation |
| Reconcile removed or remapped units | Update owned report inventory | Current unit identities and historical mappings | Coverage update with exclusions/gaps | Current counts change; original historical evidence remains historical |
| Proceed with refresh gaps | Existing review handoff | Current subject, gap status and unaffected required gates | Explicit gap/handoff facts | No special advisor waiver or transferred review acceptance |

## Validation and permissions

Use actual current caller/source/disclosure scope before revealing a hit or reference. A historical score/report,
unchanged path or old permission does not establish current authority. Validate manifests and result identities
as untrusted inputs against the owning source/evidence capability. Reject unverifiable mappings and stale lifecycle
results; never manufacture full context coverage. Preserve TASK-00178's score semantics and specialized-consumer
boundaries. Source revalidation is bounded and does not grant unrelated repository or production access.

## Acceptance criteria

- [ ] A real Pi 1.1.0 changed-subject handoff rebuilds the current report, reassesses affected units and reuses a
  qualified unchanged result without another provider evaluation, with old and current provenance clearly separated.
- [ ] Changed base/head, requirements/conventions, surrounding/dependent evidence, rubric/evaluator/configuration,
  policy or current permission prevents inappropriate reuse even when the unit text is unchanged.
- [ ] Unknown impact/context coverage causes reassessment or explicit gaps, not speculative reuse. Additions,
  deletions, renames and split/merged units retain honest population and per-dimension counts without duplicates.
- [ ] Partial/N/A/unknown outcomes remain explicit, removed units do not count as assessed current code, and a
  historical report or another session's result cannot bypass shared cache/access restrictions.
- [ ] Concurrent edits, stop/reload, late results and exhausted budgets cannot publish a stale mixed-subject report,
  double-charge reuse, reset limits or block handoff solely because advisory refresh is unavailable.
- [ ] Representative refresh comparisons report actual hit/miss/invalidation rates, local revalidation work, missed
  context/concerns, coverage, total available cost and latency without assuming cache hits eliminate all reads.
