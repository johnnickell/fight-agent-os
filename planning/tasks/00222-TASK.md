# Qualify and preflight an exact application deployment target

## Outcome

A claimed release Workflow can determine whether one certified application artifact/commit and one named
production environment have a **qualified project-owned** deployment procedure, observable provider state,
required health checks and recovery options under the current bounded plan. A safe readiness result is
bound to exact revisions; unsupported, missing or changed inputs refuse before production mutation. This is
one independently reviewable preflight use case, not a generic deployer or a production enrollment.

## Scope

- Consume [TASK-00215](00215-TASK.md)'s immutable certified deployable artifact/digest or commit,
  [TASK-00216](00216-TASK.md)'s attributed effect plan and [TASK-00217](00217-TASK.md)'s human signing proof
  **only when** this project's policy requires signing (otherwise its qualified policy-based N/A). Resolve
  [TASK-00212](00212-TASK.md)'s exact application runbook, Repository, versioned environment/provider
  identity, release line, artifact storage, rollout mode, named health criteria, budget and rollback/forward
  options. Inspect the actual provider's current target state and prior same-Workflow intents; do not infer a
  clean production environment from a successful local build or a PR landing.
- Establish a narrow supported adapter/observation contract for the selected project and environment:
  distinguish provider identity, current rollout/artifact, ready/partial/unknown state and trustworthy
  observations. Qualify actual procedure/permissions/health and rollback support using project-owned tools
  before enabling effects. Return typed unsupported, stale, conflicting or unavailable reasons rather than
  constructing shell commands from runbook prose, accepting an arbitrary endpoint or choosing a fallback
  deployment platform. Team Lead coordinates inspection and the human decision; it cannot obtain Release
  Manager credentials or treat preflight as effect authorization.
- Record an attributed current preflight/blocked fact on the existing release Workflow with exact TASK,
  certification, runbook/context, environment and plan revisions, health/rollback policy and observed
  provider identity. Preflight is not an independent queue, second readiness authority or durable production
  effect. [TASK-00223](00223-TASK.md) must revalidate all authority and currentness again before an effect.
- Out of scope: actual rollout, health success or rollback ([TASK-00223](00223-TASK.md) and
  [TASK-00224](00224-TASK.md)), branch follow-through/closeout ([TASK-00225](00225-TASK.md)), tag/GitHub
  publication and another release TASK per deployment stage.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preflight exact target | Scoped same-Workflow confirm/preflight operation | Certified artifact/commit, signer requirement, current policy, named environment, plan and live provider state | Attributed readiness or blocked fact with versions | An inspectable decision; no production mutation or claim |
| Explain unavailable or changed support | N/A — permission-scoped inspection | Qualified provider/runbook identity, target, required health/recovery checks and safe exclusion | N/A — inspection grants nothing | Concrete next action without leaking provider credentials |

These are application-owned interactions consuming the existing Workflow, not commands for a universal
production platform.
