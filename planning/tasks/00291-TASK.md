# Provision missing Features atomically through protected operations

## Outcome

An authorized operator can provision only missing candidate Feature definitions as OFF through the package's
one-transaction command. Existing settings survive, and all relevant reference writers and managed-policy removal
share qualified final-write integrity. Provisioning completion is not preparation, runtime access or deployment.

## Scope

- In scope: Protected synchronous operator entry, exact candidate/target/default composition, direct package
  command, existing repository/reference integration, safe outcomes and actual PostgreSQL concurrency evidence.
- Out of scope: Another schema/repository system, Permission creation or generic CRUD, Feature management UI,
  runtime auto-provisioning, new availability policy, deployment, retirement and complete Agent enablement.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Provision exact candidate | Package `ProvisionFeatures` | Complete CANDIDATE discovery; authoritative Feature and required default Permission lookups | `FeatureCreated` only after commit for new records | All missing names commit OFF together; existing state remains unchanged |
| Reject unsafe reference changes | Existing owning Feature/Permission/Role/Agent writes and `ReconcileManagedPolicy` | Complete expected state; unpaginated `hasFeatureReference`; managed-policy preview | Owning facts only on actual committed success | One fenced winner, or rollback without partial reconciliation/provisioning |
| Reconcile uncertain provision | New explicit bounded authorized pass after fresh inspection, never blind internal replay | Fresh discovery and committed catalog state | No recreation/replay of existing records' creation facts | Preserve winners and create only still-missing names; unresolved outcomes stay truthful |

## Validation and permissions

Compose `ProvisionFeaturesHandler` directly through the existing Common command bus and canonical
`DoctrineTransactionalUnitOfWork`, sharing the EntityManager/DBAL connection with all participating repositories.
Do not wrap the handler in an outer transaction, copy provisioning policy into SQL/CLI or use repository/event
side effects for extra business behavior. Reuse TASK-00126's implemented Feature storage and reference fences;
complete demonstrated integration gaps rather than rebuilding that foundation or creating a proof-only TASK.

Reuse TASK-00036's protected local operational approach, with explicit current trusted operator, intended target,
selected immutable candidate identity and bounded scope. Configure/verify actual database identity and least
privilege before writes; do not silently repoint a development/test wrapper to another environment. A CLI flag,
managed role name, testing Permission, Feature being ON or a proposed deployment is not authorization. Protect
all exposed bus/service entry paths; no web, worker or Agent exposure follows merely from handler registration.
Resolve code identity in the actual candidate composition; queued dispatch alone cannot pin it. Record source/
lock and operational authority separately from product management Permission ownership in TICKET-00073.

The package requires complete CANDIDATE discovery before its transaction, and creates each missing definition
with its owning ID factory, strict name, selected existing Permission ID, OFF and revision 1. Pass configured
`DEFAULT_FEATURE_PERMISSION` as the package's nullable raw string, not a caller-selected grant. It is validated/
resolved only when a missing name needs creation. Empty discovery or all-existing names accept unused absent or
malformed defaults according to the package; do not add unconditional startup validation that changes that rule.
A changed default affects only later new records. Never reset, repair, delete or rebind existing/unreferenced rows,
including an existing broken definition. Provisioning creates no Permission, Role membership or Agent grant.

Qualify the existing shared transaction-duration Permission-reference fence across Feature add/replace/remove,
Permission removal/reclassification, Role/Agent reference writes and managed-policy preview/reconcile. All relevant
participants use the same connection/protocol and final expected-state comparison, not an advisory preflight.
Preserve full immutable identity/name/binding/status/positive-revision tuples, valid no-op checks, exact revision
advancement, canonical uniqueness and fresh committed reads. `hasFeatureReference` is an unpaginated existence
check over every status, not first-page listing. Permission removal rejects remaining Role, Agent or Feature
references; managed-policy failure rolls back all other changes in that pass.

Preserve package tiers: a Feature may bind any existing eligible Permission tier, including SUPER_ADMIN_ONLY;
that reference does not grant it to an Agent or change protected promotion/delegation rules. Missing IDs cannot
be replaced by same-name Permissions. Preserve applicable cohort-first ordering on authority-changing participants
as TASK-00227/00228/00231 establish it, without making this independent Feature use case depend on a fully live
Agent runtime or silently enabling unavailable Agent operation contracts. No second fence/epoch authority is added.
Future writers consume this protocol and must supply their affected race evidence before exposure.

Retain READ COMMITTED/fence ordering and final constraints from ADR 0002 and the implemented reference adapter.
Competing provisioners may conflict; the losing pass must roll back all its inserts without overwriting the winner.
After failed/uncertain transactions discard stale transaction-local state and closed EntityManagers; a fresh
invocation reads authoritative state. No unlimited retry, upsert-to-OFF or name-based replacement is permitted.

The handler returns `void` and publishes `FeatureCreated` best-effort after commit. A lost acknowledgement or
publisher exception does not establish rollback. No event receipt, normal return or count proves preparation.
Do not add a replay ledger, outbox or event-recovery worker: these notifications are not required durable effects.
The package's `CommandFailedEvent` can carry the original command/error message even after commit; contain it
within trusted handling and prevent generic logging/transport from serializing arbitrary errors/configuration.
Use fixed safe diagnostic categories and meaningful exit outcomes; do not claim exact original creation from a
later existence lookup. Explicit repeat consults storage and never republishes existing creation facts.
