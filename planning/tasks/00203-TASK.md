# Configure and preview Repository branching and normal routes

## Outcome

An authorized Repository manager can set, preview, inspect and restore an explicit versioned branching strategy
and route bases/targets for one Repository. A versioned initial catalog resolves `feature`, `bugfix` and `chore`
to the existing Team Lead → Software Engineer Workflow without a second model call. This is one independently
reviewable configuration-to-preview path; it does not start work.

## Scope

- Extend [TASK-00081](00081-TASK.md)'s typed Repository configuration, immutable revision, preview, restore,
  audit and permission paths with GitFlow, trunk-based or explicit custom strategy and named normal/hotfix route
  base/target mappings. Resolve the current effective values through [TASK-00082](00082-TASK.md)'s context
  snapshot and show safe provenance/impact to an authorized manager. Existing sessions keep their bound snapshots;
  changed selections invalidate outstanding unbound preflight/Start intents rather than silently retargeting work.
  Future-only publication does not itself stale an already-pinned run; TASK-00084/00341 still guard genuine bound
  input drift and current revocation.
- Version an initial deterministic catalog for supported `feature`, `bugfix` and `chore` classification to the
  same standard Team Lead → Software Engineer Workflow, with category-specific guidance only within that
  Workflow. Verify configured source base/target identity against current Repository/Git evidence at resolution;
  ordinary GitFlow commonly uses `develop` and hotfix commonly uses `main`, but neither name is a default
  authority. Missing, contradictory, inaccessible or changed bases are safe unsupported/blocked outcomes.
- Provide a scoped preview of effective strategy, catalog revision and route bases/targets before an authorized
  revision/restore. The hotfix production base is **configured here**, while emergency confirmation, claims and
  execution belong to [TICKET-00053](../tickets/00053-TICKET.md). The future release kind/route is excluded.
- Do not infer policy from Jev, TASK prose or branch-name convention. No configuration write starts a Workflow,
  creates a Git branch, grants a role or changes an existing claimed Workflow.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview and revise Repository strategy | Reuse authorized versioned Repository configuration revision | Read effective strategy, bases/targets, catalog identity and expected revision | Existing attributed configuration-revised fact on successful write only | One immutable validated revision and safe preview; no branch or Workflow |
| Restore a prior route configuration | Reuse authorized append-only configuration restore | Compare prior/current policy against live restrictions and Repository identity | Existing restoration fact on success | A fresh validated revision; historical snapshots remain immutable |
| Resolve a normal route | N/A — read-only deterministic resolution | Current supported category, context/configuration/catalog revisions and verified base | N/A — resolution alone emits no Workflow event | Typed supported route or safe reason; no claim, Jev call or change to TASK priority |

These describe behavior, not new message names or a second configuration authority.

## Validation and permissions

Require TASK-00081's separate `READ_REPOSITORY_CONFIGURATION`, `REVISE_REPOSITORY_CONFIGURATION` and
`RESTORE_REPOSITORY_CONFIGURATION` rights as applicable, plus current Repository access for either a human or Agent.
A manager label, profile, prompt, Agent-authored input or local instruction cannot widen policy. Policy sections
consume TASK-00496's permitted override/composition validation and TASK-00081's atomic revision/audit/original-result
path; no parallel policy endpoint, implicit membership or new management Permission is introduced. Validate strategy
and closed route mappings, branch patterns, Repository lifecycle, live base identity and revision before persisting or exposing effective
routes. Reuse existing compare-and-append/restore contracts; an outdated revision or now-invalid prior mapping
fails safely. Catalog identity is versioned and retained for start validation, not an Agent-editable config blob.
A route preview cannot claim eligibility, start authority, hotfix status or a completed Git effect. Do not
require the normal route to be present for every unrelated Repository operation; report unsupported affected
routes rather than guessing fallback branches.

## Acceptance criteria

- [ ] An authorized manager previews and appends/restores GitFlow, trunk or explicit custom mappings with
  attributed immutable revisions and effective route/catalog provenance; stale and forbidden changes refuse.
- [ ] Each supported normal category deterministically resolves to the same approved Team Lead Workflow;
  `bugfix` is a routing label for Planning `bug`, not a new kind. No extra Jev route question is invoked.
- [ ] Normal and hotfix bases/targets are explicit and independently checked; missing, conflicting or changed
  branch evidence never defaults to `develop`/`main` or silently retargets a bound session.
- [ ] Preview/configuration changes do not grant a start, change TASK metadata, create a branch or affect
  existing Workflow state. Release remains unsupported here.
