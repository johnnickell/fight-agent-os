# Remove first-party trust and reconcile owned cleanup

## Outcome

An authorized user explicitly removes one first-party origin, stops subsequent affected use and reconciles its
owned cache/credential cleanup through existing owners, with pending work visible and secret-free history intact.

## Scope

- In scope: Exact expected-state origin removal, current-use/enrollment coordination, bounded original-outcome
  recovery and cache/credential owner composition with truthful partial/complete results.
- Out of scope: Another credential issuer/sink/queue, raw-key access, immediate physical key destruction, deleting
  shared holders/successor credentials, database resource purge, automatic re-enrollment and a new session engine.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Remove exact first-party origin | Explicit expected-state removal through owning Harness authority | Current binding/generation, actor scope, affected owned entries and lifecycle status | Owning trust/removal facts and existing credential revocation facts only | Subsequent use denied; exact owned cleanup is requested through its owners |
| Reconcile interrupted removal | Existing original cleanup/revocation operations only under current authority | Exact original removal, independent current authority/cache/credential outcomes | Existing confirmed facts, not duplicate success events | Bounded progress or truthful pending/unavailable state |
| Inspect safe result | N/A — authorized read | Separate trust-disabled, use-denied, cache-cleaned and credential-cleanup states | N/A | Complete only when required owning outcomes are actually confirmed |

## Validation and permissions

Consume TASK-00333's exact trust binding transitively through the loader/cache chain and TASK-00337's scoped cache
fences/removal. Require explicit current intent, target installation/origin and expected generation; a hostname,
client-supplied path, cached receipt or another connection's ownership grants no removal authority. Inspect only
necessary authorized metadata. Preserve unrelated connections, protected shared holders and secret-free evidence.

Disable affected future trust/use through owning controls before describing removal as effective. Coordinate
TASK-00243's current enrollment/activation hold and TASK-00237's actual credential revocation where authorized;
TASK-00244 continues to enforce current use. Distinguish denial of subsequent admission from already-admitted effects,
which retain their separately qualified stop/cancellation windows. Do not claim database rollback recalls a prior
network/provider effect or erase a live session's history to manufacture shutdown.

Reuse exact original lifecycle identities and TASK-00240's maintenance/cleanup rules. A current delivered credential
is not eligible for sink erasure; revocation and original retention/grace/terminal eligibility precede protected
cleanup. Do not bypass that policy by deleting keyring entries directly or equating local handle removal with
revocation. If authority, store or retention policy prevents completion, report pending cleanup and retain enough
safe original provenance to resume. Shared/current successor material must not be removed to satisfy this origin's
cleanup. Physical key/backup destruction remains separately authorized owner work.

Origin/cache generations fence late fetches and writes; interrupted or restarted stale work cannot repopulate removed
content or restore trust. Re-enrollment is a new explicit choice and cannot make old removal target a new generation.
Coordinate actual outside-transaction filesystem/store effects with bounded durable owning outcomes, not an invented
second queue or a transaction wrapped around package handlers. Lost acknowledgement is uncertainty, not rollback;
reconcile the exact original operation before retry and never rotate/provision a replacement to recover removal.

Cache deletion removes only owned disposable bytes; immutable database resources, manifests/provenance required for
history and permitted secret-free session/audit records survive. Current access still controls retained evidence.
Safe views distinguish partial states, stale/denied intent and uncertain effect; no credential bytes, handles, private
paths, raw transcripts or arbitrary provider errors enter output. Reading status never retries cleanup automatically.

## Acceptance criteria

- [ ] Actual explicit removal targets the exact authorized origin/generation and denies subsequent affected use,
  preserving unrelated connections, current successors and retained secret-free history.
- [ ] Cache cleanup fences delayed/restarted writes and removes only owned entries without path escape or stale
  generation resurrection.
- [ ] Revocation/enrollment and eligible credential cleanup use existing lifecycle owners; retention/authority/
  storage holds remain visibly pending and are never bypassed by direct secret-store deletion.
- [ ] Interrupted removal, lost acknowledgements, concurrent replacement/re-enrollment and stale completion
  reconcile original outcomes without duplicate issuance, accidental successor cleanup or false full success.
- [ ] Actual in-flight limitations and partial/complete results are inspectable without secret disclosure; no
  database resource purge, global configuration reset or automatic re-enrollment occurs.
