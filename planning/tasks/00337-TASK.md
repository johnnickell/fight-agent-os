# Reuse verified cached content safely

## Outcome

Users can reuse previously verified first-party Skill content across reads/restarts and understand offline limits,
without allowing cached bytes to become trusted filesystem Skills, a stale access grant or new runtime authority.

## Scope

- In scope: Bounded on-demand persistent origin-separated cache, immutable or rehashed content, restart recovery,
  truthful offline states, current authorized cached disclosure and exact cache-generation/cleanup participation.
- Out of scope: Another resource authority, eager mirroring, generic cache service, session/transcript storage,
  credential storage, automatic trust enrollment and final origin/credential removal orchestration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Retain a verified fetched file | Host-owned bounded cache population after actual verification | Exact origin/revision/manifest/content key and current cache generation | Safe cache observation, no Domain resource revision | One isolated verified entry, never filesystem Skill publication |
| Reuse exact cached content | N/A — current authorized content read | Exact held identity, verified cache integrity and current access/trust | Safe read/verification observation only | Exact bytes or visible unavailable result; no network/source fallback |
| Recover after restart/offline | Existing authorized loader/reconnect flow | Held provenance, cache integrity, current authority availability and missing entries | No new trust or selection fact merely from recovery | Reuse only within accepted availability rules; explicit misses/holds |
| Participate in origin cleanup | Exact owned cache fencing/removal capability for TASK-00338 | Current origin/cache generation, owned entries and late writes | Safe bounded cleanup observations | Prevent stale repopulation and expose truthful owned cleanup state |

## Validation and permissions

Consume TASK-00336's actual verification and held origin/revision/manifest identity. Cache keys include host-assigned
origin, immutable revision/manifest and content identity; aliases, filenames and transport hostnames alone are
insufficient. Populate only demanded files after verification. Storage is host-only-writable and immutable or every
access rehashes raw bytes; partial/modified/mismatched entries never reach model context. Keep entries outside all
Pi filesystem Skill discovery and preserve their MCP origin classification across restart/disconnection.

Cache is disposable, not authoritative resource history or a credential store. Bound total storage, individual
files, concurrent writes/reads and recovery work; do not eagerly mirror catalogs or silently fetch another origin,
revision or local file on a miss. Eviction affects only owned disposable entries and does not delete database bytes,
active retained evidence or unrelated files. Validate paths and ownership before any deletion; no broad recursive
cleanup of caller-supplied directories.

Recheck current resource access, delegated scope and exact origin before every new protected cached disclosure.
A digest, prior allow or cached metadata cannot authorize use. Offline already-loaded/verified content is reusable
only within the owning availability/current-authority rules; if needed authority is unavailable, deny the protected
read/effect rather than claim an offline grant. Existing model context is not magically recalled. Separate historical
loaded content, an exact verified cache hit, missing bytes, unavailable authority and revoked access in diagnostics.

Preserve exact held selection through restart; cached newer content cannot refresh an active snapshot. Reconnect
and meaningful drift remain with snapshot/session owners. No new session or acceptance ceremony is manufactured
for an unchanged valid reconnect. Keep credentials, private paths, source bodies and arbitrary transport errors out
of routine output. Cached content does not authorize provider disclosure or local execution.

Provide exact origin/generation-scoped cleanup participation for TASK-00338: removing/revoking an origin fences late
fetch/write completion, and resumed stale operations cannot resurrect removed entries or trust. External cache effects
stay outside business transactions, with honest uncertain outcomes and bounded original-state reconciliation. Do not
create a second workflow/queue or perform credential lifecycle operations here.

## Acceptance criteria

- [ ] Real demand-only cache population and exact reuse preserve origin/revision/manifest identity across restart,
  outside all filesystem Skill discovery, with no content/credential authority inferred from storage.
- [ ] Actual tampering, partial writes, changed manifests and path/ownership violations reject safely before
  disclosure; immutable protection or rehash-on-every-access is qualified on the supported host.
- [ ] Offline hits/misses, denied/revoked access and authority outage are distinct; retained bytes cannot bypass
  current scope or silently substitute a local/remote revision.
- [ ] Restart/reconnect preserves exact held selection and historical evidence without in-place active refresh.
- [ ] Origin cleanup can fence late writes and safely remove only owned entries; uncertainty remains visible
  without resurrection, broad filesystem deletion or credential mutation.
