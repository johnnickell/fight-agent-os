# Publish the project-required hosted library release

## Outcome

When the qualified library runbook requires a GitHub release, Release Manager can reconcile a matching
preexisting draft or publication and carry an approved release through notes/assets, draft and publication
as **distinct observed effects** of the same release Workflow. A remote tag alone, accepted API request or
draft is not a published release. Projects without hosted-release requirements receive a qualified,
explicit N/A rather than an invented GitHub effect.

## Scope

- Consume [TASK-00218](00218-TASK.md)'s verified remote tag object and peeled commit,
  [TASK-00215](00215-TASK.md)'s certified candidate, [TASK-00216](00216-TASK.md)'s exact bounded effect list,
  and [TASK-00212](00212-TASK.md)'s project-owned library runbook. Resolve the **qualified** source host,
  release/version/line, tag identity, existing release/draft ID, notes provenance, prerelease/latest policy,
  required assets and digests and immutability rules. Confirmed not-found differs from authentication,
  throttling, transport or ambiguous response; no assumed universal GitHub release or public asset bundle.
- On a project requiring GitHub, Release Manager uses only its own current direct host Permission and the
  specific approval for creation/reconciliation and publication. Record durable identities/intents and
  separately verify draft, asset inventory and final published provider state. Prepare notes from reviewed
  project material and verified facts, not from secret receipts or claimed future effects. Do not let a
  host create a tag implicitly; revalidate the exact existing remote tag before each named effect. Before
  publication inspect required assets and their hashes/public suitability; do not overwrite an immutable
  release, replace assets, publish a conflicting version, change provider settings or expand the effect list.
  Distinguish existing matching published release, matching draft and conflicting/unknown host state.
- Use the same Workflow's effect identities to inspect provider state and reconcile lost responses before
  retrying. A successfully created draft still needs a *separate* verified publish step where policy
  requires publication. A single [TASK-00216](00216-TASK.md) human approval may already enumerate both
  supported steps; do not prompt routinely between them while still current. Revocation, changed commit,
  release notes/assets, target, checks or grant stops and may require new bounded human approval. Record a
  published-but-unverified outcome honestly and keep this release TASK open for recovery.
- Where the qualified project policy has no hosted release, record a safe policy/version-bound N/A for this
  phase and verify the actual required tag-based publication facts; N/A cannot substitute for a required
  release or create a generic non-GitHub publisher. Out of scope: registry/consumer qualification
  ([TASK-00220](00220-TASK.md)), branch follow-through/closeout ([TASK-00221](00221-TASK.md)),
  autonomous PR approval/merge and application deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect existing hosted state | N/A — read-only inspection | Qualified policy, remote tag, host release ID, draft/published state, notes/assets and current grant | N/A — observation alone is not publication | Matching draft/published, confirmed absent, conflict or unknown result |
| Prepare draft and assets | Existing scoped same-Workflow effect operations where approved | Recheck host, tag, assets/digests, grant, Permission and prior intents | Distinct durable draft/asset intent and verified result or blocked fact | Only named draft/asset effects, not implicit tag creation or public release |
| Publish and verify | Existing scoped publication effect under same bounded grant | Current draft/asset evidence, live authority, tag and provider state | Separate publish intent, observed published state or unresolved fact | Exact approved public release/URL only after verified provider evidence |
| Skip non-required host | Policy-scoped disposition, no provider command | Current qualified runbook and verified required tag publication | Explicit N/A with policy revision, no false publish event | No GitHub effect for tag-only project |

These names describe observable Workflow stages, not a universal host API or blanket publication authority.

## Validation and permissions

Revalidate same-TASK Workflow/claim, exact certified tag/commit, current host/runbook configuration,
Release Manager direct Permission, approval for each exact effect, limits and expected state before every
mutation. Team Lead may coordinate but cannot publish by role inference; ordinary `land` grant does not
authorize a library release. Durable effect intent commits before external provider calls, outcomes after
commit and observation; uncertain effects cannot auto-retry or claim success. Block conflicting host/release,
unknown/missing permission, unqualified provider, unchecked private asset, changed notes or prerelease/latest
choice outside grant, immutable state and revoked/stale authority with safe reasons. Credentials, raw host
errors and private receipts stay out of messages and public release assets.

## Acceptance criteria

- [ ] For a qualified GitHub-runbook project, an exact remote tag, current approvals/direct Permission and
  matching notes/assets allow separately verified draft and publication; a draft, queued call or tag alone
  never counts as a published release.
- [ ] Matching existing draft or publication is inspected and reused; conflicting tag/release/assets,
  unclear not-found, immutable-release state and unknown provider response stop without duplicate creation,
  overwrite, implicit tag creation or unsupported side effect.
- [ ] Required assets, prerelease/latest status, release ID/URL and public provider state are verified against
  policy; incomplete verification remains visible and blocks final release completion.
- [ ] A library policy with no hosted-release requirement records an explicit qualified N/A and performs no
  GitHub mutation; downstream registry and branch checks remain independent.

## Verification and evidence

Test owned effect/permission decisions, draft-versus-published, no-host N/A, wrong tag/remote, asset drift,
immutable conflict, disabled host, lost response and duplicate publication with focused Application/API,
PostgreSQL effect-consistency and significant host-adapter contracts. Qualify installed GitHub/host API,
authorized disposable draft/publication and actual asset visibility with owning tools; controlled fixtures
are not proof of a live release. Do not product-test CLI flags, instructions, configuration, migrations or
test infrastructure. Run focused checks and `./bin/build`; record fresh counts/exits, actual host IDs,
warnings and deferred proof. Independent review/delivery remain separate.
