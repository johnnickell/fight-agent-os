# Establish the production-like HTTPS security envelope

## Outcome

All completed browser journeys run inside one production-like security envelope with explicit reversible trusted local HTTPS, mandatory HTTPS and validated proxy/origin assumptions elsewhere, same-origin API delivery with CORS denied, compatible CSP and standard response headers, and fail-closed production startup validation for every signing, encryption, CSRF, cookie, provider, canonical-origin, and rate-limit control.

## Scope

- In scope: Pinned local TLS/proxy tooling and repository wrappers; local certificate/trust setup/status/removal documentation; same-origin application/API routing; production HTTPS/proxy/origin enforcement; CSP and standard security-header policy/middleware; sensitive cache/referrer policy; CORS deny behavior; environment-scoped Storybook/Swagger/catcher exceptions; consolidated typed secret/security/rate configuration validation; production-like startup checks; HTTP-observable TLS/header/cookie/CORS/security behavior tests and operator documentation.
- Out of scope: Public certificate/production reverse-proxy enrollment, deployment, DNS, production mail-provider enrollment, cross-origin clients, broad infrastructure automation, weakening journey-owned request controls, secret generation/storage service, and release certification.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Enroll local HTTPS trust | Repository setup/status/remove wrappers | Inspect supported local trust tool, generated cert scope, and hostnames | N/A — no domain event | Explicit user trust is installed/reported/reversed; private CA/key remains untracked and user-controlled |
| Start secure local stack | Repository run wrapper | Validate local certificate, origin, proxy, application and catcher configuration | N/A — no domain event | Browser reaches same-origin application/API with Secure-cookie behavior over trusted HTTPS |
| Start production-like mode | N/A — composition/startup | Validate HTTPS origin/proxy trust, keys/secrets, cookies, provider capability, limit policies and environment exceptions | N/A — no domain event | Unsafe/missing/default/weak configuration prevents serving requests |
| Serve browser response | N/A — HTTP middleware | Resolve route/environment-specific CSP, cache, referrer, transport and standard header policy | N/A — no domain event | Application/API receives compatible restrictive headers; unapproved cross-origin requests remain denied |

## Validation and permissions

Select and pin a supported local certificate/trust mechanism and TLS termination path compatible with repository Docker wrappers. Enrollment must be opt-in, show exact trust scope/hostnames/files, never require hidden privilege escalation, and provide status/removal/cleanup. Generated CA private keys, leaf keys, certificates, credentials, and machine-specific trust state remain ignored outside tracked source. Record platform/browser limitations honestly.

Use one canonical configured HTTPS origin for browser/application/API links and same-origin requests. Validate scheme, normalized host, optional approved port, path policy, no userinfo/query/fragment, and trusted proxy topology. Never trust arbitrary `Host`, `Forwarded`, or `X-Forwarded-*`; configure explicit proxy sources/hops. Production-like composition refuses insecure origin/proxy/cookie combinations before serving. Edge redirect policy for safe navigation and application rejection of insecure sensitive mutations must be explicit and tested.

Keep CORS disabled/deny-by-default: no wildcard/reflected origins or credentialed cross-origin API. Handle preflight and absent/malformed Origin consistently with accepted browser-auth ADR. Development tools use separate explicit composition/routes/origins and cannot broaden production API policy.

Define a route-compatible CSP from actual production assets with at least restrictive `default-src`, `script-src`, `style-src`, `connect-src`, `img-src`, `font-src`, `object-src`, `base-uri`, `form-action`, and `frame-ancestors`; use nonces/hashes or self-hosted static assets rather than broad `unsafe-inline`/`unsafe-eval` unless a narrowly evidenced transitional exception is separately recorded and blocking for closure. No mutable remote runtime resources. Add compatible content-type sniffing, referrer, permissions, framing, transport, and cross-origin isolation/resource headers where they do not break approved behavior. Apply HSTS only under safe HTTPS/environment semantics. Sensitive API/HTML routes use explicit no-store/private policy.

Keep Storybook, mail catcher and browser test hooks narrowly environment-scoped, authenticated/restricted as
previously required, and absent/inert in production-like composition. Swagger has a separately approved
**exact allowed-environments set** owned by [TASK-00154](00154-TASK.md), initially `["local"]` for this project;
production and `test` require deliberate opt-in, both guarded viewer/bootstrap and private OpenAPI document
require current `READ_SWAGGER` (`SUPER_ADMIN_ONLY`) under [TICKET-00010](../tickets/00010-TICKET.md), and Try
it out retains real endpoint authority. A production-enabled viewer is **not** permission to expose other
developer tools or weaken normal application CSP, headers, CORS, same-origin, no-store or credential controls.
Permission and APP_DEBUG never substitute for the environment set. Safe optional debug may follow independently
strictly parsed APP_DEBUG outside local, but exact APP_ENV=`prod`/`production` with APP_DEBUG=true **fails startup**;
false suppresses it, and redaction applies everywhere. Preserve [ADR 0004](../adr/0004-client-authority-and-runtime-state.md)'s
narrow public booleans, not raw environment values. This TASK verifies integrated policy without introducing
Swagger serving or broadening other development-tool eligibility.

Consolidate typed startup validation for JWT signing/key rotation, delivery encryption, CSRF, cookie names/scope/security, canonical app/mail origins, provider capabilities, trusted proxies, CSP nonce/hash inputs, and all required limiter policies. Reject absent/default/placeholder/malformed/weak/duplicated/incompatible values without printing them. Verify configured limits exist for login, activation, reset request/completion, refresh, invitation issuance, retry/resend/correction, and other approved delivery actions, while journey TASKs retain behavioral ownership.

No runtime permission grants access to infrastructure configuration. Startup/headers are enforcement, not evidence of endpoint authorization.
