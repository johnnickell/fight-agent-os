# Adopt React-Bootstrap for standard frontend controls

## Outcome

Use React-Bootstrap for standard UI mechanics while retaining owned components only for application meaning,
repeated compositions or additional behavior. Adapt existing controls without changing their accepted
interaction/accessibility contracts or selecting a final visual language. This is a separate follow-up to
[TASK-00148](00148-TASK.md), not a component refactor hidden in its formatting and SCSS migration.

## Scope

- In scope: Qualify and pin `react-bootstrap`; adopt its applicable primitives in existing buttons, fields,
  notices and loading/state compositions; preserve meaningful owned contracts; update affected tests/stories
  and small owned SCSS partials; document the standard-control selection rule.
- Out of scope: Adding product journeys or unused control galleries, wrapping every library export, migrating
  application state/transport/form libraries, Bootstrap imperative JavaScript, a new theme or brand, wholesale
  dependency upgrades, new broad end-to-end suites, upstream-library testing and combined-gate integration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Activate an existing ready/busy/disabled control | Existing client callback | Read props and native/ARIA state | Client-only input | Ready activates; busy suppresses action/submission while preserving focus; disabled remains unavailable |
| Enter and validate an existing form field | Existing caller-owned change/submit callback | Read label, help, error and value | Client-only input | Labels/descriptions/ref/focus and rejection/recovery remain observable; no automatic save or network call |
| Present status or content state | N/A — presentation | Read caller-owned loading/empty/error/success state | N/A — no domain event | Status urgency and text remain explicit; retry requires an explicit user action |
| Select a standard control for future work | N/A — engineering convention | Determine whether React-Bootstrap already owns the UI mechanics | N/A — no runtime effect in this TASK | Use the library directly unless an owned component adds a documented contract |

## Accepted conventions

Prefer React-Bootstrap for standard buttons/forms, alerts/spinners, accordions/collapse, modals/offcanvas,
dropdowns, tabs/navigation, tooltips/popovers and similar library-supported mechanics. Use supported React
APIs and controlled/uncontrolled contracts, not Bootstrap's imperative JS plugins or `data-bs-toggle` wiring.
Bootstrap SCSS supplies appearance; React-Bootstrap supplies React component behavior.

Do not implement every named control in this TASK. Accordions and other presently unused controls receive
catalog examples and relevant keyboard/focus/state checks when adopted for an actual scoped use case. No
speculative `Accordion`, `Modal` or generic control wrapper merely renames the package's API.

Assess each existing owned component by responsibility:

- `Button`: retain the meaningful busy-label, focus-retention and activation/native-submission suppression
  contract over the appropriate library button; avoid a second implementation of ordinary Bootstrap styling.
- `forms/TextField`: retain label/help/error association, unique IDs, caller ref and validation ownership while
  using applicable library form primitives. Do not introduce Formik, a validation framework or remote submission.
- `Notice`: preserve explicit polite/assertive/off announcement behavior, urgency, atomicity and non-color-only
  meaning when using the library alert. Library defaults must not silently change every notice into an alert.
- `ContentState` and `ContentPanel`: keep application-relevant composition, loading/empty/error/success and
  explicit-retry contracts. Use appropriate existing library primitives without replacing semantic structure
  with layout-only markup or adding wrappers that contribute no behavior.

Use direct supported package imports for standard controls at their actual point of use. Do not create a
local barrel/registry facade for the entire library. Extend the existing production-backed stories rather
than inventing parallel example implementations.

Owned styling follows TASK-00148: separate `client/styles/`, thin SCSS composition, small component/layout
partials only where needed, runtime semantic CSS variables, shallow class selectors and singleton-ID layout
rules confined to their owner. Prefer supported Bootstrap Sass variables/custom properties over selector
escalation. Keep component styling overridable by a future theme's plain CSS, including direct component
selectors, rather than limiting customization to Sass compilation or token editing. A future base-HTML theme
`<style>` block is distinct from scattered inline component styles and requires separate CSP-safe delivery.
Do not introduce inline component style systems, CSS-in-JS, a theme loader/engine or a new style framework.
Database-driven theme management remains the future Wayfinder topic recorded in TASK-00148.

## Validation and permissions

Qualify the selected React-Bootstrap release against the actual locked React, React DOM, Bootstrap,
TypeScript and Storybook versions. Inspect public prop/ref/event contracts and supported peer ranges, then
commit an exact manifest/lock addition through repository tooling. A missing compatible release blocks the
adoption decision; do not force peers, downgrade the stack or replace the accepted runtime without authority.

Treat native element type, button default type, disabled/busy semantics, focus, field descriptions, status
roles, retry and caller-owned state as compatibility requirements, not incidental implementation details.
Preserve server-authority boundaries and fake local story data. No business command, persistence, credential,
HTTP permission, external network request or product route is added.

Keep tests of owned behavior and important integration contracts. Do not test React-Bootstrap's unrelated
internals, exhaustive prop surface or tool installation. Use direct tooling checks for dependency/configuration
qualification. Report an out-of-scope product defect rather than silently widening this migration.
