# Ask typed questions about one permitted memory entry

## Outcome

An authenticated Agent asks a bounded typed yes/no or predeclared-choice question about one currently
permitted private or shared memory entry without loading its body into the Agent's context. The application
passes an eligible exact source revision to the qualified shared Jev evaluator under independently checked
provider-disclosure policy, then returns a typed judgment with provenance or its actual failure. Ordinary
known-ID exact reading remains a separate operation and works when only Jev is unavailable. This is one
independently reviewable single-entry MCP-to-Application-to-evaluator use case.

## Scope

- Reuse [TASK-00188](00188-TASK.md)'s private/shared entry identity, current-versus-historical eligibility,
  exact authorized read and first-party HMAC MCP caller (transitively TASK-00185/TASK-00171). Use the shared
  bounded Jev typed-question/evaluator/receipt contracts from TASK-00159/TASK-00171, not a second provider,
  autonomous Agent identity, database credential or memory-specific judgment cache. Agent identity and
  Repository/assignment/Workflow/TASK authority come from the authenticated invocation, not an entry ID,
  request assertion or Jev answer.
- Accept a bounded question with declared answer kind, choices and explicit entry ID; resolve current source
  status, revision, provenance, scope, lifecycle and caller Permission in one authoritative operation before
  admitting provider input. No second authorization ceremony within that same already-authorized operation;
  a later exact read independently rechecks current authority and returns original text/status, not Jev prose.
  No bulk startup memory preload or MCP Resource is needed: initial instructions and authoritative handoff
  explain on-demand use without changing their execution authority.
- Protect secrets/prohibited material and independently qualify provider disclosure **before** sending any
  memory body to Jev. Apply shared bounded question, source-size, time, budget, concurrency, cancellation and
  receipt rules, with a memory-specific source policy where necessary; do not borrow the file relevance tool's
  threshold or the Level 9 example's file cap without qualification. Receipts/results identify evaluator,
  question, source ID/revision, observed outcome, coverage and bounded available usage, never the memory body
  or credentials. Jev is a classifier, not a free-form summarizer, source of truth or permission grant.
- Exclude retracted ordinary guidance and pending/rejected proposals. Explicitly authorized historical
  inquiries and published Repository/Workspace sources are later TASK-00195 paths. Known-ID authorized
  reads and Jev failure remain distinct: timeout, provider refusal/error, input limit and database failure
  are neither fabricated negatives nor a fallback to offline memory authority.
- Out of scope: multi-entry scope selection (TASK-00194), historical/published lookup (TASK-00195),
  correcting/publishing content, general SQL/file screening, embeddings, human UI and exceptional safety
  removal (TICKET-00050).

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Judge one entry | Submit typed evaluation intent; no memory write | Resolve exact authorized current entry/revision and validated typed result | Evaluation/usage observation, not a memory-change event | Bounded permitted provider request and redacted provenance |
| Read exact source later | N/A — read-only | Existing exact current entry read with fresh authority | N/A — no memory mutation | Original text reaches the Agent only after separate requested read |
| Deny or fail safely | Rejected evaluation request or explicit provider failure | Resolve live actor/scope or actual evaluator outcome | Safe failure observation where applicable | No forbidden body or fabricated yes/no, no silent alternate search |
| Continue during Jev outage | N/A — no automatic fallback judgment | Known-ID exact read if Application/database is healthy | Provider outage observation belongs to judgment request | Permitted ordinary read remains usable; database outage stops reads |

Semantic operation names do not fix PHP types, MCP wire format or event-sourcing requirements.

## Validation and permissions

Authenticate the first-party Agent and authorize entry scope and egress independently on each request.
An ID, stale role template, historical receipt or prior model session is not a read grant. Filter malformed,
removed, retracted-in-ordinary-mode, excessive, sensitive or unauthorized entries **before** provider
submission; return safe absence/denial without titles/snippets or counts that reveal hidden notes. Fail
closed when a provider-disclosure filter is unqualified; do not solve prohibited-content safety solely with
instructions. Preserve distinct refusal, unknown, incomplete, timeout, invalid output, provider failure,
input limit, cancellation and database-unavailable results. Never introduce an offline source of authority.
No live memory ingestion or unrestricted live Jev disclosure is enabled until TICKET-00050's qualified
safety-removal/secret-handling path exists; bounded synthetic non-sensitive provider qualification is
separate evidence.

## Acceptance criteria

- [ ] A real authenticated first-party MCP Agent with current assignment obtains a typed yes/no and declared-
  choice result over one permitted current memory revision, with source/evaluator/question/outcome provenance
  but no source text in its judgment response.
- [ ] Wrong Agent, unrelated Repository/Workflow, closed ordinary scope, revoked Permission, forged entry ID,
  retracted normal guidance and denied disclosure produce no provider submission or hidden metadata leak.
- [ ] Missing, malformed, ambiguous or undeclared answers, timeouts, provider/input-limit failures and
  uncertain usage remain explicit; none becomes an ordinary negative or an unqualified retry.
- [ ] A separate exact read returns original source text only under refreshed authority during a Jev outage;
  database/application unavailability stops that read rather than serving a cached memory copy.
- [ ] Memory-use instructions do not preload entry bodies or substitute for an authoritative handoff; no
  live unsafe memory/provider disclosure is claimed before TICKET-00050's safety-removal qualification.
