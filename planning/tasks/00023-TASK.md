# Process registered durable intents after commit

## Outcome

A single-intent processor claims committed eligible work, resolves only an allowlisted effect handler, invokes its external capability outside database transactions, and durably records delivered, retryable, or terminal outcome using a stable idempotency identity. Post-commit immediate coordination is an optimization; durable pending intent remains authoritative.

## Scope

- In scope: Registered effect-handler contract/registry; explicit intent-to-capability mapping; short claim transaction; out-of-transaction invocation; separate outcome transaction; success/recoverable/permanent/unknown/malformed/stale outcomes; stable idempotency propagation; post-commit immediate coordinator; safe status/logging; deterministic mail/audit processor tests and PostgreSQL claim tests.
- Out of scope: Batch/recovery console runner, retry timing/backoff policy beyond persisted outcome, lease reclamation, production providers, invitation/reset event integration, user-facing status UI, exactly-once delivery, and unrelated background jobs.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Process one eligible intent | Internal processing operation by stable intent ID | Claim committed eligible revision and resolve registered type | Post-commit coordination may request this operation | One capability attempt occurs after claim commit and before outcome transaction |
| Record success | N/A — processor outcome operation | Compare claimed revision/ownership | N/A — no product event inferred | Delivered state commits and safe attempt evidence is retained |
| Record failure | N/A — processor outcome operation | Inspect typed recoverable/permanent result | N/A — no product event inferred | Retryable or terminal state commits without arbitrary provider detail |
| Survive duplicate invocation | Same internal operation may repeat | Resolve current state and stable idempotency identity | Original event may be absent or duplicated | No state corruption; any repeated provider attempt carries the same idempotency identity |

## Validation and permissions

Processing order is: claim in `commitTransactional()`, commit, map through a closed registered handler registry, invoke capability with no open database/business transaction, then record outcome in a separate `commitTransactional()`. A rollback or uncommitted intent cannot invoke a capability. Do not keep a transaction open across provider latency.

Persisted type or payload values cannot name arbitrary PHP classes, container services, callables, templates, or provider endpoints. Registry entries are code/configuration controlled and map known bounded schemas into TASK-00022 inputs. Malformed/unknown work fails safely into an explicit operator-visible state or quarantine selected by the ADR; it never executes dynamically.

Map only typed capability outcomes. Provider success followed by process loss may lead to another invocation; every attempt carries the same stable idempotency key and semantics remain at-least-once. A stale claimant cannot overwrite newer state. Exactly-once delivery is not claimed.

Logs/status projections include safe intent/type/attempt/state/reason codes and correlation only. Exclude credentials, tokens, provider secrets, ciphertext, credential-bearing URLs, full destinations where not approved, arbitrary payloads, and provider exception messages.

Processing authority is internal and may execute only registered committed work. End-user authorization belongs to the originating use case.

## Acceptance criteria

- [ ] One processor follows claim-commit, external invocation, and outcome-commit as distinct transaction phases.
- [ ] Rolled-back, absent, ineligible, delivered, terminal, or stale work cannot invoke a capability.
- [ ] External mail/audit capabilities are demonstrably called with no open originating, claim, or outcome transaction.
- [ ] A closed registry permits only known effect types and bounded mappings; persisted class/service/callable/provider names cannot trigger dynamic resolution.
- [ ] Success, recoverable failure, permanent failure, malformed payload, unknown type, and stale outcome have explicit durable behavior.
- [ ] Competing single-intent claims permit one live owner for the relevant revision.
- [ ] Duplicate processing reuses the exact stable idempotency identity and does not infer duplicate business events.
- [ ] Post-commit immediate coordination can attempt newly committed work but is not required for later recovery.
- [ ] Logs and safe projections expose no credentials, tokens, provider secrets, ciphertext, URLs, arbitrary payloads, or unsafe exception messages.
- [ ] Focused processor/PostgreSQL/redaction checks and `./bin/build` pass with fresh evidence.
