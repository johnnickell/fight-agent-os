# Deliver the confirmed elevated invitation journey

## Outcome

A deliberately isolated elevated invitation route uses TASK-00041's existing orchestrator only when the current principal has both `INVITE_USERS` and exact `ASSIGN_SUPER_ADMIN`, requires unambiguous confirmation, and creates one pending identity assigned managed `ROLE_SUPER_ADMIN` with normal seven-day activation, recoverable delivery, and durable safe actor/target audit evidence.

## Scope

- In scope: Separate protected elevated invitation route and complete two-permission metadata; permission-controlled navigation; canonical email form; elevated risk explanation and explicit confirmation interaction; typed existing-API request; pending/validation/forbidden/conflict/throttle/success/system states; directory/status invalidation/navigation; integrated exact-permission/audit/PostgreSQL/HTTP/component/accessibility/redaction tests.
- Out of scope: New elevated backend endpoint/orchestrator, elevation option in ordinary form, arbitrary role/permission assignment, standalone active-user promotion, custom-role administration, role removal/demotion, bootstrap reset/bypass, lifecycle administration, administrator-selected password, bulk elevation, raw credentials, and broad browser automation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invite pending Super Admin | Existing TASK-00041 elevated Action/orchestrator uses `InvitePendingUser` and `AssignRoleToUser` | Resolve current principal permissions, canonical email, explicit confirmation, managed role and target/policy state | `UserInvited`, `RoleAssignedToUser` plus package/owned audit | On complete success: pending managed Super Admin, seven-day grant, recoverable delivery and required audit; later-step failure can retain origin, delivery or membership |
| Reject absent elevation authority | N/A before command dispatch | Evaluate exact `INVITE_USERS` and `ASSIGN_SUPER_ADMIN` | N/A — no domain event | Safe `403`; no identity/assignment/grant/audit-success/delivery created |
| Reject missing/ambiguous confirmation | N/A before elevated orchestration | Validate exact confirmation contract and canonical target | N/A — no domain event | Controlled validation result; ordinary flow is not substituted silently |
| Continue after success | N/A — cache/navigation | Evaluate READ_USERS and registered routes | Client invalidation/navigation signal | Directory refetches and authorized actor may inspect credential-free status |

## Validation and permissions

Use a distinct route and interaction from TASK-00061. Complete route metadata requires both exact `INVITE_USERS` and `ASSIGN_SUPER_ADMIN`; TASK-00041 server Action independently rechecks both through authoritative principal resolution. Possession/display of `ROLE_SUPER_ADMIN`, role names, client route visibility, JWT/HTML claims, or one permission alone grants nothing. Unknown/stale/mismatched authority fails closed.

Accept one bounded canonical email and TASK-00041's exact elevated mode/confirmation fields only. Expose no arbitrary role ID/name, permission set, actor, target user ID, password, grant, template/provider, lifetime, or bootstrap flag. The server resolves only stable managed `ROLE_SUPER_ADMIN`; malformed/hidden values cannot select another role or elevate the ordinary endpoint.

Require deliberate explicit confirmation after showing canonical target, managed elevated role, installation-wide consequence, invite-only activation, and actor accountability. Use an unambiguous boolean/typed protocol accepted by TASK-00041; absent/false/wrong-type/stale confirmation rejects before mutation. Avoid fragile phrase entry unless accepted design requires it. Confirmation cannot be preselected and duplicate submission is disabled while pending.

Reuse owned invitation/package behavior for pending invitation, managed Role assignment, audit, seven-day grant/delivery, rates, conflicts and business-consistency fences. Apply the [canonical contract](../../docs/engineering/STANDARDS.md#architecture): each entry owns admission before configured bus dispatch; registered handlers coordinate persistence and required audit within each owning step's transaction using its shared connection, not one transaction across the consumed composition.

Preserve [TASK-00041's explicit implementation amendment](00041-TASK.md#implemented-contract-and-criterion-evidence) and the [independent issuance commits](../../docs/engineering/INVITATION_API.md#independent-issuance-commits): invitation origin (pending identity, grant, recoverable delivery and user.invited audit), membership and confirmation audit commit independently. Delivery may start after origin commit before assignment; later assignment/audit failure may retain invitation, sent mail or membership without confirmed audit. No private handler calls, outer/nested consumer transaction, fictitious all-step rollback or duplicate blanket Application permission gate is permitted.

[TASK-00577](00577-TASK.md) owns the HTTP invitation source correction and preserves these partial outcomes; qualify its actual consumed interface without implementing that cutover here. Ordinary admitted work may finish after concurrent permission revocation; preserve managed-Role, confirmation, uniqueness and required per-step transaction/audit guarantees rather than revocation/commit locking. This flow's “assignment” is the role assignment within creation of a newly invited pending identity. General promotion of an existing active user is not exposed because broad role administration is out of scope; document this boundary rather than silently adding an endpoint.

Audit must durably distinguish authenticated actor, target, elevated action/role, time/result and approved safe context without password/grant/credential/link/provider secret. Required evidence is not optional because a prior step committed; missing/unconfirmed audit is not complete success. Success does not claim inbox receipt.

On partial/uncertain issuance (including 503), timeout or lost response, stop automatic submission, invalidate stale directory/status observations, retain only safe correlation/known ID in memory and direct trusted operator inspection of identity, membership, audit and delivery. An exception does not prove rollback; never automatically reinvite, compensate, replay or offer browser elevation repair. READ_USERS permits deliberate fresh safe user/status reads only; it does not establish audit completion or authorize assignment recovery. Elevated or unknown-state repair requires investigation under the runbook, not retry/resend as assignment repair.

After success invalidate directory and, with exact READ_USERS, offer TASK-00060 status (2026-11-02 human correction; management alone grants no reading); otherwise safe success only. Do not broadcast target authority snapshots or persist form/permission state.

Recreate accepted high-risk warning/confirmation/form states with semantic alert/heading/dialog behavior, labels/instructions, keyboard/focus/escape/return, status announcements, visible focus, target/reflow, themes, reduced motion, long/Unicode email, and clear distinction from ordinary invitation. No color-only risk meaning.
