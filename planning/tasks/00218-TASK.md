# Verify the library candidate and publish its exact remote tag

## Outcome

On the one certified library release Workflow, Release Manager verifies the exact local tag and approved signer
when required, then publishes **only** its approved tag object to the qualified remote or recognizes an exact
preexisting remote match. Distinct local signature, remote tag intent and observed remote object/peeled commit
remain separately recorded. A lost response, conflict or unverified subject pauses the same Workflow without
force, retargeting or another release TASK.

## Scope

- Consume [TASK-00215](00215-TASK.md)'s final certified commit/version,
  [TASK-00216](00216-TASK.md)'s current bounded named-effect plan,
  [TASK-00217](00217-TASK.md)'s verified local signing result or explicitly qualified policy-based N/A, and
  [TASK-00212](00212-TASK.md)'s project-specific library runbook. Reinspect the local tag *object*, annotation,
  verified signer/key when required and peeled commit; inspect the release line, actual remote/push destination
  and existing remote tag object **and** peeled commit independently before any effect. A missing local tag
  when signing is optional uses only an expressly supported project-owned preparation procedure and grant;
  never invent an unsigned/lightweight fallback or ask an Agent to sign.
- Extend the owning same-Workflow recoverable-effect path for exact tag publication. Release Manager alone
  receives direct source-host Permission and the live exact-candidate tag-push grant, never Team Lead or the
  ordinary `land` publisher grant. Persist a stable effect identity and intent before invoking a scoped,
  non-force, single-ref push **after** the business transaction. Recheck approved tag object, certified
  commit, remote, runbook/checks, actor, grant and budget immediately before the effect. Reuse a verified
  matching remote tag; conflicting object or peeled commit (even if only annotation differs), failed remote
  inspection or advanced/incompatible release line blocks without deletion/replacement or silent recertification.
- After an attempted push or unknown response, independently observe remote object and peeled commit against
  the approved local identities before recording a verified result. Reconcile the existing effect intent
  after timeout/restart; do not infer success from command exit, process history, PR merge or a signature
  alone, and do not retry an uncertain push without a current provider observation. Preserve private receipts
  in approved ignored `.runs/` storage and emit only safe attributed references.
- Out of scope: interactive human signing (TASK-00217), GitHub release/draft/assets
  ([TASK-00219](00219-TASK.md)), registry projection ([TASK-00220](00220-TASK.md)), protected-branch
  follow-through and release closeout ([TASK-00221](00221-TASK.md)), automatic tag rewrite, force push,
  branch push, PR approval/merge and application deployment. These are **implementation slices**, not
  separate live release TASKs or per-stage approvals.

| Publish authorized tag | Existing scoped same-Workflow Release Manager effect operation | Revalidate release subject, current grant, direct Permission, checks, remote/tag state and effect intent | Durable tag-push intent, then separately verified result or blocked fact | One non-force exact-ref tag push only when absent and approved |

## Acceptance criteria

- [ ] Required signer/tag object/peeled certified commit, exact remote and current grant/Permission are checked
  before publication; an optional signer policy never becomes implicit permission to improvise a tag.
- [ ] Release Manager publishes only one exact approved tag ref or reuses the *verified* same remote object and
  commit. Conflicting tag, stale candidate, advanced line, denied authority or unknown remote state blocks
  without force, branch push, deletion or retargeting.
- [ ] Durable intent and separately observed remote result survive timeout, duplicate delivery and restart
  without duplicate publication or fictional success; local and remote facts remain distinct.
- [ ] No GitHub release, registry result, PR merge, deployment or release TASK `done` is inferred from tag push.
