# Resolve native collection and privilege blockers

## Outcome

Remove the concrete design blocker preventing recoverable, bounded operational capture: identify an implementable
native reader/driver/collector composition, its actual privilege boundary and early supplier contracts. This is
approved slice A of [TICKET-00112](../tickets/00112-TICKET.md), not a generic backend comparison or permission to
build an unapproved custom collector. No currently inspected candidate demonstrates the whole accepted contract.

## Scope

- In scope: Evidence-backed selection/reconciliation of native mechanisms, exact source/runtime compatibility,
  source identity/checkpoint/framing, queue/disposition/preservation participation, independent status, physical
  enforcement and bounded qualification paths; early producer and destination contracts needed by dependent TASKs.
- Out of scope: Service startup, image/dependency installation, Docker grants, live ingestion, production enrollment,
  bespoke queue/proxy/plugin/protocol implementation, changed access/loss/preservation policy and new product scope.

Consume [WF-038](../wayfinder/tickets/WF-038-define-log-collection-and-failure-recovery.md) and its
[primary-source research](../wayfinder/research/operational-log-collection-recovery-boundaries.md). Reconcile exact
candidate capabilities, not product names: stateless source plus persistent sink, native drop-oldest without hold
eligibility, a logical queue cap without physical enforcement, or socket filtering without authorization is insufficient.

Produce one concrete design with source/enrollment/retirement authority; supported reading/rotation and replay;
trusted identity/original-clock and reversible framing contracts; independent destination dispositions; eligibility/
fencing and verified-copy participation; failure-status integration; and complete accounting against the finite
profile. Identify exact native settings/APIs, supported platform/versions, license/security obligations, remaining
implementation qualification and stop conditions. Do not promise a mechanism because an Adapter interface can be named.

Keep early contracts separate from later complete UI, installation and composed release acceptance. Their known
limits must let TASK-00451 and TASK-00456–00460 implement real paths without waiting for completed consumer TICKETs.
An unsupported guarantee returns to its existing decision/engineering owner; a gap matrix by itself is not a resolved
design. Required product/security policy amendments remain human decisions, while routine finite sizing stays an
evidence-backed engineering judgment under WF-038.

## Validation and permissions

Use installation inventory and trusted runtime ownership, not project labels or broad daemon discovery as authority.
No browser, PHP request, Agent or ordinary delivery sink receives Docker/backend/storage credentials. A read-only
socket mount is not a method policy. Any necessary root-equivalent reader exposure requires explicit security
acceptance before selecting/enrolling that configuration; existing docker-gen access is not a transferable grant.

Retain all accepted source families/levels, exclusions, no pipeline redaction, newest-context eligible eviction,
protected sole-copy preservation and independent status. Follow [ADR 0001](../adr/0001-application-ownership-and-orchestration.md)
and [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md); do not invent another transaction, evidence
owner or inline backend delivery dependency. Runtime paths belong under ignored `var/`, not execution scratch.

## Acceptance criteria

- [ ] One reviewed implementable design maps every required capability to exact native mechanisms and the owning
  integration; no unsupported privilege, framing, persistence, eviction, hold or quota guarantee is assumed.
- [ ] Existing runtime/storage/preservation owners supply the concrete early contracts and finite physical boundaries;
  required security acceptance is recorded, not inferred from this TASK's approval.
- [ ] Producer-to-capture/framing and independent status contracts can be consumed by TASK-00451/00456 without a
  completed producer/browser/collector prerequisite; downstream receipt/lifecycle dependencies are explicit.
- [ ] Source evidence distinguishes supported facts from unmeasured behavior and names bounded qualification for
  checkpoints, physical limits, failures and integration. Composed runtime acceptance remains with implementing TASKs.
- [ ] Any design/guarantee conflict is resolved by its owner before claiming this blocker removed. Merely documenting
  an unsupported candidate or recommending a custom component does not complete the TASK.

## Verification and evidence

Inspect exact primary documentation/source and existing owner contracts, record versions/references and countercheck
compatibility against WF-038. Walk normal emission/restart and exhaustion/held-only/unknown-authority cases through
the actual mechanisms. Validate the design and links directly; add no product tests for planning or configuration.
Any needed experiment requires separately approved target, resources, time, effects and cleanup; no previous backend
experiment grant transfers here. Runtime findings must be labelled separately from documentation evidence.

Run `./bin/planning-check --write`, `./bin/planning-check`, whitespace checks and required `./bin/build` before
implementation acceptance/commit/publication. Record warnings and unverified claims; a green build cannot qualify
a native collector. No production service or code implementation is needed merely to demonstrate this design TASK.
