# Finish application branch follow-through and release closeout

## Outcome

After the exact approved application candidate is observed in the named environment and independently
passes all required health checks, the **same** release Workflow verifies any configured branch
forward-port/merge-back and invokes [TASK-00211](00211-TASK.md)'s guarded release TASK completion.
Protected branches stay under their human PR merge policy; trunk/no-target projects have an explicit
policy-based no-action. Unverified production or branch state never becomes `done`.

## Scope

- Consume [TASK-00224](00224-TASK.md)'s current verified deployment identity and health,
  [TASK-00215](00215-TASK.md)'s certified source/commit or deployable-to-source provenance,
  [TASK-00216](00216-TASK.md)'s bounded effect approval and [TASK-00212](00212-TASK.md)'s configured
  branching policy. A verified deployed artifact whose source cannot be linked to the configured production
  branch is insufficient for GitFlow inclusion. Inspect actual remote/provider source and target refs/OIDs,
  PR/branch protection, existing inclusion, later changes and required checks. Trunk-based projects with
  no separate development base do **not** inherit a GitFlow `develop` merge-back; custom/maintenance lines
  use only a qualified project-owned forward path, not an old-line wholesale merge.
- Where policy requires a branch effect, request the exact release follow-through already named by the
  current human grant or stop for new approval. Only a separately permissioned Release Manager may
  prepare permitted branch changes/PRs under live direct Permissions, current source/target identities and
  protected-branch rules. Persist distinct durable effect intent before provider mutation; preserve
  newer unrelated development content and run required integration/review/checks. No force-push, silent
  PR approval/merge, merging development into production, rerouting the release TASK or reusing the
  hotfix-specific button/grant. Pause for human PR approval/merge when required, then inspect trusted
  target inclusion and checks independently before calling follow-through verified.
- Reconcile lost response, duplicated request, advanced ref or conflict against actual authoritative
  remote/provider state before retrying the **same** effect identity; keep same release TASK/Workflow
  history and claim where applicable without reacquiring an already released claim. Record verified
  inclusion, policy-bound no-action, blocked or Needs Human reason distinctly from rollout/health facts.
- At closeout revalidate the exact candidate, approved environment/rollout effect and provider-observed
  deployed artifact, current required health/checks, signing proof if required, policy/runbook revisions,
  budget/authority and verified follow-through or qualified N/A. Invoke the existing release-kind
  intent-specific completion guard, not a new status setter or second queue. A rolled-back, partial,
  unknown or unhealthy candidate remains incomplete; PR landing, successful build and effect intent
  are never proof of deployment. Out of scope: library tag/GitHub/registry release, automatic rollback,
  archive, cleanup of unrelated resources, and per-stage live release TASKs.
