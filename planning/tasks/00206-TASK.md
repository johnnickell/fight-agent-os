# Confirm and repair a direct hotfix

## Outcome

An authorized human can confirm one urgent bugfix's incident scope and verified production base in a quick
interaction; the existing authoritative start claims one TASK for a distinct, isolated Hotfix Engineer Workflow.
The Hotfix Engineer performs the smallest scoped repair and hands off exact regression/check evidence in Awaiting
Review, with the initiating human or named incident owner as contact. No hidden Team Lead stage or production
merge is created. This is one independently reviewable emergency-start-to-repair use case.

## Scope

- Consume [TASK-00201](00201-TASK.md)'s current, usable `bugfix`/urgency proposal and
  [TASK-00202](00202-TASK.md)'s human disposition when a material category conflict exists. Jev alone cannot
  grant emergency authority; a declared-kind fallback with unknown priority cannot silently infer a hotfix.
  Present incident scope, limits, exact TASK, Repository, route, versioned configuration and verified production
  base from [TASK-00203](00203-TASK.md) in **one** human emergency confirmation. Do not ask for another
  branching-strategy confirmation or assume `main`/`develop`.
- On a current bounded grant, call the **same** server-authoritative Start coordinated work operation as
  [TASK-00204](00204-TASK.md), with a distinct hotfix route and direct senior-capability Hotfix Engineer
  identity/session. Revalidate canonical eligibility, live Permissions, grant, TASK/context/configuration/
  catalog/classification revisions, claim owner, base, limits and qualified Runner at the atomic start. Persist
  hotfix Workflow, dispatch intent and exclusive claim only on success; Triage has no claim/start power.
- Reuse [TASK-00142](00142-TASK.md)'s qualified isolation and recovery. The Hotfix Engineer begins from the
  exact configured production base in an owned workspace, performs a bounded incident repair with a reproducing
  regression case where applicable, runs required focused and canonical checks and records commit-specific
  changed-tree, base/head, checks, warnings and evidence for a separately permitted reviewer. The initiating
  human or named incident owner receives progress and blockers; the application owns state, escalation and
  resource fencing without a Team Lead stage. Unknown process/effect state pauses; no unqualified sandbox
  fallback or role switch inside an existing Agent session.
- A proposed exception to a **specific** required check pauses for a separate explicit human authorization
  naming risk, containment/rollback and follow-up; a skipped check is never reported green. New incident
  scope/limit or changed base requires a fresh grant. Independent review, QA and PR handoff belong to
  [TASK-00207](00207-TASK.md); normal-to-hotfix transfer to [TASK-00208](00208-TASK.md), and post-merge
  merge-back to TICKET-00054. No PR approval/merge, tag, release or deployment authority is included.

## Acceptance criteria

- [ ] One quick authorized emergency confirmation identifies exact TASK, incident, verified production base,
  limits and human contact; unconfirmed, stale, missing or mismatched base starts nothing.
- [ ] Exactly one distinct Hotfix Engineer Workflow/claim begins from that base under direct grants and a
  qualified owned sandbox; duplicates return the same request result, competing requests cannot start another.
- [ ] Repair records smallest authorized scope, regression evidence, actual required check results, exact
  source/base/head and safe Awaiting Review handoff, without a Team Lead step or self-review.
- [ ] Scope/grant drift, lost process, exhausted limit and uncertain effects pause with the incident owner and
  an actionable next step; any specifically waived check retains its human approval, risk and follow-up without
  fabricated passing results. No merge, release or deployment occurs.

## Verification and evidence

Test owned emergency confirmation, authority/currentness, production-base mismatch, idempotent start, direct
human escalation, check-exception restrictions and exact repair handoff with focused application and PostgreSQL
integration/concurrency evidence. For bugs, reproduce the behavior and add a failing regression before repairing
unless impossible with recorded reason. Qualify real sandbox/Git isolation and branch source directly with owning
tools in authorized disposable scratch, not product tests of Docker, Git or configuration prose. Run focused
checks and `./bin/build`; record fresh check exits/counts, warnings, reviewed subject and missing capabilities
honestly. Formal independent review and publication follow separately.
