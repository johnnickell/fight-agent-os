# Accept the Agent persistence and restoration design

## Outcome

An explicitly accepted, evidence-backed supplement to ADR 0002 selects the concrete persistence, admission and
restoration design for the current Agent contract. Downstream implementation has an actual writer inventory,
lock order and independent evidence boundary, not a diagram that assumes empty storage or trusted readiness.

## Scope

- In scope: Inspect available tagged package capabilities and actual installation data/participants; select the
  supported contract and deliberate dependency-adoption plan; specify Agent/operation/audit correlation, schema
  and hydration strategy, shared connection, fences, authority epochs, storage-incarnation identity, independent
  witness/history mechanism, controlled switch/restore tools and safe transition from storage-only behavior.
- Out of scope: Runtime admission, production restoration, credentials, sink implementation, upstream package
  changes, invented historical backfill, legacy readers, application migration or mutation, and a new proof product.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Select actual contract and boundaries | Read-only inspection and bounded feasibility probes using owning tools | Available tagged API, exact lock/source, hydration/transaction contracts and actual storage/tool capabilities | N/A — design evidence is not a product event | Attributable supported-contract selection and explicit unresolved blockers |
| Inventory writers and restore evidence | N/A — no runtime writer or restore command is enabled | Actual HTTP/direct/CLI/worker/policy/destination/key paths, storage identities and independent history provenance | N/A — no business mutation | Complete ownership/fence matrix and supported stop/reconcile/resume design |
| Accept the supplement | Explicit human approval of the ADR supplement | Tradeoffs, infrastructure feasibility, safe transition and qualification plan | N/A — approval is a planning record, not runtime admission | Accepted implementation contract without rewriting historical ADR receipts |

## Validation and permissions

Apply [ADR 0001](../adr/0001-application-ownership-and-orchestration.md) and
[ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md). Package Domain/Application owns transitions;
Agent OS owns real adapters and operational admission. Do not put provider calls inside business transactions,
add nested Unit of Work wrappers, mutate package private state or substitute a local ready flag for independent
attestation. Package version strings alone do not prove compatibility.

Inspection needs appropriate source/storage/operator access without reading/exporting raw credentials or private
material. Record exact target and safe inventory; no local reset, data deletion, production probe or credential
access is authorized by this design TASK. If feasibility needs an effect outside bounded read-only inspection,
obtain separate scope/authority first. Empty local tables do not establish absence of external history.

## Acceptance criteria

- [ ] The maintainer accepts a focused supplement naming actual supported package contracts/source/lock facts,
  transition limits and the deliberate reproducible adoption plan; historical TASK-00126 storage-only evidence
  and ADR 0002's old baseline remain labeled historical.
- [ ] The design inventories every actual relevant writer and participant, including Permission/Role/User and
  managed-policy paths, delegation, destination/key changes, direct connections and restarted binaries. It defines
  cohort-first lock ordering, atomic expected-state/reference checks and advancing epochs without revoke/regrant ABA.
- [ ] A feasible independent witness/history mechanism binds exact live storage incarnation, never restores with
  the target dataset, retains complete original operation/audit/order/receipt/tombstone evidence and fails closed
  on unavailable/uncertain reconciliation. Its update/crash boundary and monotonic generation strategy are explicit.
- [ ] Supported storage/binary exclusion and physical backup/restore tools are identified with observed feasibility,
  limitations and abort conditions; a backup file or package fixture is not claimed to qualify restoration.
- [ ] The transition preserves existing data and foundation behavior without legacy support or uncorrelated Agent
  writes. Incompatible existing state is an explicit stop/owner decision, not guessed repair or permissive fallback.
- [ ] TASK-00228 through TASK-00233 have a concrete implementation/evidence contract, including the distinct
  TICKET-00060/00061 dependencies and a closed runtime gate until the full composition is qualified.
