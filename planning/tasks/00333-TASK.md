# Establish explicit first-party Skill trust

## Outcome

A user explicitly establishes and inspects Skill trust for the configured first-party installation/origin.
Protected transport and later loading consume the same exact binding, never a second registry or hostname grant.

## Scope

- In scope: Skill trust establishment, exact connection/origin binding, expected-state changes, bounded inspection
  and current trust/eligibility facts for transport, collision, snapshot and removal consumers.
- Out of scope: New connection/credential stores, MCP server or loader, third-party origins, cache cleanup,
  credential enrollment, session switching and another authorization or approval platform.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Establish first-party Skill trust | Explicit expected-state trust operation through existing Harness authority | Exact configured connection and verified host-assigned installation/origin | Safe owning trust fact/local observation as applicable | Deliberate bound trust, not Tool or Agent authority |
| Inspect current binding | N/A — protected read | Exact identity, revision, trust state and mismatch/unavailable reason | N/A | Safe facts for current-use checks, never automatic enrollment |
| Reject changed or substituted binding | No implicit repair/retrust | Actual identity versus expected binding/generation | Safe denial observation | Subsequent affected use holds; historical identity stays intact |

## Validation and permissions

Reuse TASK-00322's explicit machine-local connection and protected identity verification. Trust belongs to the
host-assigned installation/origin, not transport location, server display name, `localhost`, repository input or
an arbitrary URL. Establish trust only through current authorized user/operator intent bound to exact connection
revision and installation. A saved credential handle, TLS success or repository project-trust decision is not a
Skill trust grant. Reject unexpected redirects, mismatched identity, stale state and origin substitution.

Use the existing Harness ownership for any retained origin/trust state. Do not create a competing endpoint or
credential registry. Bound fields and observations; preserve unrelated connections and private handles. Expected
selection/trust generations cannot accept a stale choice after a changed-away-and-back binding. An uncertain change
requires original-state reconciliation, not implicit retrust. Repository configuration may neither register nor
redirect this accepted first-party origin, even when the host's generic project configuration permits overrides.

First-party origin trust is explicit once. New static revisions do not require another per-revision content prompt,
but each file and exact frontmatter still need later manifest verification. Trust grants no live direct Permission,
provider disclosure, local execution or nested activation. TASK-00245 consumes current binding alongside its existing
authentication/current-use checks; this trust primitive cannot depend on that completed transport or final loader.

Keep exact safe origin facts available independently of completed session snapshots. Current binding changes must
be observable to admission/loading owners before subsequent use; stale or unavailable state denies affected work.
No retroactive cancellation of an already admitted effect is claimed. TASK-00338 owns complete explicit removal and
credential/cache cleanup, using this same binding rather than a separate trust deletion path.

Apply ADR 0001 ownership and ADR 0002 atomic state/audit where authoritative database state is involved. Local state
uses safe expected-state replacement; external identity inspection is outside business transactions. Reads create
no Domain change event. Diagnostics omit credentials, handles, private paths, raw server errors and hidden content.

## Acceptance criteria

- [ ] Actual explicit establishment/inspection binds trust to the configured verified first-party installation/
  origin and exact connection revision without creating another registry or enrolling credentials.
- [ ] Repository overrides, display names, hostnames, redirects, stale selections and wrong installations cannot
  establish or substitute trust; unknown identity/current state holds safely.
- [ ] Later transport/snapshot/loader consumers receive precise current trust and immutable identity facts without
  requiring final onboarding, active-session switching or completed loader delivery.
- [ ] Trust changes preserve history and unrelated configuration; uncertain outcomes reconcile original state.
- [ ] Trust is distinct from static content verification and current authority, with safe inspectable denial states.
