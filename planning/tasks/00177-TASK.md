# Analyze data through constrained SQL access

## Outcome

An authorized Pi 1.1.0 caller can obtain bounded data observations through a qualified read-only SQL capability and
ask typed questions about permitted minimized results. Replica access is preferred; primary SQL requires explicit
applicable authorization and a visible target. Actual caller authority, enforced database controls and resource
bounds govern the operation independently of Jev.

## Scope

- Add a complete Agent-controlled SQL evidence capability to [TASK-00174](00174-TASK.md)'s authenticated composition
  path, reusing its principal propagation, per-call authority, guard policy for covered effects, budgets, receipts
  and shared evaluator. Apply this boundary whenever the Agent controls SQL, including SQL submitted through MCP.
- Accept a configured database/environment target, bounded SQL with schema-validated parameters, an admitted query
  profile and typed questions/preset. Resolve physical connections/credentials through protected configuration;
  no Agent-supplied connection string, arbitrary host, credential, role escalation or alternative privileged adapter.
  Keep raw SQL/parameters and result bodies out of ordinary logs and default Agent-facing receipts.
- Enforce current caller permission for Agent-controlled SQL and the actual repository/environment/data scope on
  every request. Business API permission does not grant SQL permission, and physical database credentials do not
  prove caller authority. If the permitted data scope cannot be enforced for the selected SQL capability, deny it
  rather than relying on Jev, model instructions or post-query result filtering to authorize access.
- Prefer a qualified read replica for production-data SQL. Bind the selected target role to trusted configuration
  and verified connection facts, record endpoint role and query observation time, and report available replication
  lag/freshness or explicit unknown values. A replica is neither a caller-authorization nor a resource-safety boundary.
- Apply a configured freshness requirement. Missing, unavailable, too-stale or unverifiable replica freshness must
  produce an explicit limitation under that policy, never a silent switch to the primary. An explicitly permitted
  query that tolerates unknown freshness must still report it and cannot claim current-primary completeness.
- Support primary read-only SQL only when explicit applicable caller/target authorization exists and the chosen
  endpoint is visible before execution. Replica failure, possession of primary credentials or a prior approval for
  another operation cannot create that authorization. Preserve selected-target identity through execution/result.
- Both paths require a dedicated database identity with enforced read-only permissions and a qualified restricted
  execution profile. Validate actual grants, transaction/session controls, accessible functions/extensions and
  indirect execution/effect routes; a SELECT prefix or read-looking statement is not enforcement. Reject unsupported
  statement forms and any means to change data/schema/roles/settings, escape the allowed scope or invoke unsafe
  external effects. Database restrictions must remain effective if submitted SQL is adversarial.
- Require finite protected limits for SQL/parameter bytes, statement count, query/lock/transaction time, concurrency,
  resource consumption, rows/result bytes and retained evidence. Bound database work as well as client output:
  fetching fewer rows is not proof of bounded query impact. Qualify cancellation/timeouts, cleanup and reused-
  connection state reset; no inherited privileged session or open transaction may leak between callers.
- Use an explicitly separate read-only operational connection under ADR 0002. It cannot perform writes or claim
  participation in a business transaction. This capability does not alter ordinary API/MCP business operations:
  those may use the primary and authorized writes through their existing owning domain/effect contracts. Internal
  application SQL is not Agent-controlled merely because an operation uses a database.
- Obtain query observations freshly by default. Record exact permitted query/input identity, target role, current
  caller/scope, schema/profile revision as applicable, observation time, available freshness, row/byte coverage and
  execution receipt separately from classification. Truncated/limited/partial results cannot imply a complete
  population; independent queries are not one consistent snapshot unless the actual qualified contract proves it.
- Minimize/redact permitted query results and check independent provider-disclosure authority before evaluation.
  Authorization to query production does not permit sending its rows to Jev. Return compact typed answers,
  coverage, freshness and authorized evidence references; raw query/result access is a separate current permission
  check through bounded protected evidence storage, never a default main-Agent dump or production fixture export.
- Preserve denied/invalid/unavailable/timeout/cancelled/incomplete outcomes and uncertain billing without converting
  them to zero rows, false or healthy. On revocation/stop/reload/target change stop dependent work and use qualified
  cancellation for owned queries; do not claim a cancel request proves the database stopped. Reject late obsolete
  results, preserve actual state and never retry or switch targets to populate a cache or obtain a preferred answer.
- Historical immutable query receipts can answer only historical questions under current reference permissions;
  matching SQL strings do not establish live freshness. Reuse cannot replay a query without its current authority.
- Exclude automatic replica/database provisioning, primary cutover, production access/role grants, unrestricted SQL,
  mutation routes, deployment and source-data extraction into fixtures. Operator-provided replica/read-only
  integration is a route-readiness requirement, not an assumed existing resource or permission to create one.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Analyze permitted replica data | Submit a bounded admitted read-only SQL invocation | Current caller/data scope, endpoint readiness and query observations | Query completed/limited/failed with endpoint/freshness provenance | Bounded database read load and protected result evidence |
| Analyze explicitly authorized primary data | Submit a separately authorized primary read-only invocation | Current primary authorization, selected target and enforced role/profile | Primary selection/query observations | Bounded primary read load; no data mutation |
| Judge permitted query evidence | Submit minimized disclosure-permitted observations | Typed questions, result coverage and actual freshness | Judgment completed/unavailable observation | Bounded provider usage; no automatic raw result disclosure |
| Handle replica or query failure | Cancel owned query/stop dependent work where applicable | Actual endpoint/freshness/query state | Unavailable/stale/cancelled/uncertain observations | No fallback to primary or hidden retry |
| Inspect historical evidence | N/A: historical receipt access | Current reference permission and original result/time/role | Existing evidence access observation where applicable | No SQL execution or fresh-state claim |

## Validation and permissions

Enforce three independent checks: invoking-principal SQL/data scope, actual database read-only/resource controls,
and provider disclosure. None substitutes for another. Keep credentials and target configuration protected, bind
all operations and results to current authenticated context, and use package authority directly rather than role-
name assumptions. Qualify connection and statement restrictions against indirect effects as well as obvious writes.
Unknown schema, role/profile drift or missing resource guarantees block the affected route. An authorized normal
business mutation remains its owning command's responsibility and cannot be reissued through this SQL capability.

## Acceptance criteria

- [ ] A real Pi 1.1.0 inquiry through TASK-00174 obtains bounded SQL evidence and a useful typed judgment with actual
  caller/data scope, endpoint role, query receipt, coverage and honest freshness provenance.
- [ ] A qualified replica route is preferred, while unavailable/stale/unknown freshness follows the configured
  policy without silent primary fallback. Explicitly authorized primary-read selection is separately demonstrated.
- [ ] Dedicated enforced read-only roles plus actual database/query controls reject data/schema/authority changes
  and unsafe indirect effects. Caller checks independently deny forged/revoked/cross-environment/data-scope access.
- [ ] Query/lock/transaction/resource/concurrency/result bounds hold, cancellation and connection reuse are qualified,
  and a row/output cap alone is not treated as proof of safe database work.
- [ ] Partial/truncated/mixed-time/historical evidence stays explicit; failures do not become empty successful
  results. Stop/reload/revocation and late responses cause no retry, privileged fallback or stale disclosure.
- [ ] Data minimization and separate egress checks prevent prohibited provider disclosure; compact results preserve
  references/provenance without raw rows, secrets or production-data fixture export.
- [ ] Ordinary primary-backed API/MCP operations retain their existing domain authority and effect behavior; their
  permissions neither confer general SQL access nor acquire a new SQL-primary exception requirement.
- [ ] Actual query/profile/evaluator evidence reports useful coverage, limitations, available total cost and latency;
  unavailable live target qualification is recorded as outstanding rather than inferred from mocks or plans.

## Verification and evidence

Test owned target/authorization/freshness admission, bounded result handling, provenance, cancellation and judgment
integration. Qualify actual database roles, connections, replica behavior and resource/indirect-effect controls
with the owning database tools in controlled authorized environments; do not create product-suite tests of
infrastructure/configuration or seed failures to test the testing machinery. Qualification of write denial must
never risk production data; production readiness uses its separately authorized evidence and cannot be inferred
solely from a controlled replica substitute. Do not provision a replica or grant access as a planning side effect.
Run applicable focused backend checks, `./bin/harness-check` and canonical `./bin/build`; retain direct exits,
tested-content identity, exact database/runtime/profile/evaluator versions and redacted receipts under
`.runs/tasks/TASK-00177/`. Missing authorized replica/primary qualification remains a named acceptance gap.
