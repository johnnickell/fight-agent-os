# Investigate large evidence sets through resumable stages

## Outcome

An authorized Pi 1.1.0 caller can investigate questions across many files through bounded MCP/Harness stages,
inspect compact honest progress and explicitly resume interrupted work. Source and provider limits apply to each
stage while an admitted aggregate budget makes useful large investigations possible without loading the corpus
into the main Agent's context.

## Scope

- Extend [TASK-00171](00171-TASK.md)'s authenticated typed judgment path using
  [TASK-00163](00163-TASK.md)'s existing list/glob discovery and source-policy mechanics. Avoid a second resolver,
  provider client or source-authorization system. Keep the general investigation lifecycle distinct from the
  original file-screening call's 0.70 read policy and single-call limits.
- Accept explicit paths, lists, globs and a repository scope resolved through the caller's currently permitted
  root. Paths cannot nominate an arbitrary server filesystem. Narrow candidates using metadata/frontmatter,
  exact search or existing graph results where useful; no shell expansion or automatic code execution.
- Add versioned start, inspect, resume and cancel operations. Start accepts the existing question/preset envelope,
  scope and a configured aggregate-profile reference. Return an opaque investigation identity, generation, lifecycle
  status, bounded progress page/cursor, typed outcomes, coverage and consumed/remaining budget with uncertainty.
  Subsequent operations resolve caller ownership server-side; an identifier or cursor never grants access.
- Use protected Harness-owned durable metadata outside repository-controlled source for progress. Bind it to the
  authenticated principal, installation/session and repository scope, question/context/preset/evaluator/policy
  digests and exact evidence identities. Store pending/completed work, discovery continuation, attempt/dispatch
  identities, status, usage reservations and bounded reference/result metadata; no raw source bodies or credentials.
  Qualify the storage location, permissions, atomic persistence and actual Pi lifecycle before activation. This is
  not a new Planning database, transcript store or source of permission; unavailable/corrupt storage stops unsafe resume.
- Resolve an explicit operator-owned aggregate profile before starting: maximum candidates, visited entries,
  aggregate source bytes, upstream requests, cumulative active time, concurrency, retained metadata/output page
  sizes and per-investigation monetary ceiling. Include bounded storage capacity/retention and a job expiry.
  Every field must be concrete and finite in the deployed profile; missing/unknown spend bounds reject admission.
  Reuse the shared conservative reservations and tighter session/child allocation; the model cannot increase limits.
- Permit many stages under that profile. Retain initial per-stage ceilings of 50 files, 1 MiB source, 10,000 visited
  entries and 60 seconds; retain 32 KiB per file and shared 64 KiB serialized request, eight questions, sixteen
  choices, two concurrent requests, fifteen-second upstream timeout and zero automatic retries. Do not reinterpret
  these per-stage values as the whole-job cap or raise them implicitly. Qualify a configured many-stage workload
  with sufficient aggregate allocation; publish actual profile values with its acceptance evidence.
- Accumulate discovery, evaluation, time, output and spend use across continuation/reload, not anew for each stage.
  Resume cannot reset an exhausted budget or reissue ambiguously billed attempts. Explicitly increasing a profile
  requires the authorized operator path and an attributable new admission decision, not an Agent continuation loop.
- Enumerate deterministically with bounded work, containment and symlink-loop/escape protection. Deduplicate actual
  canonical evidence identities, recheck access and disclosure per source, and detect changes during reads. Internal
  resolution never recursively preflights its own inputs with Jev. Binary/oversized/excluded/changed/unvisited items
  remain explicit unresolved coverage; do not silently truncate or chunk a source and claim its whole contents read.
- Bind each answer to its actual evaluated subset. Return per-source/stage results by default; cross-stage reduction
  must be declared and validated for the question semantics. A positive existential result may identify an actual
  supporting source, but incomplete enumeration cannot establish absence or a universal conclusion. Do not average
  probabilities/scores or treat majority votes as a whole-repository answer without a defined qualified rubric.
- Keep discovered/evaluated/skipped/unresolved counts, known versus unknown total population, excluded categories
  and coverage limits explicit. Protect unauthorized paths/counts as required. If evidence changes, invalidate the
  affected progress/results and mark coverage stale; do not mix revisions into a claimed coherent snapshot.
- Persist progress before presenting a recoverable stage. On resume, recheck current authority, source identity,
  question/context/evaluator/policy and job generation before using completed stages or dispatching new work.
  Safe resume of the same job is required here; TASK-00173 owns optional reuse across separate judgments.
- Cancellation stops new dispatch, invalidates late completions and preserves uncertain charges. Reload does not
  silently restart cancelled/stopped/failed jobs. Explicit permitted resume establishes a new generation while
  retaining usage and completed evidence; uncertain dispatches require reconciliation rather than automatic replay.
  Corrupt/missing/stale/expired state yields a clear unavailable/invalid/incomplete outcome, not a fabricated answer.
- Bound inspection, paging, stored progress and lifecycle cleanup. Expiry or cleanup does not delete source files,
  erase unresolved billing obligations or make an old job identifier reusable. Preserve authorized provenance under
  the applicable history policy, separate from reusable progress; expose retention/expiry limits to the caller.
- Exclude arbitrary shell/SQL, gathering new runtime/MCP observations, memory ingestion, main-model routing and
  any automatic change to consumer policies. No dependency on compaction or production analysis/SQL integration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Start a broad investigation | Admit a scoped job under a finite aggregate profile | Current authority, questions and bounded candidate discovery | Job admitted/rejected; stage observations | Protected progress metadata, authorized reads and bounded provider usage |
| Inspect progress | N/A: inspection is read-only | Bounded authorized pages of coverage, results and budget | N/A: inspection cannot resume or grant authority | Compact main-Agent output without source-body ingestion |
| Resume interrupted work | Resume owned job with revalidation and generation change | Source/context/authority identity and retained usage | Resume/revalidation/invalidation observations | Only newly admitted safe work; no uncertain operation replay |
| Cancel or expire work | Cancel owned job; apply configured lifecycle expiry | Current generation and unresolved reservations | Cancelled/expired/late-result observations | Stop new dispatch and stale delivery; retain required usage facts |

## Validation and permissions

Every operation authenticates through TASK-00171, including progress inspection, resume and cancellation. Apply
source and disclosure checks during discovery, reads, result delivery and revalidation, not only at initial job
creation. Untrusted source instructions cannot change queries, roots, budgets, identities or lifecycle. A protected
progress record proves recorded work, not current permission or immutable filesystem state. Qualify concurrent
resume/cancel handling so only the active generation dispatches or publishes; do not claim exactly-once provider
execution after an ambiguous transport failure. Same-user local isolation limitations remain explicit.

## Acceptance criteria

- [ ] A real Pi 1.1.0 investigation processes a representative corpus exceeding one stage within an explicitly
  configured aggregate profile, returning useful compact results with exact source/question/evaluator provenance.
- [ ] Lists, globs and repository scopes preserve bounded discovery and per-source access/disclosure checks;
  symlink loops/escapes, duplicates, oversized/binary inputs and denied sources cannot bypass limits.
- [ ] Aggregate discovery/bytes/requests/time/concurrency/output/storage/spend limits hold across stages and resume;
  existing request and stage ceilings stay intact. Missing limits and uncertain remaining spend stop new dispatch.
- [ ] Coverage distinguishes partial, excluded, changed and unknown populations; per-stage results do not become an
  unsupported whole-repository negative, score or synthesized proof of absence.
- [ ] Protected progress survives a qualified interruption and explicit resume with current authority and evidence
  rechecks; revoked access, changed contexts/revisions and corrupt/stale/expired records cannot produce stale answers.
- [ ] Concurrent resume/cancel, reload, explicit stop and late responses cannot duplicate accepted progress, reset
  budgets or replay an uncertain dispatch. Accounting preserves possible charges without double counting.
- [ ] Measured many-file comparisons report missed relevant evidence, unsupported conclusions, main-context volume,
  local reread/discovery work, total available provider/main-Agent cost and latency against direct/structural/graph methods.
