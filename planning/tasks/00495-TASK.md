# Standardize Pi extension and integration naming

## Outcome

Maintainers can identify each Pi module's capability and distinguish package-loaded extension entry points
from internal integrations by name. Replace the ambiguous header entry point and misleading internal
extension suffix while preserving package loading, commands, optional Jev behavior and deterministic policy.
This is bounded maintenance of the existing harness, following the exploration recorded in
[TASK-00492](00492-TASK.md); no new runtime capability or Workflow editor prerequisite is introduced.

## Scope

- Document a Pi/TypeScript naming convention in the existing engineering standards and link it from the
  harness package guidance. Apply capability ownership without importing PHP namespaces or class boilerplate.
- Use kebab-case capability filenames. Reserve `-extension.ts` for entry points loaded by the Pi package
  manifest; use `-integration.ts` for internal SDK registration modules where that boundary needs a suffix.
  Reusable logic keeps capability names such as `header`, `file-admission` and `workflow-access`.
- Use camelCase functions, PascalCase exported classes/types and `install<Capability>` registration functions.
  Retain provider names for actual provider adapters. Avoid generic `extension`, `manager`, `utils` or
  `service` names that hide responsibility; do not introduce wrappers or directories solely for uniformity.
- Apply the following migration and align affected registration names, imports, declarations, owning tests,
  native probes, typecheck inputs, package contents and documented direct-load examples together.

| Current module under `harness/pi/src/` | Target | Ownership |
|---|---|---|
| `extension.ts` | `header-extension.ts` | Pi-loaded terminal header/appearance entry point |
| `jev-extension.ts` | Retain | Pi-loaded provider adapter |
| `tool-policy-extension.ts` | Retain | Pi-loaded deterministic tool-policy entry point |
| `file-screening-extension.ts` | `file-screening-integration.ts` | Internal SDK integration installed by the Jev adapter |

- Inventory supported explicit-path loading and exported registration callers before removal. Update owned
  callers and document the old-to-new path migration. If a supported old path must remain, use a temporary,
  documented compatibility export outside the manifest and verify it cannot cause duplicate registration in
  supported configurations. Otherwise remove it and give an actionable migration instruction.
- Out of scope: package or public tool/command ID changes, feature or permission changes, module ownership
  refactors, new extension frameworks, global installation/settings edits and automatic user-session restart.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Find the adapter that owns a capability | N/A — source maintenance | Package entry list and documented naming rule | None | Clear source ownership without behavior changes |

| Migrate a supported direct-load path | Existing explicit extension selection | Old-to-new path guidance and compatibility status | None added | Deliberate path update; no operator-state mutation |

## Validation and permissions

The rename grants no new read, write, execution or provider authority. Preserve optional Jev startup without
configured credentials, existing file-reader boundaries and independent deterministic tool policy. Keep
enrollment, configuration, session invalidation, budget/account ledgers and public command/tool IDs unchanged.
Use isolated fixtures and supported installed SDKs for qualification; do not rewrite personal installation
paths or operator state. Document a full Pi process restart after authorized adoption of renamed modules.

  compatibility paths. Historical evidence remains historical.
- [ ] Package loading and supported explicit-path loading register each capability exactly once on supported
  Pi versions; missing/obsolete-path recovery is documented and exercised where applicable.
- [ ] Header appearance and its existing command behave unchanged; Jev-disabled/unconfigured startup works,

  tool policy remains independently selectable with unchanged decisions.
- [ ] Public command/tool identifiers, enrollment, operator state and account ledgers remain unchanged;
  adoption instructions explain the required full restart and any direct-path migration.
- [ ] Owning harness checks, native SDK qualification, strict typechecks, planning validation and the canonical
  build pass. Independent review and applicable behavioral/visual QA are recorded before publication.
