# Deliver recoverable secret-safe password-reset email

## Outcome

Package-owned encrypted password-reset delivery generations become recoverable mail through qualified package discovery, claims, direct handlers, and outcomes: invocation materializes a canonical fragment-based HTTPS completion link only in memory, terminal package outcomes destroy ciphertext, and crashes retain honest at-least-once recovery without a consumer intent pipeline.

## Scope

- In scope: Password-reset mapping for the exact locked package provider-neutral credential-delivery capability; stable delivery-generation idempotency; protected credential handling at the invocation boundary; canonical reset URL builder; deterministic text/HTML templates; generic mail capability mapping; development catcher reuse; production key/provider/origin guards; provider/outcome crash recovery; retry/expiry/redaction tests and operational documentation.
- Out of scope: Package discovery/claim/outcome policy or persistence, reset-request HTTP/UI, reset completion HTTP/UI, production mail-vendor enrollment, arbitrary template engine/endpoints/callables, any consumer outbox/queue, user-facing delivery status, plaintext credentials in operational views, analytics/tracking, and scheduler/platform enrollment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Recover reset delivery | Existing TASK-00024 runner dispatches exact package handlers | Discover package-owned pending, due-retry, and expired-lease reset work | `PasswordResetRequested` may prompt immediate processing but is not recovery authority | Committed package work remains discoverable without consumer registration or reconciliation |
| Invoke reset mail | Exact locked package handler invokes its provider capability after claim commit | Receive only package-approved invocation-lifetime destination, credential material, and delivery-generation ID | Package outcomes remain package-owned | Credential is materialized transiently, canonical mail is invoked with stable idempotency, and a typed result returns to the handler |
| Record successful delivery | Same package handler lifecycle | Compare exact live claim token, revision, and delivery generation | Package event only after durable state as defined upstream | Matching delivered outcome commits and package ciphertext is destroyed |
| Expire undelivered work | Qualified package discovery and handler lifecycle | Resolve recoverable delivery at/after one-hour expiry | Package expiry event as defined upstream | Package terminal state destroys ciphertext and prevents later mail invocation |

## Validation and permissions

Treat the password-reset delivery generation persisted with the one-hour grant as the sole durable work authority. `PasswordResetRequested` may trigger prompt post-commit package processing, but correctness depends on bounded deterministic package due-work discovery recovering the originating commit/event gap. Agent OS must not register, reconcile, map, or persist a second intent/reference for that generation.

Implement reset-mail mapping through the exact locked package provider-neutral capability from TASK-00022. Persisted package state cannot dynamically select Agent OS code, service, template, endpoint, or callable; those choices remain fixed composition. Protected material remains encrypted at rest and is materialized under package control only for invocation. Plaintext exists only during that call; PHP zeroization limitations are documented and references are minimized.

Build completion URLs only from configured canonical HTTPS origin/path, never request Host/forwarded headers/user input. Place bounded user routing identity and reset credential in the URL fragment according to the approved contract below so neither reaches request lines/referrers. Reject userinfo, ambiguous host/path, query credentials, and non-HTTPS; local examples also use HTTPS.

### Approved invocation routing and fragment contract

The owner explicitly approved this compatible routing contract on resumption of initial TASK-00053 Work. With the
locked Access Control v0.6.0 (`dc4621d13851dd08cdf85ed9715ead24b1051e80`), dispatch public
`FindCredentialDeliveryStatus(invocation purpose, invocation idempotency ID)` through the configured query bus
inside the `password_reset` provider invocation. Require a `CredentialDeliveryStatusView` whose purpose and
exact delivery ID match the invocation; consume only its immutable `getUserId()`. Missing, wrong-type,
mismatched or failed lookup sends nothing and returns a generic retryable provider outcome. Never infer identity
from destination email or the newest user grant, enrich/mutate the opaque invocation, add consumer persistence,
or bypass the query pipeline. Destination, credential and idempotency ID remain the unchanged invocation values.

Independent installed-source qualification: `FindCredentialDeliveryStatusHandler` selects
`PasswordResetGrantRepository::getByDeliveryId`; the application repository queries the unique `delivery_id`
without latest-generation filtering, including terminal history. Its supported writes preserve UserId/delivery ID
through same-generation changes and successors retain distinct IDs. The View exposes no destination, credential,
digest, ciphertext or claim token. No dependency update or upstream release is needed for this bounded use.
The repository internally hydrates protected state; no raw aggregate/secret projection crosses this query boundary.

This lookup supplies routing identity only. Its status/revision/expiry are advisory, not a live-claim fence or new
send authorization. Succession/revocation/expiry or lease reclamation can race before/after the lookup or mail
submission; immutable historical routing remains stable, while package handlers fence matching outcomes and
completion rejects obsolete credentials. Preserve the accepted at-least-once/stale-mail window; do not claim that
this lookup prevents an already-invoked provider from sending after a concurrent terminal transition.

The exact shared TASK-00053/TASK-00055 fragment is
`#user_id=<package UserId UUID string>&credential=<RFC3986-encoded opaque reset credential>` in that order.
There are exactly two fields, each once: `user_id` is the canonical 36-character UUID and `credential` decodes to
1–4096 bytes, unchanged and untrimmed. No email, generation ID, claim token or advisory status/expiry is added.
Encode credential bytes with RFC3986 encoding, including separators, percent signs and whitespace; no query
parameters carry authority. TASK-00055 validates the bounded fields once, rejects duplicates/unknown fields or
malformed encoding, captures them transiently and removes the fragment before ordinary rendering. UserId is
routing, never reset authority without the matching current package credential. This clarifies only the handoff;
TASK-00055 implementation, dependencies, priority and acceptance remain unchanged.

### Mail and lifecycle safety

Use fixed/versioned escaped text and HTML templates with expiry, ignore-if-unrequested, and recovery guidance. Include no remote image/font/script, tracking pixel, analytics parameter, unnecessary identity data, or mutable content. Reuse TASK-00040's mail capability/catcher/provider composition and never print links to console/logs.

Preserve package-owned claim/invoke/outcome phases, stable delivery-generation idempotency, bounded retry, leases, stale-worker protection, and honest at-least-once semantics. The direct package handler records only a matching delivered, retryable, or permanent outcome; no pipeline-to-package confirmation bridge exists. Provider-success-before-outcome may duplicate under recovery. At expiry, package policy prevents new invocation and terminalizes work with ciphertext destruction. Internal package runner authority is not an anonymous product endpoint.
