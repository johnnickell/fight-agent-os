# Design the project-alignment adopt skill

## Outcome

A project-local `adopt` skill compares a named project's actual conventions and package contracts to the current Agent OS engineering guidance, then presents proportionate alignment choices without importing Factory plans or editing the assessed project.

## Scope

- In scope: Design `.pi/skills/adopt/SKILL.md` for read-only project intake and comparison; inspect package ownership/version facts, local code conventions, existing decisions, test/gate capacity and migration risk. Compare Factory `skills/Fight-Adopt-Skill.md` as non-authoritative evidence; update the [skill gap map](../../docs/engineering/SKILL_GAPS.md). Distinguish non-applicable, compatible, conflicting, and undecided guidance, including where Fight Common or Fight Access Control differs from current Agent OS preferences.
- Out of scope: Rewriting an external project, imposing Agent OS-specific decisions as universal Fight Common policy, importing Factory EPIC/TICKET/TASK records, automatically opening PRs or changing dependency versions, and approving an adoption decision on the maintainer's behalf.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Compare a selected project | N/A — read-only assessment | Inspect the project's decisions/code/tests, locked package contracts and current local guidance | N/A | Return sourced differences, non-applicability, options, compatibility/risk and an optional human planning handoff; no project mutation |

## Validation and permissions

Ask for the target project and scope; respect its existing authority and source ownership. Never assume this repository's rules supersede another project's accepted decisions or package APIs; mark conflicts for human resolution. Avoid secrets or private source in portable reports. Later authorized changes belong to that project's own planning and checkout/branch process, not this assessment.

## Acceptance criteria

- [ ] Skill intake and report separate observed differences from preferences, inherited package behavior, absent evidence and explicit human decisions; show graded adopt/adapt/defer/reject options and risks.
- [ ] Assessment addresses relevant architecture, naming, PHP/HTTP, testing, ownership and delivery guidance without treating current Agent OS standards as universal or copying Factory's automatic adoption/publishing workflow.
- [ ] Exact source comparison identifies why Factory adoption behavior is rejected or adapted and how existing local `audit`, `architecture`, `review` and planning workflows would receive a human-approved handoff.
- [ ] Directly validate links/instructions and a bounded non-mutating comparison example, refresh planning views and run `git diff --check` and `./bin/build`; no product-suite tests of instructions or static configuration.

## Verification and evidence

Read Factory adopt instructions and the target project's accepted guidance with authorization for access; use a limited safe comparison of currently available project facts, not an external mutation. Directly check references, planning views, diff and canonical gate, reporting warnings and unknowns.
