# Operate custom roles and the read-only permission catalog

## Outcome

An authorized operator can browse the real role and permission catalogs and manage only custom roles/eligible permission associations in an accessible, permission-aware browser journey.

## Scope

- In scope: Registered Roles/Permissions routes; typed read and mutation services; managed/custom distinctions; role create/rename/remove and eligible permission grant/revoke controls; confirmations, audit/result feedback, authority invalidation/refetch, responsive/loading/empty/denied/conflict and accessibility/Storybook states.
- Out of scope: Backend API, permission definition CRUD, managed-role edits, unsupported custom/unknown-tier grants, arbitrary scope or treating client visibility as authorization.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Browse roles and permissions | None | Existing `READ_ROLES`/`READ_PERMISSIONS` APIs | None | Safe server Views only, never an anonymous catalog |
| Maintain allowed custom role | Existing CRUD/role-permission APIs | Refetch roles/permissions/current principal | Existing server events only | Confirmed result converges on authoritative state |

## Validation and permissions

Use exact `READ_ROLES`, `READ_PERMISSIONS`, `CREATE_ROLES`, `UPDATE_ROLES`, `DELETE_ROLES`, `MANAGE_ROLE_PERMISSIONS` independently in the shared client evaluator for presentation. Unknown authority fails closed; server route and Application service remain final authorities. Distinguish managed immutable roles and `SUPER_ADMIN_ONLY`/unknown-tier ungrantable permissions visibly without implying rejected operations succeeded. Accessible focus/dialog/keyboard/status, mobile/desktop reflow, theme and redaction are required. No credential, permission snapshot or mutation form persists in browser storage.

## Acceptance criteria

- [ ] Browsing and controls match exact independent permissions and registered backend Actions without role-name bypass.
- [ ] Managed roles and ineligible tiers cannot be edited/delegated in UI or by direct API; confirmation/cancel/stale responses are truthful.
- [ ] Server-confirmed mutations invalidate/refetch authoritative role/principal data; no optimistic grants or persistent authority.
- [ ] Focused client/HTTP/accessibility/redaction checks and `./bin/build` pass with test/state counts, warnings and manual limits.

## Verification and evidence

Exercise role/permission combinations, managed/custom/ineligible/no-permission states, direct route denial, stale and racing responses, confirmation focus and a11y across viewports/themes. Inspect DOM/storage/logs for secrets and authority leaks; run focused checks, `./bin/planning-check`, `git diff --check`, `./bin/build`; record counts/warnings.
