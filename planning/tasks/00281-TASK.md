# Cancel a pending change without affecting a successor

## Outcome

An active owner explicitly cancels the pending change they reviewed through the real account journey, making
that exact reservation/grant unusable without promoting an address or touching a successor. Required self-
cancellation attribution commits with the operation. This safety path does not require an operational mail provider.

## Scope

- In scope: Supported expected-change/authority/audit contract qualification, package cancellation integration,
  protected self API and account confirmation UI, exact outcome observation and stale/race recovery.
- Out of scope: New package lifecycle, latest-target cancellation disguised as exact intent, consumer grant
  mutations, notice deletion, request/credential reissue, production provider dependency or cross-user UI.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Review current cancellation | N/A | TASK-00279's current scoped status and qualified non-authorizing context | N/A | Explicit human confirmation identifies the intended pending change; no reservation |
| Cancel the confirmed change | Package `CancelEmailChange` through a supported exact-intent boundary | Current active principal, exact intended grant/reservation and expected state | Package cancellation fact after commit and required durable attributable audit | Exact reservation cleared and grant revoked atomically, canonical email unchanged |
| Reject stale or reconcile uncertain result | Owning operation rejects mismatch; supported original-state observation | Current and exact original facts, not only the latest pending destination | No false success fact on rejection/uncertainty | Newer change remains untouched; safe refetch or explicit unresolved status |

## Validation and permissions

**Contract gate:** the inspected `CancelEmailChange` takes only actor/target IDs. Its handler loads the latest
issued grant, owns its transaction and audits only administrator cancellation. Repository comparisons protect
what the handler reads, not a generation the human reviewed earlier. Browser confirmation, a preflight revision
check or lack of automatic retries cannot alone prevent delayed cancellation from selecting a newer change.

Qualify a supported public exact-change/expected-state and required self-audit integration against the actual
selected tagged/source/locked package. Reuse any applicable qualified coordination from TASK-00273, but do not
assume its request/confirmation seam also covers cancellation. If support is absent, obtain explicit owner
resolution and separately authorized tagged adoption; no vendor patch, copied handler, outer nested transaction,
audit-repository side effect or after-commit audit write may manufacture the guarantee. No upstream TASK ID is mapped.

Derive actor and self target from TASK-00278's current active principal. A displayed revision/context is not
authority; enforce the exact intended change inside the owning serialized operation. Same-email successor/ABA,
changed context and expired confirmation intent require safe conflict/refetch, not cancellation of whatever is
current. Authenticate non-HTTP callers as well; shared behavior must remain reusable under TASK-00282's distinct
cross-user policy, never a target override on this self route.

Use package reservation/grant lifecycle and canonical transaction boundaries. Required audit, reservation clear
and grant revocation commit or roll back together; preserve initiating actor versus target and no secret material.
The original old-mail request notice is an accepted historical fact and remains recoverable. Cancellation does
not produce a completion notice, promote an address, revoke unrelated sessions, authorize a replacement request
or claim to recall email already sent/in flight. Later use of the cancelled credential must fail under its owner.

Cancel versus confirm, expiry, User disable and new request follow supported package/expected-state winner
semantics. No observed absence or changed email alone proves this original cancellation succeeded. A post-commit
event failure/lost response may follow success; observe exact original outcome where supported or retain
uncertainty. No automatic replay on refresh/reload or new request identity to escape an unknown result.

Integrate explicit accessible confirmation into TASK-00279's account panel using one volatile draft/current-
authority owner. Refetch on conflict, retire late responses on auth/context change, and retain canonical email
presentation until actual confirmation changes it. Restrict status to safe current/original facts; no credential,
grant object, worker claim, private provider result or raw audit is displayed. Keep no business state in browser
storage/URLs/history and provide keyboard, focus, announcement, responsive and light/dark behavior.
