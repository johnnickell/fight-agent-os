# Approve a bounded exact-candidate release plan

## Outcome

After current certification, a permitted human can approve **one bounded plan** for the exact release
candidate naming all currently supported downstream effects, targets, checks and limits. Team Lead can
coordinate the approved phases without another routine per-effect prompt, but only a separately permissioned
Release Manager can later perform effects within its direct grant. Start, certification, Jev, PR landing and
role labels never substitute for this approval.

## Scope

- Present a permission-scoped plan from [TASK-00215](00215-TASK.md)'s exact certified subject and
  [TASK-00212](00212-TASK.md)'s current qualified project policy: Repository, version/tag or deployable
  digest, branch/line, named registry/host or environment, evidence and warnings, required checks and human
  steps, concrete permitted effect identities (such as tag push, GitHub release, supported deployment,
  follow-through or explicitly approved rollback), ordering/dependencies, validity window and budget/attempt
  limits. Include only effects that the runbook and actual adapter/Permission capabilities support. Library
  and application effect sets are project-specific, not a universal plan.
- Extend WF-015's scoped human approval/continuation operation, not ordinary TASK `land`, to record one
  attributed, expected-version release-effect grant on the **same Workflow**. Starting the Workflow is a
  distinct grant. The human can approve multiple named downstream effects together; no routine extra prompt
  is needed while candidate, targets, evidence, policy, actor/Agent Permissions, time/cost/attempt budgets
  and allowed effect scope remain current. Do not require that a downstream effect has already occurred to
  record an approval, and do not infer that recording the plan carried it out.
- Bind each subsequent effect request to this exact candidate and plan, unique effect identity, live direct
  Release Manager Permission and bounded grant; verify current Workflow claim/phase, intended target and
  authority before an effect or continuation. Invalidate/pause for changed commit/digest, target, runbook,
  required check or exception, permission revocation, exhausted limits or an effect not enumerated. Offer a
  reasoned new **human** approval only for the changed/exhausted scope; preserve the old attributed plan,
  recorded intents and observations for same-Workflow recovery. Signer instructions and verification are
  [TASK-00217](00217-TASK.md); library/app effect dispatch and provider reconciliation are
  [TICKET-00057](../tickets/00057-TICKET.md)/[TICKET-00058](../tickets/00058-TICKET.md).
- Out of scope: generic grant over every future provider, collecting signing secrets, agent-issued approval,
  an agent self-grant, initial TASK start, actual push/merge/tag/deployment/rollback, and a second release TASK.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview exact release plan | N/A — read-only preview | Current certification, policy, live Permissions, allowed named effects/limits and evidence | N/A — preview grants nothing | Safe human decision with candidate/effect identity; no execution |
| Approve or refuse plan | Attributed expected-version human approve/refuse operation | Revalidate certified subject, project policy, allowed effects, signer needs, role/actor and budget | Bounded grant or refusal fact on the same Workflow | Named future effects authorized within limits; no provider call or publication |
| Continue or seek renewed authority | Existing scoped continue/recover or reasoned reapproval operation | Current claim/plan, consumed effects, drift, direct Release Manager Permission and results | Reconciled continuation, paused or renewed-grant fact | No duplicate grant/effect on retry; material changes require a fresh human decision |

These are semantic interactions extending current Workflow authority, not a global approval token or new
Planning status.

## Validation and permissions

PHP must verify the human actor's scoped approve Permission and authentic attributed decision; an Agent,
Team Lead prompt, UI button rendering, Triage classifier or ordinary PR landing cannot impersonate it.
Team Lead cannot inherit Release Manager direct Permissions, credentials or execution session. Match approved
subject/target to current certified identity, immutable plan revision, runbook and evidence; require live
direct Release Manager Permission again at effect time rather than treating the human grant as sufficient.
Check exception and rollback must be individually named and risk-bounded; an unknown/unsupported effect or
absent provider capability cannot be approved as runnable. Persist approval with effect identities, expiry
and limits in the owning Workflow with expected-version/idempotent concurrency; never send raw credentials,
secret values or unredacted provider messages into Commands, events or human preview. No provider effect
inside the grant transaction.

## Acceptance criteria

- [ ] One authorized human approval names the exact certified candidate, scope, targets, evidence, allowed
  effects and limits; a refusal records no grant and start/certification cannot masquerade as approval.
- [ ] Multiple approved routine effects can proceed under one still-current grant without repeated prompts;
  changed candidate/target/check, additional effect, risk exception, revocation or exhausted limit stops and
  requires a new bounded human decision.
- [ ] Duplicate/concurrent approval and continue commands keep one attributed, recoverable same-Workflow
  history without granting an unapproved effect or duplicate authority; denial gives a safe next action.
- [ ] Team Lead has no Release Manager direct effect Permission. Approval alone neither signs nor publishes,
  deploys, rolls back, completes the release TASK or authorizes an unsupported provider.

## Verification and evidence

Test preview scope/redaction, actor identity, exact subject/certification drift, stale policy, effect list,
limits, permission revocation, refusal, duplicate and concurrent grant/continue, and renewed exception behavior
through focused Domain/Application, API and PostgreSQL consistency tests. Use controlled downstream effect
capabilities to prove consumption and denial; actual source host/deployment qualification belongs to
TICKET-00057/00058. Run focused checks and `./bin/build`; report fresh counts, identity/authority results,
warnings, missing real provider capabilities and independent review/delivery separately. Do not add product
tests of runbook prose, configuration wiring, role instructions or infrastructure.
