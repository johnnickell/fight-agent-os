# Keep expected HTTP-failure logs out of PHPUnit console

## Outcome

The backend suite reports test progress and genuine PHPUnit failures without printing structured
`Unhandled HTTP request failure.` records produced by intentionally exercised HTTP error paths. Expected
failures still return their safe correlated API responses, and production HTTP errors still generate
sanitized ERROR logs through the configured sink. This is a standalone bug, not part of the durable-memory
EPIC or a change to its published planning.

## Reproduction and diagnosis

On 2026-10-10, at the pre-fix checkout based on `develop` at
`2dafdfb9bd95dfe3264064c48afdd96c601fdbb5`, a scoped
`./bin/phpunit --testsuite Functional --filter CsrfContractTest` completed successfully with 16 tests /
136 assertions yet printed one JSON `http-failure` ERROR record inline among PHPUnit dots (ignored diagnostic:
`.runs/notes/http-log-noise/repro.log` in the main checkout). The `bbbb…` correlation ID comes from
`CsrfContractTest::test_that_unexpected_failure_matches_the_generic_contract()`, which deliberately
injects a `RuntimeException` and expects a generic correlated HTTP 500 response. The latest complete
local build before this TASK also passed 439 backend tests / 3,329 assertions while emitting that record
and six additional generated-correlation records. The extra records require tracing rather than assuming
they all came from the one injected failure.

`config/middleware.php` unconditionally constructs a dedicated Monolog `StreamHandler('php://stderr')`
for `ApiFailureMiddleware`. Functional tests load `bootstrap/app.php`, so expected HTTP-error behavior
writes real JSON diagnostics into the test runner's stderr even on green runs. Direct unit middleware tests
already use a `TestHandler` and assert safe redacted context without writing to stderr. This identifies the
observed output source, not a real user request failure or grounds to disable production error logging.

## Scope

- In scope: Trace all structured HTTP-failure records in the full suite; provide a narrow test-time
  capture/injection of the existing API failure logger so expected negative-path requests are inspectable
  without becoming console output. Preserve production logging and the real middleware's generic 500,
  correlation, `no-store` and redaction behavior. Extend an owned HTTP error behavior assertion only if
  the investigation exposes a genuine missing product guarantee; do not add a product test of the test
  runner, log configuration text or quality tooling merely to assert quiet output.
- Out of scope: Silencing all application errors, changing Monolog ERROR level, hiding actual PHPUnit
  failures or warnings, creating a test-only product route, altering JWT/CSRF security policy, changing
  Docker/build wrappers to filter stderr, or amending historical receipts that accurately recorded logs.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Handle an unexpected API failure | N/A — failure path, no business command | Resolve generic safe failure response and validated correlation reference | Structured sanitized ERROR observation | Production configured sink receives diagnostic; caller sees generic HTTP 500, not exception text |
| Exercise that failure in functional tests | N/A — intentionally injected exception | Inspect HTTP 500, safe correlation and captured log context | Same failure observation, captured by test-owned sink | PHPUnit console remains free of expected JSON error records |
| Encounter a real test failure | N/A — ordinary test-runner behavior | Read PHPUnit failure/result output | N/A — no application business event | Failure and its actionable diagnostics remain visible; no global stderr suppression |

## Validation and permissions

The HTTP failure middleware must keep fixed safe log fields and never pass a raw throwable, request,
headers, URI, body or private message to a logger. Client correlation values remain validated; the
`bbbb…` ID is test-controlled, and generated IDs are not request authority. Keep the real production
logging destination available and do not use `APP_ENV=test` as permission to turn off diagnostics
inside product code. Any test-specific sink must be explicitly scoped and must not affect other
principals, production composition or concurrent tests. Distinguish intentional negative-path logs from
unexpected errors before changing their handling.

## Acceptance criteria

- [x] The focused functional failure scenario returns the same generic HTTP 500, `no-store` and
  correlation, with its safe ERROR observation inspectable through a bounded test sink; the focused
  PHPUnit process no longer prints its expected structured JSON error.
- [x] The full backend coverage phase and `./bin/build` report real failures and warnings normally but
  do not print any expected `http-failure` JSON from HTTP negative-path tests. Trace and account for the
  previously observed additional generated-correlation records rather than concealing them with a
  blanket stderr filter.
- [x] Production composition still sends an unexpected real API failure to a sanitized ERROR sink;
  no exception message, path, token, cookie, body or private value leaks into response/log context.
- [x] No product-suite meta-test of test/configuration/build infrastructure, loss of HTTP failure evidence,
  new undocumented production switch or change to application authorization is introduced.

## Verification and evidence
