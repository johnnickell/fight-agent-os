# Register local project and task domains across installed harness consumers

## Outcome

John can use `https://local.fight-agent.dev` for the selected primary app and stable,
one-level TASK/checkout names beneath it. This implements the bounded operator
portion of [WF-046](../wayfinder/tickets/WF-046-define-optional-local-routing-trust-and-recovery.md)
through TICKET-00023's existing shared-ingress owner, without waiting for the full
Planning installation or a Dashboard installer.

## Scope

- Explicit preview/apply/remove registration binds the primary name and each actual
  TASK ID to a stable registered Checkout UUID. Names use the first ten lowercase
  SHA-256 hexadecimal characters of the canonical UUID string, never a path or Git
  revision. Reject collisions and stale plans; never silently reassign a name.
- Adapt the existing generic gateway/origin seam and shared ingress; preserve
  ordinary direct localhost and unregistered `.localhost` worktree startup.
- Reuse the qualified workstation CA with one project leaf covering the base and
  its one-level wildcard. CA signing material stays outside every container.
- Keep the canonical local registry at the supplier installation's ignored
  `var/local-ingress/hosts.json`. Enroll each project's `local.{domain}` namespace
  explicitly. Repository up and environment creation ensure actual TASK/Checkout
  registrations through the same local operation, with machine-local supplier discovery.
- Supply scoped DNS and standalone ingress from Fight itself. DockerProxy remains
  an optional external front door, never a harness dependency. Preserve DirectMeds
  `.test`, unrelated routes and the live supplier while Pi owns TASK-00063.
- Adapt active framework consumers in separate isolated worktrees. Projects without
  an HTTP preview remain independent; no fabricated domains or automatic enrollment.
- Define the same local registration boundary for future browser Project creation.
  Hosted Project creation can offer a reviewed local enrollment command; no hosted
  installation can directly mutate an unrelated workstation's local registry.
- Provide independent DNS, TLS, proxy and application diagnostics, explicit
  enrollment/renewal/removal/recovery and persistent maintenance-stop behavior.
  Qualify current macOS/Docker operation; label other platforms unverified.
- Exclude app product behavior, public DNS, hosted contributor enrollment,
  Dashboard UI, production rollout and TASK-00063 security acceptance. Preserve
  active supplier templates and their owning checkout until an explicit safe cutover.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Select a primary or TASK checkout | Explicit local-domain preview/apply | Native Git registration, identity, ownership and conflicts | N/A — operator infrastructure | Persist only the selected local binding |
| Enroll project DNS and TLS | Explicit shared resolver and certificate operations | Namespace, listeners, CA, SANs, expiry and trust | N/A | One scoped namespace and project leaf; privileged OS enrollment is a separate human action |
| Start and browse a checkout | Existing repository up with registered binding | Canonical HTTPS root/CSRF, authority and cookies | N/A | Only the selected application uses its exact origin |
| Stop, recover or retire | Existing down plus explicit binding/certificate/resolver operations | Native health and peer preservation | N/A | No fallback to another checkout or public application; no app data/trust removal by route retirement |

## Acceptance criteria

- [ ] Explicit primary and two concurrent same-TASK registrations yield stable,
  distinct canonical names, with collision/stale-plan/unknown-checkout rejection.
- [ ] Base plus wildcard project leaf is validated and reused, with explicit renewal
  and safe removal; CA signing material is never mounted in any container.
- [ ] Shared scoped DNS and hostname routing preserve other apps and return local
  failure for unknown, stopped, unhealthy or unavailable targets, without public fallback.
- [ ] Host/browser and a named container consumer reach the intended app through
  verified HTTPS; exact authority/origin and host-only secure cookies remain enforced.
- [ ] Enrollment/removal/recovery and maintenance intent work independently of the
  Dashboard. Restart and sleep/wake claims distinguish actual evidence from configuration.
- [ ] Ordinary contributor/CI startup remains independent and required native
  qualification plus the normal full gate pass; independent Review/QA remain distinct.
