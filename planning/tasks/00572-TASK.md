# Adopt Common DBAL transaction boundary for existing persistence

## Outcome

Run existing DBAL-backed application use cases through a qualified canonical Common DBAL implementation of
`TransactionalUnitOfWork`, removing unnecessary ORM transaction scaffolding after checking actual callers.
Deliver the first complete integration slice of [TICKET-00133](../tickets/00133-TICKET.md), normally one PR.
This is a concrete persistence-consumer correction, not a package-upgrade-only or configuration-demonstration TASK.

## Scope

- Refresh the consumed Common/Access Control transaction/repository/handler contract inventory and surviving
  production/test callers. The inspected production composition uses DBAL repositories on one shared Connection
  but constructs an otherwise unused EntityManager for DoctrineTransactionalUnitOfWork; several consumer fixtures
  also construct that ORM adapter. Treat this as bounded source evidence, not proof that future ORM callers cannot exist.
- Qualify an actual supported tagged Common release with a DBAL-only implementation of the existing generic
  TransactionalUnitOfWork and its required lifecycle/failure behavior. Inspect exact signatures and affected
  transitive consumers; record version/source/Composer lock identities and deliberately update manifest/lock.
  Common v1.5.0 supplies DbalTransactionalUnitOfWork; qualify its exact released contract, not a provisional API.
- Bind the canonical implementation directly on the existing shared DBAL Connection. All actual aggregate,
  required audit/durable-intent and justified consistency participants in an operation share that authority.
  Handlers/real owning coordinators retain completion; repositories do not begin/commit, independently flush,
  intercept events for audit or accept a second unrelated write connection.
- Migrate affected consumer fixtures and actual existing persistence paths to the selected boundary, preserving
  meaningful behavior coverage. Remove unnecessary EntityManager/ORM setup and the direct ORM dependency only
  after verifying all surviving consumers, including tests and package/composition requirements. Do not replace
  actual ORM persistence with DBAL merely for uniformity; any genuine ORM participant still needs the correct
  canonical implementation and one authority for its operation, not two competing boundaries.
- Prove retained business atomicity, actual reference/expected-state consistency, committed delivery intent,
  exception cleanup and truthful uncertain/post-commit outcomes through existing owned integration paths. No
  new nested/savepoint workaround, business-aware transaction subtype, retry/outbox platform or exactly-once promise.
- Reconcile shared composition, affected test fixtures, current transaction/persistence documentation/runbooks
  and actual callers in the adoption slice. Correct descriptive collaborator names in touched owned code; do not
  hide upstream contracts behind local aliases or copy a provisional implementation into Agent OS.
- Coordinate manifest/composition overlap with TASK-00573 and TICKET-00136. Each owns its actual qualification;
  do not introduce a package-upgrade prerequisite or a universal minimum release for unrelated capabilities.

Excludes implementing/releasing Common or Access Control, vendor patches/development snapshots, blanket ORM
