# Design the CQRS and DDD architecture skill

## Outcome

A project-local `architecture` skill offers bounded, evidence-backed architecture improvement options within accepted Agent OS CQRS/DDD, package ownership and transport boundaries, without substituting itself for an accepted ADR or independent implementation review.

## Scope

- In scope: Design `.pi/skills/architecture/SKILL.md` around an explicitly scoped architecture question and affected use cases. Inspect Matt Pocock's original `improve-architecture` skill and relevant primary writing by Mathias Verraes and Robert C. Martin as possible inspiration; cite the exact sources and license/attribution requirements before adapting any material. Evaluate insights against [ADR 0001](../adr/0001-application-ownership-and-orchestration.md), [engineering standards](../../docs/engineering/STANDARDS.md), local CQRS/DDD and Fight naming, and the distinction between architectural discovery, audit and independent review. Update the [skill gap map](../../docs/engineering/SKILL_GAPS.md).
- Out of scope: Copying a third-party skill, adopting conflicting command/event names, autonomous refactoring, changing an ADR or product behavior without human decision, generating a repository-wide audit, or approving an implementation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Explore one architectural improvement | N/A — read-only examination | Inspect actual use-case flow, package ownership, decisions, boundary/transaction/effect facts and primary references | N/A | Present alternatives and trade-offs, evidence, conflicts and a recommendation or decision request, without modifying source |

## Validation and permissions

Preserve Agent OS command and event naming even when references suggest different names. Check real code/accepted ADRs before proposing abstractions; distinguish proven placement or policy faults from opinion and identify the decision owner for changes to accepted architecture. Do not lift third-party text without checking provenance/license and attribution. If a bounded issue requires implementation, propose an approved planning handoff rather than silently doing it.

## Acceptance criteria

- [ ] Scope and intake distinguish improvement exploration from cross-module `audit`, TASK-specific `review` and code implementation in `work`; outputs include concrete options, trade-offs and decision ownership.
- [ ] The skill checks Domain policy location, package-versus-owned orchestration, CQRS intent/facts, Adapter boundaries, authorization across entry paths, and transaction/effect guarantees as relevant rather than imposing generic patterns.
- [ ] Cited primary-source comparison of `improve-architecture`, Verraes and Martin explains what is adopted, adapted and rejected; local message-naming rules and accepted ADR authority win conflicts, with license/attribution verified.
- [ ] Directly qualify a bounded architecture walkthrough and links without product-suite tests of skill text; refresh planning views and run `git diff --check` and `./bin/build` with actual warnings and limits.

## Verification and evidence

Read original external sources at identified versions and local decisions before implementation. Walk a real bounded code/ADR question, documenting what the skill would conclude or escalate and why, without code edits to that use case. Validate skill metadata/references directly and run planning, diff and canonical gate.
