# Accept the application ownership and orchestration ADR

## Outcome

An explicitly accepted architecture decision defines ownership between Fight Access Control and Fight Agent OS, the narrow role of application orchestration, dependency direction, CQRS composition, HTTP interaction boundaries, authorization ownership, and transaction/effect constraints before affected production scaffolding begins.

## Scope

- In scope: Create and obtain explicit acceptance for a concise ADR covering direct Fight Access Control Domain/Application use; justified `App\Application` orchestration; Domain/Application/Adapter and composition-root dependencies; capability-oriented adapters; command/query/event dispatch; one-Action/one-interaction Action–Domain–Responder delivery; server-side authorization; transaction/external-effect boundaries; structural enforcement and deferred checks.
- Out of scope: Production scaffolding or representative code, persistence schemas, HTTP representations, authentication/invitation endpoints, React behavior, event sourcing, architecture-tool installation, upstream package changes, and speculative contexts or abstractions.

## Validation and permissions

The ADR must state that Fight Access Control owns identity and authorization Domain/Application commands, queries, entities, policies, Views, events, and capability contracts. Agent OS uses those types directly and owns framework integration, persistence, transport, composition, external effects, and only genuine application-specific or cross-boundary orchestration. `App\Application` is justified by behavior spanning ownership boundaries or application policy, never by a renaming wrapper.

Domain cannot depend on Application, Adapter, frameworks, persistence, HTTP, or external providers. Application may depend on Domain/package Domain/Application contracts and capability abstractions but not Adapter/framework implementations. Adapters implement capabilities and depend inward. Configuration/composition may know concrete outer and inner types. Business code uses injected dependencies rather than service location.

Actions map transport input and dispatch one command, query, or explicit orchestrator; they contain no business or persistence policy. Endpoint Responders own successful safe representations. Package entities, hashes, grants, credentials, and secrets are not transport models. Authorization remains server-side and permission/ownership based, with no role-name bypass.

Transactions contain business state and required durable intent, not email/HTTP/filesystem effects. Post-commit delivery and recovery belong to later requirements. The ADR must identify what architecture tooling can enforce now, what requires review or later representative code, and the owning downstream TICKET.

No runtime permission model applies. Architecture documentation and planning evidence are authorized; production structure and implementation are not.
