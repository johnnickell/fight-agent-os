# Repair API Docs navigation and Dashboard scrolling with concise navigation labels

## Outcome

Keep API documentation browsing inside the viewer, remove the reported unnecessary Dashboard scrolling on initial
load, and make application navigation concise and visually consistent. Use **API Docs** with an appropriate
presentation icon and **Invitation Admin** instead of the current longer labels. This is one bounded browser-UX
repair for the existing application frame and private documentation journey, not a new Dashboard or API feature.

The maintainer reported these issues together and explicitly authorized creation of this standalone bug TASK.
Scope and record creation are accepted; implementation, checkout choice, independent acceptance and publication
remain separate.

## Scope

- In scope: Clicking the documented `GET /api/v1/workspaces/{workspace_id}/repositories` operation without
  leaving API Docs; the relevant embedded Swagger/application-navigation integration; Dashboard initial layout
  and scroll behavior; consistent API Docs and Invitation Admin navigation/title labels; API Docs navigation icon;
  focused behavioral regressions and responsive visual evidence.
- Out of scope: Enabling live execution of Repository/Workspace operations in Swagger; changing API paths,
  permissions, credential/session ownership or documentation eligibility; implementing invitation administration,
  product Dashboard data or a new design system; vendor source patches, unrelated navigation redesign and
  globally disabling scroll to hide content.

## Reproduction and diagnosis

Source inspected at `9983c0dcfc85407f7a0f15db7da5050a22802250` on `develop` in the repository main checkout.
The preceding TASK-00513 planning edits were present and are unrelated; preserve them.

Reported reproduction:

1. With an authorized ordinary application session, open `/app/swagger`.
2. Click the displayed `GET /api/v1/workspaces/{workspace_id}/repositories` operation.
3. Expected: browse/expand that documentation inside API Docs, without executing an API request.
   Reported actual result: the application navigates to Dashboard.
4. Open/load Dashboard. The maintainer reports that it “still has a scroll on load.” Expected: no unnecessary
   initial overflow or unsolicited scroll movement. Record whether this is a visible scrollbar, a position jump,
   or both before selecting a repair; browser, viewport, zoom and exact scroll geometry were not supplied.
5. Inspect navigation: the API documentation label is too long and not title cased, has no icon, and Invitation
   Administration should instead be Invitation Admin.

Source-confirmed findings:

- `client/src/routes/applicationRoutes.ts` names `/app/swagger` **API documentation** and supplies no icon;
  `/app/admin/invitations` is titled **Invitation Administration**. `client/src/pages/SwaggerPage.tsx` separately
  hardcodes the old documentation heading. The frame renders route icons only when metadata supplies one.
- `client/src/features/swagger/mountSwagger.ts` embeds upstream operation components and has `deepLinking: false`.
  `client/src/routes/useApplicationNavigation.ts` intercepts eligible same-origin registered links at document
  level; `ApplicationJourney.tsx` sends authenticated application-root navigation to Dashboard. This is a
  plausible integration boundary to investigate, not proof of the clicked link's actual target or root cause.
- Dashboard has stacked informational panels; the frame has viewport minimum height, content padding and a
  footer. These are layout investigation targets, not demonstrated causes of excess height or scroll movement.

Confidence: high for the label/icon omissions; navigation and initial-scroll failures are user-reported and
not independently browser-reproduced during task creation. No authenticated browser session was exercised and
no API operation was executed. Capture the actual clicked element/href, route/history transition, scroll owner,
viewport and before/after geometry with disposable authorized fixtures before claiming a diagnosis. The earlier
local HTTPS documentation-availability mismatch is separately tracked by [TASK-00513](00513-TASK.md); do not
silently alter the operator's runtime or enable documentation to obtain reproduction.

## Validation and permissions

Preserve server-side READ_SWAGGER and each destination's existing permission rules, sole session/authority cache,
private viewer teardown and supported-operation allowlist. Repository/Workspace operations remain documentation-only.
Expanding, filtering or following in-view operation controls must not select credentials, execute requests or replay
mutations. Do not solve navigation by disabling all application links, weakening URL validation or admitting arbitrary
external links. Preserve valid application navigation, browser history, keyboard activation and focus behavior.

Use the existing self-contained `PresentationIcon` convention: adjacent text provides meaning, the icon is decorative
and hidden from assistive technology, with no external asset request or duplicate accessible name. Keep navigation
labels consistent without changing operation/schema descriptions that legitimately discuss documentation.

Do not clip Dashboard content, hide the footer, shrink required hit targets or apply blanket overflow suppression to
pass a viewport check. Natural scrolling remains necessary for smaller screens, zoom/enlarged text or genuinely long
content. Preserve keyboard reachability, focus visibility, responsive drawer/menu behavior and background authority
renewal continuity. Use disposable authorized browser fixtures; never capture passwords, tokens or private bodies.
