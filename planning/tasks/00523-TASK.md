# Build and deliver the exact production candidate through GitHub CI

## Outcome

The actual GitHub Build workflow produces, exercises and delivers TASK-00522's complete production candidate with
inspectable source/lock/runtime identities and verified artifact digests. An authorized consumer can retrieve the
same bytes for staging without rebuilding, deploying automatically or requiring retained Git release tags.

## Scope

- In scope: Integrate production packaging/probes with `.github/workflows/build.yml`, retain the canonical gate,
  safe candidate upload/retention/retrieval and provenance, protected build/publication authority, failure handling,
  independent retrieval verification and concise delivery guidance for environment/promotion owners.
- Out of scope: Packaging reimplementation, trigger-policy expansion, new registry/account purchases, production
  credentials or provisioning, deploy-on-merge, promotion/rollback automation, package releases, a new CI platform,
  product-suite tests of workflow configuration and standalone certification tasks.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Build and exercise the candidate in CI | Existing approved Build workflow operation using TASK-00522 | Actual checked-out commit, locks, packaging/runtime and gate/probe results | CI/build receipts, not Domain events | Build one identified candidate in CI and exercise its actual packaged runtime |
| Deliver a successful candidate | Authorized bounded artifact transfer/publication | Completed build/gate/probes, complete release set, intended channel/access and digests | Safe upload/availability receipts only | Make complete candidate bytes available without deploying them |
| Retrieve and inspect the candidate | Authorized read/download plus owning-tool digest inspection | Original manifest, complete downloaded artifacts and recorded identities | None from inspection | Verify retrieved bytes match the tested candidate; no rebuild or service mutation |
| Handle incomplete or failed delivery | Inspect original run/upload; explicitly bounded corrective operation if authorized | Actual build/upload state, retained objects and warnings | Truthful failed/partial/unknown receipts | Never label an incomplete upload or failed candidate as verified; no inferred publication success |

## Validation and permissions

Extend the existing GitHub CI path, not a second gate or replacement local architecture. Retain explicit locked
setup, the sole canonical `./bin/build`, safe gate receipts and owned-service cleanup. Use TASK-00522's production
packaging entry path and actual packaged-runtime probes; development Compose success alone is not production
artifact evidence. Record the exact checked-out source identity, including a synthetic PR merge commit when that
is what CI built, instead of claiming it was the branch head or another reviewed commit.

Preserve TASK-00129's approved filters: pushes to `develop`/`main` and PRs targeting those branches only. The
CalVer `release/<version>` branch name does not add release/tag/manual triggers or deployment authority. Eligible
PR runs can build release-branch candidates through the existing policy. Any later trigger change needs separate
authorization; do not use privileged PR execution merely to work around missing credentials or publication rights.

Build jobs have no staging/production administration or application secrets. Protect any private dependency inputs
through the supported build-secret capability, never build arguments/layers, ordinary logs, caches or uploaded
artifacts. Scope publisher permissions to the authorized channel/effect; untrusted PR execution receives no
privileged publication credentials. Explicitly handle unavailable credentials/capabilities without leaking them,
using another user's access, or reporting skipped delivery as success. No credential inspection follows from planning.

Use an existing suitable artifact channel within approved access/retention/cost constraints; no mandatory new
registry or paid service is selected. Check artifact/license visibility before publication, including private
runtime dependencies. Artifact retention must cover its declared staging/promotion handoff; report expiry or missing
bytes honestly. A download is evidence only for the actual retrieved complete set. Transport/archive checksums and
runtime image/content digests are distinct and must be labeled accurately; a tag alone is not immutable identity.

Retain a release/candidate record binding application CalVer, exact source/lock/build/runtime identities and every
required artifact digest from TASK-00522's manifest. No retained Git release tag is required. Branch movement does
not change that record; no accepted release identifier silently points to rebuilt bytes. Same-date `.2`/`.3` and
optional `-rc.N` distinguish releases/candidates under the approved numbering contract. Candidate-to-final promotion
uses the same bytes and remains TICKET-00125's explicitly approved operation, not a CI rebuild or auto-deploy.

Only successful required build/gate/packaged checks yield a verified candidate. Preserve safe failure receipts and
clean up only owned CI resources; upload acknowledgment or a green unrelated job does not prove complete retrievable
artifact availability. Failed or partial transfers remain explicit. Inspection does not repair, republish, create
branches/tags or start target services implicitly.
