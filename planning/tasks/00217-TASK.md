# Hand off human signing and verify its result

## Outcome

When a project's release policy requires a signature, Team Lead coordinates an exact, safe handoff to the
human's trusted terminal/key and resumes the **same** release Workflow only after independently verifying
the resulting local signature and its certified subject. Signing is an interactive human action, not a
Team Lead or Release Manager capability. An unknown, mismatched or unfinished signature remains visibly
blocked; a signed local result is not remote publication or completed release.

## Scope

- Read [TASK-00215](00215-TASK.md)'s current exact certification and
  [TASK-00216](00216-TASK.md)'s bounded plan plus [TASK-00212](00212-TASK.md)'s project signer policy.
  For a qualified library runbook, prepare a version-scoped handoff that names Repository/remote, immutable
  certified commit, version, tag identity and required signer, then offers the concrete *local signing*
  commands and a distinct **later** publication step. Put any generated instructions/scripts and safe
  receipts only in project-approved ignored `.runs/` storage with provenance and limited access; never
  supply an executable script that silently pushes/tags remotely or invokes a signer from an Agent session.
  For application projects, use only a qualified project-owned artifact signing mechanism **if required**;
  absence of a signing requirement is an explicit policy decision, not a fabricated signed tag.
- Give the human a separate, attributable interactive action in their own trusted terminal/key. Do not
  capture, solicit or forward signing keys/passphrases, arbitrary prompts, key agents or provider credentials
  to Agents, tools, logs, reports, generated scripts or the Workflow history. A signing plan or the human's
  verbal confirmation does not prove a signature, push or deployment. Team Lead reports exact next action
  and the source/target of a requested operation without pretending to own the signer.
- After handoff, independently inspect the project-qualified signature proof: for a library, verify local
  tag object, signer/key against current trusted policy and peeled commit against the *certified* commit;
  reject lightweight, conflicting, mismatched or retargeted tags. For an application, check the
  runbook-specific signed artifact identity/digest and signer if required; do not invent a universal signer
  or verifier. Persist separate attributed handoff, local verified result, refused/unknown and recovery
  facts in the original Workflow. On timeout, process exit or ambiguous state, reread trusted local/provider
  observations before recording success or asking for another human step. Revalidate project policy,
  candidate, checks and grant before advancing to any next effect; material drift returns to certification
  and scoped approval rather than signing over a stale subject.
- Out of scope: automatically producing a signature, pushing a tag, publishing a GitHub release, querying
  registry projection, application deployment or rollback. [TICKET-00057](../tickets/00057-TICKET.md)
  independently revalidates signed candidate and owns tag push/publication; TICKET-00058 owns any required
  application provider effect.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Prepare signer handoff | Scoped same-Workflow prepare/handoff operation | Current certified subject, signer/runbook policy, plan and allowed target | Attributed handoff fact with secret-free script/evidence identity | Human receives exact trusted-terminal instructions; no Agent signing or remote effect |
| Inspect signed result | Scoped verify/resume operation only after human action | Actual local tag or signed artifact, trusted signer identity, peeled commit/digest, current policy and certified subject | Independently verified, conflicting or unknown local result fact | Advance same Workflow only with current verified local proof, not a verbal claim |
| Resume uncertain handoff | Existing inspect/recover operation | Persisted handoff/result identities, current filesystem/provider and Workflow stage | Reconciled blocked/result fact where independently proved | No second release TASK or fabricated signature, push or deployment |

Descriptions leave provider-specific verification to qualified adapters and project tools, not a shared
signing executable.

## Validation and permissions

Only a permitted human can perform the interactive signer step in their own environment. Team Lead may
prepare safe instructions and request verified inspection but has no key access or publication grant.
Check current Workflow claim, actor direct Permission, bound certified subject/runbook/plan revisions,
trusted signer identity and evidence digest. Keep actual key material out of Agent processes and evidence;
postconditions must be independently checked before advancing. A changed tag, unsigned/lightweight tag,
unknown signer, different commit/artifact, stale checks, failed verification or absent required tool produces
a safe Needs Human/blocked next action. A verified **local** signature remains distinct from a remote tag,
GitHub release, registry result, deployment or TASK `done`. Do not reissue expired approval implicitly.

## Acceptance criteria

- [ ] A required signing handoff specifies exact candidate/tag or artifact and trusted signer, with separate
  human local signing and later effect instructions; Agent credentials, environments, receipts and scripts
  contain no signing secrets.
- [ ] Only independently verified current local signer proof and exact peeled commit or artifact digest lets
  the same Workflow advance; a spoken claim, stale result, wrong signer, lightweight/conflicting tag or
  unknown tool state cannot.
- [ ] Optional signing is skipped only by qualified project policy; duplicate/interrupted handoffs reconcile
  in the same history without duplicate TASKs, silent re-signing or remote effects.
- [ ] TICKET-00057/00058 must recheck current effect authority and provider state; this slice cannot push,
  publish, deploy, roll back or mark release `done`.

## Verification and evidence

Test owned handoff subject/scoping, secret redaction, policy-required/optional signing, signer/postcondition
matching, stale certification/approval, mismatched tag/artifact and interrupted/repeated verification using
focused Application/API and important integration behavior. Qualify target-owned Git/signing or artifact
verifier and trusted signer with their own tools in authorized disposable state; synthetic fixture outcomes
do not prove a real signer or publication. Do not product-test generated instructions, signer CLI, runbook
prose, config or infrastructure. Run focused checks and `./bin/build`; record fresh counts, signer-policy
qualification and warnings without exposing private material. Formal review and delivery are separate.
