# Represent and validate current delivery handoffs offline

## Outcome

Give current delivery handoffs explicit authoritative identity and consistent generated views in the Agent OS
reference implementation. Ordinary planning checks and explicit refreshes remain network-independent, and
historical prose, `done` or an ordinary PR URL cannot silently become current delivery authority.

This delivers the offline use case of [TICKET-00119](../tickets/00119-TICKET.md), consuming the Land ownership
contract from [TASK-00515](00515-TASK.md).

## Scope

- Inspect and qualify Fight Common's current-delivery marker and generated-view implementation before reuse;
  distinguish its actual source behavior from historical work receipts and independent acceptance.
- Define and document the minimal current-handoff representation linking an authoritative subject to an exact
  PR/repository identity. Use Common's `delivery: awaiting-merge` convention as a reference, not an unqualified
  compatibility guarantee.
- Implement offline validation of marker/subject/PR identity and generated current-handoff views in the Agent OS
  planning tools. Update necessary reference-project conventions and shared guidance about their authority.
- Derive current delivery views from authoritative records; authored current handoffs agree with or point to
  that authority. Retain distinct planning/decomposition handoffs and existing Board selection/order.
- Keep ordinary read-only checking non-mutating and explicit view refresh network-independent. Preserve
  historical acceptance/checkpoint content without scanning it to infer current claims.
- Out of scope: live hosted verification and routing integration (TASK-00518), post-merge correction mechanics
  (TASK-00516), ten-project alignment (TICKET-00120), application/runtime changes and unrelated planning cleanup.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Check current delivery identity locally | `./bin/planning-check` | Authoritative subject/PR metadata and generated current views | N/A — tooling only | Read-only success or precise malformed/stale-state failure; no live-freshness claim |
| Refresh authorized current views | `./bin/planning-check --write` | Validated source records and existing parent/view rules | N/A — tooling only | Only explicit authorized local refresh; no hosted request |
| Preserve historical evidence | Ordinary check/refresh | Explicit current fields, not historical prose as live authority | N/A | Old completion and PR references remain historical; priority and planning handoffs remain intact |

No application Command, Query, Domain event, permission or database record is introduced.

## Validation and permissions

Follow [planning conventions](../CONVENTIONS.md), [landing standards](../../docs/engineering/LANDING.md),
[handoff rules](../../docs/engineering/HANDOFFS.md) and
[Writing for Agents](../../.pi/skills/writing-for-agents/SKILL.md). Keep representation and ownership documented
with the supported command shapes and failure behavior. Land owns current-handoff correction; the validator
does not infer merge, repair authored history or grant publication authority.

Ordinary validation and refresh must not require hosting credentials or network access. Reject malformed or
contradictory local identity rather than silently dropping a current claim. Read-only failure must not rewrite
records or refresh views. Preserve existing parent-rollup semantics in explicit write mode and report actual
changes. Do not infer independent acceptance from valid metadata or a fresh generated view.

## Acceptance criteria

- [ ] Common's reference behavior is inspected and the qualified representation, supported command shapes and
  local identity rules are documented for Agent OS without claiming fleet compatibility.
- [ ] Current handoffs explicitly bind their authoritative subject and exact PR/repository; `done`, historical
  prose and unmarked PR links cannot independently create a current delivery claim.
- [ ] Offline validation rejects malformed identity and stale generated current views with actionable errors,
  while read-only success and failure leave tracked files unchanged.
- [ ] Ordinary checks and explicit refresh remain network-independent and usable without hosting credentials;
  neither claims live PR freshness.
- [ ] Generated views and necessary authored pointers are consistent without altering historical evidence,
  Board priority, active-work selection or the distinct planning/decomposition frontier.
- [ ] Direct tooling evidence, planning validation, canonical full gate and independent review/QA identify the
  actual candidate, warnings and limitations. Project rollout is not claimed by reference implementation alone.
