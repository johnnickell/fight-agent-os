# Make invitation API throttle tests deterministic

## Outcome

Remove the concrete local-delivery blocker exposed while landing TASK-00537: invitation API throttle verification
must not pass or fail depending on which side of a wall-clock minute the requests execute. Preserve the existing
production admission policy and prove same-window refusal and next-window admission through the real HTTP and
PostgreSQL boundaries with coherent, explicitly controlled fixture time.

## Reproduction and diagnosis

TASK-00537's one explicitly authorized resumed canonical gate, `20261026T153751Z-14085`, failed at
`InvitationApiTest::testThrottleAndStatusInput`: the second issue request returned HTTP 201 instead of the
expected 429 (`tests/Integration/Postgres/InvitationApiTest.php:497`). All 1,904 backend tests ran, with
21,791 assertions and this sole failure; source remained unchanged. Guarded schema cleanup succeeded and
later gate phases did not run. The second response carried an expiry timestamp at exactly 15:43:00 UTC;
the test ran for 0.669681 seconds.

Read-only inspection establishes the clock-sensitive assumption: the fixture reads wall time and does not
replace the application's `Clock`; the test constructs a one-request, 60-second policy with that application
clock. `PostgresInvitationRateLimiter::consume` aligns fixed windows to minute boundaries and expires rows at
`window_end <= now`. Crossing the minute legitimately admits a new request. The first request timestamp was
not retained, so the precise historical crossing is consistent with, but not proven by, the failure evidence.
Do not turn that limitation into a claimed product-policy defect.

The same test's status-read assertion previously failed across a suspected minute boundary in TASK-00513's
historical completion notes. That TASK delivered CI/TLS integration, not this fixture repair; no existing
standalone owner for this bounded clock correction was found in the inspected live/archive records.
TASK-00078 records an accepted coherent-fake-clock approach for a different invitation-recovery test, and
[backend testing standards](../../docs/engineering/BACKEND_TESTS.md#deterministic-test-time) already require it.
Do not reopen either historical TASK or broaden this into a suite-wide conversion.

Canonical local diagnosis and failed-gate evidence are retained outside disposable checkouts under
`.runs/tasks/TASK-00537/runs/land-20261026/`, especially `diagnosis.md`, `final-gate-resume.log`,
`gate-20261026T153751Z-14085/receipt.json` and `resumed-failed-backend-reports/`. These are ignored maintainer
