# Read a complete authenticated Feature catalog

## Outcome

One authenticated `GET /api/v1/features` returns every Feature within a bounded complete response, including OFF,
with safe settings and package-computed availability for the current User. Concurrent changes cannot turn a page,
partial result or inconsistent binding into a successful complete catalog. Confirmed complete-empty is valid.

## Scope

- In scope: Current User authorization, package query/availability composition, bounded coherent enumeration,
  explicit safe HTTP projection, no-store/errors, package/PostgreSQL/HTTP evidence and documented limits.
- Out of scope: Browser integration, management writes/Permission grants, anonymous/Agent catalog, another
  evaluator or registry, runtime provisioning, push infrastructure and a dummy product Feature.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Read the complete catalog | N/A — authenticated read | Direct package `ListFeatures` pages and `FeatureAvailability` for the admitted User | N/A — no business event | One complete safe response, including unavailable rows; no business mutation |
| Inspect a known missing binding | N/A — read cannot repair | Exact original Permission ID and safe `FeatureView` binding marker | N/A | Retain identity, nullable name and explicit repair marker with `available: false` |
| Reject incomplete or failed observation | N/A | Bounded enumeration/consistency qualification | N/A | Safe correlated error, never an empty/partial successful catalog or permissive fallback |

## Validation and permissions

Consume TASK-00293's package/persistence and authoritative HTTP boundary, including TASK-00117 transitively.
Require an active current User for every invocation, not a supplied principal/target ID, JWT Permission snapshot,
role shortcut or client `/me` data. This approved read is available to all signed-in Users without
`VIEW_DASHBOARD`, testing or management Permissions. It is not anonymous, Agent authentication or a new public
exception. Enforce the read policy in the owning Application composition as well as the HTTP gate; unqualified
direct callers cannot select another User or bypass authentication. Do not flag the catalog itself or make
reading OFF records depend on those records being available.

Use direct package `ListFeatures` through the existing Common query bus and package `FeatureAvailability`.
An owned Application operation is justified by authenticated complete enumeration, consistent composition and
safe per-User results, not by renaming a package query. Keep SQL/framework/transaction adapters out of the Action
and inward orchestration. Do not copy status policy, return entities, patch vendor code or introduce a second
Feature repository contract. Record the actually qualified package/Common versions, source and Composer lock.

Deliver one fixed complete-response protocol: a JSend data object with `features`, exact `total_records` and
`complete: true` only after successful full assembly. Each item explicitly maps safe `feature_id`, immutable
`name`, `status`, original `permission_id`, nullable `permission_name`, `binding_missing` and Boolean `available`.
Do not serialize the package View wholesale: edit revision/detail belongs to separately protected management
reads, and no principal/grant/session/credential/provider or persistence internals enter this catalog. Use safe
snake_case HTTP fields and truthful OpenAPI for the real endpoint, not another spec-serving route.

No client pagination, filtering, sorting, arbitrary query fields, request body or actor/Permission input is needed.
Server-owned `ListFeatures` pages have fixed bounded size and deterministic total ordering. Validate page numbers,
counts, progress, complete unique identity/name enumeration and safe View shape; reject malformed/duplicate/
mismatched records and positive revision violations internally. Do not trust package array casts as HTTP input
validation. Establish and document finite row, page/query, serialized-byte and whole-operation/lock-wait limits
before exposing the endpoint; caller input cannot increase them. Exceeding any limit is a safe unavailable/error,
not a truncated success, a streamed partial catalog or unlimited retry. Buffer/validate before sending success.

The inspected `PostgresFeatureRepository::getAll()` fetches rows and count separately; `ListFeaturesHandler`
then reads Permission definitions, and availability rereads Feature/binding. A stable count, repeated page,
final digest or entity revision alone does not establish completeness under concurrent insertion/deletion.
Own qualification of a bounded coherent read boundary across those operations using existing canonical
connection/reference ownership. Reuse the established READ COMMITTED reference protocol where applicable;
qualify every relevant writer rather than assuming an advisory lock protects unparticipating paths. In particular,
the inspected Permission `add()` does not acquire the reference fence, unlike replace/remove. Account for actual
creation and missing-binding transitions as well as Feature create/rebind/status/remove and Permission changes.
This is a catalog consistency obligation, not a claim of a reproduced defect in the existing storage supplier.

Keep transaction ownership explicit through the canonical capability if the selected protocol requires a
transaction; query handlers own no inner transaction. Repositories must not secretly begin/commit transactions,
and a GET must not flush unrelated pending writes, audit, repair or publish facts. No new global epoch/catalog
store, long-lived cross-request snapshot, held browser cursor transaction or second write connection. Do not weaken
the package's fresh-per-call availability contract with cached repository results or a stale isolation snapshot.
Prove finite lock lifetime, cleanup on error and no stale/closed manager reuse. Missing supported guarantees hold
the affected path for owner resolution rather than accepting uncertain completeness.

For each healthy row, evaluate package availability with the same admitted immutable User snapshot and the
original bound Permission ID. Do not infer testing rights from Permission names, ROLE_SUPER_ADMIN or defaults.
A narrowly qualified missing definition may retain the package View's `binding_missing`, null name and false
availability; an exception named binding failure alone is insufficient to excuse an inconsistent observation.
Mismatched IDs, invalid hydration, vanished/reintroduced Feature identity, arbitrary exceptions and database
outages fail the read. Never blanket-catch all package failures into false, fabricate a replacement Permission
or repair state on GET. Runtime enforcement retains TASK-00293's stricter error behavior independently.

A complete result is a bounded observation for one admitted principal, not a durable grant or atomic snapshot
with a separate `/me` request. Subsequent operations still resolve current authority and recheck Features.
Use `Cache-Control: no-store` for success and private error responses, existing sanitized correlation/error
ownership and bounded authenticated resource protections. No conditional cache reuse or raw SQL/exception output.

## Acceptance criteria

- [ ] All currently authenticated Users can read the same complete safe identities/settings, with appropriate
  per-User availability; anonymous/invalid/revoked authority and unqualified direct calls receive no catalog.
- [ ] Empty is explicitly complete; multiple internal pages enumerate every Feature exactly once, including OFF,
  and all row/byte/time bounds fail safely without success-prefix/partial publication.
- [ ] Controlled concurrent creation/removal/reintroduction, status/rebinding and Permission changes cannot produce
  a false complete result or mixed identity/availability; count equality is not treated as sufficient proof.
- [ ] Known missing binding remains safely visible and unavailable; same-named IDs, invalid state, outages and
  uncertain observation never grant availability or masquerade as ordinary OFF/empty state.
- [ ] Real HTTP shape/no-store/current-authentication behavior and direct package composition are qualified;
  no mutation, implicit repair, business event or hidden management authority is added.
