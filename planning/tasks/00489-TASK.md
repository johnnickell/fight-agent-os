# Use authorized repository worktrees across Pi skills without repeated approval

## Outcome

An operator authorizes a repository once, then uses its verified Git worktrees through every applicable Pi
skill without separate worktree enrollment, per-file access approval, or shell read/write workarounds.
Work can create and immediately use an isolated checkout; independent Review and QA can inspect it and publish
their canonical reports in the base checkout; Land can complete its authorized delivery. Existing role limits
still determine which files each agent may edit.

This repairs the concrete TASK-00488 handoff failure: a Reviewer in the main checkout could identify the repair
worktree through Git but received `root-denied` when reading its TASK. Starting inside a separately enrolled
worktree still does not grant the base checkout's canonical report paths. This task restores the complete
isolated workflow, not just the first successful source read.

## Scope

- In scope: Automatic resolution of the enrolled repository, selected checkout, verified linked worktrees and
  canonical base/report locations through trusted Git/filesystem metadata, including worktrees outside the
  main checkout and worktrees created after the current session started.
- In scope: Ordinary native reads and role-appropriate `write`/`edit` across those locations, portable governing
  instructions, optional Jev discovery within the inherited repository disclosure, and consistent native
  interactive, fresh delegated, resumed and restarted sessions.
- In scope: Worktree access for all installed project skills; one shared access contract with an explicit
  skill/effect inventory, including Build's stage preflight and canonical Review/QA handoffs.
- In scope: Lifecycle, revocation, exclusion propagation, task-owned report writes, diagnostics, owning-tool
  regression coverage and actual native Pi qualification.
- Out of scope: Trusting unrelated repositories or directory trees, relaxing secret/runtime protections,
  general filesystem access, changing command-risk approval policy, provider/budget changes, new skill powers,
  managed PHP Workflow implementation, OS confinement, merge/release/deploy authorization, or automatic
  worktree creation when the operator has not selected that workflow.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create or reuse an isolated task checkout | Existing Work/Build worktree flow; native read/write/edit | Verified repository/common-directory/worktree membership and selected task | Existing access/status diagnostics | Normal source work without worktree setup or file-access prompts; no operator-account or budget reset |
| Review or QA from either checkout | `/skill:review`, `/skill:qa`; native file tools | Selected source, task evidence, canonical base report paths | Existing reports/status | Source readable; own reports/scratch writable at canonical base paths; source writes still rejected |
| Complete authorized delivery | `/skill:land` and existing Git operations | Accepted reports, task/branch identity and current ownership | Existing delivery receipts | Owned planning/source reconciliation and report writes work across the selected checkout/base boundaries |
| Run other skills in a worktree | Existing installed skill entrypoints | Governing instructions, target planning/source and selected references | Existing skill outputs only | Same repository access, with only the effects already authorized for that skill |
| Remove, move or revoke a worktree/repository | Existing operator/Git lifecycle | Current canonical membership and standing authorization | Concise actionable denial/status | Stale target access withdrawn; unaffected authorized checkouts remain usable; no fresh approval for valid members |

## Validation and permissions

John authorized this planning-only follow-up on October 16, 2026, for publication with
[TASK-00488's PR #108](https://github.com/johnnickell/fight-agent-os/pull/108). The requested policy is that
existing repository authorization covers its verified worktrees automatically. A skill-created worktree needs
no second operator confirmation or manual `/file-screening setup`. This must also work in an already-running
session anchored in the main checkout; changing the shell directory alone is not the access mechanism.
First authorization of a genuinely different repository remains separate.

Derive repository relationships from canonical filesystem identity and Git's registered worktree/common-dir
metadata, not a remote URL, matching directory/branch name, model-supplied JSON or a relevance judgment. Validate
membership and current role again before effects. Preserve explicit exclusions in every checkout, including
repository-relative excluded paths, `.env`, `.env.local` and other protected secret variants; `.env.example`
remains an ordinary role-editable file. Keep operator credentials, unrelated worktrees/repositories and live
harness resources protected. Native metadata lookup may inspect the necessary Git pointers without granting
general direct writes to Git internals. Revocation of the repository applies to its worktrees; a removed stale
registration must not invalidate unrelated valid projects or reset any enrollment/accounting record.

Access follows the selected task and existing skill authority, not blanket write access to every checkout:

| Skill or group | Reads without additional access approval | Permitted writes without additional access approval |
|---|---|---|
| Work / Engineer | Selected repository worktrees, governing instructions and required canonical evidence | Ordinary task-owned files in the selected implementation checkout, including planning/skills and `.env.example`, plus task scratch; no accidental writes to another checkout's source |
| Review / Reviewer | Selected source, requirements and relevant base-checkout evidence | Its canonical `.runs/reviews/<TASK-ID>/` report/history and task-owned scratch; never source, tests or planning |
| QA | Selected source, requirements, review and QA evidence | Its canonical `.runs/qa/<TASK-ID>/` reports/captures and task-owned scratch; existing isolated execution effects remain allowed, source edits remain denied |
| Land | Selected implementation, base planning and canonical Review/QA evidence | Task-owned delivery/reconciliation files in the intended checkout and canonical delivery scratch; Git/publication authority still comes from the existing invocation |
| Build / Team Lead | Required source/planning and every delegated stage's canonical reports | Task coordination ledger, requests and scratch; no source-write promotion; child roles retain their own limits |
| Next, Fix, Audit, Architecture, Security Audit, Adopt, Design Review | Their selected repository/worktree inspection targets and governing instructions | Only reports/scratch or planning outputs already permitted by the invoked skill; inspection is not implementation authority |
| Grill, To Tickets, To Tasks, Wayfinder, Research, Design, Prototype, Writing for Agents, Graphify | Required target instructions, planning and source | Only explicitly authorized planning/design/prototype/instruction/graph outputs in the selected checkout; query-only modes remain read-only |
| Release | Required release source, planning and evidence | Only files and effects already authorized by its release workflow; no new signing, publishing, merge or deployment permission |

Inventory the actual installed skills during implementation and explicitly account for modes/aliases and any
additional discovered skill; do not silently default unknown roles to elevated writes. Use trusted operator or
launcher selection consistent with TASK-00488 role-restoration safeguards. A Markdown instruction alone does
not grant access. The skill contract may be narrower than its transport role and must remain so.

Resolve canonical report paths through Git metadata, preserve the current report publication/atomic-replacement
rules, and allow the exact task-owned output directories even when outside the selected worktree. Do not move
reports into disposable worktrees or grant all of the user's home or all sibling checkouts merely to fix access.
Required report parent creation is included. Shared instructions remain portable to other enrolled repositories;
no hardcoded provider checkout path or copied policy file is required.

"Without approval" here means no extra worktree-enrollment or ordinary file-access prompts once the repository,
task and workflow are authorized. Jev remains optional discovery with strong guidance for unfamiliar reads.
Final Agent/user shell commands retain their existing role-aware risk assessment and any independently required
command approval. Routine file access must not be routed through a command-approval workaround. No provider call
or receipt is needed solely to recognize repository/worktree membership or read a known permitted file.

## Acceptance criteria

- [ ] With only the repository enrolled, Work creates an external linked worktree and immediately reads/edits
  its normal task files through native tools in the same main-anchored session, with zero worktree/file-access
  confirmations and no enrollment, disclosure, credential or budget reset.
- [ ] An existing linked worktree and a newly started session rooted there inherit the same repository access
  automatically. Build preflight and each fresh delegated role use that access without manual setup or silently
  falling back to an unscreened/unenrolled execution profile.
- [ ] Main-to-worktree and worktree-to-base reads succeed for selected task requirements/source/evidence. All
  roles can read required AGENTS, README, Board, Roadmap, selected skills and native documentation; ordinary
  exclusion and bounded-read rules still apply.
- [ ] Every skill/group and applicable mode in the inventory is mapped and exercised against its permitted
  effects. Work/Land source edits succeed where authorized; Reviewer/QA and coordinator source edits fail;
  `.env.example` succeeds for eligible writers while protected secrets remain denied.
- [ ] Review, QA and Build create/read/update their actual canonical task-owned reports, histories and scratch
  in the base checkout while running from an external worktree, using native file tools. Unrelated task output
  overwrites and source promotion remain denied. Existing atomic publication and evidence preservation work.
- [ ] Unrelated repositories (including clones with the same remote), forged Git pointers, symlink escapes,
  excluded files and stale/replaced worktree identities cannot gain access. Existing inode/runtime protections
  remain effective; no arbitrary parent-directory or operator-state grant is introduced.
- [ ] New/moved/removed/pruned worktrees, restart/resume/fork/tree navigation, role changes and repository
  revocation are covered. Revalidate pending operations before effects; a removed target is denied without
  breaking other valid checkouts or reactivating historical privileged authority.
- [ ] Read/write authorization and optional Jev disclosure use the same verified repository scope; direct reads
  make no provider call, command-risk assessment remains intact, and shared monthly usage/liabilities are
  preserved across worktrees. Unsupported metadata yields a specific recovery action, not a shell workaround.
- [ ] An isolated native flow proves Work creates/edits a checkout, independent Review reads it and publishes
  its base report, QA reads/publishes evidence, and Land consumes both and edits only owned delivery metadata.
  No manual worktree enrollment or file-access approval occurs; real push/merge is not needed for this probe.
- [ ] Regression-first owning-Harness/native checks, current supported Pi compatibility checks, strict types,
  planning validation and the canonical full gate pass; fresh independent review and affected QA confirm the
  behavior. Documentation explains inherited worktree access, role boundaries and actual recovery actions.

## Verification and evidence

Reproduce both initial failures before repairing: an enrolled main session reading/editing its new external
worktree, and a worktree-rooted Reviewer/QA writing the canonical base report. Add meaningful failing regressions
at the owning Harness seams, not product-suite tests of skills or test tooling. Use disposable Git repositories
with real linked-worktree metadata and the actual native Pi tool/lifecycle pipeline; distinguish controlled
provider results from live provider qualification. Count access prompts separately from existing command-risk
prompts and assert the absence of forbidden effects as well as successful reads/writes.

Use the repository wrappers and [engineering verification rules](../../docs/engineering/EXECUTION.md), including
`./bin/harness-check`, `./bin/planning-check`, `git diff --check` and `./bin/build`. Exercise success, role refusal,
external report creation, stale membership and cleanup without changing the operator's real enrollment or
removing live worktrees. Keep evidence under ignored task scratch; retain canonical handoffs outside disposable
checkouts. Document any native-version or environment limitation without treating it as a pass.
