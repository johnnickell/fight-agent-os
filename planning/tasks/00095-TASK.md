# Version TASK sequencing and queue overrides

## Outcome

Authorized planners can semantically sequence TASKs and set or clear explicit attributed queue overrides against expected revisions, including direct placement for standalone work, while blocked or archived work retains priority for later eligibility.

## Scope

- In scope: Workspace-scoped authored TASK ordering with optional Repository filter; lower-positive-ranked-first/unranked-last semantics and stable Repository/TASK-reference ties; inherited Roadmap grouping/priority; explicit `ReorderTasks`, `SetTaskQueueOverride`, `ClearTaskQueueOverride` commands and semantic events; standalone bug/chore direct placement; normalized queue override position and rationale/provenance; preview/impact/current/history queries; expected ordering/override/constraint revisions and idempotency; transactional streams/current projections/rebuild; separate repository/workspace reorder and override Permissions; PostgreSQL concurrency; versioned API/OpenAPI.
- Out of scope: Executable eligibility calculation, lifecycle/status transitions, manual Blocked/Hold, dependency changes, claims, Runner/capability availability, provider inference, Markdown import/cutover, browser drag/drop/components and automatic clearing due to blockage/archive.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Reorder authored TASK sequence | `ReorderTasks` | Preview inherited Roadmap grouping, current TASK order and expected revision | `TaskOrderRevised` or equivalent | Authored TASK order changes atomically without changing lifecycle or eligibility |
| Set queue override | `SetTaskQueueOverride` | Preview inherited priority, authored order, existing override, blockers and resulting position | `TaskQueueOverrideSet` | Explicit attributed priority persists for the TASK until superseded/cleared |
| Clear queue override | `ClearTaskQueueOverride` | Preview resulting inherited Roadmap/TASK placement and current override revision | `TaskQueueOverrideCleared` | Override ends semantically; inherited ordering becomes effective without rewriting it |
| Inspect queue priority | N/A — read-only interaction | Get current authored/inherited/override positions and semantic history | N/A — reads emit no Domain event | Safe Views explain why a TASK occupies its priority independent of eligibility |

## Validation and permissions

Use stable TASK identities from TICKET-00026 and Roadmap revisions from TASK-00094. Authored TASK order is workspace-scoped and may be filtered/reordered within an authorized Repository. Lower positive ranks sort before unranked records; deterministic ties use Repository then TASK reference. Validate positive bounded positions, unique entries, active/archived identity, scope and expected revisions. Do not store a computed single rank that loses authored/inherited/override provenance.

Inherited Roadmap priority groups parented TASKs by EPIC/TICKET position and authored TASK order sequences peers. Standalone bug/chore TASKs receive explicit direct placement in the workspace/repository order without fabricated parentage. A queue override is an explicit durable attributed position among candidate work and can place independent work ahead of inherited priority. Define deterministic override ties and preserve the underlying Roadmap/TASK order unchanged.

Blocked, Needs Info, Human Action, in-progress, Done, Won't Fix and archived TASKs retain authored order/override history. Setting an override never makes work executable, changes lifecycle, removes a blocker, reopens a parent or grants authority. Clearing restores current inherited/authored placement, not a stale copied position. Override remains until changed/cleared; no automatic lifecycle/archive event clears it.

Preview authenticates and explains existing blocker/lifecycle facts for impact only. Execution revalidates identity, actor scope, expected TASK ordering/override and relevant Roadmap/constraint revisions. Repository authority affects only owned TASKs; cross-repository workspace sequence/override requires workspace authority over affected scope. Commands append semantic Planning events and update current ordering projections/idempotency atomically.

Require distinct Planning view, TASK reorder and queue override Permissions, with repository/workspace scope as justified. APIs expose safe explicit priority provenance/history without hidden TASKs, dependency details outside authority, internal stream data or provider facts.
