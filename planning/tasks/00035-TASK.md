# Independently accept the authentication and dashboard production handoff

## Outcome

An independent `design-review` invocation renders and challenges the authentication/dashboard candidate, separate design invocations resolve every blocking finding, re-review returns `accept`, and authoritative planning completion records preserve the accepted production handoff without making disposable prototype code authoritative.

## Scope

- In scope: Confirm independent reviewer and complete review target; render candidate; trace all approved routes/tasks/states/modes/viewports; challenge provenance, responsive interaction, keyboard/focus, semantics, contrast, copy, error/recovery, theme behavior, permission visibility, evidence claims, and production handoff; classify findings; coordinate separate designer revision without reviewer edits; re-review; final verdict; durable accepted handoff and limitations in TASK/TICKET planning records.
- Out of scope: Reviewer repair of the artifact, production React/backend implementation, expansion of approved product scope, merge/deployment approval, private data, broad browser/assistive-technology certification, and preserving prototype implementation as production source.

## Validation and permissions

The reviewer must be independent of TASK-00034's design author and any revision author. Intake requires the brief, alternatives, selected candidate, runnable artifact where expected, source/asset provenance, route/state matrix, claimed evidence, required viewports/modes, token/Bootstrap mapping, and candidate handoff. Missing or ambiguous material blocks or qualifies review.

Render rather than relying solely on source/screenshots when safe. Trace Login, activation, reset request/completion, dashboard, account/security, password change, sessions, users, invitation, pending-invitation recovery, root routing, unknown, forbidden, expired-link, expired-session, and system states. Review narrow/wide and system/light/dark behavior, representative loading/empty/validation/failure/success conditions, long content, and permission variants.

Challenge keyboard order/operation, focus visibility/obscuring, semantics, labels/instructions, contrast, target sizes, zoom/reflow, reduced motion, accessible authentication, status/error announcement, recovery copy, tables/forms, theme initialization/selection, sensitive URL handling, fake-data honesty, and no-client-security claims. Automated/screenshot/manual evidence cannot establish universal WCAG conformance; record untested browsers, assistive technologies, forced colors, zoom levels, content, and interactions.

A blocking finding cites an unmet approved requirement, reproducible interaction/accessibility defect, unsafe provenance/tooling/data handling, dishonest product claim, or material handoff omission. Taste/polish is non-blocking unless tied to an accepted requirement. Findings include observation, reproduction/evidence, affected user task/requirement, severity, and correction recommendation.

The reviewer has read/render/check/report authority only and does not edit the candidate. `revise` returns work to a separate `design` invocation; independent re-review is required. `reject` requires a newly authorized direction if requirements cannot be met. Completion requires `accept`; unresolved blocking findings prevent it.
