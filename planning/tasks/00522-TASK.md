# Package a runnable immutable production application

## Outcome

One complete, identifiable Fight Agent OS production artifact runs through NGINX/PHP-FPM without a source checkout.
The same bytes accept separate staging/production runtime configuration and expose explicit service/writable-state
requirements for environment owners, without replacing normal contributor workflows or waiting for production hosts.

## Scope

- In scope: Actual production packaging/build entry path, NGINX/PHP-FPM runtime, required PHP extensions and locked
  runtime dependencies, browser assets, required private exports, password corpus/licenses, immutable identity and
  runtime configuration/state contract, direct packaged-application probes and concise operator/build guidance.
- Out of scope: Hosted CI candidate delivery (TASK-00523), provisioning/public TLS/DNS, environment supervision,
  deployment/promotion, production secrets, new security/Planning/provider behavior, local installation replacement,
  a registry purchase, generic packaging framework or verification-only application.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Build the production candidate | Explicit repository build operation; no new Domain command | Exact source/locks, supported runtime inputs, generated assets and licenses | Build receipts, not business events | Produce a complete production artifact without environment secrets or checkout mounts |
| Identify and inspect the candidate | N/A — read-only owning-tool inspection | Commit, lock/build/runtime identities, artifact digests and declared contents | None | Safe provenance and missing/unsafe-input errors without mutation or secret disclosure |
| Run the packaged application | Explicit authorized bounded runtime operation | Exact artifact, required services/configuration/schema and writable locations | Existing application facts only | Serve actual browser/API behavior through NGINX/PHP-FPM, without development fallback |
| Reuse the same bytes in another environment | Explicit isolated run with separate configuration | Same artifact identity, environment-specific nonsecret settings and protected secret inputs | Existing application facts only | Run the same digest without rebuilding or copying another environment's authority/data |

## Validation and permissions

Reuse the completed TASK-00032 frontend build, TASK-00039 corpus/Argon2id, TASK-00151 validation export,
TASK-00153 OpenAPI export and existing application security/runtime-configuration contracts. Do not rebuild their
policy or treat their historical receipts as proof of new packaged behavior. Use existing Docker wrappers for
repository operations, with a bounded production build/run path rather than replacing contributor Compose defaults.

Build from exact source and locked dependencies with explicit setup; keep development-only dependencies/tools in
build stages, not the final runtime. Include actual production-required extensions/capabilities, browser assets,
private OpenAPI/validation exports, the approved hashed password corpus and its integrity/license metadata, required
runtime commands and schema migration files. Migrations remain explicit owner operations, never boot/request-time
schema mutation. Missing assets or unsupported runtime capabilities fail visibly rather than silently falling back.

Exclude Xdebug/development configuration, source mounts, tests/catalog/tooling outputs where not runtime inputs,
credentials, dependency authentication material and execution scratch. `.runs/` is never a runtime dependency.
Keep required private exports and corpus outside public static delivery; their inclusion does not expose Swagger
or private files. Existing allowlisted validation APIs retain their own safe publication contract.

Separate immutable generated build inputs from mutable application state. Declare needed writable/cache/temp/log
locations and permissions using established runtime/private-storage contracts, including `var/` where applicable;
do not hide mutations inside supposedly immutable image layers. Declare required database/services and startup
conditions early. Actual persistence/backup, mail, protected provider operation and full diagnosis remain their owners.

Accept narrowly validated runtime configuration and protected secret inputs without baking environment credentials
or origins into artifacts. Preserve ADR 0004's allowlisted public bootstrap producer/decoder contract, exact same-
origin API, CSP/no-store and server authority. No server environment dump or private config in browser assets.
Staging/production use debug off; reject invalid configuration and prohibited production debug. Existing security
requirements cannot be bypassed merely to boot a small image.

Give the candidate inspectable source/lock/runtime/build provenance and exact content identities. If NGINX and FPM
need separate images, one release manifest binds every required image/asset digest; do not pretend one component
identifies the complete application. Use TICKET-00121's application CalVer (`YYYY.MM.DD`, same-date `.2`/`.3`,
optional `-rc.N`) and `release/<version>` naming. Retained Git release tags are not required. Branch names are
mutable; exact commit and artifact digests, not current branch tips, identify candidate bytes. Never silently
rebind an accepted release identifier, and never rebuild solely to promote a candidate. This changes no package/
Harness version contract or CI trigger. No branch/tag mutation or publication is authorized by this record.

## Acceptance criteria

- [ ] Actual packaging produces the complete required runtime/assets/exports/corpus/licenses with inspectable
  provenance and digest(s), excluding development-only tooling, secrets, checkout mounts and `.runs/` dependency.
- [ ] The packaged application runs through NGINX/PHP-FPM without a checkout and exercises representative existing
  browser/API behavior, public-safe validation and required password-corpus use; image creation alone is insufficient.
- [ ] The same artifact identity runs under two isolated configurations without a rebuild or cross-environment
  authority/data reuse; required services and writable locations are explicit and work as declared.
- [ ] Private exports/corpus remain inaccessible through static delivery, public bootstrap contains only allowed
  fields, invalid settings fail safely and prohibited production debug cannot start.
- [ ] Artifact contents, actual extensions/runtime support, dependency/license identities and immutable versus
  writable paths are directly inspected. A multi-image release binds the complete set, not just a tag or one image.
- [ ] Ordinary local wrappers, contributor defaults and native checks remain usable. No completed production,
  TASK-00072 local-stack transition, final browser Planning or provider connection is a packaging prerequisite.

## Verification and evidence

Use owning build/image/runtime tools directly to build, inspect and start the actual artifact on bounded owned
local targets with synthetic configuration and isolated service data. Run representative existing application
checks against packaged serving; test any owned application change with its meaningful behavior/integration tests.
For a discovered product bug, reproduce and add a failing regression before repair through its correct owner.
Do not add product tests of Dockerfiles, Compose, wrappers, migrations, generated assets, CI or quality mechanisms,
and do not seed tooling failures to prove tools work.

Record exact inputs, artifact identities, contents/license inventory, writable/service contract, runtime observations,
failures and warnings, plus safe browser evidence where behavior is visible. Direct local configuration probes are
not public production TLS or hosted CI evidence. Run focused checks and full `./bin/build`; independent Review/QA
remain separate. Keep execution scratch/evidence under ignored `.runs/`, never inside the application artifact.
