# Preserve the current page through background session renewal

## Outcome

An authenticated user can leave and return to a browser tab, remain on a page past the principal-cache freshness
interval, and renew access credentials without losing the current page, scroll position, focus or local navigation
state. Routine successful checks run in the background without a manual refresh, full-page loading replacement,
login detour or forced Dashboard navigation. Server authorization remains authoritative on every protected request.

This repairs the delivered browser continuity/frame outcome from [TASK-00048](00048-TASK.md),
[TASK-00049](00049-TASK.md) and [TASK-00051](00051-TASK.md), rather than creating another authentication owner.

## Scope

- In scope: Existing memory-token/coordinator, sole principal cache, application routing/frame and focus lifecycle;
  automatic bounded background renewal/revalidation; same-context presentation continuity; in-memory route,
  scroll, focus and navigation-state preservation; current-generation failure/revocation handling; explicit updates
  to the affected accepted authentication contracts; regression-first and real-browser verification.
- Out of scope: New authentication endpoints or a second principal store; extending server session/token lifetime;
  server authorization relaxation; persistent access tokens, principal snapshots or private drafts; service workers,
  offline private-data caches, automatic business-mutation replay, profile/header redesign, or guaranteed recovery of
  volatile state after browser tab discard, document reload or process termination.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Return to an authenticated tab | Existing coordinated refresh only when credential renewal is needed | Inspect volatile credential budget and revalidate through `GET /api/v1/me` | Existing client lifecycle/coordination signals, not new Domain events | Same route, scroll, focus and frame remain through a successful background check; a usable token is not discarded solely because the tab was hidden |
| Reach the principal freshness interval | N/A — revalidate presentation, not a business mutation | Coalesced background `/me` read | Existing principal-generation notifications | Replace the sole projection in place; elapsed cache time alone never removes the Dashboard or requires a click |
| Renew access credentials | Existing `POST /api/v1/auth/refresh` with established cookie/CSRF controls | Current credential budget and fresh `/me` | Existing bounded cross-tab protocol and package outcomes | New access remains memory-only; no document reload, route replacement or duplicate owner |
| Observe changed authority or session end | Existing current-session logout when explicitly requested | Current server authentication/authorization result | Existing invalidation/logout/terminal signals | Remove affected unavailable content/controls, clear private state on context end and fence late responses; never replay a denied mutation |
| Recover from an outage | Explicit bounded retry after an unsuccessful automatic attempt | Retry the affected existing read/restoration | Client recovery status only | Explain unavailable verification without claiming logout or successful revocation; retain safe layout/navigation context without authorizing protected operations |

## Validation and permissions

The maintainer explicitly accepted background permission revalidation rather than treating the 60-second cache
budget as a reason to replace the page. Retain the existing maximum 60-second foreground revalidation interval
as a trigger for a coalesced background request, not a hard presentation-unmount timer. Revalidate on hidden-tab
return and relevant authorization-change/server-denial signals. Do not substitute an unchanged session-long
permission cache. Coalesce visibility/focus/timer demand and bound attempts; pause routine checks while hidden,
resume once on return, and do not turn a network/protocol failure into an endless retry or refresh loop.

Separate last-verified same-context presentation from authority to dispatch protected work. Routine in-flight
revalidation may retain the mounted page and its last-verified display, but stale/pending authority cannot admit
new protected loaders or permission-dependent actions. Show unobtrusive status when needed rather than moving
focus or replacing the frame. A failed check exposes a safe unavailable/retry state and disables affected actions;
it does not silently renew authority. A new principal updates allowed controls in place; a confirmed route denial
removes the protected outlet and presents the normal forbidden state. Known logout, revocation, identity change
or terminal authentication failure must not retain another user's or a known-revoked private view.

Keep access credentials in the existing volatile owner and refresh credentials exclusively in the existing
HttpOnly cookie. Preserve early renewal, conservative timing, clock-discontinuity rejection, CSRF/Origin controls,
server rate limits, bounded Web Locks/BroadcastChannel fallback and generation fencing. A still-usable token may
remain in memory through routine checks; an expired or invalid token never authorizes a request. Token readiness
alone never supplies a principal, and peer messages never supply trusted permissions. A server `403` remains a
denial even if old UI presentation allowed the control. No automatic mutation replay is permitted.

Before changing behavior, revise [ADR 0003](../adr/0003-browser-authentication-security-profile.md) and
[ADR 0004](../adr/0004-client-authority-and-runtime-state.md) with this explicitly authorized distinction between
routine background checking, presentation retention and genuine invalidation. Update affected session/current-
principal/frame runbooks and tests in the implementation PR. Preserve historical decisions and record the
supersession; do not leave contradictory requirements to clear valid credentials on every wake or unmount all
protected presentation at every routine check. This planning record authorizes that bounded amendment, not a
server-security or persistence-policy relaxation.

## Acceptance criteria

- [ ] A signed-in page remains usable without a refresh click after repeated foreground principal-cache intervals;
  successful automatic revalidation keeps its route, page state, scroll position, focus and sidebar state.
- [ ] Switching away and back with a usable memory token does not discard it merely because visibility changed,
  show a replacement loading/login screen, force navigation to Dashboard or scroll/focus the main content.
- [ ] Early token renewal and delayed hidden-tab return use the existing bounded coordinator and recover silently
  on success; expired/invalid credentials are never dispatched as valid or persisted in browser storage.
- [ ] The sole `/me` owner performs coalesced background revalidation, updates changed permissions in place and
  prevents stale/pending authority from admitting new protected actions or loaders without destroying routine
  same-context presentation.
- [ ] Initial boot/unknown authentication, genuine forbidden access, logout, revocation, identity replacement and
  terminal refresh rejection retain distinct safe behavior; late responses cannot restore an ended context.
- [ ] Offline, timeout, malformed response, rate-limit and exhausted-conflict cases are bounded and truthful;
  failure offers explicit recovery without redirect/retry loops, falsely claiming logout, or replaying mutations.
- [ ] Routine checks cause no unsolicited focus movement or scroll reset; explicit navigation, forbidden/session-
  end announcements and keyboard recovery retain appropriate accessible focus behavior.
- [ ] Existing authentication ADRs and affected runbooks describe the amended presentation/authority contract
  consistently, including its security limits and lack of browser-discard/reload state guarantees.
- [ ] Regression-first tests, actual narrow/wide browser continuity evidence, affected security/race checks and
  `./bin/build` pass; independent Review and applicable QA accept the implementation separately.

## Verification and evidence

### Intake diagnosis and reproduction

Source baseline: clean `develop` at `cc03e34493a34b2005297828a8b05e8ac26c6f55`.
The reported journey is: sign in, open Dashboard or another protected route, scroll away from the top, switch
browser tabs and return; separately remain on the page beyond the principal freshness interval. Expected:
unchanged destination/scroll/focus and background renewal. Reported: restoration-like page replacement, scroll
movement, and eventually a refresh click needed to regain the Dashboard.

Concrete source findings:

- `client/src/features/authority/AuthorityCache.ts` retires the projection at 60 seconds and on hidden-tab resume.
- `client/src/features/auth/SessionCoordinator.ts` retires the memory token on authenticated `resume()` even when
  it still has a usable lifetime, then enters restoration.
- `client/src/routes/ApplicationJourney.tsx` only requests stale-authority navigation recovery when its pathname/
  session effect runs, replaces the authenticated frame during stale/restoring states, and focuses main content
  when authority/credential status or title changes.
- `client/src/layouts/ApplicationFrame.tsx` owns navigation state that is lost when the frame is unmounted.

Fresh intake `./bin/client test` passed 42 files / 924 tests on the repository Docker Vitest 4.1.11/jsdom setup.
The existing tests explicitly assert 60-second retirement without polling and clearing access on wake; their
passing result supports the source diagnosis, not the desired repaired UX. No failed regression has yet been
added, and no live reproduction in the reporter's browser, exact scroll measurement or final build is claimed.
The scroll cause is strongly supported by the focus/remount trace but still needs browser confirmation.

Reproduce before repair and add the smallest failing composed regression: render an authenticated protected
page, advance the fake monotonic clock past 60 seconds with a successful controlled `/me` response, and assert
that the page is retained and revalidation happens without a click. Add hidden/visible and scheduled token-
renewal cases using the real coordinator/cache/frame composition; assert mount/state/focus continuity and bounded
requests rather than only mock calls. Verify actual scroll geometry and visibility/focus event ordering in a real
browser, which jsdom cannot establish. Include non-Dashboard routes, collapsed navigation and user-positioned focus.

Countercheck revoked permission, identity change, logout during refresh, late `/me` success/error, token expiry,
clock discontinuity, offline/recovery, 401 versus 403, 429, refresh conflict and supported/unsupported multi-tab
coordination. Inspect credentials/storage/history and network request counts without recording secrets. Run
focused frontend checks, production-backed Storybook/accessibility and browser probes, relevant existing backend
security checks, planning validation, diff checks and the canonical `./bin/build`. Record browser/revision,
inputs, expected/observed results, warnings and incomplete coverage. Do not add tests of planning text or tooling.
