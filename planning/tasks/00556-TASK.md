# Recreate disposable worktree environments for on-demand human QA

## Outcome

A maintainer can reopen a published TASK revision in an isolated browser environment after its original
worktree and Docker resources have been removed, inspect what is still running, and dispose of the QA
environment when finished. John authorized this bounded local tooling follow-up on 2026-11-01. Existing
Land/task cleanup remains unchanged and does not wait for merge or a possible future human QA session.

This is a thin convenience layer over TASK-00543's Worktrunk/Compose operations and TASK-00553's shared HTTPS
ingress, not another resource manager. Task acceptance, human QA, publication and merge remain distinct.

## Scope

- Add operator commands `bin/qa up TASK-ID [--ref REVISION]`, `bin/qa list`, and `bin/qa down SELECTOR`.
  Work qualification and independent acceptance are recorded below. Reuse native Git/Worktrunk registration,
  existing runtime locators, Compose preparation, readiness and the shared guarded removal callable.
- Resolve the requested TASK to one unambiguous published revision using existing TASK/PR delivery information.
  Resolve once to a full commit OID before allocation and display the selected revision and source. If no
  unambiguous retrievable revision exists, require `--ref`; never substitute current develop, a similarly named
  branch, another TASK or a different PR. Explicit refs also resolve to a fixed OID. Do not create a delivery
  ledger or preserve every original task worktree to support reconstruction.
- Create a separate native registered QA worktree at that revision through Worktrunk. Never repurpose an active
  engineering checkout or the main stack. Invoke the existing `bin/up --worktree` path with its unique Compose
  project, isolated database/storage and existing hostname policy; no separate Compose template or proxy.
  Keep the QA entry point available from the surviving operator checkout so an older target need not contain it.
- Prepare dependencies, assets, schema and synthetic QA accounts/data through the target revision's documented
  setup commands. QA up authorizes those operations only inside the disposable QA environment. Preserve lockfile
  versions, require declared external prerequisites, and report unsupported revisions or missing fixture setup
  honestly. Do not copy main/production databases, private settings or historical manually entered QA data.
- Repeated up for the same TASK/revision reuses its healthy QA environment without resetting data or creating
  duplicates. An existing different revision or ambiguous session requires an explicit selection or down/up;
  never silently switch a running checkout. Print the exact revision, checkout, verified browser URL and copyable
  down command only after application/setup readiness. Handle duplicate concurrent starts without duplicate stacks.
- List QA environments from native registration and existing Compose/locator metadata. Show TASK, full revision,
  checkout, URL when verified, and running/stopped/partial/unavailable status with an exact cleanup selector.
  Reuse the smallest QA-purpose annotation needed for discovery; no parallel inventory, session database,
  admission receipts, PID gates, daemon or automatic expiry service. Listing is read-only; unavailable inventory
  must not be reported as no environments.
- Down uses the SAME public task down and guarded Worktrunk removal path as Land: Docker first, then source
  and temporary QA refs/configuration. Repeated down is harmless, and interrupted creation/removal is discoverable
  and retryable through the existing locators. Reuse clean-fixture exact-revision removal qualification; do not
  fabricate a PR or rerun Land to remove a disposable QA checkout. Real dirty/unique source protections remain;
  they must not prevent independent Docker teardown.
- Update operator guidance and relevant QA/Land handoffs with the delivered commands, exact-revision semantics,
  repeatable scenario setup and explicit end-of-session cleanup. QA environments stay available until down;
  terminal/browser closure is not reliable cleanup. Failed startup attempts must attempt owned cleanup and
  report any remaining environment with its retry command instead of silently accumulating resources.
- Out of scope: changing existing cleanup timing or acceptance/merge rules; retaining original environments
  until merge; automatic merge-triggered cleanup; global pruning; a new provisioning/ownership system; custom
  DNS or hostname policy changes; production deployment; browser-managed infrastructure; implementing unrelated
  missing application journeys; automatic certificate trust or shared-ingress enrollment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Reopen a TASK for browser testing | `bin/qa up TASK-ID [--ref REVISION]` | Resolve exact revision and existing QA environment; inspect prerequisites/readiness | N/A — local tooling | Create/reuse one isolated Worktrunk/Compose environment and print its verified URL/revision |
| Find environments left running | `bin/qa list` | Native Git/Compose registration and existing locators | N/A — read-only | Report current QA environments and precise cleanup commands without starting or stopping anything |
| Finish human testing | `bin/qa down SELECTOR` | Resolve one QA checkout and inspect actual removal results | N/A — local tooling | Dispose its stack/data/route, then retire eligible QA source/refs through existing cleanup |

## Validation and permissions

These trusted local operator commands grant no application or managed Runner authority. Reject unknown TASKs,
ambiguous selectors and unavailable revisions before allocation. Resolve the chosen ref once; a later remote
advance must not change the running revision. Do not reset, force-delete or adopt an engineering checkout.
Honor existing effective-hook and source protections without adding new lifecycle holds. Reuse existing safe
setup/hook execution rules; a supplied ref is not blanket approval for arbitrary host scripts or changed hooks.
Shared ingress, main data, other worktrees and shared images/build caches retain their existing lifecycle.

Use only synthetic isolated data and existing secret-safe local account/setup mechanisms. Do not print passwords,
tokens, private environment values or certificate keys. Missing trust/ingress/setup dependencies produce actionable
prerequisites, not hidden enrollment or fallback to main. Human findings belong in the existing TASK/PR; opening
or closing a QA environment never marks acceptance, changes task status, publishes or merges anything.

## Acceptance criteria

- [x] A published TASK can be recreated at the selected full OID after its original checkout/runtime is gone;
      an explicit ref works when default resolution is unavailable, and unknown/ambiguous inputs fail before allocation.
- [x] QA up reuses Worktrunk and existing Compose/ingress preparation; its browser serves the selected source
      with isolated data, working HTTPS and a documented repeatable synthetic login/scenario setup.
- [x] Repeated/concurrent up does not multiply the same environment or erase QA data; an advancing ref cannot
      silently alter a running revision, and multiple QA environments remain isolated from main and each other.
- [x] QA list exposes running, stopped and interrupted environments with exact revision/cleanup selectors;
      it performs no mutations and distinguishes unavailable inventory from an empty result.
- [x] QA down removes the selected task resources and route before eligible source/refs/config; repeated and
      interrupted cleanup work through existing mechanisms without requiring a new publication or merge.
- [x] Dirty/unique QA edits receive the existing source protection while independent Docker teardown proceeds;
      failed startup cleans eligible allocations or reports specific remaining resources and a retry command.
- [x] Main, active engineering worktrees, another QA environment and shared ingress remain usable after teardown.
- [x] Existing Land/task cleanup and completion semantics remain unchanged; guidance names the explicit QA down
      action, fresh-data limitations and unresolved prerequisites without introducing another resource system.
