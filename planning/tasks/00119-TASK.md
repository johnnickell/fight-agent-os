# Guard user disable and enable transitions

## Outcome

An authorized operator can deliberately disable or enable one eligible user through package lifecycle commands, with immediate session/authority effects and safe audit.

## Scope

- In scope: `POST /api/v1/users/{userId}/disable` and `/enable` FQCN Actions, `DISABLE_USERS`/`ENABLE_USERS`, adapter actor/target admission and owned last-admin business safeguards, confirmation/revision, package `DisableUser`/`EnableUser`, safe responses/OpenAPI, audit and principal invalidation.
- Out of scope: General `UPDATE_USERS`, email edit, delete/restore, raw password/session mutation, broad web admin interface and bypassing package lifecycle invariants.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Disable user | Package `DisableUser` through configured CommandBus after entry admission | Resolve actor/target/current managed authority | Package user event plus safe audit | Eligible target becomes disabled; established authority fails closed |
| Enable user | Package `EnableUser` through configured CommandBus after entry admission | Same | Package user event plus safe audit | Eligible target becomes enabled without minting a new session |

## Validation and permissions

Every actual entry adapter authenticates its caller, checks the exact respective installation-wide `SUPER_ADMIN_ONLY` permission and target/scope, and validates bounded ID/confirmation/revision before configured bus dispatch. HTTP declares admission once through its Action metadata; do not add a second blanket Application gate. Under the [canonical contract](../../docs/engineering/STANDARDS.md#entry-admission-and-authorization-timing), admitted work may finish after concurrent permission revocation; the next request checks fresh authority. Self-lockout, last-effective-admin, lifecycle, expected-state and managed-policy consistency remain owned business invariants, enforced transactionally by registered handler/package coordination with required audit on one shared generic transaction. Qualify supported package participation, never nested transactions or audit side effects. Do not trust role names/JWT claims or disclose target state before admission. Inspect real supplier contracts rather than assume a version's behavior.

## Acceptance criteria

- [ ] Each transition uses only its own permission; anonymous/forbidden/stale actors dispatch no package command.
- [ ] Self/last-admin/raced/conflicting/invalid state cannot remove the final authorized administrator or create partial state.
- [ ] Package lifecycle and resulting session invalidation are observed in PostgreSQL; audit is durable and secret-safe.
- [ ] Actions/Views/OpenAPI are exact and route/target IDs cannot override actor; focused concurrency/HTTP/application checks and `./bin/build` pass.
