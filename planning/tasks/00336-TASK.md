# Load verified Skills and supporting resources in Pi

## Outcome

An admitted Pi session deliberately loads an exact trusted first-party Skill and lazily reads its verified supporting
resources, preserving origin/selection provenance while instructions remain unable to expand tools or authority.

## Scope

- In scope: Actual Pi host activation integration, held complete manifest/frontmatter, bounded lazy reads, exact
  origin-tagged model context and selection evidence, collision revalidation and current-use/host-policy composition.
- Out of scope: New protocol/server/credential path, resource authoring, generic session or sandbox engine, persistent
  cache recovery (TASK-00337), origin cleanup, arbitrary third-party/dynamic Skills and filesystem-discovery bypasses.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Select and load exact Skill | Explicit invocation or authorized bounded workflow selection | Current trust/access, resolved collision choice, exact static manifest and session admission | Safe exact selection/activation provenance, not authority grants | Verified Skill enters model context tagged with its real origin/revision |
| Read supporting resource | N/A — authorized bounded read | Held manifest entry and exact originating server bytes | Safe verification observation only | Verified requested content, never unrelated file or nested activation |
| Hold changed/denied use | Existing owning admission/hold behavior | Current origin, authority, host/session and exact reference state | Owning hold observation only | No new protected disclosure/effect or silent refresh/fallback |

actual effective choice at loading; old observations do not lock future filesystem changes. Hold complete immutable

revisions require full verification but no extra per-revision content prompt; they cannot silently replace an active
