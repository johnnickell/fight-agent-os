# Version authoritative Roadmap ordering

## Outcome

Authorized planners can preview and semantically reorder repository and workspace Roadmaps against explicit ordering revisions, giving EPICs and TICKETs deterministic inherited priority without changing artifact lifecycle, hierarchy or content.

## Scope

- In scope: Authoritative versioned Roadmap ordering model/projection over active/archived EPIC and TICKET identities; repository-local EPIC/TICKET ordering and authorized workspace cross-repository order; lower-positive-ranked-first/unranked-last semantics; stable repository/reference tie-breakers; descendant priority inheritance; explicit `ReorderRoadmap` command/`RoadmapReordered` event; normalized complete order intent, preview/impact and expected ordering revision; idempotency; event-stream/constraint/current projection persistence/rebuild; history/detail Views; separate repository/workspace reorder Permissions; PostgreSQL concurrency; versioned API/OpenAPI.
- Out of scope: Generic artifact revision/status changes, TASK order/overrides, executable eligibility, manual Blocked/Hold, hierarchy reparenting, lifecycle transitions, Markdown import, browser drag/drop/components, GitHub/provider inference and planning-authority cutover.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview Repository Roadmap order | N/A — read-only validation | Compare proposed ordered EPIC/TICKET references with current ordering revision and inherited impact | N/A — preview emits no Domain event | Authorized normalized order, omissions/additions and affected descendant priority are returned without persistence |
| Reorder inside one Repository | `ReorderRoadmap` | Revalidate active records, complete intent and expected ordering revision | `RoadmapReordered` | One semantic Roadmap revision and current order projection commit atomically; artifacts do not change |
| Reorder across a Workspace | `ReorderRoadmap` with workspace scope | Revalidate authority over all affected repositories and current workspace ordering revision | `RoadmapReordered` | Authorized cross-repository priority changes atomically without changing ownership/reference |
| Inspect Roadmap history | N/A — read-only interaction | Get current ordering revision, normalized entries, inherited positions and semantic history | N/A — reads emit no Domain event | Safe rebuildable Views explain authored and inherited priority/provenance |

## Validation and permissions

Use a closed ordering contract referencing stable Planning identities from TICKET-00026. Order is positive integer rank where authored, then unranked records, with deterministic Repository and human-reference tie-breakers. Normalize sparse/repeated requested positions into one unambiguous complete semantic result while rejecting duplicate identities, invalid ranks, unknown/cross-scope/unauthorized entries and inconsistent EPIC/TICKET ancestry.

Roadmap priority flows from ordered EPICs to their TICKETs and later descendant TASKs, while explicit child ordering refines peers under the accepted model. Reordering changes only Roadmap ordering state. It cannot alter Repository ownership, parents, statuses, archive flags, criteria, evidence, dependencies, context, claims or delivery links. Archived records remain inspectable with retained historical position but are excluded from active order unless the explicit query asks for archive.

Every preview/command authenticates the actor and resolves current authorized identities server-side. A Repository-scoped Permission may reorder only entries inside that Repository. Cross-repository workspace ordering requires workspace authority over every affected Repository and must not reveal inaccessible records. Preview is advisory; execution repeats validation against expected Roadmap ordering revision and relevant current constraint versions.

Persist Roadmap semantic events through the TICKET-00026 Planning event authority. Append, idempotency result and transactionally current ordering projection commit together on the canonical PostgreSQL connection. Competing commands against one revision yield one accepted order; stale callers receive current revision and safe intervening ordering facts without partial reorder, silent merge or repository-global locking of unrelated scopes.

Require independent Planning view, repository Roadmap reorder and workspace Roadmap reorder Permissions. HTTP Actions dispatch one query/command and explicit safe Views map to JSend `snake_case`; errors/OpenAPI follow the shared boundary. Hide inaccessible repositories/artifacts, internal stream/persistence details and unnecessary identifiers.

- [ ] Priority inheritance from EPIC/TICKET order is explicit and inspectable without changing descendant lifecycle/content.
- [ ] Preview reports normalized resulting order, affected inherited priority and current revision without persistence.
