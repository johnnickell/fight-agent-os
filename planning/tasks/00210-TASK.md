# Authorize and reconcile the same-hotfix merge-back

## Outcome

After a trusted production merge, one authorized Yes/button action can merge the exact hotfix into the
Repository-configured development base under current branch rules, verify checks and the resulting target
state, and reconcile uncertain or repeated attempts. The result is recorded **within the same hotfix Workflow
history** after PR handoff without a new TASK, Workflow or silent reacquisition of its released claim. This is
one independently reviewable authorization-to-observed-effect use case.

## Scope

- Present [TASK-00209](00209-TASK.md)'s current preview through a human-accessible button and equivalent
  scoped terminal operation, naming the exact hotfix, verified production-merged subject, configured source
  and development target identities/OIDs, limits, relevant checks and authorized effect. One Yes/action gives
  only this bounded merge-back grant; it does not approve a PR, change Planning priority or grant generic
  branch writes. Do not demand another routine strategy confirmation or infer consent from the earlier
  emergency start, PR publication or production merge.
- Implement the narrow post-PR exception to [WF-015's stop policy](../wayfinder/tickets/WF-015-define-coordinated-task-authority-protocol.md)
  for this hotfix only. Preserve original claim release and accepted PR handoff. Revalidate exact immutable
  hotfix/PR identity, trusted provider merge, configured GitFlow bases, live Permissions, scoped effect grant,
  current source and target OIDs, already-included fix, branch protection and required checks immediately
  before the effect. Persist attributed approval and durable effect intent before external branch/provider
  operations; reuse the owning recoverable-effect pattern rather than a second Workflow state machine.
- Merge or forward-port **only** the verified hotfix into the development base using the approved project
  procedure. Keep newer unrelated development changes intact and run applicable integration checks. Where
  protected-branch rules require a PR or distinct review/approval, stop at the permitted step, preserve
  pending status and await that authority; the Yes/button is not automatic PR approval or merge. Never force
  update a ref, merge development into production, retarget a signed tag or modify an unrelated checkout.
- Inspect actual remote/provider refs and inclusion after effect or lost response; record separate intent,
  verified result, blocked/conflict and recovery facts in the existing hotfix history. An already included fix
  is idempotent only after verified inclusion; stale identities, conflicts, failed checks, revoked authority
  or uncertain outcomes pause with a concrete human resolution path. Repeat clicks resume/reconcile the
  same operation, not duplicate merges. Trunk-based projects offer no operation.

## Validation and permissions

Human approval is bound to the exact Workflow/hotfix, verified production source, target/OIDs, allowed
operations and current policy; live Permissions and policy revisions are rechecked before every effect.
Triage, Hotfix Engineer and UI presentation do not inherit post-PR branch authority. A stopped Workflow
retains its history but does **not** reacquire an exclusive TASK execution claim. Provider acknowledgements,
local checkout changes and PR status alone are not verified target inclusion. Refuse missing/outdated
consent, mismatched GitFlow configuration, inaccessible target, advanced/incompatible refs, protection,
failed check or uncertain source state; recover without unsafe retry, force push, new workflow or fabricated
success. Never assert TASK implementation completion or release/deployment from this branch result.

## Acceptance criteria

- [ ] A permitted human can authorize one exact verified hotfix merge-back with a single Yes/button or
  terminal equivalent; a stale/revoked grant or changed subject/target requires new scoped authority.
- [ ] The post-PR operation remains in the same historical hotfix Workflow, with separate PR handoff,
  effect-intent and observed-result facts; it does not reacquire a released TASK claim or create another TASK.
- [ ] Verified target inclusion and applicable integration checks, not intent or provider acceptance alone,
  establish success; preserve newer development work and prohibit development-to-production merge and force.
- [ ] Protected branch restrictions, conflicts, changed refs, failed checks and uncertain responses stop or
  remain pending with precise safe next steps; duplicate clicks and retries do not create duplicate effects.
- [ ] Trunk-based/no-target policy never offers or executes GitFlow merge-back; PR approval, release and
  deployment remain outside this action.
