# Persist and discover every implementation review handoff

## Outcome

Every completed `review` invocation atomically writes its full report to the base worktree at
`.runs/reviews/<TASK-ID>/review.md`, retains the same report in unambiguous immutable sequence history, and identities
all reviewed bytes before returning a verdict. The `work` workflow automatically locates, validates, and consumes the
canonical latest handoff when revising an implementation. A later session can continue from the exact reviewed state
without relying on chat history, guessing among reports, or searching linked worktrees.

## Scope

- In scope:
  - Update `.pi/skills/review/SKILL.md` and `docs/engineering/REVIEW.md` to require the complete final report at the
    canonical base-worktree path before the reviewer returns its response.
  - Define base-worktree discovery from both the primary checkout and linked worktrees without assuming the current
    working directory is the base worktree.
  - Require atomic publication, a stable canonical `review.md`, immutable `review-<NNNNN>.md` history, exact
    TASK/target/base/head/content identity in the report, and an explicit final-response handoff containing both paths.
  - Include explicitly reviewed ignored/non-Git artifacts in deterministic snapshot identity so their mutation makes a
    report stale even when Git status and `HEAD` remain unchanged.
  - Fail closed: if the report cannot be written and read back, do not present the review as a completed handoff or
    return an actionable acceptance verdict only in ephemeral chat.
  - Update `.pi/skills/work/SKILL.md` and `docs/engineering/EXECUTION.md` so intake checks the canonical review path,
    validates that the report belongs to the requested TASK and reviewed target, and uses a `revise` report as the
    authoritative correction handoff.
  - Preserve first-time implementation behavior when no review exists, and reject stale, mismatched, partial, or
    ambiguous review files instead of silently applying them.
  - Reproduce the TASK-00005 incident and prove the corrected review-to-work handoff from a linked target worktree.
- Out of scope:
  - Fixing TASK-00005's implementation findings, changing its verdict, or treating the recovered report as acceptance.
  - Committing review reports, moving them into authoritative planning, or requiring chat/session history retention.
  - Changing design-review, landing, publication, merge, release, or deployment workflows.
  - Adding product-suite tests for Markdown workflow instructions.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Persist an implementation review | `/skill:review TASK-NNNNN` | Read TASK, target, evidence, Git common directory, base worktree, and existing sequence | N/A — repository workflow | Complete report is atomically published and read back at base `.runs/reviews/TASK-NNNNN/review.md` and the next immutable numbered history path before the verdict response |
| Resume rejected work | `/skill:work TASK-NNNNN` | Locate canonical review, validate sequence plus TASK and reviewed target/content identity, and read blocking findings | N/A — repository workflow | Revision scope starts from the unambiguous persisted `revise` handoff without requiring transcript context |
| Reject unusable handoff | N/A — workflow validation | Inspect file existence, completeness, identity, target head, and verdict | N/A — repository workflow | Missing-on-required-revision, stale, mismatched, partial, or unreadable reports stop with the exact path and reason |

## Validation and permissions

Review remains read-only over implementation and planning files. It may create its owned directory and canonical plus
numbered history reports only beneath the base worktree's ignored `.runs/reviews/` root. Resolve the base worktree through inspected Git worktree
metadata; never infer it from an arbitrary parent path, write into the linked target worktree by default, or search
unbounded home/project directories.

The report must not contain secrets, credentials, private production data, or unrelated worktree content. Create
parent directories safely; inventory reviewed non-`HEAD` and ignored artifacts by relative path, type, mode, and content
digest; write through report-owned temporary files; publish without replacing numbered history; atomically update the
canonical file; and read both files back. On any path, sequence, identity, write, publication, rename, or read-back
failure, preserve the target and state that no completed review handoff exists.

`work` receives read authority for the canonical report, not authority to alter review findings. It must distinguish a
missing report during first implementation from a missing report during an explicitly requested revision. A report
for another TASK, base/head, or superseded target is not applicable evidence.

      handoff and names the exact failed canonical path.

      findings, evidence, verification, limitations, risks, and verdict.

      directly.
- [x] `work` automatically checks the canonical path, validates report identity and reviewed target, and consumes a
      matching `revise` verdict and its blocking findings as revision input.
- [x] First implementation may proceed when no report exists; requested revision fails closed for a missing,
      unreadable, partial, stale, mismatched, or ambiguous report.
- [x] A linked-worktree demonstration proves the report is written under the base worktree rather than the target
      worktree and that a fresh `work` invocation can locate it without transcript context.
- [x] The TASK-00005 failure is recorded as the regression: the reviewer originally returned findings only in chat,
      forcing manual recovery to `.runs/reviews/TASK-00005/review.md` in the base worktree.

- [x] Version-2 snapshot identity inventories every explicitly reviewed ignored artifact and descendant by deterministic
      path, type, mode, and content digest; changing an ignored reviewed byte invalidates intake despite clean Git status
      and unchanged `HEAD`.
