# Configure protected Jev access and verify Pi readiness

## Outcome

An operator can configure protected Jev access, inspect redacted effective settings and run one fixed synthetic
readiness question from the existing local Pi Harness. Deliver a complete setup-to-result path without requiring
the browser, database Planning or managed execution service. This is the first approved slice of
[TICKET-00037](../tickets/00037-TICKET.md), normally one independently reviewable PR.

## Scope

- Extend the existing TypeScript package under `harness/pi/` with operator-facing setup, inspection and an explicit
  readiness action. Qualify the supported Pi runtime and extension lifecycle; record exact versions. Do not
  replace the main Agent provider or introduce PHP Workflow authority into the local adapter.
- Use an injected Pi-managed OpenRouter credential capability through the supported model registry API.
  Store only nonsecret connection settings in operator-owned machine-local configuration outside the repository.
  Resolve credentials only on an explicitly approved readiness action; never read/copy auth files or independently
  select an ambient fallback. Missing or failed opaque resolution produces `credential-unavailable`; Pi 1.2.0's
  `getApiKeyForProvider` returns undefined for both absent authentication and resolution errors, so do not claim
  missing versus locked/denied distinctions. Qualify supported runtime/host combinations directly.
- Select the OpenRouter Decisions API through an injected transport, validate the current contract and pin the
  exact qualified evaluator identity. Endpoint/model selection is operator-controlled, never sourced from
  repository instructions or Agent-authored request state. Reuse Pi-managed OpenRouter authentication only through
  the qualified injected API; reuse is not proof of Decisions access. Do not copy private auth files or introduce
  a duplicate Jev-specific credential store.
- Run only a fixed, bounded synthetic yes/no question in this slice, without repository/private content. Validate
  its result strictly and show readiness, categorized failures, elapsed time and available usage in redacted form.
  Readiness is tied to the effective configuration revision; changing it invalidates prior readiness.
- Define shared operator limits now: at most 64 KiB serialized decision input, eight questions per request,
  sixteen choices per choice question, two concurrent requests, a fifteen-second request timeout and no automatic
  retries. Provider limits may lower these ceilings. This readiness action uses one fixed question; general
  question submission is delivered by TASK-00159.
- Require explicit request and session spending ceilings before activation. Establish the qualified price/upper
  bound needed to reserve a bounded request before dispatch. Missing cost is unknown, never zero; retain the
  reservation for an uncertain billed result and do not automatically retry. If no defensible bound is available,
  the live readiness action remains unavailable with a precise reason.
- Provide adopter setup and troubleshooting guidance, including permitted disclosure, credential handling, billing,
  supported runtime/host and the live check's small but real charge. Do not run a check automatically on load/reload.
- Out of scope: arbitrary Agent-callable judgments, file screening, command guards, compaction, provider/model
  routing, workflow dispatch, sandbox provisioning, managed MCP service delivery and account enrollment by default.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Configure access | Set/revise operator connection and limits | Inspect redacted effective settings | Local configuration revision observation; no Workflow event | Protected nonsecret local settings; authentication remains Pi-owned |
| Check readiness | Explicit fixed synthetic check | Inspect configuration-bound outcome and usage | Check completed/failed observation | One bounded upstream request without private source |
| Handle unavailable access | N/A: no implicit repair or account mutation | Inspect missing setup, opaque credential unavailability, billing or provider denial/failure | Redacted failure observation | No fallback provider or fabricated ready state |

Names describe semantic operations, not speculative PHP classes or MCP wire contracts.

## Validation and permissions

Only the operator may configure the endpoint, evaluator, disclosure policy and ceilings; Pi owns authentication.
The readiness interaction exposes no credential retrieval tool or arbitrary payload field. Keep secrets out of
repository files, Agent prompts/tool output, sessions, logs, receipts, child environments and process arguments;
qualify the actual credential transfer and redaction behavior. Treat upstream errors as untrusted data and present
bounded safe failures instead of raw provider bodies.

This is a trusted human-operated local Pi integration. Pi-managed authentication may itself prompt for access;
its configured source and same-process key handling do not isolate the key from arbitrary same-user processes or
malicious trusted extensions. Managed infrastructure-owned credentials remain future work; do not claim
TASK-00138 qualification or local isolation. A working directory or prompt rule is not credential isolation.

Enforce the applicable payload, timeout, concurrency and spending bounds on readiness calls, including repeated
operator requests. Distinguish missing setup, opaque credential unavailability, provider access denied, billing failure,
refusal, timeout, unavailable service and malformed result. Cancel outstanding work on session shutdown/reload;
old completions cannot mark a replacement context ready. Require explicit setup and permission for live use;
planning approval itself does not authorize inspecting credentials or making provider calls.
