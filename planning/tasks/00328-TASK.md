# Create and revise scoped custom Skills

## Outcome

Authorized users create or revise database-backed Workspace/Repository Skills through bounded protected operations,
with deliberate effective-alias collision resolution rather than silent shadowing or managed-resource overwrite.

## Scope

- In scope: Custom Skill create/revise/inspect through the existing type-specific authority; exact complete static
  bundles, expected revisions, scoped effective-catalog validation and explicit collision-resolution evidence.
- Out of scope: General browser Skill authoring, repository-file editing, a second catalog, managed reconciliation,
  MCP transport/cache, host discovery implementation, automatic alias preferences, grants and session activation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create custom Skill | Explicit scoped custom creation with exact candidate and collision choice | Authorized effective catalog, references and current host observations | Committed custom creation/revision fact | New identity, immutable bundle/current selection and audit |
| Revise custom Skill | Explicit complete revision with expected selection generation | Current/history and fresh candidate/collision validation | Committed revision/selection fact | New immutable revision; existing history and pinned consumers unchanged |
| Inspect or resolve a conflict | N/A for read-only preview; revised intent requires explicit resubmission | Safe collision alternatives, exact identities and original outcome | N/A for inspection | Actionable hold or deliberate qualified selection, never implicit publication |

## Validation and permissions

Reuse TASK-00327's Skill store, scoped current management/read authority, static bundle validation and reference
fences. Managed and custom identities remain distinct; a custom command cannot adopt or overwrite a managed key,
rename historical identity or grant tool access. Generate new IDs through the owning factory/UUID library.
Reject invalid type/frontmatter, incomplete manifests, reserved names, traversal, oversize content, missing/cross-scope
references and stale expected state. No script execution, dynamic expansion or credential-bearing bundle is accepted.

Validate the effective catalog, including current database choices and bounded host observations supplied by
TICKET-00087. Personal/project filesystem Skills keep a colliding bare alias over MCP with visible conflict and
qualified alternative; personal-versus-project ambiguity requires an explicit picker/saved choice, not discovery
order. Names remain aliases rather than identity. Bind the reviewed collision choice to exact target/scope/candidate
and observation identity/freshness. Unknown, incomplete, stale or changed observations hold publication instead of
asserting uniqueness. Do not scan private filesystem configuration on the server or make client claims authority.

TICKET-00087 owns host observation/selection semantics and rechecks actual collisions at loading. Database publication
cannot lock future filesystem changes or promise permanent host uniqueness. Implement its early observation contract
independently of this completed publication consumer; no whole-TICKET or final-loader reverse dependency.

Commit complete custom state, immutable revision, expected current generation and required audit in one shared
ADR 0002 transaction, with real alias/reference constraints and all participating database writers. External host
observations are bounded inputs outside the transaction, revalidated according to their owning contract. Reads create
no revision; stale previews and pointer return cannot overwrite newer selections. Reconcile original uncertain
publication before another explicit attempt; matching bytes alone do not prove the original request committed.

Inspection requires current scope and exposes no hidden resource bodies, private paths, credentials or unrelated
host catalog details. Publication changes no active session, Agent Permission, provider disclosure or local file.
Existing template publication remains TASK-00300; no browser editor is added merely to demonstrate this capability.

## Acceptance criteria

- [ ] Actual protected custom create/revise retains complete static bundles, exact history and current selection
  without managed overwrite or source-file mutation.
- [ ] Database and applicable host collisions are visible; unresolved/stale observations block publication and
  explicit resolution retains accessible qualified identities without silently shadowing filesystem Skills.
- [ ] Current access, type/scope/reference validation and expected state protect direct and adapter paths with safe
  denied/conflict/unavailable results and no cross-scope disclosure.
- [ ] PostgreSQL competing aliases/revisions, pointer return, rollback and lost-response cases preserve atomic audit,
  immutable bytes and original-operation distinctions.
- [ ] Loading remains a separate authorized operation; later host changes are checked there and published content
  never grants authority or silently refreshes a session.
