# Prepare and certify the exact release candidate

## Outcome

The claimed release Workflow lets Team Lead coordinate project-owned preparation, independently accept
changed material where required, and certify the **exact** library source commit or application deployable
artifact/commit with fresh project-required checks. The immutable certified subject, evidence and warnings
remain inspectable after interruption. A failed, stale, incomplete or unreviewed subject pauses without a
release grant or fictional green result.

## Scope

- In the **same** Workflow from [TASK-00214](00214-TASK.md), inspect current Repository/branch/PR/deployable
  and provider state against [TASK-00212](00212-TASK.md)'s qualified versioned project runbook; prepare
  release docs, integration and a proposed release plan using Team Lead's actual scoped authority. Where
  material changes require implementation, delegate to an appropriately authorized implementer, preserve
  exact changed-tree/commit/check handoffs and obtain **non-contributing** Senior Engineer acceptance and
  applicable QA before final source integration; Team Lead neither implements beyond its grant nor accepts
  its own contributions. Do not equate an ordinary TASK PR's handoff with its merge or final release source.
- Run the project's own certification on the final actual source commit or deployable artifact/digest and
  named environment/registry after required integration, including required checks, freshness, branch/host
  observations, independent acceptance when relevant and known limitations. Bind certified version/candidate,
  Repository, runbook/context revision, base/commit or artifact digest, checks, current targets, stage identity
  and evidence provenance. A clean checkout, prior build, reviewed pre-merge tree or successful process exit
  alone is not certification. Do not make generic release check scripts or claim all projects have one tool.
- Store attributed preparation, blocked/failed/verified certification facts in the owning Workflow history
  with idempotent stage identities. On crash, lost process or stale observations inspect authoritative source,
  review and provider state before continuing this **same** TASK. Changed material, failing/unknown check,
  stale runbook, invalid acceptance or unavailable evidence invalidates current certification/next approval
  and exposes a specific recovery step; no automatic check exception or grant.
- Out of scope: release effect approval ([TASK-00216](00216-TASK.md)), signing
  ([TASK-00217](00217-TASK.md)), branch publication or merge-back, provider publication/deployment and a
  second managed review/QA implementation built solely for release work.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |

| Prepare project candidate | Scoped same-Workflow phase operations | Current project runbook, source/provider state, ownership, required changed-material review and checks | Attributed preparation/blocked facts | Authorized docs/integration/independent handoffs only, no release effect |
| Certify exact subject | Semantic certification operation after actual project checks | Final commit or deployable digest, current policy/targets, fresh checks, independent acceptance and limits | Certified/failed/blocked fact with immutable subject and evidence | One certified candidate ready for approval, no signing/publication/deployment |
| Recover interrupted certification | Existing inspect/reconcile/resume operations | Workflow stage, task/runbook revisions, pending identities and current authoritative observations | Existing recovered/invalidated fact where proved | Same Workflow, no duplicate task or inherited stale certification |

Certification is a domain-specific fact in the existing Workflow, not a new Planning lifecycle or effect queue.

## Acceptance criteria

- [ ] Team Lead prepares authorized non-human material on one release Workflow, sends material changes to
  qualified independent review and applicable QA and cannot self-accept its contribution.
- [ ] Certification names the **final** exact source commit or deployable artifact/digest and current version,
  project/target/runbook with fresh required checks and independently accepted changes where applicable;
  prior PR landing, old checks and an early candidate cannot qualify.
- [ ] Duplicate, interrupted and stale certification operations retain one attributable stage history and
  expose a truthful next action. Changed subject, invalid review, unknown/failed check or missing qualified
  runbook cannot advance to exact-effect approval.
- [ ] Real project certification/acceptance is qualified with owning tools and managed capability; no release
  effect or human signing is inferred from a certified candidate alone.
