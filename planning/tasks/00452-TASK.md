# Explain HTTP failures without changing public responses

## Outcome

An operator can explain expected and unexpected API failures using useful private diagnostics and existing
correlation references while callers receive exactly the established public response behavior. This is approved
slice B of [TICKET-00111](../tickets/00111-TICKET.md), consuming TASK-00451's diagnostic boundary.

## Scope

- In scope: Enrich the existing API failure boundary, observe direct rejection outcomes without exception fabrication,
  propagate existing validated correlation into request diagnostics, preserve single reporting ownership and
  existing response behavior, integrate diagnostic-failure isolation and bounded independent degradation signaling.
- Out of scope: Public error redesign, new global/non-API response mapper, browser Logs, authentication changes,
  full request/response dumps, safe-middleware adoption, backend/storage access and another exception serializer.

Use [WF-037's HTTP contract](../wayfinder/tickets/WF-037-define-redacted-diagnostics-and-shared-http-adoption.md#existing-common-http-usage-no-new-safe-middleware-adoption).
Retain the current API-only middleware scope, existing mapper and Common JSend APIs. Status and JSend kind remain
independent; existing 4xx `error` envelopes are not defects to convert to `fail`. Preserve safe public messages/data,
successful responses, no-store behavior and the exact validated/generated correlation policy and provenance.

Report mapped and unexpected throwables through native Monolog, with useful emitted causes/traces and permitted
context, without adding those details to public responses. Observe directly returned rejection outcomes using known
status/operation context, not by reading/logging arbitrary bodies or inventing a throwable. Keep one error reporter
for this actual catch boundary; a bus failure observation is distinct and must not be deduplicated away.

Set and retire request context around downstream work, including failures; stale context must not survive reused
services. Non-API response behavior remains untouched. Agent OS server-side browser-request coverage remains an
included source, not browser JavaScript-error ingestion; runtime/service capture remains TICKET-00112's owner.
Diagnostic failure must not replace the original success/rejection/unknown-error response or replay the handler;
response-construction failure remains a separate failure, not something logging can promise to repair.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Handle a mapped or unexpected API failure | Existing request operation only | Existing mapper and native diagnostic context | Private boundary failure observation, not a new business event | Useful diagnostic and unchanged public failure response |
| Observe direct rejection | No additional business dispatch | Known response outcome and trusted operation context | Outcome observation without fabricated exception | Expected rejection is attributable without body dumps |
| Propagate/retire request correlation | Existing request lifetime | Existing correlation validator/generator and provenance | No Domain event | Downstream logs use the correct diagnostic reference; later requests do not inherit it |
| Handle logger failure | TASK-00451's guarded diagnostic path | Independent bounded status | Safe degraded/unknown fact | Original public outcome survives when independently possible; no business retry |

## Validation and permissions

No new endpoint, permission or raw-detail response is introduced. A valid inbound correlation is a diagnostic
reference only, never identity/authorization. Preserve the existing 32-lowercase-hex validation and generation
behavior and prevent malformed/multiple/oversized values from controlling structured output or headers.

Raw exception messages may contain private material and stay in the accepted private diagnostic path. Producers
must avoid deliberate secret emission; do not add headers/cookies/tokens/URI search strings/body/object snapshots,
stack arguments or locals to enrich diagnostics. Preserve existing security/credential producer restrictions.
Use [ADR 0001](../adr/0001-application-ownership-and-orchestration.md); no Domain policy or transaction moves into
HTTP middleware. No SafeJSendErrorMiddleware/SafeHttpDiagnostics adoption or manifest/lock change is required.

## Acceptance criteria

- [ ] Expected mapped and unexpected API failures emit useful native exception/context records with current
  correlation/provenance; direct rejections emit truthful outcomes without an invented stack or body dump.
- [ ] The existing HTTP status, envelope kind, safe public message/data, response headers/cache and correlation
  contract is unchanged, including API route/method misses and non-API pass-through behavior.
- [ ] Diagnostic projection/format/handler failure cannot replace the original public outcome, recurse, retry
  downstream business work or silently assert healthy collection.
- [ ] One reporting owner handles this boundary; distinct bus/HTTP observations remain distinguishable, and reused
  context is cleared/restored on success and failure.
- [ ] Test-owned log capture preserves inspectable records and production output without global stderr filtering,
  production test-mode suppression or tests of the test runner.
- [ ] Owned HTTP/diagnostic tests, direct relevant output checks and full `./bin/build` pass with fresh evidence.

## Verification and evidence

add no demonstration product endpoint. Cover the mapping matrix, direct validation/auth rejection, unexpected and
chained exceptions, malformed/multiple correlations, success/pass-through and failing diagnostics. Compare actual
response status/envelope/headers and emitted private observations; do not infer public semantics from HTTP status.
