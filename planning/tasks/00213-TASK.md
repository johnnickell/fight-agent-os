# Resolve supported release eligibility and route

## Outcome

For one selected standalone release TASK, canonical Planning eligibility and a versioned Triage catalog
resolve whether its exact project/candidate policy supports a **distinct release** Workflow route. An
unsupported, unqualified or stale release fails safely instead of falling through to ordinary feature,
bugfix or chore implementation. This is one independently reviewable read-only selection/eligibility path;
[TICKET-00056](../tickets/00056-TICKET.md) owns the actual release start and claim.

## Scope

- Extend [TASK-00096](00096-TASK.md)'s single canonical eligibility facts/reasons for
  [TASK-00211](00211-TASK.md)'s standalone `release` kind and [TASK-00212](00212-TASK.md)'s current
  project-owned release policy. Check TASK/project identity, unarchived/ready lifecycle, relevant blockers,
  context/Repository authority, policy/runbook qualification and needed route capability without a second
  semantic readiness gate or queue. Distinguish deterministic Planning exclusions from a Planning-ready
  release TASK whose execution capability is unsupported; neither is an executable candidate.
- Extend [TASK-00203](00203-TASK.md)'s **versioned** deterministic Triage catalog with a distinct release
  candidate route only for an explicitly supported project release type/line/target, and expose the
  qualification/currentness/provenance required by TICKET-00056. The initial feature/bugfix/chore mapping
  stays unchanged; `chore` is never silently treated as `release`. No generic deployer, implied
  publication/deployment rights or automatic fallback to the standard Team Lead implementation Workflow.
- A selected release receives the bounded, permission-filtered Jev classification call under
  [TASK-00201](00201-TASK.md)'s every-selection contract. Version/qualify the expanded advisory rubric and
  typed release category/disposition rather than pretending its original three choices can classify release;
  honor material conflicts and explicit unknown/unavailable outcomes. The declared-kind **normal-route**
  fallback from EPIC-00012 is not release authorization. Stop or ask a human for a supported resolution on
  uncertain release classification; no silent ordinary route or fabricated urgency/priority.
- Return a safe proposed route or typed unsupported/stale/denied reason bound to exact TASK,
  Planning/context/eligibility, rubric/evaluator, Repository policy/runbook and catalog revisions. No
  preflight result grants start, creates a Workflow, claims a TASK or sets `done`. TICKET-00056 must
  revalidate live Permissions, eligibility, policy and route at its authoritative atomic start. Where no
  qualified release Workflow exists yet, expose unavailable route capability rather than claiming that
  planning configuration alone enables execution.

## Validation and permissions

Enforce live actor/Triage direct Permissions, Planning and Repository scope, bounded egress and redacted source
disclosure. Jev and TASK prose cannot create or approve a runbook, mutate kind, adjust Board order, select
an unapproved destination, issue a release grant or override canonical eligibility. Verify versioned
rubric/category compatibility and subject, runbook, catalog and authority revisions before displaying or
reusing any proposal. Denied egress, unsupported kind/project, stale configuration, missing qualification
and unknown evaluator state remain distinct. Existing normal kinds keep their own supported fallback; do
not route a declared release to the normal Workflow if Jev is unavailable or the release implementation is
not installed. No new launch, branch, signing, tagging, registry or deployment effect here.

## Acceptance criteria

- [ ] A currently permitted release TASK and qualified project policy are evaluated through the existing
  canonical eligibility owner and versioned catalog with a typed distinct route and exact provenance;
  unsupported route capability remains explicitly unavailable until delivered.
- [ ] Every selected release causes a bounded Jev judgment attempt under current allowed disclosure and a
  qualified release vocabulary; material conflicts, unknown outcomes and denied/stale input cannot silently
  dispatch as a normal chore or claim authority.
- [ ] Missing, incompatible, stale or unqualified runbook, branch target or route yields safe reasons and no
  execution claim. Existing feature/bugfix/chore routing and Board priority remain unchanged.
- [ ] Proposed route is advisory: only the later server-authoritative release start can revalidate and atomically
  claim, and ordinary PR landing cannot make the release `done`.

## Verification and evidence

Test owned eligibility/route decision tables and currentness, category conflict/unknown, denied disclosure,
unsupported/missing runbook, disabled Workflow capability and normal-kind nonregression through focused
Application/API behavior and important integration contracts. Qualify real Jev category/priority suitability,
latency and spend separately from fixtures; no deterministic fixture proves real release classification.
Directly validate provider/runbook support using owning tools; do not product-test Markdown, prompts,
configuration wiring, migrations or test infrastructure. Run focused checks and `./bin/build`; record fresh
counts, errors, evaluator/rubric and outstanding runtime availability/review/delivery honestly.
