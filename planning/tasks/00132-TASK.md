# Design the diagnosis-to-bug-TASK fix skill

## Outcome

A project-local `fix` skill investigates a reported problem and drafts one standalone `kind: bug` TASK for human acceptance. Implementation, failing regression and repair belong to `work` on the accepted TASK, not to `fix`.

## Scope

- In scope: Design `.pi/skills/fix/SKILL.md` with problem intake, safe reproduction or explicit limits, evidence and suspected cause versus fact, acceptance/rejection/failure and scope, bug-TASK drafting under repository conventions, human approval and `work` handoff. Compare Factory `skills/Fight-Fix-Skill.md` without inheriting its automatic repair path; update the [skill gap map](../../docs/engineering/SKILL_GAPS.md).
- Out of scope: Fixing production code, adding a regression test during triage, publishing a PR, creating a requirements TICKET for a standalone bug, silently assigning implementation, or claiming reproduction when unavailable.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Triage a reported problem | Safe, read-only diagnostic commands only | Inspect real behavior, ownership, existing records and affected contracts | N/A | Propose one human-reviewable standalone bug TASK with reproduction and verification plan; no code repair |

## Validation and permissions

Identify the repository, checkout, symptom, expected behavior, affected surface, safety of reproducing it and existing TASK/issue ownership first. Do not perform destructive state changes or expose credentials in receipts. If reproduction is risky or unavailable, record the gap and ask for evidence or human authorization rather than inventing a red test. Drafting a TASK does not approve it; avoid duplicate IDs and refresh generated planning views only after authorized record creation. Implementation starts with `work` after acceptance and checkout choice.

## Acceptance criteria

- [ ] `fix` separates evidence-backed diagnosis and human-approved standalone bug TASK drafting from regression-first implementation in `work`; does not repair or publish.
- [ ] The draft records repro steps (or exact obstacle), expected versus observed, impact, ownership, bounded outcome, permissions and failures, acceptance evidence, dependency/order and a failing regression test plan for `work` where feasible.
- [ ] The skill checks existing bug/TASK ownership and live/archive ID allocation, asks before unsafe actions, and does not silently create a parent TICKET or claim approval.
- [ ] Cited source comparison states why Factory's repair workflow is rejected; directly validate instructions and a sample bug handoff, planning views, `git diff --check` and `./bin/build`, without product tests of the skill.

## Verification and evidence

Read the Factory fix instructions and current planning/work conventions. Walk a non-destructive example from symptom through draft TASK and subsequent `work` handoff; do not manufacture a failing test or modify product code for this qualification. Verify links, read-only planning after view refresh, diff check and canonical gate with warnings noted.

## Coordination

Depends on TASK-00130's guidance and delivery baseline. Standalone chore, one independently reviewable PR on a new `feature/task-00132-<slug>` branch from `develop` in a human-selected checkout. Do not start implementation of any drafted bug in this skill invocation.
