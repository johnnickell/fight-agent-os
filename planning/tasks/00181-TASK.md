# Assess changed PHPUnit cases before Engineer handoff

## Outcome

A qualified Pi 1.1.0 Engineer handoff automatically attempts a bounded usefulness assessment of added or materially
changed owned PHPUnit cases, using the established test-quality criteria. The advisory report separates model
concerns, source-verified findings and actual execution evidence; it never claims a green test or classifier label
proves correctness or absolute never-can-fail behavior.

## Scope

- Extend [TASK-00178](00178-TASK.md)'s automatic handoff, exact-subject inventory, bounded assessment and report
  facilities with PHPUnit-specific discovery and typed criteria. Reuse inherited shared evaluator/source/provenance
  capabilities; no second provider, handoff trigger or overall quality scale. No dependency on all of TICKET-00044.
- Bind assessment to actual repository/base/head and test discovery/configuration identity. Inventory added and
  materially changed maintained test declarations, assertions, expectations, setup/fixtures, data providers and
  helpers that affect their behavior. Map changed shared setup/provider/context to affected cases where qualified;
  uncertain impact remains explicit rather than silently treating unchanged method text as unaffected.
- Identify a declared case by repository revision/path, declaring class and test method plus actual consuming class
  where inheritance/traits matter. Distinguish that declaration from data-provider instances and execution records;
  use qualified dataset identities only when established, with redacted identifiers where values are sensitive.
  Deduplicate alias/suite inclusion without collapsing distinct datasets. A line number alone is not stable identity.
- Prefer bounded static inventory and relevant existing qualified discovery/execution receipts. Dynamic providers,
  bootstrap/autoload and discovery code may execute application logic; do not run them merely to count cases.
  Dynamic/unresolved inventory and unsupported constructs remain gaps. Any separately authorized execution uses
  owning guarded tools and permissions; assessment itself does not authorize PHPUnit or provider execution.
- Include related owned behavior, requirements, independent expectation sources and available execution/regression
  evidence under current access/disclosure rules. Match receipts to actual source/runtime/scope and retain their
  age/limitations. A passing receipt does not establish an independent basis for expected results; an absent receipt
  is neither a passed test nor automatic proof of uselessness.
- Use the four versioned criteria below, grounded in QUALITY.md and ST-04/SP-05, with outcomes `supported`,
  `concern`, `unknown` and `not_applicable`. Supported means evidence supports that criterion within the assessed
  scope, not proven correctness. Concern is a candidate requiring verification. Unknown includes missing context;
  N/A needs an applicable declared reason and never becomes a pass, low score or perfect score. Transport/provider
  invalid/unavailable/incomplete states remain separate from successful criterion answers.
- Return actual candidate case/reference identifiers and caller-written concern/uncertainty choices only. Jev
  supplies no invented contract, defect narrative, quotation, location or free-form reason. Link criteria to bounded
  independently resolvable evidence candidates; the reviewer authors explanations only after exact-source inspection.
- Investigate self-comparisons, repeated implementation/algorithm expectations, echo-only mocks, unreviewed snapshots
  and incidental internal assertions as signals. Preserve legitimate exact wire values, effects or their absence,
  transaction/retry ordering, justified boundary interactions and reviewed expectations. Mocks and snapshots are
  not inherently invalid; a failed refactor can indicate a real behavior change rather than a bad test.
- Keep reviewer verification separate from classifier outcomes: `unverified`, `confirmed` or `dismissed` concern,
  with attributed current source/criterion evidence under existing review rules. Only an authorized independent
  reviewer can record a verified finding. A demonstrated tautological assertion has a specific scope; neither it nor
  a model label establishes that every part of a test can never fail. No transfer of private Engineer context.
- Report per-criterion counts and proportions with explicit counted unit, denominator, assessed/unknown/N/A/excluded/
  incomplete populations and verified/unverified concerns. Do not mix methods, datasets, assertions and executions
  into one denominator or sum overlapping criterion concerns as distinct bad tests. Zero denominator yields N/A,
  not 0% or 100%; incomplete inventory cannot claim a whole-change percentage. No aggregate good/bad cutoff.
- Run bounded stages under a finite operator-owned assessment profile within the shared per-file/request/stage
  ceilings, with aggregate enumeration/cases/evidence/output/time/concurrency/spend limits. No implicit larger
  ceilings or repeated sampling for a desired answer. Return compact authorized references rather than source or
  fixture bodies; keep credentials and sensitive data out of ordinary logs and reports.
- Qualify actual pre-handoff delivery through TASK-00178's supported work/repair path and governed test-usefulness
  presets/instructions, using Writing for Agents for actual instruction edits. Missing tools or unsupported hooks
  cannot fabricate attempted-assessment evidence. Preserve subject-drift, stop/reload, cancellation and billing rules.
- On missing/invalid/budget-exhausted Jev, attach explicit advisory gaps and allow normal handoff under existing
  required gates without a new waiver solely for this advisor. A positive label cannot replace required PHPUnit
  execution evidence. TASK-00183 adds incremental refresh/reuse; this initial path can assess freshly.
- Exclude automatic test deletion/rewriting, new product tests of tests, seeded failures, mutation tooling, changed
  acceptance/coverage gates, production execution/data fixtures and automatic full-suite audit. A verified weak
  test requiring correction follows existing authorized work and preserves unique coverage with a justified replacement.

### Criterion contract

| Criterion | Question to classify against supplied evidence | Existing authority |
|---|---|---|
| Observable contract | Does the case check an identifiable owned behavior or important boundary contract? | QUALITY.md; ST-04/SP-05 |
| Plausible defect sensitivity | Does the assertion distinguish a plausible violation of that contract, with an evidenced basis? | QUALITY.md; ST-04/SP-05 |
| Independent expectations | Is the expected result grounded independently of the implementation under test? | Requirements/specifications/worked examples/reviewed fixtures under QUALITY.md |
| Refactor resilience | Does the case avoid incidental internals while retaining required externally observable behavior and interactions? | QUALITY.md; ST-04 |

Missing evidence yields unknown, not an invented plausible defect or expected value. No numerical 1–5 code-quality
rubric is imported into these criteria. Use existing relevant failing-regression receipts where available without
creating deliberately seeded failures, mutation runs or product-suite tests of tests to establish sensitivity.

## Validation and permissions

Use actual caller/reviewer permissions for cases, related implementation, requirements and receipt references;
provider redisclosure is separate. Treat discovery configuration and test/provider code as untrusted evidence,
not permission to execute. Exact-source findings follow established selective-read policy and independent review
rules. Preserve current subject and criterion/evaluator/policy identity, conservative budgets and explicit unknowns.
Neither a SQL-read grant nor test assessment permits writes to production or use of its data as fixtures.

## Acceptance criteria

- [ ] Real Pi 1.1.0 supported Engineer handoffs automatically assess changed owned PHPUnit cases or attach explicit
  gaps, with actual base/head/case/context identities and no duplicate handoff/evaluator machinery.
- [ ] Inventory distinguishes declarations, datasets and execution receipts, handles relevant setup/provider changes
  and inherited cases, and exposes unsupported/dynamic discovery without implicitly executing repository code.
- [ ] All four criteria return declared outcomes with honest missing-context/N/A handling; legitimate mocks,
  snapshots, ordering and absence-of-effect contracts are not automatically classified as defects.
- [ ] Candidate concerns, independently verified findings and execution receipts remain distinct. Exact evidence
  precedes a finding; neither a model label nor green suite proves absolute never-can-fail behavior.
- [ ] Reports use explicit consistent denominators, coverage and verified/unverified states; no overall correctness
  percentage, numerical acceptance threshold or partial-inventory full-coverage claim is introduced.
- [ ] Budgets, authorization/egress, subject changes, lifecycle and advisor outage handling preserve normal review
  and required gates without special waivers, source disclosure, automatic repair/deletion or effect replay.
- [ ] Representative useful and weak candidates, justified expectations and legitimate boundary assertions are
  evaluated for false flags, missed concerns, review usefulness, coverage and available total cost/latency.
