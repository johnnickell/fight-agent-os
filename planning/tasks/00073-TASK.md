# Establish contained approved-root access

## Outcome

An operator can explicitly configure, inspect, change and remove bounded project roots through the installation path; the runtime exposes only canonical approved roots, rejects ambiguous or escaping paths, and reports actual access without registering repositories or granting Agent authority.

## Scope

- In scope: Versioned installation configuration for zero or more approved project roots; explicit host-side add/change/remove/status operation; canonical path and platform validation; symlink, traversal, overlap and ambiguity handling; least-privilege read/write mount declaration needed by later repository operations; runtime reconfiguration and recovery instructions; application-visible read-only root capability; safe display locators; behavior tests for owned containment policy; direct mount and permission verification.
- Out of scope: Complete-home mounts, arbitrary browser-entered host paths, Repository/Host/Checkout/Worktree identity, repository registration, Git identity validation, branch changes, worktree creation, Planning import/cutover, Agent runner mounts, sandbox enforcement, source mutation, remote filesystems, and automatic host configuration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Add an approved root | N/A — explicit installation operation, not a Domain command | Validate canonical host path, containment shape and intended runtime mount | N/A — installation configuration is not a filesystem Domain event | Versioned local configuration changes and requires an explicit runtime reconfiguration before access is claimed |
| Inspect approved roots | N/A — read-only operator/application interaction | Query configured roots and actual runtime visibility/capability | N/A — reads emit no Domain event | Safe canonical locators and available/unavailable reasons are returned without directory contents |
| Change or remove a root | N/A — explicit installation operation | Inspect dependent configuration and current mount state | N/A — installation configuration is not a Domain event | The proposed change is shown, explicitly applied, and reversible where possible; history is not rewritten into Repository identity |
| Reject unsafe root input | N/A — validation only | Resolve path components and platform facts | N/A — rejected input has no side effect | Missing, relative, ambiguous, overlapping or escaping paths fail with a secret-safe reason |

## Validation and permissions

Accept only explicit absolute roots supported by the verified host platform. Resolve existing path components through operating-system canonicalization, require an unambiguous directory, and compare canonical paths by platform-appropriate rules. Reject relative paths, empty/root-wide paths, complete home directories, traversal, symlink escape, unsupported network/removable semantics, unsafe overlap, duplicate aliases, inaccessible paths, and paths whose identity changes between validation and application. Do not infer approval from directory names, environment variables, current working directory, Git remotes, or prior registration.

Treat mount exposure as physical authority. Configuration is not proof that a path is mounted or usable: after explicit runtime reconfiguration, inspect the runtime-visible path and report configured, mounted, readable, writable where intentionally granted, or unavailable as separate facts. Do not hide a broader mount behind application filtering. Keep later Agent runner access separate; this TASK exposes only the services required by EPIC-00005.

The host-side operation must preview the exact canonical root, affected local configuration, required runtime restart/recreation, expected result and recovery before mutation. Never create, move, chmod, chown, delete or scan the selected root; never request sudo, secrets or arbitrary environment dumps. Removal changes installation exposure only and does not delete source. Machine-specific configuration remains ignored and secret-safe.

The authenticated application may expose safe root locators and availability to a separately authorized installation-information query, but browser visibility cannot add/change mounts. Exact operator mutation authority remains outside ordinary application permissions. Do not create Repository, Checkout or Worktree records and do not emit invented filesystem events.

## Acceptance criteria

- [ ] An explicit operator operation previews and applies add/change/remove/status for approved roots without scanning or mutating source contents.
- [ ] Root validation canonicalizes platform paths and rejects relative, missing, ambiguous, duplicate, overlapping, root-wide, complete-home and symlink-escaping selections.
- [ ] Machine-specific root configuration is versioned in shape, ignored from Git, secret-safe, and produces understandable recovery guidance.
- [ ] Configuration changes do not claim availability until the runtime has been explicitly reconfigured and the exact mount is directly observed.
- [ ] Runtime exposure contains only approved roots with the minimum required access; no complete home directory or hidden broader parent is mounted.
- [ ] Read-only application capability distinguishes configured, mounted, readable, intentionally writable and unavailable facts without listing private contents.
- [ ] Browser permissions cannot add, change or remove host mounts, and source deletion/movement/permission changes never occur as side effects.
- [ ] No Repository, Host, Checkout, Worktree, registration, Git authority, Planning authority or Agent execution state is created.
- [ ] Owned path-policy tests, direct host/runtime mount checks, planning validation and the canonical build pass with fresh evidence.
