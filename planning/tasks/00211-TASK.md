# Create standalone release TASKs with guarded completion

## Outcome

An authorized planner can create, revise and inspect one standalone `release` TASK for a concrete library
version or application deployment candidate without an invented parent TICKET. Its lifecycle cannot become
`done` merely from preparation, implementation acceptance or PR landing: release completion requires actual
verified project-specific effects, checks and configured follow-through. Existing TASK kinds and completion
rules remain intact. This is one independently reviewable Planning interaction and closeout boundary, not a
release Workflow.

## Scope

- Extend [TASK-00089](00089-TASK.md)'s closed TASK-kind catalog and standalone rules to `release` for a
  registered project with a concrete library version/release line or named application environment and
  candidate intent. Support a release candidate whose final exact source commit is certified **later**;
  do not treat an initial proposed revision as certified. Keep one TASK for preparation, approval, signing,
  publication/deployment, verification, recovery and any branch follow-through; no per-stage TASK or parent
  EPIC/TICKET is created. Preserve immutable identity, attributed revisions, scope-safe Views and existing
  status/order semantics for ordinary work.
- Extend [TASK-00092](00092-TASK.md)'s intent-specific lifecycle policy with a release-specific completion
  guard. Require current authorized project policy and release Workflow evidence of all *required* effects,
  checks and follow-through verified against the exact certified subject before a `release` TASK can be
  marked `done`. An intent, partial/unknown provider effect, signed local tag, deployment acknowledgement,
  implementation PR, or old certification cannot substitute. Partial and uncertain releases remain
  nonterminal with safe reasons and recovery. Positive completion consumes qualified release evidence from
  [TICKET-00056](../tickets/00056-TICKET.md) through [TICKET-00058](../tickets/00058-TICKET.md) when those
  consumers exist; this TASK does not fabricate it or implement provider effects.
- Preserve existing Markdown Planning authority until an approved, verified database cutover. Adapt its
  authoritative representation, conventions and supported authoring/validation path deliberately as needed,
  and plan parity with the eventual database lifecycle. Verify Markdown/planning tooling directly with its
  owning tool, **not** by adding product-suite tests for records, wrappers or generated views. No premature
  migration, automatic removal/archiving or change to another kind's accepted `done` rule.
- Out of scope: policy/runbook setup ([TASK-00212](00212-TASK.md)), classifier/catalog resolution
  ([TASK-00213](00213-TASK.md)), start, claim, independent review, signing, publishing or deploying.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create or revise release TASK | Existing authorized Planning create/revise operations extended for standalone release | Inspect project/candidate intent, kind, scope, current revision and status | Existing TASK creation/revision fact on successful write | One standalone release identity without a TICKET or per-stage TASK |
| Inspect candidate status | N/A — read-only | Current safe TASK detail and accepted lifecycle/eligibility reason, no inferred certification | N/A — inspection emits no lifecycle event | Explain concrete candidate and incomplete release honestly |
| Complete release TASK when verified | Existing intent-specific lifecycle completion after qualified release evidence | Current policy, exact Workflow subject, verified required effects/checks/follow-through | Existing TASK completion fact only after validation | `done` for the one release TASK, never from attempted effects or ordinary PR landing |

These are owning semantic operations, not additional Planning statuses or a generic status setter.

## Validation and permissions

Require current scoped Planning create/revise/complete authority and registered Repository identity. Validate
supported release candidate shape and immutable project binding, expected revisions and idempotency; only the
release-kind path accepts an absent TICKET beyond existing standalone bug/chore rules. A `chore` must never
become a release by interpretation of its prose; existing feature/bug/chore transitions are unchanged.
For release closure, insist on the authoritative same-TASK Workflow's qualified exact subject and verified
project-specific completion, not client-supplied provider claims, agent role titles, arbitrary URL or static
Markdown text. If downstream release evidence is not available or authority is uncertain, refuse `done` with
actionable reasons; never block a legitimate ordinary TASK through this new release guard. Preserve historical
facts, independently verify acceptance rather than asserting provider effects from lifecycle alone.

## Acceptance criteria

- [ ] A permitted planner creates/revises one standalone library or application release TASK naming a concrete
  project/candidate, with no extra parent or stage TASK; invalid, missing or cross-project facts refuse safely.
- [ ] Ordinary feature/bug/chore kinds retain their creation, queue, statuses and completion behavior; `chore`
  cannot acquire release semantics or authority from its title.
- [ ] Release-specific `done` refuses preparation, PR publication, a local signature, queued provider effect,
  partial/failed/uncertain effects and missing project-required checks/follow-through. Positive completion
  requires verified current release evidence from the qualified owning Workflow when available.
- [ ] Current Markdown authority and eventual database parity are explicit; no generic status mutation,
  silent cutover, duplicate lifecycle authority or inferred release/deployment event is introduced.

## Verification and evidence

Test owned kind/standalone/candidate and lifecycle authorization, revision races, evidence-bound release
completion refusal and ordinary-kind nonregression at Application and important PostgreSQL/API contracts.
Use controlled typed downstream observations to test the guard without claiming live publication; qualify
positive end-to-end completion with TICKET-00056–00058 consumers later. Validate Markdown and planning
representations directly with `./bin/planning-check`, not product tests of planning artifacts, migration syntax
or tooling. Run focused checks and `./bin/build`; record fresh results, counts, warnings, authority mode and
outstanding downstream qualification. Formal review and delivery remain separate.
