# Expose canonical Roadmap and work-queue views

## Outcome

Authorized application, HTTP and read-only terminal consumers receive the same revisioned Roadmap, hierarchy progress, dependency impact, archive and Kanban-style work-queue Views backed by the canonical ordering and eligibility capability, with no client-specific lifecycle or selection rules.

## Scope

- In scope: Repository/workspace Roadmap Views; hierarchy progress Views; canonical executable/excluded queue Views; current/archive filters; direct/transitive dependency-impact Views; derived Ready, In Progress, Blocked, Human Action, In Review and Complete presentation lanes; criteria/child progress counts; ordering/eligibility/context/authority revision provenance; bounded filters/pagination; versioned JSend API/OpenAPI; read-only console/terminal interaction calling the same application query; stable safe unavailable/stale/partial states; independent view Permissions; consumer-contract/list-explain equivalence tests; explicit TICKET-00028 Markdown Board/`next` parity and switch handoff.
- Out of scope: React pages/components/drag/drop, mutating Roadmap/TASK order, starting/claiming coordinated work, changing lifecycle, persisting lanes/Blocked/Hold, Pi/MCP transport, modifying the Markdown `next` skill before authority cutover, Markdown migration/cutover execution, provider polling and a second eligibility/priority algorithm.

## Validation and permissions

Every View composes typed TICKET-00026 projections, TASK-00094/95 ordering and TASK-00096 eligibility; it does not parse Markdown, inspect the generated Board or reproduce rules in an Action, console command, serializer, frontend service or SQL query. One application query/result model is the canonical source. API and terminal adapters only validate transport, dispatch and represent.

Roadmap and hierarchy progress count authoritative current children/criteria under explicit denominator rules. Explain denominator changes when children/required criteria are added; do not use turns, tokens, elapsed time or fabricated completion percentages. Archived records are hidden by default and available through an explicit permission-scoped filter. Dependency impact is bounded and redacts inaccessible nodes while preserving a safe explanation.

Presentation lanes are derived and never writable statuses. Ready reflects canonical eligibility; In Progress reflects Planning lifecycle/current authorized claim facts where available; Blocked/Human Action reflect reason categories; In Review/Complete may combine typed trusted review/delivery observations without appending another TASK completion event. TASK Done remains implementation acceptance. Never infer Planning status from GitHub, treat provider observations as Planning events or allow manual drop into a derived lane.

Results carry exact aggregate/order/eligibility/context/authority revisions and observation timestamp so consumers can identify stale/partial/unavailable state. Fail closed on unknown permission/authority; do not mix revisions silently. API and terminal output for the same actor/scope/revision must have semantically identical candidate order, reason codes and priority provenance even when formatting differs.

Require authoritative Roadmap, hierarchy, queue, archive and dependency-impact view Permissions as justified and scope every query server-side. Safe Views omit hidden artifact identities/titles, private evidence, internal paths/services, raw events/projections and arbitrary provider data. Terminal interaction authenticates an explicit application actor; it does not infer Agent OS authority from the operating-system user.

The existing Markdown `.pi/skills/next` remains authoritative before TICKET-00028 cutover. This TASK documents the exact canonical application/terminal contract and parity inputs; TICKET-00028 compares the migrated Fight Agent OS Board/frontier and switches post-cutover agent-facing consumers. Do not introduce dual authority or modify the skill prematurely.
