# Reconcile trusted merge and downstream eligibility

## Outcome

After human merge, validate trusted GitHub and base-inclusion facts to update delivery/Complete projections and
canonical downstream prerequisite availability, without asserting Agent OS approved or performed the merge.

## Scope

- In scope: Trusted source-host refresh, exact merge-result/base-inclusion verification across merge strategies,
  authorized reconciliation, separate delivery facts and typed canonical prerequisite-availability integration.
- Out of scope: Autonomous approval/merge, another TASK-completion event, a competing eligibility algorithm,
  rewriting Review/Workflow history, local checkout maintenance and release/deployment follow-through.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Observe source-host state | Authorized bounded refresh of exact original PR | Provider-native Repository/PR, configured base, accepted/published head and merge result | Attributed observations only | Safe current provider facts, no authoritative merge transition |
| Reconcile verified merge | Semantic delivery reconciliation | Exact identity, trusted observation, actual base inclusion and expected revisions | Verified merge/delivery or explicit unresolved facts | Rebuildable Complete/delivery projection, no repeated TASK completion |
| Explain dependent availability | N/A — canonical eligibility query with typed prerequisite facts | Direct downstream dependencies and their configured bases | N/A — query cannot change authority | Eligible or concrete unmet/unknown prerequisite reason |

## Validation and permissions

Use current intent-specific source-host read and reconciliation authority, bounded Repository/Workflow scope and
expected state. Webhooks, polling payloads and cached projections are observations until an authorized semantic
command validates them. Do not trust a title, branch, URL, webhook signature alone or the provider's bare merged
boolean without full identity and source verification. External reads remain outside business transactions.

Match native Repository/PR, configured base, accepted/published head, actual merge result and inclusion on the
relevant base. Qualify merge-commit, squash and rebase strategies without assuming the original head must be an
ancestor in every strategy or treating patch similarity alone as conclusive. Retain the actual correlation proof,
provider/source provenance and limitations. Retargeted, replaced-head, inaccessible, closed-unmerged, unknown or
ambiguous results stay explicit; they cannot unblock dependent work.

Planning done, independent acceptance, PR handoff, human approval, merge, release and deployment remain distinct.
TASK-00096 retains the only eligibility algorithm. Extend its typed fact seam with verified prerequisite change
availability on each dependent TASK's configured base; a Done blocker alone is insufficient and a merge into some
other base cannot satisfy it. Preserve historical dependency edges and authored priority; independent eligible work
remains available. Missing merge/base proof produces an explicit hold rather than optimistic availability.

Commit authoritative reconciliation/audit and required projection intent atomically under ADR 0002. Duplicate,
stale and reordered observations cannot regress verified state, create extra completion events, release unrelated
claims or rewrite Workflow/Review history. Project verified merge into Kanban Complete through existing views;
rebuild/read lag is not authority. Complete delivery/eligibility updates even when TASK-00318 checkout maintenance
is pending. Post-handoff observation does not restart the stopped execution Workflow or select another TASK.

## Acceptance criteria

- [ ] Actual trusted refresh is matched to exact native identities, accepted/published source and configured
  base, with supported merge/squash/rebase result and inclusion proof before semantic reconciliation.
- [ ] Unknown, closed-unmerged, replaced-head, retargeted or inaccessible state remains explicit and cannot
  count as merge or unblock work.
- [ ] Canonical eligibility requires verified change availability on the dependent TASK's configured base,
  not merely Done or a PR merged elsewhere; independent work and historical edges remain intact.
- [ ] Verified merge updates separate delivery/Complete facts without duplicate TASK completion, history
  rewriting, implicit merge approval or another TASK start.
- [ ] Duplicate/reordered/racing refresh and projection rebuild preserve authority and truthful freshness;
  pending checkout maintenance cannot suppress valid merge/delivery facts.

## Verification and evidence

Test owned observation validation, merge correlation, reconciliation idempotency and canonical eligibility facts,
including real PostgreSQL concurrency and important API/query behavior. Qualify provider/Git observations directly
on authorized merged subjects for each supported strategy; test owned negative decisions with controlled fixtures,
not GitHub internals. Record exact PR/source/base/result and dependent eligibility before/after with honest live
versus simulated limits. Run focused checks and `./bin/build`; no product tests of configuration or generated views.
