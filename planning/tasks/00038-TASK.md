# Guard the one-time Super Admin bootstrap

## Outcome

A separate explicitly confirmed trusted-console operation reconciles managed policy, acquires a PostgreSQL-backed one-time guard, verifies no prior bootstrap or Super Admin assignment, creates one pending identity through the normal invitation path, assigns managed `ROLE_SUPER_ADMIN` through package behavior, records a distinct bootstrap actor, and permanently refuses later attempts.

## Scope

- In scope: Application-owned bootstrap orchestrator and dedicated console adapter; explicit confirmation; policy reconciliation; durable one-time bootstrap state; authoritative Super Admin assignment check; transaction-duration race guard; pending invitation and exact managed elevated assignment; distinct audit evidence; isolated bootstrap assignment authorization/composition; normal authenticated `ASSIGN_SUPER_ADMIN` authorization capability for later use; recoverable normal activation delivery; rollback/concurrency/redaction tests; operator documentation.
- Out of scope: Web/admin invitation UI, activation completion, arbitrary role assignment, resetting/reopening bootstrap, administrator-selected password, role-name authorization, custom roles, multiple workspaces, provider choice, and production deployment automation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Bootstrap initial Super Admin | Dedicated Agent OS bootstrap orchestrator using `ReconcileManagedPolicy`, `InvitePendingUser`, and `AssignRoleToUser` package behavior | Inspect durable bootstrap state and authoritative assignments to managed `ROLE_SUPER_ADMIN` | `ManagedPolicyReconciled`, `UserInvited`, `RoleAssignedToUser`, distinct audit evidence | Exactly one pending elevated identity and recoverable invitation state commit; bootstrap closes permanently |
| Refuse later bootstrap | Policy reconciliation may still run; no invitation/assignment command | Read consumed guard and any pending/active/disabled/deleted assignment according to accepted guard semantics | Safe failure only | No second identity, grant, assignment, success audit, or delivery work is created |
| Compete bootstrap attempts | Same dedicated bootstrap command | Lock/recheck one-time state and role assignments on separate transactions | Events only for winner after commit | Exactly one contender commits; losers receive controlled non-secret refusal |
| Authorize later elevated assignment | `AssignRoleToUser` through normal authenticated composition | Resolve current authoritative principal permission | Existing package assignment event | Only an actor with `ASSIGN_SUPER_ADMIN` may proceed; no bootstrap bypass is reachable |

## Validation and permissions

Bootstrap is a dedicated command, not an option on ordinary invitation. Require canonical email, bounded explicit bootstrap-operator identity, and deliberate confirmation; non-interactive use requires an equally explicit documented flag/input. Reconcile TASK-00036's policy before checking eligibility, but policy success alone must not consume bootstrap.

Persist a one-time marker/state with stable semantics and enforce it under a PostgreSQL transaction-duration guard. Eligibility fails closed when the marker is consumed or any authoritative user assignment references managed `ROLE_SUPER_ADMIN`, including the pending identity produced by a prior successful bootstrap. Once consumed, later deletion/disablement/role change does not reopen bootstrap; recovery requires a separately planned operation, not marker reset.

The winner uses TASK-00037's validated normal invitation/delivery path but hard-codes `ROLE_SUPER_ADMIN`. Use Fight Access Control `InvitePendingUser` and `AssignRoleToUser` behavior; do not directly insert users/assignments or bypass role reference fences. Pending identity, assignment, bootstrap marker, audit evidence, grant/delivery state, and required intent must reach one coherent committed result. Provider execution remains outside the business transaction.

Represent bootstrap as a distinct trusted-console actor in durable audit evidence; do not claim the pending user authenticated or authorized its own elevation. Any package authorization accommodation must be isolated to this bootstrap console composition, scoped to the one guarded operation, and impossible to resolve through HTTP/normal command composition. If package contracts cannot represent the actor/transaction boundary faithfully, stop and surface the contract gap rather than install a permanent or role-name bypass.

Normal authenticated elevated assignment uses an implementation of the package authorization capability that resolves current authoritative permission and requires exact `ASSIGN_SUPER_ADMIN`; identity/role names are not shortcuts. Unknown, stale, mismatched actor, and absent authority fail closed. Explicit web confirmation and endpoint/UI arrive in TICKET-00021.

Never print/log password, grant credential/digest/ciphertext, credential-bearing URL, access/refresh token, provider secret, SQL, or private configuration. No administrator selects a password; the pending user completes normal activation.

## Acceptance criteria

- [ ] Bootstrap is a distinct trusted console operation with explicit operator identity, canonical email validation, and deliberate interactive/non-interactive confirmation.
- [ ] The operation reconciles the exact managed policy before eligibility and resolves stable managed `ROLE_SUPER_ADMIN` by ID, not a role-name authorization shortcut.
- [ ] A durable one-time marker and authoritative assignment check are revalidated under a PostgreSQL transaction-duration guard.
- [ ] Fresh bootstrap commits one pending user assigned exactly managed `ROLE_SUPER_ADMIN`, normal seven-day activation grant/delivery state, distinct audit evidence, and consumed guard.
- [ ] Bootstrap uses package `InvitePendingUser` and `AssignRoleToUser` behavior without direct identity/assignment persistence or copied package policy.
- [ ] Bootstrap audit identifies a distinct trusted actor and never represents the pending user as the authorizing principal.
- [ ] Any bootstrap-only assignment authorization is scoped to dedicated console composition and cannot be resolved/invoked through HTTP or normal authenticated command paths.
- [ ] Normal authenticated elevated assignment requires exact authoritative `ASSIGN_SUPER_ADMIN`; missing/stale/mismatched authority fails closed without role-name bypass.
- [ ] Existing consumed marker or any prior Super Admin assignment, including pending/active/disabled cases, refuses later bootstrap without new user/grant/assignment/audit-success/delivery state.
- [ ] Controlled simultaneous attempts produce exactly one committed winner and deterministic safe loser outcomes without sleeps.
- [ ] Injected failure before complete commit leaves no partial identity, assignment, consumed marker, success audit, or unrecoverable delivery; a legitimate retry remains possible.
- [ ] Once committed, lifecycle/role changes do not reopen bootstrap and no reset/backdoor command exists.
- [ ] Passwords and activation credentials are user-chosen/normal-flow only; output/logs/diagnostics contain no credentials, links, tokens, provider secrets, SQL, or private config.
- [ ] Focused unit/PostgreSQL/concurrency/console/authorization/delivery/redaction tests and `./bin/build` pass with fresh evidence.
