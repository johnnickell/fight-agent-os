# Guard the one-time Super Admin bootstrap

## Current supersession — TASK-00446

The owner-approved [TASK-00446](00446-TASK.md) replaces the permanent-claim/no-retry and concurrent-bootstrap
requirements below with a trusted manual presence check: existing Super Admin or lookup failure refuses;
otherwise proceed, one operator at a time. A later manual attempt is allowed after partial/failure while no
Super Admin exists. It also replaces command-specific containers/intent scopes and raw-message authentication
with one graph and an explicit authenticated assignment use case. Raw package dispatch becomes trusted internal
infrastructure; authenticated permission decisions remain mandatory at the supported use-case boundary.
Historical claims/audit and this TASK's old evidence remain unchanged. Current semantics and fresh acceptance
belong to TASK-00446; the following requirements/reports describe the earlier candidate, not new verification.

## Outcome

A separate explicitly confirmed trusted-console operation reconciles managed policy, durably claims the one-time bootstrap under a PostgreSQL guard after checking prior bootstrap and Super Admin assignments, then creates one pending identity and assigns managed `ROLE_SUPER_ADMIN` through independently committed package operations. It records a distinct bootstrap actor, reports partial/uncertain results truthfully, and permanently refuses another bootstrap after the claim commits.

## Owner amendment — separate commits

On 2026-10-15, after comparing TASK-00037's accepted separate-commit invitation path with the demonstrated package transaction gap, the owner directed: “Then fix the task as a part of this work.” This amendment replaces the original all-or-nothing bootstrap requirement with normal independent package commits and explicit partial outcomes. It does not amend package ownership ADRs or authorize transaction joining, deferred events or an upstream edit.

The safety tradeoff is deliberate: a durable claim closes bootstrap **before** invitation. A crash or later failure may therefore leave no user, an invited user without elevation, or an assigned user without confirmed final audit. Delivery may begin after invitation commits. These are non-success/uncertain outcomes, not rollback. No automatic claim release, second target, blind reinvitation or bootstrap retry after a committed claim is allowed. Recovery of an interrupted claimed bootstrap remains a separately planned trusted operation; this TASK documents the retained safe state and that limitation rather than adding a reset/backdoor.

## Scope

- In scope: Application-owned bootstrap orchestrator and dedicated console adapter; explicit confirmation; policy reconciliation; durable one-time bootstrap state; authoritative Super Admin assignment check; transaction-duration guard for eligibility and durable claim; independently committed pending invitation and exact managed elevated assignment; explicit partial/uncertain outcomes; distinct audit evidence; isolated bootstrap assignment authorization/composition; normal authenticated `ASSIGN_SUPER_ADMIN` authorization boundary for later use; recoverable normal activation delivery; per-step rollback/concurrency/redaction tests; operator documentation.
- Out of scope: Web/admin invitation UI, activation completion, arbitrary role assignment, resetting/reopening or resuming an interrupted claimed bootstrap, administrator-selected password, role-name authorization, custom roles, multiple workspaces, provider choice, and production deployment automation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Bootstrap initial Super Admin | Dedicated Agent OS bootstrap orchestrator using `ReconcileManagedPolicy`, `InvitePendingUser`, and `AssignRoleToUser` package behavior | Inspect durable bootstrap state and authoritative assignments to managed `ROLE_SUPER_ADMIN` | `ManagedPolicyReconciled`, `UserInvited`, `RoleAssignedToUser`, distinct audit evidence | One durable claim closes bootstrap first; normal invitation and assignment commit independently; completed success has one elevated identity, while partial/uncertain results retain actual committed state |
| Refuse later bootstrap | Policy reconciliation may still run; no invitation/assignment command | Read consumed guard and any pending/active/disabled/deleted assignment according to accepted guard semantics | Safe failure only | No second identity, grant, assignment, success audit, or delivery work is created |
| Compete bootstrap attempts | Same dedicated bootstrap command | Lock/recheck one-time state and role assignments on separate transactions | Normal package events after each winning step's own commit | Exactly one contender claims bootstrap; only that invocation may proceed; losers receive controlled non-secret refusal |
| Authorize later elevated assignment | `AssignRoleToUser` through normal authenticated composition | Resolve current authoritative principal permission | Existing package assignment event | Only an actor with `ASSIGN_SUPER_ADMIN` may proceed; no bootstrap bypass is reachable |

## Validation and permissions

Bootstrap is a dedicated command, not an option on ordinary invitation. Require canonical email, bounded explicit bootstrap-operator identity, and deliberate confirmation; non-interactive use requires an equally explicit documented flag/input. Reconcile TASK-00036's policy before checking eligibility, but policy success alone must not consume bootstrap.

Persist a one-time claim with stable semantics. In one short PostgreSQL transaction, acquire a transaction-duration guard, recheck the claim and authoritative assignments to managed `ROLE_SUPER_ADMIN` regardless of user lifecycle, and commit the claim with immutable operator/target attribution and distinct claim audit before dispatching invitation. The claim is consumed even if later steps fail. Refuse subsequent bootstrap whenever a claim exists or a prior assignment exists; pending/active/disabled/deleted assignments all count. A failure known to occur before claim commit leaves bootstrap available; uncertain claim commit requires safe fresh-state inspection and fail-closed output, never blind retry. Later lifecycle/role changes cannot reopen bootstrap. Recovery requires a separately planned operation, not marker reset.

Only the invocation that committed the claim may proceed, once, for its recorded target. Use TASK-00037's validated public invitation/delivery conventions, not its ordinary `ROLE_USER` assignment; bootstrap hard-codes managed `ROLE_SUPER_ADMIN`. Dispatch Fight Access Control `InvitePendingUser` then `AssignRoleToUser` through configured buses with their normal independently owned transactions/events. Do not directly persist identity/assignments, copy package policy, bypass role-reference fences, wrap/join/nest package transactions or defer package events. Bootstrap state coordinates one-time eligibility, not a consumer credential-delivery intent/participant/queue. Delivery stays package-owned; provider execution remains outside package claim/outcome transactions.

Invitation may commit and delivery may start before role assignment. Inspect actual safe persisted state after postcommit exceptions, using a usable fresh manager where needed; never infer rollback from an exception. Retain committed invitation/assignment on later failure. Mandatory assignment-confirmation/bootstrap completion audit may commit separately; disclose its crash window and never report success without verified required evidence. Report safe target ID and known step statuses, distinguish partial from uncertain outcomes, and direct interrupted claims to separately planned recovery rather than ordinary `user:role:add`, which continues to prohibit Super Admin. No compensation, reinvitation, automatic retry of an uncertain mutation or reopened claim.

Represent bootstrap as a distinct trusted-console actor in durable audit evidence; do not claim the pending user authenticated or authorized its own elevation. Any package authorization accommodation must be isolated to this bootstrap console composition, scoped to the one guarded operation, and impossible to resolve through HTTP/normal command composition. The explicit operator UUID may be represented by the package's typed assignment actor while durable audit distinguishes the trusted-console actor from the target; this does not assert an authenticated database User. Any other unsupported package guarantee remains a stop condition, not permission for a permanent or role-name bypass.

Normal authenticated elevated assignment uses an Application-owned authorization boundary backed by supported package current-principal/permission capabilities; do not assume an assignment-handler callback exists. Resolve current authoritative permission and require exact `ASSIGN_SUPER_ADMIN` (and `MANAGE_USER_ROLES` for direct role assignment under the parent); identity/role names are not shortcuts. Unknown, stale, mismatched actor, and absent authority fail closed. Explicit web confirmation and endpoint/UI arrive in TICKET-00021.

Never print/log password, grant credential/digest/ciphertext, credential-bearing URL, access/refresh token, provider secret, SQL, or private configuration. No administrator selects a password; the pending user completes normal activation.
