# Unify local HTTP and HTTPS startup under bin/up

## Outcome

Make `./bin/up` the single local application startup and refresh command, including the HTTPS gateway and PHP
runtime. Operators must not need a separate `./bin/https up` after configuration changes to make the browser
runtime agree with the HTTP runtime. Keep `./bin/https setup` as explicit certificate and machine-trust enrollment.
This standalone bug removes a concrete blocker to reliable local authenticated browser and private API-documentation
use; it does not change Swagger eligibility or application authorization.

The maintainer explicitly accepted this scope and authorized record creation in the reporting conversation.
Implementation, checkout selection, independent acceptance and publication remain separate.

## Scope

- In scope: Move ordinary HTTPS startup/refresh and its prerequisite checks into `bin/up`; remove the `up`
  operation from `bin/https`; preserve explicit `setup` and existing status/down/remove responsibilities;
  update current startup guidance and executable callers to use the single startup command.
- Out of scope: Automatic CA enrollment or certificate generation during startup; changing application secrets,
  Swagger defaults/permissions, authentication, ports, proxy trust or production deployment; database resets,
  migrations or dependency installation as new implicit startup effects; broad wrapper refactoring.

## Reproduction and diagnosis

Inspected checkout: repository main checkout on `develop`, revision
`9983c0dcfc85407f7a0f15db7da5050a22802250`, with a clean tracked working tree at diagnosis.
The operator reported `/app/swagger` displaying “Documentation disabled” and
“This installation has not enabled documentation in this environment.”

Safe diagnostic inputs and observations:

- The ignored local `.env` contained `APP_ENV=local` and `APP_SWAGGER_ALLOWED_ENVIRONMENTS='["local"]'`.
  Only these non-secret settings were inspected; no full environment was printed.
- Python `urllib.request.urlopen` fetched `/app/swagger` without authentication or cookies, with a ten-second
  timeout and normal TLS verification, from `http://localhost:18087` and `https://localhost:18443`.
  Both returned HTTP 200. Extracting only the public boot field `"swagger_available"` yielded `true` over HTTP
  and `false` over HTTPS. No protected documentation read or API execution was attempted.
- `bin/up` invokes ordinary `docker compose up --detach --build`; HTTPS services in `compose.yaml` belong to
  the `https` profile. `bin/https up` separately enables that profile, waits for startup, validates Nginx and
  reloads its configuration. The current local HTTPS runbook explicitly requires that second command after
  environment changes.

Expected under the accepted corrected contract: one `./bin/up` invocation refreshes both PHP runtimes and the
TLS gateway; the same effective documentation settings produce matching public boot eligibility on both origins.
Observed: separate startup paths permit the browser's HTTPS runtime to retain different configuration.
The split command ownership and live boot mismatch are demonstrated. Stale container environment is the likely
cause of this particular mismatch, not yet confirmed by inspecting/recreating the running services. No startup,
configuration mutation or causal before/after recreation was performed during diagnosis.

## Validation and permissions

`bin/up` must retain existing dependency/cache preparation while incorporating the existing HTTPS preflight,
certificate validity, readiness and gateway validation/reload responsibilities. Missing/invalid origin, keys,
certificates or dependencies must produce a nonzero, actionable error, not an HTTP-only success. Run available
preflight before service mutation; report partial startup honestly if a later build, readiness or reload fails.
Do not prompt for a system password, run `mkcert -install`, rewrite `.env`, rotate secrets or generate leaves in
ordinary startup. Point missing enrollment to `./bin/https setup`.

Preserve effective Compose environment precedence, loopback bindings, unexposed FastCGI, verified TLS and existing
security checks. Do not print resolved Compose environments, private keys, cookies or protected responses.
Existing `status`, `down` and `remove` remain separate operations; no database volume removal or global CA cleanup.
Execution requires the selected checkout and authority to affect its Docker services. Disposable verification
must not recreate unrelated or the operator's running stack without authorization.
