# Open and fence protected runtime sessions

## Outcome

The actual supported Harness opens and inspects protected session/storage state for an exact authorized intent,
with a single active storage owner and enforceable acting windows. Broker, loader and invocation owners gain a
real host/session boundary without requiring completed provider execution or final role journeys.

## Scope

- In scope: Protected runtime adapter/storage integration, exact application-to-Pi lineage, open/inspect/reconcile
  operations, runtime-owner fencing, acting-window enforcement and safe capability/unavailable facts.
- Out of scope: New sandbox/provisioner/broker platform, Runner/Workflow delivery, credential lifecycle, tool grants,
  paid generation, final conversation execution/recovery, duplicate checkpoint selection or browser UI.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Open protected runtime state | Exact committed session-open intent through qualified owner | Current original attempt, binding, enrolled host and supported storage/runtime | Confirmed owned binding/open observations | One protected runtime lineage, not a running model turn or new credential holder |
| Inspect or reconcile opening | Explicit original-open reconciliation; ordinary status is read-only | Actual original storage/process binding, owner epoch and capability facts | Confirmed original observations only | Same lineage or explicit hold, no duplicate runtime created on missing acknowledgement |
| Fence an acting window | Existing owning revocation/hold/epoch operation and host enforcement | Current authenticated runtime owner and bounded operation context | Existing owning state facts | Stale processes cannot initiate protected effects or write retained state |
