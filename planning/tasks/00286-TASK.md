# Recover and inspect email-change credential work

## Outcome

The existing protected bounded human-delivery runner processes email-change generations after lost events or
restart, alongside invitation/reset work. Exact package discovery/dispatch, safe operational status and independent
key-free expiry recover work without another queue or a fabricated delivery-success count.

## Scope

- In scope: Extend existing recovery dispatch/preflight and narrow audit identity support; actual email-change
  claim/outcome/expiry integration, bounded contention recovery, safe status/diagnostics and operator guidance.
- Out of scope: New scheduler framework, vendor enrollment, public worker/status/retry endpoints, owner/admin
  UI projection, consumer lifecycle/backoff/attempt policy or raw-token recovery tools.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Recover one bounded page | Direct package `DeliverEmailChange` for returned User/delivery identity | `FindDueCredentialDeliveries` at the captured current boundary | Existing package delivery facts after matching commit | At most admitted page/capacity attempts; no request reissue |
| Clean expired authority | Existing `ExpireEmailChange` using the returned grant identity | `FindExpiredCredentialDeliveries` and safe persisted rediscovery | Existing package expiry fact on actual transition | Exact bound reservation/authority/material cleanup without key/provider |
| Inspect original generation | N/A — protected read only | `FindCredentialDeliveryStatus` for exact purpose/delivery ID | N/A | Safe persisted operational state, not proof of usable pending change or mailbox receipt |

## Validation and permissions

Extend `RecoverCredentialDeliveryPage`, the existing console/preflight and exact package registration rather than
introducing parallel discovery or application aliases. Email-change work is currently counted as unsupported;
map its actual purpose-specific User/delivery identity. Preserve deterministic package eligibility/order before
limits and package five-minute lease capped at expiry, backoff and terminal policy as qualified from source.
Capacity limits dispatch work, never changes grant lifecycle or renews an attempt budget.

The existing `credential-recovery` audit allowance covers only four invitation/reset delivery actions. Narrowly
admit the actual email-change delivered/failed action names needed by the selected handler without permitting
that operational actor to request, cancel, confirm or administer accounts. This is validation of package audit
facts, not hidden audit-repository orchestration. Actor strings and `--internal` are not authentication; protect
all enabled console/scheduler/direct-bus entries through actual OS/service/dispatch authority. No browser grant
or arbitrary client ID becomes operational authority.

Claim/decrypt/invoke/outcome stays in the package handler. Extend expected contention handling only for qualified
package failures; stop a page on the existing closed-Doctrine-manager boundary and use a fresh invocation to
resume. Unexpected failures stop with fixed safe diagnostics, not optimistic success. Do not spin on unchanged
rows, omit inconsistent work to fake progress or turn handler return counts into delivered counts.

Preflight actual required delivery capabilities, including the email cipher, before live dispatch. Preserve
standalone `expire` and status without resolving keys/ciphers/providers. Due discovery excludes exact/post-expiry
work, so expiry remains a separately bounded phase. Email authority cleanup must include delivered/permanently
failed/material-free delivery and inactive User states according to package policy, clearing only the exact bound
reservation. Never synthesize expiry status or clear a reservation by destination equality; retain same-email
successor/ABA protection and actual no-progress/budget-exhaustion reporting.

Status stays an exact protected safe operational projection: no credentials, hashes, ciphertext, destination,
claim token, body, URL or arbitrary provider/audit internals. Persisted delivery state is not proof of current
email authority, usable confirmation or actual mailbox receipt; TASK-00279 owns the coherent browser projection.
Unknown outcome after provider acceptance is unresolved and may lead to a same-generation repeat under package
policy, never a new request or exactly-once claim. Accepted old-mail notices remain separate.
