# Establish source-verified Python diagrams for a documented PHP feature

## Outcome

Publish a shared standard and repeatable local Python Diagrams rendering path, then qualify them on one existing
PHP feature. A reader can inspect the feature's source and rendered diagrams beside its documentation and trace
the represented ownership and interactions to the cited source revision.

## Scope

- In scope: Define view selection, labels and arrow meanings, source links and revision labels, uncertainty and
  omissions, and the limits of diagram evidence. Establish a supported local Python Diagrams and Graphviz setup
  without relying on undocumented global packages. Add Python diagram source and rendered image beside one
  existing feature's documentation. Include a readable Domain/Application/Adapter ownership view and any
  additional flow view that materially helps explain that feature. Inspect generated images and verify them
  against source.
- Out of scope: Automatic repository-wide graph extraction, a general architecture catalog, application behavior
  changes, moving or creating classes to fit a diagram, PR automation or review policy, and the Pi show-me skill.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Maintain a diagram for the selected feature | Run the documented local renderer | Read the feature documentation, ownership guidance, source files, and revision being described | N/A — no application or workflow event | Add or update the diagram source, rendered image, and explanatory links beside the feature documentation |

## Validation and permissions

Use the supported local rendering path and inspect the generated image. Verify its links, labels, arrows, and
revision against the selected feature source. Do not upload private source to a third-party renderer. Do not change
application classes or behavior to fit the illustration. No application commands, queries, events, or permissions
apply. Do not add product-suite tests for documentation, rendering tools, or generated assets.

## Acceptance criteria

- [ ] A shared standard documents when a diagram helps, applicable view choices, source/revision references, static dependency versus runtime interaction arrows, proposal labels, uncertainty, omissions, and the limits of diagram evidence.
- [ ] Feature documentation owns editable Python Diagrams source and the corresponding rendered image.
- [ ] A documented local rendering path regenerates the image with qualified Python and Graphviz requirements rather than undocumented global setup.
- [ ] One existing PHP feature has a readable view showing actual Domain, Application, and Adapter class placement, with relevant dependencies or runtime flow labeled and linked to source.
- [ ] The rendered view is inspected against the source revision it names; classes and important arrows can be traced, and uncertainty or unsupported representation is stated.

## Verification and evidence

Run the documented renderer with its owning tools, inspect every generated image, and check local source links and
the cited revision against implementation. Record the renderer and dependency setup used. Run
`./bin/planning-check --write` and `./bin/planning-check` for the planning records; these checks do not replace the
diagram and source inspection. No product-suite tests or application build are required for this documentation
and tooling outcome.

and TICKET-00128 consume the resulting source/image/documentation contract.
