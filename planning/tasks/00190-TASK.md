# Propose broader guidance from permitted memory

## Outcome

An Agent that currently reads a private or shared source entry can propose broader Repository or Workspace
guidance through the authenticated first-party MCP path, including a direct target jump, without acquiring
publication authority. The attributed proposal and its safe rationale persist for separately authorized
review or historical learning but never enter ordinary guidance. This TASK delivers one independently
reviewable proposal path from Application policy through guarded PostgreSQL and MCP delivery.

## Scope

- Build on [TASK-00188](00188-TASK.md)'s entry IDs, private/shared source provenance, correction and
  scope-authorized reads, including TASK summaries. Resolve current source status, Agent, assignment,
  permission, source Repository/Workspace and declared target through authoritative state; a target ID is a
  proposed destination, not a grant. Permit direct jumps to a legitimate ancestor scope without requiring
  intervening proposals; disallow arbitrary unrelated Repository/Workspace targets.
- Store a bounded, attributed pending proposal with source identity/revision/status, target, suggested
  applicability, rationale, actor, request identity and safe evidence references. The proposal may carry
  deliberately supplied new draft guidance; it must not automatically copy private entry text, Pi transcripts,
  secret sources or hidden reasoning into reviewer output. A target reviewer gets no permission to read the
  source merely because the proposal links it; later assessment requires independent authority and evidence.
- Deduplicate an exact repeated proposal command (including an uncertain MCP retry) without conflating
  separately submitted similar/contradictory proposals. Normal memory selection and later Jev guidance exclude
  pending and rejected proposal bodies. Authorized proposal-review/historical queries are distinct, bounded
  and safely redacted for actors who lack source access.
- Keep Domain/Application ownership, authorization and lifecycle rules separate from MCP/Doctrine under
  ADR 0001/0002; share the qualified first-party HMAC caller boundary from TASK-00185 rather than adding
  a new credential or database route. Do not add a human approval solely to submit a proposal.
- Out of scope: target-owner acceptance/rejection/publication (TASK-00191), derived owner notices and later
  retractions (TASK-00192), human proposal-history UI and exceptional removal (TICKET-00050), or Jev
  relevance selection (TICKET-00049). Proposals cannot change published Planning or Workflow authority.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Suggest broader guidance | Propose publication from a currently permitted entry to Repository or Workspace | Resolve authenticated Agent, live source, valid target and ancestry | Proposal recorded after commit | One attributed pending proposal, no published entry |
| Retry suggestion | Repeat the same request identity | Resolve prior command outcome and safe current presentation | N/A — no duplicate proposal event | Original proposal identity returned without another write |
| Inspect own proposal | N/A — read-only | Fetch authorized proposal status and redacted lineage | N/A — no memory mutation | Actor can see safe status without receiving target publication power |
| Deny ordinary reuse | N/A — read-only selection | Select current published guidance only | N/A — no mutation | Pending/rejected drafts do not enter an Agent's normal memory results |

Semantic names do not prescribe PHP/MCP wire types or event sourcing.

## Validation and permissions

Check current source read independently of proposed target: even a previously known entry ID, a cached
session or a role title cannot restore revoked scope access. Validate target ancestry, registered
`RepositoryId` and Workspace identity, text size, source revision and safe source references. The Agent
need not have target **write** Permission to propose, but cannot use a proposal to transfer private content
to an unauthorized steward. Return bounded safe errors without revealing forbidden entry titles, text or
metadata. Keep rejected proposals available only through separately authorized review/history; later decision
status must not alter the original. An unavailable dependency or prohibited content blocks unsafe proposal
creation; no live memory ingestion before TICKET-00050's safety-removal capability.

## Acceptance criteria

- [ ] An assigned Engineer proposes a Repository target from a currently readable scoped entry and, where
  ancestry applies, a Workspace target directly; neither operation creates a broader entry or permission.
- [ ] Forged source identity, stale/revoked source access, cross-Repository target and unrelated Workspace
  requests fail without disclosing private/shared bodies or hidden record metadata.
- [ ] Exact request retry returns one proposal; distinct similar or contradictory requests retain separate
  actor, target, rationale, source revision and order for future review.
- [ ] Ordinary Agent guidance excludes pending/rejected proposal text; restricted private source remains
  restricted even if a broader reviewer sees a safe proposal record.
- [ ] No publication, automatic approval, live ingestion or new Planning/Workflow authority occurs in this TASK.
