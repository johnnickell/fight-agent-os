# Keep Pi Jev setup valid without periodic renewal

## Outcome

The operator configures Pi Jev once, without daily price/disclosure renewal prompts. Existing valid settings
remain usable across elapsed time, reloads and sessions for the same pinned connection and approved limits.
This removes recurring setup friction from the file-screening adoption path owned by
[TASK-00309](00309-TASK.md), which separately owns one-time repository/project enrollment.

## Scope

- Remove the 24-hour pricing-confirmation lifetime; retain its timestamp as confirmation provenance, not a lease.
  Accept existing protected settings without rewriting their timestamp, revision, identity, disclosure or ceilings.
- Keep exact provider/model/evaluator/price pins, payload price maxima, configuration-change invalidation,
  current consumer permission checks, credentials, conservative reservations and breach halts.
- Explain persistent setup in the operator dialog and runbook. No routine reconfirmation on session, day or month
  changes. Missing/corrupt settings, changed connection pins or authority, revoked permission, exhausted funds and
  provider/credential failures still require the relevant corrective action, not automatic permission expansion.
- Record John's matching standing project-enrollment requirement in TASK-00309 without editing its active worktree
  or duplicating its profile/launcher/accounting implementation. Temporary execution grants are not enrollment.
- Out of scope: new pricing discovery, automatically accepting higher prices, changing budgets or credentials,
  enrolling actual projects, live paid requests, replacing TASK-00309's implementation, publication and merge.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Configure once | `/jev setup` | Confirmation of pinned connection, disclosure and finite ceilings | Local setup notification | Protected nonsecret settings only; no credential resolution or provider request |
| Reuse prior approval | Existing readiness/consumer evaluation | `/jev inspect` and current configuration validation | Existing readiness/receipt observations | No renewal write; evaluation retains separate permission and spending checks |
| Handle actual change/failure | Explicit setup or relevant corrective action | Precise unavailable state | Existing failure observations | No silent price/authority/budget expansion or ledger reset |

These are local Harness observations, not managed Domain/Workflow events. Repository enrollment remains
TASK-00309's command and persistence contract.

## Validation and permissions

Persistent operator setup is a maximum disclosure allowance, not source-specific permission. Consumers still
recheck current authority at admission, dispatch and delivery. Validate configuration shape, nonnegative integral
confirmation time not in the future, exact pins and finite request/session ceilings. Price confirmation does not
claim current live pricing indefinitely: outgoing provider maxima and conservative accounting remain, including
halt on a reported breach. Provider maxima are requests, not proof that an upstream billing error cannot occur.
No operator settings, credential stores or ledgers are changed by implementing this chore.
