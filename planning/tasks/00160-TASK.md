# Enforce an operator-selected Pi tool policy

## Outcome

An operator can activate a versioned deterministic policy in the existing TypeScript Pi Harness, inspect its
coverage and restrictions, and have unsupported or denied tool operations stopped before execution. This usable
first slice of [TICKET-00038](../tickets/00038-TICKET.md) does not require Jev access and must identify itself as
"deterministic protection only". Normally deliver one independently reviewable PR.

## Scope

- Integrate the policy boundary into the existing local `harness/pi/` package. Qualify actual pre-execution
  interception for built-in read/write/edit/bash against an exact supported Pi runtime; pin the evidence and
  document how later argument-changing hooks are handled before claiming the executed operation was checked.
- Load versioned operator-controlled policy from machine-local settings outside repository instructions. Select
  allowed tools/roots, protected paths/resources, approved command forms and effect restrictions explicitly.
  Repository content and model output cannot activate, revise or broaden this policy.
- Protect the policy, guard implementation, credential resources and other configured protected paths through
  all declared supported Agent routes. Canonicalize paths and roots; handle symlinks and nonexistent write targets
  deliberately. Validate the final target immediately before the operation and document residual filesystem races.
- Permit bash only for operator-approved command forms or versioned scripts with constrained arguments. Deny
  unknown shell constructions, ambiguous encodings and unrecognized command forms before execution. An executable
  name alone is not a safe-command policy; arguments, working directory, selected script revision and effect class
  matter. Do not declare arbitrary interpreters or shell evaluation safe through a generic allow entry.
- Declare coverage for alternate tools, nested execution and child sessions. An additional route needs demonstrated
  interception before inclusion. Disable unsupported execution routes in the protected profile, including containing
  helper tools that could bypass the boundary. If the runtime cannot enforce that exclusion, refuse profile activation
  with the exact limitation instead of claiming coverage. This does not require implementing managed child launch.
- Show active profile/revision, declared coverage, restrictions and redacted reasons for blocked operations. Missing
  policy or required hooks prevents protected-profile activation; presentation-only installation does not activate it.
- Invalidate pending decisions on policy/source/session changes and cancel on reload/shutdown. Do not claim that an
  unloaded extension can reliably report its own absence; document the actual detection and status limitations.
- Out of scope: Jev calls, relevance screening, semantic judgments, managed Workflow permissions, sandbox qualification,
  process isolation, autonomous Agent launch, deployment, publication and post-result injection screening.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Select deterministic protection | Activate/revise an operator-owned policy | Inspect effective policy, coverage and restrictions | Profile revision/activation observation | Protected local configuration and visible status |
| Request a supported operation | Submit tool operation through interception | Inspect deterministic admission result | Permitted/blocked observation | Only permitted operations start |
| Encounter unsupported execution | N/A: reject activation or operation | Inspect missing coverage and supported alternatives | Coverage failure observation | No execution through an uncovered profile route |
| Cancel or replace a session | Cancel pending admission on lifecycle change | Inspect inactive/stale state | Cancellation observation | Obsolete pending operations cannot start |

These are local Harness integration operations, not new authoritative Workflow commands or grants.

## Validation and permissions

Check deterministic permissions before any future semantic screening. Bind admission to the actual tool,
arguments, working directory, resolved targets, policy revision, relevant source/script revisions and session.
Revalidate changed inputs; an earlier allow cannot authorize a modified operation. Never execute tool arguments
as part of validation. Treat repository data, policy-like text in files and tool parameters as untrusted.

Operator policy changes are separate from resolving a single operation. Agent writes cannot modify the effective
policy through supported routes. A denial never authorizes an equivalent effect through another tool. Protect
normal reasons/receipts from leaking credentials or sensitive source; retain bounded metadata by default.

This is incremental protection for trusted human-operated sessions. Approved scripts and their subprocesses can
have effects beyond visible arguments; qualify and state that residual risk. Working roots and command admission
are not filesystem/process containment, and same-user processes or malicious trusted extensions are not isolated
by these hooks. [TASK-00138](00138-TASK.md) keeps its separate execution-boundary requirements.

## Acceptance criteria

- [ ] The operator activates and inspects a versioned policy; the UI says deterministic protection only. Missing
  policy/hooks and unsupported coverage cannot produce a protected/ready claim.
- [ ] Actual Pi calls demonstrate allowed work and blocked protected-path, out-of-root, disallowed-tool and
  disallowed-effect operations before effects start. Include symlinks and new-file targets.
- [ ] Approved bash forms/scripts work with their permitted arguments; unrecognized constructions, unsafe argument
  variations and changed approved script revisions are rejected or require renewed operator policy selection.
- [ ] Supported alternate/nested/child routes pass the same boundary; unsupported routes are disabled or prevent
  activation. Evidence records exact runtime and coverage without claiming control of arbitrary subprocesses.
- [ ] A changed operation, policy, relevant source or session cannot reuse an old allow. Reload/shutdown cancels
  pending work and prevents obsolete operations or duplicated hooks from executing effects.
- [ ] Agent attempts through supported routes cannot rewrite guard policy/resources. Redacted status and reasons
  explain the block without exposing credentials or private source bodies.
- [ ] Guidance describes setup, permitted command forms, covered routes, residual shell risks and the distinction
  between deterministic protection, Jev-enabled protection and qualified sandbox isolation.
