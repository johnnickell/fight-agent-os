# Independently verify and hand off a hotfix PR

## Outcome

A confirmed hotfix repair with an exact Awaiting Review handoff can pass through independent non-contributing
Senior Engineer assessment, applicable targeted QA and separately granted Release Manager PR publication
against the configured production base. The initiating human receives the verified PR and retains merge
control. This is one independently reviewable hotfix-specific end-to-end verification and handoff integration,
not a reimplementation of generic Review, QA or landing infrastructure.

## Scope

- Consume [TASK-00206](00206-TASK.md)'s bounded incident scope, direct human contact, source/base/head,
  changed-tree, regression/check evidence, warnings, check-exception approvals and immutable handoff. Reuse
  managed independent Review, bounded revision, QA and publication capabilities described by
  [EPIC-00008](../epics/00008-EPIC.md) **only once implemented and qualified**. Do not mistake that EPIC's
  `done` metadata or [TASK-00146](00146-TASK.md)'s local QA skill for a managed runtime.
- Assign a separate Senior Engineer Agent/session with direct review Permissions, no contribution to this
  repair or its acceptance evidence. Validate the exact subject and all required checks or specifically
  authorized exceptions. An independent verdict alone cannot accept a changed/stale subject or skip review
  for urgency. Persist findings, bounded repair/re-review cycles and escalation to the incident owner through
  existing phase operations, without smuggling Team Lead into the direct route. Check exceptions name precise
  risk, containment/rollback and follow-up, not a fictional green gate.
- Run applicable targeted QA in a separate qualified session against the reviewed subject; record real
  pass/failure and justified criterion-specific N/A with provenance. A QA blocker stops PR publication and
  any material repair returns to independent technical review before affected QA repeats. Do not treat absence
  of a UI as automatic QA N/A; preserve visual or executable evidence as appropriate.
- Once current technical acceptance **and** QA permit, Release Manager alone uses its bounded PR publication
  grant to hand off one PR targeting the Repository-configured production base. Recheck live permissions,
  subject/base/head, source host, canonical eligibility/Workflow state and granted effects. Reconcile
  uncertain push/PR outcomes; no force-push, auto-approval, merge, signed tag, release or deployment. Distinguish
  verified PR handoff from production merge, which TICKET-00054 must later observe independently.

## Acceptance criteria

- [ ] Only a non-contributing Senior Engineer reviews the exact hotfix subject; changed commit/evidence, role
  collision or insufficient checks pause acceptance. Specific exception approvals remain visible and scoped.
- [ ] Applicable targeted QA challenges the reviewed behavior with fresh evidence or justified N/A. Failed or
  uncertain QA blocks landing; material repair receives fresh technical Review and affected QA within limits.
- [ ] Authorized Release Manager publishes/verifies **one** PR against the configured production base only
  after current independent acceptance and QA; duplicate/lost requests reconcile rather than duplicate push/PR.
- [ ] The incident owner sees progress, findings, blockers and verified PR URL. No hidden Team Lead phase,
  self-review, PR approval/merge, signed tag, package release or deployment is inferred.
