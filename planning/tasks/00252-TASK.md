# Manage Project associations and preferred Teams

## Outcome

A currently authorized administrator can associate a Team with additional registered Projects, inspect
current default/alternative Teams and explicitly change a Project's preferred Team. Changes are revisioned,
atomic and attributable, without granting access or retargeting already assigned work.

## Scope

- In scope: Protected add-association and set-default operations, complete safe association/default queries,
  PostgreSQL references/constraints and shared fences, current policy, expected-state checks, audit and safe
  post-commit outcomes through server/API paths.
- Out of scope: Unlink/removal, Agent membership/transfer, assigning work, fairness/selection, automatic fallback,
  Project identity duplication, browser UI or changes to existing Workflow/session provenance.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Link another Project | Owned explicit association command with expected Team/Project state | Current registered Project, Team, associations and default | Owned association/default facts after commit | Unique link and valid explicit default if first assignment, with atomic audit |
| Select preferred Team | Owned expected-state set-default operation | Complete current association set and linked candidate | Owned default-change fact after commit | Exactly one preferred associated Team; prior work retains its Team |
| Inspect default/alternatives | N/A — read-only | Safe current authorized associations and revisions, deterministic pagination | N/A | Complete bounded facts for administration and existing selection owners, not an eligibility grant |

## Validation and permissions

Each supported entry adapter admits TASK-00251's current managed Team-management authority and registered-Project
scope before configured bus dispatch. Registered Team-owned handlers coordinate expected state, Project lifecycle/
reference invariants, collection persistence and required audit through one generic transaction, including no-ops.
Ordinary admitted administration may finish after caller revocation; the next request checks fresh authority.
Unknown/archived Project, hidden Team, unlinked default candidate, lost authority and conflicting revisions
fail safely. If linking creates a Project's first Team assignment, require explicit default confirmation in
that atomic operation; otherwise preserve the existing default unless replacement was explicitly requested.

Enforce unique Team/Project links and exactly one linked default where associations exist through PostgreSQL
constraints and canonical transaction/reference fences. Cohort-first lock ordering and monotonic relevant authority
revisions apply to all writers and supported consumers; removal/readdition later cannot restore an old allow.
Use exact expected state rather than an HTTP-only preflight. State and required audit share commit/rollback;
no external provider call or nested repository transaction. Unknown commit results require fresh authoritative
inspection, not automatic replay, blind inverse operations or false rollback.

A new association supplies only one necessary scope fact: it grants no direct Permission, expands no bound Agent
Project scope or initiating-human grant, and adds no Workflow authorization. Default selection affects future
intake preference, never existing Team assignments, session snapshots or already-granted work. TICKET-00064
revalidates actual eligibility at the owning start; it cannot treat this query as a durable admission token.

Return only safe typed Team/Project/default identities and authorized metadata/revisions. Stable paging must not
lose alternatives or confuse partial/outage results with an empty set. Do not expose unrelated roster, private
session/tool data or credential material. HTTP follows existing protected JSend/OpenAPI/error conventions.

## Acceptance criteria

- [ ] One Team can serve several explicit registered Projects and a Project can list several Teams while
  retaining exactly one explicit linked default; no duplicate association or silently selected alternative exists.
- [ ] Competing default edits, link/default changes, Project lifecycle changes and no-ops serialize safely;
  rejected/rolled-back work leaves no partial default, association or audit.
- [ ] Safe complete queries identify current revisions and alternatives without granting authority or changing
  selection fairness, TASK claims, Agent scope, active sessions or historical assignments.
- [ ] Revoked management rights, wrong scope, unknown/archived Project, stale confirmation and unavailable
  storage deny direct/API writes with useful safe recovery, not a partial-success result or automatic retry.
- [ ] Confirmed commits retain post-commit event semantics; uncertain outcomes remain distinguishable until
  authoritative inspection. Destructive unlink/removal is unavailable until TASK-00254's protections exist.
