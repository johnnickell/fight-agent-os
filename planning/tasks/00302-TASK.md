# Generate and review real AI template proposals behind controlled rollout

## Outcome

An authorized administrator requests a real provider-assisted template suggestion, edits both the proposed system
prompt and complete requested Permission set, and explicitly publishes through TASK-00300's existing editor.
This delivers TICKET-00077's actual AI authoring outcome and the first real `ai-template-proposals` Feature use.
Recovery, controlled rollout and affected integration evidence belong inside this single vertical TASK, normally
one PR, not separate infrastructure, demonstration or proof products.

## Scope

- In scope: Generate/Regenerate integration in the existing browser editor; protected Harness/provider proposal
  admission, scoped structured candidates, human editing/discard/review, status/result/cancellation/recovery;
  actual Feature declarations and all supported admission guards; real provider-to-publication evidence.
- Out of scope: A new model endpoint/provider client, conversation platform, proposal queue or browser draft store;
  generic Harness primitives owned by EPIC-00006; another editor/publisher, Agent creation or Permission assignment;
  ancestor review, existing-Agent reconciliation, Skill/repository-instruction editing, autonomous publication,
  Feature retirement or manual-create Feature UI/API.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Request or deliberately regenerate a suggestion | Existing protected Harness proposal admission with exact human intent | Current template-management authority, Feature admission, scope, allowed provider/model, disclosure and budget | Owned committed attempt facts, not template publication | One bounded authorized provider request after recoverable intent commits |
| Inspect and edit a suggestion | Volatile human edits or explicit discard; inspection is read-only | Protected exact attempt/result, structured candidate, provenance and current references | Existing lifecycle observations only | Untrusted proposed prompt and complete requested set become human-reviewable, never authoritative |
| Stop or recover admitted work | Existing authorized cancellation or exact-attempt recovery | Current authority, original attempt/outcome and provider/session state | Owning lifecycle facts only when established | Safe cancellation/continuation or truthful uncertainty without a new paid request |
| Publish human-reviewed content | TASK-00300's existing publication operation | Fresh actor/scope/candidate/reference and expected-selection checks | Existing committed publication fact | Immutable template revision for future use; no Agent grant, rebind or session change |

These names describe integration responsibilities, not existing message classes. Use the existing Harness owner
and actual qualified contracts; unsupported capabilities stay unavailable rather than acquiring guessed APIs.

Reuse TASK-00300's supported eligible Permission choices and validation. Decode bounded structured output strictly;

items, not a salvaged successful complete set. No name substitution, automatic Permission creation/grant or silent

A result is advice, not a template revision or an executable instruction. Let the human inspect, edit or discard
both prompt and requested set and deliberately request another bounded suggestion. Any candidate edit invalidates
prior publication review under TASK-00300. Late output may remain an authorized historical result but cannot replace
newer human edits, reattach to another draft, revive discarded/cancelled work or approve itself. Conflict requires
fresh explicit human choice; no automatic merge-and-publish. Publication uses only TASK-00300's ordinary operation,
expected-state protections and original-outcome handling, changing no existing Agent grants/bindings or snapshots.

### Recoverable lifecycle without duplicate paid work

Use protected durable Harness attempt/result ownership for admitted work, separate from authoritative template
revisions and volatile browser edits. Persist required intent/audit in its canonical transaction before external
provider effects; claim and outcome transitions retain the owning fence/currentness rules. No external call inside
a business transaction, nested package transaction, repository-hidden audit or event-only recovery authority.
Do not repurpose AccessControl credential-delivery state as a model request queue.

Define and qualify the original-attempt admission/dispatch/outcome boundaries, duplicate request correlation,
cancellation and recovery with actual provider semantics. Pending, completed, failed, stale, cancelled and uncertain
states remain distinguishable. Browser disconnect/refresh is not cancellation, regeneration, publication or proof
of failure. A stop request cannot promise to unsend accepted work, erase billing or instantly kill an external call.
A late completion cannot revive cancellation or overwrite a superseding attempt.

After timeout, worker replacement, lost acknowledgement or uncertain billing, reconcile the original protected
attempt using supported outcome/status facilities. No automatic new provider call, duplicate session, spend-reset,
new identity or silent regeneration may hide uncertainty. Where the provider cannot establish safe recovery, retain
a bounded unresolved/needs-human state rather than claim exactly-once delivery. Explicit regeneration is a new
admission and cannot disguise replay of an unknown call; resolve uncertainty as required by the provider owner.
Status/result reads remain nonmutating and never invoke the provider or repair/retry work as a GET side effect.
