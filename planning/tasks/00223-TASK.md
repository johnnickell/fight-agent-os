# Execute the approved application rollout and reconcile provider state

## Outcome

On the same certified application release Workflow, a separately permissioned Release Manager requests
**only** the approved project-specific rollout to the named environment, records durable intent and
independently reconciles the provider's observed rollout/deployable identity. Duplicate or timed-out requests
cannot silently create another deployment, and acknowledgement is not verified health or release completion.

## Scope

- Consume [TASK-00222](00222-TASK.md)'s qualified project target/preflight,
  [TASK-00215](00215-TASK.md)'s exact artifact digest or commit and [TASK-00216](00216-TASK.md)'s current
  bounded named-effect grant. Recheck TASK/Workflow claim, certified subject, optional required signer proof,
  Repository/provider/environment identity, versioned runbook, required checks, current provider target,
  actor's direct Release Manager deploy Permission, budgets and approved effect scope **at invocation**.
  Team Lead coordinates but never inherits provider credentials; ordinary `land` is not deployment authority.
- Persist one stable effect identity and durable attempt intent in the owning Workflow transaction before
  invoking the *qualified selected project's* deployment adapter after commit. Broker provider credentials
  behind the adapter, not in Agent shells, prompts, logs, event payloads or receipts. Do not create a generic
  shell executor, arbitrary endpoint deployment or platform-independent rollback operation. Never perform
  network/provider effects inside a database transaction or claim exactly-once provider delivery.
- After request/timeout/interruption, observe actual provider rollout status, target environment,
  deployed artifact/digest, revision and effect identity. Record requested, provider-accepted, running,
  partial, verified-target, failed and unknown outcomes separately as supported by the project contract.
  On lost response reconcile authoritative/provider state **before** retry, using the same Workflow and
  effect identity; ambiguous state pauses with a concrete next action. A provider acknowledgement, green
  command exit or replica/pod with the correct image is not sufficient evidence of all configured targets
  or healthy service. Leave health and permitted recovery to [TASK-00224](00224-TASK.md).
- Out of scope: automatic rollback, human signing, host/tag release, branch follow-through, final health
  acceptance or release TASK `done`. One deployment stage on one release TASK, not a TASK per attempt.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Start approved rollout | Existing same-Workflow bounded Release Manager deployment operation | Fresh grant, direct Permission, certified subject, exact environment/provider, prior intents and current target | Durable deployment intent before effect, separate provider observation afterward | Only the named rollout with stable effect identity; no implicit second target |
| Reconcile interrupted/partial outcome | Existing inspect/resume operation for that effect identity | Current provider rollout and target/artifact, prior intent, live authority | Verified-target, partial, failed or unknown recovery fact | No duplicate request on unknown outcome or inferred health |

These are selected project-provider effects using existing Workflow authority, not an Agent-issued
production grant.

## Validation and permissions

Require direct Release Manager deploy Permission **and** an unexpired, unused, exact-candidate human grant
that names this environment and effect. Enforce expected Workflow/plan/runbook/Repository versions,
artifact/digest identity, health prerequisites and limits; deny expired, revoked, mismatched, repeated or
expanded requests. Plan approval alone does not supply credentials. Provider secrets remain isolated in
qualified adapters; mask error/response content in safe Views and logs. Only observed authoritative/provider
facts can resolve uncertain effects; changed config/target, ambiguous provider state or lost authority
pauses without a second TASK or automatic retry/rollback. Never confuse Planning TASK implementation
acceptance or ordinary PR landing with production deploy approval.

## Acceptance criteria

- [ ] Release Manager, with direct Permission and current bound grant, can request only the certified
  artifact to the approved named environment under the qualified runbook; wrong candidate, new target,
  stale policy, revocation or exhausted limits refuses before mutation.
- [ ] Durable intent survives interruption and is distinct from provider acknowledgement, observed target
  identity and independently verified health. No status/event asserts successful release on queued rollout.
- [ ] Duplicate/concurrent delivery and timed-out requests reconcile the same effect against actual
  provider state before retry and avoid repeated production mutations or fabricated completion.
- [ ] Team Lead/Agent prompts, local PR landing and runbook text never expose deployment credentials or
  create a generic deploy/rollback authority.

## Verification and evidence

Test owned permission/plan/candidate/environment decisions, durable intent, concurrency, revocation,
provider timeout before/after acceptance, partial target and duplicate/restart reconciliation using
focused Domain/Application, PostgreSQL transaction/race and important selected-provider adapter contracts.

never deploy to production to prove this implementation absent specific authority. Record exact observed
identities and provider limitations separately from fixtures; do not product-test deployment CLI,
configuration/runbook prose, migrations or test infrastructure. Run focused checks and `./bin/build` with
fresh counts/exits/warnings; independent review and delivery remain separate.
