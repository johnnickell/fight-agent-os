# Prepare and reuse exact worktree-owned testing runtimes in local Work and Build

## Outcome

Remove repeated manual runtime reconstruction and ambiguous shared-stack use from approved local isolated
Work/Build journeys. Work prepares the repository's actual required testing runtime early; Build carries its
exact verified binding through independent stages, repairs and final cleanup. John approved this bounded
standalone chore and cleanup-first top priority on 2026-10-27. This is local workflow preparation, not the
future managed PHP-owned provisioner, browser authority or a second Workflow engine.

## Scope

- After task/scope/checkout validation, Work resolves the target's documented capabilities and owning wrappers
  and prepares its required services. Applications receive the actual web/API, database, cache, worker and
  client/browser prerequisites needed by their checks, as applicable. Libraries such as Fight Common receive
  their real disposable test dependencies, not a dummy persistent application stack to populate a log pane.
- Use a unique task/worktree-owned Compose identity or equivalent qualified binding, private database/cache/
  storage, nonconflicting loopback ports and disposable local settings. Main-checkout execution is an explicit
  separate mode; never infer permission to use its shared application as a fallback or mutate shared services.
- Prove source mounts/build revision, current service generations, exact configuration/override/env-file
  locators/digests, service allowlist/purpose, readiness, processes and endpoints. A healthy URL alone is not
  source proof. Retain secrets privately; handoffs carry identities/digests, not environment values or keys.
- Establish finite per-runtime and concurrent CPU/memory/PID/storage/port/time budgets and observable readiness/
  recovery limits. Account for task-created versus used/shared resources, including named and image-declared
  anonymous volumes before creating containers disappear, networks, processes and build/cache artifacts.
- Revalidate and reuse a healthy exact-subject runtime across Work, independent Review, QA, repairs and resume.
  Build coordinates the existing handoff; it neither implements source nor provisions a competing stack.
  Role changes alone must not multiply resources, regenerate keys, reinstall dependencies or repeat full gates.
  Record material source/runtime changes and their effect on evidence applicability.
- Publish a narrow observation binding through the existing accepted local runtime/source mechanism under
  ignored `var/`; retain execution evidence under `.runs/`. The human-only log observer verifies source and
  generation independently, receives no start/stop authority and never automatically ingests logs into the model.
  Reuse existing metadata/handoffs, not a speculative global registry or model-owned provisioning service.
- Apply TASK-00542's cleanup contract on success, failure, cancellation and interrupted recovery. Unknown or
  required unresolved cleanup is incomplete, not blanket retained-by-policy success. Shared reuse needs an
  explicit owner/consumer/accounting/retention contract and cannot become implicit disposable ownership.
- Out of scope: managed Runner/PHP preparation, restricted execution or durable Workflow intents, hostile-code
  sandbox claims, browser process management, automatic fleet setup, global installation, production services,
  external credentials/inboxes, shared-service shutdown and indiscriminate pruning.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Start isolated application work | Existing local Work/Build entry and target owning runtime wrappers | Required capabilities, exact checkout/configuration/source and readiness | Existing private runtime handoff; no application domain event | Required owned services ready with private state/ports and verified observation binding |
| Work in a library | Existing package checks and disposable test-dependency launcher | Actual dependencies and supported transient log sources | Private readiness/no-persistent-stack state | Real test dependencies only, no invented application stack |
| Change stage, repair or resume | Existing handoff and owning read-only runtime checks | Current source/configuration/generation, budgets and consumers | Revalidated or explicitly superseded binding | Reuse exact healthy runtime or finite prerequisite, without duplicate setup |
| Finish, fail or cancel | Existing bounded cleanup/recovery | Creation provenance, authority, actual resources and prior effects | Cleanup result or finite hold | Eligible disposable resources absent; protected/shared resources unchanged |

## Validation and permissions

Implementation requires an approved task and operator-selected registered checkout plus documented runtime/setup
authority; a planning record or observer cannot expand it. Reject unknown source, contradictory settings,
missing dependencies, stale generations, port/resource conflicts and unsupported capabilities with an exact
prerequisite/owner. Do not recover by starting defaults, modifying shared services, importing main private
settings or weakening controls. Distinguish explicitly permitted shared dependency use from private owned
state. Qualification may create bounded task-owned disposable fixtures under its execution authority, never
use live Omphalos data or another task's stack as disposable proof. Keep runtime under `var/`, evidence outside
deletion candidates under `.runs/`, and private state/credential values out of reports.

## Acceptance criteria

- [ ] Work prepares the real required application stack or library-specific disposable dependencies through
  owning commands, with exact source/readiness proof and truthful library/no-persistent-stack handling.
- [ ] Two concurrent registered worktrees run their required checks without source/database/cache/port/artifact
  cross-contamination; private settings, finite budgets, exact identities and forbidden shared writes are observed.
- [ ] Existing handoffs carry configuration/env locators/digests, source/service generations, endpoints,
  readiness, resource provenance/budgets and cleanup authority through Work, independent Review/QA and a
  repair/resume boundary. Exact-subject revalidation enables reuse without per-stage resource multiplication.
- [ ] The existing `var/` runtime-binding mechanism gives human-only observers independently verifiable
  sources. No observer provisioning, automatic model log ingestion, global registry or shared-source fallback appears.
- [ ] Success, failure, cancellation and interruption meet TASK-00542's qualified lifecycle: zero required
  owned disposable leftovers or precise incomplete holds, complete named/anonymous volume provenance, finite
  recovery and unchanged protected resources. Shared retention is evidenced rather than assumed.
- [ ] Direct owning-tool probes, focused checks, planning/diff validation and one final canonical local gate
  qualify the finished implementation; independent Review and affected QA assess actual local stage/runtime use.

## Verification and evidence

Use real owning wrappers with bounded disposable application and library fixtures, two registered worktrees,
actual runtime/source/mount/port observations, and Work/independent-stage/repair-resume handoffs. Include missing
setup, contradictory source, stopped/replaced generation, port/resource conflict and interrupted cleanup. Record
fresh versus reused evidence, exact revision/tool/runtime subjects, counts/exits/warnings and cleanup results;
record installed supported Pi capabilities/versions as evidence, never future version guarantees. Qualify
infrastructure directly, with no product-suite tests of wrappers/planning/runtime wiring and no deliberately
seeded quality-tool failures. Run focused owning checks, planning refresh/check, `git diff --check` and one
complete final `./bin/build` on frozen finished implementation. Independent Review and applicable nonvisual/
interaction QA remain separate from Work's probes. Missing required fixtures/capabilities are incomplete, not PASS.
