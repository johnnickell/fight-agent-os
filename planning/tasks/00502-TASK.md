# Follow current-session children and their worktree test logs automatically

## Outcome

The Pi terminal workspace automatically observes the current session's active child and the existing test Docker
stack associated with that child's worktree. Operators can choose among concurrent children and pin one without
manually supplying a socket or repeating runtime selection on every switch. This extends
[TICKET-00110](../tickets/00110-TICKET.md)'s local observation experience after TASK-00448 and TASK-00449.

## Scope

Include trusted current-session child registration/discovery, automatic observation selection, a concurrent-child
selector, pin/unpin, and worktree-bound test-stack selection through the existing trusted Docker reader. Include
the minimal local runtime association needed to identify an existing stack reliably. Retain the initial explicit
shared main-checkout log mode as a separately labelled operator choice.

Exclude provisioning per-worktree containers, Compose overrides, starting/stopping/reconfiguring containers,
changing agents' directories or permissions, managed Workflow attachment, browser integration, log collection,
retention/search and automatic ingestion of either pane into model context. Existing runtime preparation remains
with TASK-00140/TICKET-00032; this TASK does not depend on their entire managed scope or broader observability.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Observe the current session | Enable automatic following; choose child | Trusted session-bound live child registrations and safe monitor state | Existing child lifecycle observations | Read subscriptions and bounded presentation state only |
| Keep a particular child visible | Pin/unpin child | Selected attempt, worktree and lifecycle | Completion/disconnection never changes a pinned selection | Pin scoped to the current parent session |
| Follow the observed worktree's test logs | Follow worktree; select an associated stack/service when ambiguous | Verified existing test-stack binding and bounded Docker output | Selection/source-generation changes | Replace the log reader; no container lifecycle changes |
| Resume or change session | Existing supported session selection/resumption | Actual Pi session identity and eligible child registrations | Session change invalidates old selection/subscriptions | Recompute observation sources without changing any agent's execution |

### Session and child association

Use supported Pi session identity plus a trusted launcher/monitor association, not task names, working directory,
process proximity or same-user socket ownership as proof of parent membership. Extend the local build launch path
and monitor contract so newly launched authorized children register their parent session, attempt, canonical
worktree, endpoint and generation automatically. The existing observation identity lacks parent-session identity;
implement that association rather than assuming TASK-00448 already supplies discovery. Registration is local
observation metadata, never workflow authority or a grant to launch another child.

Use ignored `var/` for runtime registrations and preferences. Do not make `.runs/` ledgers/evidence an application
runtime dependency. Preserve the supported native-Pi workflow launch/resume boundary: the custom RPC client must
not start executing native-only workflow commands to obtain discovery. Qualify the actual supported launch path,
including native launch followed by workspace resumption of the same session. Unsupported/legacy children without
trusted registration remain explicitly unavailable; observing them must not relaunch them.

Automatic following is the default for eligible current-session children. With one active child, select it. With
multiple, retain the selected child while it remains active and show a keyboard-accessible selector with role,
TASK, worktree, attempt and state. If no selected active child exists, select the most recently started eligible
child using trusted start order and a stable attempt-ID tie-breaker. New output or a newly started sibling does not
steal an active selection. An explicit choice becomes the current selection; pinning prevents automatic switches
even after completion or disconnection. Unpinning recomputes the active choice. With none active and no pin, show
an honest idle state and return worktree-log context to the primary session's worktree. Session changes clear pins
and subscriptions from the previous session; resumption rediscovers only valid registrations for that session.

### Worktree and test-stack association

In follow-worktree mode, logs follow the selected/pinned child's verified worktree; with no selected child they
follow the primary session's worktree. Show primary-session, observed-child and log-source identities separately.
Selection changes observation only, never the primary process directory, session or grants.

Establish a trusted local association for an already existing test stack: canonical worktree, test-stack purpose,
Docker context and resolved local endpoint, Compose project, source generation and eligible services/containers.
Integrate association publication with the existing trusted test-runtime preparation path where available;
provide explicit human binding for an existing stack when it has no association. Qualify the repository's actual
test launch lifecycle before implementing this bridge. Do not infer ownership from a project-name prefix, current
directory, arbitrary repository configuration, model output or an old evidence receipt. A saved binding is a
candidate, not authorization to trust changed Docker metadata.

Reuse TASK-00449's fixed read adapter and verify current Docker metadata, exact canonical checkout labels and
container identities before subscribing. A shared Docker daemon or main-checkout runtime is not proof of a
worktree test stack. If several valid test stacks belong to the worktree, require a labelled stack selection;
remember that choice only while its verified binding remains valid. Preserve service selection where valid and
otherwise show the available verified services. Switching children within one worktree can retain the same valid
source. Switching worktree, stack or container generation cancels the old reader and rejects late old-source
output; old lines must never appear attributed to the new source.

Missing, stopped, removed, ambiguous, denied or mismatched stacks show an explicit state. Never silently fall back
to main-checkout logs or create a stack to fill the pane. A recreated stack requires fresh identity validation.
The operator can explicitly choose the existing shared-runtime mode, whose label and behavior remain distinct
from follow-worktree mode. No manual per-child socket flags or per-switch runtime flags are required for the
qualified automatic path.

## Validation and permissions

Preserve Harness tool restrictions, file screening, current enrollment and provider protections. Local observation
is not a sandbox or new permission boundary. Validate registration provenance, endpoint custody, parent/attempt
membership and lifetime; reject stale, malformed, cross-session and replaced registrations. Do not permit an
agent-controlled file or payload to grant access to another session's child or an unrelated Docker source.

Docker access stays in the trusted human-facing host adapter with fixed argument operations and no shell or
arbitrary Docker/Compose configuration execution. Never expose Docker socket access, credentials, arbitrary
commands or pane streams to children/tools/model context. Docker daemon authority itself remains powerful.
Retain safe terminal rendering, finite buffers, bounded subscriptions/reconnects, visible gaps and truthful
completion states. Pinning cannot expand authority. Closing/rebinding panes stops readers only, not children or
containers. Choose and document limits for registration discovery/cleanup and concurrent subscriptions.

## Acceptance criteria

- [ ] A newly launched supported child appears automatically in the workspace for its actual parent session, including native launch followed by resumption; no manually supplied observation socket is needed.
- [ ] Two parent sessions in the same checkout cannot discover/select each other's children; stale/replaced registrations and late events do not cross session or attempt boundaries.
- [ ] One active child is followed automatically; multiple children have a usable selector and stable selection under concurrent output. Completion, pin/unpin, disconnect and session switching follow the specified rules.
- [ ] Selecting or pinning a child selects its verified worktree test-log context. With no selected child, the primary session's worktree supplies context; the UI never implies the conversation directory changed.
- [ ] Two worktrees with distinct existing test stacks display only the selected worktree's verified output. Multiple stacks require selection; changing/recreating sources cannot mix identities or buffered output.
- [ ] Missing/unavailable/mismatched sources are explicit, with no silent shared-runtime fallback or container lifecycle action. Explicit shared mode remains available and clearly labelled.
- [ ] Real wide/narrow terminal use demonstrates the selector, pin state, focus and source identities; observing or switching cannot grant tools, cancel children or feed pane output to the model.
