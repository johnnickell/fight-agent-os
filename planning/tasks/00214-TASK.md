# Start one recoverable release Workflow

## Outcome

One deliberate authorized start for a supported `release` TASK passes Triage into a **distinct**, durable
Team Lead-coordinated release Workflow using the existing authoritative atomic start/claim operation. It
returns the one Workflow's identity and actual stage without a second routing confirmation, and recovers
interrupted dispatch without a second claim. Start does **not** certify a candidate, approve publication,
perform an external effect or complete the TASK.

## Scope

- Extend [TASK-00204](00204-TASK.md)'s terminal Triage-to-start interaction and
  [TASK-00139](00139-TASK.md)'s existing PHP Start coordinated work operation for the qualified release route
  from [TASK-00213](00213-TASK.md). No separate release queue, status setter, claim API or routing authority.
  Bind the initiating human's scoped intent to TASK/project, candidate intent, Repository context/runbook and
  route revisions, grant, chosen role/profile, budgets, current Planning eligibility, and expected claim.
  Server-side PHP rechecks live Permissions, current eligibility, qualified route and runbook, context, actor,
  grant, profile availability, sandbox and cost/time limits when it atomically persists the one Workflow,
  exclusive claim and durable dispatch intent. Enable the catalog's executable release capability only when
  this distinct managed route is actually qualified; otherwise remain explicitly unsupported.
- Team Lead is the distinct accountable release coordinator and human contact, with a separate scoped session
  and direct Permissions. Do not send a release to ordinary feature/bugfix/chore implementation, or give Team
  Lead Release Manager credentials, implementation acceptance or a signer key. Preparation, independent
  acceptance, grant and signing phases are later slices on this **same** TASK/Workflow.
- Reuse [TASK-00142](00142-TASK.md)'s runner isolation, durable lease, recovery, cancellation and process
  reconciliation: a duplicate command returns the original Workflow, a competing request returns safe
  current-owner reasons, and a lease expiry alone never releases the TASK. Resume checks the existing claim,
  session/phase identity, attempts, authority and pending intent before dispatch; cancel/release only after
  quiescence or explicit human recovery. Keep unrelated checkouts and claims intact.
- Out of scope: project certification ([TASK-00215](00215-TASK.md)), bounded effect approval
  ([TASK-00216](00216-TASK.md)), signing ([TASK-00217](00217-TASK.md)), library publication
  ([TICKET-00057](../tickets/00057-TICKET.md)) and application deployment
  ([TICKET-00058](../tickets/00058-TICKET.md)).

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Start supported release | Existing authorized start operation via terminal Triage | Current selected TASK, canonical eligibility, qualified project policy/route, direct grant, ownership and runner availability | Existing start/claim/dispatch facts with release type and bound context | Exactly one Team Lead Workflow and TASK claim; no publication/deployment on start |
| Inspect or retry start | Existing inspect/idempotent start operation | Authoritative Workflow, claim, command identity, stage and dispatch observation | Existing reconciliation facts only if an outcome is established | Same Workflow for same request; safe refusal of competing or stale intent |
| Pause or cancel | Existing bounded pause/cancel/recover operations | Live phase, active peers, costs, limits, revocation and pending intents | Existing attributed paused/recovered/cancelled facts | Recover or stop the same Workflow; no claim release while effects are uncertain |

No new generic start command or inference of success from a process exit is authorized by these names.

## Validation and permissions

Treat Triage/Jev recommendation as advisory; the current human start request is not a candidate-effect grant.
Check actor and Team Lead direct Permissions, Repository/project scope, current route and runbook qualification,
TASK/context/catalog/profile revision, sandbox readiness, budget and idempotency under the owning atomic
claim. A request before managed release capability is qualified returns unavailable. A changed candidate
intent, policy, authority, conflicting claim, unavailable profile, missing resource or unsafe prior dispatch
pauses/refuses with redacted actionable reasons; no ordinary-route fallback. No external effects occur inside
Planning/Workflow transactions. Live authority is checked again at every later effect; the start grant never
silently expands to signing, push, GitHub release, deployment, rollback or merge.

## Acceptance criteria

- [ ] One authorized selected release uses one start intent, the existing server-authoritative start/claim,
  and the distinct Team Lead route with no extra routing prompt or per-stage TASK; unsupported release refuses.
- [ ] Start atomically rechecks canonical eligibility, live scoped grant and Permissions, policy/route/context,
  profile, resources and owner; it records one durable Workflow and exclusive claim, not a completed release.
- [ ] Duplicate start and interrupted dispatch return/recover the same Workflow; competing start, expired
  lease, stale scope or uncertain active effects cannot create a second Workflow or release the claim early.
- [ ] Visible stage and refusal preserve provenance and a concrete next action without leaking secrets or
  claiming that Team Lead acquired Release Manager/signing authority.
