# Establish the installation-owned Planning runtime

## Outcome

The completed application foundation runs through one installation-owned, pinned, health-checked Compose topology with shared HTTPS ingress, private PostgreSQL and Planning evidence storage, foundation-required supporting services, explicit migrations, durable state, and no competing development architecture or premature Agent execution capability.

## Scope

- In scope: Replace the inherited single `web` service with the EPIC-00005 portion of the accepted topology; shared Nginx and separate `docker-gen`; application Nginx/PHP-FPM; existing PostgreSQL authority; private pinned SeaweedFS S3-compatible storage; Mailpit required by the completed authenticated foundation; any Redis/Mercure roles actually required by that foundation; private and ingress networks; health/readiness checks; bounded restart policies; named durable volumes; service-specific secret mounts; explicit migration/start/update/down/status/backup-recovery guidance; thin host wrappers and container-native build/test entrypoints; zero-host-mutation `<name>.localhost` HTTPS plus explicit custom-name seams.
- Out of scope: Agent runner/consumers, Workflow dispatch, provider traffic, Execution Artifact semantics, browser-triggered installation, arbitrary registered-project lifecycle control, observability stacks, dynamic previews, autoscaling, production deployment, automatic schema migration, automatic upgrades, and hidden certificate/DNS/privilege mutation.

## Validation and permissions

Pin every image and runtime tool to an explicit reviewed version. Use readiness and health checks instead of sleeps, keep migrations and upgrades separate from container start, and reject unsafe or incomplete production-like configuration before serving traffic. Preserve the one shared Doctrine/PostgreSQL authority and the completed authentication/security contracts rather than introducing alternate connections, request-time schema changes, or another application runtime.

Only shared public ingress joins the installation-owned external ingress network. Application runtime and all databases, mail, caches, hubs, and object storage remain private. Follow the accepted separate proxy topology: only non-public `docker-gen` receives the required read-only Docker socket; application Nginx, PHP-FPM, workers, and storage receive none. Do not expose SeaweedFS, PostgreSQL, Redis, Mercure administration, or Mailpit publicly. Any development-only Mailpit browser path remains narrowly restricted under the completed security envelope.

Generate or enroll secrets only through explicit operator steps. Keep keys, credentials, connection details, certificate private material, and machine state ignored and outside images/logs/browser output. Mount each secret only into the service that needs it. Use durable installation-owned volumes for PostgreSQL and SeaweedFS; declare the role and persistence expectation of every other volume.

Use standard 80/443 shared ingress as accepted. `<name>.localhost` requires no hosts-file mutation; custom names, certificate trust, DNS/hosts changes, privileged ports, backup, restore, and upgrades remain explicit, reversible human-run operations. Never collect sudo or administrator credentials. Do not claim installation success from container creation alone.

No application permission grants infrastructure mutation. Runtime wrappers are operator tools and must not imply browser authority, Repository registration, approved-root access, Planning cutover, Agent execution, or Artifact availability.

## Acceptance criteria

- [ ] One installation-owned Compose project replaces the inherited single-service path without retaining a competing development architecture.
- [ ] The application runs behind application Nginx/PHP-FPM and shared HTTPS ingress while PostgreSQL, SeaweedFS, mail and supporting services stay on private networks.
- [ ] Shared ingress follows the accepted Nginx/`docker-gen` separation, and only `docker-gen` has a read-only Docker socket.
- [ ] Images and tools are pinned; services use bounded health/readiness and restart behavior with no sleep-based or automatic-upgrade claims.
- [ ] PostgreSQL schema changes occur only through explicit migrations, and application startup does not create or update schema.
- [ ] PostgreSQL and SeaweedFS use durable installation-owned volumes and survive a directly exercised bounded restart.
- [ ] Secret and certificate material remains ignored, absent from images/logs/browser output, and mounted only where required.
- [ ] `<name>.localhost` reaches the application through HTTPS; custom hostname, trust and privileged host effects remain explicit and reversible.
- [ ] Existing host wrappers stay thin, and prepared containers run application/build commands without recursive Docker or a mounted Docker socket.
- [ ] No Runner, Agent consumer, provider, Workflow, registered-project control, or Execution Artifact capability is fabricated.
- [ ] Direct runtime, migration, ingress, isolation, persistence and recovery checks plus the canonical build pass with fresh evidence.
