# Establish secret-safe outbound effect capabilities

## Outcome

Application-owned mail-delivery and external-audit-publication capabilities expose minimal provider-neutral, idempotent, secret-safe inputs and typed outcomes, with deterministic network-free adapters for tests and fail-closed production composition when no real provider is configured.

## Scope

- In scope: Capability contracts and immutable input/outcome types; stable idempotency identity; minimum destination/template/reference/bounded variables; safe handling of credential-bearing invocation material; recoverable/permanent outcome classification; redacted diagnostic projection; null/in-memory mail and audit adapters; test/development composition and production absence guard.
- Out of scope: Production provider enrollment, SMTP/API clients, invitation/reset business policy, credential generation/cipher selection, durable processor/runner, user-facing delivery status, general job infrastructure, and provider-specific payloads.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invoke mail capability | N/A — outbound capability operation | Read minimal in-memory destination/template/reference/variables and stable idempotency identity | N/A — no domain event | Adapter records/sends one provider-neutral attempt and returns a typed outcome |
| Publish safe audit evidence | N/A — outbound capability operation | Read approved secret-free actor/action/subject/context projection | N/A — no domain event | Adapter records/publishes evidence with stable idempotency identity |
| Classify provider result | N/A — capability result | Inspect typed success/recoverable/permanent outcome and bounded safe code | N/A — no domain event | Caller can persist retry/terminal state without parsing arbitrary messages |
| Test effects deterministically | N/A — test adapter operation | Inspect redacted invocation records | N/A — no domain event | Tests assert attempts/outcomes without network or secret capture |

## Validation and permissions

Use capability names based on behavior, not a vendor or transport. Inputs contain only the minimum required destination, template/reference, bounded variables or safe audit evidence, and stable idempotency identity. Define strict size/type keys and prevent arbitrary object serialization.

Credential-bearing values may be materialized only for the invocation lifetime. They must not appear in ordinary query/status Views, `__toString`, dumps, snapshots, logs, exception messages, audit context, analytics, or recorded test-adapter output. Redacted records retain only safe identifiers/classification needed for assertions and operations. Provider credentials remain external and never enter capability inputs or durable intents.

Success, recoverable failure, and permanent failure are typed. Safe bounded reason codes may be returned; arbitrary provider exception text is diagnostic-only under redaction and cannot decide policy implicitly. Stable idempotency identity is passed unchanged on every repeated attempt.

Null/in-memory adapters are deterministic, configurable, and network-free. They are registered only in explicit test/development composition. Production composition must fail closed when a required real capability is absent; it cannot silently drop delivery through a null adapter.

No end-user permission applies. Internal capability invocation is later restricted to registered durable work; this TASK does not authorize product delivery or provider credentials.

## Acceptance criteria

- [ ] Mail and external-audit capability interfaces are application-owned, provider-neutral, and behavior-named.
- [ ] Immutable inputs expose only minimum bounded destination/template/reference/variables or approved audit evidence plus stable idempotency identity.
- [ ] Credential-bearing material is available only during invocation and absent from ordinary reads, stringification, logs, exceptions, snapshots, audit context, and test-adapter records.
- [ ] Provider credentials cannot be stored in capability inputs or durable intent.
- [ ] Success, recoverable failure, and permanent failure are explicit typed outcomes with bounded safe diagnostics.
- [ ] Stable idempotency identity is preserved unchanged across configured repeated in-memory attempts.
- [ ] Null/in-memory mail and audit adapters are deterministic, network-free, and inspectable through redacted records.
- [ ] Test/development composition can select deterministic adapters explicitly; production-like composition fails when no real required capability is configured.
- [ ] No invitation/reset policy, real provider, processor, or worker is introduced.
- [ ] Focused capability/composition/redaction checks and `./bin/build` pass with fresh evidence.
