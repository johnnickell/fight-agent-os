# Integrate separate QA Engineer verification

## Outcome

Connect a distinct same-Team QA Engineer to the existing managed QA phase after current independent technical
acceptance. Exercise actual changed behavior with attributable evidence and safe current-use bindings. QA can
block publication but cannot repair reviewed source, grant technical acceptance or create another revision loop.

## Scope

- In scope: Missing Agent/Team/session/current-use and exact-subject bindings at the owning QA handoff, meaningful
  actual behavioral verification, safe evidence/reporting, applicable rejection/recovery and repair routing.
- Out of scope: Generic QA engine, new acceptance/evidence registry, copying the local QA Skill as runtime,
  source/test repair by QA, repeated technical review merely for new QA evidence, publication or deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Admit separate QA session | Existing owning QA-phase admission with current same-Team guard | Current technical acceptance, exact subject, QA identity/profile/grant and qualified resources | Existing QA/session facts only after admission | One separate scoped QA session, no implementation authority |
| Verify changed behavior | Existing bounded QA tools and report/disposition operations | Reviewed behavior, scenarios, actual observations and permitted evidence | Existing attributed QA findings/pass/fail/N/A facts | Safe behavioral evidence; publication eligibility still determined by its owner |
| Handle a blocker or interruption | Existing findings/revision/recovery operations | Exact affected subject, original outcome, current limits and authority | Owning blocked/recovery/revision facts | Team Lead routes repair to Engineer; no QA source edit or duplicate phase |
