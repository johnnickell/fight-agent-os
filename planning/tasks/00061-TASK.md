# Deliver the ordinary web invitation journey

## Outcome

The accepted Invite User route uses TASK-00041's versioned API to let an authoritative actor with exact `INVITE_USERS` submit one canonical email, always select managed `ROLE_USER` server-side, create the pending identity/assignment/seven-day activation/durable delivery/audit through existing orchestration, and reach a truthful success or permitted status destination without exposing invitation authority.

## Scope

- In scope: Protected ordinary invitation route and exact permission metadata; typed existing-API client service/runtime decoding; canonical email form; fixed ordinary request mode with no role input; pending/validation/conflict/throttle/success/system states; safe success navigation conditional on READ_USERS; directory/status cache invalidation; accepted responsive components/Storybook/accessibility; integrated permission/PostgreSQL/HTTP/UI/redaction tests.
- Out of scope: New invitation backend endpoint/orchestrator, elevated invitation, arbitrary role/permission choice, public registration, bulk import, administrator password, invitation recovery implementation, provider choice, delivery-receipt claim, credential/link display, and broad browser automation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invite ordinary user | Existing TASK-00041 Action/orchestrator dispatches package invitation/assignment | Resolve authoritative actor, canonical email, managed `ROLE_USER`, identity/policy state, limiter | `UserInvited`, `RoleAssignedToUser` as applicable | Pending ordinary identity, audit, seven-day grant, and package-owned recoverable delivery state reach one package-valid outcome |
| Reject invalid/conflicting invite | N/A beyond existing API request | Validate email/authority/policy/existing identity/rate | Safe existing API failure | No client claim of partial success; form offers controlled correction/retry |
| Continue after success | N/A — navigation/cache effect | Evaluate exact `READ_USERS` and registered routes | Client invalidation/navigation signal | Directory refetches; authorized reader may open status, otherwise receives safe success guidance |

## Validation and permissions

Complete route metadata and TASK-00041 server Action both require exact `INVITE_USERS`; actor is the request-scoped current principal. Do not infer access from `ROLE_SUPER_ADMIN`, client visibility, JWT/HTML, or submitted actor. Unknown/stale authority fails closed. Client checks are presentation only.

The form accepts one bounded canonical email. The request uses only TASK-00041's ordinary invitation contract and offers no role ID/name, permission list, elevated flag/mode, confirmation override, actor, user ID, password, credential, template, provider, lifetime, or return URL. Server always resolves stable managed `ROLE_USER`; client copy may explain this but cannot determine assignment authority.

Use the existing API's owned invitation composition for canonical conflicts, pending/active/disabled/deleted state, policy drift, Role references, atomic rate limits and required assignment/audit/grant/delivery behavior. Follow the [canonical contract](../../docs/engineering/STANDARDS.md#architecture): entry-owned admission, configured package bus dispatch and explicit registered-handler transaction/audit coordination, not copied policy, private handler calls or a new forwarding service. TASK-00577 owns correction of existing HTTP invitation composition; this UI TASK neither implements that source cutover nor treats today's source as the target authority. Qualify the actually consumed interface and safe typed results/failures without guessing a package release. Do not pre-query identity for availability or duplicate package policy. Success means accepted authoritative creation/registration, not provider delivery or recipient receipt.

After success, invalidate user directory. If current principal has exact `READ_USERS` and response includes approved safe target ID (2026-11-02 human correction; management alone grants no reading), offer/navigate to TASK-00060 status. Otherwise show generic safe success and Users/Dashboard destination permitted by exact route metadata. Do not broaden status data based solely on inviting authority. Suppress stale/duplicate submission results with request generations.

Recreate accepted form with email autocomplete, paste, labels/instructions, visible focus, keyboard submission, pending duplicate prevention, validation/conflict/throttle/success/system announcements, long/Unicode content, narrow/wide, themes, reduced motion, and safe recovery. Do not put email form state into persistent storage/history unless a separately approved URL representation exists; never retain credentials because none are returned.
