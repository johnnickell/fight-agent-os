# Respect retained checkouts during cleanup report protection

## Outcome

Remove the false cleanup-completion blocker caused by treating an explicitly retained checkout as a deletion
candidate merely because it contains protected Review/QA reports. Permit that retained location while preserving
protected-file integrity checks and every safeguard against actual removal of canonical reports. John approved
this bounded standalone bug on 2026-10-28. This record authorizes future repair, not implementation acceptance.

## Reproduction and evidence

At Agent OS revision `1ccba352f7bbf0bee09139719050d915cec7f2ba`,
`.pi/skills/land/scripts/cleanup.py:257` unconditionally rejects a protected-file path beneath the plan's
worktree identity. `subject_checks()` is shared by removal qualification and final verification; its containment
check does not consult the worktree disposition. Consequently, a plan explicitly retaining the canonical main
checkout can fail cleanup even when its protected reports are unchanged and no checkout removal is requested.

A safe direct Python probe on Python 3.9.6 / Darwin arm64 imported the unchanged helper and allocated a
`Cleanup` object without constructing or applying a receipt. Controlled Git identity observations and an
existing source-file path stood in for identity evidence and a protected report. For worktree dispositions
`retain`, `hold` and `remove`, the same inside-checkout path raised
`Hold("canonical report inside deletion candidate")` before `file_record()` was reached. For `retain`, the
expected behavior is to allow the location and verify the recorded integrity instead. Rejection remains correct
for an actual removal candidate. A held checkout must remain incomplete, not be converted into successful retention.

This demonstrates the shared-check defect, not an end-to-end reproduction of the original delivery incident.
No report was changed, no real cleanup receipt was applied and no Git/Docker removal or hosting command was
performed by the probe. The reported original incident left the PR and reports intact; that report is human
context, not a fresh independent audit. Planning evidence is retained outside the new checkout under canonical
`.runs/tasks/TASK-00545/runs/planning-svQuthcK/`.

## Scope

- In scope: distinguish actual worktree removal candidates from explicit retention when applying the protected
  report location safeguard; preserve protected-file integrity verification before effects and at final intake.
- Preserve finite, truthful results for retained, held, removed, failed and malformed resources. Missing or
  unknown disposition is not permission to bypass protection or manufacture cleanup completion.
- Exercise the existing helper and affected caller/final-verification path with bounded owning-tool diagnostics.
  Keep the repair small; no parallel cleanup implementation or registry.
- Out of scope: Symfony/application behavior, standalone Docker support, volume/storage lifecycle redesign,
  TASK-00542 implementation, historical report edits, new deletion authority, automatic merge or deployment.

## Validation and permissions

Existing cleanup authority is unchanged. A receipt or `retain` disposition never grants broader removal
permission. Preserve the main checkout, active/foreign resources, canonical reports and their bytes, modes,
ownership, flags, extended attributes and ACLs. A missing, unreadable or changed protected file must prevent
successful completion even when its checkout is retained. Invalid/missing disposition and unavailable
inspection fail safely. An explicitly held resource remains a hold.

Reproduce and qualify with disposable, task-owned fixtures and evidence outside any removal candidate. Do not
alter actual reports or protected runtime data. No force, sudo, ACL/mode/ownership/flag changes, shared-service
shutdown, pruning, unrelated consumer termination or relabelling unresolved holds as retention. Missing proof
produces a finite prerequisite handoff rather than a repeated destructive attempt.
