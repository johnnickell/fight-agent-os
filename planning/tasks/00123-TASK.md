# Operate full user administration in the browser

## Outcome

An authorized operator can inspect safe user detail, choose explicitly permitted lifecycle/role/session actions, confirm sensitive changes, and refetch server authority in an accessible responsive browser journey.

## Scope

- In scope: Extend the accepted Users area and typed API services; detail/lifecycle/roles/admin sessions views; exact permission-aware controls; separate confirmation for lifecycle/elevation/managed Super Admin removal/session revoke; safe reason entry; current-principal/list/detail invalidation; loading/stale/denied/conflict/failure/success states; semantic responsive/accessibility evidence.
- Out of scope: Backend endpoints, client-enforced authorization, general profile edit/email change, bulk operations, credential display, workspace/repository scope or speculative account features.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect admin detail | None | Existing safe user/session/role APIs | None | Only authoritative server state is rendered |
| Perform permitted change | Existing protected lifecycle/role/session APIs | Refetch current principal and affected Views | Existing server events only | Explicitly confirmed result converges on committed state |

## Validation and permissions

Use shared client evaluator for independent complete-route and per-action checks, but never treat hiding as authorization; every API repeats Agent OS permission/target checks. Forms validate for usability; server remains authoritative. Preserve TASK-00059/00060/00061/00062 invitation flows and TASK-00057/00058 self-service isolation. Require bounded safe confirmation/reason UI, no credentials/session tokens in DOM/storage/URLs, accessible focus/labels/status announcements and narrow/wide/theme states. Unknown/stale permission state fails closed; reload refetches after authority change.

## Acceptance criteria

- [ ] Operator sees only authorized real actions, including the distinct `ASSIGN_SUPER_ADMIN`/`REMOVE_SUPER_ADMIN` authority checks, direct-route denial and separate self/admin session meanings.
- [ ] Lifecycle, role/elevation and admin revocation require explicit accessible confirmation; no optimistic authority success.
- [ ] Success/conflict/denial invalidates and refetches exact affected user/session/principal Views without persisting authority.
- [ ] Focus/keyboard/reflow/theme/redaction plus typed client/API checks and `./bin/build` pass with actual warnings reported.

## Verification and evidence

Use real bounded API contracts with controlled client state for permission combinations, out-of-order responses, stale revisions, confirmation/cancel/error, long identity labels and storage/redaction checks. Run focused frontend/backend integration and accessibility checks, `./bin/planning-check`, `git diff --check`, `./bin/build`; record tests/stories/states, warnings and manual limits.
