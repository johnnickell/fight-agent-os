# Operate full user administration in the browser

## Outcome

An authorized operator can inspect safe user detail, choose explicitly permitted lifecycle/role/session actions, confirm sensitive changes, and refetch server authority in an accessible responsive browser journey.

## Scope

- In scope: Extend the accepted Users area and typed API services; detail/lifecycle/roles/admin sessions views; exact permission-aware controls; separate confirmation for permitted lifecycle/role/elevation/session revoke changes; safe reason entry; current-principal/list/detail invalidation; loading/stale/denied/conflict/failure/success states; semantic responsive/accessibility evidence.
- Out of scope: Backend endpoints, client-enforced authorization, general profile edit/email change, bulk operations, credential display, Workspace/Project scope or speculative account features.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect admin detail | None | Existing safe user/session/role APIs | None | Only authoritative server state is rendered |
| Perform permitted change | Existing protected lifecycle/role/session APIs | Refetch current principal and affected Views | Existing server events only | Explicitly confirmed result converges on committed state |

## Validation and permissions

Use shared client evaluator for independent complete-route and per-action checks, but never treat hiding as authorization; every API entry performs its own current permission/target admission before configured bus dispatch. This is not a requirement for duplicate Application checks; intrinsic lifecycle/last-admin/session invariants remain with their business owners under the [canonical contract](../../docs/engineering/STANDARDS.md#entry-admission-and-authorization-timing). Hide role assignment and removal controls for the signed-in user targeting themselves and for inactive (pending, disabled or deleted) targets. Otherwise show only allowed role controls, retaining the distinct `ASSIGN_SUPER_ADMIN` permission and explicit confirmation for managed Super Admin assignment; never offer managed Super Admin removal. TASK-00121's target-state and self-target checks are admission-time only, without a commit-time recheck requirement. Direct requests remain subject to authoritative server denial; hidden controls are not authorization. Forms validate for usability; server remains authoritative. Preserve TASK-00059/00060/00061/00062 invitation flows and TASK-00057/00058 self-service isolation. Require bounded safe confirmation/reason UI, no credentials/session tokens in DOM/storage/URLs, accessible focus/labels/status announcements and narrow/wide/theme states. Unknown/stale permission state fails closed; reload refetches after authority change.

## Acceptance criteria

- [ ] Operator sees only authorized real actions, including the distinct `ASSIGN_SUPER_ADMIN` check, no role assignment or removal controls for self or inactive (pending, disabled or deleted) targets, only allowed role controls otherwise, no Super Admin role-removal or account-deletion controls, no self-deletion control, direct-route denial and separate self/admin session meanings.
- [ ] Lifecycle, role/elevation and admin revocation require explicit accessible confirmation; no optimistic authority success.
- [ ] Success/conflict/denial invalidates and refetches exact affected user/session/principal Views without persisting authority.
- [ ] Focus/keyboard/reflow/theme/redaction plus typed client/API checks and `./bin/build` pass with actual warnings reported.
