# Review and apply artifact Planning operations

## Outcome

A planner explicitly invokes grill, Make Tickets, Make Tasks or Continue planning, reviews the exact structured
proposal and applies it through existing semantic commands. Stale/conflicting changes remain inspectable and any
requested AI reconciliation produces another candidate for human review, never silent acceptance.

## Scope

- In scope: Browser operation entry, current-child inspection, structured preview/correction, exact human Apply,
  atomic decomposition results, conflict comparison, explicit reconciliation and original-outcome recovery.
- Out of scope: Another proposal/transaction/queue engine, whole-document replacement, implicit reopen/restore,
  automatic follow-on work, instruction-file mutation, template publication and persistent direct-edit drafts.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Begin distinct Planning operation | Explicit exact-parent grill/decomposition/continuation intent | Current parent/children, eligibility and authority | Existing operation/input facts | Bounded preparation of additions or explicit revisions, not duplicates |
| Review and apply | Explicit complete candidate correction/discard/Create/Apply | Typed changes, base/current versions and complete member set | Owning candidate or semantic Planning facts | Reviewed atomic change or preserved rejection |
| Resolve conflict or uncertainty | Explicit bounded reconciliation only after original outcome is known | Original command outcome and base/current/rejected versions | Existing new candidate facts | New current-base proposal, requiring another human review |

## Validation and permissions

Consume TASK-00361 browser intake/target binding and TASK-00360's proposal/answer/Apply/reconciliation chain. Reuse
existing direct-edit and guarded lifecycle presentation where appropriate, never a generic status setter or a
second semantic policy. Grill proposes one EPIC; Make Tickets/Make Tasks target their exact eligible parent.
Prominent initial decomposition and deliberate Continue planning inspect existing children. Terminal/archived parents
require their separate owning reopen/restore action. Creating/applying an artifact completes only that operation.

Display a complete bounded typed candidate and affected member relationships with exact base/current revisions.
Current read/propose/create/revise rights remain distinct; acting-Agent provenance never makes the model the approver.
Any manual correction changes the reviewed candidate version. Confirm only the exact candidate under current scope;
server owners recheck permissions, revisions and all transaction participants. One stale or denied member rejects
the complete batch. Do not treat optimistic UI, model output or request dispatch as successful application.

Double submission/lost response resolves the original command identity before another Apply becomes available.
Unknown commit outcome is an explicit hold, not rejection or automatic replay. Offer reconciliation only as a new
explicit finite provider request, displaying compatible changes versus typed, relationship and narrative conflicts.
Preserve original history; a new current-base candidate still needs review. Unresolved preferences remain human work.
No automatic paid regeneration, merge, acceptance or subsequent decomposition/execution.

Enforce ADR 0003/0004 current-authority/cache fences, no-store, strict decoding and inert safe content rendering.
Unsaved preview edits are volatile with a leave warning, not durable server drafts. Late candidate/status results
cannot overwrite newer edits, change target or restore private data after logout/revocation/context replacement.

## Acceptance criteria

  and propose additions/revisions rather than duplicate children or bypass lifecycle prerequisites.
- [ ] Human review/Apply invokes existing semantics; atomic multi-record failure leaves no partially accepted
  hierarchy, and success never launches another Planning or coding operation.
- [ ] Stale proposals preserve exact history/comparison; explicitly requested reconciliation yields a new reviewed
  candidate and never silently merges, applies or chooses preferences.
- [ ] Lost acknowledgements and duplicate clicks resolve the original result; uncertain Apply disables another
  mutation without an automatic retry interceptor or hidden provider call.
- [ ] Owned client/API integration tests and actual accessible candidate-to-Apply/conflict evidence pass.
