# Match public and error headers to the compact application frame

## Outcome

Login and application-access error screens use the same compact visual scale as the Dashboard's application
header, with appropriately small appearance controls. Correct the shared public shell rather than introducing
page-specific headers. This removes the inconsistent tall header reported during local browser use.

## Scope

- In scope: Shared public/error header branding, row layout, spacing and compact System/Light/Dark appearance
  presentation; affected login, session-access failure and other existing ShellLayout consumers; responsive,
  keyboard and light/dark/system verification; relevant current documentation and production-backed stories.
- Out of scope: Login hero/form or error-content redesign; diagnosing or repairing the underlying session
  connection error; authentication, permissions, routing, recovery behavior, authenticated account-menu or
  sidebar redesign; new theme persistence, dependencies, endpoints or account operations.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Open login or a public/error screen | N/A — presentation only | Existing route/session presentation state | Existing route/render events only | Shared compact header places branding left and compact appearance controls right at desktop widths, with safe narrow-screen reflow |
| Change appearance | Existing local theme selection | Existing preference/effective-mode store | Existing preference, OS and storage notifications | System/Light/Dark choices update the same appearance-only store and preserve the explicit selected preference |
| Recover from session-access failure | Existing explicit recovery actions, unchanged | Existing session outcome, unchanged | Existing recovery signals, unchanged | Compact header does not alter retry/sign-in behavior or imply server revocation |

## Validation and permissions

Public/error presentation must not expose the authenticated User Menu, identity, private navigation or protected
content. Reuse the existing theme store and compact selector capability where appropriate; do not create a
parallel preference owner. Preserve exact System/Light/Dark names, native radio keyboard semantics, selected
state, OS following, cross-tab updates, storage-denial fallback and prepaint. Missing optional theme state must
still render a usable shell without inventing preferences.

Aim for the authenticated header's approximately 56–64 CSS-pixel desktop scale at default text size, with
branding and controls on one row. Do not impose a fixed height or shrink interactive targets below the existing
44-pixel minimum. Preserve visible focus, skip-link/main landmarks, zoom/enlarged-text reflow and accessible
appearance/effective-mode information without retaining the old tall visible stack. No authority, secret,
remote asset, CSP exception or new permission is required.

## Acceptance criteria

- [x] Login and the reported session-connection-unavailable screen show a compact shared header matching the
  Dashboard/application-frame visual scale, with brand left and compact appearance controls right on desktop.
- [x] Other existing public/error ShellLayout consumers receive the same consistent header, including safe
  render/configuration failures and screens rendered without an optional theme store.
- [x] Compact icon-supported System/Light/Dark choices retain accessible names, explicit preference selection,
  keyboard operation, visible focus and the existing theme lifecycle/persistence behavior.
- [x] Desktop, narrow (320 CSS pixels), zoom/enlarged-text and light/dark/system presentations have no clipping,
  horizontal overflow or undersized targets. No authenticated-only controls appear on public/error screens.
- [x] Login forms, session recovery actions, error copy and protected application-frame behavior remain unchanged.
- [x] A failing owning regression precedes repair; focused checks and the canonical build pass, with before/after
  visual evidence. Independent Review and applicable visual/behavioral QA remain separate acceptance stages.
