# Inspect fresh candidate preparation against the intended target

## Outcome

An authorized operator can inspect whether every reference in an exact candidate currently resolves to a valid
stored Feature and its original bound Permission ID on the intended target. The separate read-only package query
reports safe issues or a prepared observation without provisioning, repair, runtime admission or deployment.

## Scope

- In scope: Protected preparation entry through the existing operational boundary, direct package query, fresh
  authoritative adapter/error qualification, safe result presentation and real provision-to-validation evidence.
- Out of scope: Automatic provisioning/repair, stored readiness authority, runtime evaluator, UI catalog,
  Feature setting changes, deployment workflow, current-code retirement or a proof-only acceptance registry.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect candidate preparation | N/A — read-only | Package `ValidateFeaturePreparation` with exact CANDIDATE discovery and target Feature/Permission repositories | N/A — inspection emits no business success fact | Prepared observation or explicit safe issues, no mutation |
| Explain incomplete or failed preparation | N/A | All distinct references and original bound Permission IDs | N/A | Missing/broken/invalid diagnostics or unavailable/error; no inferred absence or fallback binding |
| Inspect again after provisioning or uncertainty | Separately authorized provisioning remains TASK-00291's operation | New `ValidateFeaturePreparation`, not reuse of a command return/event | N/A | Fresh observation bound to current candidate/target; no event replay or deployment effect |

## Validation and permissions

Compose `ValidateFeaturePreparationHandler` directly through the established Common query bus, with TASK-00290's
complete discovery and the same target repository composition qualified by TASK-00291. No owned query/result
aliases, package-policy copy, outer transaction or new persistence store. The query's canonical payload is empty;
do not accept caller-injected reference lists, scanner internals, default Permission, principal or arbitrary target
credentials in the package message. The protected composition owns trusted operator/candidate/target context.

Reuse TASK-00291's qualified operator and safe output boundary. Inspection needs explicit trusted scope but does
not require provisioning to have run: it can report an empty candidate, missing records or existing valid state.
Do not use the future Feature-management or testing Permission as privileged setup authority, expose a public
catalog, resolve another installation implicitly or perform request-time discovery/repair as an availability check.
Query errors must never execute a compensating command or silently retry mutations.

Request fresh complete CANDIDATE discovery, then visit every distinct name without default-page truncation.
Read authoritative Feature state by strict name and the bound Permission by its exact ID, not Permission name,
client membership or the current default. A same-name replacement Permission cannot repair an old ID binding.
OFF, PREVIEW and ON records with valid original bindings can all be prepared; the query does not evaluate the
current caller's availability or ordinary action authorization. Existing unreferenced rows are not cleanup targets.

Preserve package safe issue semantics: `missing_feature`, `broken_binding` and `invalid_definition` with validated
reference names. Mismatched Feature names/Permission IDs and malformed persisted definitions are not ordinary
absence. Qualify Feature and Permission hydration against the package's `FeatureStateException` signal for invalid
definitions; add only justified adapter/error integration, not a blanket catch that turns driver failures into
configuration issues. Storage failure, failed/incomplete/wrong-scope discovery or arbitrary exceptions remain safe
unavailable/error outcomes, never prepared or an empty list. Raw repository/driver messages, SQL, private settings
and arbitrary persisted bytes stay out of output/logging and query results.

Fresh means no stale negative lookup or ORM identity-map snapshot after provisioning, rollback, another writer or
uncertain completion. Reused processes must consult current authoritative state. A failed canonical transaction
may close its EntityManager; obtain a fresh valid invocation through owning lifecycle rules rather than attempting
to reuse it. Prepared output identifies the exact inspected candidate/source/lock, target and observation limits
without serializing secrets or inventing new fields on the package result.

The query is a read observation, not a cross-deployment fence or durable readiness certificate. Do not promise
that sequential fresh reads establish a distributed snapshot or prevent later privileged edits. Changed candidate/
target identity, unsupported coverage or known intervening changes require new inspection under the owning policy.
Before considering activation, use this fresh observation together with ordinary deployment authorization and
TICKET-00071's complete runtime checks; do not activate within the query. TICKET-00074 independently owns fresh
CURRENT discovery and actual overlapping-version retirement qualification, not substitution of this candidate result.
