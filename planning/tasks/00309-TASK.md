# Activate and enforce visible file screening across Pi workflow sessions

## Outcome

An operator enables file screening once for an approved project policy, then ordinary Pi and local `build`
parent/child sessions activate it automatically within that authority. Discovery content reaches an Agent only
after a current positive Jev decision or a validated, visible exception. The operator sees screening activity,
cache reuse, exceptions, blocks and actionable setup failures rather than unexplained ordinary reads.

This extends [TICKET-00039](../tickets/00039-TICKET.md) beyond the initial instruction-based delivery. It removes
the concrete adoption blocker in TASK-00162: hidden-by-default tooling, manually authored file policy and separate
manual allocations for every actual session ID. One implementation PR owns activation, admission and visibility;
no new Wayfinder session, general Agent scheduler or managed Workflow service is required.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Enroll or inspect screening | Trusted operator policy enrollment/revision | Effective policy, coverage, setup gaps and budget | Safe activation/unavailable observation | Protected policy and ledger changes only on enrollment; no paid status check |
| Start or resume workflow roles | Trusted local session bootstrap under enrolled policy | Actual identity, remaining/reserved budget and tool/rule coverage | Session bound/held observation | Bounded ledger allocation; no extra disclosure authority |
| Read discovery evidence | Supported read admission and bounded Jev evaluation | Current receipt or independently validated exception | Screening, admission or rejection observation | Reserved paid request when needed; selected content only after admission |
| Reuse a decision | N/A: lookup alone has no provider effect | Current scoped receipt/cache identity | Cache-use observation | No new provider spend; current source/access checks remain |
| Recover from failure or month change | Reconcile existing reservation/session; operator policy amendment when needed | Pending effects, usage, reset boundary and recovery action | Recovery/limit observation | No duplicate requests, free reset or silent unscreened fallback |

These are local Harness policy/receipt observations, not new authoritative Domain or managed Workflow events.

## Validation and permissions

Keep local file permission, provider disclosure, relevance and spending as separate checks. Jev is advisory typed
judgment; trusted deterministic code decides admission and cannot enlarge authority from repository text. Stored
policy and accounting must be protected through all supported Agent routes. Operator revocation applies to new
and resumed sessions; standing project enrollment does not expire with time. Bounded execution grants may still
expire without turning project permission into a renewal requirement. No parent can allocate authority it lacks.
Existing connection/request limits also bind.
The $10 approval authorizes planning and later enrollment of this cap, not immediate account mutation, credential
access or disclosure of all local repositories. Do not promise to cap provider charges from unrelated clients.

## Acceptance criteria

- [ ] Fresh operator setup requires no policy-file editing/session-ID hashing; a subsequent native Pi session and
  actual local `build` parent/child path activate the same approved policy without repeated permission prompts.
  Enrollment remains valid across days and monthly budget rollover without renewal; explicit revocation and
  authority expansion remain enforced. Existing finite enrollments need an explicit compatibility decision, not
  silent conversion of a deliberately bounded historical grant into standing disclosure permission.
- [ ] Before work, missing credentials/disclosure, invalid or revoked policy, exhausted limits and unavailable hooks
  show precise next actions. Tool/rule/profile coverage is inspected; missing support never appears as protected.
- [ ] $10 is shared across two concurrent parents and children, resumes and retries. Atomic reservations prevent
  overcommit; cancellation/crash/unknown usage/month rollover preserve liabilities. Budget exhaustion blocks new
  paid screens; approved bounded exceptions remain visible. Report available spend, reservations and reset time.
- [ ] A discovery read without evidence releases no contents. Current positive evidence permits only the requested
  useful range; changed source/need/policy/session, false receipts, negative/partial/failed judgments cannot admit it.
- [ ] Real governing-instruction, verified known-target and required-evidence reads succeed with per-file visible
  exceptions. Fabricated reasons and inferred batch exceptions fail. Exceptions never waive access/disclosure rules.
- [ ] Shell/search/alternate/nested/child bypass attempts are denied or make activation fail with a specific coverage
  limitation. Native CLI/TUI and the real build launcher are qualified; SDK-only evidence is insufficient.
- [ ] Operator-visible traces distinguish screening calls, internal evaluation, cache hits, exceptions and blocked/
  unavailable states. Show child progress in the ordinary build feed without leaking bodies, keys or reasoning.
- [ ] Representative parent/child investigations record context avoided, latency, measured cost and misses; unknown
  costs remain unknown. A missing cache implementation does not block the complete single-file use case.
