# Record an old-mailbox notice with each accepted request

## Outcome

Each accepted package email-change request durably records one attributable, secret-free informational notice
for the old canonical mailbox in the same transaction. A crash before immediate dispatch cannot lose that
intent, and cancellation does not erase it or redirect it to a later address.

## Scope

- In scope: Owned notice identity/state and supported cross-boundary integration; PostgreSQL persistence,
  exact change/stage uniqueness, recipient/actor binding, required audit and safe internal observation.
- Out of scope: Public request/status/cancel routes, email administration Permission policy, credential queue,
  confirmation notice, provider sending, deployed scheduler or arbitrary notification registration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Accept an owner request | Public package `RequestEmailChange` through TASK-00273's qualified boundary | Trusted actor/target, original canonical email and accepted grant/reservation generation | Package request fact and distinct owned notice fact after their commit | One request intent alongside package reservation/grant and required audit |
| Accept an administrator request | Same package operation under its qualified administration authorization | Distinct trusted requester and target, exact accepted generation | Package administrative audit and owned attributable intent | Old-mail notice still belongs to target, never the administrator's mailbox |
| Observe an interrupted accepted request | Supported original-transition observation; no automatic reissue | Exact retained change/notice state, safe restricted status | N/A for read | Truthful committed/unknown result without new notice or business mutation |

## Validation and permissions

Use only TASK-00273's qualified public seam and selected tagged/locked package. All writes share the canonical
transaction and DBAL connection under [ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md).
Notice persistence failure rolls back reservation, grant and required audit; precommit rollback leaves no notice.
No external send occurs here. Package post-commit events are optional wakeups, never recovery authority.

Generate a separate stable notice ID with its owning ID factory/UUID library. Enforce database uniqueness for
one request notice per exact accepted change/stage and immutable bindings to target, initiating actor, original
canonical address, generation/transition identity and necessary occurrence/content-version facts. Do not infer
identity from an email/time pair or recapture the recipient during dispatch. Preserve correlation needed by
TASK-00275 even if request delivery finishes first. Duplicate delivery of the same committed fact cannot create
another intent; a later legitimately accepted change has its own identity. This does not invent idempotency for
`RequestEmailChange` or permit replay after uncertain acknowledgement.

Derive notice facts from authoritative state inside the owning transaction, never caller-supplied recipient,
actor, timestamp or arbitrary payload. TICKET-00067 owns current active self-principal and cross-user Permission/
callback enforcement on every exposed path. Do not replace `UnavailableEmailChangeAdministration` here or grant
access by role name. Controlled integration tests may exercise trusted permitted/denied package callers, but must
not label an injected test authorization as production administration. No standalone enqueue route/command may
bypass the accepted owning transition.

Retain the distinction between requester and target without credentials, hashes, ciphertext, confirmation links,
raw provider responses or unnecessary personal data. Recipient data is restricted to the owning operation and
qualified dispatch/operator access. Internal status reveals only necessary safe state. No user-delete cascade,
credential cancellation/expiry or live-email refresh may silently discard or retarget an accepted notice. No
age-based purge is enabled before TASK-00277's explicit retention policy is qualified.

Post-commit publisher failure may surface after both business and notice state committed. Reconcile exact
original state where supported; lack of a success response is not rollback, delivery failure or permission for
a fresh request. Unavailable observation is unknown, not absent. Both notice and package event retain their owners.

## Acceptance criteria

- [ ] Owner and permitted administrator request contracts atomically retain exactly one stage-specific notice
  addressed to the old canonical mailbox with correct requester/target/generation provenance.
- [ ] PostgreSQL rollback and competing request/reservation tests preserve package outcomes; a failed intent
  write cannot leave an accepted unnotified change, and rejected requests leave no notice.
- [ ] Process failure immediately after commit and failed immediate event publication leave recoverable intent;
  original-fact duplication, later cancellation and later address changes neither erase nor misaddress it.
- [ ] Secret-free restricted state preserves completion correlation; unauthenticated/unauthorized or fabricated
  standalone notice creation is unavailable. No product exposure, provider send or credential queue is added.
