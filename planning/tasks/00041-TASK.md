# Expose authorized invitation issuance and safe status

## Outcome

Versioned JSend API operations let an authoritative authenticated actor issue ordinary or explicitly confirmed elevated invitations and inspect safe delivery status, with exact permission checks, bounded rate limiting, package-owned behavior, typed Views, correlated failures, and no grant or provider secret exposure.

## Scope

- In scope: Invitation request/status routes and single-use-case Actions; validated request values; authenticated actor resolution; ordinary/elevated application orchestration reusing TASK-00037/00038/package behavior; exact `INVITE_USERS`, `ASSIGN_SUPER_ADMIN`, and `MANAGE_USER_INVITATIONS` checks; explicit elevation confirmation; production rate limiter for invitation operations; JSend safe Views/error mapping; OpenAPI; PostgreSQL/permission/rate/HTTP/delivery/redaction tests.
- Out of scope: Admin React pages/forms, user listing, retry/resend/correction, public registration, custom roles, provider configuration, activation UI, bulk invitation, and client-side authorization as enforcement.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Invite ordinary user | Application orchestrator using `InvitePendingUser` and managed role assignment | Resolve current principal, canonical email, existing state, and managed `ROLE_USER` | `UserInvited`, `RoleAssignedToUser` as applicable | Pending ordinary user, audit, grant, and recoverable delivery state commit |
| Invite Super Admin | Explicit elevated orchestrator using the same package behavior | Resolve exact current permissions, confirmation, policy, and target state | Invitation/assignment events plus durable safe audit | Pending managed Super Admin exists only after authorized confirmed request |
| Inspect delivery status | N/A — read-only API | `FindInvitationDeliveryStatus` | N/A — no domain event | Safe user/status/expiry View is returned without credential/provider detail |
| Reject/throttle request | N/A until valid/authorized | Read authoritative principal and atomic limiter state | Safe failure only | No invitation/status disclosure or partial side effect occurs |

## Validation and permissions

Use [TASK-00155](00155-TASK.md)'s source-only `JsonBody` and Validation-owned fields/rules; consume checked
request values without input-only DTOs. Follow [canonical attribute ordering](../tickets/00010-TICKET.md#canonical-action-and-responder-attribute-ordering)
at each Action/Responder declaration. This first planned body consumer proves the real JSON/input-rule HTTP
matrix and no-dispatch failures; status reads do not gain undeclared query input.

Validate JSON shape/types/bounds and canonical email before dispatch. Accept only the two approved invitation modes; ordinary maps to stable managed `ROLE_USER`, elevated maps to stable managed `ROLE_SUPER_ADMIN`. Do not accept arbitrary role IDs/names/permissions. Elevated invitation requires `INVITE_USERS` and `ASSIGN_SUPER_ADMIN` plus explicit unambiguous confirmation; ordinary requires `INVITE_USERS`. Status requires `MANAGE_USER_INVITATIONS`.

Only register these protected routes after TASK-00117's JWT-by-default FQCN Action guard exists. Resolve the request-scoped authoritative principal in Agent OS Application and check exact permission names through the shared authorization boundary; the HTTP attributes are an early no-dispatch gate. Never grant based on `ROLE_SUPER_ADMIN`, client route visibility, JWT/HTML claims, or submitted actor ID. Unknown/stale/mismatched authority fails closed. Actor ID comes from authenticated context, not JSON.

Use TASK-00037's coherent invitation orchestration and package commands/handlers directly; do not recreate identity/grant/assignment rules. Responses use explicit Views and may include only approved stable user/delivery identifiers, canonical email when justified for authorized actor, lifecycle/delivery status, and expiry. Map only package-approved grant delivery lifecycle and provider-attempt outcome fields; no parallel consumer status is created and no field implies receipt not evidenced.

Apply a real atomic bounded rate limiter keyed by safe non-secret actor/action and, where justified, one-way bounded target dimension. Validate windows/limits, avoid raw email/credential keys in diagnostics, and return safe retry metadata. Rate limiting supplements permission checks and database uniqueness.

Known validation/authorization/conflict/throttle/not-found/delivery failures map through centralized JSend handling and correlation. Do not return raw grant, digest, ciphertext, activation link, provider payload/message/key, SQL, stack trace, or arbitrary package exception text. Same-origin Bearer API behavior and CORS deny-by-default remain intact.
