# Enforce one-Team Agent membership and shared admission fences

## Outcome

Supply one authoritative Agent-to-Team membership and coherent roster/reference capability, including the
supported initial creation binding and shared transaction-duration fences used by admission and membership
writers. Every product Agent has exactly one Team; membership never substitutes for Permissions or a grant.

## Scope

- In scope: Owned initial Team-binding integration, authoritative roster/association queries, membership
  constraints/history/revisions, current scope validation and shared admission/reference fences; supported
  coordination with actual package creation and owning session/start operations, with safe direct entry.
- Out of scope: Named-Agent browser creation, credential policy, transfer UI, another commitment/claim/session
  registry, Workflow selection/dispatch, generic unteamed provisioning or live cohort enablement.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Establish initial Team binding | Owned creation participant composed through a supported package/consumer boundary | Exact trusted creation intent, resulting Agent identity, current Team/Repository and management authority | Owned membership fact only when established; preserve original package issuance facts | Original product Agent and exactly one Team binding are consistent at commit, with required audit |
| Inspect current roster/scope | N/A — read-only | Exact Team membership, eligible association facts and revisions under current caller scope | N/A | Safe bounded roster/current-scope result; absence and failure remain distinct |
| Admit against current membership | Existing owner holds shared roster/reference fence in its canonical transaction | Current Agent/Team/Repository and exact revisions/epochs | Existing owning admission facts only after its commit | No stale membership admission or second claim/commitment store |
| Refuse invalid membership mutation | Guarded owning operation, including desired-state no-op | Current exact expected state and relevant references | No successful change fact for a refusal | No orphan, double membership, hidden grant or bypass through direct persistence |

## Validation and permissions

**Required evidence remains missing:** the inspected package `AgentProvisioningService` generates the Agent ID
and commits issuance inside its own transaction. It does not, merely by being called, establish Agent OS Team
membership. Qualify and document a supported initial creation/membership integration against the selected tagged/
locked package and actual retained creation intent before exposure. This is a concrete design/contract hold,
not permission to assume a callback, wrap a nested transaction, attach policy to audit persistence, patch vendor
code or repair a committed unteamed Agent in a post-commit subscriber. Any required upstream capability needs
separate owner authorization/release qualification. Do not reinterpret the hard one-Team requirement as merely
"unteamed Agents cannot run". Unknown/missing seams block creation.

Coordinate with TASK-00237's retained original lifecycle identity and TICKET-00063's future creation owner without
introducing a second credential queue or generation. Authoritative original-state reconciliation handles lost
acknowledgements; no blind reissuance, second Agent, legacy adoption/backfill or fixture-only claim of product use.
A qualified primitive must be consumable by named creation without depending on that final UI/journey.

Use distinct current managed Team/Agent-management authority as appropriate to the operation, with an explicit
reviewed complete-policy extension for any needed rights, initially `SUPER_ADMIN_ONLY` through managed Super Admin
only. Coordinate stable definitions with TICKET-00063 rather than duplicating them. Internal current-use consumers
receive only facts permitted by their trusted scoped invocation; no admin grant is silently assigned to Agents.
Team Lead cannot recruit/transfer members or expand its own authority. Reads, initial binding and no-ops validate
actual actor/target, intended Agent Repository scope, Team links and expected state; no name-based authority.

PostgreSQL enforces one-Team membership, stable references and exact replacements on the canonical connection.
Acquire cohort before membership/association/subordinate locks and hold through commit/rollback. Advance relevant
authority epochs so removal/regrant or transfer back cannot rescue old admission. All actual enabled admission,
commitment and membership writers must participate; a preflight query, cached busy boolean, polling or an event
subscriber cannot establish serialization. Reuse owning session/Workflow state, not another busy/claim registry.
Queries alone never reserve an Agent or claim a TASK. TASK-00254 owns the confirmed idle-transfer operation.

An existing Agent cannot be administratively unassigned into zero Teams, including a revoked Agent whose identity
is retained. Preserve historical session/grant Team bindings. Package Agent and permission/lifecycle state remain
package-owned; Team membership does not alter credentials, direct grants, bound template or existing scope.

## Acceptance criteria

- [ ] The supported initial binding seam is documented and qualified with actual package/consumer participants;
  successful product creation has exactly one Team at commit and rollback/uncertainty cannot expose an orphan.
- [ ] Real PostgreSQL constraints and independent competing writes reject dual membership, stale/no-op bypass,
  invalid associations and partial state/audit without duplicating Agent, Repository or commitment authority.
- [ ] Actual supported admission/reference consumers use the shared transaction-duration fence and current
  epochs; held observations or revoke/regrant cannot authorize a stale membership. Unsupported writers stay disabled.
- [ ] Safe roster/scope queries enforce caller/Repository/Team boundaries with complete deterministic paging,
  distinguishing missing from unavailable and exposing no credential, private tool or session content.
- [ ] Direct paths enforce current intent-specific rights; no unassignment creates a teamless identity, and
  creation/membership grants no Repository access, direct Permission, Workflow claim or launch authority.
