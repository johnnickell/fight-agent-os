# Keep standalone Pi skills separate from Fight workflow selection

## Outcome

A project-local operational skill runs through native Pi without requiring Fight planning artifacts or changing Fight workflow authority. Changes to the project itself still follow the project's normal engineering workflow.

## Reproduction and cause

At `3bd5e9d9fe6f208aa24fe3dcc3365de451eceeaf` with installed Pi 1.5.2, start a trusted fixture project containing `.pi/skills/job-search/SKILL.md` and invoke `/skill:job-search Demo` in a fresh session. Pi discovers and expands the local skill, but Fight reports `held / unknown-workflow-role`. The native TUI shows the warning. Pi calls the input hook before expanding skills; `harness/pi/src/workflow/access.mjs` rejects the native skill name because it is not in `skillEffects`, and `harness/pi/src/workflow-extension.ts` publishes a hold. The defect is in routing, not discovery or restored state. Project trust separately controls whether Pi loads the skill at all.

The fixture used an isolated home and scripted local model responses, with no external provider or private job data. The same CLI qualified the valid `/skill:work TASK-00604` and invalid `/skill:sync` paths. A collision between auto-discovered project and user skills warned and used the project skill in Pi 1.5.2.

## Scope and contracts

| Use case | Command or event | Expected effect |
| --- | --- | --- |
| Standalone skill | `/skill:job-search Demo`, interactive Pi input | If Pi loaded the skill and Fight does not reserve its name, let Pi expand it. Do not write a workflow checkpoint, change role, subject or checkout, or add or clear a hold. |
| Engineering skill | `/skill:work TASK-NNNNN`, interactive Pi input | Preserve workflow selection and validation. A missing required skill or invalid workflow request still gives a useful diagnostic. |
| Switching and resuming | Ordinary input, another skill, Pi reload or exact-session resume | Preserve the existing Fight selection and restore provenance. Standalone skill history grants no authority. |

Use the native Pi command inventory and Fight's workflow registry. Preserve Pi's collision diagnostic and precedence; reserved Fight names cannot opt out of workflow validation. Document the boundary and the exact nickell-jobs configuration and invocation. No new metadata, global warning mute, per-project exception, session exemption, native tool gate, or changes to nickell-jobs or the live installation.

## Acceptance and verification

- Add a failing regression before repair for the discovered standalone skill. Verify unchanged status and checkpoint count on a fresh session and during an existing selection.
- Cover valid workflow selection, missing or invalid required input, a real hold that a standalone skill cannot clear, and existing SDK/input-provenance boundaries. Skill text cannot grant exemptions or authorize unrelated code changes.
- Verify project discovery, invocation, local/global collisions, and exact-session restoration with the installed Pi runtime and isolated fixtures. Distinguish automated, real CLI fixture, and provider-backed checks.
- Run the focused harness checks and the final repository gate. Independent Review, QA, and installed rollout remain separate.

## Implementation and verification

Fight now checks Pi's loaded skill commands before selecting a workflow. Loaded non-reserved skills pass through
without writing a checkpoint or changing a hold. Reserved names retain Fight validation, and unresolved commands
cannot select a workflow. The [workflow guide](../../harness/pi/WORKFLOW.md#standalone-project-skills) documents
nickell-jobs setup and the limits of project trust.

- The focused regression failed with `unknown-workflow-role` before the repair. The full harness suite then
  passed 333 tests with no failures or skips; Node reported the existing experimental MockTimers warning.
- Installed Pi 1.5.2 passed 10 isolated TUI probes plus one exact-session resume probe. These covered native
  discovery and project/user collision precedence, expansion, checkpoint counts, Work/Review switches, invalid
  Sync, missing Build, a preserved hold, ordinary input, and reload. The installed SDK/process probes also
  passed, including input provenance, persistence failure, and stage admission. These used scripted local
  responses, not a live provider or nickell-jobs data.
- The maintainer approved a test-fixture correction in this TASK after the full gate failed in `testCookieSources`.
  A fixed synthetic correlation ID containing `bad` reproduced the false positive: the secret check matched the
  short malformed cookie marker in the unrelated response header. Replacing the marker with
  `malformed-refresh-cookie` made the focused PostgreSQL test pass (1 test, 471 assertions). The test retains
  the fixed header and checks that it is echoed, along with all existing rejection, cookie deletion, secret
  observability and non-revocation checks. No PHP product code or shared assertion changed.
- An earlier gate stopped because the scoped Linux ARM64 runtime lacked Rolldown's native binding. Restoring
  `@rolldown/binding-linux-arm64-gnu` 1.2.13 from the vendored lock with its SHA-512 verified let Vitest start.
  The focused Pi subagent engine check passed 2,550 tests with seven skipped. This verified the prepared
  worktree runtime, not a clean install. No manifest or lockfile changed.
- The normal `./bin/build` then passed from start to finish without reusing a prior result: 2,356 backend tests
  (142,382 assertions), 313 Pi Harness tests (one skipped), 2,550 Pi subagent engine tests (seven skipped),
  1,299 frontend tests, 227 Storybook tests, 473 catalog captures with no violations, and five HTTPS browser
  smoke scenarios (87 assertions). The gate logged one HTTP 500 fixture diagnostic, Node's `DEP0187`,
  Bootstrap Sass deprecations and a Storybook chunk-size warning.
- Independent review, behavioral QA and installed rollout are not part of these results.
