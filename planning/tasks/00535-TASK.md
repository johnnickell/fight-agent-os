# Launch native Pi with workspace panes already open

## Outcome

Provide a globally installed `fight-workspace` executable that starts native Pi in the caller's project or
worktree inside Herdr and opens the existing child-activity and verified-log companions automatically. The
operator gets the complete workspace from one shell command, without subsequently typing `/fight-workspace open`.
This is one independently reviewable follow-up to [TICKET-00110](../tickets/00110-TICKET.md), not a revival of the
retired RPC conversation frontend.

## Scope

- Deliver the package-owned `fight-workspace` executable and an explicit, supported user-level installation,
  update and removal flow. Qualify executable installation separately from `pi install`; do not assume Pi's
  package declaration installs a command on PATH. Reuse the trusted local-source/private-package distribution.
- Start ordinary native Pi in the caller's directory, preserving native resource discovery, editor, completion,
  themes, Markdown, dialogs, session handling and workflow authority. Open the accepted Herdr layout through
  the existing owned companion lifecycle, rather than implementing a second conversation renderer.
- Make automatic pane opening specific to this explicit launcher invocation. Ordinary `pi` remains unchanged;
  retain `/fight-workspace open` and `/fight-workspace close` for manual open, recovery and companion-only close.
- Preserve supported native startup/session options, including exact-file `--session` resume. Document supported
  forwarding and reject unsupported combinations before effects; do not forward options through shell interpolation.
- Retain explicit human log-source bindings and all existing observation/custody boundaries. Automatic opening
  is not automatic Docker-source authorization; missing bindings remain visibly unavailable until supplied.
- Document migration from `fight-terminal`, including existing copied installations and saved RPC session files.
  Keep its retirement notice or owned removal explicit; never silently overwrite another command or package.
- Exclude RPC fallback, a custom editor/session engine, automatic Herdr/integration installation, global setup
  as a planning side effect, container provisioning/restarts, inferred log bindings and managed TASK execution.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Install, update or remove the launcher | Documented explicit user-level package operations | Trusted source, actual prefix, destination ownership and PATH resolution | N/A — local package operation | Add/update/remove only owned executable/package artifacts; preserve unrelated Pi configuration and history |
| Start the complete workspace | `fight-workspace` inside Herdr | Caller checkout, compatible Pi/Herdr capabilities and actual native session | Existing native Pi and companion lifecycle; no new Workflow event | Start native Pi and open owned child/log companions without a follow-up slash command |
| Resume an existing conversation | `fight-workspace --session /absolute/actual-session.jsonl` | Actual stored session identity and current native workflow binding | Existing native resume lifecycle | Open the same conversation and companions without cloning history or selecting a workflow |
| Recover or close companions | Existing `/fight-workspace open` and `/fight-workspace close` | Current opaque ownership, native lifetime and companion health | Existing companion lifecycle | Reuse/recover or close only proven-owned companions; primary Pi and observed work remain usable |
| Handle missing prerequisites or partial startup | Explicit launch and actionable diagnostic | Herdr context, required APIs, installed resources and actual partial effects | N/A — local failure diagnostic | No automatic installation, RPC fallback, duplicate primary session or unrelated-pane cleanup |

## Validation and permissions

Launching is the operator's explicit request to open this workspace, not permission to select a role, TASK,
model/provider, enroll a project, resolve credentials or send a model turn. Use qualified supported native Pi
startup/extension mechanisms, not prompt/transcript injection, model-generated shell or a second RPC client.
Qualify currently installed APIs by capability; record tested versions as evidence, never as equality gates.

Resolve implementation assets from the trusted installed package independently of target-project files. Preserve
caller paths with spaces and argument boundaries. Detect destination ownership conflicts, missing dependencies,
missing/duplicate/filtered Harness resources and unavailable/incompatible Herdr with actionable diagnostics.
Outside Herdr, explain how to use ordinary `pi`; do not silently substitute a different workspace or install a
multiplexer. On partial failure disclose what started, avoid duplicate sessions and clean up only proven-owned
resources under the existing lifecycle contract. Do not kill an existing conversation, child or container.

Keep human-only log data outside Pi messages, tools and provider context. Preserve current explicit source
selection, fixed Docker readers, finite buffers/process lifetimes and unavailable-without-fallback behavior.
Store application runtime state under ignored `var/`, never `.runs/`. Installation/removal must preserve saved
sessions, Pi credentials/settings unrelated to this launcher, enrollment/accounting and unrelated prefix commands.
No administrator privileges, forced command replacement, automatic shell-profile edits or registry publication.
