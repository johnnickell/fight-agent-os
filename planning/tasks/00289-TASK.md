# Confirm explicitly and return to fresh login

## Outcome

A deliberate action on the safe landing submits the same new-mailbox credential, confirms exactly one current
change through the supported atomic completion-notice boundary and retires old authentication authority. The
complete self/admin-initiated browser journey returns to fresh login with the new email and existing password,
or a separately requested password reset, without treating mailbox proof as a session.

## Scope

- In scope: Protected public POST and typed client integration, explicit accessible confirmation/result/recovery,
  package/notice composition, secret-safe failures, existing cookie/auth/cache/tab invalidation, login/reset links
  and actual combined mailbox/browser/session evidence for both initiation paths.
- Out of scope: New confirmation policy or validity oracle, copied authentication service, direct User mutation,
  second confirmation secret, password requirement/form, admin override, automatic login/reset/reissue, general
  profile editing, duplicate notices/queues/providers/schedulers or broad logout of unrelated server identities.

## Use cases and contracts

|---|---|---|---|---|
| Confirm deliberately | Package `AuthenticationService::confirmEmail()` through TASK-00275's qualified boundary | Package current User/grant/reservation plus exact original-recipient binding | Package `EmailChangeConfirmed` after commit and owned completion-notice fact | One transaction consumes/promotes, advances authentication authority, revokes target sessions, audits and records completion intent; no new session |
| Handle rejection or uncertain acknowledgement | No automatic replay | Only qualified original-outcome observation where permitted; no public account lookup | No invented success/rollback event | Generic rejection or truthful unresolved result; conservative local-authority invalidation |

| Return to login/recovery | Navigation; existing login or separate reset request only on user choice | Existing registered safe destinations | No business event for navigation | New email plus unchanged password needed for login; confirmation credential grants no other action |

## Acceptance criteria

- [ ] A deliberate protected POST from the actual landing submits the same captured secret and confirms once,
  without prior login/password/admin Permission, automatic submission or session issuance.
- [ ] Qualified PostgreSQL exact-generation/reservation fencing, required-write rollback and duplicate/cancel/
  expiry/successor/account-state/refresh races preserve one package-valid outcome and no extra completion intent.
- [ ] All old target sessions fail current server checks; local authority/cookies/private data/intent retire safely,
  including uncertain acknowledgement, late responses, another local identity and bounded cross-tab fallbacks.
- [ ] Actual self/admin request paths deliver only the new-mail credential; explicit confirmation durably binds
  completion notice to the original old mailbox. Post-commit process interruption recovers that notice without
  reconfirming, creating a new identity or delaying committed session revocation.
- [ ] Actual login uses the new email and unchanged password, with safe separate reset-request navigation; old
  target authority and confirmation credentials cannot authorize fresh sessions or another purpose.
- [ ] Real accessible result/recovery states, safe errors and redaction are qualified; provider acceptance, receipt,
  confirmation and login remain distinct. Missing contract/provider/target proof remains a hold.
