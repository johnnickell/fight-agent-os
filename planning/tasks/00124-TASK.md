# Expose guarded role and permission catalogs

## Outcome

Authorized installation operators can read bounded safe role and permission catalogs without exposing a general mutation route or leaking the security policy to anonymous callers.

## Scope

- In scope: `GET /api/v1/roles`, `/roles/{roleId}`, `/permissions`, `/permissions/{permissionId}` FQCN Actions; `READ_ROLES`/`READ_PERMISSIONS`; package list/get queries; safe paginated Views, deterministic ordering, no-store JSend/OpenAPI and typed client reads.
- Out of scope: Mutations, membership edits, unrestricted policy dump, raw entities, unimplemented permission CRUD or workspace-scoped administration.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Read roles | None | `ListRoles`, `GetRoleById` | None | Safe managed/custom presentation only |
| Read permissions | None | `ListPermissions`, `GetPermissionById` | None | Safe names/tier/managed marker only as approved by policy, never grants |

## Validation and permissions

Require JWT-by-default route metadata and Agent OS Application checks of exact `SUPER_ADMIN_ONLY` `READ_ROLES`/`READ_PERMISSIONS` on every caller before query dispatch. A role name or JWT role claim confers no authority. Restrict page/order/IDs; missing or stale references fail closed, authorized not-found is safe, anonymous/forbidden cannot enumerate. Views cannot leak raw grant membership or persistence/internal data; document managed/custom mutability truthfully.

## Acceptance criteria

- [ ] Distinct read permissions gate each real Action before package query; anonymous/forbidden/stale authority produces no dispatch.
- [ ] Valid authorized bounded pages/get Views, no-store/JSend/OpenAPI and typed client mapping are safe and deterministic.
- [ ] No route can create or edit permission definitions or mutate managed roles.
- [ ] Focused permission/HTTP/PostgreSQL/pagination/redaction/client checks and `./bin/build` pass with warnings recorded.
