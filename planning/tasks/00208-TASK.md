# Transfer an active normal bugfix to a linked hotfix

## Outcome

A started normal bugfix can become an emergency **without another TASK**: the original Workflow pauses and
is reconciled, and a new, separately granted hotfix Workflow on the same TASK begins from the verified
production base only after ownership and process effects are safely fenced. Both histories remain linked and
at most one executor is active. This is one independently reviewable transfer/recovery use case.

## Scope

- From [TASK-00204](00204-TASK.md)'s currently claimed normal bugfix, accept a deliberate emergency
  escalation by an authorized human. Explain current incident evidence, work already performed, the resolved
  production base, changed scope and limits. Obtain a fresh bounded emergency confirmation/grant under
  [TASK-00206](00206-TASK.md)'s direct hotfix policy; a former Jev `urgent` priority or an old normal start
  grant is not sufficient. Do not silently retarget an Agent's branch, session, role or Workflow.
- Durably pause normal dispatch, establish quiescence of Engineer and provisioned work, reconcile outstanding
  Git/process/provider effects and exclusive claim using [TASK-00142](00142-TASK.md)'s recovery and the
  existing WF-015 start/claim authority. Atomically fence/relinquish the old Workflow's execution ownership
  and start/link one new authorized hotfix Workflow for the same TASK; an uncertain old process, claim or
  effect keeps the TASK paused with no concurrent hotfix executor. Preserve old evidence, owner, revisions,
  commits, attempts, consumed budgets and original development branch/worktree without destructive cleanup.
- Establish a fresh owned workspace from the exact verified production base; carry forward only attributable,
  requalified incident evidence or deliberately reimplemented scoped changes. Never cherry-pick unreviewed
  development work blindly, merge unfinished `develop`, include unrelated changes or elevate the Software
  Engineer session to Hotfix Engineer. The initiating human/incident owner becomes direct contact for blockers.
- A retry of the same authorized transfer returns the linked Workflow or a safe pending state; competing
  transfers and normal resumption cannot reactivate two executors. Hotfix repair/review/QA/PR follow TASK-00206
  and TASK-00207 as applicable, while post-merge follow-through remains TICKET-00054. No publication, merge,
  release or deployment occurs from the transfer itself.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Request emergency transfer | Pause normal work and record bounded human emergency confirmation | Normal Workflow/claim, incident, current authority, exact production base and active effects | Pause/confirmation and reconciliation facts | Old work stops under same TASK; no new executor before safe fencing |
| Start linked hotfix after quiescence | Existing authoritative start with explicit transfer identity and new grant | Verified old owner/quiescence, canonical owned-active transfer facts, base, grant and repository/context revisions | Linked-start/claim and dispatch facts only on successful authoritative handoff | One new hotfix Workflow on same TASK in separate workspace/session |
| Recover failed or duplicate transfer | Reuse existing Workflow inspection/recovery operations | Persisted transfer identity, current processes/effects and both Workflow histories | Safe pending/blocked/reconciled facts | No double claim, silent status edit, role escalation or discarded history |

Descriptions are semantic; use the owning durable Workflow/claim contract rather than inventing a second queue.

## Validation and permissions

Require a current authorized human emergency decision bound to the *same* TASK, verified incident scope and
production base. Current Planning/context/route/configuration, live Permissions and new effect grant must be
rechecked at the authoritative transition. Never release a claim or start a second worker merely because a
lease expired or the old process stopped reporting; prove no active operations or unknown effects and fence
stale workers. Concurrent normal continue/cancel/transfer must serialize with the linked start so only one
active executor can exist. A stopped/terminal normal Workflow must keep immutable history; a blocked transfer
remains visible and recoverable rather than discarding evidence or guessing success.

## Acceptance criteria

- [ ] A started normal bugfix requires a new exact human emergency confirmation/grant before linked hotfix
  start; the old normal grant or Jev priority alone cannot authorize transfer.
- [ ] Old process, worktree, effects and claim are quiesced/reconciled before the new hotfix Workflow obtains
  exclusive ownership of the **same TASK**. Competing start/resume/cancel and duplicate delivery preserve
  one active executor and both attributed histories.
- [ ] An uncertain old effect/process, changed authority/base or failed fence pauses the transfer with a
  concrete next action and never starts a concurrent worker or fabricates completion.
- [ ] The new repair starts in a separate owned workspace on the configured verified production base, retaining
  prior evidence provenance but not unrelated or unreviewed `develop` changes; no role switch, extra TASK,
  automatic PR merge, release or deployment occurs.

## Verification and evidence

competing requests, stale owners, retries and simulated interruption before/after fencing and dispatch; assert

isolation and uncertain-effect reconciliation with owning tools in authorized disposable scratch, not product
tests of sandbox or Git configuration. Run focused checks and `./bin/build`; record fresh counts, branch/
process identities, warnings, recovery results and separately observed limitations. Formal review and delivery
remain separate from implementation acceptance.
