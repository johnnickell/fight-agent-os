# Connect through qualified protected credential storage

## Outcome

Interactive Harness users can connect, inspect actual protected-credential readiness and disconnect safely using
qualified macOS Keychain or Linux Secret Service support, without receiving, copying or exposing an Agent key.

## Scope

- In scope: Interactive handle-only setup/selection/readiness and disconnection integration with existing
  holder/destination, fixed-sink, activation/current-use and recovery owners; exact installation/holder binding,
  supported OS-store behavior and useful secret-safe unavailable outcomes.
- Out of scope: New credential issuer, sink/queue, encryption or signing platform, raw-key-return flow, provider
  account qualification, Agent creation, general secret-read APIs and live enrollment without explicit authority.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Configure interactive protected access | Explicit setup through existing holder/lifecycle operations | Exact connection, enrolled holder/destination, original operation and supported OS store | Existing owning lifecycle facts and safe selection observations | Handle-only client configuration; no raw secret returned |
| Select and inspect readiness | Existing owner selection/current-readiness operations; inspection is read-only | Exact delivery, activation, continuing-use authority and qualified storage state | No readiness event for a read; owning facts only after actual state change | Actual ready/unavailable reason, not a cached local grant |
| Recover rotation or uncertainty | Existing original-operation recovery only | Original identity, current selected tuple and independent receipt/authority evidence | Existing confirmed lifecycle outcomes | Reconciled original credential state without new issuance |
| Disconnect safely | Explicit scoped connection/lifecycle disconnection through owning operations | Current connection, holder, active-session state, retained evidence and exact cleanup authority | Owning revocation/removal facts and safe local outcome | Stop affected use and remove only authorized owned references/material |

## Validation and permissions

Consume TASK-00241's actual qualified credential/current-use composition and TASK-00322's pinned connection.
TASK-00234 owns protected holder/destination enrollment, TASK-00236 the fixed sink and history, TASK-00243 exact
activation and TASK-00244 bounded protected signing/use. Interactive OS-store adapter support and qualification
belong through those existing owners; integrate their supported profile rather than build a parallel secret store
or require those primitives to depend on this completed client journey. Missing platform support remains unavailable.

Interactive credential storage uses macOS Keychain or a compatible Linux Secret Service with no plaintext fallback.
The fixed protected-sink lifecycle supersedes historical one-time raw-key-return wording. Store/choose only private
handles at the connection boundary; no browser/Pi-child secret, copy/paste key, `.env` value, repository file or
model-visible signing capability. Protected delivery/signing stays within qualified holders. Provider credentials
retain their separate Pi/provider owner and are never repurposed as Agent authentication.

Revalidate actual installation/origin, holder/destination, current credential tuple, delivery, activation, live
Permissions and relevant human/Team/Repository/session/host authority through their owners. A saved handle,
receipt, successful keyring lookup or signature alone is not usable readiness. Missing/locked/unavailable OS store,
revoked or rotated credentials, unsupported host and authority-store outage fail closed. Cache may explain prior
observations but cannot authorize use. No unrelated keyring search or secret-content diagnostic is permitted.

Setup, enrollment, rotation/revocation and removal are explicit scoped human/operator actions under existing
intent-specific authority; inspection performs no repair or enrollment. Preserve original operation keys and
outcomes across interruption, rotation and lost acknowledgements. External store effects stay outside business
transactions; a lost response cannot cause replacement issuance or deletion of a successor.

Disconnection distinguishes local configuration removal, revocation, origin/cache cleanup and retained history.
Coordinate current-use/session holds and exact owning cleanup rather than erase active/uncertain recovery material,
shared holders, unrelated connections or secret-free audit evidence. TICKET-00087 now maps TASK-00338's exact
origin-removal/cache-cleanup composition, using TASK-00337's cache fences and existing credential lifecycle owners.
Consume that capability rather than duplicate it; if required cleanup is unavailable or retention-held, report
pending cleanup without pretending disconnection fully completed.
Removing a connection never transfers its authority to another installation or silently starts a new session.

  readiness through the existing credential owners, with no raw-key or plaintext fallback path.
- [ ] Missing/locked/substituted storage, wrong installation/holder, stale material and changed authority deny
  use despite saved handles or old receipts; issued/delivered/activated/usable states remain distinct.
- [ ] Rotation/revocation and interrupted original operations reconcile exact current state without duplicate
  issuance, obsolete reactivation, key leakage or implicit Agent/provider enrollment.

- [ ] Real supported-host behavior, exact source/runtime and safe diagnostics are recorded; unsupported or
  untested platform combinations cannot be advertised as qualified managed access.
