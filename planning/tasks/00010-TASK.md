# Prove and enforce application ownership boundaries

## Outcome

A small representative composition path demonstrates direct Fight Access Control public-contract use with injected capabilities and CQRS composition, while deterministic architecture checks enforce the accepted ownership and dependency directions. Feature-specific endpoints, schemas, and product behavior remain absent.

## Scope

- In scope: Select the minimum non-user-facing package-owned behavior needed to prove direct public-type composition; wire its handler/capabilities through the existing composition/CQRS boundary; add focused tests; configure Deptrac or an equivalent deterministic architecture check for currently enforceable ownership/layer rules; prove positive structure and seeded invalid dependencies; document rules deferred to later representative HTTP/persistence/delivery code.
- Out of scope: Authentication, invitation, session, or authorization journeys; public endpoints and representations; database schemas/repositories; external delivery; React; event sourcing; package-type renaming wrappers; speculative application contexts; complete style/static-analysis/coverage gate expansion.

## Validation and permissions

Choose the smallest Fight Access Control public command/query/handler contract that can prove composition without implementing a feature journey or persistence schema. Use package commands, queries, Views, events, policies, and capability interfaces directly. Any owned `App\Application` type must document a genuine cross-boundary/application-specific responsibility; omit it when package behavior alone suffices. Capabilities are constructor-injected; business code must not access the service container.

Architecture checks must enforce currently applicable rules: Domain cannot depend on Application, Adapter, framework, persistence, or transport; Application cannot depend on Adapter/framework implementations; Adapter may depend inward and implement capabilities; configuration/composition is the explicit outer wiring boundary; owned source must not copy Fight namespaces or create generic alias wrappers. Tool configuration and justified exceptions must be narrow, readable, and deterministic.

Do not manufacture placeholder Actions, Responders, repositories, or contexts merely to make a rule testable. Action–Domain–Responder, transport safety, transaction/effect behavior, and authorization checks that lack representative code must be listed honestly for TICKET-00009 through TICKET-00011 and final quality-gate closure. Architecture tooling may begin here; TICKET-00013 owns complete gate integration and final policy.

No user-facing permission model applies because no endpoint is introduced. Repository source, composition, tests, and focused architecture tooling are authorized; product behavior, schemas, external effects, and upstream changes are not.

- [ ] Deterministic architecture checks enforce the currently applicable Domain/Application/Adapter, composition-root, and package-ownership rules from the accepted ADR.
- [ ] Positive production examples pass and seeded invalid dependencies or equivalent isolated fixtures fail with clear diagnostics.

- [ ] Every accepted ADR rule not yet enforceable is documented with reason and a downstream owner.
- [ ] Focused composition tests, architecture checks, and `./bin/build` pass with tool versions, counts, warnings, and exceptions recorded.
