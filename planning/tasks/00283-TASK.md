# Protect email-change issuance material

## Outcome

Supply secure email-change credential generation and purpose-separated authenticated encryption through the
supported package capabilities. This small prerequisite lets accepted request capture persist recoverable material
without enabling an unfinished request path, provider or new credential store.

## Scope

- In scope: Actual `EmailChangeCredentialGenerator` and `EmailChangeDeliveryCipher` integration, external key
  validation, protected material lifetime and compatibility with existing invitation/reset encryption.
- Out of scope: Request HTTP/UI or administration callback enablement, provider sending, new grant policy,
  arbitrary token console, key-ring platform, automatic rotation/destruction or historical data backfill.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Supply issuance material | Package `RequestEmailChange` in its owning qualified transaction | Current package generation/reservation facts | Owning request fact only after commit | Unpredictable purpose credential and authenticated encrypted material persisted with package state |
| Materialize a committed delivery | Package `DeliverEmailChange` later consumes the cipher | Exact package-owned encrypted material under a committed live claim | Owning delivery outcome, not a new crypto event | Plaintext exists only for the bounded provider invocation |
| Reject unavailable protection | N/A — capability validation/failure | Required protected key/configuration | N/A | Issuance/delivery fail safely; key-free expiry and status stay available |

## Validation and permissions

Inspect and record the selected tagged/source/locked public contracts. Implement the package generator using a
cryptographically secure random source with at least 256 bits of entropy and bounded transport-safe encoding;
`EmailChangeCredential::fromString()` validates nonempty input but does not generate secure randomness. Use owning
factories for identities. No fixture string, email-derived value or reusable session/reset credential is issuance.

Extend the demonstrated `SodiumCredentialDeliveryCipher` boundary or a justified compatible adapter, not package
policy. The inspected adapter implements invitation/reset only and allowlists those purpose labels. Add the exact
email purpose while retaining existing ciphertext compatibility, independent random nonces, authenticated decryption,
purpose-separated derivation and safe failures. Wrong key, wrong purpose, corruption and malformed material must
not yield plaintext, synthetic replacement material or a fallback key. Key material stays external to source/logs
and separate from signing/CSRF keys. Preserve the original human-delivery key while any affected purpose has
outstanding recoverable work; do not infer safe retirement from one email table or elapsed grant lifetime.

Prove package request rollback removes reservation/grant/material together on the canonical shared PostgreSQL
transaction. TASK-00274 separately supplies required atomic notice/self-audit coordination through TASK-00273's
qualified seam. Controlled package integration fixtures here establish crypto/persistence contracts only, not
permission to expose notice-free requests. Register no public issuance/decryption route and do not replace the
unavailable administration callback or trust caller-supplied actor IDs.

Neither safe queries, logs, exceptions, audit, serialization, diagnostics nor retained test records may contain
raw credentials, ciphertext, keys, token-bearing URLs or plaintext bodies. Decryption belongs only to the supported
claim/invoke boundary; fixture round-trip probes are not production access paths. Minimize plaintext lifetime and
state PHP's inability to guarantee zeroization. Do not make `expire` or status resolve a cipher/provider.

## Acceptance criteria

- [ ] Real package issuance receives secure generation and purpose-separated authenticated material; existing
  invitation/reset ciphertext and behavior remain compatible.
- [ ] Guarded PostgreSQL proves exact round trip and rollback, including failed encryption/persistence without
  partial reservation/grant state; wrong-purpose/key/tampered material fails without leakage or reissuance.
- [ ] Protected configuration rejects missing/invalid key material without weakening independent expiry/status;
  no request route, raw-token console, callback grant or second credential queue is enabled.

## Verification and evidence

Test owned generator/cipher behavior and important package/persistence contracts, not the randomness library's
internals or configuration text. Validate composition and any migrations directly with owning tools. Use synthetic
secrets without recording them; record exact source/lock, compatibility, redaction and key-retention limits. Run
focused checks, planning/whitespace and `./bin/build`; surface warnings and distinguish fixtures from actual delivery.
