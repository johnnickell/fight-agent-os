# Visually configure Workflow stages, Agent assignments and tool policies

## Outcome

An authorized administrator can understand and configure an execution policy as a draggable graph of registered
stages, supported transitions, Agent assignments and MCP tool access. It edits the same versioned configuration
used by the existing application, and explains how that policy will govern autonomous runs.

## Scope

- Separate policy configuration page reached from the existing authenticated Dashboard; retain the compact
  sessions table and runtime detail design. Select Repository and exact policy revision before editing.
- Nodes for registered execution stages; typed connections for supported success, failure, retry and handoff
  transitions. Node details select eligible Agent/role/template references, available tool capability IDs and
  policy bounds. Display an explainable projection of existing owners, not a new runtime object hierarchy.
- Drag/reposition, connect/disconnect, zoom/pan and accessible selection; a keyboard/list-form equivalent can
  perform every meaningful edit. Persist layout separately so moving a node cannot change execution semantics.
- Read-only inspection of a run's pinned policy, with current stage and outcomes drawn from authoritative history.
  Distinguish that view from editing a draft for future runs; unavailable facts are not invented.
- Draft/validate/diff/publish/restore flow through existing semantic configuration operations with expected
  revisions and audit. Show affected stages, Agent/tool changes, authority expansion and future-run impact.
- No new Workflow engine, scheduler, policy registry, Agent provisioning or duplicate tool catalog. No arbitrary
  JavaScript, shell commands, MCP endpoint URLs or unrestricted expression/code nodes. No deployment or permission
  grant follows from drawing an edge. Do not select a canvas library until actual delivery constraints are known.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect a policy or pinned run | None | Exact authorized configuration, stage/tool/Agent catalogs, effective access and history | None | An attributable graph with honest gaps; no execution |
| Arrange and edit a draft | Scoped layout save and existing typed draft/revision operations; exact supplier mapping pending | Valid node/edge choices, eligibility and current expected revision | Only owning persisted draft/layout facts | Non-authoritative layout or validated draft; no live grant change |
| Validate and compare | None for read-only validation/preview | Owning graph/reference validation and revision impact | None | Explain unsupported edges, missing capabilities, authority expansion and stale inputs |
| Publish or restore configuration | Existing owner-authorized revision/publication or append-only restore operation | Current actor scope, dependencies, diff and affected future runs | Owning committed configuration facts | One new immutable policy revision; existing runs retain their snapshot |

## Ownership and permissions

TICKET-00025/00052 own Repository configuration and route catalogs. TICKET-00032/00083 own stage effects and
execution authority; TASK-00139's standing policy derives exact grants without per-run approval. TICKET-00061
owns current tool authorization, TICKET-00062/00063/00064 own Teams/Agents and eligibility, and TICKET-00075/00076
own templates. TICKET-00088 resolves immutable snapshots; TICKET-00096 supplies run history. This UI cannot add
policy semantics those owners do not expose, or promote requested tool access into granted Permission.

Require separate current viewing and management authority. Use typed IDs, registered capabilities, expected
revisions and server-side eligibility for every mutation. Reject missing/cross-scope/retired references, unsupported
transitions, unreachable required stages, invalid inputs and unbounded retry cycles. Preserve valid bounded repair
loops and independent Review/QA constraints. Never let a graph bypass required stages, standing policy limits or
publication authority. Tool/Agent details omit credentials and hidden metadata. Revoke access in cached and live
views. Stale/denied writes restore authoritative state and preserve recoverable draft input where permitted.

Publication is an administrator configuration action. Permitted runs then start and proceed automatically under
standing policy; do not insert a human consent node into every run. Running grants are never silently rewritten
when their source policy changes. Revocation and any separately supported migration use their owning operations.

## Acceptance criteria

- [ ] Load a real persisted policy and show its exact stages, transitions, Agent assignments and effective tool access.
- [ ] Pointer and keyboard/list-form paths produce equivalent validated configuration; layout-only edits change no semantics.
- [ ] Draft, validate, compare, publish and restore preserve attributable immutable revisions and reject stale/cross-scope requests.
- [ ] Unsupported links, missing/retired tools or Agents, forbidden stage bypass and unbounded loops produce actionable errors.
- [ ] Current versus historical/pinned views are explicit; editing policy never launches work or mutates an existing grant.
- [ ] A representative permitted Workflow consumes the published revision through the existing Start owner without per-run confirmation.
- [ ] Responsive, accessibility, denial, loading, empty, stale, partial and recovery behavior is verified against real authorized APIs.
- [ ] Owned behavior checks, fresh browser evidence and the canonical build pass; inspection/configuration tests do not become tests of a graph library.

## Required decisions before implementation

The draggable representation is approved; a general graph execution language is not. Map the exact early owners
for stage topology/transition constraints, standing-policy draft/validation/publication and aggregate-safe revision
fencing. Existing route configuration alone does not establish these contracts. Identify the minimal supported
initial stage set and map tool/Agent/effective-access queries from existing owners. Resolve whether required early
supplier TASKs need bounded amendments; do not reverse-block TASK-00139 or create a parallel engine to fill gaps.
Until then this record remains `needs-info`, unranked. Prototype/library selection and any implementation split
belong inside this named product outcome after those contracts are resolved.
