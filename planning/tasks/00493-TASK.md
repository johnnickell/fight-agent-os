# Visually configure Workflow stages, Agent assignments and tool policies

## Outcome

An authorized administrator can inspect a fixed Workflow stage sequence and configure its per-stage instructions,
Agent assignments, MCP tool access and bounded policy through a draggable visual representation. It edits the same
versioned configuration consumed by execution owners and explains how that policy governs autonomous runs.
Building new Workflows from scratch, custom stages and dynamic topology are deferred to v2.

## Scope

- Separate policy configuration page reached from the existing authenticated Dashboard; retain the compact
  sessions table and runtime detail design. Select Repository and exact policy revision before editing.
- Nodes show the fixed registered stage sequence and its owner-defined success, failure, retry and handoff
  transitions. Node details edit bounded stage instructions, eligible Agent/role/template references, requested
  tool capability IDs and permitted policy values. Display an explainable projection of existing owners, not a
  new runtime object hierarchy. V1 cannot add/remove/reorder execution stages or connect arbitrary edges.
- Drag/reposition, zoom/pan and accessible selection; a keyboard/list-form equivalent can perform every meaningful
  edit. Persist layout separately so moving a node cannot change execution order or semantics. Configure only
  registered retry/repair behavior within the fixed sequence; do not expose dynamic graph construction.
- Read-only inspection of a run's pinned policy, with current stage and outcomes drawn from authoritative history.
  Distinguish that view from editing a draft for future runs; unavailable facts are not invented.
- Draft/validate/diff/publish/restore flow through existing semantic configuration operations with expected
  revisions and audit. Show affected stages, Agent/tool changes, authority expansion and future-run impact.
- No new Workflow engine, scheduler, policy registry, Agent provisioning or duplicate tool catalog. No arbitrary
  JavaScript, shell commands, MCP endpoint URLs or unrestricted expression/code nodes. No deployment or permission
  grant follows from drawing an edge. Do not select a canvas library until actual delivery constraints are known.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect a policy or pinned run | None | Exact authorized configuration, stage/tool/Agent catalogs, effective access and history | None | An attributable graph with honest gaps; no execution |
| Arrange and edit a draft | Scoped layout save and existing typed draft/revision operations; exact supplier mapping pending | Valid node/edge choices, eligibility and current expected revision | Only owning persisted draft/layout facts | Non-authoritative layout or validated draft; no live grant change |
| Validate and compare | None for read-only validation/preview | Owning graph/reference validation and revision impact | None | Explain unsupported edges, missing capabilities, authority expansion and stale inputs |
| Publish or restore configuration | Existing owner-authorized revision/publication or append-only restore operation | Current actor scope, dependencies, diff and affected future runs | Owning committed configuration facts | One new immutable policy revision; existing runs retain their snapshot |

## Ownership and permissions

TICKET-00025/00052 own Repository configuration and route catalogs. TICKET-00032/00083 own stage effects and
execution authority; TASK-00139's standing policy derives exact grants without per-run approval. TICKET-00061
owns current tool authorization, TICKET-00062/00063/00064 own Teams/Agents and eligibility, and TICKET-00075/00076
own templates. TICKET-00088 resolves immutable snapshots; TICKET-00096 supplies run history. This UI cannot add
policy semantics those owners do not expose, or promote requested tool access into granted Permission.

Require separate current viewing and management authority. Use typed IDs, registered capabilities, expected
revisions and server-side eligibility for every mutation. Reject missing/cross-scope/retired references, unsupported
transitions, unreachable required stages, invalid inputs and unbounded retry cycles. Preserve valid bounded repair
loops and independent Review/QA constraints. Never let a graph bypass required stages, standing policy limits or
publication authority. Tool/Agent details omit credentials and hidden metadata. Revoke access in cached and live
views. Stale/denied writes restore authoritative state and preserve recoverable draft input where permitted.

Publication is an administrator configuration action. Permitted runs then start and proceed automatically under
standing policy; do not insert a human consent node into every run. Running grants are never silently rewritten
when their source policy changes. V1 resumes use the pinned policy and stage instructions; adopting a different
revision requires a new run through normal eligibility, claim and admission checks, not an in-place migration.
Current revocations and emergency stops still apply at protected-operation boundaries. Already-admitted effects
retain their owning cancellation/reconciliation limits; publication alone is neither revocation nor recall.

- [ ] Pointer and keyboard/list-form paths produce equivalent validated configuration; layout-only edits change no semantics.
- [ ] Draft, validate, compare, publish and restore preserve attributable immutable revisions and reject stale/cross-scope requests.
- [ ] Fixed stage topology cannot be changed by semantic edits or layout movement; unsupported links, missing/retired references, forbidden bypass and unbounded loops produce actionable errors.
- [ ] Editable stage instructions are versioned and pinned with the policy; text cannot grant tools, weaken gates or erase reviewer independence.
- [ ] Effective policy explains installation constraints/defaults, permitted Repository overrides and run-specific narrowing with per-value provenance; Team-level policy inheritance is unavailable in v1.
- [ ] Classified transient retries and finding-driven repair loops enforce distinct finite counters and overall resource budgets; exhaustion or uncertainty holds without gate skipping or blind replay.
- [ ] Current versus historical/pinned views are explicit; future publication changes no active run, resume retains the pinned revision, and current revocation/stop controls still prevent new protected effects.
- [ ] A representative permitted Workflow consumes the published revision through the existing Start owner without per-run confirmation.
- [ ] Responsive, accessibility, denial, loading, empty, stale, partial and recovery behavior is verified against real authorized APIs.
- [ ] Owned behavior checks, fresh browser evidence and the canonical build pass; inspection/configuration tests do not become tests of a graph library.

## Approved v1 policy decisions

John approved the following in the isolated planning follow-up. These narrow the earlier visual-editor scope;
they do not approve implementation, new permissions or runtime enablement. The later approved supplier allocation
is recorded separately below.

- **Fixed sequence:** configure the existing registered sequence, not a general graph execution language.
  V2 is the intended destination for creating Workflows from scratch with custom stages, transitions and stage
  instructions. No v2 implementation or decomposition is authorized by this deferral.
- **Stage instructions:** v1 supports editable versioned instructions pinned with the run policy. They supplement
  required checks and role guidance; they cannot override structured authority, required gates or independence.
- **Retries and repairs:** only classified transient failures may retry automatically. Blocking Review/QA findings
  return to implementation and repeat fresh Review and affected acceptance/QA through their owners. Apply finite
  retry/repair limits within overall run budgets; exhaustion or uncertain outcomes pause for intervention. No
  silent gate skip, reset of consumed allowance or retry of an unreconciled effect is permitted.
- **Inheritance:** installation policy supplies mandatory constraints and defaults. Repository policy overrides
  only explicitly configurable defaults and cannot weaken mandatory constraints. Run-specific choices may only
  narrow authority. Show each effective value and its source; Team-level policy inheritance is deferred to v2,
  without changing current Team membership, eligibility or delegation requirements.
- **Active runs:** policy and stage instructions remain pinned. New published revisions affect future runs only;
  current revocation and emergency-stop authority still apply at protected-operation boundaries. Resume uses the
  pinned revision; changing it requires a new run. In-place policy migration is deferred to v2. A new run cannot
  bypass an existing claim, unresolved effects or the original run's accounting/recovery obligations.

### Publication and admission contract to allocate

The owning contracts must define the following behavior for this editor; implementation must make it work and
test it. This is not a separate preliminary qualification phase:

1. **Draft and preview:** exact Repository, installation baseline, fixed sequence/schema, stage instructions,
   role/resource revisions and bounded requested tool/policy values; return normalized effective values,
   per-value provenance, typed validation failures and old/new impact. Preview writes no grant or Workflow.
   Layout storage remains non-authoritative. Durable versus volatile draft storage and its exact owner remain
   an engineering allocation, not an implied new generic draft service.
2. **Publish or restore:** current separate view/manage authority, original operation identity, exact reviewed
   candidate and expected baseline/Repository/reference generations. Revalidate mandatory gates, instructions,
   eligibility and limits through actual shared writer participants; append one immutable policy revision,
   current selection and required audit atomically. Restore revalidates old values and appends a fresh revision.
   Stale/conflicting inputs refuse; a lost acknowledgement resolves the original result before another write.
3. **Start:** authenticate the User/delegated controller and compose fresh eligibility, authority and current
   policy under TASK-00139's existing admission transaction. Bind the exact effective policy/instruction and
   role references with claim, bounded grant, reservations and dispatch intent. Publication versus Start must
   serialize to a coherent old-or-new revision; no mixed generations or extra per-run approval.
4. **Continue:** use the retained run policy/instructions and original accounting, while current authority,
   real bound-input integrity, runtime owner and stop/revocation fences govern every protected admission.
   Reconcile unknown effects before replay; do not promise recall of already-admitted work or qualify host
   enforcement with a database lock. Exact host/session participants remain held under their existing owners.
