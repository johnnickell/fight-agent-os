# Record resource creation and drive cleanup from one lifecycle receipt

## Outcome

Make approved local Work/Build resource creation, stage reuse and retirement one executable lifecycle.
Owning commands capture creation evidence as effects happen; stages carry the same machine-readable receipt;
Land generates and executes the qualified cleanup plan without reconstructing ownership from Markdown.
This removes the repeated delivery blocker where publication succeeds but cleanup never reaches preview/apply.

execution priority in the current conversation. Board changes are limited to generated placement; do not add
an authored Board narrative, delivery queue or another approval ceremony.

## Scope

- Extend existing owning local runtime/setup wrappers, exact-subject Work/Build handoff and Land cleanup
  operation. No parallel cleaner, global resource registry, background scheduler or second Workflow engine.
- Persist private allocation intent before effects, binding TASK, origin, checkout/source revision, exact
  configuration/env locators and digests, operation identity, intended created/reused resources, data
  classification, discard authority, preservation requirements and finite resource/time budgets. Refuse new
  allocation when intent cannot be durably recorded.
- Capture actual returned identities and immutable observations during creation: containers, networks, named
  and image-declared anonymous volumes with creating-container mounts, image roots/references, cache/builder
  relationships, host processes/sessions and generated private/runtime paths. Names or before/after deltas
  alone do not establish ownership. Event watchers may corroborate but cannot be the sole capture mechanism.
- Capture creator/mount proof before temporary containers disappear. If creation succeeds but recording fails,
  stop dependent allocation and reconcile that exact pending operation from original evidence; retain unknowns.
  Do not promise an atomic Docker/filesystem transaction or exactly-once effects.
- Keep one versioned machine-readable receipt in the existing canonical TASK run outside removal candidates.
  Record created, reused, replaced/superseded, removed, absent, held and intentionally retained states with
  dependencies and history. Keep original attempts immutable. Runtime observation binding belongs under
  ignored `var/`; application runtime must not depend on `.runs/`. Never put secret values in public output.
- Carry and revalidate that binding through Work, independent Review, QA, repairs and resume. Every stage that
  creates or replaces a resource contributes to the same history. Build validates evidence completeness before
  advancement; stage changes alone must not allocate competing stacks or require manual Markdown-to-JSON work.
- Mechanically derive a cleanup candidate plan from the recorded lifecycle using the existing helper schema;
  bind actual publication/acceptance/worker evidence at the appropriate stage. Recorded ownership is not removal
  permission: freshly qualify identity, service/host consumers, authority, protected state and preservation.
- Give task-owned observers a recorded, finite supervised lifecycle and safe completion outside the removal
  candidate. Keep their exact process identity and dependencies; do not kill arbitrary, reused or foreign PIDs,
  active coordinators or unrelated sessions to clear a hold.
- Preserve artifacts before retirement, execute dependency-ordered eligible effects, continue independent
  eligible resources despite unrelated holds, verify actual absence and protected-state preservation, and
  resume only unfinished effects. Aggregate cleanup with unresolved required effects remains incomplete.
- Account explicitly for shared images/cache and their accepted owner/consumer/retention or recoverability
  policy; use existing supported storage capabilities rather than classifying all used artifacts as owned.
  Unsupported exact retirement remains a resource-specific hold, never an invented empty inventory.
- Out of scope: automatic deletion of legacy unknown resources, retrospective intent, blanket prune/force,
  permission/protection changes, shared service shutdown, remote-ref deletion, automatic publication/merge,
  global installation, managed PHP provisioning, hostile-code isolation and unrelated product features.
