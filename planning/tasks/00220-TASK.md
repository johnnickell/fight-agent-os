# Verify library distribution against project policy

## Outcome

The same release Workflow can establish the project-required registry projection or installed-consumer proof
for the exact certified library version, distinguishing it from local signing, remote tag and hosted
publication. If no registry/consumer proof is required, the project policy records a qualified N/A while
all other required publication facts remain independently verified. Missing, stale or inaccessible results
leave the release incomplete with a bounded next action.

## Scope

- Resolve [TASK-00212](00212-TASK.md)'s qualified library runbook to determine *whether* a registry,
  distribution host or consumer installation check applies, its approved package name/source identity,
  expected version, certified commit and tag, necessary asset/host publication state and observation policy.
  Consume [TASK-00218](00218-TASK.md)'s independently verified remote tag and
  [TASK-00219](00219-TASK.md)'s required hosted-release fact or explicit policy N/A. Do not treat hosted
  draft/publication as proof of registry visibility or a version string as proof of the correct source.
- Query the target's qualified registry/provider read-only for an exact normalized version and source
  reference matching the certified commit (and dist identity when required). For Packagist, use the
  project's approved metadata endpoint and parse its actual representation, including declared minified
  metadata before comparing inherited fields. Distinguish confirmed missing, mismatched, outdated,
  inaccessible and unknown responses; record observation time/URL/identity. Apply a bounded policy-defined
  recheck window, not open-ended background polling. No implicit registry update/webhook or credential change.
- When the project requires *installed-consumer* proof in addition to registry visibility, qualify a
  public install in an authorized isolated environment against the registry version, verifying resolved
  version/source/dist reference and required behavior. A local path install, previously certified archive,
  CLI exit alone or copied metadata cannot stand in for consumer evidence. Preserve failed/incomplete
  outcomes and clean only owned resources.
- Record separate attributed registry/consumer observed result or explicit policy-bound N/A on the one
  release Workflow. Before handing off to [TASK-00221](00221-TASK.md), recheck all **project-required**
  publication facts from the owning stage rather than assuming they were met by an earlier process result.
  Out of scope: introducing a universal Packagist dependency, provider update effect, changing a published
  release, GitFlow follow-through, release `done` or application deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect registry projection | Existing scoped read/record observation operation, no provider mutation | Current policy, actual remote tag and published release where required, registry version and source/dist reference | Attributed observed/blocked distribution fact after validation | Verified matching projection or concrete missing/stale/unknown next action |
| Prove consumer install if required | Scoped qualified observation in owned disposable workspace | Public registry resolution and installed package/behavior | Consumer qualification result or incomplete fact | Separate public-consumer evidence; no published-version substitution |
| Record policy-based skip | Same-Workflow N/A disposition bound to policy version | Current qualified project requirements and existing publication facts | Explicit optional-check N/A, not release-publication event | No registry/consumer claim when policy omits it |

Queries to external registries are observations, not authorized publishing or health claims by themselves.

## Validation and permissions

Only the current permitted Workflow actor can request/record scoped observations; resolve the exact
Repository/package identity and current runbook/claim/context/subject revisions. Read-only provider adapters
must use qualified endpoints/credentials and redact private content; inability to query is **unknown**, not
absent. Reject mismatched repository/reference, incomplete metadata, stale cache, non-public consumer source,
stale certification or policy drift. A registry version may appear before GitHub release publication; this
does not waive a separately required host stage. If the provider requires an update effect, stop for an
expressly supported runbook and [TASK-00216](00216-TASK.md) grant rather than using observation authority
as a write grant. Keep check evidence/time and limits durable; do not infer TASK `done` from read results.

## Acceptance criteria

- [ ] A project-required registry version is checked against exact version and source (plus required dist),
  not a mere HTTP success, version string, remote tag or GitHub release. Missing/mismatch/unavailable states
  remain distinguishable with bounded retry/recovery.
- [ ] Required public consumer proof resolves and exercises the published registry package; local path or
  archived package evidence is not substituted. Inapplicable consumer checks have policy-bound N/A.
- [ ] Projects without a configured registry/consumer requirement do not invent Packagist or a provider;
  their N/A still verifies remaining required publication facts separately.
- [ ] No registry update, publication, branch mutation or release `done` is performed by a read-only check.

## Verification and evidence

Test owned package identity/version/reference resolution, complete/minified metadata interpretation where
supported, disabled/missing optional checks, required consumer proof, stale/mismatch/unknown responses,
bounded rechecks, grant/subject drift and safe evidence persistence with focused Application/API and important
provider-contract behavior. Qualify real project registry/Composer consumer installation using owning tools
in authorized disposable state, with actual observed references and timestamps; fixtures are not live
projection evidence. No product tests of Packagist API, Composer CLI, configuration/runbook prose, scripts,
migrations or build infrastructure. Run focused checks and `./bin/build`; retain fresh counts, warnings,
limits and remaining project-specific evidence. Review and PR delivery are separate.
