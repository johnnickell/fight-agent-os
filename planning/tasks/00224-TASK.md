# Verify production health and coordinate bounded recovery

## Outcome

For the **same** application release Workflow, Team Lead can inspect independently observed provider target
identity and project-required health before continuing. Failed, partial, stale or unavailable health remains
incomplete and offers a specific recovery choice. Rollback or forward repair is a **separate**, durable,
permissioned effect only where the exact human plan already names it or a new bounded human approval is
given; a rolled-back candidate never becomes a successfully deployed release.

## Scope

- Consume [TASK-00223](00223-TASK.md)'s durable rollout/effect identity and current provider-observed
  artifact/digest, [TASK-00215](00215-TASK.md)'s certified candidate, and [TASK-00222](00222-TASK.md)'s
  qualified environment/runbook. Inspect the actual selected provider's environment and deployment revision
  and run the project-owned required health observations (target coverage, service checks, timing and
  dependencies as specified). Pin result to the observed deployed identity and observation time, not only
  a successful HTTP status, prior green check or controller's acknowledgement. Team Lead coordinates
  monitoring and reports limits; it cannot accept an unknown health result as green.
- Persist separate verified deployment identity, health pass/fail/partial/unknown, blocked and recovery facts
  with evidence/provenance in the existing Workflow. A healthy old version, wrong environment, stale check,
  missing replica/target, partial rollout or unavailable telemetry cannot support candidate completion.
  Permit bounded reinspection against authoritative/provider state; after a timeout, inspect state before
  any new effect. Never lose the original intent/observations or create a new release TASK to recover.
- Present policy-qualified rollback or forward options including target revision/artifact, risks, health
  expectations, limits and existing [TASK-00216](00216-TASK.md) grant coverage. If a rollback/forward
  effect is explicitly named and still within limits, require current *direct* Release Manager Permission,
  revalidate subject/env and record a **new distinct durable effect identity** before invoking the approved
  project adapter after commit; verify the actual resulting target and health separately. If not covered,
  stop for specific human approval, never infer consent from the original rollout grant or automate
  rollback simply because a check failed. Changed target or risk exception also requires renewed human
  decision. Preserve audit of a failed original candidate; observed rollback cannot make it `done`.
- Out of scope: inventing a universal health/rollback executor, logging provider secrets, library release,
  branch follow-through or final lifecycle closeout ([TASK-00225](00225-TASK.md)).

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Observe exact deployed health | Bounded same-Workflow verification operation | Actual environment, deployed artifact/revision, required health and current checks | Distinct verified, failed, partial or unknown health fact | No production mutation; only evidence for exact candidate |
| Preview recovery | N/A — read-only scoped plan | Current rollout/health, project options, direct Permissions and exact-effect grant | N/A — preview grants nothing | Human sees permitted next action and exceptions without implicit rollback |
| Perform authorized recovery | Existing same-Workflow scoped Release Manager effect operation | Recheck bound rollback/forward grant or new human approval, provider state and prior intents | Separate durable recovery intent and independently observed result | Only expressly approved project-specific effect; no automatic success |
| Resume uncertain recovery | Existing reconcile/inspect operation | Fresh provider identity/health, pending effect IDs and authority | Attributed blocked/recovery fact when verified | No repeated production effect on unknown outcome |

Observation and provider mutation remain separate; these names do not grant an Agent a production key.

## Validation and permissions

Revalidate same-TASK claim, certified subject/target and runbook revision, observation freshness,
actor/role direct Permissions, human grant, effect identity and remaining time/cost/attempt limits for
**every** new effect. A Team Lead or monitor may request bounded health observation but cannot deploy,
rollback or approve an exception. Store only sanitized results, stable provider references and digests;
credentials remain brokered outside Agent sessions. Health success is not a blanket claim of no defects;
required project criteria must actually pass for the exact target. Deny unsupported recovery, changed
artifact/env, unknown provider state, absent approval or unavailable qualified health tools with a concrete
next action. Do not attempt provider mutations inside the database transaction.

## Acceptance criteria

- [ ] Current provider observations identify the certified candidate on the named environment and all
  project-required health conditions before marking the deployment healthy; queued, acknowledged, partial,
  failed, wrong-version or unknown outcomes remain incomplete.
- [ ] Timed-out/failed rollout or missing telemetry is recovered by reconciling the **same** effect, without
  duplicate production calls, lost history or inferred success.
- [ ] Rollback/forward requires an explicitly enumerated current grant (or new human approval) plus live
  Release Manager Permission, its own durable effect identity and verified postconditions; unapproved or
  changed-scope recovery pauses instead of acting automatically.
- [ ] A successful rollback of a failed candidate does not satisfy that candidate's release `done` guard;
  health and rollout evidence are separately visible from ordinary PR landing and publication.

## Verification and evidence

Test owned provider-identity/health matching, old-version health, missing replicas, stale observations,
partial/failure/unknown classification, changed environment, scoped rollback denial/approval, duplicate
requests and lost outcomes using focused Domain/Application, API, PostgreSQL and qualified adapter behavior.
Qualify actual project health/rollback observations through owning tools in authorized safe/disposable
environments; fixtures are not production health evidence. Do not run a destructive rollback to test the
test suite, product-test provider scripts/configuration, or claim green from inherited receipts. Run focused
checks and `./bin/build`, report fresh counts, warnings and limits; keep formal review/delivery separate.
