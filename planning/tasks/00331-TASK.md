# Retire resources and select retained revisions

## Outcome

Authorized users explicitly retire managed/custom Skills, prompts, personas and themes or select retained revisions
for future use, preserving exact history and pinned consumers under competing publication and reconciliation.

## Scope

- In scope: Type-specific protected retirement and retained-revision selection over existing authorities, expected
  state, current eligibility/history inspection, shared reference fences and atomic attributable lifecycle evidence.
- Out of scope: Purge/tombstone policy implementation, deletion of source or historical bytes, package rollback,
  Agent-template lifecycle, automatic Agent updates, session switching, cascading cleanup and a generic editor.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Retire a resource | Explicit type-specific retirement with expected current lifecycle/selection | Current identity, generation, eligibility and exact authorized references | Committed retirement fact | Future eligibility changes; historical bytes and pinned references remain |
| Select retained revision | Explicit expected-state retained-revision selection | Exact historical revision, current access/reference validity and selection | Committed selection fact | Future selection points to retained bytes; history is not rewritten |
| Inspect history or uncertainty | N/A — authorized read | Retained content, lifecycle, provenance and original operation outcome | N/A | Safe exact history and actionable conflict/unresolved state |

## Validation and permissions

Reuse each resource owner's current scoped management/read authority, immutable identity, content validation and
reference contracts. Preserve distinct type semantics and managed/custom ownership. Retirement and retained-selection
are explicit bounded intents against actual logical/revision IDs, not alias matches or absent source entries.
Require expected lifecycle and independently advancing selection generations; changed-away-and-back state cannot
validate stale approval. Selecting history grants no authority or provider disclosure.

Validate the retained revision exists, belongs to the exact resource/type/scope and satisfies the owning current
selection/reference rules. Preserve history even if referenced capabilities later become unavailable; authorized
historical reading is distinct from eligibility for a new selection. Deny invalid future selections rather than
rewriting references or substituting another resource. Retirement must never erase bytes needed by snapshots,
Agents or audit; current live access still governs disclosure despite a pinned revision.

Qualify all actual managed reconciliation, custom publication, retirement and selection participants under the
same reference/selection contract. Serialize conflicting operations through real PostgreSQL constraints and shared
fences, with consistent lock order. A stale reconciler cannot silently undo an explicit retirement/rollback using
an old expected generation. Explain later explicit reconciliation against newly inspected state as a separate
intent, not a permanently pinned source policy. No resource disappears merely because its source bundle is absent.

Commit lifecycle/selection and required Harness audit in the owning shared ADR 0002 transaction. No external cache,
filesystem, provider or session effects belong inside it. Events follow commit; unknown outcomes remain original-
operation uncertainty, not presumed rollback or permission to repeat. Reads do not repair or reactivate resources.
No generic event-sourced registry or operation ledger is introduced.

Expose precise lifecycle/reference fences for future profile/template publication, but leave complete candidate,
current Permission/Repository and final consumer-transaction qualification with TASK-00300 and other mutation owners.
Those completed consumers cannot reverse-block this lifecycle. Retained content needs bounded current authorization;
ordinary logs/events contain only safe metadata, not private bodies or credentials. No purge is authorized here.

- [ ] Historical bytes remain exact and authorized-readable after retirement/rollback; pinned consumers do not

- [ ] Invalid references, stale intent/pointer return, denied access and unknown original outcomes fail safely

- [ ] No source-absence cleanup, purge, package rollback, template propagation or active-session mutation occurs;
  consumer publication still requires its separate complete qualification.
