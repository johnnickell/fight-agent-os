# Attribute console and worker failures to the correct operation

## Outcome

Operators can attribute console, recovery-worker and accepted managed-runtime diagnostics to the actual operation/
job/attempt, without stale context, unsafe console rendering or altered recovery semantics. This is approved slice D
of [TICKET-00111](../tickets/00111-TICKET.md); missing managed-runtime bindings remain a delivery gate.

## Scope

- In scope: Single reporting ownership at actual console/worker/process boundaries; native useful diagnostics on
  the private diagnostic path; root/job/attempt context lifetimes and reset; integration with existing console,
  credential-recovery/cleanup and accepted managed-run boundaries; safe output/exit/partial-outcome compatibility.
- Out of scope: A new worker/scheduler/executor, process retries, runtime enrollment, managed-output capture/queues,
  evidence receipt ownership, transcripts, prompts, hidden reasoning, raw argument/environment dumps or new authority.

Consume [WF-037](../wayfinder/tickets/WF-037-define-redacted-diagnostics-and-shared-http-adoption.md#diagnostic-contract).
Bind actual service/process/operation and available Workflow/TASK/run/attempt/actor relationships at their owning
boundaries, preserving unknown values and distinct attempts rather than manufacturing lineage. Use TASK-00453's
nested restoration inside the job; reset contextual processor/handler state at every job/root exit, including errors,
contention, cancellation and interrupted outcomes where the process remains able to report.

Retain current trusted-console and credential-recovery entry contracts, safe stdout/stderr presentation, exit codes,
partial/uncertain state and package-owned retry/claim/audit semantics. Ordinary console rendering must not gain
verbose traces or private input merely because operational diagnostics are richer. Respect existing producer-side
credential restrictions: do not revive discarded input-bearing exception chains, serialize arguments or expose
provider material. Distinguish the configured private diagnostic output from user-facing protocol/presentation.

Select one reporting owner per actual catch/fatal boundary; use available original failure once rather than add
competing global handlers. Bus lifecycle failures and enclosing operation outcomes are distinct observations. An
already handled contention/rejection can be observed without being rethrown as an unexpected fatal error. Report
known lifecycle/retry/attempt facts only; successful dispatch is not a delivery, commit, Workflow or evidence receipt.
Do not rerun a job/check/provider operation to repair missing logs.

Failures before normal logger/container availability need bounded safe degraded/unknown reporting through the
qualified independent path; they cannot trigger a second container, recursive logging or raw PHP/Symfony fallback.
Shared fatal/resource failures can prevent reports. Disclose that boundary rather than promise complete fatal capture.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Explain an existing console operation | Existing trusted console command unchanged | Known operation/actor and original outcome | Private boundary observations only | Useful diagnostics with unchanged safe output, exit and partial-result semantics |
| Process consecutive recovery jobs | Existing package recovery/cleanup dispatch only | Current delivery/job/attempt identity and actual known outcome | Lifecycle observations, not new claim/retry/audit authority | Correct attribution with reset between jobs and preserved package recovery behavior |
| Observe managed execution boundary | Existing authorized execution operation only | Actual execution-owned Workflow/TASK/run/process/attempt context | Diagnostic observations, not Workflow transition or check receipt | Available lineage binds to the real run; unavailable lineage remains explicit |
| Handle diagnostic/startup failure | TASK-00451's guard/independent path; no business replay | Actual known stage and uncertainty | Bounded degraded/unknown signal | Safe original outcome where possible; no stale-context or duplicate-reporter cascade |

## Validation and permissions

No new execution, log-read, credential or installation permission is introduced. Existing internal CLI authority,
current execution grants, protected check targets and credential/audit requirements remain mandatory. Context IDs
are references, not grants. Use trusted owner values and validate supplied context rather than accepting arbitrary
process arguments or client metadata as identity.

Follow [ADR 0001](../adr/0001-application-ownership-and-orchestration.md) and
[ADR 0002](../adr/0002-postgresql-consistency-and-durable-effects.md). Keep orchestration with existing owners and
runtime/console integration in Adapter/composition. Logging must not create a transaction, provider attempt, business
retry or another evidence store. Raw diagnostics remain separate from sanitized Activity and required check Artifacts.

## Acceptance criteria

- [ ] Existing console/recovery/cleanup operations have one actual boundary reporter and useful attributable private
  diagnostics without changed safe output, exit, partial/uncertain state or package-owned retry/audit semantics.
- [ ] Sequential jobs, nested calls, retries and exceptions restore/reset context correctly; a later job never
  inherits another actor/run/attempt, and missing identity remains unknown.
- [ ] Concrete accepted managed-runtime bindings supply actual available run/process/attempt metadata. Controlled
  producer fixtures alone cannot qualify this path or substitute for its unimplemented owner.
- [ ] Diagnostic/startup failure neither masks the original outcome nor triggers a second dispatch/container, raw
  unsafe rendering or recursive status; preboot/fatal reporting limits are explicit.
- [ ] Input-bearing parser errors, secret arguments/environment, credentials/provider data and transcript material
  are not newly emitted. Native diagnostics do not weaken existing producer-side protections.
- [ ] Real console/recovery and managed-boundary evidence, owned behavior tests and full `./bin/build` pass, with
  inherited evidence, unqualified paths and shared-fault limits explicitly distinguished.

## Verification and evidence

Test the owned adapters/context behavior using current trusted console operations and actual credential-recovery
orchestration, with safe controlled providers and guarded PostgreSQL where state/recovery claims require it. Exercise
sequential jobs, contention, failure after commit, retry identity, interrupted/uncertain output and logger/status
faults. Inspect original authoritative state to prove logging added no retry or changed package lifecycle.

Qualify the execution-owner context binding through its real approved run/check path once available; do not invent
a generic worker or launch another proof-only TASK. Directly validate process/console mechanisms with owning tools,
not product tests of wrappers, config or infrastructure. Run focused repository checks and `./bin/build`; preserve
warnings, original operation identities, actual source coverage and preboot/fatal limitations. Confirmed bugs require
a reproducing regression before repair. Runtime effects need their own bounded execution authority.
