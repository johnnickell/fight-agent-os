# Administer another user's email change from user detail

## Outcome

An authorized administrator can request, inspect and explicitly cancel an active target's email change from the
existing Users detail journey. Reuse qualified request/status/cancel primitives with distinct current cross-user
authority, target-specific confirmation and attributable audit; only the new mailbox can confirm the address.

## Scope

- In scope: Guarded cross-user API/typed client integration, existing user-detail actions/forms/status,
  explicit target/intent confirmation, current authority and actor-versus-target evidence for actual operations.
- Out of scope: New Users directory/detail owner, profile editor, administrator confirmation override,
  credential inspection, public worker/retry controls, old-mail undo or independent request/cancel implementation.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect target change | N/A | TASK-00279's safe projection under TASK-00278 cross-user policy, alongside existing user detail | N/A | Current scoped status without grant/provider/audit internals |
| Request for active target | Package `RequestEmailChange` through qualified shared request/notice coordination | Current protected Permission, active target, explicit intended address and actual readiness | Package request/admin audit and durable old-mail request notice | Same one-hour new-mailbox proof requirement, no direct canonical-email edit |
| Cancel target's reviewed change | Package `CancelEmailChange` through TASK-00281's qualified exact-intent boundary | Current cross-user authority and exact target/change context | Package cancellation/admin audit on actual committed transition | Only the reviewed target generation becomes unusable, without deleting accepted notices |

## Validation and permissions

Use TASK-00278's stable managed `SUPER_ADMIN_ONLY` email-change Permission and qualified package callback plus
current entry guards. Actor comes from a trusted current active principal; target is separately validated and
must be an active permitted installation User. `ROLE_SUPER_ADMIN`, `READ_USERS`, invitation rights, a client
projection or access to user detail alone cannot authorize these operations. Existing detail-route permissions
remain independent; do not relax them to show email controls or grant directory access through a self-service path.

Reuse TASK-00280's qualified request composition, TASK-00279's coherent bounded status and TASK-00281's exact
cancellation behavior. Cross-user HTTP Actions and non-HTTP callers independently apply current policy; never
forward an arbitrary actor ID or add a target override to the self endpoint. One Action invokes one package/owned
use case, not transaction logic or copied package lifecycle policy. Unsupported input or state denies safely.

Explicit confirmation shows the target and intended destination or exact pending change without credentials.
Recheck current authority and target/context at dispatch; stale selection, removed Permission, disabled target,
reservation conflict or successor generation requires safe refetch/new consent, not an operation on newer state.
Request never silently replaces pending work and cancellation never acts on a different generation. Keep current
admin authentication distinct from the target's future confirmation/session invalidation.

The original target mailbox receives TASK-00274/00275's informational notices; the new target mailbox alone
receives the purpose-bound confirmation credential under TICKET-00068. The administrator receives neither that
credential nor authority to confirm, impersonate, reset a password or set active email directly. Preserve actual
initiating actor, target and later proof attribution rather than claiming the administrator performed confirmation.
No old-mail approval/cancel/undo link or second secret is introduced.

Keep status/acknowledgement semantics from the shared owners: issued is not delivered or confirmed, post-commit
failure is not rollback and unknown result is not permission for automatic replay. Qualified request readiness
is required; cancellation remains usable when provider sending is unavailable. Provider uncertainty never erases
accepted notice or promotes the address. Do not introduce another intent queue, grant history or mailer.

Extend TASK-00123's existing Users workspace with independent route/loader/action guards and the sole `/me`
projection. Scope volatile form/status state to target and auth generations; switching target, permission loss,
logout or delayed responses cannot leak or act on the prior target. No PII/business drafts in storage, URLs,
history or telemetry. Preserve explicit confirmation, safe validation, focus/keyboard/announcements, narrow/wide
and light/dark states. Use safe non-enumerating errors, not private package/provider details.
