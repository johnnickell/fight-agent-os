# Finish library branch follow-through and release closeout

## Outcome

After independently verified project-required library publication and distribution, the **same** release
Workflow resolves any configured GitFlow merge-back or maintenance-line forward-port under the original
bounded plan or a newly approved specific scope. A release TASK becomes `done` only through
[TASK-00211](00211-TASK.md)'s guarded lifecycle when every required publication, check and branch
follow-through fact is current and verified; trunk/no-target projects receive an explicit policy-bound
no-action. Conflicts, protected branches and uncertain observations preserve a recoverable incomplete release.

## Scope

- Consume [TASK-00218](00218-TASK.md)'s verified remote tag, [TASK-00219](00219-TASK.md)'s hosted release
  or qualified N/A, [TASK-00220](00220-TASK.md)'s required registry/consumer evidence or policy-bound N/A,
  [TASK-00215](00215-TASK.md)'s exact certified commit and [TASK-00212](00212-TASK.md)'s current branching
  strategy. A GitFlow/current-line project verifies the actual released source/production ref is included in
  the configured development target; a maintenance line follows the **project's explicit** forward-port
  policy rather than merging older content wholesale. Trunk-based projects with no separate development
  branch do not receive a GitFlow action. Inspect remote/provider state; no PR publication or tag alone
  proves source inclusion.
- Where current policy requires a branch effect, use only the bounded explicit follow-through effect from
  [TASK-00216](00216-TASK.md), direct Release Manager Permissions and current source/target OIDs and branch
  protection. Record a durable effect intent under the existing Workflow before a qualified project-specific
  PR/merge operation; never force-push, retarget signed tags, merge unrelated unfinished changes or silently
  accept/merge a protected PR. Preserve later development work, run required integration/review/checks and
  pause at any separate human PR approval/merge step. A grant authorizing a permitted preparatory PR is not
  permission to merge it. Observe trusted resulting target inclusion and checks before recording completion.
- Reconcile duplicate requests, lost responses, advanced refs and partial effects against authoritative
  provider/remote state **before** retry. Keep the same release TASK/Workflow and claim while applicable;
  never silently reacquire a released claim or start a new Workflow for follow-through. Unsupported,
  conflicted, unverified or revoked paths remain blocked with the exact next human/qualification action.
- At closeout revalidate the project-required current checks, exact candidate/tag object and source commit,
  approved host/release/registry/consumer evidence, configured branch inclusion or explicit N/A, direct
  completion authority and live Workflow/Planning revisions. Invoke the release-specific completion guard
  from TASK-00211, not a second status authority; only verified requirements permit `done`. Planning
  implementation acceptance, ordinary PR landing, a local signed tag or a queued effect cannot stand in
  for release completion. Do not alter application-release completion logic, archive automatically or
  claim publication of the implementation PR as a library release.
