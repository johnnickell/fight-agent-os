# Preserve applicability across mechanical reconciliation

## Outcome

Let accepted work survive proven mechanical base reconciliation without unnecessary model review, human approval
or revision-cycle consumption, while material changes and uncertain interactions still block publication.

## Scope

- In scope: Exact old/new subject comparison, constrained mechanical reconciliation, append-only provenance
  bridges, fresh verification and semantic PHP validation of Review/QA applicability for downstream consumers.
- Out of scope: Implementation repair, requirement/authority changes disguised as documentation, rewriting
  finalized reports, waiving checks, force-push and automatic acceptance of arbitrary rebases or identical patches.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Reconcile accepted work | Authorized bounded mechanical reconciliation under existing Workflow | Original acceptance, current base/branch publication state and exact changes | Durable reconciliation intent/outcome | Owned mechanical Git changes only, or explicit hold |
| Validate applicability | Semantic bridge validation against expected revisions | Old/new base/head, conflict manifest, effective diff, dependencies and fresh checks | Accepted bridge or denied/unresolved applicability fact | Review/QA provenance carried forward only where proved |
| Inspect provenance | N/A — read-only | Original Review/QA, bridge chain, verification and current applicability | N/A | Honest original-versus-current subject presentation |

## Validation and permissions

Follow [landing provenance rules](../../docs/engineering/LANDING.md#reconcile-an-advancing-base), specialized by
EPIC-00008's database-authoritative Planning boundary. Bind Workflow/TASK revision, original finalized Review/QA,
old and new full base/head OIDs, complete status/tree/Artifact manifests, resolved paths, effective implementation
differences, dependency interactions and required fresh verification. Original immutable reports never claim to
have reviewed the new OIDs. A model assertion or patch equality alone does not establish absence of interactions.

Permit only authorized mechanical reconciliation that preserves independently authored changes and accepted
behavior. Regenerate applicable derived views from their authoritative source; never write frozen Planning
Markdown after database cutover. Requirements, Permissions, instructions, behavioral contracts, tests and
configuration are substantive regardless of filename. Preserve accepted implementation on material/ambiguous
results, invalidate applicability as required and route to independent Review or the exact human decision rather
than have Release Manager repair it. Persisted blocking findings alone authorize the Engineer revision loop.

Inspect remote state first. Rebase only unpublished owned history when allowed; published history must not be
rewritten or force-pushed. Validate current authority, clean/owned worktree, qualified tools, exact intent and
expected revisions before effects. Commit intent before Git effects and reconcile uncertain original outcomes
before retry. No stash, discard, blanket conflict-side choice or unrelated cleanup is authorized.

Required fresh focused/full checks and affected behavioral evidence establish bridge applicability. Preserve
unchanged QA only with explicit behavior/source applicability; fresh supporting QA artifacts do not invalidate
technical acceptance by themselves. Mechanical validation consumes no revision cycle and does not add another
approval ceremony. Changed OIDs alone neither erase original acceptance nor prove current delivery readiness.

## Acceptance criteria

- [ ] A verified mechanical reconciliation retains immutable Review/QA provenance and produces a complete
  old/new subject bridge accepted by PHP before downstream applicability is carried forward.
- [ ] Dependency interaction, material/ambiguous changes, changed requirements and failed or stale checks hold
  publication; identical patches and file suffixes cannot bypass this decision.
- [ ] Original acceptance remains historical truth; no report rewrite, extra model review, new human ceremony
  or consumed revision cycle is required solely for a proven mechanical conflict/OID change.
- [ ] Published history is never force-rewritten and independently authored changes survive reconciliation.
- [ ] Authority/subject races and interruption retain the original operation and safe recoverable state.

## Verification and evidence

Test owned bridge eligibility, subject chaining, evidence/currentness and fail-closed disposition with PostgreSQL
concurrency as needed. Qualify actual mechanical Git reconciliation and verification using owned disposable
repositories and meaningful existing changes, not Git-internals or quality-tool detection tests. Record exact
before/after source, bridge, check and QA applicability evidence; run focused checks and `./bin/build`. Preserve
warnings and distinguish inherited acceptance from fresh reconciliation verification.
