# Manage revisioned user Harness profiles

## Outcome

Users manage their own non-secret Harness preferences through the configured connection, retaining exact
immutable revisions and authorized resource/model selections for reproducible future sessions.

## Scope

- In scope: User-owned database Harness profile create/revise/inspect/select operations, bounded preference and
  exact-reference validation, immutable history/current selection, expected-revision protection and terminal/API
  delivery with safe Views.
- Out of scope: Machine-local connection storage, Agent templates/role resolution, resource/model catalogs,
  credential storage, granting Permissions, active-session mutation and a general profile-editor browser product.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Create or revise own profile | Intent-specific profile create/revise with expected state | Owned current/history, authorized scope and exact available choices | Committed profile creation/revision facts | New immutable preference revision and selected current state |
| Select a retained revision | Explicit expected-state profile selection | Exact owned revision and current reference eligibility | Committed selection fact | Future default changes, never historical bytes or an active session |
| Inspect preferences and choices | N/A — authorized bounded reads | Profile history, resource/model references, availability and safe differences | N/A | Exact non-secret configuration or explicit missing/denied/stale reasons |

## Validation and permissions

Profiles contain only bounded non-secret resource selections, themes, aliases, prompts/persona selections, model
defaults and update preferences under TICKET-00085. Use type-specific resource owners and exact identity/revision/
scope references from TICKET-00086 and qualified allowed-model facts from TICKET-00089. Do not copy resources,
create another catalog, silently substitute missing/retired choices or turn user preferences into Agent templates.
User Harness profiles, role templates and authenticated Agents remain distinct identities and authorities.

Authorize every read/write for the current user, expected installation and applicable Workspace/registered
Repository scope. TASK-00078 supplies stable Repository references; ordinary login, a supplied owner ID or profile
name cannot grant cross-user access. Bound field sizes and reference collections; reject stale expected state,
missing/cross-scope references, unsupported releases/models and unresolved invalid selections. Safe Views omit
raw credentials, protected handles, private provider configuration, unrelated preferences and persistence models.

Use current state plus immutable revisions, not event sourcing by default. PostgreSQL uniqueness, reference and
selection fencing must make accepted revisions coherent under resource/model/profile changes. Commit profile state,
selection and required audit atomically on the shared ADR 0002 connection; external resolution occurs outside the
transaction with exact references revalidated at commit. Changed-away-and-back selections cannot validate an old
approval. Duplicate/uncertain writes resolve their original outcome rather than append accidental revisions.

Selecting a profile or changing update preferences grants no Permission, provider disclosure, automatic package
update or session restart. Historical bytes remain available to authorized consumers. New selections apply to
future resolution; active changes require TICKET-00088's explicit linked continuation, later surfaced by
TASK-00325. Missing continuation support never mutates an active snapshot. This profile capability supplies
snapshot inputs independently of completed session, template, Explorer or browser Planning journeys.

## Acceptance criteria

- [ ] Actual terminal/API create/revise/inspect/select operates on owned non-secret profiles with immutable
  history, exact current-selection provenance and no credential or cross-user disclosure.
- [ ] Scope, missing/unsupported resource/model choices, stale edits and invalid references reject without
  silent substitution or partial profiles advertised as usable.
- [ ] Controlled PostgreSQL competing edits/reference changes and rollback preserve one coherent exact revision;
  unknown outcomes reconcile original state and cannot duplicate writes.
- [ ] Profile changes and retained-revision selection preserve historical/active snapshots and grant no Agent
  authority, automatic update or provider call.
- [ ] Snapshot consumers can inspect exact profile facts through the owning capability without depending on
  final switching, named Agent creation or database Planning cutover.
