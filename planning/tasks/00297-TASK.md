# Manage the testing audience and rollout state for AI template proposals

## Outcome

An authorized administrator can inspect the provisioned `ai-template-proposals` Feature, select its existing
testing Permission and change OFF/PREVIEW/ON through one complete browser/API management path. This removes the
rollout-management blocker for [TICKET-00077](../tickets/00077-TICKET.md)'s real AI-assisted template authoring,
not a demonstration of Feature infrastructure. This TASK normally owns one PR; inspection, authorization,
mutation and UI are parts of that outcome rather than separate delivery TASKs.

## Scope

- In scope: Managed `MANAGE_FEATURES` Permission extension; current management authorization at supported entries;
  existing catalog list integration; protected detail/revision and Permission choices; package-backed binding and
  status edits; confirmation, safe repair/readiness composition, browser invalidation and affected evidence.
- Out of scope: Manual-create UI/API, dummy Feature or product route, automatic provisioning/grants, generic
  Permission CRUD, Feature renaming, deletion/cleanup, new deployment platform/readiness registry, Agent delegation,
  AI provider calls or publication, and a separate proof-only TASK. Real declarations/OFF provisioning retain
  TASK-00290/00291 ownership; actual AI admission and provider evidence remain TICKET-00077's work.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Establish management authority | Existing protected `ReconcileManagedPolicy` operation for the complete accepted policy | `PreviewManagedPolicy`, current original Permission and actor authority | Package reconciliation facts only | Stable managed `MANAGE_FEATURES` definition and initial managed Super Admin membership; no testing grants |
| Inspect rollout settings | N/A — read-only | Existing complete catalog, protected `GetFeatureById`, bounded `ListPermissions` choices | N/A — reads publish no business fact | Safe immutable name/ID, status, original binding/repair marker and positive edit revision |
| Select or repair testing audience | Authorized `SetFeaturePermission` with stable IDs and current positive expected revision | Fresh target, selected Permission, applicable trusted readiness | Package `FeaturePermissionChanged` only after a real committed change | Revision-checked binding/reference replacement; no Permission creation or assignment |
| Change rollout state | Authorized `SetFeatureStatus` with current positive expected revision and required confirmation | Fresh target and applicable trusted preparation/runtime-coverage observations | Package `FeatureStatusChanged` only after a real committed change | One status transition; no deployment, proposal request or retroactive cancellation |
| Resolve conflict or uncertainty | No automatic retry or compensating command | Fresh protected detail and catalog under current authority | Local invalidation only; no invented durable outcome fact | Retire stale browser data/intent and obtain new confirmation when needed |

## Validation and permissions

### Current management authority

Extend TASK-00036's one managed policy with `MANAGE_FEATURES`, tier `ADMIN_SAFE`, initially assigned only to
managed `ROLE_SUPER_ADMIN`. Preserve the initial policy and every accepted extension; reconcile the whole policy,
not a one-Permission replacement. Generate the stable definition ID through the owning ID factory or UUID library
at implementation and version it; do not generate new identities at runtime. Include actual application references.
No Role name, testing Permission, Feature setting or tier eligibility authorizes management by itself. Initial
assignment does not grant custom Roles or Agents this right; later delegation needs its separately accepted scope.

Use current authoritative human Permission and target/intent checks in shared Application policy before every
supported HTTP, direct-bus, CLI or worker entry; unsupported entry modes fail closed rather than inventing new
adapters for coverage. Trust only established actor/operation context, not a User ID or readiness claim from the
payload. Reuse the request's qualified principal where appropriate, without borrowing credentials or treating a
previous page as current authority. The inspected `InstallationAuthority::assertInstallationPermission()` requires
`SUPER_ADMIN_ONLY`; it cannot enforce this `ADMIN_SAFE` extension unchanged. Do not weaken that existing protected
boundary, change this Permission's approved tier or add a role-name bypass to make it fit.

Keep ordinary JWT/current-session, target, same-origin/CSRF, validation and safe failure contracts at the actual
HTTP boundary. Feature management must remain reachable to authorized managers when `ai-template-proposals` is
OFF or unavailable; do not guard its repair controls with that Feature's own availability.

### Reads and exact mutations

Reuse TASK-00295's sole complete `GET /api/v1/features` for listing, not a competing broad admin catalog. Protected
package detail supplies the positive revision and repair information excluded from the ordinary catalog. Map safe
Views explicitly; exclude arbitrary entity fields and infrastructure details. Existing Permission choices are
bounded, deterministic and honestly paginated if needed; do not label a truncated choice list complete. Selected
IDs are revalidated on mutation, irrespective of what the earlier list showed. Reads perform no repair, audit write
or business event. Missing binding retains the original ID and an explicit marker, never a same-name substitute;
storage/malformed-state failure is not ordinary absence.

Dispatch `SetFeaturePermission` and `SetFeatureStatus` through the existing Common/package composition. Consumer
orchestration is justified only for actual authorization, confirmation and readiness policy; no forwarding aliases,
copy of Feature policy, vendor patch, hidden repository/audit behavior or outer/nested transaction. Each handler
owns its canonical transaction. Separate commands do not supply an atomic two-field edit: expose distinct confirmed
operations using freshly observed revisions rather than a misleading combined Save.

Require stable Feature/Permission IDs, strict status and positive expected revision. TASK-00291's final full-state
comparison and transaction-duration reference fences apply to actual edits and valid no-ops. Identity/name never
change; a valid no-op advances no revision and publishes no change fact. Rebinding and Permission removal cannot
both win. Qualify fresh reads after other writers, rollback and reused ORM instances; use a fresh valid invocation
when a failed transaction closes its EntityManager. Preserve existing lock order and applicable cohort participation.

Before leaving ON for PREVIEW/OFF, show an accessible warning and require explicit intent bound to the current
actor, Feature ID, requested transition and revision. Cancellation dispatches nothing. A stale conflict requires
rereading and reconfirming the still-intended dangerous transition, not replaying an old checkbox/command. Enabling
PREVIEW/ON, changing a PREVIEW audience or repairing an active broken binding may admit new requests: require the
qualified safety boundary below, not just a valid selected Permission or the browser's confirmation.

### Readiness and active-repair hold

This TASK remains `needs-info` until its consumer composition has an accepted, supported answer for:

1. **Trusted rollout scope:** How a management operation obtains and validates the actual code/target identity,
   applicable entry coverage and fresh preparation/current-policy observations under the protected operator
   boundary. TASK-00292 supplies a scoped read observation, not deployment authority or a durable certificate.
   A management Permission, caller-supplied source hash, previous build or stored Boolean cannot supply this trust.
2. **Safe active repair:** How the intended binding repair is qualified before it can restore PREVIEW/ON access,
   without requiring the already-broken pre-state to pass preparation or committing a live repair and checking
   afterward. The two package setters do not constitute an atomic repair-and-status operation; status changes
   also validate bindings, so an assumed OFF-first workaround is not established support.

Own and resolve these questions within this bounded management outcome using existing suppliers. Record the
chosen supported mechanism, trusted participants and race/currentness limits before marking ready; if it requires
a missing upstream seam, obtain separate owning-package authorization and qualified release rather than patching
or bypassing the handlers. These are unqualified integration guarantees, not demonstrated exploits. Unknown scope,
coverage or repair safety refuses the affected change with a truthful hold. Do not add an unmapped TASK ID, new
readiness platform or finished AI-provider journey as a reverse prerequisite.

TASK-00293 supplies HTTP enforcement. TASK-00294 is required where an actual alternative admission path uses its
registered non-HTTP/Agent boundary, not as a blanket dependency for human-only management. TICKET-00077 must map
and qualify all its actual paths before rollout. OFF stops new/regenerated AI proposals, not authorized inspection,
cancellation or recovery of admitted attempts. Changing the flag grants no template/provider authority and cannot
silently replay paid requests. Manual editing/publication remains independent; product integration is TICKET-00077's.

### Browser state and uncertain completion

Use TASK-00296's catalog owner and existing sole `/me`/private-data generations. Gate presentation and activation
by current ordinary management authority; retain accessible empty/loading/denial/repair/conflict/unavailable states.
After a setting/binding command completes or its outcome is uncertain, invalidate affected catalog/detail/private
data before bounded refetch. Fence old successes and errors; they cannot revive drafts or terminate a newer login.
Do not patch availability from a command/event, persist business drafts, broadcast authority or replay a mutation.

The inspected setters return `void` and publish best-effort events after commit. Lost acknowledgement or event
publication failure does not prove rollback; a later matching row does not establish this operation's original
outcome. Show uncertainty and current observations separately. Do not create an outcome ledger/outbox or promise
eventual notification merely to handle these setters. Sanitize `CommandFailedEvent` command/error-bearing context
and HTTP/log diagnostics; never expose SQL, private configuration or arbitrary throwable text.
