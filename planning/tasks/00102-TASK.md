# Cut over Planning authority atomically

## Outcome

An authorized human can invoke one explicit operation that revalidates an approved immutable source, atomically imports its complete baseline into the empty authoritative PostgreSQL target and changes the Repository from Markdown-authoritative to database-authoritative Planning, or leaves all authority unchanged.

## Scope

- In scope: `CutOverPlanningAuthority`/`PlanningAuthorityChanged`; cutover preview/readiness and exact human confirmation; final source/manifest/mapping/approval/importer/schema/target/configuration/context/mode revalidation; production baseline stream/constraint/projection/order import through TICKET-00026/27 contracts; complete final projection/render/canonical-queue validation inside/against one canonical transaction; authority-mode revision/current state and migration provenance; context invalidation; write fence/freeze state during operation; idempotency/expected revisions; induced rollback; narrowly explicit pre-first-database-write recovery/discard operation; first database-authoritative write marker/fence; PostgreSQL concurrency/audit/API/Permissions.
- Out of scope: Scheduled/agent-only cutover, dual write, source modification/deletion, best-effort/partial import, warning waiver, reverse migration after database writes, automatic fallback, browser UI, backup implementation, retirement branch/PR and migrating a real Repository in this implementation TASK.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Preview final cutover | N/A — read-only validation | Revalidate approval/source/target/mode and explain exact imported state/impact | N/A — preview emits no event | Human sees current readiness and recovery boundary without mutation |
| Cut over authority | `CutOverPlanningAuthority` | Revalidate every exact approved fact and final imported projections/queue | Baseline aggregate events plus `PlanningAuthorityChanged` in authority history | Complete baseline/current constraints/projections/mode commit atomically; source remains unchanged |
| Recover before first database write | Explicit guarded recovery/discard command | Prove exact CutoverId, untouched source, no post-cutover Planning command and recoverable state | Type-specific authority recovery evidence | Imported cutover state is discarded and Markdown authority restored only before any database-authoritative mutation |
| Refuse late rollback | N/A — rejected recovery | Show first-write boundary and forward-repair/backup guidance | N/A — rejection emits no Planning event | No reverse migration or automatic fallback occurs after database-authoritative work starts |

## Validation and permissions

Require registered/Markdown-authoritative mode, active Repository, current designated source/context and a current TASK-00101 approval. Re-read the clean committed source and require exact manifest/commit/tree/digests. Revalidate mapping/report/importer/event/projection/template/queue schemas, target identity and complete emptiness, Repository/configuration/context/authority revisions, approval/confirmation/Permission and absence of a competing cutover/freeze. Any change or warning blocks before authoritative effect.

Acquire a Repository Planning-authority write fence that rejects both Markdown-authoritative application mutations and database-authoritative Planning commands during the bounded operation. Do not claim to stop an operating-system user from editing files; before commit, repeat source Git/tree/digest observations and abort if changed. No scheduled switch, dual writer, separate follow-up mode transaction or agent-only trigger exists.

In one canonical PostgreSQL transaction, append every self-contained baseline event with migration provenance, populate command-critical constraints/current projections/order, validate rebuild-equivalent state/render/canonical queue, record CutoverId/import mapping/approval provenance and change mode to registered/database-authoritative. If full rebuild/comparison cannot safely occur inside the transaction, stage deterministic transaction-local state and validate before commit without exposing it. Any exception/mismatch rolls back streams, constraints, projections, migration authority and mode together.

Human confirmation binds user, Repository/CutoverId, source/approval/mapping/report/target/current revisions, impact, recovery boundary and short expiry. Cutover Permission is distinct from preview/approval and cannot be delegated to the migration process. Exact command retry resolves its prior result; competing cutovers permit one accepted operation.

After commit, all pre-cutover context bindings become stale and new registered contexts resolve database mode. Preserve tracked source untouched. WF-011 permits one narrow explicit recovery only while a durable authority fence proves no database-authoritative Planning mutation has committed since cutover; recovery atomically discards only this CutoverId's imported authority and restores exact Markdown mode. The first accepted database Planning command permanently closes that recovery path. Thereafter use database backup/restore and forward repair only—never automatic fallback/reverse import.
