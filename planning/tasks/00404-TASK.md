# Withdraw starters and resolve conflicts without losing attempts

## Outcome

An authorized operator withdraws or archives a starter and explicitly resolves changed-release conflicts while
actual creation attempts retain their pinned source. Catalog changes affect future availability, not trusted
historical bytes or existing generated projects.

## Scope

- In scope: Protected API/console lifecycle/conflict inspection and expected-state operations, attributable
  explicit resolution, actual creation-attempt reference/hold integration, competing selection/withdrawal safety.
- Out of scope: Source releases/edits, rewriting installed snapshots, general archive/purge service, automatic
  compensation, project upgrades, creation attempt transitions, preview wizard and a new retention platform.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Withdraw/archive entry | Exact current-authorized lifecycle change | Current entry/generation, eligibility and retained references | Committed availability/lifecycle facts | New admission closes; historical snapshots/attempts remain intact |
| Inspect a changed release | N/A — read-only | Original and observed identity/digest evidence, uncertainty and current references | N/A | Bounded safe conflict explanation without fetching or resolving it |
| Resolve known conflict | Explicit bound operator decision or normal newer-release installation through TASK-00402 | Exact old/new evidence, current authority and expected generation | Attributed resolution/successor facts | Future selection changes only after verified eligibility; old evidence remains |
| Protect an actual attempt | Shared reference/hold participant invoked by attempt owner | Exact pinned snapshot, original attempt and current eligibility | Committed reference/hold facts | No missing protection between admission, withdrawal and snapshot use |

## Validation and permissions

TASK-00411 now supplies the exact independently deliverable creation-attempt admission/reference participant.
Only the allocation hold is resolved; ready metadata remains blocked by unfinished suppliers, including that
participant's preflight holds and TASK-00402's real-release prerequisite. Actual participant integration remains
mandatory, not a requirement to finish the browser, all generation stages or the complete create/register journey. TASK-00402's early pin/reference/eligibility fences precede that participant; neither it
nor early admission depends on this completed lifecycle consumer. Full lifecycle acceptance needs actual producer
composition, not a fabricated attempt table or injected ID advertised as runtime evidence.

Require separate current lifecycle/resolution/read authority, exact Workspace/source/entry, complete expected state
and bounded original operation identity. Archived, deliberately removed or withdrawn entries are unavailable to
new attempts; naming a retained snapshot does not bypass this rule. Reject stale or changed-away-and-back generations
and inaccessible references without leaking hidden attempt details or treating denied reads as no references.

Coordinate actual admission, current selection, install/refresh completion, lifecycle transitions and reference
writes on the shared PostgreSQL connection with deterministic ordering/fencing. If admission wins it must durably
pin and protect the exact bytes; if withdrawal wins, new admission rejects. No query-check/write gap, nested commit
or late install completion may reopen withdrawn availability. Preserve references required by active or failed
attempts. Unknown ownership, incomplete participant coverage and uncertain operation outcomes preserve content and
hold affected changes rather than infer it is unused. Cancellation/cleanup and stage progress remain with attempt
owners; no terminal or failure label alone permits deletion.

A previously known tag changing commit or archive digest is a real conflict, not an opportunity to overwrite the
trusted snapshot or silently relabel new bytes. Resolution must bind the exact contradictory evidence and record
the operator, rationale, authority and expected state. A newer stable release follows TASK-00402's normal validation.
Any explicitly permitted acceptance of changed evidence creates distinct immutable successor provenance while
preserving original references; it cannot erase the conflict, mutate old bytes or bypass manifest/source/digest
checks. Unknown or unsupported resolution remains held, not repaired by a broad fetch/rebaseline.

New releases and profile selections apply only to future operations. Already pinned attempts retain their exact
source/provenance; independently changed authority or safety constraints are still checked by their owners. Never
modify generated directories, Git history, projects, selected branches, remote repositories or Planning records.
No automatic compensation deletes snapshots, registrations or profile revisions. Physical removal is outside this
slice; conservative preservation is an honest result, not a claimed storage reclamation or complete erasure.

Commit state, audit and original outcome atomically. External retrieval needed for a new installation stays with
TASK-00402's explicit committed operation, outside transactions; ordinary conflict/reference reads never fetch,
retry, repair or publish. Expose safe bounded original/current facts through protected API/console paths, keeping
raw private source content, provider errors and credentials out of metadata and diagnostics.
