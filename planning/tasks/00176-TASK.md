# Inspect running applications for fresh judgments

## Outcome

An authorized Pi 1.1.0 caller can inspect a separately qualified local or production application through declared
bounded read-only diagnostic capabilities and ask typed questions about fresh observations. Evidence identifies
the actual target deployment and observation time; a local checkout or old receipt cannot stand in for production.

## Scope

- Extend [TASK-00174](00174-TASK.md)'s authenticated composition path with specifically qualified running-application
  inspection capabilities. Reuse caller propagation, current authority, budgets, execution guards where applicable,
  evidence receipts and shared evaluation. Keep repository static analysis and Agent-controlled SQL in their own
  TASKs; neither TASK-00175 nor TASK-00177 is a dependency for ordinary application diagnostic inspection.
- Accept an operator-configured environment/application target, a declared diagnostic capability with constrained
  arguments and typed questions/preset. Resolve the target through protected configuration and actual repository/
  application association. No arbitrary host/URL, endpoint, remote command, debugger evaluation or shell access.
- Deliver useful read-only application diagnostics through existing maintained operations or a justified owned
  inspection adapter where no equivalent exists. Exact permission/capability and target mapping must be qualified
  before activation. An API name, read-looking method or diagnostic label alone does not establish harmless effects.
- Qualify local and production target profiles independently: intended read-only effects, permitted endpoints,
  protocol identity, redirects, credentials, environment scope, resource impact, data sensitivity and cancellation.
  Protected credentials must be scoped to inspection, not an ambient administrative identity. Unsupported/unconfigured
  environments stay unavailable. Planning and local qualification do not enroll or grant production access.
- Recheck caller and target authorization for every request and before result/reference disclosure; retain actual
  Agent/assignment scope where it exists. Verify the contacted application/environment and available deployed
  revision/build identity using authoritative observations. Reject target mismatch; record unavailable revision
  identity explicitly and do not make a source-specific conclusion requiring an identity that was not established.
- Record actual observation time, target/environment/deployment identity, capability revision, freshness and any
  response/cache limitations. Obtain fresh observations by default with the owning API's qualified freshness
  behavior; historical receipt inquiry remains explicit. A service cache or missing timestamp cannot be reported
  as a confirmed current snapshot, and independent observations are not automatically one atomic state.
- Require finite profile bounds for calls, elapsed time, concurrency, response/retained-evidence size and resource
  impact, within TASK-00174's aggregate budget. No unbounded log tail, subscription, paging or polling. Oversized,
  incomplete, stale or unavailable diagnostics return explicit coverage/status, never an assumed healthy result.
- Restrict inspection to its qualified read-only effects. Operations such as restarts, repair, cache flush or
  configuration changes remain ordinary separately authorized command capabilities and cannot be smuggled into a
  diagnostic request. Detect capabilities exposing Agent-controlled SQL and require TASK-00177's SQL boundary;
  ordinary application queries may use the primary under their existing domain authority.
- Minimize/filter sensitive diagnostic data before evaluator input and apply independent provider-disclosure
  policy. Authorization to inspect production does not authorize exporting its data to Jev. Protect receipts and
  exact diagnostic output in the owning evidence facility with bounded storage/retention and current reference
  access; ordinary logs and main-Agent responses contain compact metadata, not raw logs, secrets or customer data.
- Preserve explicit invalid/unavailable/unknown/incomplete outcomes and typed choice/score semantics. Return actual
  environment/revision/time, permitted evidence references and coverage with classifications. Jev cannot assert
  the application was repaired, deployed, verified healthy or correctly functioning beyond observed evidence.
- On stop/reload, revocation, budget exhaustion or target change, stop dependent work, cancel only owned requests
  through qualified controls and reject late delivery. Do not retry diagnostics automatically or launch corrective
  commands when evidence is absent. Retain operation and provider usage uncertainty through the shared contract.
- Exclude production access grants, enrollment/deployment, arbitrary remote execution, raw SQL, production-data
  fixture extraction, automated remediation and broad telemetry/browser platform delivery.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Inspect a selected application | Admit a bounded diagnostic invocation | Current target/caller authority and qualified read-only observations | Inspection completed/partial/failed observations | Bounded authorized request load; no domain mutation |
| Judge current observations | Submit minimized disclosure-permitted evidence | Typed questions plus actual environment/revision/time and coverage | Judgment completed/unavailable observation | Bounded provider usage and protected evidence references |
| Inspect a historical run | N/A: read an existing authorized receipt | Recorded target/time/result and current evidence access | Existing access observation where applicable | No new request or claim of current application state |
| Cancel or reject a changed target | Cancel owned request/stop dependent work | Actual generation, target and receipt state | Cancelled/stale/mismatch observations | Qualified request cancellation; no corrective operation |

## Validation and permissions

Use TASK-00174's verified caller context without substituting service credentials for the actor. Both operation
permission and exact repository/environment scope must hold, including for metadata and raw-evidence inspection.
Protect target selection against user-controlled redirection and source-contained instructions. Use the owner's
business rules for ordinary queries; do not copy policy into diagnostic adapters. Data access and provider egress
are independent. Unknown deployment identity/freshness remains an explicit limitation rather than inferred from
local files. Missing required production readiness blocks only that target and its acceptance claim.

## Acceptance criteria

- [ ] Actual Pi 1.1.0 local application inspection through the shared MCP path yields useful fresh typed judgments
  with verified target and available deployment/revision/time provenance.
- [ ] Production-capable integration is separately qualified against its real authorized target profile; unavailable
  production access or identity evidence remains an explicit outstanding acceptance item, not simulated live proof.
- [ ] Forged/revoked/cross-environment authority, target mismatch, unapproved redirects/capabilities and attempts at
  mutation/SQL/remote execution fail without falling back to privileged credentials or another environment.
- [ ] Finite call/time/concurrency/output/resource bounds and qualified cancellation hold. Partial, cached, stale,
  unavailable and mixed-time evidence cannot become a fabricated current complete observation or healthy result.
- [ ] Separate egress policy prevents unauthorized data disclosure; result metadata is compact and redacted, while
  exact diagnostic access requires current authorization to its protected reference.
- [ ] Stop/reload, target changes and late responses do not trigger unwanted retries, repairs or stale delivery;
  representative inquiries report useful coverage, uncertainty, available total cost and latency.

## Verification and evidence

Test owned target/capability admission, authority, observation identity/freshness, output filtering, limits and
lifecycle behavior. Qualify the actual diagnostic adapter and Pi/MCP path directly against authorized controlled
application environments, retaining the distinction between local, simulated deployment and real production
observations. Production use requires its separately applicable authorization; leave missing evidence outstanding.
Do not add product tests of network/configuration wiring, wrappers or test infrastructure. Run applicable focused
backend checks, `./bin/harness-check` and canonical `./bin/build`; record direct exits, tested-content identity,
exact target/profile/runtime/evaluator and redacted receipts under `.runs/tasks/TASK-00176/`.
