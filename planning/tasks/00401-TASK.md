# Administer the scoped starter catalog

## Outcome

An authorized administrator can register, revise and inspect Workspace starter entries through protected API/console
operations without downloading source or implying that an entry is an eligible installed release. This supplies
truthful catalog administration and selection inputs for the accepted project-creation journey.

## Scope

- In scope: Managed/custom catalog identity, source locators and revisioned metadata, five initial managed entries,
  protected administration and bounded safe queries, explicit unverified/unavailable reasons and original outcomes.
- Out of scope: Snapshot retrieval, source authentication, manifest execution, release publication/certification,
  lifecycle/conflict resolution, profile associations, creation wizard, project generation and a general registry.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Register or revise an entry | Intent-specific catalog operation with complete expected state | Current scoped entry, canonical source locator and conflicts | Committed catalog identity/revision facts | Owned metadata and audit commit together; no GitHub or filesystem effect |
| Establish managed entries | Explicit bounded installation/catalog operation | Existing entries and original setup outcome | Committed entry facts only for genuine changes | Preserve existing custom/history data without recurring source overwrite |
| Inspect catalog choices | N/A — read-only | Authorized bounded entries, provenance, installed-release status and unavailable reasons | N/A — browsing changes nothing | Safe exact inputs for downstream selection, never implicit installation |
| Inspect an uncertain change | N/A — read-only | Original operation and current revision distinguished | N/A | Original result or unresolved status, not automatic replay |

## Validation and permissions

Consume TASK-00078's initial typed Workspace identity without registering a new Repository for a starter entry.
Starter source identity, eventual generated Repository identity, display name and URL remain distinct. Generate
owned identities through the owning factory/UUID library. Apply ADR 0001 ownership and existing Access Control
policy; current operation-specific catalog administration and read permissions are checked on every supported
entry path. A Workspace administrator label, source URL, shell access or client actor ID is not permission.

Register the accepted managed sources under `johnnickell`: `project-symfony`, `project-slim`, `project-laravel`,
`project-yii` and `project-codeigniter`. Managed origin grants no certification or exemption from snapshot rules.
Custom public/private GitHub entries use the same catalog contract; other providers are unsupported. Validate
bounded canonical GitHub locator forms, uniqueness and expected state. Reject embedded credentials, arbitrary
network destinations, malformed/ambiguous sources and cross-scope disclosure. Retain verified provider-native
identity from the installation owner separately from an unverified configured locator; renames or name reuse
cannot silently substitute a source. Inaccessible/unverified entries cannot be advertised as selectable releases.

This operation stores safe configuration, not proof of source access. TASK-00402/00403 establish actual source
identity/access and installed eligibility. Catalog reads never fetch tags/archives, authenticate, refresh, repair
or invoke a model. Until those suppliers exist, report unavailable rather than return demonstration releases.
Selected-source changes invalidate availability through expected-state/generation fencing, never rewrite retained
snapshot provenance or active references. TASK-00404 owns explicit withdrawal and changed-tag resolution.

PostgreSQL enforces identity/source uniqueness and coherent current state using the canonical shared transaction.
Commit catalog revision, original operation/outcome and required bounded audit together. Compare complete expected
state and monotonic selection generations, including changed-away-and-back cases. Repetition of managed setup
preserves custom entries, later authorized revisions and history; collisions/partial setup require explicit
resolution, not a reset. Keep current-state/reference participants compatible with TASK-00402's later pinning;
no future consumer transaction may rely on a stale availability query alone.

Expose one protected Action per HTTP interaction with safe bounded Views, stable pagination, validation, JSend,
OpenAPI and sanitized errors. Supported console operations enforce the same authority, not an internal bypass.
Never expose provider credentials, raw errors or hidden catalog counts/names. Browser creation presentation stays
with TICKET-00101; no new browser administration product is required by this slice.

## Acceptance criteria

- [ ] Authorized managed/custom registration, revision and inspection retain exact scoped identities and truthful
  availability; the five managed entries are not falsely described as released, installed or certified.
- [ ] Denied, malformed, duplicate, ambiguous and stale operations fail without partial state, hidden disclosure,
  source retrieval, automatic authentication or project/source mutation.
- [ ] Real PostgreSQL competing revisions/setup and rollback preserve complete state/audit/original outcomes;
  repeated setup cannot overwrite custom/history content or reset later selections.
- [ ] Bounded API/console queries expose safe provenance and genuine unavailable reasons without provider effects;
  source changes cannot substitute pinned snapshots or imply Repository, Agent or execution authority.
