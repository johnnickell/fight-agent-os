# Create and qualify a Pi skill for on-demand architecture diagrams

## Outcome

A user can explicitly ask Pi to show a focused diagram of a named existing feature, source area, or proposed
change. The skill renders a source-linked Python Diagrams view inline when the active terminal supports it, with
a usable browser preview when inline display is unavailable or unsuitable.

## Scope

- In scope: Add a project-local `.pi/skills/show-me/SKILL.md` with a narrow explicit trigger and add it to
  `.pi/skills/_index.md`. Follow the shared Python Diagrams source and rendering contract from TASK-00549. Read
  only the selected feature or proposed scope; choose only the useful class/layer, dependency, runtime/data-flow,
  before/after, or system-context view. Label the source revision, provide source links or exact paths, and state
  uncertainty, omissions, and any limitation in representing class ownership. Mark proposed relationships as
  proposed and separate them from current source. Write temporary diagram source and preview output under
  ignored `.runs/` scratch. Qualify the skill in an actual installed Pi session, recording the observed Pi version
  as evidence and exercising a browser fallback when inline image display is unsupported or unsuitable.
- Out of scope: Replacing or duplicating the existing architecture analysis skill, whole-repository graph
  generation, durable feature documentation or PR edits, application source changes, persistent Git changes,
  external rendering or service uploads, global dependency installation, and Pi version pinning.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Show an existing feature | Explicit `/skill:show-me` invocation for a bounded feature or source area | Read selected source and documentation, ownership guidance, and current revision | N/A — no application or workflow event | Create temporary Python diagram source and rendered image under ignored `.runs/`, then display the focused view |
| Show a proposed architecture change | Explicit `/skill:show-me` invocation with the proposed diff or accepted design context | Read the exact proposed scope and current source it affects | N/A — no application or workflow event | Display a view labeled proposed and distinguish proposed relationships from current implementation |
| Explain a display or evidence limit | Existing skill invocation | Check the supported renderer, inline display behavior, browser preview availability, and source completeness | N/A — no application or workflow event | State what is unavailable or uncertain and use the supported fallback when suitable |

## Validation and permissions

Apply the repository Writing for Agents guidance. Directly validate skill metadata, index entry, relative links,
and routing against a normal existing-feature request and a proposed-change request. Qualify actual image display
in the installed Pi session; use and inspect a browser preview when inline display is unavailable or unsuitable.
Record the observed Pi version without making it an equality gate or future compatibility guarantee. Confirm
temporary artifacts are inside ignored `.runs/` and source, durable docs, Git state, PRs, and external services are
unchanged. If renderer or display capability is unavailable, report that limitation without installing global
dependencies, uploading source, or claiming an unrendered view was verified. No application commands, queries,
events, or permissions apply. Do not add product-suite tests for the skill or rendering infrastructure.

## Acceptance criteria

- [ ] A project-local `/skill:show-me` exists, is indexed, and has a narrow explicit trigger for a bounded existing or proposed architecture view.
- [ ] An existing-feature invocation renders a readable Python Diagrams view labeled with its source revision and linked to the represented source.
- [ ] A proposed-change invocation labels proposed relationships and distinguishes them from current implementation.
- [ ] The skill selects only useful views, states uncertainty and omissions, and reports a class/layer representation gap rather than showing a misleading diagram.
- [ ] An actual installed Pi session demonstrates inline display when supported and a browser preview when inline display is unavailable or unsuitable; the Pi version is recorded only as evidence.
- [ ] Temporary output stays under ignored `.runs/`; the on-demand skill changes no application source, durable documentation, Git state, pull requests, or external services.

## Verification and evidence

Use the shared renderer established by TASK-00549 and exercise a representative existing-feature request and a
proposed-change request in an actual installed Pi session. Inspect rendered output, source links, revision and
proposed/current labels. Verify inline display and the browser fallback when needed, and record the Pi version,
renderer availability, artifact locations, results, and limitations. Run `./bin/planning-check --write`,
`./bin/planning-check`, and `git diff --check` when planning records change. No product-suite tests or application
build are required for this skill and workflow outcome.
