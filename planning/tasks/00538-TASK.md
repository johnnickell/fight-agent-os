# Keep installed workspace child activity and runtime logs portable across repositories

## Outcome

An operator can use the installed Fight workspace harness from different repositories and their registered
worktrees on one host. The child activity pane follows the actual session's authorized Build children, and
the logs pane discovers matching containers even when they start after the workspace. This repairs the
existing workspace journey delivered by TASK-00502, TASK-00511, TASK-00512 and TASK-00535.

## Scope

- In scope: portable provider/monitor identity across installed package and source skill locations; automatic
  child association; useful bounded observation failure diagnostics; exact-checkout Docker log discovery and
  recovery as containers appear, stop, restart or are replaced; directly affected packaging, instructions and
  owning Harness regression checks.
- Out of scope: application business features, new execution authority, arbitrary process/log attachment,
  remote hosts, global installation changes, changes to unrelated repositories or running user sessions,
  merge, release and deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Run Build from a different repository using the installed harness | Existing workspace and provider stage-monitor commands | Verify actual parent, provider and monitor identities | Existing safe child progress | Human-only child pane displays the current session's eligible child without per-child setup |
| Start matching containers after opening the workspace | Operator independently starts the intended runtime | Bounded repeated local Docker discovery and ownership verification | Container availability and generation changes | Log pane automatically attaches to an unambiguous eligible source |
| Change selected child/worktree or replace a container | Existing child selection/pin and log controls | Revalidate current context, mounts and container identity | Selection and lifecycle changes | Release obsolete readers and clear stale output before following the verified replacement |

## Validation and permissions

Preserve exact native ancestry/lifetime, provider ownership, current-session identity and registered worktree
checks. Preserve the accepted trusted-local-process limitation; portability must not turn arbitrary paths or
editable metadata into observation authority. Log discovery remains local and read-only, verifies exact source
mounts, never starts Docker or containers, and never falls back to another checkout. Ambiguous sources retain
readable selection. Manual close/pause/cancel choices must not be undone by background discovery. Observation
failure cannot change execution, results or responsiveness; logs and transcripts never enter model context.
No database, HTTP permission, domain command or migration changes apply.

## Acceptance criteria

- [x] Reproduce the installed-package/source-monitor mismatch with a failing owning Harness regression before
  repair, then demonstrate automatic activity using an installed-layout package and a separate target Git
  repository, including its registered worktree. No provider checkout-relative assumption or copied target
  skill is required; explicit trusted package selection is honored consistently.
- [x] Current-session children appear without a manual observation socket or relaunch. Unsupported, stale,
  mismatched and unrelated children remain unavailable, with a useful safe diagnostic where determinable.
- [x] With no matching runtime at workspace startup, starting an eligible container later automatically
  populates logs within a documented bounded interval, without pressing retry or reopening the workspace.
- [x] Stop/restart/replacement and delayed Docker availability recover through fresh ownership and generation
  checks; ambiguity, wrong-checkout mounts and lost child authority cannot expose an unrelated source.
- [x] Switching or pinning children follows the correct worktree, clears stale output and bounds concurrent
  readers and discovery work. Explicit reader closure and cancellation remain respected.
- [ ] Direct Harness checks cover repaired behavior and failure paths; fresh independent Review and behavioral
  QA exercise installed-layout portability and late container startup. Applicable terminal captures are
  inspected and limitations reported under the shared QA policy.
- [x] Planning checks, diff checks and the complete canonical `./bin/build` pass with warnings disclosed.
