# Record completion notices without losing the original recipient

## Outcome

Successful package confirmation atomically creates one separate completion-notice intent for the original old
mailbox while consuming the exact credential, promoting the reserved address and invalidating sessions. Neither
a changed current address nor a later grant can change the notice's recipient or attribution.

## Scope

- In scope: Supported confirmation/notice coordination, immutable original-recipient/generation linkage,
  completion-stage uniqueness, required audit and PostgreSQL rollback/concurrency behavior.
- Out of scope: Public link landing/submit, validity-probe API, login/reset, new confirmation policy, provider
  sending, administrator bypass, additional credential or old-mailbox approval/cancel action.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Confirm a current change | Package `AuthenticationService::confirmEmail()` through the qualified seam | Exact current grant/reservation and original-recipient binding from TASK-00274 | Package confirmation fact and distinct owned completion-notice fact after commit | Credential consumption, address promotion, session invalidation, required audit and one completion intent |
| Reject stale or competing confirmation | Same package operation; no consumer substitute | Current owning package authority and exact retained transition | No successful confirmation/notice fact on rejection | No extra notice or partial transition |
| Inspect after lost acknowledgement | Supported restricted original-outcome observation | Exact consumed generation and completion intent, not latest-email inference | N/A for read | Committed or unresolved result without another confirmation/send |

## Validation and permissions

Consume TASK-00273's supported tagged/locked contract, TASK-00274's exact original binding and the package's
credential, lifetime, reservation, User lifecycle and session policies. One canonical shared transaction contains
all required writes. Notice failure must roll back grant consumption, promotion, authentication-authority changes,
session revocation and required audit together. Never reconstruct atomicity with an event subscriber, nested
transaction, audit-repository side effect or copied confirmation service.

TASK-00289's source inspection also found that `confirmEmail()` checks destination equality but does not
explicitly compare the grant's bound reservation revision or call `matchesReservation()`. Qualify exact binding
against the selected supported contract, including same-address successor/ABA and all supported reservation
writers, rather than inferring it from latest-grant lookup or repository CAS alone. This is an unresolved guarantee,
not a reproduced exploit. TASK-00273 owns any required contract/owner resolution; retain the hold if absent,
without copied policy, a preflight outside the transaction or a vendor patch. A discovered bug requires a failing
reproduction before separately authorized repair.

Completion identity is unique for the exact accepted change/stage and distinct from the request-notice identity.
Use owning ID factories/UUID libraries. Resolve the immutable old recipient associated with that change before
promotion; do not use the new canonical address, latest unrelated request, timestamp matching or caller-selected
recipient. Missing, mismatched or ambiguous original binding fails closed and requires owner resolution, not
historical backfill by guessing. Request-notice delivery/retention must not destroy this pending correlation.

Preserve the initiating self/admin actor from the accepted request separately from target and confirmation proof.
A purpose-bound bearer proves mailbox-secret possession, not the original administrator's participation or an
independently authenticated natural person. Record only what package evidence establishes. Confirmation still
requires neither a preexisting session nor a password and issues no tokens. TICKET-00069 owns transport, explicit
user action, non-mutating GET, throttling and client invalidation; this primitive creates no new public entry.

Duplicate/stale/expired/wrong-purpose or cancelled credentials cannot create another completion intent. Concurrent
cancel/expiry/confirm follows package winner semantics; a later same-address reservation must not match by address
alone. Accepted request notices survive cancellation regardless of whether confirmation wins. Delayed notice
sending does not postpone or undo a successfully committed address change/session revocation.

Post-commit publication failure or lost response can occur after success. Do not claim rollback, automatically
reconfirm, issue a new credential or manufacture a success result from absence. Observe exact original state
through qualified safe contracts or report uncertainty. No raw credential, digest, grant material, link, provider
secret or unnecessary address data appears in notice audit, status, ordinary logs or evidence.

## Acceptance criteria

- [ ] Actual package confirmations for self- and administrator-initiated changes retain one distinct completion
  intent for the captured old mailbox, with correct generation and honest requester/confirmation attribution.
- [ ] Controlled PostgreSQL duplicate/cancel/expiry/reservation races have the package-defined winner, no extra
  completion intent, and no surviving partial promotion/session state after required persistence failure.
- [ ] Post-commit process failure leaves the completion notice recoverable; current-email changes and later
  same-address generations do not retarget or miscorrelate it. Missing original binding holds safely.
- [ ] Confirmation, notice intent, notice delivery and login are distinct outcomes. No old-mailbox credential,
  approval action, password requirement, automatic reissue or public validity/mutation path is introduced.
