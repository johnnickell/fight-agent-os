# Deliver shared local HTTPS ingress for main and worktree stacks

## Outcome

Operators can reach main and isolated worktree applications at distinct canonical `<name>.localhost` HTTPS
origins through ONE independently operated shared ingress. This removes TASK-00543's concrete browser-readiness
blocker without waiting for the complete Planning installation. John explicitly approved this narrow extraction
from TASK-00072 on 2026-10-31 while replacing TASK-00543's local Compose lifecycle contract.

## Scope

- Deliver explicit setup/up/down/status/removal operations for one separately owned ingress Compose project:
  public pinned Nginx and separate nonpublic docker-gen, sharing generated configuration. Only docker-gen gets
  the required read-only Docker socket; neither public Nginx nor application/private services get it.
- Own the external ingress network and automatic route addition/removal from actual application gateway metadata.
  Only stack web gateways join it. Private PHP, databases, storage, mail and workers stay private. Strip inherited
  host publishing from proxy-connected stacks. Do not implicitly start/stop application or foreign projects.
- Consume TASK-00543's explicit task Compose project/hostname consumer seam and settle/qualify shared-topology
  integration against the delivered supplier. Main shared-ingress participation must be explicit; ordinary main
  `bin/up` remains the direct `https://localhost:18443` stack without this supplier or generated proxy overrides.
  No reverse dependency on TASK-00543 acceptance; qualified consumer fixtures suffice.
- Extend/reuse TASK-00145's explicit certificate tooling for actual main/worktree names. Trust enrollment,
  certificate generation and privileged port binding remain explicit human operations; no custom DNS/hosts setup.
- Standard local ports 80/443, canonical HTTPS and distinct exact origins. Preserve the application's direct TLS
  authority: qualify encrypted proxy-to-application gateway transport, exact Host/port, secure cookies and actual
  available auth flows. Never promote arbitrary forwarded headers or weaken security to make the proxy work.
- Out of scope: full installation provisioning, TASK-00066 foundation completion, SeaweedFS/Redis/Mercure/Runner
  provisioning, custom DNS, production deployment, wildcard preview orchestration, global install/reset/prune,
  automatic CA trust and unrelated application behavior.

## Validation and permissions

Inventory existing shared ports/projects before effects. Bind only explicit ingress resources. Fail clearly on
missing tooling, unavailable ports, invalid/missing/expiring actual-name leaves, unknown configuration or failed
readiness. Keep secrets/private leaves ignored under `var/` and out of reports. Do not collect privilege passwords,
change hosts/DNS/trust implicitly, run migrations or infer success from container/config creation. Read-only socket
mount reduces exposure, not Docker API authority; document that risk. No browser/application permission grants
infrastructure mutation. Dependency setup remains explicit.

## Acceptance criteria

- [ ] One independently operated pinned Nginx/docker-gen project supplies ingress; only docker-gen has a read-only socket.
- [ ] Main and TWO worktree full stacks have distinct `<name>.localhost` canonical origins and actual-name certificates.
- [ ] Only app TLS gateways join ingress; no private service or inherited task host publishing becomes public.
- [ ] Real TLS verification, exact canonical authority, Secure/HttpOnly/SameSite cookies and available authentication
  succeed; wrong authority/origin, insecure transport and spoofed forwarding remain denied.
- [ ] App commands print usable URLs only after real readiness; missing task/shared-ingress prerequisites and
  partial failures are explicit. Ordinary main up works without ingress; task down/repeated teardown do too.
- [ ] Task teardown removes its route without disrupting main/other task/shared ingress; repeated cleanup is harmless.
- [ ] Explicit ingress/certificate status/down/removal and recovery are exercised without foreign cleanup or implicit trust/DNS.
- [ ] Direct owning-tool evidence and final canonical build pass; independent Review/QA remain required.
