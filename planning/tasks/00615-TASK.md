# Run Pi Harness verification as a standalone pass

## Outcome

Verify the Pi Harness and vendored engine locally or on GitHub without preparing or starting the application stack.

## Scope

- Extend `./bin/harness-check` and reuse the owning Harness and vendored engine checks rather than creating parallel suites. Account for Harness tests, engine lint, type checking and tests, and applicable packaging and native checks.
- Demonstrate the pass in the prepared local tooling container and through direct owning commands on a GitHub runner without containers. Keep preparation explicit and preserve existing isolation. List native or live-provider qualification that must be performed separately.
- Keep Node and TypeScript for checks and probes where they fit; there is no requirement to rewrite checks in PHP. Do not change role authority, pin Pi, rewrite the engine, or add installation or publication effects. Shared input selection, pass receipts, and required-check cutover belong to [TICKET-00149](../tickets/00149-TICKET.md).

## Acceptance criteria

- [ ] The local route and GitHub invocation complete without the application stack; the hosted route starts no container.
- [ ] Verification accounts for existing Harness and engine checks, including packaging contents and attribution. Separately qualified native or provider behavior is not reported as passed by routine CI.
- [ ] Local checks preserve checkout isolation and do not install dependencies during verification. The pass does not change session or checkout authority.

## Verification and evidence

Record the inventory, exact local and hosted commands, results, tested Pi capabilities, and any unverified checks. Use owning commands and applicable native probes rather than product tests of check machinery. Hand off to independent Review and applicable QA.

## Coordination

No prerequisite TASKs. The standalone pass can initially retain its current dependencies, but it is not Python-free until [TASK-00616](00616-TASK.md) and [TASK-00617](00617-TASK.md) are verified. Planning approval does not select a checkout or authorize implementation or publication.

## Completion notes

Implemented a standalone Harness pass. `./bin/harness-check setup` builds the checkout's tooling image,
`./bin/pi-dependencies setup` prepares locked Linux dependencies, and `./bin/harness-check` checks them
without installing or pulling. The local pass exited 0 on Linux arm64 (Node 24.22.1, npm 11.19.1,
Git 2.56.1, Python 3.11.2). `./bin/runtime inspect` showed no containers, volumes or networks for
`fight-wt-3d6d3b941a52` before and after; no application runtime or ingress was prepared.

- Harness: 332 passed, one macOS-only custody case skipped. Engine: lint checked 195 files, types passed,
  and 125 test files reported 2,550 passed and seven live-provider tests skipped. The 145-file npm archive
  contained the runtime entries, docs and both licenses, including tintinweb's MIT attribution; no tests,
  check scripts or installed dependencies were shipped.
- The GitHub job prepares dependencies with `node harness/pi/scripts/dependencies.mjs setup` and then runs
  `sh harness/pi/scripts/check.sh` on Ubuntu with Node 24 and no containers. The same commands passed on a
  private macOS copy with Node 22.23.1/npm 12.2.2 (`CI=1`), including all 333 Harness tests, the same
  engine counts and package inventory. That was not a hosted run. An authorized draft PR to `develop` (or
  `main`) with this candidate must trigger the **Pi Harness pass qualification** workflow and supply the
  exact-head hosted result.
- The separate installed Pi 1.6.0 SDK module-loading probe passed six scenarios and 229 assertions without
  credentials or provider requests. It covered package and explicit loading, deduplication, command/flag/tool

  stage, Herdr and visual probes and live providers were not qualified by this work.
